<Note>
  **Tidak ada instruksi init-tick-array, dan tidak ada yang diperlukan.** Tick array dibuat *di dalam*
  `OpenPosition*` / `IncreaseLiquidity*` oleh `TickArrayState::get_or_create_tick_array`, dibayar oleh
  `payer`. Lewatkan PDA tick-array (mungkin masih belum diinisialisasi, milik sistem) sebagai
  `tick_array_lower` / `tick_array_upper` dan program mengalokasikannya jika hilang.
  `OpenLimitOrder` melakukan hal yang sama untuk `tick_array` tunggalnya.
</Note>

Sebagian besar instruksi admin-only (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) dijaga oleh pubkey `admin` yang dikodekan keras dalam program. `CreateSupportMintAssociated` / `CloseSupportMintAssociated` menerima pubkey `admin` **atau** kunci pemilik support-mint khusus; `CollectExcessLamports` menerima pubkey `admin` **atau** dompet collect-lamports khusus. Instruksi admin aliran reward (`TransferRewardOwner`, `CollectRemainingRewards`) dijaga oleh pendana reward, bukan admin program.

Akhiran V2 berarti "mendukung Token-2022 di vault / NFT, memerlukan slot bitmap-extension". SDK memilih V2 secara default untuk pool baru.

## `CreatePool`

**Argumen**

```
sqrt_price_x64: u128           // harga awal
open_time:      u64            // swap ditolak sebelum waktu ini
```

**Akun (ringkas)**

| # | Nama | W | S | Catatan |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Tier biaya yang dipilih. |
| 3 | `pool_state` | W |   | `init` di sini. |
| 4 | `token_mint_0` |   |   | Diurutkan. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` di sini, dimiliki oleh PDA otoritas pool. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` di sini. |
| 9 | `tick_array_bitmap` | W |   | PDA `TickArrayBitmapExtension`; `init` di sini. |
| 10 | `token_program_0` |   |   | Program yang memiliki `token_mint_0` — SPL Token **atau** Token-2022. |
| 11 | `token_program_1` |   |   | Program yang memiliki `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Slot 10 dan 11 adalah **per-mint**, bukan "SPL Token lalu Token-2022". Masing-masing dibatasi oleh
  `mint::token_program` pada mint yang cocok, jadi untuk pool yang `token_mint_0` adalah Token-2022 dan
  `token_mint_1` adalah SPL klasik Anda harus meneruskan Token-2022 di slot 10 dan SPL Token di slot 11.
  `CreateCustomizablePool` dan `CreateCustomizablePoolV2` menggunakan dua slot yang sama.
</Warning>

**Prekondisi**

- `token_mint_0 < token_mint_1` menurut urutan byte.
- `amm_config.disable_create_pool == false`.
- Mint tidak ditolak oleh daftar allow-list ekstensi Token-2022.

**Postkondisi**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (belum ada posisi).
- `pool_state.fee_on = FromInput` (default warisan).
- `pool_state.dynamic_fee_info` adalah nol (dynamic fee dinonaktifkan).

## `CreateCustomizablePool`

Direkomendasikan untuk pool baru. Efek yang sama dengan `CreatePool` ditambah mode pengumpulan biaya per-pool dan opt-in dynamic-fee opsional.

**Argumen**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Akun** — tepat 13 akun yang dideklarasikan dari `CreatePool`. `dynamic_fee_config` **bukan** akun yang dideklarasikan.

<Warning>
  Ketika `enable_dynamic_fee = true`, `DynamicFeeConfig` yang akan di-snapshot harus disediakan sebagai
  **akun sisa terakhir** — handler membaca `ctx.remaining_accounts.last()`. Setiap
  PDA bypass `SupportMintAssociated` harus oleh karena itu datang *sebelumnya*, atau program mengambil snapshot
  akun yang salah dan gagal deserialisasi. Menghilangkannya saat flag diatur gagal dengan
  `AccountLack`.
</Warning>

**Prekondisi** — sama dengan `CreatePool`. Jika `enable_dynamic_fee = false`, tidak ada `remaining_account` yang diperlukan dan yang dilewatkan hanya dipindai untuk catatan support-mint.

**Postkondisi**

- `pool_state.fee_on` diatur ke varian `CollectFeeOn` yang dipilih.
- Jika dynamic fee diaktifkan: `pool_state.dynamic_fee_info` diinisialisasi dari `DynamicFeeConfig` yang disediakan (lima parameter kalibrasi disalin; bidang status dinolkan).
- Jika tidak: `pool_state.dynamic_fee_info` adalah nol (= dynamic fee tidak aktif selamanya untuk pool ini).

`fee_on` dan bit enablement dynamic-fee diatur **hanya** saat pembuatan pool. Tidak ada upgrade in-place — pool yang dibuat melalui `CreatePool` warisan tidak dapat secara retroaktif mendapatkan dynamic fee atau biaya satu sisi. Deployment baru harus default ke instruksi ini.

## `CreateCustomizablePoolV2`

Baik `CreatePool` maupun `CreateCustomizablePool` menurunkan pool PDA dari `["pool", amm_config, token_mint_0, token_mint_1]`, sehingga ada tepat **satu** alamat pool kanonik per triple `(config, mint0, mint1)` — inisialisasi kedua pada seed yang sama akan gagal. `CreateCustomizablePoolV2` menghilangkan batasan tersebut dengan melipat `seed_index: u16` yang disediakan klien ke dalam seed pool PDA, memungkinkan **beberapa pool untuk pasangan dan tier biaya yang sama** — masing-masing di alamatnya sendiri. Siapa pun dapat memanggilnya.

Segala hal lain tentang pool identik dengan `CreateCustomizablePool`: ia mengambil `CreateCustomizableParams` yang sama dan mendukung biaya satu sisi serta opsi dynamic-fee.

<Note>
  Hingga [upgrade 2026-10-22](/id/reference/changelog/2026-10-22-clmm-customizable-pool-v2), instruksi ini disebut `CreatePermissionedPool` dan memerlukan pembayar untuk memegang PDA `Permission` yang dikeluarkan admin. Upgrade tersebut mengganti namanya, menghapus akun `permission`, dan menghapus mesin permission. Diskriminator berubah seiring dengan nama, jadi klien yang dibangun terhadap `CreatePermissionedPool` harus dibangun ulang.
</Note>

**Argumen**

```rust
customizable_params: CreateCustomizableParams   // struct yang sama dengan CreateCustomizablePool
seed_index:          u16                          // harus bukan nol; dilipat ke dalam seed pool PDA
```

**Akun**

| # | Nama | W | S | Catatan |
|---|------|---|---|---------|
| 1 | `payer` | W | S | Membayar sewa untuk setiap akun baru. Dompet apa pun. |
| 2 | `pool_creator` |   |   | Dicatat sebagai `pool_state.owner`. Mungkin berbeda dari `payer`. Bukan penanda tangan dan tidak diperiksa. |
| 3 | `amm_config` |   |   | Tier biaya yang diikat pool. |
| 4 | `pool_state` | W |   | `init` di `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`. |
| 5 | `token_mint_0` |   |   | Harus diurutkan sebelum `token_mint_1`. |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`. |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`. |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`. |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`. |
| 11 | `token_program_0` |   |   | Program yang memiliki `token_mint_0`. |
| 12 | `token_program_1` |   |   | Program yang memiliki `token_mint_1`. |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts`: PDA registri support-mint ketika mint Token-2022 membutuhkannya, dan `DynamicFeeConfig` **terakhir** ketika `enable_dynamic_fee = true` — seperti dalam `CreateCustomizablePool`.

**Prekondisi**

- `seed_index != 0`. `seed_index` bernilai `0` dicadangkan untuk pool warisan dan ditolak di sini; komponen seed `[0, 0]` adalah yang membuat alamat pool warisan runtuh ke bentuk empat-seed klasik.
- Tidak ada pool yang sudah ada di alamat yang diturunkan.
- Aturan mint / allow-list yang sama dengan `CreatePool`.

**Postkondisi**

- `pool_state` baru ada di alamat yang diturunkan `seed_index`, dengan `pool_state.seed_index = seed_index`.
- Semua post-state lainnya cocok dengan `CreateCustomizablePool` (mode biaya, dynamic fee opsional).

<Warning>
  Karena `pool_creator` tidak diperiksa, pembayar apa pun dapat menulis alamat apa pun ke dalam `pool_state.owner`. Alamat tersebut dapat memanggil `InitializeReward` di pool, tetapi itu bukan bukti siapa yang membuat pool. Integrator tidak boleh memberi label atau menentukan peringkat pool V2 berdasarkan `owner` mereka.
</Warning>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Buat posisi baru di dalam pool yang sudah ada.

**Argumen**

```

tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // L yang diinginkan (atau 0 untuk menggunakan jumlah di bawah)
```

`OpenPositionWithToken22Nft` adalah daftar yang sama dengan `metadata_account` (5) dan `metadata_program` (19) **dihapus** — ia menulis metadata posisi melalui ekstensi metadata Token-2022 pada mint NFT sebagai gantinya — menghasilkan 20 akun. `position_nft_mint` adalah `Signer` biasa dan `position_nft_account` adalah `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` bukan akun yang dideklarasikan di kedua varian.** Ketika jangkauan posisi berada di luar `tick_array_bitmap` inline pool (±512 tick array), tambahkan PDA `TickArrayBitmapExtension` di seed `["pool_tick_array_bitmap_extension", pool_state]` sebagai `remaining_accounts[0]`.
</Warning>

**Matematika** — lihat [`products/clmm/math`](/id/products/clmm/math). Diberikan `base_flag`, program menyelesaikan baik `liquidity` atau `(amount_0_max, amount_1_max)` menjadi `L` aktual dan jumlah token aktual yang dikonsumsi.

**Prekondisi**

- `tick_lower < tick_upper`, keduanya kelipatan `pool.tick_spacing`, dalam `[MIN_TICK, MAX_TICK]`.
- Dua PDA tick-array dilewatkan. Mereka **tidak perlu** sudah ada — `get_or_create_tick_array` mengalokasikan yang hilang di biaya `payer` di dalam instruksi ini. Tidak ada instruksi init-tick-array terpisah.
- Pengguna memiliki setidaknya `amount_0_max` dan `amount_1_max` di ATA sumber.

**Postkondisi**

- `personal_position` ada, `liquidity` diatur, `fee_growth_inside_last` difoto.
- Entri tick-array di `tick_lower` dan `tick_upper` diperbarui (`liquidity_gross += L`, `liquidity_net ± L`, snapshot pertumbuhan biaya dipertahankan).
- `pool_state.liquidity += L` jika posisi dalam jangkauan (`tick_lower ≤ tick_current < tick_upper`).
- Mint NFT posisi mencatat `pool_state` sebagai otoritas pembekuan. Otoritas mint dihapus setelah NFT tunggal dimint. Mencatat otoritas pembekuan tidak mengubah status akun token NFT.
- Akun token NFT tetap tidak beku kecuali instruksinya adalah `OpenPositionV2` atau `OpenPositionWithToken22Nft` **dan** otoritas pembekuan mint vault cocok dengan daftar penerbit terbatas CLMM. Hanya jalur V2 yang cocok yang membekukan akun. `OpenPosition` V1 tidak membekukan.

**Kesalahan umum** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (titik akhir bukan kelipatan `tick_spacing`), `InvalidTickIndex` (di luar `[MIN_TICK, MAX_TICK]`), `MissingTickArrayBitmapExtensionAccount` (jangkauan di luar bitmap inline dan ekstensi tidak ditambahkan), `NotApproved` (`pool_state.status` memblokir pembukaan), `ZeroAmountSpecified`.

<Note>
  Pembekuan posisi tidak menambahkan akun instruksi yang dideklarasikan atau argumen. Klien dapat membuka posisi ini dengan tata letak V2 yang ada. Perilaku dipilih on-chain dari `vault_0_mint` dan `vault_1_mint`.
</Note>

Pembangun lama yang menghilangkan akun pool yang tersisa gagal dengan `AccountLack` saat menutup posisi yang dibekukan. Melewatkan pool untuk setiap penutupan adalah strategi yang paling kompatibel.

- `pool_state.status` memungkinkan swap.
- `now >= open_time`.
- `sqrt_price_limit_x64` berada di sisi yang benar dari `sqrt_price_x64` untuk arahnya.

**Kesalahan umum** — `TooLittleOutputReceived` (slippage exact-in), `TooMuchInputPaid` (slippage exact-out), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (bit swap diatur pada `pool_state.status`). CLMM tidak memiliki varian `ExceededSlippage` — nama itu milik CPMM — dan tidak ada `TickArrayNotFound`.

**Apa yang dilakukan `SwapV2` secara internal yang harus diketahui pemanggil** (rilis pasca-2025):

1. **Surcharge biaya dinamis** — jika `pool.dynamic_fee_info` bukan nol, program memperbarui akumulator volatilitas menggunakan jarak tick yang dilalui sejak swap terakhir (dengan aturan filter/decay dari [`products/clmm/fees`](/id/products/clmm/fees)) dan menambahkan `dynamic_fee_component` di atas `AmmConfig.trade_fee_rate`. Total biaya dibatasi pada 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Pencocokan limit order** — ketika jalan harga melintasi tick yang memegang limit order terbuka, program pertama-tama mengisi likuiditas limit order yang tersedia di tick itu (FIFO oleh `order_phase`), kemudian melanjutkan di sepanjang kurva likuiditas LP. Jumlah yang diisi memperbarui `tick.unfilled_ratio_x64` dan `tick.part_filled_orders_remaining` untuk penyelesaian nanti; order itu sendiri tetap tidak dihabiskan sampai pemiliknya memanggil `SettleLimitOrder`.
3. **Perutean biaya satu sisi** — ketika `pool.fee_on = Token0Only` atau `Token1Only`, langkah swap masih menghitung perdagangan input-output yang sama; biaya kemudian dirutkan ke sisi yang dikonfigurasi. Untuk arah di mana sisi biaya yang dikonfigurasi adalah output, biaya dikurangi dari output swap (pengguna menerima `out − fee`); untuk arah di mana itu adalah input, perilaku cocok dengan `FromInput`. Lihat `is_fee_on_input(zero_for_one)` dan `is_fee_on_token0(zero_for_one)` pada `PoolState`.

`Swap` (V1) mengimplementasikan biaya dinamis yang sama, perutean biaya satu sisi, dan pencocokan limit order seperti `SwapV2`; satu-satunya fitur yang tidak dimilikinya adalah dukungan Token-2022 — kedua vault harus berupa SPL Token klasik. Pool dengan mint Token-2022 apa pun harus ditukar melalui `SwapV2`. Agregator dan SDK sudah lebih memilih V2 untuk setiap leg CLMM sehingga pemanggil tidak perlu bercabang pada jenis mint.

  Tidak ada akun **`rent`**: struct berakhir di `system_program`, 13 akun yang dideklarasikan. `rent` yang tersesat di posisi 14 mendarat tepat di mana ekstensi bitmap opsional dibaca, sehingga pesanan tampak berfungsi sampai pertama kali array tick di luar bitmap inline harus dibuat — dan kemudian gagal.
</Warning>

<Note>
  **Perubahan daftar akun (rilis 2026-07).** `OpenLimitOrder` sekarang juga mengambil akun **sisi output** — `output_token_account`, `output_vault`, dan `output_vault_mint` — selain sisi input. Mereka digunakan hanya untuk validasi: program menolak pesanan jika akun token input **atau** output pemilik dibekukan. Ini menjamin bahwa pengisian benar-benar dapat diselesaikan ke ATA output pemilik, yang penting untuk mint Token-2022 dengan daftar izin / beku default (misalnya token berlisensi) di mana akun mungkin belum dicairkan. Klien yang dibangun terhadap daftar akun satu sisi yang lebih lama harus menambahkan tiga akun output.
</Note>

**Kondisi awal**

- Baik `input_token_account` maupun `output_token_account` tidak dibekukan (jika tidak `NotApproved`).
- `pool_state.status` memungkinkan operasi swap (bit 4) dan limit-order (bit 5) (jika tidak `NotApproved`).
- `tick_index % pool.tick_spacing == 0` dan dalam `[MIN_TICK, MAX_TICK]`.
- `tick_index` berada di **sisi kanan `pool.tick_current`** untuk arah yang dipilih (menjual token0 → tick harus di atas saat ini, dan sebaliknya). Menjual pada tick yang sudah dilintasi akan dicocokkan segera dan ditolak.

**Kondisi akhir**

- `limit_order` ada, mengambil snapshot `tick.order_phase` dan `tick.unfilled_ratio_x64` pada waktu pembukaan.
- `tick.orders_amount += amount` (dalam kohort saat ini).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` dipancarkan.

**Kesalahan umum** — `NotApproved` (akun token input atau output dibekukan, atau pool memiliki swap / limit-order dinonaktifkan), `ZeroAmountSpecified` (`amount == 0` setelah biaya transfer sisi input), `InvalidLimitOrderAmount` (jumlah akan menghasilkan output di bawah 1 unit dasar pada tick itu, atau overflow `u64`), `InvalidTickIndex` (di luar `[MIN_TICK, MAX_TICK]`, atau di sisi yang salah dari `tick_current` untuk arah yang dipilih), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

Hanya kelebihan yang bergerak. Saldo token, data akun, pemilik, status pool, dan kurva harga tidak tersentuh. Akun yang sudah mencapai minimumnya dibiarkan apa adanya, sehingga instruksi dapat dijalankan kembali dengan aman setelah setiap peluncuran.

Penandatangan lain apa pun gagal dengan `NotApproved`. |

Mint NFT posisi tidak dapat disapu, karena otoritas mint-nya dibatalkan saat posisi dibuka.

**Cara setiap akun sumber ditangani**

Program membuat dua lintasan atas `remaining_accounts`: setiap CPI program token terlebih dahulu, kemudian debit langsung. Menyelipkan keduanya membatalkan dengan kesalahan `UnbalancedInstruction` runtime, jadi urutan ditetapkan dalam program dan Anda tidak harus mengurutkan daftar sendiri.

| Lintasan | Pemilik akun sumber | Penanganan |
|---|---|---|
| 1 | SPL Token atau Token-2022, akun token non-native | CPI `WithdrawExcessLamports` (diskriminan program token `38`), ditandatangani oleh `pool_state`. |
| 1 | SPL Token atau Token-2022, **native** (wSOL) akun token | `WithdrawExcessLamports` menolak akun native. Program CPI `SyncNative`, mengukur berapa banyak `amount` yang dibungkus tumbuh, dan memanggil `UnwrapLamports` (diskriminan `45`) untuk delta yang tepat. Kemudian memerlukan saldo yang dibungkus sama dengan nilai pra-sinknya, atau gagal dengan `LamportsCalculateError` (`6052`). Vault pool sisi SOL menyimpan likuiditas penuhnya. |
| 2 | `pool_state` (slot 2) | Didebit langsung ke `rent.minimum_balance(data_len)`. |
| 2 | Program CLMM: `AmmConfig`, `ObservationState`, `TickArrayBitmapExtension`, `TickArrayState`, `PersonalPositionState`, `LimitOrderState`, dan sebagainya | Didebit langsung ke `rent.minimum_balance(data_len)`. Akun **tidak** harus milik pool di slot 2. |
| — | Apa pun yang lain | **Dilewati diam-diam.** Tidak ada kesalahan, tidak ada lamport yang bergerak. |

<Warning>
  **Lintasan 2 mencakup akun yang sewanya dibayar pengguna.** `PersonalPositionState` atau `LimitOrderState` yang dilewatkan di sini melepaskan kelebihannya seperti akun milik CLMM lainnya. Tetap bebas sewa dan menyimpan datanya. Ketika kemudian ditutup, pemilik mendapatkan kembali apa pun yang dipegang akun pada saat itu, yang setelah penyapuan adalah minimum sewa saat ini.
</Warning>

Ukuran transaksi adalah batas nyata pada berapa banyak sumber yang cocok dalam satu panggilan. Ini adalah batasan yang sama dengan penyapuan sisi dompet yang dijelaskan dalam [`solana-fundamentals/rent-and-reclaimable-rent`](/id/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**Kesalahan umum**:
- `NotApproved` (`6000`): penandatangan salah.
- `LamportsCalculateError` (`6052`): putaran wSOL tidak nol bersih.
- Kesalahan ketidakcocokan pemilik program token: sumber token tidak dimiliki oleh `pool_state`.
- `InsufficientFunds`: akun milik program menyimpan kurang dari minimum sewa-nya sendiri.

**Tidak ada pembangun SDK.** `@raydium-io/raydium-sdk-v2` tidak mengirimkan pembangun untuk jalur admin ini. Enkode dengan tangan dari IDL.

## `InitializeReward`

Tambahkan aliran reward baru ke pool. Hingga 3 aliran dapat aktif sekaligus.

**Argumen** — satu struct, `param: InitializeRewardParam`:

```rust
pub struct InitializeRewardParam {
    pub open_time:                u64,
    pub end_time:                 u64,
    pub emissions_per_second_x64: u128,   // Q64.64
}
```

Pengkodean wire adalah tiga bidang berturut-turut, jadi instruksi yang dibangun dengan tangan tidak terpengaruh — tetapi klien yang didorong IDL harus melewatkan satu objek `param` daripada tiga argumen posisional.

**Akun**

| # | Nama | W | S | Catatan |
|---|------|---|---|---------|
| 1 | `reward_funder` | W | S |
| 2 | `funder_token_account` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `operation_state` |   |   | PDA status operasi CLMM gating pembuatan reward. |
| 6 | `reward_token_mint` |   |   |
| 7 | `reward_token_vault` | W |   | `init` di sini. |
| 8 | `reward_token_program` |   |   |
| 9 | `system_program`, `rent` |   |   |

**Prasyarat**

- Kurang dari 3 aliran saat ini aktif di pool.
- Funder menyetor `total_emission = emissions_per_second × (end_time − open_time)` senilai token reward ke vault sebagai bagian dari instruksi ini.
- Mint reward yang masuk daftar putih per `operation_state`.

## `SetRewardParams`

Perpanjang, isi ulang, atau ubah tingkat emisi pada aliran reward yang ada. Biasanya dipanggil oleh pembuat pool atau multisig Raydium. Batasan hidup on-chain: Anda biasanya dapat memperpanjang `end_time` atau meningkatkan emisi, bukan menyusutnya secara retroaktif. Periksa daftar pemilik `operation_state`.

## `UpdateRewardInfos`

Pembukuan murni — menyelesaikan `reward_growth_global_x64` ke waktu saat ini dengan mengalikan `emissions_per_second × Δt / liquidity`. Dipanggil secara internal oleh setiap instruksi yang menyentuh likuiditas. Diekspos sebagai instruksi mandiri karena aktor eksternal (UI, crank) kadang-kadang ingin memicunya.

## Mengumpulkan reward

<Warning>
  **Tidak ada instruksi kumpul-reward mandiri.** Program tidak mengekspos entrypoint `CollectReward`, dan IDL yang dipublikasikan juga tidak memilikinya.
</Warning>

Reward yang diterima posisi dibayarkan oleh `DecreaseLiquidity` / `DecreaseLiquidityV2`. Untuk mengumpulkan tanpa mengubah posisi, panggilnya dengan `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`. Vault reward dan akun penerima masuk `remaining_accounts` dalam grup tiga per reward aktif, dalam urutan `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`.

`CollectRemainingRewards` adalah hal yang berbeda: memungkinkan reward *funder*, setelah `end_time` aliran, menyapu token yang tidak pernah dialokasikan ke posisi apa pun.
