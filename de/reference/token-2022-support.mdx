## Unterstützung auf Programmebene

| Programm | Token-2022 Base/Quote-Mints? | Modus |
|---|---|---|
| **CPMM** | Ja — gated | Strikte Erweiterungs-Allowlist + Admin-Pro-Mint-Registry. Die statische 4-Mint-Whitelist wurde im Upgrade 2026-09 entfernt. |
| **CLMM** | Ja — gated | Strikte Erweiterungs-Allowlist + Admin-Pro-Mint-Registry. Die statische 6-Mint-Whitelist und die Superstate-Erkennung wurden beide im Juli 2026 entfernt. |
| **AMM v4** | Nein | Programm stammt aus der Zeit vor Token-2022; beide Mints müssen klassisches SPL Token sein. |
| **Stable AMM** | Nein | Gleiche Einschränkungen wie AMM v4. |
| **Farm v6** | Ja, teilweise | Der Reward-Mint kann Token-2022 sein (unterliegt der gleichen Allowlist, wenn eine Farm einen CPMM/CLMM-LP umhüllt); Benutzer-Stake-LP-Mints erben vom umhüllten Pool. |
| **LaunchLab** | Ja — Base-Programm-verwaltet, Quote ungated | Der Base-Mint kann Token-2022 sein, aber nur über die dedizierte `initialize_with_token_2022`-Anweisung; das Programm erstellt den Mint selbst mit `MetadataPointer` (immer) und optional `TransferFeeConfig` (Rate ≤ 5%). Bereits vorhandene Token-2022-Mints mit beliebigen Erweiterungen können nicht als Base verwendet werden. Der **Quote**-Mint kann ein beliebiger Token-2022-Mint sein, den ein Admin an eine `GlobalConfig` bindet, ohne Erweiterungsprüfung — siehe [unten](#launchlab-quote-mints). |
| **Burn & Earn** | Spiegelt Pool-Programm | Erbt CPMM/CLMM-Gating. |

Die Allow-List-Prüfungen befinden sich in:

- **CPMM**: `is_supported_mint` in [`raydium-cp-swap/programs/cp-swap/src/utils/token.rs`](https://github.com/raydium-io/raydium-cp-swap/blob/master/programs/cp-swap/src/utils/token.rs), aufgerufen von `Initialize` und `InitializeWithPermission`.
- **CLMM**: `is_supported_mint` in [`raydium-clmm/programs/amm/src/util/token.rs`](https://github.com/raydium-io/raydium-clmm/blob/master/programs/amm/src/util/token.rs), aufgerufen von `CreatePool`.
- **LaunchLab**: `initialize_with_token_2022` in `raydium-launchpad/programs/launchpad/src/instructions/initialize_with_token_2022.rs` (Quellcode nicht öffentlich verfügbar).

Es gibt **keine** Swap-Zeit-Mint-Prüfung auf CPMM oder CLMM — das Gate wird nur bei der Pool-Erstellung aktiviert. Sobald ein Pool existiert, vertrauen Swaps darauf, dass sich die Mints nicht geändert haben, was für die unveränderlichen Teile des Token-2022-Mint-Status korrekt ist.

## CLMM-Position-NFT-Einfrieren für eingeschränkte Emittenten

Position-NFT-Konten bleiben standardmäßig aufgetaut. CLMM friert einen nur ein, wenn die Position einen V2-Open-Pfad verwendet **und** mindestens eine Vault-Mint der aktuellen `freeze_authority` in der hardcodierten `frozen_position_nft_authorities::IDS`-Liste erscheint. Diese Liste ersetzte CLMMs frühere Superstate-Token-Erkennung und trägt die gleiche Emittenten-Autorität, die die alte Heuristik abgeglichen hat. Das Setzen der Pool-PDA als Freeze-Autorität des Position-NFT-Mints ist selbst kein Einfrieren. Dies ist eine Position-Custody-Regel, keine Pool-Erstellungs-Allowlist:

- Der Pool kann bereits existieren und bleibt tauschbar.
- Der Position-NFT-Mint verwendet die CLMM-Pool-PDA als seine eigene Freeze-Autorität; der zugrunde liegende Emittent kontrolliert den Position-NFT nicht.
- `OpenPositionV2` deckt klassische SPL-Position-NFTs über Token-2022-Pool-Assets ab. `OpenPositionWithToken22Nft` deckt Token-2022-Position-NFTs ab.
- `OpenPosition` V1 inspiziert Vault-Mints nicht und kann die Token-2022-eingeschränkten Assets, auf die die ausgelieferte Liste abzielt, nicht bedienen.
- Bestehende Positionen bleiben unverändert.

Eingefrorene Positionen bleiben von ihrem Besitzer verwaltbar, können aber nicht übertragen werden. `ClosePosition` taut auf und brennt atomar, wenn der Client den Pool als das erste verbleibende Konto übergibt. Siehe [`products/clmm/ticks-and-positions`](/de/products/clmm/ticks-and-positions#restricted-issuer-positions).

## LaunchLab-Quote-Mints

Die beiden Mints von LaunchLab sind sehr unterschiedlich gated, und die Asymmetrie ist leicht zu übersehen.

- **Base-Mint** — LaunchLab erstellt ihn. Ein Token-2022-Base-Mint ist nur über `initialize_with_token_2022` erreichbar, und das Programm wird nur `MetadataPointer` und (optional) `TransferFeeConfig` anhängen. Alles andere gibt `NoSupportExtension` zurück. Ein bereits vorhandener Token-2022-Mint kann überhaupt nicht als Base bereitgestellt werden. Wenn `TransferFeeConfig` angehängt ist, ist die `transfer_fee_config_authority` des Mints die Launch-Autorität-PDA bis zur Graduation, während seine `withdraw_withheld_authority` die konfigurierte `transfer_fee_extension_auth` der Plattform ab der Mint-Erstellung ist — das Launchpad-Programm selbst hat keine Withdraw-Withheld-Anweisung. Siehe [`products/launchlab/platform-config`](/de/products/launchlab/platform-config#token-2022-transfer-fee-authorities).
- **Quote-Mint** — LaunchLab erstellt ihn nicht und prüft ihn nicht. `CreateConfig` akzeptiert das Mint-Konto wie gegeben, daher gibt es **kein `is_supported_mint`-Äquivalent auf der Quote-Seite**. Das einzige Gate ist, welche Mints ein Admin an eine `GlobalConfig` bindet.

Das macht das Binden eines Token-2022-Quote-Mints zu einer vertrauenswürdigen Aktion, aus dem gleichen Grund wie das Registrieren eines Mints unten: Ein `TransferHook`-Quote-Mint würde seinen Hook bei jedem Kauf, Verkauf und Gebührenanspruch in jedem Pool, der darin notiert ist, ausführen, und ein `PermanentDelegate`-Quote-Mint würde dem Delegaten erlauben, die Quote-Vaults dieser Pools zu leeren. Keines wird vom Programm blockiert.

Was LaunchLab korrekt handhabt, sobald ein Quote-Mint gebunden ist:

- Der Quote-Vault, beide Fee-Vaults und das Token-Konto des Share-Fee-Empfängers werden auf dem eigenen Programm des Quote-Mints erstellt.
- `TransferFeeConfig` auf der Quote-Seite wird in alle vier Trade-Anweisungen eingepreist, und die Slippage-Grenze wird gegen den Netto-Betrag des Zahlers statt gegen die Brutto-Bewegung des Vaults geprüft. Siehe [`products/launchlab/instructions`](/de/products/launchlab/instructions#quote-side-transfer-fees).
- `PoolState.token_program_flag` zeichnet die Programme beider Mints auf — Bit0 für den Base-Mint, Bit1 für den Quote-Mint. Dekodieren Sie es pro Bit; das Byte ist kein Boolean. Siehe [`products/launchlab/accounts`](/de/products/launchlab/accounts#poolstate).

Die veraltete `Initialize`-Anweisung nimmt immer noch ein Legacy-Only-Quote-Programm, daher ist eine Config mit einem Token-2022-Quote-Mint nur über `InitializeV2` und `InitializeWithToken2022` erreichbar.

## CPMM- und CLMM-Erweiterungs-Allowlist

Nach den zwei Kurzschlüssen, die [unten](#the-one-bypass-the-per-mint-registry) behandelt werden, iteriert das Programm die Erweiterungen des Mints und lehnt den Mint ab, wenn er **eine** Erweiterung trägt, die nicht diese fünf sind:

| Erweiterung | Grund, warum sie erlaubt ist |
|---|---|
| `TransferFeeConfig` | Pool-Mathematik subtrahiert die eingehende Gebühr; das Token-2022-Programm handhabt die ausgehende Gebühr. Siehe [`algorithms/token-2022-transfer-fees`](/de/algorithms/token-2022-transfer-fees). |
| `MetadataPointer` | Dekorativ — zeigt auf On-Chain-Metadaten. |
| `TokenMetadata` | Dekorativ — Inline-Metadaten. |
| `InterestBearingConfig` | Pool sieht den Hauptbetrag; UI-Multiplikator ist nur Dekoration und der zugrunde liegende Saldo bleibt erhalten. |
| `ScaledUiAmount` | Gleiche Form wie Zinsträger — Skalierungsfaktor gilt nur für UI-Anzeige. |

Alles, was nicht auf dieser Liste steht — `TransferHook`, `NonTransferable`, `ConfidentialTransferMint`, `PermanentDelegate`, `MintCloseAuthority`, `DefaultAccountState`, `GroupPointer`, `GroupMemberPointer`, `MemberPointer`, `Pausable` usw. — führt dazu, dass `is_supported_mint` `false` zurückgibt und die Pool-Erstellung zurückgerollt wird.

Die relevanten Zeilen (CPMM, identische Form in CLMM):

```rust
for e in extensions {
    if e != ExtensionType::TransferFeeConfig
        && e != ExtensionType::MetadataPointer
        && e != ExtensionType::TokenMetadata
        && e != ExtensionType::InterestBearingConfig
        && e != ExtensionType::ScaledUiAmount
    {
        return Ok(false);
    }
}
Ok(true)
```

— [`cp-swap/src/utils/token.rs`](https://github.com/raydium-io/raydium-cp-swap/blob/master/programs/cp-swap/src/utils/token.rs)

## Bypass-Pfade

Ein Token-2022-Mint, der nicht in die Allowlist passt, kann immer noch zugelassen werden, durch einen Mechanismus in jedem Programm. Beide Programme hatten auch in der Vergangenheit hardcodierte Bypasses; keiner von ihnen überlebt.

| Bypass | CPMM | CLMM |
|---|---|---|
| Pro-Mint-Registry-PDA | Ja — der einzige Bypass | Ja — der einzige Bypass |
| Statische `MINT_WHITELIST` | Entfernt 2026-09 (4 Adressen) | Entfernt 2026-07 (6 Adressen) |
| Superstate-Autoritäts-Form-Erkennung | Hatte nie eine | Entfernt 2026-07 |

`is_supported_mint` ist jetzt Byte-für-Byte die gleiche Funktion in beiden Programmen: Legacy-SPL-Token-Mints passieren, ein Mint mit einer Registry-PDA passiert, und alles andere muss nur erlaubte Erweiterungen tragen.

## Der einzige Bypass: die Pro-Mint-Registry

Beide Programme konsultieren eine `SupportMintAssociated`-PDA bei Seed `[b"support_mint", mint]`. Wenn diese PDA für den Mint existiert, wird der Mint unabhängig von seinem Erweiterungssatz zugelassen.

Jedes Programm hat seine eigene Kopie der PDA (sie leiten unter verschiedenen Programm-IDs ab), sein eigenes `CreateSupportMintAssociated`/`CloseSupportMintAssociated`-Paar und seine eigene dedizierte Autorität neben dem gemeinsamen Admin:

Die vier Schlüssel (CPMM und CLMM × Mainnet und Devnet) sind unter [Support-Mint-Registry-Autoritäten](/de/reference/program-addresses#support-mint-registry-authorities) aufgeführt.

In beiden Programmen akzeptiert die Anweisung entweder `crate::admin::ID` oder die dedizierte Autorität dieses Programms und erfordert, dass der Mint von Token-2022 besessen wird. Effekt: Ein spezifischer Token-2022-Mint kann ohne Programm-Upgrade in die Pool-Erstellung aufgenommen werden — deshalb konnten die hardcodierten Listen gehen.

Jedes Programm konsultiert die Registry von **jedem** Pool-Erstellungs-Pfad, den es hat: CPMM von `Initialize` und `InitializeWithPermission` (letzteres ist das, was LaunchLab-Graduationen verwenden, daher graduiert ein registrierter Mint sowie erstellt), CLMM von `CreatePool`, `CreateCustomizablePool` und `CreatePermissionedPool`.

## Die entfernten Bypasses

Beide hardcodierten Mechanismen sind aus den bereitgestellten Programmen verschwunden. Sie werden hier nur dokumentiert, weil Integrationen, die gegen das ältere Verhalten geschrieben wurden, sie möglicherweise immer noch annehmen.

### Statische `MINT_WHITELIST` — entfernt

Ein konstantes Array von Base58-Mint-Adressen, das früher `is_supported_mint` vor der Erweiterungsiteration kurzschloss. CLMMs hielt sechs Adressen und wurde am 2026-07-24 gelöscht; CPMMs hielt die ersten vier der gleichen Menge und wurde im [Upgrade 2026-09-09](/de/reference/changelog/2026-09-09-cpmm-anchor-1-and-excess-lamports) gelöscht.

| Früher auf der Whitelist in | Mints |
|---|---|
| CPMM und CLMM | `HVbpJAQGNpkgBaYBZQBR1t7yFdvaYVp2vCQQfKKEN4tM`, `Crn4x1Y2HUKko7ox2EZMT6N2t2ZyH7eKtwkBGVnhEq1g`, `FrBfWJ4qE5sCzKm3k3JaAtqZcXUh4LvJygDeketsrsH4`, `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` |
| Nur CLMM | `DAUcJBg4jSpVoEzASxYzdqHMUN8vuTpQyG2TvDcCHfZg`, `AUSD1jCcCyPLybk1YnvPWsHQSrZ46dxwoMniN4N2UEB9` |

**Ein Pool, der bereits für einen dieser Mints existiert, bleibt im Handel** — die Mint-Prüfung wird nur bei der Pool-Erstellung ausgeführt. Das Erstellen eines *neuen* Pools für einen erfordert stattdessen eine Registry-PDA dafür.

### Superstate-Autoritäts-Form-Erkennung — entfernt

CLMM identifizierte Superstates tokenisierte Assets kurzzeitig anhand ihrer Autoritäts-Form statt anhand der Adresse: Ein Token-2022-Mint, dessen `freeze_authority` **und** permanenter Delegat beide `superstate_allowlist::ID` gleich waren, mit `DefaultAccountState` auf `Frozen` gesetzt, wurde zugelassen. Es war eine Heuristik, daher würde jeder zukünftige Mint mit der gleichen Form automatisch zugelassen worden sein.

Es wurde am 2026-07-31 zusammen mit dem `superstate_allowlist`-Modul gelöscht. Was es ersetzte, ist enger und dient einem anderen Zweck: `frozen_position_nft_authorities::IDS`, das nichts zulässt — es entscheidet, ob eine **Position-NFT** eingefroren wird, und wird [oben](#clmm-position-nft-freezing-for-restricted-issuers) beschrieben. Die eine Emittenten-Autorität, die die alte Heuristik abgeglichen hat, ist der eine Eintrag in dieser Liste.

## Was die Bypasses nicht verzeihen

Die Bypasses überspringen die Erweiterungs-Allowlist, aber das Programm erzwingt immer noch:

- Der Mint wird von entweder `Token` oder `Token-2022` besessen. Ein benutzerdefiniertes Token-Programm wird vorgelagert abgelehnt.
- Die Pool-Vaults werden mit den richtigen ATA-Erweiterungen für Token-2022-Pools erstellt (`ImmutableOwner` usw.).
- Alle Transfers gehen durch `transfer_checked` — gebührentragende Mints landen den richtigen Betrag im Vault.

Ein auf die Whitelist gesetzter oder PDA-registrierter Mint, der z. B. später einen `TransferHook` hinzufügt, erhält keine Swap-Zeit-Prüfung; der Hook würde einfach bei jedem Transfer ausgeführt und könnte Swaps blockieren. Das Registrieren eines Mints ist daher eine vertrauenswürdige Aktion.

## „Blockiert"-Semantik

Wenn `is_supported_mint` `false` zurückgibt, wird die Pool-Erstellung mit `ErrorCode::NotSupportMint` (CPMM) / `ErrorCode::NotSupportMint` (CLMM) zurückgerollt. Siehe [`reference/error-codes`](/de/reference/error-codes) für die numerischen Codes.

Bestehende Pools können diese Prüfung nicht rückwirkend fehlschlagen — das Gate wird nur bei der Erstellung ausgeführt. Mint-Erweiterungen sind unveränderlich für die Kategorien, die Raydium ablehnt (Transfer-Hook, nicht übertragbar, vertrauliche Übertragung können nach der Erstellung nicht hinzugefügt werden), daher ist die statische Prüfung ausreichend.

## Warum jede ausgeschlossene Erweiterung ausgeschlossen ist

- **TransferHook** — ruft ein benutzerdefiniertes Programm bei jedem Transfer auf, mit beliebigem CU-Verbrauch, beliebigen Fehlerbedingungen und der Möglichkeit, das aufrufende Programm erneut einzugeben. Es gibt keine sichere Sandbox. Einige DEXes führen Hook-Allowlists; Raydium nicht.
- **NonTransferable** — `Transfer` schlägt immer fehl. Ein Pool kann keine Verwahrung übernehmen.
- **ConfidentialTransfer** — Übertragsbeträge sind verschlüsselt; die Kurve kann den Swap nicht bewerten.
- **PermanentDelegate** — ein Inhaber des Delegaten kann jedes Token-Konto leeren, einschließlich des Pool-Vaults. Nur durch Registrierung des Mints zulässig, was ist, wie ein vertrauenswürdiger Emittent (z. B. eine regulierte Stablecoin) Fall für Fall eingebunden wird.
- **MintCloseAuthority** — der Mint kann geschlossen werden; bestehende Pools werden unbrauchbar. Standardmäßig nicht zulässig.
- **DefaultAccountState (Frozen)** — Pool-ATAs würden im `Frozen`-Status landen und müssen pro Konto aufgetaut werden. Nur durch Registrierung des Mints zulässig, was davon ausgeht, dass der Emittent institutionelle Konten bei der Registrierung auftaut.
- **Group/Member-Pointer** — nicht aktiv schädlich, aber ungeprüft. Standardmäßig nicht zulässig, um die Oberfläche eng zu halten.

## Gebührenabrechnung übertragen

Für Mints mit `TransferFeeConfig` bewegt sich bei jedem Swap, Deposit und Withdraw weniger als der nominale Betrag. Zwei separate Zahlen sind beteiligt, und das SDK hält sie auseinander:

- **Die Pool-Gebühr** (LP + Protokoll + Fonds + Creator) kommt aus der Kurve. `raydium.cpmm.computeSwapAmount({ ... })` gibt sie als `fee` zurück, zusammen mit `amountIn`, `amountOut`, `minAmountOut`, `executionPrice`, `priceImpact` und dem rohen `swapResult`.
- **Die Token-2022-Übertragsgebühr** kommt vom Mint, nicht vom Pool. Sie wird von den `getTransferAmountFee`-Helfern in `@raydium-io/raydium-sdk-v2` berechnet, die eine `GetTransferAmountFee` zurückgeben:

```ts
export interface GetTransferAmountFee {
  amount: BN;                  // der Betrag, der tatsächlich bewegt wird
  fee: BN | undefined;         // vom Mint einbehalten; undefined, wenn der Mint keine TransferFeeConfig hat
  expirationTime: number | undefined;  // gesetzt, während eine geplante Gebührenänderung ausstehend ist
}
```

Deposit und Withdraw zeigen es direkt: `computePairAmount` gibt `inputAmountFee` und `anotherAmount` als `GetTransferAmountFee`-Werte zurück.

Eine korrekte UI zeigt:

- den Eingabebetrag **plus** seine Übertragsgebühr als „Sie senden"
- den Ausgabebetrag **minus** seine Übertragsgebühr als „Sie erhalten"
- die Pool-Gebühr als separate Zeile — es ist nicht die Token-2022-Gebühr

Eine naive UI, die nur `amountIn → amountOut` zeigt, unterschätzt die Kosten. Übergeben Sie `epochInfo` vom Cluster an diese Helfer, anstatt sie zu cachen; die Epoch ist das, was zwischen der `older`- und `newer`-Gebührenconfig eines Mints wählt.

### `maximumFee`-Obergrenze

Token-2022-Übertragsgebühren sind pro Übertrag begrenzt. Für einen 1%-Mint mit einer 10.000-Token-Obergrenze zahlt eine 100.000.000-Token-Übertragung nur 10.000 in Gebühren. Das SDK `computeSwapAmount` wendet die Obergrenze an; direkte Programmaufrufer müssen sie replizieren.

### Epoch-Übergang

Eine Mint-Autorität kann eine Gebührensatz-Änderung planen, die in der nächsten Epoch aktiviert wird. Während des Übergangsfensters leben zwei Configs (`older`, `newer`) gleichzeitig auf dem Mint und `TransferChecked` wählt nach aktueller Epoch. Sowohl CPMM `SwapV2` als auch CLMM `SwapV2` übergeben das vollständige Mint-Konto in `accounts`, daher liest das Programm die richtige Config ohne zusätzliche Suche.

Wenn Sie mehr als eine Epoch im Voraus über die Trade-API oder SDK zitieren, kann die ausgeführte Gebühr von der zitierten Gebühr abweichen — begrenzt durch die `maximum_fee_basis_points` der älteren Config.

## Zinsträger und ScaledUiAmount

Der Pool hält den Hauptbetrag; der „UI-Betrag" ist der Hauptbetrag multipliziert mit einem zeitabhängigen oder von Admin gesetzten Skalierungsfaktor. Swap-Mathematik arbeitet mit Hauptbetrag:

```
principal_in = ui_amount_in / ui_multiplier(now)
```

Das SDK konvertiert automatisch. Direkte RPC-Leser sollten `pool.token0Vault.amount` als Hauptbetrag behandeln.

## „Token-2022-Pool"-Definition

Ein Pool ist ein Token-2022-Pool, wenn **einer** Mint `programId == TokenzQdB...` hat. Die API zeigt dies:

```
GET /pools/info/ids?ids=<POOL_ID>
```

```json
{
  "data": [{
    "mintA": { "programId": "TokenzQdB...", "hasTransferFee": true, ... },
    "mintB": { "programId": "Tokenkeg...", ... }
  }]
}
```

Verwenden Sie `programId` zum Dispatch und `hasTransferFee` zum Anzeigen einer UI-Warnung.

## SDK-Helfer

```ts
import { Raydium } from "@raydium-io/raydium-sdk-v2";
// TOKEN_2022_PROGRAM_ID is not re-exported by the Raydium SDK — import it from
// @solana/spl-token, as the SDK itself does.
import {
  TOKEN_2022_PROGRAM_ID,
  ExtensionType,
  getExtensionTypes,
  unpackMint,
} from "@solana/spl-token";

const raydium = await Raydium.load({ owner, connection });

const acct = await connection.getAccountInfo(mintPubkey);
if (!acct) throw new Error("mint not found");
const mint = unpackMint(mintPubkey, acct, acct.owner);

if (acct.owner.equals(TOKEN_2022_PROGRAM_ID)) {
  const extensions = getExtensionTypes(mint.tlvData);
  const accepted = new Set([
    ExtensionType.TransferFeeConfig,
    ExtensionType.MetadataPointer,
    ExtensionType.TokenMetadata,
    ExtensionType.InterestBearingConfig,
    ExtensionType.ScaledUiAmount,
  ]);
  const rejecting = extensions.filter(e => !accepted.has(e));
  if (rejecting.length) {
    console.warn("Pool creation will revert unless this mint is whitelisted:", rejecting);
  }
}
```

## Häufige Integrationsfehler

- **Nur die Programm-ID vorab-flighting.** Ein Mint kann Token-2022 *und* nicht unterstützt sein. Gehen Sie die Erweiterungsliste gegen die Allowlist durch und prüfen Sie auf die Registry-PDA des Mints, bevor Sie die Pool-Erstellung zulassen.
- **Der SDK-Quote vertrauen, wenn der Mint überhaupt nicht akzeptiert wird.** Die Quote-API weigert sich nicht zu zitieren — Pool-Erstellung ist das, was zurückgerollt wird. Bestätigen Sie `is_supported_mint`-Semantik offline, bevor Sie die Pool-Erstellung in Ihrer UI verfügbar machen.
- **Zitieren ohne den Übertragsgebühren-Haarschnitt.** Ein 1%-Übertragsgebühren-Mint auf beiden Seiten eines 0,25%-CPMM-Pools hat eine effektive Gebühr von etwa 2,25%, nicht 0,25%. Verwenden Sie das SDK-Quote oder Trade-API-Quote — berechnen Sie die Gebühr niemals manuell nur aus der Pool-Gebühren-Stufe.
- **Die Legacy-`Swap`-Anweisung auf einem Token-2022-Pool aufrufen.** `Swap` stammt aus der Zeit vor Token-2022. Verwenden Sie `SwapV2`, wenn einer der Mints Token-2022 ist.
- **Automatisches Auflisten neuer Token-2022-Mints.** Wallets und Aggregatoren sollten auf `TransferHook` und `NonTransferable` prüfen, bevor sie einen Mint Benutzern anzeigen; beide sind Raydium-feindselig.

## Zukünftige Arbeit

Solana-Ökosystem- und Protokoll-Roadmap-Elemente, die diese Matrix ändern würden:

- Auf Solana-Ebene erlaubte Transfer-Hook-Programme (Ökosystem-Konvention entwickelt sich).
- Vertrauliche-Transfer-kompatible AMMs (Forschungsstadium).
- Breitere CPMM-Pro-Mint-Registry (Parität mit CLMM).
- Ein öffentlicher Lesepfad für die Registry, damit eine UI „nicht unterstützt" von „nicht unterstützt aber registriert" unterscheiden kann, ohne die PDA selbst abzuleiten.
