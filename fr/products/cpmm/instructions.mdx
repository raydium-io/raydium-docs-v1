## Résumé des instructions

| Nom du discriminateur | Qui signe | Ce qu'elle fait |
|-------|-----------|--------------|
| `Initialize` | créateur du pool | Créer un nouveau pool CPMM à partir de deux mints et d'une `AmmConfig`. Sans permission ; n'importe qui peut l'appeler. Encode en dur `enable_creator_fee = false` sur le nouveau pool. Le compte `pool_state` peut être soit le PDA canonique, soit une nouvelle paire de clés aléatoire (voir les comptes Initialize). |
| `InitializeWithPermission` | payeur + détenteur d'un PDA `Permission` | Variante avec permission de `Initialize`. L'appelant (`payer`) doit posséder un PDA `Permission` dérivé de sa propre clé publique. Utilisée par les plateformes qui ont besoin d'une création de pool contrôlée (par exemple, les graduations LaunchLab). Permet à l'appelant d'épingler `creator_fee_on` (`BothToken` / `OnlyToken0` / `OnlyToken1`) et force `enable_creator_fee = true` sur le nouveau pool. Le champ `creator` sur `pool_state` est défini sur un compte `creator` passé séparément, pas le payeur. Même flexibilité PDA-canonique-ou-paire-aléatoire pour `pool_state` que `Initialize`. |
| `Deposit` | LP | Ajouter de la liquidité dans les deux tokens ; recevoir des tokens LP. |
| `Withdraw` | LP | Brûler les tokens LP ; recevoir les deux tokens sous-jacents au prorata. |
| `SwapBaseInput` | swappeur | Swap à entrée exacte (`amount_in` en, ≥ `minimum_amount_out` en sortie). |
| `SwapBaseOutput` | swappeur | Swap à sortie exacte (≤ `maximum_amount_in` en, `amount_out` en sortie). |
| `CollectProtocolFee` | `protocol_owner` (de `AmmConfig`) | Collecter les frais de protocole accumulés des coffres. |
| `CollectFundFee` | `fund_owner` (de `AmmConfig`) | Collecter les frais de fonds accumulés des coffres. |
| `CollectCreatorFee` | `pool_creator` | Collecter les frais de créateur accumulés (si les frais de créateur étaient activés). |
| `CollectCreatorFeePermissionless` | n'importe quel payeur | Collecter tous les frais de créateur accumulés vers les comptes de tokens canoniques du `pool_creator`. Le payeur peut créer les ATAs destinataires manquantes mais ne peut pas rediriger le transfert. |
| `UpdatePoolStatus` | `admin` | Mettre en pause / reprendre des opérations spécifiques sur un pool via un masque de bits. |
| `UpdateAmmConfig` | `admin` | Modifier les taux de frais ou le propriétaire du protocole/fonds sur une `AmmConfig`. |
| `CreateAmmConfig` | `admin` | Créer un nouveau palier de frais (nouveau compte `AmmConfig`). |
| `CreatePermissionPda` | `admin` ou créateur de PDA de permission délégué | Émettre un PDA `Permission` qui permet à une autorité spécifique d'appeler `InitializeWithPermission`. |
| `ClosePermissionPda` | `admin` ou le créateur de PDA de permission dédié | Révoquer un PDA `Permission` précédemment émis. Depuis la mise à niveau 2026-09, l'autorité créatrice dédiée peut également fermer une subvention qu'elle a émise ; c'était réservé à l'admin avant. |
| `CreateSupportMintAssociated` | `admin` ou le propriétaire de mint de support dédié | Enregistrer un mint Token-2022 qui échouerait autrement la liste blanche d'extensions, en créant son PDA `SupportMintAssociated`. |
| `CloseSupportMintAssociated` | `admin` ou le propriétaire de mint de support dédié | Supprimer l'enregistrement d'un mint. |
| `CollectExcessLamports` | `admin` ou le portefeuille de collecte de lamports dédié | Collecter les lamports au-dessus du minimum exempt de loyer des coffres contrôlés par CPMM, des mints LP et des PDAs. Ajouté en 2026-09. |

Masque de statut : le `status` de chaque pool est un `u8` où le bit 0 = dépôt désactivé, bit 1 = retrait désactivé, bit 2 = swap désactivé (`PoolStatusBitIndex { Deposit, Withdraw, Swap }` dans le programme). Un bit clair signifie que l'opération est autorisée ; un bit défini signifie qu'elle est en pause. `UpdatePoolStatus` prend un `u8` brut et remplace la valeur existante.

Les sections suivantes détaillent chacune. L'ordre des comptes suit l'IDL CPMM ; le SDK et le client Rust dans `raydium-cp-swap/programs/cp-swap/src/instructions` correspondent à cet ordre.

## `Initialize`

Créer un nouveau pool CPMM.

**Arguments**

```
init_amount_0: u64
init_amount_1: u64
open_time:     u64   // Timestamp Unix ; les swaps sont rejetés avant cela
```

**Comptes** (W = inscriptible, S = signataire)

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `creator` | W | S | Paie le loyer ; enregistré comme `pool_state.pool_creator`. |
| 2 | `amm_config` |   |   | Le palier de frais choisi. |
| 3 | `authority` |   |   | PDA d'autorité globale CPMM. |
| 4 | `pool_state` | W | S* | `init`ialisé ici. **Soit** le PDA canonique `["pool", amm_config, token_0_mint, token_1_mint]` **soit** une nouvelle paire de clés aléatoire — quand ce n'est pas le PDA canonique, le programme exige que `pool_state` signe (`require_eq!(pool_account_info.is_signer, true)`). Le chemin de paire aléatoire permet à un créateur d'éviter les tentatives de front-running sur le PDA canonique. Les PDAs en aval (`lp_mint`, `vaults`, `observation_state`) sont dérivés de `pool_state.key()` de toute façon. |
| 5 | `token_0_mint` |   |   | Triés : `token_0_mint < token_1_mint`. |
| 6 | `token_1_mint` |   |   | |
| 7 | `lp_mint` | W |   | `init`ialisé ici. Autorité définie sur `authority`. |
| 8 | `creator_token_0` | W |   | ATA source pour `init_amount_0`. |
| 9 | `creator_token_1` | W |   | ATA source pour `init_amount_1`. |
| 10 | `creator_lp_token` | W |   | ATA du créateur sur `lp_mint`. `init` (et non `init_if_needed`) — elle ne doit pas déjà exister, ce qui est impossible puisque `lp_mint` est créé dans cette même instruction. |
| 11 | `token_0_vault` | W |   | `init`ialisé ici. Possédé par `authority`. |
| 12 | `token_1_vault` | W |   | |
| 13 | `create_pool_fee` | W |   | ATA destination pour le `create_pool_fee` payé par le créateur. |
| 14 | `observation_state` | W |   | `init`ialisé ici. |
| 15 | `token_program` |   |   | SPL Token (pour le mint LP). |
| 16 | `token_0_program` |   |   | SPL Token ou Token-2022. |
| 17 | `token_1_program` |   |   | SPL Token ou Token-2022. |
| 18 | `associated_token_program` |   |   | |
| 19 | `system_program` |   |   | |
| 20 | `rent` |   |   | |

`*` `pool_state` signe uniquement sur le chemin de paire aléatoire ; le chemin PDA canonique s'exécute sans que `pool_state` signe.

**Conditions préalables**

- Les mints sont triés (`token_0_mint < token_1_mint` par ordre d'octets).
- Aucun mint n'utilise une extension en dehors de la liste blanche CPMM (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) — voir [`products/cpmm/accounts`](/fr/products/cpmm/accounts#vaults-and-token-2022). Un mint dont la PDA `SupportMintAssociated` (seed `[b"support_mint", mint]`) existe ignore la vérification d'extension — **mais vous devez ajouter cette PDA à `remaining_accounts`**. Le programme ne balaie que les comptes que vous passez et ne charge jamais la PDA lui-même, donc se reposer sur le registre sans fournir le compte échoue quand même avec `NotSupportMint` (`6007`). L'ordre n'a pas d'importance (la correspondance se fait par clé) ; passez une entrée par mint ayant besoin du contournement. Ce registre est le seul contournement depuis que la mise à niveau 2026-09 a supprimé la liste blanche de quatre mints codée en dur.
- `creator` a au moins `init_amount_0` et `init_amount_1` dans les ATAs respectifs.
- `amm_config.disable_create_pool == false`.

**Postconditions**

- `pool_state.lp_supply = sqrt(init_amount_0 * init_amount_1)` — la racine carrée **complète**. Le créateur reçoit `lp_supply − 100` ; les 100 unités de base verrouillées sont comptées dans `lp_supply` mais jamais frappées.
- Donc `lp_mint.supply == pool_state.lp_supply − 100` pendant toute la vie du pool. Toute la mathématique de part LP (dépôt, retrait) divise par `lp_supply` ; utilisez donc ce champ et ne le remplacez pas par l'offre on-chain du mint. Annulé avec `InitLpAmountTooLess` si `sqrt(...) < 100`.
- `observation_state` est initialisé ; `observation_index = 0` et `pool_id = pool_state.key()`.
- Les lamports `create_pool_fee` sont transférés du créateur au destinataire et synchronisés en SOL natif (c'est un ATA wSOL).
- Le masque de statut du pool est `0` (dépôt / retrait / swap tous activés).
- `enable_creator_fee = false` et `creator_fee_on = BothToken`. `Initialize` ne **supporte pas** l'activation des frais de créateur — ce chemin est `InitializeWithPermission`.
- `open_time` est augmenté à `block_timestamp + 1` si l'appelant a passé une valeur `<= block_timestamp`. Les swaps sont rejetés avant `open_time` ; les dépôts et retraits fonctionnent immédiatement.

**Erreurs courantes** (liste complète dans [`reference/error-codes`](/fr/reference/error-codes))

- `InvalidInput` — mints non triés, ou mints identiques.
- `NotSupportMint` — extension Token-2022 bloquée.
- `ExceededSlippage` — rarement ; si `init_amount_0/1` résultent en zéro LP en raison d'une inadéquation de décimales.

## `Deposit`

Ajouter de la liquidité dans les deux tokens proportionnellement au pool.

**Arguments**

```
lp_token_amount:   u64   // combien de tokens LP à émettre au LP
maximum_token_0:   u64
maximum_token_1:   u64
```

**Comptes**

| # | Nom | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `owner_lp_token` | W |   |
| 5 | `token_0_account` | W |   |
| 6 | `token_1_account` | W |   |
| 7 | `token_0_vault` | W |   |
| 8 | `token_1_vault` | W |   |
| 9 | `token_program` |   |   |
| 10 | `token_program_2022` |   |   |
| 11 | `vault_0_mint` |   |   |
| 12 | `vault_1_mint` |   |   |
| 13 | `lp_mint` | W |   |

**Mathématiques**

```
total_0 = vault_0 − protocol_fees_0 − fund_fees_0 − creator_fees_0    // same for side 1

needed_token_0 = ceil(lp_token_amount * total_0 / lp_supply)
transfer_0     = needed_token_0 + inverse_transfer_fee(needed_token_0) // Token-2022
require(transfer_0 <= maximum_token_0, "ExceededSlippage")             // same for side 1
```

Deux détails à bien retenir : la base au prorata est le total du coffre **hors frais** (`vault_amount_without_fee`, c'est-à-dire le solde brut moins les compteurs de frais de protocole, de fonds et de créateur accumulés), et non le solde brut du coffre ; et le plafond de slippage est vérifié par rapport à ce que le payeur transfère réellement, *après* l'ajout des frais de transfert Token-2022, et non par rapport au mouvement brut du coffre.

Aucun changement à la proportionnalité de `k` — les deux totaux et `lp_supply` se mettent à l'échelle par le même facteur.

**Postconditions**

- `lp_supply += lp_token_amount`.
- `vault_0 += needed_token_0` (net de tout frais de transfert Token-2022 à l'entrée).
- `vault_1 += needed_token_1` (net de tout frais de transfert Token-2022 à l'entrée).

**Erreurs courantes** — `ExceededSlippage`, `ZeroTradingTokens`, `InvalidStatus` si le dépôt est en pause.

## `Withdraw`

Brûler les tokens LP et recevoir les deux tokens sous-jacents au prorata.

**Arguments**

```
lp_token_amount:   u64
minimum_token_0:   u64
minimum_token_1:   u64
```

**Comptes**

| # | Nom | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `owner_lp_token` | W |   |
| 5 | `token_0_account` | W |   |
| 6 | `token_1_account` | W |   |
| 7 | `token_0_vault` | W |   |
| 8 | `token_1_vault` | W |   |
| 9 | `token_program` |   |   |
| 10 | `token_program_2022` |   |   |
| 11 | `vault_0_mint` |   |   |
| 12 | `vault_1_mint` |   |   |
| 13 | `lp_mint` | W |   |
| 14 | `memo_program` |   |   |

Les 13 premiers comptes sont identiques à ceux de `Deposit`, et `lp_mint` est inscriptible car les tokens LP sont brûlés. `Withdraw` prend en plus un 14e compte, `memo_program` (contraint par `address = memo::ID`) — ce que `Deposit` ne fait pas. Un `Withdraw` à 13 comptes échoue à la désérialisation Anchor, et le LP ne peut donc pas sortir.

**Mathématiques**

```
total_0 = vault_0 − protocol_fees_0 − fund_fees_0 − creator_fees_0    // same for side 1

out_token_0     = min(total_0, floor(lp_token_amount * total_0 / lp_supply))
receive_token_0 = out_token_0 − transfer_fee(out_token_0)             // Token-2022
require(receive_token_0 >= minimum_token_0, "ExceededSlippage")       // same for side 1

// As with Deposit: the base is the fee-excluded vault total, and the floor is
// checked against what the LP actually receives, after the transfer fee.
```

**Postconditions**

- `lp_supply -= lp_token_amount`.
- Les coffres envoient `out_token_0` / `out_token_1` (brut ; l'utilisateur reçoit net de tout frais de transfert Token-2022).

## `SwapBaseInput`

Swap à entrée exacte.

**Arguments**

```
amount_in:            u64
minimum_amount_out:   u64
```

**Comptes**

| # | Nom | W | S |
|---|------|---|---|
| 1 | `payer` |   | S |
| 2 | `authority` |   |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_token_program` |   |   |
| 10 | `output_token_program` |   |   |
| 11 | `input_token_mint` |   |   |
| 12 | `output_token_mint` |   |   |
| 13 | `observation_state` | W |   |

L'ordre **entrée → sortie** est selon la direction de l'utilisateur, pas selon le `token_0 / token_1` canonique du pool. Le programme détermine quel coffre est lequel en faisant correspondre les mints.

**Mathématiques** — voir [`products/cpmm/math`](/fr/products/cpmm/math).

**Conditions préalables**

- `open_time <= now`.
- `pool_status` autorise le swap.
- Aucun mint en pause ou gelé pour cette autorité.
- `amount_in > 0`.

**Erreurs courantes**

- `ExceededSlippage` — `amount_out < minimum_amount_out`.
- `ZeroTradingTokens` — le trade s'arrondit à zéro.
- `NotApproved` — le pool est en pause pour les swaps via `UpdatePoolStatus`.
- `InvalidInput` — les mints ne correspondent à aucun des mints de coffre du pool.

## `CollectFundFee`

Même structure que `CollectProtocolFee` mais signée par `amm_config.fund_owner` — ou, là encore, par l'admin du programme — et mettant à zéro les compteurs `fund_fees_*`. Même `InvalidOwner` en cas de mauvais signataire.

## `CollectCreatorFee`

Signé par `pool_state.pool_creator`. Il transfère les soldes complets `creator_fees_token_0` et `creator_fees_token_1` aux comptes de tokens du créateur, puis met à zéro les deux compteurs. Il retourne `NoFeeCollect` quand les deux compteurs sont à zéro.

## `CollectCreatorFeePermissionless`

N'importe qui peut déclencher la collecte des frais de créateur. L'instruction envoie toujours les soldes accumulés complets aux comptes de tokens associés canoniques possédés par `pool_state.pool_creator` ; l'appelant ne peut pas choisir un autre créateur ou destination. Si l'une des ATAs est manquante, le payeur finance sa création.

Le `CollectCreatorFee` original reste appelable, donc les clients existants restent compatibles.

**Arguments** — aucun.

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|

| 2 | `creator` |   |   | Doit égaler `pool_state.pool_creator` ; ne signe pas. |
| 3 | `authority` |   |   | PDA d'autorité de coffre et mint LP global CPMM. |
| 4 | `pool_state` | W |   | Contient les compteurs de frais de créateur accumulés. |
| 5 | `token_0_vault` | W |   | Doit correspondre au coffre token 0 du pool. |
| 6 | `token_1_vault` | W |   | Doit correspondre au coffre token 1 du pool. |
| 7 | `vault_0_mint` |   |   | Doit correspondre à `token_0_vault.mint`. |
| 8 | `vault_1_mint` |   |   | Doit correspondre à `token_1_vault.mint`. |
| 9 | `creator_token_0` | W |   | ATA canonique du créateur pour `vault_0_mint` ; créée si manquante. |
| 10 | `creator_token_1` | W |   | ATA canonique du créateur pour `vault_1_mint` ; créée si manquante. |
| 11 | `token_0_program` |   |   | SPL Token ou Token-2022, correspondant au token 0. |
| 12 | `token_1_program` |   |   | SPL Token ou Token-2022, correspondant au token 1. |

**Effet**

- Transfère la totalité de `creator_fees_token_0` et `creator_fees_token_1` des coffres du pool vers les ATAs du créateur.

- Retourne `NoFeeCollect` quand les deux compteurs sont à zéro.

**Arguments**

```
status: u8      // nouveau masque de bits
```

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `authority` |   | S | Doit correspondre à la clé admin du programme CPMM. |

La clé admin est une pubkey **compilée dans le programme** (`crate::admin::ID`), et non l'autorité de mise à niveau BPF — la modifier nécessite une mise à niveau du programme. Voir [`reference/program-addresses`](/fr/reference/program-addresses) pour la valeur et [`security/admin-and-multisig`](/fr/security/admin-and-multisig) pour savoir qui la détient.

## `CreateAmmConfig`

Créer un nouveau palier de frais.

**Arguments**

```
index:             u16
trade_fee_rate:    u64
protocol_fee_rate: u64
fund_fee_rate:     u64
create_pool_fee:   u64
creator_fee_rate:  u64
```

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `owner` | W | S | Admin. |
| 2 | `amm_config` | W |   | `init`ialisé ici. |
| 3 | `system_program` |   |   |

**Conditions préalables**

- Aucune `AmmConfig` existante avec le même `index`.
- `protocol_fee_rate + fund_fee_rate <= FEE_RATE_DENOMINATOR_VALUE`.

<Note>
  **Modifié en 2026-09 : les propriétaires de frais de la nouvelle config ne proviennent plus du signataire.** `create_amm_config` écrit maintenant le `protocol_fee_owner::ID` codé en dur du programme dans `protocol_owner` et `fund_fee_owner::ID` dans `fund_owner`, au lieu de copier la clé du signataire admin dans les deux. Les adresses se trouvent dans [`reference/program-addresses`](/fr/reference/program-addresses#cpmm-fee-owner-wallets).

  Conséquences : les frais d'une `AmmConfig` nouvellement créée atterrissent dans les portefeuilles de frais dédiés plutôt que dans celui de l'admin. L'admin reste un *signataire* accepté pour la collecte — `CollectProtocolFee` / `CollectFundFee` acceptent `amm_config.protocol_owner` / `fund_owner` **ou** `crate::admin::ID` — donc rien n'a besoin d'être pivoté pour balayer ; ce qui a changé, c'est uniquement la destination par défaut des produits. **Les comptes `AmmConfig` existants ne sont pas réécrits** — ce qui y est stocké gouverne toujours, donc lisez toujours `protocol_owner` / `fund_owner` du compte au lieu de supposer l'une ou l'autre valeur. Les paramètres `UpdateAmmConfig` `3` et `4` les font toujours pivoter.
</Note>

## `UpdateAmmConfig`

Modifier les taux de frais ou la propriété sur une `AmmConfig` existante. Prend un `param: u8` (quel champ mettre à jour) et une `value: u64`. La table de répartition complète :

- `param = 0` → `trade_fee_rate` (vérifie `trade_fee_rate + creator_fee_rate < 1_000_000`)
- `param = 1` → `protocol_fee_rate` (vérifie `≤ 1_000_000` et `+ fund_fee_rate ≤ 1_000_000`)
- `param = 2` → `fund_fee_rate` (vérifie `≤ 1_000_000` et `+ protocol_fee_rate ≤ 1_000_000`)
- `param = 3` → `protocol_owner`. La nouvelle clé n'est **pas** dans `value` : ajoutez-la comme `remaining_accounts[0]` (en lecture seule suffit). Elle ne doit pas être la pubkey par défaut, et omettre le compte provoque un panic sur un `unwrap()`.
- `param = 4` → `fund_owner`. Même mécanisme que `3`.
- `param = 5` → `create_pool_fee`
- `param = 6` → `disable_create_pool` (toute `value` non nulle désactive)
- `param = 7` → `creator_fee_rate` (vérifie `creator_fee_rate + trade_fee_rate < 1_000_000`)

Tout autre `param` retourne `InvalidInput`.

Les modifications sont signées par l'admin et affectent **chaque pool lié à cette `AmmConfig`** au prochain swap. Aucune migration ; les pools lisent simplement les nouvelles valeurs.

## `CollectExcessLamports`

Balayage admin des lamports assis au-dessus du minimum exempt de loyer sur les comptes que CPMM contrôle. Ajouté dans la mise à niveau 2026-09 pour que le protocole puisse récupérer le sur-financement que la [réduction de loyer SIMD-0437](/fr/solana-fundamentals/rent-and-reclaimable-rent) laisse derrière sur les comptes créés avant chaque étape.

Seul l'excédent se déplace. Les balances de tokens, les données de compte, les propriétaires, l'état du pool et la courbe restent inchangés, et l'instruction est un no-op contre un compte déjà à son minimum — donc il est sûr de le réexécuter après chaque étape de déploiement.

**Arguments** — aucun.

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Destination pour chaque lamport balayé. Doit être soit l'admin du programme CPMM, soit le portefeuille de collecte de lamports dédié — voir [`reference/program-addresses`](/fr/reference/program-addresses#excess-lamports-collection-wallets). Tout autre signataire échoue avec `InvalidOwner`. |
| 2 | `authority` |   |   | Le PDA d'autorité de coffre et mint LP CPMM au seed `[b"vault_and_lp_mint_auth_seed"]`. Il signe les CPIs du programme de tokens. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Les deux sont requis inconditionnellement ; le programme choisit par compte source. |
| 5.. | `remaining_accounts` | W |   | `M` comptes source à balayer, n'importe quel nombre, n'importe quel ordre. |

**Comment chaque compte source est traité**

Le programme se distribue sur le `owner` du compte source :

| Propriétaire du compte source | Traitement |
|---|---|
| SPL Token ou Token-2022, compte de token non natif ou mint — coffres de pool et mints LP | CPI `WithdrawExcessLamports` (discriminant du programme de tokens `38`), signé par `authority`. |
| SPL Token ou Token-2022, compte de token **natif** (wSOL) | `WithdrawExcessLamports` rejette les comptes natifs. Le programme CPIs `SyncNative`, mesure combien le `amount` enveloppé a grandi, `UnwrapLamports` (discriminant `45`) pour exactement ce delta, puis exige que le solde enveloppé égale sa valeur pré-sync — sinon `LamportsCalculateError` (`6015`). Un coffre de pool côté SOL garde donc sa liquidité complète. |
| Le programme CPMM lui-même — `PoolState`, `AmmConfig`, `ObservationState`, `Permission`, `SupportMintAssociated` | Le programme débite le compte directement jusqu'à `rent.minimum_balance(data_len)`. |
| N'importe quoi d'autre | **Ignoré silencieusement.** Aucune erreur, aucun lamport déplacé. |

Parce qu'il prend une liste `remaining_accounts` non bornée, la taille de la transaction est la vraie limite — la même contrainte que le balayage côté portefeuille décrit dans [`solana-fundamentals/rent-and-reclaimable-rent`](/fr/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**Erreurs courantes** — `InvalidOwner` (`6001`, mauvais signataire), `LamportsCalculateError` (`6015`, l'aller-retour wSOL n'a pas donné zéro), et `InsufficientFunds` du chemin possédé par le programme quand un compte détient moins que son propre minimum de loyer.

**Pas de constructeur SDK.** `@raydium-io/raydium-sdk-v2` ne livre pas de constructeur pour cette instruction, et non plus le repo `raydium-sdk-V2-demo` — c'est un chemin admin. Encodez-le à la main, de la même manière que le balayage côté portefeuille dans [`solana-fundamentals/rent-and-reclaimable-rent`](/fr/solana-fundamentals/rent-and-reclaimable-rent#building-the-instruction) le fait pour l'instruction du programme de tokens.
