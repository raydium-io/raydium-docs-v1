<Info>
  `PlatformConfig` est la surcouche **au niveau de la plateforme** qui s'ajoute à [`GlobalConfig`](/fr/products/launchlab/global-config). Tandis que `GlobalConfig` définit les règles au niveau du protocole (« les frais de trading sont 1 %, l'offre doit être au minimum 10M, seul ce portefeuille peut diplômer »), `PlatformConfig` est ce que chaque plateforme de lancement — pump.fun, l'interface propre de Raydium, les launchpads tiers — utilise pour ajouter ses frais, réclamer sa part du LP post-graduation, restreindre les formes de courbes que leurs lancements peuvent choisir, et afficher leur image de marque (nom, site web, image) on-chain.
</Info>

## Qu'est-ce que c'est

Un compte `PlatformConfig` gère cinq préoccupations transversales pour une plateforme :

1. **Image de marque** — nom, site web, lien d'image, tous stockés en ligne pour que tout explorateur ou agrégateur puisse afficher la plateforme qui a lancé un token.
2. **Frais de plateforme** — un frais de trading supplémentaire (`fee_rate`) en plus du `trade_fee_rate` du protocole. S'accumule dans le `platform_fee_wallet` de la plateforme. Plafonné à 500 bps (`50000`) sur les chemins de création et de mise à jour, relevé de 100 bps (`10000`) le 2026-08-26 — voir [Plafonds de taux](#plafonds-de-taux).
3. **Répartition de migration LP** — trois entiers stockés (`platform_scale`, `creator_scale`, `burn_scale`) qui totalisent `1_000_000`. Avant la mise à jour du 2026-08-17, l'échelle du créateur produisait une clé de frais créateur séparée. Les migrations exécutées après la mise à jour combinent les deux premières en une part LP verrouillée détenue par la plateforme ; le reste est brûlé.
4. **Liste blanche des paramètres de courbe** — un `Vec<PlatformCurveParam>` listant exactement quelles combinaisons `(supply, total_base_sell, total_quote_fund_raising, migrate_type, migrate_cpmm_fee_on, vesting_params...)` sont autorisées sur cette plateforme. Si le vecteur est vide ou toutes les entrées sont invalides, **toute** combinaison est autorisée ; sinon les lancements doivent correspondre exactement à l'une des entrées.
5. **Liste blanche de configuration globale** — une restriction optionnelle qui exige un `PlatformAllowConfig` créé par la plateforme pour le `GlobalConfig` sélectionné.

Dérivation PDA :

```ts
const [platformConfigPda] = PublicKey.findProgramAddressSync(
  [
    Buffer.from("platform_config"),
    platformAdmin.toBuffer(),       // clé publique propriétaire de la plateforme
  ],
  LAUNCHLAB_PROGRAM_ID,
);
```

(Voir `create_platform_config` dans le code source pour la liste canonique des seeds.)

## Disposition

```rust
// states/platform_config.rs
pub const PLATFORM_CONFIG_SEED: &str = "platform_config";
pub const NAME_SIZE: usize = 64;
pub const WEB_SIZE:  usize = 256;
pub const IMG_SIZE:  usize = 256;
pub const MAX_CREATOR_FEE_RATE: u64 = 5000;       // 50 bps (dénominateur 1_000_000)
pub const MAX_TRANSFER_FEE_RATE: u16 = 500;       // 5%   (dénominateur 10_000)
pub const MAX_CURVE_PARAMS: usize = 10;

#[account]
pub struct PlatformConfig {
    pub epoch:                       u64,
    pub platform_fee_wallet:         Pubkey,            // signe ClaimPlatformFee
    pub platform_nft_wallet:         Pubkey,            // reçoit la part NFT de la plateforme à la graduation CPMM
    pub platform_scale:              u64,               // part du LP frappé pour le NFT de la plateforme
    pub creator_scale:               u64,               // part du créateur avant la mise à jour ; ajoutée à la part de la plateforme après
    pub burn_scale:                  u64,               // part du LP brûlée définitivement
    pub fee_rate:                    u64,               // frais de trading de la plateforme (1/1_000_000)
    pub name:                        [u8; 64],          // utf-8 complété avec des zéros
    pub web:                         [u8; 256],
    pub img:                         [u8; 256],
    pub cpswap_config:               Pubkey,            // AmmConfig CPMM que le pool post-grad liera
    pub creator_fee_rate:            u64,               // frais côté créateur prélevés avant la graduation
    pub transfer_fee_extension_auth: Pubkey,            // pour les lancements Token-2022 : autorité de retrait du mint, autorité de configuration des frais à la graduation
    pub platform_vesting_wallet:     Pubkey,
    pub platform_vesting_scale:      u64,               // part de la plateforme du total_locked_amount
    pub platform_cp_creator:         Pubkey,            // créateur optionnel du pool CPMM post-graduation
    pub restrict_global_config:      u8,                // 0 = sans restriction, 1 = exiger PDA d'autorisation
    pub padding:                     [u8; 107],
    pub curve_params:                Vec<PlatformCurveParam>, // liste blanche des formes de courbes autorisées
}
```

`platform_scale + creator_scale + burn_scale` doit égaler `1_000_000`. Avant la mise à jour du 2026-08-17, `creator_scale` était verrouillé séparément et sa clé de frais allait au créateur du token. Pour les migrations exécutées après la mise à jour, elle est ajoutée à `platform_scale` et ses droits LP verrouillés vont à la plateforme à la place. Exemples de résultats selon la logique mise à jour :

- `(0, 100_000, 900_000)` — 90 % du LP brûlé, 10 % verrouillé pour la plateforme.
- `(50_000, 100_000, 850_000)` — 85 % brûlé, 15 % verrouillé pour la plateforme.
- `(0, 0, 1_000_000)` — brûlage complet, pas de frappe NFT. Lancements stricts « sans initiés ».

## Champs d'image de marque

`name`, `web` et `img` sont des tableaux d'octets en ligne complétés avec des zéros jusqu'à leurs constantes de taille. Pour les lire en tant que chaînes, découpez jusqu'au premier `\0` :

```ts
function readString(bytes: Uint8Array): string {
  const end = bytes.indexOf(0);
  return Buffer.from(end === -1 ? bytes : bytes.subarray(0, end)).toString("utf-8");
}
```

Les constantes sont délibérément généreuses (`name: 64`, `web: 256`, `img: 256`) pour que les plateformes puissent inclure suffisamment de métadonnées pour les explorateurs et agrégateurs sans toucher au stockage off-chain. Tout ce qui dépasse ces tailles revient avec `InvalidInput` à `CreatePlatformConfig`.

## Mécanique des frais

Un swap sur une courbe liée à un `PlatformConfig` facture trois frais en couches :

```
trade_fee     = amount_in × global_config.trade_fee_rate    / 1_000_000
platform_fee  = amount_in × platform_config.fee_rate        / 1_000_000
creator_fee   = amount_in × platform_config.creator_fee_rate / 1_000_000

amount_after_fee = amount_in − trade_fee − platform_fee − creator_fee
```

- `trade_fee` s'accumule dans le `protocol_fee_owner` du protocole (réclamé via `CollectFee`).
- `platform_fee` s'accumule dans un coffre par plateforme (réclamé via `ClaimPlatformFee` ou `ClaimPlatformFeeFromVault` ; voir [`instructions`](/fr/products/launchlab/instructions)).
- `creator_fee` s'accumule dans un coffre par créateur clé par la clé publique du créateur + le mint de cotation (réclamé via `ClaimCreatorFee`).

### Plafonds de taux

Les deux taux sont libellés en `1/1_000_000`, donc `5000` est 50 bps et `50000` est 500 bps.

| Taux | Plafond | Appliqué dans |
|---|---|---|
| `fee_rate` | `50000` (500 bps) | `PlatformParams::check()` à la création — revient avec `InvalidInput`. `update_platform_fee_rate` à chaque variante de mise à jour qui la touche (`FeeRate` et `AllInfo`) — revient avec `InvalidPlatformInfo`. |
| `creator_fee_rate` | `MAX_CREATOR_FEE_RATE = 5000` (50 bps) | `create_platform_config` à la création et `update_creator_fee_rate` à la mise à jour — les deux reviennent avec `InvalidPlatformInfo`. |

Les deux points d'application pour `fee_rate` sont des appels `require!` séparés dans des fichiers différents, ils portent donc des codes d'erreur différents, mais ils appliquent le même plafond. Une plateforme créée à n'importe quel taux autorisé peut être modifiée ultérieurement, y compris via la variante `AllInfo` en masse qui réécrit chaque champ à la fois.

Les deux plafonds `fee_rate` étaient à l'origine 100 bps (`10000`). Le plafond de mise à jour est passé à `25000` (250 bps) le 2026-01-27 ; le 2026-08-26 les deux sont passés à `50000` (500 bps) — voir [l'entrée du journal des modifications](/fr/reference/changelog/2026-08-26-launchlab-platform-fee-rate-cap).

`GlobalConfig.max_share_fee_rate` ne limite **pas** l'un ou l'autre taux. Il limite l'argument `share_fee_rate` par transaction que les quatre instructions de swap prennent — les frais de parrainage — et rien d'autre. Voir [`global-config`](/fr/products/launchlab/global-config#fees).

## Autorités de frais de transfert Token-2022

`transfer_fee_extension_auth` nomme la clé de plateforme qui finit par détenir les autorités `TransferFeeConfig` du mint de base lorsqu'un lancement est créé via `InitializeWithToken2022` avec un frais de transfert attaché. L'extension porte deux autorités, et elles sont remises à **différents points du cycle de vie du lancement** :

| Autorité | Détenteur à la création du mint | Détenteur après `MigrateToCpswap` |
|---|---|---|
| `withdraw_withheld_authority` — retire les frais que Token-2022 retient sur les comptes de tokens | `transfer_fee_extension_auth`, écrit directement dans le mint. Revient à la PDA `authority` du lancement lorsque le champ est `Pubkey::default()`. | Déjà la clé de la plateforme, donc rien ne bouge. La migration la réassigne uniquement lorsque la PDA `authority` la détient toujours. |
| `transfer_fee_config_authority` — change le taux de frais et les frais maximaux | Toujours la PDA `authority` du lancement. | `transfer_fee_extension_auth`, à condition que ce champ soit non-défaut. |

Avant le 2026-08-27, le mint était créé avec la PDA `authority` sur les deux autorités, et les deux ont été transférées à la plateforme à la graduation. Le programme n'expose aucune instruction de retrait ou de récolte, donc les frais retenus pendant la phase de courbe de liaison étaient inaccessibles jusqu'à la graduation du lancement. Écrire le côté retrait à la création du mint les rend réclamables dès le premier trade — voir [l'entrée du journal des modifications](/fr/reference/changelog/2026-08-27-launchlab-token2022-withheld-authority).

Deux conséquences à prévoir :

- **Définissez le champ avant de lancer, pas après.** Un lancement créé tandis que `transfer_fee_extension_auth` est `Pubkey::default()` met la PDA `authority` sur le côté retrait. Définir le champ plus tard fonctionne toujours — la graduation trouve la PDA en place et remet l'autorité — mais rien ne peut retirer le solde retenu entre-temps.
- **Faire tourner le champ en cours de lancement divise les deux autorités.** Changez `transfer_fee_extension_auth` entre la création et la graduation d'un lancement et l'autorité de retrait du mint reste avec la clé configurée à la création (la PDA ne la détient plus, donc la migration saute ce transfert) tandis que l'autorité de configuration des frais va à la nouvelle clé. Faites tourner entre les lancements, ou prévoyez de réconcilier les deux clés vous-même via Token-2022 directement.

Une plateforme qui laisse le champ à `Pubkey::default()` pour toute la vie d'un lancement garde les deux autorités sur la PDA `authority` définitivement : le taux de frais ne peut jamais être changé et le solde retenu ne peut jamais être retiré. N'attachez un frais de transfert à un lancement que si la plateforme a l'intention de détenir ces clés.

## Répartition de migration NFT (CPMM uniquement)

Lorsqu'un lancement diplôme vers CPMM, l'instruction de migration divise les tokens LP frappés par `CPMM::InitializeWithPermission` de deux façons :

```
lp_to_platform = floor(lp_total × (platform_scale + creator_scale) / 1_000_000)
lp_to_burn     = lp_total − lp_to_platform
```

Si `lp_to_platform` est non-zéro, le programme LP-Lock l'enveloppe dans un NFT Fee Key détenu par `platform_nft_wallet`. Cela remplace le comportement pré-mise à jour qui créait des Fee Keys de plateforme et de créateur séparés. Les Fee Keys créées par les migrations complétées avant la mise à jour restent inchangées. Ce droit de frais LP est séparé des frais de créateur CPMM contrôlés par `platform_cp_creator`.

La part brûlée est brûlée directement, donc aucun compte ne peut la retirer ou réclamer les frais LP représentés par cette part.

Les lancements existants avec `migrate_type = 0` stocké peuvent toujours utiliser le chemin AMM v4 hérité. La nouvelle initialisation rejette ce type de migration.

## Liste blanche des paramètres de courbe

`curve_params: Vec<PlatformCurveParam>` est le mécanisme de la plateforme pour restreindre quelles formes de courbes ses lancements peuvent choisir. Si le vecteur est non-vide et au moins une entrée est valide, le programme applique à `Initialize` que les paramètres du lancement correspondent exactement à au moins une entrée.

```rust
#[derive(AnchorSerialize, AnchorDeserialize, Clone)]
pub struct PlatformCurveParam {
    pub epoch:                u64,
    pub index:                u8,           // ordinal dans la liste blanche de cette plateforme
    pub global_config:        Pubkey,       // quel GlobalConfig cette entrée s'applique à
    pub bonding_curve_param:  BondingCurveParam,
    pub padding:              [u64; 50],
}

#[derive(AnchorSerialize, AnchorDeserialize, Clone)]
pub struct BondingCurveParam {
    pub migrate_type:               u8,    // les nouveaux lancements exigent 1 = CPMM ; u8::MAX = joker
    pub migrate_cpmm_fee_on:        u8,    // 0 = cotation uniquement, 1 = les deux. u8::MAX = joker
    pub supply:                     u64,   // 0 = joker
    pub total_base_sell:            u64,   // 0 = joker
    pub total_quote_fund_raising:   u64,   // 0 = joker
    pub total_locked_amount:        u64,   // u64::MAX = joker
    pub cliff_period:               u64,   // u64::MAX = joker
    pub unlock_period:              u64,   // u64::MAX = joker
}
```

Chaque champ a une valeur sentinelle qui signifie **joker** (toute valeur correspond) : `u64::MAX` pour les champs `u64`, `u8::MAX` pour les champs `u8`, `0` pour les champs d'offre / vente / levée de fonds. Un `BondingCurveParam` avec tous les sentinelles est « autoriser n'importe quoi » — équivalent au comportement de liste blanche vide.

L'algorithme de correspondance à `Initialize` :

1. Filtrez `curve_params` aux entrées dont `global_config` correspond au `GlobalConfig` choisi du lancement.
2. Si la liste filtrée est vide, autorisez n'importe quels paramètres (la plateforme n'a rien listé en blanc pour ce `GlobalConfig`).
3. Si chaque entrée de la liste filtrée a `all_is_invalid()` (chaque champ est le joker), autorisez n'importe quels paramètres.
4. Sinon, itérez les entrées ; pour chaque entrée, vérifiez les paramètres du lancement contre chaque champ non-joker. Si tous les champs non-joker correspondent, acceptez et retournez.
5. Si aucune entrée n'a correspondu, revenez avec `InvalidInput`.

Cela permet à une plateforme de dire « nous n'autorisons que la forme standard 1B-offre / 800M-vendu / 30k-USDC-levée / pas-vesting » en écrivant une seule entrée avec des valeurs concrètes pour ces quatre champs et des jokers partout ailleurs. Ou une plateforme plus stricte pourrait énumérer trois ou quatre formes discrètes, une par niveau de lancement supporté.

`MAX_CURVE_PARAMS = 10` plafonne la taille de la liste blanche.

## `PlatformAllowConfig` — restreindre une plateforme

Chaque plateforme décide si elle restreint quel `GlobalConfig` ses lancements peuvent utiliser. Définissez `restrict_global_config` avec `UpdatePlatformConfig::RestrictGlobalConfig(0 | 1)`.

```rust
pub const PLATFORM_ALLOW_CONFIG_SEED: &str = "platform_allow_config";

#[account]
pub struct PlatformAllowConfig {
    pub bump:            u8,
    pub platform_config: Pubkey,
    pub global_config:   Pubkey,
    pub padding:         [u64; 8],
}
```

Seeds PDA : `[b"platform_allow_config", platform_config, global_config]`.

L'administrateur de la plateforme crée ou ferme un compte par paire autorisée via `CreatePlatformAllowConfig` et `ClosePlatformAllowConfig`. Lorsque la restriction est `1`, l'initialisation recherche dans `remaining_accounts` la PDA attendue et rejette un compte manquant avec `NotEnoughRemainingAccounts`. Lorsque la restriction est `0`, aucun compte d'autorisation n'est requis.

Le compte `PlatformGlobalAccess` géré par l'administrateur du protocole antérieur et ses instructions de création/fermeture sont retirés. Les tailles existantes de `PlatformConfig` et `GlobalConfig` ne changent pas, mais les décodeurs doivent remplacer l'ancien drapeau global par le nouveau drapeau de plateforme. Les anciennes PDAs d'accès ne sont pas consommées par la nouvelle vérification.

## Chemin de mise à jour

| Instruction | Qui signe | Ce qui change |
|-------------|-----------|--------------|
| `CreatePlatformConfig` | administrateur de plateforme (une seule fois) | Initialise le compte avec `PlatformParams`. |
| `UpdatePlatformConfig` | administrateur de plateforme | Dispatch générique clé par un `param: u8` ; mute un champ par appel, ou chaque champ à la fois via `AllInfo`. Les champs d'image de marque, les taux de frais, le portefeuille de vesting et les différents portefeuilles sont tous définissables via ceci. Les deux taux de frais sont re-validés contre les plafonds dans [Plafonds de taux](#plafonds-de-taux) à chaque variante qui les touche. |
| `CreatePlatformAllowConfig` / `ClosePlatformAllowConfig` | administrateur de plateforme | Ajouter ou supprimer un `GlobalConfig` autorisé pour cette plateforme. |
| `UpdatePlatformCurveParam` | administrateur de plateforme | Ajouter ou remplacer une entrée `PlatformCurveParam` par `(global_config, index)`. |
| `RemovePlatformCurveParam` | administrateur de plateforme | Effacer une entrée (la définir à tous-sentinelles = joker). |
| `ClaimPlatformFee` | `platform_fee_wallet` | Balayer les frais de plateforme par pool depuis `PoolState.quote_vault`. |
| `ClaimPlatformFeeFromVault` | `platform_fee_wallet` | Balayer le coffre de frais par plateforme (PDA à `[platform_config, quote_mint]`). |

Les rotations de portefeuille (`platform_fee_wallet`, `platform_nft_wallet`, `platform_vesting_wallet`, `platform_cp_creator`, `transfer_fee_extension_auth`, `cpswap_config`) passent toutes par `UpdatePlatformConfig`. Lisez la table de dispatch `update_platform_config` du code source pour les codes `param` exacts.

## Pièges courants

- **Sentinelles de liste blanche mal définies.** Un `BondingCurveParam` avec `total_locked_amount = 0` n'est **pas** un joker — il correspond aux lancements qui refusent explicitement le vesting. Le joker pour ce champ est `u64::MAX`. Le même piège existe pour `cliff_period` et `unlock_period`. Utilisez `clear()` (que le programme expose) pour définir correctement les sentinelles.
- **Arrondi de répartition NFT.** Les trois échelles doivent totaliser exactement `1_000_000`. Les erreurs d'une unité à `CreatePlatformConfig` reviennent ; une erreur d'une unité à l'exécution frapperait ou brûlerait une unité LP supplémentaire, ce que la vérification d'égalité stricte est là pour prévenir.
- **Double allocation de vesting de plateforme.** Si `platform_vesting_scale > 0`, la plateforme doit appeler `CreatePlatformVestingAccount` une fois après la fin de la levée de fonds du lancement ; si elle oublie, cette part reste non allouée et dormante à jamais (le budget `total_locked_amount` du lancement est consommé mais la plateforme ne réclame jamais).
- **Ambiguïté de `platform_cp_creator`.** Lorsqu'elle est définie à `Pubkey::default()`, le créateur du lancement est enregistré comme `pool_creator` du pool CPMM post-graduation ; lorsqu'elle est définie à une clé réelle, cette clé est enregistrée à la place. Cela détermine le bénéficiaire des frais de créateur CPMM post-graduation et qui peut signer le chemin `CPMM::CollectCreatorFee` d'origine. Le chemin de collection sans permission paie toujours les ATAs canoniques de cette clé enregistrée. Décidez au moment de la création de la configuration de plateforme quel modèle vous voulez.
- **`transfer_fee_extension_auth` défini tard ou tourné.** Le champ est lu deux fois par lancement Token-2022 — une fois à la création du mint pour `withdraw_withheld_authority`, une fois à la graduation pour `transfer_fee_config_authority` — donc une valeur qui change entre ces deux moments laisse les deux autorités sur des clés différentes. Voir [Autorités de frais de transfert Token-2022](#autorités-de-frais-de-transfert-token-2022).
- **Restriction sans compte d'autorisation.** Activer `restrict_global_config` avant de créer le `PlatformAllowConfig` requis bloque les nouveaux lancements qui sélectionnent cette configuration.
