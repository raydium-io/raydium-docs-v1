<Note>
  **Il n'y a pas d'instruction d'initialisation de tableau de ticks, et aucune n'est nécessaire.** Un tableau de ticks est créé *à l'intérieur*
  `OpenPosition*` / `IncreaseLiquidity*` par `TickArrayState::get_or_create_tick_array`, payé par
  `payer`. Passez le PDA du tableau de ticks (possiblement encore non initialisé, appartenant au système) en tant que
  `tick_array_lower` / `tick_array_upper` et le programme l'alloue s'il est manquant.
  `OpenLimitOrder` fait de même pour son unique `tick_array`.
</Note>

La plupart des instructions réservées aux administrateurs (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) sont contrôlées par la clé publique `admin` codée en dur du programme. `CreateSupportMintAssociated` / `CloseSupportMintAssociated` acceptent soit la clé publique `admin` **soit** une clé de propriétaire de support-mint dédiée ; `CollectExcessLamports` accepte soit la clé publique `admin` **soit** un portefeuille dédié de collecte de lamports. Les instructions admin du flux de récompenses (`TransferRewardOwner`, `CollectRemainingRewards`) sont contrôlées par le financeur de récompenses, pas par l'admin du programme.

Le suffixe V2 signifie « supporte Token-2022 sur les coffres-forts / NFT, nécessite l'emplacement d'extension bitmap ». Le SDK choisit V2 par défaut pour les nouveaux pools.

## `CreatePool`

**Arguments**

```
sqrt_price_x64: u128           // prix initial
open_time:      u64            // les swaps sont rejetés avant cette heure
```

**Comptes (abrégés)**

| # | Nom | W | S | Notes |
|---|-----|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Palier de frais choisi. |
| 3 | `pool_state` | W |   | `init` ici. |
| 4 | `token_mint_0` |   |   | Trié. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` ici, appartenant au PDA d'autorité du pool. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` ici. |
| 9 | `tick_array_bitmap` | W |   | Le PDA `TickArrayBitmapExtension` ; `init` ici. |
| 10 | `token_program_0` |   |   | Le programme qui possède `token_mint_0` — SPL Token **ou** Token-2022. |
| 11 | `token_program_1` |   |   | Le programme qui possède `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Les emplacements 10 et 11 sont **par mint**, pas « SPL Token puis Token-2022 ». Chacun est contraint par
  `mint::token_program` sur le mint correspondant, donc pour un pool dont `token_mint_0` est Token-2022 et
  `token_mint_1` est SPL classique, vous devez passer Token-2022 à l'emplacement 10 et SPL Token à l'emplacement 11.
  `CreateCustomizablePool` et `CreateCustomizablePoolV2` utilisent les mêmes deux emplacements.
</Warning>

**Préconditions**

- `token_mint_0 < token_mint_1` par ordre d'octets.
- `amm_config.disable_create_pool == false`.
- Les mints ne sont pas rejetés par la liste blanche d'extension Token-2022.

**Postconditions**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (aucune position encore).
- `pool_state.fee_on = FromInput` (défaut hérité).
- `pool_state.dynamic_fee_info` est mis à zéro (frais dynamiques désactivés).

## `CreateCustomizablePool`

Recommandé pour les nouveaux pools. Même effet que `CreatePool` plus le mode de collecte des frais par pool et une activation optionnelle des frais dynamiques.

**Arguments**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Comptes** — exactement les 13 comptes déclarés de `CreatePool`. `dynamic_fee_config` n'est **pas** un compte déclaré.

<Warning>
  Quand `enable_dynamic_fee = true`, le `DynamicFeeConfig` à capturer doit être fourni en tant que
  **dernier** `remaining_account` — le gestionnaire lit `ctx.remaining_accounts.last()`. Tout
  PDA de contournement `SupportMintAssociated` doit donc venir *avant* lui, ou le programme capture
  le mauvais compte et échoue la désérialisation. L'omettre alors que le drapeau est défini échoue avec
  `AccountLack`.
</Warning>

**Préconditions** — identiques à `CreatePool`. Si `enable_dynamic_fee = false`, aucun `remaining_account` n'est requis et tous ceux qui sont passés ne sont scannés que pour les enregistrements de support-mint.

**Postconditions**

- `pool_state.fee_on` défini à la variante `CollectFeeOn` choisie.
- Si les frais dynamiques ont été activés : `pool_state.dynamic_fee_info` est initialisé à partir du `DynamicFeeConfig` fourni (cinq paramètres d'étalonnage copiés ; champs d'état mis à zéro).
- Sinon : `pool_state.dynamic_fee_info` est mis à zéro (= frais dynamiques inactifs à jamais pour ce pool).

`fee_on` et le bit d'activation des frais dynamiques sont définis **uniquement** à la création du pool. Il n'y a pas de mise à niveau sur place — les pools créés via le `CreatePool` hérité ne peuvent pas acquérir rétroactivement les frais dynamiques ou les frais unilatéraux. Les nouveaux déploiements doivent utiliser cette instruction par défaut.

## `CreateCustomizablePoolV2`

Les instructions `CreatePool` et `CreateCustomizablePool` dérivent l'adresse PDA du pool à partir de `["pool", amm_config, token_mint_0, token_mint_1]`, ce qui signifie qu'il existe exactement **une** adresse de pool canonique par triplet `(config, mint0, mint1)` — une deuxième tentative d'`init` aux mêmes seeds échoue. `CreateCustomizablePoolV2` lève cette restriction en intégrant un `seed_index: u16` fourni par le client dans les seeds de la PDA du pool, permettant **plusieurs pools pour la même paire et le même palier de frais** — chacun à sa propre adresse. N'importe qui peut l'appeler.

Tout le reste concernant le pool est identique à `CreateCustomizablePool` : il prend les mêmes `CreateCustomizableParams` et supporte les frais unilatéraux et l'opt-in pour les frais dynamiques.

<Note>
  Jusqu'à la [mise à jour du 2026-10-22](/fr/reference/changelog/2026-10-22-clmm-customizable-pool-v2), cette instruction s'appelait `CreatePermissionedPool` et exigeait que le payeur détienne une PDA `Permission` émise par un administrateur. La mise à jour l'a renommée, a supprimé le compte `permission` et a supprimé la machinerie des permissions. Le discriminateur a changé avec le nom, donc les clients construits contre `CreatePermissionedPool` doivent être reconstruits.
</Note>

**Arguments**

```rust
customizable_params: CreateCustomizableParams   // même struct que CreateCustomizablePool
seed_index:          u16                          // doit être non-zéro ; intégré dans les seeds de la PDA du pool
```

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Paie le loyer pour chaque nouveau compte. N'importe quel portefeuille. |
| 2 | `pool_creator` |   |   | Enregistré comme `pool_state.owner`. Peut différer de `payer`. N'est pas un signataire et n'est pas vérifié. |
| 3 | `amm_config` |   |   | Palier de frais auquel le pool se lie. |
| 4 | `pool_state` | W |   | `init` à `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`. |
| 5 | `token_mint_0` |   |   | Doit être trié avant `token_mint_1`. |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`. |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`. |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`. |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`. |
| 11 | `token_program_0` |   |   | Programme qui possède `token_mint_0`. |
| 12 | `token_program_1` |   |   | Programme qui possède `token_mint_1`. |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts` : les PDAs du registre de support-mint quand un mint Token-2022 en a besoin, et la `DynamicFeeConfig` **en dernier** quand `enable_dynamic_fee = true` — comme dans `CreateCustomizablePool`.

**Préconditions**

- `seed_index != 0`. Un `seed_index` de `0` est réservé aux pools hérités et est rejeté ici ; la composante seed `[0, 0]` est ce qui fait qu'une adresse de pool hérité s'effondre à la forme classique à quatre seeds.
- Aucun pool n'existe déjà à l'adresse dérivée.
- Mêmes règles de mint / liste d'autorisation que `CreatePool`.

**Postconditions**

- Un nouveau `pool_state` existe à l'adresse dérivée du `seed_index`, avec `pool_state.seed_index = seed_index`.
- Tous les autres post-états correspondent à `CreateCustomizablePool` (mode de frais, frais dynamiques optionnels).

<Warning>
  Parce que `pool_creator` n'est pas vérifié, n'importe quel payeur peut écrire n'importe quelle adresse dans `pool_state.owner`. Cette adresse peut appeler `InitializeReward` sur le pool, mais ce n'est pas une preuve de qui a créé le pool. Les intégrateurs ne doivent pas étiqueter ou classer les pools V2 par leur `owner`.
</Warning>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Créer une nouvelle position à l'intérieur d'un pool existant.

**Arguments**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
```

`OpenPositionWithToken22Nft` est la même liste avec `metadata_account` (5) et `metadata_program` (19) **supprimés** — il écrit les métadonnées de la position via l'extension de métadonnées Token-2022 sur le mint du NFT à la place — donnant 20 comptes. Son `position_nft_mint` est un `Signer` nu et `position_nft_account` un `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` n'est pas un compte déclaré sur l'une ou l'autre variante.** Quand la plage de la position se situe en dehors du `tick_array_bitmap` en ligne du pool (±512 tableaux de ticks), ajoutez la PDA `TickArrayBitmapExtension` aux seeds `["pool_tick_array_bitmap_extension", pool_state]` comme `remaining_accounts[0]`.
</Warning>

**Mathématiques** — voir [`products/clmm/math`](/fr/products/clmm/math). Étant donné `base_flag`, le programme résout soit `liquidity` soit `(amount_0_max, amount_1_max)` en `L` réel et les montants de tokens réels consommés.

**Préconditions**

- `tick_lower < tick_upper`, tous deux multiples de `pool.tick_spacing`, dans `[MIN_TICK, MAX_TICK]`.
- Les deux PDAs de tableaux de ticks sont passées. Elles n'ont **pas** besoin d'exister déjà — `get_or_create_tick_array` alloue une manquante à la charge du `payer` à l'intérieur de cette instruction. Il n'y a pas d'instruction d'init-tick-array séparée.
- L'utilisateur a au moins `amount_0_max` et `amount_1_max` dans les ATAs sources.

**Postconditions**

- `personal_position` existe, `liquidity` défini, `fee_growth_inside_last` capturé.
- Les entrées du tableau de ticks à `tick_lower` et `tick_upper` mises à jour (`liquidity_gross += L`, `liquidity_net ± L`, snapshots de croissance des frais maintenus).
- `pool_state.liquidity += L` si la position est en plage (`tick_lower ≤ tick_current < tick_upper`).
- Le mint du NFT de la position enregistre `pool_state` comme autorité de gel. L'autorité de mint est supprimée après que le seul NFT soit frappé. L'enregistrement de l'autorité de gel ne change pas l'état du compte de tokens du NFT.
- Le compte de tokens du NFT reste dégelé sauf si l'instruction est `OpenPositionV2` ou `OpenPositionWithToken22Nft` **et** que l'autorité de gel de l'un ou l'autre mint du coffre correspond à la liste des émetteurs restreints du CLMM. Seul ce chemin V2 correspondant gèle le compte. `OpenPosition` V1 ne gèle pas.

**Erreurs courantes** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (une extrémité n'est pas un multiple de `tick_spacing`), `InvalidTickIndex` (en dehors de `[MIN_TICK, MAX_TICK]`), `MissingTickArrayBitmapExtensionAccount` (plage en dehors du bitmap en ligne et l'extension n'a pas été ajoutée), `NotApproved` (`pool_state.status` bloque l'ouverture), `ZeroAmountSpecified`.

<Note>
  Le gel de position n'ajoute pas de comptes d'instruction déclarés ni d'arguments. Les clients peuvent ouvrir ces positions avec les mises en page V2 existantes. Le comportement est sélectionné on-chain à partir de `vault_0_mint` et `vault_1_mint`.
</Note>

| 13 | `token_program_2022` |   |   |
| 14 | `memo_program` |   |   |
| 15 | `vault_0_mint` |   |   |
| 16 | `vault_1_mint` |   |   |

**Comptes restants** — trois par récompense active collectée, dans l'ordre `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`. Ajoutez en préfixe la PDA `TickArrayBitmapExtension` quand la plage de la position se situe en dehors du bitmap en ligne.

<Note>
  C'est aussi la **seule** façon de collecter les frais et récompenses. Pour collecter sans changer la position, appelez-la avec `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`.
</Note>

**Effet**

- Calcule `(amount_0, amount_1)` pour le `L` supprimé étant donné le `sqrt_price_x64` actuel.
- Règle les frais/récompenses accumulés depuis le dernier accès, comme `IncreaseLiquidity`.
- Transfère `amount_0 + fees_owed_0` et `amount_1 + fees_owed_1` hors des coffres vers l'utilisateur.
- Décrémente les compteurs de liquidité ; si le nouveau `personal_position.liquidity == 0`, la position est éligible pour `ClosePosition`.

**Slippage** — `amount_0_min` et `amount_1_min` sont les minimums que l'utilisateur accepte nets des frais de transfert Token-2022 du côté de la sortie.

## `ClosePosition`

Brûler le NFT de position et fermer `PersonalPositionState`.

**Comptes déclarés**

| # | Name | W | S | Notes |
|---|------|---|---|-------|
| 1 | `nft_owner` | W | S | Doit posséder le compte de token NFT contenant le montant `1`. |
| 2 | `position_nft_mint` | W |   | Doit correspondre à `personal_position.nft_mint`. |
| 3 | `position_nft_account` | W |   | Compte du propriétaire du NFT ; peut être un Token SPL classique ou Token-2022. |
| 4 | `personal_position` | W |   | Fermé vers `nft_owner`. |
| 5 | `system_program` |   |   | Ferme l'état de position. |
| 6 | `token_program` |   |   | Doit posséder le mint NFT et le compte de token. |

**Comptes restants**

- NFT non gelé : aucun requis ; un compte de pool supplémentaire est inoffensif car le gestionnaire ne le lit pas.
- NFT gelé : ajouter `personal_position.pool_id` comme premier compte restant. Le programme le charge en tant que `PoolState` et utilise ses graines PDA pour signer le dégel.

**Préconditions**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Tous les compteurs de récompense `reward_amount_owed == 0`.

(C'est-à-dire, collecter tout et diminuer à zéro d'abord.)

**Effet**

- Si le compte de token NFT est gelé, vérifie que le premier compte restant est égal à `personal_position.pool_id`, puis le dégèle avec le PDA du pool.
- Brûle le NFT.
- Ferme le compte de token NFT et `personal_position`, remboursant le loyer à `nft_owner`. Si le NFT de position utilise Token-2022, il ferme également le mint NFT ; les mints Token SPL classiques ne peuvent pas être fermés et restent avec une offre zéro.

Le dégel, la combustion et la fermeture sont atomiques. Le NFT ne peut pas devenir transférable entre ces étapes.

**Rupture client conditionnelle** — la disposition IDL déclarée est inchangée, donc les clients hérités continuent de fermer les positions existantes et non gelées. Un constructeur hérité qui omet le compte de pool restant échoue avec `AccountLack` lors de la fermeture d'une position gelée. Passer le pool pour chaque fermeture est la stratégie compatible la plus simple.

Les appelants passent une liste classée de tableaux de ticks couvrant le parcours de swap attendu ; le programme en utilise autant que nécessaire. Le SDK calcule cette liste via `PoolUtils.computeAmountOutFormat` ou le point de terminaison de devis de l'API.

- `now >= open_time`.
- `sqrt_price_limit_x64` est du bon côté de `sqrt_price_x64` pour la direction.

**Erreurs courantes** — `TooLittleOutputReceived` (slippage exact-in), `TooMuchInputPaid` (slippage exact-out), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (bit de swap défini sur `pool_state.status`). CLMM n'a pas de variante `ExceededSlippage` — ce nom est celui de CPMM — et pas de `TickArrayNotFound`.

**Ce que `SwapV2` fait en interne et que les appelants doivent savoir** (version post-2025) :

1. **Surcharge de frais dynamique** — si `pool.dynamic_fee_info` est non nul, le programme met à jour l'accumulateur de volatilité en utilisant la distance de tick parcourue depuis le dernier swap (avec les règles de filtre/décroissance de [`products/clmm/fees`](/fr/products/clmm/fees)) et ajoute un `dynamic_fee_component` en plus de `AmmConfig.trade_fee_rate`. Les frais totaux sont plafonnés à 10 % (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Appariement des ordres limites** — lorsque le parcours des prix croise un tick qui contient des ordres limites ouverts, le programme remplit d'abord la liquidité des ordres limites disponibles à ce tick (FIFO par `order_phase`), puis procède le long de la courbe de liquidité LP. Les montants remplis mettent à jour `tick.unfilled_ratio_x64` et `tick.part_filled_orders_remaining` pour un règlement ultérieur ; les ordres eux-mêmes restent non dépensés jusqu'à ce que leur propriétaire appelle `SettleLimitOrder`.
3. **Routage des frais unilatéral** — lorsque `pool.fee_on = Token0Only` ou `Token1Only`, l'étape de swap calcule toujours le même échange entrée-sortie ; les frais sont ensuite acheminés vers le côté configuré. Pour les directions où le côté de frais configuré est la sortie, les frais sont déduits de la sortie du swap (l'utilisateur reçoit `out − fee`) ; pour les directions où c'est l'entrée, le comportement correspond à `FromInput`. Voir `is_fee_on_input(zero_for_one)` et `is_fee_on_token0(zero_for_one)` sur `PoolState`.

`Swap` (V1) implémente les mêmes frais dynamiques, routage des frais unilatéral et appariement des ordres limites que `SwapV2` ; la seule fonctionnalité qui lui manque est la prise en charge de Token-2022 — les deux coffres doivent être du Token SPL classique. Les pools avec n'importe quel mint Token-2022 doivent être échangés via `SwapV2`. L'agrégateur et le SDK préfèrent déjà V2 pour chaque jambe CLMM, donc les appelants n'ont pas à se brancher sur le type de mint.

## `OpenLimitOrder`

Placer un ordre de vente à un tick spécifique. L'ordre se trouve dans une cohorte FIFO par tick et se remplit à mesure que le prix passe.

**Arguments**

```
nonce_index:    u8       // user's chosen nonce-account index (0..255 per wallet)
zero_for_one:   bool     // true: sell token0 for token1; false: sell token1 for token0
tick_index:     i32      // must be a multiple of pool.tick_spacing
amount:         u64      // input-token amount
```

**Comptes (abrégés)**

| # | Name | W | S | Notes |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Propriétaire de l'ordre ; paie le loyer. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | Le tableau de ticks contenant `tick_index`. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — créé au premier ordre de l'utilisateur sous ce `nonce_index`. |
| 5 | `limit_order` | W |   | PDA. `init` ici. |
| 6 | `input_token_account` | W |   | ATA d'entrée de l'utilisateur. Vérifié pour `frozen`. |
| 7 | `output_token_account` | W |   | ATA de **sortie** de l'utilisateur. Non débité à l'ouverture — requis uniquement pour que le programme puisse confirmer qu'il n'est pas `frozen` (c'est-à-dire que le remplissage peut être livré plus tard). |
| 8 | `input_vault` | W |   | Coffre d'entrée du pool. |
| 9 | `output_vault` | W |   | Coffre de sortie du pool. Identifie le mint de sortie pour les vérifications `output_token_account` / `output_vault_mint`. |
| 10 | `input_vault_mint` |   |   | Gestion des frais Token-2022. |
| 11 | `output_vault_mint` |   |   | Mint du côté sortie (appariement de vérification gelée). |
| 12 | `input_token_program` |   |   | SPL ou Token-2022. |
| 13 | `system_program` |   |   | Finance `limit_order`, `limit_order_nonce` et — si nécessaire — l'allocation `tick_array`. |

**Comptes restants** — `[0]` `tick_array_bitmap_extension`, requis uniquement lors de l'initialisation d'un tableau de ticks dont l'index de départ se situe en dehors de la bitmap en ligne du pool. Ne passer rien sinon.

<Warning>
  Il n'y a **pas de compte `rent`** : la structure se termine à `system_program`, 13 comptes déclarés. Un `rent` égaré en position 14 se retrouve exactement où l'extension bitmap optionnelle est lue, donc l'ordre semble fonctionner jusqu'à la première fois où un tableau de ticks en dehors de la bitmap en ligne doit être créé — et échoue ensuite.
</Warning>

<Note>
  **Changement de liste de comptes (version 2026-07).** `OpenLimitOrder` prend maintenant aussi les comptes du **côté sortie** — `output_token_account`, `output_vault` et `output_vault_mint` — en plus du côté entrée. Ils sont utilisés uniquement pour la validation : le programme rejette l'ordre si le compte de token d'entrée **ou** de sortie du propriétaire est gelé. Cela garantit qu'un remplissage peut réellement être réglé vers l'ATA de sortie du propriétaire, ce qui importe pour les mints Token-2022 avec liste d'autorisation / gelés par défaut (par exemple, les tokens autorisés) où un compte peut ne pas encore être dégelé. Les clients construits par rapport à l'ancienne liste de comptes unilatérale doivent ajouter les trois comptes de sortie.
</Note>

**Préconditions**

- Ni `input_token_account` ni `output_token_account` n'est gelé (sinon `NotApproved`).
- `pool_state.status` autorise à la fois les opérations de swap (bit 4) et d'ordre limite (bit 5) (sinon `NotApproved`).
- `tick_index % pool.tick_spacing == 0` et dans `[MIN_TICK, MAX_TICK]`.
- `tick_index` est du **bon côté de `pool.tick_current`** pour la direction choisie (vendre token0 → le tick doit être au-dessus du courant, et vice versa). Vendre à un tick déjà croisé serait immédiatement appairé et est rejeté.

**Postconditions**

- `limit_order` existe, capturant `tick.order_phase` et `tick.unfilled_ratio_x64` au moment de l'ouverture.
- `tick.orders_amount += amount` (dans la cohorte actuelle).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` émis.

**Erreurs courantes** — `NotApproved` (compte de token d'entrée ou de sortie gelé, ou le pool a le swap / ordre limite désactivé), `ZeroAmountSpecified` (`amount == 0` après les frais de transfert du côté entrée), `InvalidLimitOrderAmount` (le montant produirait une sortie inférieure à 1 unité de base à ce tick, ou déborderait `u64`), `InvalidTickIndex` (en dehors de `[MIN_TICK, MAX_TICK]`, ou du mauvais côté de `tick_current` pour la direction choisie), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `CollectExcessLamports`

Balayage admin des lamports au-dessus du minimum exempt de loyer sur les comptes que CLMM contrôle. Il a été ajouté dans la mise à niveau 2026-09 pour récupérer le surfinancement que la [réduction de loyer SIMD-0437](/fr/solana-fundamentals/rent-and-reclaimable-rent) laisse sur les comptes créés avant chaque étape.

Seul l'excédent se déplace. Les soldes de jetons, les données de compte, les propriétaires, l'état du pool et la courbe de prix restent inchangés. Un compte déjà à son minimum est laissé tel quel, donc l'instruction peut être réexécutée en toute sécurité après chaque étape de déploiement.

**Arguments** : aucun.

**Comptes**

| # | Nom | W | S | Notes |
|---|-----|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Reçoit chaque lamport balayé. Doit être l'admin du programme CLMM ou le portefeuille de collecte de lamports dédié (voir [`reference/program-addresses`](/fr/reference/program-addresses#excess-lamports-collection-wallets)). Tout autre signataire échoue avec `NotApproved`. |
| 2 | `pool_state` | W |   | Le pool en cours de balayage. Ses graines PDA signent les CPI du programme de jetons, et le compte est toujours balayé lui-même. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Les deux programmes sont requis ; l'instruction en choisit un par compte source. |
| 5.. | `remaining_accounts` | W |   | `M` comptes sources, n'importe quel nombre, n'importe quel ordre. |

**Portée : un pool par appel.** CLMM n'a pas d'autorité de coffre à l'échelle du programme. Les coffres de chaque pool sont possédés par son propre `PoolState`. Chaque source du programme de jetons doit donc avoir le `pool_state` à l'emplacement 2 comme autorité : `token_vault_0`, `token_vault_1`, ou l'un des coffres de récompense de ce pool. Si vous passez le coffre d'un autre pool ou un compte de jetons d'un utilisateur, la vérification du propriétaire du programme de jetons échoue et l'instruction entière est annulée. Elle n'est pas ignorée. Les mints NFT de position ne peuvent pas être balayés, car leur autorité de mint est révoquée à l'ouverture de la position.

**Comment chaque compte source est traité**

Le programme effectue deux passages sur `remaining_accounts` : d'abord chaque CPI du programme de jetons, puis les débits directs. L'entrelacement des deux abandonne avec l'erreur `UnbalancedInstruction` du runtime, donc l'ordre est fixé dans le programme et vous n'avez pas à trier la liste vous-même.

| Passage | Propriétaire du compte source | Traitement |
|---------|------------------------------|-----------|
| 1 | SPL Token ou Token-2022, compte de jetons non natif | CPI `WithdrawExcessLamports` (discriminant du programme de jetons `38`), signé par `pool_state`. |
| 1 | SPL Token ou Token-2022, **natif** (wSOL) compte de jetons | `WithdrawExcessLamports` rejette les comptes natifs. Le programme appelle `SyncNative`, mesure la croissance du `amount` enveloppé, et appelle `UnwrapLamports` (discriminant `45`) pour exactement ce delta. Il exige ensuite que le solde enveloppé soit égal à sa valeur pré-sync, ou échoue avec `LamportsCalculateError` (`6052`). Un coffre de pool côté SOL conserve sa liquidité complète. |
| 2 | `pool_state` (emplacement 2) | Débité directement jusqu'à `rent.minimum_balance(data_len)`. |
| 2 | Le programme CLMM : `AmmConfig`, `ObservationState`, `TickArrayBitmapExtension`, `TickArrayState`, `PersonalPositionState`, `LimitOrderState`, et ainsi de suite | Débité directement jusqu'à `rent.minimum_balance(data_len)`. Le compte n'a **pas** besoin d'appartenir au pool à l'emplacement 2. |
| — | N'importe quoi d'autre | **Ignoré silencieusement.** Pas d'erreur, pas de lamports déplacés. |

<Warning>
  **Le passage 2 couvre les comptes dont le loyer a été payé par un utilisateur.** Un `PersonalPositionState` ou `LimitOrderState` passé ici abandonne son excédent comme tout autre compte appartenant à CLMM. Il reste exempt de loyer et conserve ses données. Lorsqu'il est fermé ultérieurement, le propriétaire récupère ce que le compte détient à ce moment, qui après un balayage est le minimum de loyer actuel.
</Warning>

La taille de la transaction est la vraie limite sur le nombre de sources qui tiennent dans un appel. C'est la même contrainte que le balayage côté portefeuille décrit dans [`solana-fundamentals/rent-and-reclaimable-rent`](/fr/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**Erreurs courantes** :
- `NotApproved` (`6000`) : mauvais signataire.
- `LamportsCalculateError` (`6052`) : l'aller-retour wSOL n'a pas donné zéro.
- Une erreur de non-correspondance du propriétaire du programme de jetons : une source de jetons n'est pas possédée par `pool_state`.
- `InsufficientFunds` : un compte appartenant au programme détient moins que son propre minimum de loyer.

**Pas de générateur SDK.** `@raydium-io/raydium-sdk-v2` n'expédie pas de générateur pour ce chemin admin. Encodez-le à la main à partir de l'IDL.

## `InitializeReward`

Ajoutez un nouveau flux de récompense à un pool. Jusqu'à 3 flux peuvent être actifs à la fois.

**Arguments** — une seule structure, `param: InitializeRewardParam` :

```rust
pub struct InitializeRewardParam {
    pub open_time:                u64,
    pub end_time:                 u64,
    pub emissions_per_second_x64: u128,   // Q64.64
}
```

L'encodage sur le fil est les trois champs dos à dos, donc une instruction construite à la main n'est pas affectée — mais un client piloté par IDL doit passer un objet `param` plutôt que trois arguments positionnels.

**Comptes**

| # | Nom | W | S | Notes |
|---|-----|---|---|-------|
| 1 | `reward_funder` | W | S |
| 2 | `funder_token_account` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `operation_state` |   |   | PDA d'état opérationnel CLMM contrôlant la création de récompense. |
| 6 | `reward_token_mint` |   |   |
| 7 | `reward_token_vault` | W |   | `init` ici. |
| 8 | `reward_token_program` |   |   |
| 9 | `system_program`, `rent` |   |   |

**Préconditions**

- Moins de 3 flux actuellement actifs sur le pool.
- Le financeur dépose `total_emission = emissions_per_second × (end_time − open_time)` de jetons de récompense dans le coffre dans le cadre de cette instruction.
- Mint de récompense sur liste blanche par `operation_state`.

## `SetRewardParams`

Prolongez, complétez ou modifiez le taux d'émission sur un flux de récompense existant. Généralement appelé par un créateur de pool ou le multisig Raydium. Les contraintes vivent sur chaîne : vous pouvez généralement prolonger `end_time` ou augmenter les émissions, pas les réduire rétroactivement. Vérifiez la liste des propriétaires de `operation_state`.

## `UpdateRewardInfos`

Pur travail administratif — règle `reward_growth_global_x64` à l'heure actuelle en multipliant `emissions_per_second × Δt / liquidity`. Appelé en interne par chaque instruction touchant la liquidité. Exposé comme une instruction autonome car les acteurs externes (UIs, cranks) veulent parfois le déclencher.

## Collecte des récompenses

<Warning>
  **Il n'y a pas d'instruction de collecte de récompense autonome.** Le programme n'expose pas de point d'entrée `CollectReward`, et l'IDL publié n'en a pas non plus.
</Warning>

Les récompenses dues à une position sont versées par `DecreaseLiquidity` / `DecreaseLiquidityV2`. Pour collecter sans modifier la position, appelez-la avec `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`.
Les coffres de récompense et les comptes destinataires vont dans `remaining_accounts` en groupes de trois par récompense active, dans l'ordre `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`.

`CollectRemainingRewards` est une chose différente : il permet au financeur de récompense, après le `end_time` d'un flux, de balayer les jetons qui n'ont jamais été alloués à aucune position.
