<Note>
  **Il n'y a pas d'instruction init-tick-array, et aucune n'est nécessaire.** Un tick array est créé *à l'intérieur*
  `OpenPosition*` / `IncreaseLiquidity*` par `TickArrayState::get_or_create_tick_array`, payé par
  `payer`. Passez le PDA du tick array (possiblement encore non initialisé, appartenant au système) en tant que
  `tick_array_lower` / `tick_array_upper` et le programme l'alloue s'il est manquant.
  `OpenLimitOrder` fait de même pour son unique `tick_array`.
</Note>

La plupart des instructions admin uniquement (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) sont contrôlées par la clé `admin` codée en dur du programme. `CreatePermissionPda` / `ClosePermissionPda` acceptent soit la clé `admin` **soit** une clé `permission_pda_admin` dédiée ; `CreateSupportMintAssociated` / `CloseSupportMintAssociated` acceptent soit la clé `admin` **soit** une clé propriétaire de mint de support dédiée ; `CollectExcessLamports` accepte soit la clé `admin` **soit** un portefeuille de collecte de lamports dédié. Les instructions admin de flux de récompenses (`TransferRewardOwner`, `CollectRemainingRewards`) sont contrôlées par le financeur de récompenses, pas par l'admin du programme.

Le suffixe V2 signifie « supporte Token-2022 sur les coffres / NFT, nécessite l'emplacement d'extension bitmap ». Le SDK choisit V2 par défaut pour les nouveaux pools.

## `CreatePool`

**Arguments**

```
sqrt_price_x64: u128           // prix initial
open_time:      u64            // les swaps sont rejetés avant cette heure
```

**Comptes (abrégés)**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Palier de frais choisi. |
| 3 | `pool_state` | W |   | `init` ici. |
| 4 | `token_mint_0` |   |   | Trié. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` ici, appartenant au PDA d'autorité du pool. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` ici. |
| 9 | `tick_array_bitmap` | W |   | Le PDA `TickArrayBitmapExtension` ; `init` ici. |
| 10 | `token_program_0` |   |   | Le programme qui possède `token_mint_0` — SPL Token **ou** Token-2022. |
| 11 | `token_program_1` |   |   | Le programme qui possède `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Les emplacements 10 et 11 sont **par mint**, pas « SPL Token puis Token-2022 ». Chacun est contraint par
  `mint::token_program` sur le mint correspondant, donc pour un pool dont `token_mint_0` est Token-2022 et
  `token_mint_1` est SPL classique, vous devez passer Token-2022 à l'emplacement 10 et SPL Token à l'emplacement 11.
  `CreateCustomizablePool` et `CreatePermissionedPool` utilisent les mêmes deux emplacements.
</Warning>

**Préconditions**

- `token_mint_0 < token_mint_1` par ordre d'octets.
- `amm_config.disable_create_pool == false`.
- Les mints ne sont pas rejetés par la liste blanche d'extension Token-2022.

**Postconditions**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (pas de positions encore).
- `pool_state.fee_on = FromInput` (défaut hérité).
- `pool_state.dynamic_fee_info` est mis à zéro (frais dynamiques désactivés).

## `CreateCustomizablePool`

Recommandé pour les nouveaux pools. Même effet que `CreatePool` plus le mode de collecte des frais par pool et un opt-in de frais dynamiques optionnel.

**Arguments**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Comptes** — exactement les 13 comptes déclarés de `CreatePool`. `dynamic_fee_config` n'est **pas** un compte déclaré.

<Warning>
  Quand `enable_dynamic_fee = true`, le `DynamicFeeConfig` à capturer doit être fourni en tant que
  **dernier** `remaining_account` — le gestionnaire lit `ctx.remaining_accounts.last()`. Tous les
  PDAs de contournement `SupportMintAssociated` doivent donc venir *avant* lui, ou le programme capture
  le mauvais compte et échoue la désérialisation. L'omettre alors que le drapeau est défini échoue avec
  `AccountLack`.
</Warning>

**Préconditions** — identiques à `CreatePool`. Si `enable_dynamic_fee = false`, aucun `remaining_account` n'est requis et tous ceux qui sont passés sont uniquement scannés pour les enregistrements de support-mint.

**Postconditions**

- `pool_state.fee_on` défini à la variante `CollectFeeOn` choisie.
- Si les frais dynamiques ont été activés : `pool_state.dynamic_fee_info` est initialisé à partir du `DynamicFeeConfig` fourni (cinq paramètres d'étalonnage copiés ; champs d'état mis à zéro).
- Sinon : `pool_state.dynamic_fee_info` est mis à zéro (= frais dynamiques inactifs à jamais pour ce pool).

`fee_on` et le bit d'activation des frais dynamiques sont définis **uniquement** à la création du pool. Il n'y a pas de mise à niveau sur place — les pools créés via le `CreatePool` hérité ne peuvent pas rétroactivement gagner des frais dynamiques ou unilatéraux. Les nouveaux déploiements doivent utiliser cette instruction par défaut.

## `CreatePermissionedPool`

`CreatePool` et `CreateCustomizablePool` dérivent tous deux le PDA du pool de `["pool", amm_config, token_mint_0, token_mint_1]`, donc il y a exactement **une** adresse de pool canonique par triplet `(config, mint0, mint1)` — un second `init` aux mêmes graines échoue. `CreatePermissionedPool` lève cette restriction en pliant un `seed_index: u16` fourni par le client dans les graines du PDA du pool, permettant **plusieurs pools pour la même paire et palier de frais** — chacun à sa propre adresse. Parce qu'une adresse de pool arbitraire est une capacité privilégiée, le payeur doit détenir un PDA `Permission` qui l'autorise.

Tout le reste du pool est identique à `CreateCustomizablePool` : il prend les mêmes `CreateCustomizableParams` et supporte les frais unilatéraux et l'opt-in des frais dynamiques.

**Arguments**

```rust
customizable_params: CreateCustomizableParams   // même struct que CreateCustomizablePool
seed_index:          u16                          // doit être non-zéro ; plié dans les graines du PDA du pool
```

**Comptes (abrégés)** — identiques à `CreateCustomizablePool` plus, au début :

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Paie le loyer. Doit être l'autorité du PDA `permission` ci-dessous. |
| 2 | `pool_creator` |   |   | Enregistré en tant que `pool_state.owner`. Peut différer de `payer`. |
| 3 | `permission` |   |   | PDA `["permission", payer]`. Anchor rejette l'appel s'il n'existe pas / n'est pas appartenant au programme. |
| … | (`amm_config`, `pool_state`, mints, coffres, `observation_state`, `tick_array_bitmap`, programmes token/système) | | | Comme dans `CreateCustomizablePool`. |

Le PDA `pool_state` est dérivé de `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`.

**Préconditions**

- `seed_index != 0`. Un `seed_index` de `0` est réservé aux pools hérités et est rejeté ici ; la composante de graine `[0, 0]` est ce qui fait qu'une adresse de pool hérité s'effondre à la forme classique à quatre graines.
- Le PDA `permission` pour `payer` existe (créé par un admin via `CreatePermissionPda`).
- Mêmes règles de mint / liste blanche que `CreatePool`.

**Postconditions**

- Un nouveau `pool_state` existe à l'adresse dérivée de `seed_index`, avec `pool_state.seed_index = seed_index`.
- Tous les autres post-états correspondent à `CreateCustomizablePool` (mode de frais, frais dynamiques optionnels).

<Note>
  Cette instruction n'élargit **pas** l'accès général à la création de pools — la création sans permission continue via `CreatePool` / `CreateCustomizablePool`, qui restent un pool par paire. `CreatePermissionedPool` existe pour le cas spécifique où un opérateur sur liste blanche a besoin de plusieurs pools pour la même paire (par exemple, des prix initiaux ou des cohortes de lancement différents) et détient un PDA `Permission` accordé par l'admin.
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Créer une nouvelle position à l'intérieur d'un pool existant.

**Arguments**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // L désiré (ou 0 pour utiliser les montants ci-dessous)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // écrire les métadonnées NFT (Metaplex)
base_flag: Option<bool>       // true = adapter à amount0 ; false = adapter à amount1
```

**Comptes** — les deux variantes ont des listes de comptes *différentes*. `OpenPositionV2` déclare 22 ; `OpenPositionWithToken22Nft` déclare 20.

`OpenPositionV2`, dans l'ordre :

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `payer` | W | S | |
| 2 | `position_nft_owner` |   |   | |
| 3 | `position_nft_mint` | W | S | Nouvelle paire de clés. |
| 4 | `position_nft_account` | W |   | ATA du propriétaire pour le NFT. |
| 5 | `metadata_account` | W |   | PDA de métadonnées Metaplex. Déclaré **inconditionnellement**, même quand `with_metadata = false`. |
| 6 | `pool_state` | W |   | |
| 7 | `protocol_position` |   |   | Vestigial ; `UncheckedAccount` en lecture seule. |
| 8 | `tick_array_lower` | W |   | Créé ici s'il n'est pas initialisé. |
| 9 | `tick_array_upper` | W |   | Idem. |
| 10 | `personal_position` | W |   | Créé ici. |
| 11 | `token_account_0` | W |   | ATA source utilisateur. |
| 12 | `token_account_1` | W |   | |
| 13 | `token_vault_0` | W |   | |
| 14 | `token_vault_1` | W |   | |
| 15 | `rent` |   |   | |
| 16 | `system_program` |   |   | |
| 17 | `token_program` |   |   | |
| 18 | `associated_token_program` |   |   | |
| 19 | `metadata_program` |   |   | Métadonnées de jetons Metaplex. |
| 20 | `token_program_2022` |   |   | |
| 21 | `vault_0_mint` |   |   | |
| 22 | `vault_1_mint` |   |   | |

`OpenPositionWithToken22Nft` est la même liste avec `metadata_account` (5) et `metadata_program` (19) **supprimés** — il écrit les métadonnées de la position via l'extension de métadonnées Token-2022 sur le mint du NFT à la place — donnant 20 comptes. Son `position_nft_mint` est un `Signer` nu et `position_nft_account` un `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` n'est pas un compte déclaré sur l'une ou l'autre variante.** Quand la
  plage de la position tombe en dehors du `tick_array_bitmap` en ligne du pool (±512 tick arrays), ajoutez
  le PDA `TickArrayBitmapExtension` aux graines `["pool_tick_array_bitmap_extension", pool_state]` en tant que
  `remaining_accounts[0]`.
</Warning>

**Mathématiques** — voir [`products/clmm/math`](/fr/products/clmm/math). Donné `base_flag`, le programme résout soit `liquidity` soit `(amount_0_max, amount_1_max)` en `L` réel et les montants de jetons réels consommés.

**Préconditions**

- `tick_lower < tick_upper`, tous deux multiples de `pool.tick_spacing`, dans `[MIN_TICK, MAX_TICK]`.
- Les deux PDAs de tick array sont passés. Ils n'ont **pas** besoin d'exister déjà — `get_or_create_tick_array` alloue un manquant aux frais de `payer` à l'intérieur de cette instruction. Il n'y a pas d'instruction init-tick-array séparée.
- L'utilisateur a au moins `amount_0_max` et `amount_1_max` dans les ATAs source.

**Postconditions**

- `personal_position` existe, `liquidity` défini, `fee_growth_inside_last` capturé.
- Les entrées du tick array à `tick_lower` et `tick_upper` mises à jour (`liquidity_gross += L`, `liquidity_net ± L`, instantanés de croissance des frais maintenus).
- `pool_state.liquidity += L` si la position est en plage (`tick_lower ≤ tick_current < tick_upper`).
- Le mint du NFT de la position enregistre `pool_state` comme autorité de gel. L'autorité de mint est supprimée après que le seul NFT soit frappé. L'enregistrement de l'autorité de gel ne change pas l'état du compte de jetons NFT.
- Le compte de jetons NFT reste dégelé sauf si l'instruction est `OpenPositionV2` ou `OpenPositionWithToken22Nft` **et** que l'autorité de gel de l'un des mints de coffre correspond à la liste des émetteurs restreints de CLMM. Seul ce chemin V2 correspondant gèle le compte. `OpenPosition` V1 ne gèle pas.

**Erreurs courantes** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (une extrémité n'est pas un multiple de `tick_spacing`), `InvalidTickIndex` (en dehors de `[MIN_TICK, MAX_TICK]`), `MissingTickArrayBitmapExtensionAccount` (plage en dehors du bitmap en ligne et l'extension n'a pas été ajoutée), `NotApproved` (`pool_state.status` bloque l'ouverture), `ZeroAmountSpecified`.

<Note>
  Le gel de position n'ajoute pas de comptes d'instruction déclarés ou d'arguments. Les clients peuvent ouvrir ces positions avec les dispositions V2 existantes. Le comportement est sélectionné sur la chaîne à partir de `vault_0_mint` et `vault_1_mint`.
</Note>

## `DecreaseLiquidityV2`

Retirer de la liquidité d'une position.

**Arguments**

```
liquidity: u128
amount_0_min: u64
amount_1_min: u64
```

**Comptes** — 16, et **pas** la même forme ou ordre que `IncreaseLiquidityV2` : `personal_position` et `pool_state` sont échangés, les coffres viennent avant les tick arrays, les comptes côté utilisateur sont nommés `recipient_token_account_*`, et il y a un `memo_program` supplémentaire.

| # | Nom | W | S |
|---|------|---|---|
| 1 | `nft_owner` |   | S |
| 2 | `nft_account` |   |   |
| 3 | `personal_position` | W |   |
| 4 | `pool_state` | W |   |
| 5 | `protocol_position` |   |   |
| 6 | `token_vault_0` | W |   |
| 7 | `token_vault_1` | W |   |
| 8 | `tick_array_lower` | W |   |
| 9 | `tick_array_upper` | W |   |
| 10 | `recipient_token_account_0` | W |   |
| 11 | `recipient_token_account_1` | W |   |
| 12 | `token_program` |   |   |
| 13 | `token_program_2022` |   |   |
| 14 | `memo_program` |   |   |
| 15 | `vault_0_mint` |   |   |
| 16 | `vault_1_mint` |   |   |

**Comptes restants** — trois par récompense active collectée, dans l'ordre `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`. Ajoutez le PDA `TickArrayBitmapExtension` quand la plage de la position est en dehors du bitmap en ligne.

<Note>
  C'est aussi la **seule** façon de collecter les frais et récompenses. Pour collecter sans changer la
  position, appelez-la avec `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`.
</Note>

**Effet**

- Calcule `(amount_0, amount_1)` pour le `L` retiré donné le `sqrt_price_x64` actuel.
- Règle les frais/récompenses accumulés depuis le dernier toucher, identique à `IncreaseLiquidity`.
- Transfère `amount_0 + fees_owed_0` et `amount_1 + fees_owed_1` hors des coffres vers l'utilisateur.
- Décrémente les compteurs de liquidité ; si le nouveau `personal_position.liquidity == 0`, la position est éligible pour `ClosePosition`.

**Slippage** — `amount_0_min` et `amount_1_min` sont les minimums que l'utilisateur accepte nets des frais de transfert Token-2022 côté résultat.

## `ClosePosition`

Brûler le NFT de position et fermer `PersonalPositionState`.

**Comptes déclarés**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `nft_owner` | W | S | Doit posséder le compte de jetons NFT contenant le montant `1`. |
| 2 | `position_nft_mint` | W |   | Doit correspondre à `personal_position.nft_mint`. |
| 3 | `position_nft_account` | W |   | Compte du propriétaire du NFT ; peut être SPL Token classique ou Token-2022. |
| 4 | `personal_position` | W |   | Fermé à `nft_owner`. |
| 5 | `system_program` |   |   | Ferme l'état de position. |
| 6 | `token_program` |   |   | Doit posséder le mint et le compte de jetons NFT. |

**Comptes restants**

- NFT dégelé : aucun requis ; un compte de pool supplémentaire est inoffensif car le gestionnaire ne le lit pas.
- NFT gelé : ajoutez `personal_position.pool_id` en tant que premier compte restant. Le programme le charge en tant que `PoolState` et utilise ses graines PDA pour signer le dégel.

**Préconditions**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Tous les compteurs de récompenses `reward_amount_owed == 0`.

(C'est-à-dire, collectez tout et diminuez à zéro d'abord.)

**Effet**

- Si le compte de jetons NFT est gelé, vérifie que le premier compte restant égale `personal_position.pool_id`, puis le dégèle avec le PDA du pool.
- Brûle le NFT.
- Ferme le compte de jetons NFT et `personal_position`, remboursant le loyer à `nft_owner`. Si le NFT de position utilise Token-2022, il ferme également le mint du NFT ; les mints SPL Token classiques ne peuvent pas être fermés et restent avec l'offre zéro.

Le dégel, la combustion et la fermeture sont atomiques. Le NFT ne peut pas devenir transférable entre ces étapes.

**Rupture client conditionnelle** — la disposition IDL déclarée est inchangée, donc les clients hérités continuent à fermer les positions existantes et dégelées. Un constructeur hérité qui omet le compte de pool restant échoue avec `AccountLack` lors de la fermeture d'une position gelée. Passer le pool pour chaque fermeture est la stratégie compatible la plus simple.


**Comptes (abrégés)**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |

Les appelants passent une liste classée de tick arrays couvrant la marche de swap attendue ; le programme en utilise autant qu'il en a besoin. Le SDK calcule cette liste via `PoolUtils.computeAmountOutFormat` ou le point de terminaison de devis de l'API.

- `now >= open_time`.

**Erreurs courantes** — `TooLittleOutputReceived` (slippage exact-in), `TooMuchInputPaid` (slippage exact-out), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (bit de swap défini sur `pool_state.status`). CLMM n'a pas de variante `ExceededSlippage` — ce nom est celui de CPMM — et pas de `TickArrayNotFound`.

**Ce que `SwapV2` fait en interne que les appelants doivent savoir** (après la version 2025) :

1. **Surcharge de frais dynamiques** — si `pool.dynamic_fee_info` est non-zéro, le programme met à jour l'accumulateur de volatilité en utilisant la distance de tick traversée depuis le dernier swap (avec les règles de filtre/décroissance de [`products/clmm/fees`](/fr/products/clmm/fees)) et ajoute un `dynamic_fee_component` au-dessus de `AmmConfig.trade_fee_rate`. Les frais totaux sont plafonnés à 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Appariement des ordres limites** — quand la marche de prix traverse un tick qui détient des ordres limites ouverts, le programme remplit d'abord la liquidité d'ordre limite disponible à ce tick (FIFO par `order_phase`), puis procède le long de la courbe de liquidité LP. Les montants remplis mettent à jour `tick.unfilled_ratio_x64` et `tick.part_filled_orders_remaining` pour un règlement ultérieur ; les ordres eux-mêmes restent non dépensés jusqu'à ce que leur propriétaire appelle `SettleLimitOrder`.
3. **Routage des frais unilatéraux** — quand `pool.fee_on = Token0Only` ou `Token1Only`, l'étape de swap calcule toujours le même échange entrée-sortie ; les frais sont ensuite acheminés vers le côté configuré. Pour les directions où le côté de frais configuré est la sortie, les frais sont déduits de la sortie du swap (l'utilisateur reçoit `out − fee`) ; pour les directions où c'est l'entrée, le comportement correspond à `FromInput`. Voir `is_fee_on_input(zero_for_one)` et `is_fee_on_token0(zero_for_one)` sur `PoolState`.

`Swap` (V1) implémente les mêmes frais dynamiques, routage des frais unilatéraux et appariement des ordres limites que `SwapV2` ; la seule fonctionnalité qu'il manque est le support Token-2022 — les deux coffres doivent être du Token SPL classique. Les pools avec n'importe quel mint Token-2022 doivent être échangés via `SwapV2`. L'agrégateur et le SDK préfèrent déjà V2 pour chaque jambe CLMM, donc les appelants n'ont pas à se brancher sur le type de mint.

## `OpenLimitOrder`

Placer un ordre de vente à un tick spécifique. L'ordre reste dans une cohorte FIFO par tick et se remplit à mesure que le prix passe.

**Arguments**

```
nonce_index:    u8       // index de compte nonce choisi par l'utilisateur (0..255 par portefeuille)
zero_for_one:   bool     // true : vendre token0 pour token1 ; false : vendre token1 pour token0
tick_index:     i32      // doit être un multiple de pool.tick_spacing
amount:         u64      // montant du jeton d'entrée
```

**Comptes (abrégés)**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Propriétaire de l'ordre ; paie le loyer. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | Le tick array contenant `tick_index`. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — créé au premier ordre de l'utilisateur sous ce `nonce_index`. |
| 5 | `limit_order` | W |   | PDA. `init` ici. |
| 6 | `input_token_account` | W |   | ATA d'entrée de l'utilisateur. Vérifié pour `frozen`. |
| 7 | `output_token_account` | W |   | ATA de **sortie** de l'utilisateur. Non débité à l'ouverture — requis uniquement pour que le programme puisse confirmer qu'il n'est pas `frozen` (c'est-à-dire que le remplissage peut être livré plus tard). |
| 8 | `input_vault` | W |   | Coffre d'entrée du pool. |
| 9 | `output_vault` | W |   | Coffre de sortie du pool. Identifie le mint de sortie pour les vérifications `output_token_account` / `output_vault_mint`. |
| 10 | `input_vault_mint` |   |   | Gestion des frais Token-2022. |
| 11 | `output_vault_mint` |   |   | Mint du côté sortie (appariement de vérification gelée). |
| 12 | `input_token_program` |   |   | SPL ou Token-2022. |
| 13 | `system_program` |   |   | Finance le `limit_order`, `limit_order_nonce` et — si nécessaire — l'allocation `tick_array`. |

**Comptes restants** — `[0]` `tick_array_bitmap_extension`, requis uniquement lors de l'initialisation d'un tick array dont l'index de départ tombe en dehors du bitmap en ligne du pool. Ne passez rien sinon.

<Warning>
  Il n'y a **pas de compte `rent`** : la struct se termine à `system_program`, 13 comptes déclarés. Un `rent` égaré à la position 14 atterrit exactement où l'extension bitmap optionnelle est lue, donc l'ordre semble fonctionner jusqu'à la première fois qu'un tick array en dehors du bitmap en ligne doit être créé — et puis échoue.
</Warning>

<Note>
  **Changement de liste de comptes (version 2026-07).** `OpenLimitOrder` prend maintenant aussi les comptes du **côté sortie** — `output_token_account`, `output_vault`, et `output_vault_mint` — en plus du côté entrée. Ils sont utilisés uniquement pour la validation : le programme rejette l'ordre si le compte de jeton d'entrée **ou** de sortie du propriétaire est gelé. Cela garantit qu'un remplissage peut réellement être réglé à l'ATA de sortie du propriétaire, ce qui importe pour les mints Token-2022 avec liste blanche / gelés par défaut (par exemple, les jetons autorisés) où un compte peut ne pas encore être dégelé. Les clients construits contre la liste de comptes unilatérale plus ancienne doivent ajouter les trois comptes de sortie.
</Note>

**Préconditions**

- Ni `input_token_account` ni `output_token_account` n'est gelé (sinon `NotApproved`).
- `pool_state.status` permet à la fois le swap (bit 4) et les opérations d'ordre limite (bit 5) (sinon `NotApproved`).
- `tick_index % pool.tick_spacing == 0` et dans `[MIN_TICK, MAX_TICK]`.
- `tick_index` est du **bon côté de `pool.tick_current`** pour la direction choisie (vendre token0 → tick doit être au-dessus du courant, et vice versa). Vendre à un tick déjà traversé serait immédiatement appareillé et est rejeté.

**Postconditions**

- `limit_order` existe, capturant `tick.order_phase` et `tick.unfilled_ratio_x64` au moment de l'ouverture.
- `tick.orders_amount += amount` (dans la cohorte actuelle).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` émis.

**Erreurs courantes** — `NotApproved` (compte de jeton d'entrée ou de sortie gelé, ou le pool a le swap / ordre limite désactivé), `ZeroAmountSpecified` (`amount == 0` après les frais de transfert côté entrée), `InvalidLimitOrderAmount` (le montant produirait une sortie inférieure à 1 unité de base à ce tick, ou déborderait `u64`), `InvalidTickIndex` (en dehors de `[MIN_TICK, MAX_TICK]`, ou du mauvais côté de `tick_current` pour la direction choisie), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

| # | Nom | W | S |
|---|------|---|---|

Pousser les jetons de sortie remplis vers le propriétaire sans changer le reste non rempli de l'ordre. Utile quand les gardiens `auto_withdraw` veulent verser progressivement les remplissages partiels de longue durée.

## `CollectExcessLamports`

Balayage admin des lamports au-dessus du minimum exempt de loyer sur les comptes que CLMM contrôle. Il a été ajouté dans la mise à niveau 2026-09 pour récupérer le sur-financement que la [réduction de loyer SIMD-0437](/fr/solana-fundamentals/rent-and-reclaimable-rent) laisse sur les comptes créés avant chaque étape.

Seul l'excédent se déplace. Les soldes de jetons, les données de compte, les propriétaires, l'état du pool et la courbe de prix restent inchangés. Un compte déjà à son minimum est laissé tel quel, donc l'instruction peut être réexécutée en toute sécurité après chaque étape de déploiement.

**Arguments** : aucun.

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Reçoit chaque lamport balayé. Doit être l'admin du programme CLMM ou le portefeuille dédié de collecte de lamports (voir [`reference/program-addresses`](/fr/reference/program-addresses#excess-lamports-collection-wallets)). Tout autre signataire échoue avec `NotApproved`. |
| 2 | `pool_state` | W |   | Le pool en cours de balayage. Ses graines PDA signent les CPIs du programme de jetons, et le compte est toujours balayé lui-même. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Les deux programmes sont requis ; l'instruction en choisit un par compte source. |
| 5.. | `remaining_accounts` | W |   | `M` comptes source, n'importe quel nombre, n'importe quel ordre. |

**Portée : un pool par appel.** CLMM n'a pas d'autorité de coffre au niveau du programme. Les coffres de chaque pool sont possédés par son propre `PoolState`. Chaque source du programme de jetons doit donc avoir le `pool_state` à l'emplacement 2 comme autorité : `token_vault_0`, `token_vault_1`, ou l'un des coffres de récompenses de ce pool. Si vous passez le coffre d'un autre pool ou un compte de jeton utilisateur, la vérification du propriétaire du programme de jetons échoue et l'instruction entière revient. Ce n'est pas ignoré. Les mints de NFT de position ne peuvent pas être balayés, car leur autorité de mint est révoquée quand la position est ouverte.

**Comment chaque compte source est géré**

Le programme fait deux passages sur `remaining_accounts` : chaque CPI du programme de jetons d'abord, puis les débits directs. Entrelacer les deux abandonne avec l'erreur `UnbalancedInstruction` du runtime, donc l'ordre est fixé dans le programme et vous n'avez pas à trier la liste vous-même.

| Passage | Propriétaire du compte source | Gestion |
|---|---|---|
| 1 | SPL Token ou Token-2022, compte de jeton non-natif | CPI `WithdrawExcessLamports` (discriminant du programme de jetons `38`), signé par `pool_state`. |
| 1 | SPL Token ou Token-2022, compte **natif** (wSOL) | `WithdrawExcessLamports` rejette les comptes natifs. Le programme CPIs `SyncNative`, mesure combien le `amount` enveloppé a grandi, et appelle `UnwrapLamports` (discriminant `45`) pour exactement ce delta. Il exige ensuite que le solde enveloppé égale sa valeur pré-sync, ou échoue avec `LamportsCalculateError` (`6052`). Un coffre de pool côté SOL garde sa liquidité complète. |
| 2 | `pool_state` (emplacement 2) | Débité directement jusqu'à `rent.minimum_balance(data_len)`. |
| 2 | Le programme CLMM : `AmmConfig`, `ObservationState`, `TickArrayBitmapExtension`, `TickArrayState`, `PersonalPositionState`, `LimitOrderState`, et ainsi de suite | Débité directement jusqu'à `rent.minimum_balance(data_len)`. Le compte n'a **pas** à appartenir au pool à l'emplacement 2. |
| — | N'importe quoi d'autre | **Ignoré silencieusement.** Pas d'erreur, pas de lamports déplacés. |

<Warning>
  **Le passage 2 couvre les comptes dont un utilisateur a payé le loyer.** Un `PersonalPositionState` ou `LimitOrderState` passé ici abandonne son excédent comme n'importe quel autre compte appartenant à CLMM. Il reste exempt de loyer et garde ses données. Quand il est plus tard fermé, le propriétaire récupère tout ce que le compte détient à ce moment, qui après un
