## `Initialize2`

Amorcer un nouveau pool AMM v4 lié à un marché OpenBook existant.

**Arguments**

```
nonce:        u8
open_time:    u64
init_pc_amount:   u64
init_coin_amount: u64
```

**Comptes** (modifiable `W`, signataire `S`)

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `token_program` |   |   | Vérifié `== spl_token::id()`. |
| 2 | `associated_token_program` |   |   | Utilisé pour créer l'ATA LP du créateur. |
| 3 | `system_program` |   |   | |
| 4 | `rent` |   |   | Toujours transmis dans les CPI `initialize_account` / `initialize_mint` — ne le supprimez pas. |
| 5 | `amm` | W |   | PDA `AmmInfo` `[programId, market, "amm_associated_seed"]` ; créé ici. |
| 6 | `amm_authority` |   |   | PDA `["amm authority"]` ; l'argument `nonce` doit égaler son bump. |
| 7 | `lp_mint` | W |   | PDA `[programId, market, "lp_mint_associated_seed"]` ; créé ici. |
| 8 | `coin_mint` |   |   | Doit différer de `pc_mint` (`InvalidCoinMint`). |
| 9 | `pc_mint` |   |   | |
| 10 | `pool_coin_token_account` | W |   | PDA `[programId, market, "coin_vault_associated_seed"]`. |
| 11 | `pool_pc_token_account` | W |   | PDA `[programId, market, "pc_vault_associated_seed"]`. |
| 12 | `pool_target_orders_account` | W |   | PDA `[programId, market, "target_associated_seed"]`. |
| 13 | `amm_config` |   |   | PDA de configuration au niveau du programme `["amm_config_account_seed"]` ; `InvalidConfigAccount` en cas de non-correspondance. |
| 14 | `create_fee_destination` | W |   | Doit égaler `config_feature::create_pool_fee_address` ; `InvalidFee` sinon. |
| 15 | `market` |   |   | Non validé — utilisé uniquement comme seed variable pour tous les PDAs ci-dessus, et stocké comme champ de référence. |
| 16 | `user_wallet` | W | S | Créateur. Paie le rent, les frais de création de pool et le dépôt initial. |
| 17 | `user_token_coin` | W |   | |
| 18 | `user_token_pc` | W |   | |
| 19 | `user_token_lp` | W |   | ATA LP du créateur ; créée par le programme. |

<Note>
  **Deux layouts acceptés.** La liste de 19 comptes ci-dessus est celle recommandée. Pour la
  compatibilité descendante, le programme lit aussi un layout hérité de 21 comptes, qui insère un
  `amm_open_orders` ignoré en position 7 et un `market_program` ignoré en position 16 — c'est ce
  que le constructeur d'instruction `initialize2` du dépôt émet encore. Toute autre longueur est
  analysée positionnellement d'après le layout hérité et échouera.
</Note>

**Postconditions**

- LP frappés pour le créateur = `sqrt(init_coin_amount × init_pc_amount) − 10^coin_mint.decimals`. Les décimales LP égalent `coin_mint.decimals`, donc le montant soustrait vaut exactement un token LP entier ; il n'est jamais frappé et reste définitivement hors circulation. Si `sqrt(...)` est inférieur à cela, l'instruction est annulée avec `InitLpAmountTooLess`.
- `AmmInfo.lp_amount` stocke le `sqrt(...)` complet, **et non** le montant frappé — donc `lp_mint.supply` est définitivement inférieur d'un token LP entier à `amm.lp_amount`. Toute la mathématique au prorata utilise `amm.lp_amount`.
- Aucun ordre OpenBook n'est posté (la grille du carnet d'ordres a été supprimée). `AmmInfo.market` enregistre le compte passé en position 15, mais `AmmInfo.open_orders` et `AmmInfo.market_program` sont tous deux écrits comme `Pubkey::default()`, et `coin_lot_size` / `pc_lot_size` / `min_size` sont initialisés à `0`. Sur le layout hérité de 21 comptes, les comptes supplémentaires `amm_open_orders` et `market_program` sont lus puis ignorés.

**Erreurs courantes** — `InvalidCoinMint` (coin mint et pc mint identiques), `InvalidConfigAccount` (mauvais PDA `amm_config`), `InvalidFee` (mauvaise destination des frais de création de pool), `InvalidProgramAddress` (mauvais `amm_authority` ou mauvais `nonce`), `RepeatCreateAmm` (un pool existe déjà pour ce marché), `InitLpAmountTooLess`, `InvalidSupply` (l'un des montants d'initialisation vaut `0`, ou le mint LP a déjà une offre), `AlreadyInUse`.

## `SwapBaseIn`

Swap à entrée exacte. Toujours un swap **par chemin AMM** (ne route pas via l'appariement OpenBook).

<Note>
  **Utilisez les variantes V2 pour le nouveau code.** Puisque la dépendance d'AMM v4 envers OpenBook a été supprimée, les points d'entrée V1 (`SwapBaseIn`, `SwapBaseOut`) s'attendent toujours à la liste complète de 17 comptes (ou 18 avec le compte target-orders optionnel), mais les comptes OpenBook/marché sont maintenant **acceptés positionnellement et ignorés** — ils ne sont pas validés et aucun CPI n'est émis. Passer un mauvais nombre de comptes revient toujours avec `WrongAccountsNumber`, mais le *contenu* des comptes de marché n'est plus vérifié. Les nouvelles intégrations doivent utiliser [`SwapBaseInV2` / `SwapBaseOutV2`](#swapbaseinv2-/-swapbaseoutv2), qui prennent une liste de comptes beaucoup plus petite et représentent le chemin d'exécution canonique aujourd'hui. Les formes V1 sont documentées ici pour la complétude et pour lire les transactions existantes en chaîne.
</Note>

**Arguments**

```
amount_in:            u64
minimum_amount_out:   u64
```

**Comptes** (abrégé)

| # | Nom | W | S |
|---|------|---|---|
| 1 | `token_program` |   |   |
| 2 | `amm` | W |   |
| 3 | `amm_authority` |   |   |
| 4 | `amm_open_orders` | W |   |
| 5 | `amm_target_orders` | W |   |
| 6 | `pool_coin_token_account` | W |   |
| 7 | `pool_pc_token_account` | W |   |
| 8 | `market_program` |   |   |
| 9 | `market` | W |   |
| 10 | `market_bids` | W |   |
| 11 | `market_asks` | W |   |
| 12 | `market_event_queue` | W |   |
| 13 | `market_coin_vault` | W |   |
| 14 | `market_pc_vault` | W |   |
| 15 | `market_vault_signer` |   |   |
| 16 | `user_source_token_account` | W |   |
| 17 | `user_dest_token_account` | W |   |
| 18 | `user_owner` |   | S |

**Mathématiques** — voir [`products/amm-v4/math`](/fr/products/amm-v4/math).

**Préconditions**

- `AmmStatus::from_u64(amm.status).swap_permission()` est vrai — c'est-à-dire que `status` vaut `1` (`Initialized`), `6` (`SwapOnly`) ou `7` (`WaitingTrade`). `status` est une valeur d'énumération, pas un masque de bits ; voir [`products/amm-v4/accounts`](/fr/products/amm-v4/accounts#status).
- `amm.state_data.pool_open_time <= now`.
- `amount_in > 0`.
- `user_source_token_account` détient au moins `amount_in`.

**Postconditions**

- L'utilisateur perd `amount_in` du jeton source, gagne `amount_out ≥ minimum_amount_out` du jeton destination.
- Les frais de swap restent dans les coffres, ce qui augmente l'invariant `k`. Les compteurs `need_take_pnl_*` ne sont **pas** touchés par les swaps — le PnL du protocole est recalculé à partir du delta de `k` lors du prochain `Deposit`, `Withdraw` ou `WithdrawPnl` (`Processor::calc_take_pnl`).
- Remarque : les compteurs d'analyse `state_data.swap_*_in_amount` / `swap_*_out_amount` ne sont **plus mis à jour** — leurs valeurs sont figées. Utilisez les journaux de transactions pour l'analyse du volume.

**Erreurs courantes** — `ExceededSlippage`, `InvalidInput`, `InvalidStatus`, `NotAllowed` (mint coin/pc identique).

## `MonitorStep` et autres instructions supprimées

<Warning>
  **Supprimées — non plus appelables.** À partir de la mise à jour 2026-07, `MonitorStep` (tag 2) a été supprimée du programme et **revient** maintenant (`unimplemented!`) si elle est invoquée. Son builder client a également été supprimé. Il en va de même pour `MigrateToOpenBook` (5), `WithdrawSrm` (8), `SimulateInfo` (12), `AdminCancelOrders` (13), et les points d'entrée de création de pool hérités `Initialize` (0) / `PreInitialize` (10) — utilisez `Initialize2` à la place.
</Warning>

Historiquement, `MonitorStep` actionnait l'interaction OpenBook du pool : elle réglait les ordres remplis (déplaçant les produits des coffres de marché vers les coffres du pool via CPI OpenBook), annulait les ordres obsolètes et affichait de nouveaux ordres pour combler l'écart entre `target_orders` et `amm_open_orders`. Avec la dépendance OpenBook supprimée, il n'y a rien à actionner et l'instruction est partie. Tout keeper ou intégration qui l'appelle encore doit supprimer l'appel.

## `WithdrawPnl` / `TakePnl`

Récupération administrative des frais de protocole accumulés.

**Arguments**

- `WithdrawPnl` ne prend pas d'arguments ; elle lit `need_take_pnl_*` et déplace exactement ces montants.

<Warning>
  **Changement de rupture (admin uniquement).** La liste de comptes est passée de 17 (+1 optionnel) à **10** — `amm_open_orders` et les six comptes de marché ont été supprimés — sans analyse de compatibilité. L'ancien schéma se désaligne (l'ancien #5 était `amm_open_orders`, maintenant `pool_coin_token_account`) et échoue avec des erreurs telles que `InvalidCoinVault`. </Warning>

**Comptes** (nouveau schéma de 10 comptes)

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `token_program` |   |   |
| 2 | `amm` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `amm_authority` |   |   |
| 5 | `pool_coin_token_account` | W |   |
| 6 | `pool_pc_token_account` | W |   |
| 7 | `pnl_coin_token_account` | W |   | Destinataire. |
| 8 | `pnl_pc_token_account` | W |   |
| 9 | `pnl_owner` |   | S | Multisig admin. |
| 10 | `amm_target_orders` | W |   |

**Effet**

- Transfère `need_take_pnl_coin` de `pool_coin_token_account` vers `pnl_coin_token_account`.

Modifications de paramètres d'administration, appelées par le multisig Raydium. Les arguments sont une balise `param: u8` + charge utile.

<Warning>
  **Changement de rupture (admin uniquement).** La liste de comptes a été réduite à juste `[amm (W), admin (S)]` (l'autorité, les ordres ouverts, les ordres cibles, le coffre et tous les comptes de marché ont été supprimés). ## `CreateConfigAccount` / `UpdateConfigAccount`

Gestion administrative de la PDA `AmmConfig` au niveau du programme (seed `["amm_config_account_seed"]`). Le compte détient exactement trois champs significatifs — `pnl_owner`, `cancel_owner` et `create_pool_fee` — plus deux régions de remplissage réservées ; il n'y a pas d'indicateur de création de pool. `UpdateConfigAccount` définit `pnl_owner` avec `param = 0`, `cancel_owner` avec `param = 1`, et `create_pool_fee` avec `param = 2`.

<Note>
  **Modifié en 2026-09, et rétrocompatible.** `CreateConfigAccount` ne lit plus la sysvar de rent. Sa liste de comptes est maintenant **4 comptes**, en baisse par rapport à 5 :

  | # | Nom | W | S |
  |---|------|---|---|
  | 1 | `admin` | W | S |
  | 2 | `amm_config` | W |   |
  | 3 | `pnl_owner` |   |   |
  | 4 | `system_program` |   |   |

  Le programme lit les paramètres de rent de `Rent::get()` au lieu de désérialiser un compte sysvar passé — ce que la mise à jour de dépendance Solana 3.0 a rendu naturel.

  Le compte supprimé était **dernier** dans la liste, et le gestionnaire lit ses comptes positionnellement via `next_account_info` sans vérification de longueur. Un outil d'administration existant qui passe toujours l'ancienne liste de 5 comptes continue donc de fonctionner : le compte de rent final n'est simplement jamais lu. Mettez-le à jour quand c'est pratique, pas d'urgence. `UpdateConfigAccount` est inchangé.
</Note>

`Initialize2` conserve la sysvar de rent à la position 3, et l'**utilise** toujours : le programme a arrêté d'appeler `Rent::from_account_info` sur elle, mais elle est toujours transmise aux CPI `spl_token::initialize_account` et `initialize_mint` qui créent les coffres du pool et le mint LP. Ne la supprimez pas de la liste de comptes.

## `WithdrawExcessLamports`

Récupération administrative des lamports assis au-dessus du minimum exempt de rent sur les comptes que le programme contrôle. Ajouté dans la mise à jour 2026-09 pour récupérer le surfinancement que la [réduction de rent SIMD-0437](/fr/solana-fundamentals/rent-and-reclaimable-rent) laisse derrière sur les comptes créés avant chaque étape.

Il ne déplace que l'excédent. Les soldes de jetons, les données de compte, les propriétaires et l'état du pool restent inchangés, et l'instruction est un no-op sur un compte déjà à son minimum — donc il est sûr de l'exécuter à plusieurs reprises et à nouveau après chaque étape de déploiement.

**Arguments** — aucun. La charge utile est le seul octet de balise `18`.

**Comptes**

| # | Nom | W | S | Notes |
|---|------|---|---|-------|
| 1 | `collect_lamports` | W | S | Destination pour chaque lamport récupéré. Doit égaler le portefeuille de collecte de lamports du cluster — voir [`reference/program-addresses`](/fr/reference/program-addresses#excess-lamports-collection-wallets). Tout autre signataire échoue avec `InvalidSignAccount`. |
| 2 | `amm_authority` |   |   | La seule PDA d'autorité AMM v4, re-dérivée par le programme de `["amm authority"]` avec un nonce fixe de `254`. Elle signe les CPI du programme de jetons. |
| 3 | `token_program` |   |   | **SPL Token.** Vérifié par rapport à `spl_token::id()` ; une mauvaise valeur échoue avec `InvalidSplTokenProgram`. |
| 4.. | comptes source | W |   | `M` comptes à récupérer, n'importe quel nombre, n'importe quel ordre. |

**Comment chaque compte source est traité**

Le programme se divise sur le propriétaire du compte source :

| Propriétaire du compte source | Traitement |
|---|---|
| SPL Token, `data_len == 165` (un compte de jeton), non-natif | CPI `WithdrawExcessLamports` (discriminant du programme de jetons `38`), signé par `amm_authority`. |
| SPL Token, `data_len == 165`, natif (wSOL) | `WithdrawExcessLamports` ne peut pas être utilisé sur un compte natif. Le programme CPI `SyncNative`, mesure combien le `amount` enveloppé a augmenté, `UnwrapLamports` (discriminant `45`) pour exactement ce delta, puis affirme que le solde enveloppé est revenu à sa valeur pré-sync — sinon `LamportsCalculateError`. La liquidité SOL du pool n'est donc jamais touchée. |
| SPL Token, toute autre taille (un mint LP) | CPI `WithdrawExcessLamports`, signé par `amm_authority`. |
| Le programme AMM v4 lui-même (`AmmInfo`, `TargetOrders`, `AmmConfig`) | Le programme débite le compte directement jusqu'à `rent.minimum_balance(data_len)`. |
| N'importe quoi d'autre | **Ignoré silencieusement.** Aucune erreur, aucun lamport déplacé. |

**Erreurs courantes** — `InvalidSignAccount` (mauvais signataire), `InvalidSplTokenProgram` (mauvais programme à l'emplacement 3), `InvalidProgramAddress` (mauvais `amm_authority`), `LamportsCalculateError` (code personnalisé `60` ; l'aller-retour wSOL n'a pas donné zéro), et `InsufficientFunds` du chemin contrôlé par le programme quand un compte détient moins que son propre minimum de rent.

**Pas de builder SDK.** `@raydium-io/raydium-sdk-v2` ne fournit pas de builder pour cette instruction, pas plus que le dépôt `raydium-sdk-V2-demo` — c'est un chemin d'administration. Encodez-le à la main, comme le fait la récupération côté portefeuille dans [`solana-fundamentals/rent-and-reclaimable-rent`](/fr/solana-fundamentals/rent-and-reclaimable-rent#building-the-instruction) pour l'instruction du programme de jetons.
