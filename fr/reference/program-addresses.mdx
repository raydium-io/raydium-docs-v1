### Autorité d'administrateur partagée

Tous les programmes basés sur Anchor (CLMM, CPMM, LaunchLab, Lock) partagent une seule `Pubkey` d'administrateur codée en dur pour le contrôle d'accès au niveau des instructions vers les chemins d'administrateur (tels que `CreateAmmConfig` ou `UpdatePoolStatus`) :

| Cluster | Administrateur |
|---------|-------|
| mainnet-beta | `GThUX1Atko4tqhN2NaiTazWSeFWMuiUvfFnyJyUghFMJ` |
| devnet | `DRayqG9RXYi8WHgWEmRQGrUWRWbhjYWYkCRJDd6JBBak` |

Les autorités opérationnelles au niveau du compte (par exemple `protocol_owner`, `fund_owner` sur `AmmConfig` CPMM/CLMM, ou les portefeuilles de migration sur `GlobalConfig` LaunchLab) sont stockés on-chain et peuvent différer de l'administrateur du programme. Lisez-les directement depuis le compte de configuration pertinent avant d'envoyer des transactions critiques.

### Autorités de gel d'émetteur restreint CLMM

### Conventions de configuration partagée / PDA

Plusieurs programmes Raydium exposent des **comptes de configuration** dont les clés publiques sont stables et listées sur l'API publique. Préférez la recherche API au codage en dur :

```
# Configurations de frais CPMM (retourne un tableau de {id, index, tradeFeeRate, ...})
GET https://api-v3.raydium.io/main/cpmm-config

# Configurations de frais CLMM
GET https://api-v3.raydium.io/main/clmm-config
```

Paramètres de frais `AmmConfig` CPMM par défaut index `0` (pool standard 0,25%), pour référence :

| Champ | Valeur | Signification |
|-------|-------|---------|
| `trade_fee_rate` | `2500` | 0,25% du volume d'échange |
| `protocol_fee_rate` | `120000` | 12% **des frais d'échange** (pas du volume) acheminés vers le protocole |
| `fund_fee_rate` | `40000` | 4% **des frais d'échange** acheminés vers le multisig du fonds |
| `creator_fee_rate` | `500` | 0,05% du volume d'échange au créateur du pool (optionnel) |

Voir [`products/cpmm/fees`](/fr/products/cpmm/fees) pour savoir comment les répartitions se composent, et [`reference/fee-comparison`](/fr/reference/fee-comparison) pour la matrice inter-produits.

### Graines PDA

Les graines ci-dessous sont **canoniques** et utilisées à la fois par le SDK et les CPIs on-chain. Calculez toujours les PDAs ; ne codez pas en dur les adresses dérivées.

```ts
// CPMM — toutes les graines sont des chaînes ASCII statiques sauf indication contraire.
const [ammConfig]   = PublicKey.findProgramAddressSync(
  [Buffer.from("amm_config"), u16ToBytes(index)],
  CPMM_PROGRAM_ID,
);
const [authority]   = PublicKey.findProgramAddressSync(
  [Buffer.from("vault_and_lp_mint_auth_seed")],
  CPMM_PROGRAM_ID,
);
const [poolState]   = PublicKey.findProgramAddressSync(
  [Buffer.from("pool"), ammConfig.toBuffer(), token0Mint.toBuffer(), token1Mint.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [lpMint]      = PublicKey.findProgramAddressSync(
  [Buffer.from("pool_lp_mint"), poolState.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [vault0]      = PublicKey.findProgramAddressSync(
  [Buffer.from("pool_vault"), poolState.toBuffer(), token0Mint.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [vault1]      = PublicKey.findProgramAddressSync(
  [Buffer.from("pool_vault"), poolState.toBuffer(), token1Mint.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [observation] = PublicKey.findProgramAddressSync(
  [Buffer.from("observation"), poolState.toBuffer()],
  CPMM_PROGRAM_ID,
);
```

`token0Mint` / `token1Mint` sont **triés par ordre d'octets de clé publique** (token0 < token1) avant hachage. Se tromper produit un PDA valide pour un pool inexistant.

Les graines CLMM équivalentes suivent le même style ; voir [`products/clmm/accounts`](/fr/products/clmm/accounts).

## Comment vérifier une adresse on-chain

1. **Solana Explorer.** Collez l'adresse dans [explorer.solana.com](https://explorer.solana.com) et confirmez qu'elle est marquée `Program` avec une autorité de mise à niveau actuelle. Mainnet-beta devrait afficher les déploiements signés par l'autorité de mise à niveau de Raydium.
2. **CLI.** Utilisez `solana program show <PROGRAM_ID> -u mainnet-beta` pour inspecter l'emplacement du déploiement, le chargeur BPF, l'autorité de mise à niveau et la longueur des données. Enregistrez-les dans votre runbook.
3. **Attachement IDL.** Interrogez l'IDL on-chain avec `anchor idl fetch <PROGRAM_ID> --provider.cluster mainnet`. Le champ `address` de l'IDL doit correspondre. Les mêmes IDLs sont mirrorés sur [github.com/raydium-io/raydium-idl](https://github.com/raydium-io/raydium-idl) — comparez l'IDL on-chain par rapport au dépôt avant de lui faire confiance.
4. **Autorités de configuration/administrateur.** Pour les comptes de configuration CPMM/CLMM, lisez le champ `owner`/`protocol_owner` et confirmez qu'il correspond au multisig Raydium actuel publié dans [`security/admin-and-multisig`](/fr/security/admin-and-multisig).

Si l'une des quatre vérifications ci-dessus est en désaccord avec cette page, considérez cette page comme incorrecte et ouvrez un problème avant d'écrire un nouveau code par rapport aux adresses.

- Les modifications des IDs de programme sont critiques pour la sécurité. Ne **pas** déployer un changement d'ID de programme sans (a) créer un lien vers l'annonce Raydium, (b) ajouter une entrée dans [`reference/changelog`](/fr/reference/changelog), et (c) exécuter une vérification de lien sur la documentation pour confirmer qu'aucune page ne référence toujours l'ancienne valeur.
- Les dépréciations restent dans le tableau avec une note de statut plutôt que d'être supprimées — les pools existants se résolvent toujours via l'ancien programme.
