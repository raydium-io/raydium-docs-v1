### Graines PDA

Les graines ci-dessous sont **canoniques** et utilisées à la fois par le SDK et par les CPIs on-chain. Calculez toujours les PDAs ; ne codez pas en dur les adresses dérivées.

```ts
// CPMM — toutes les graines sont des chaînes ASCII statiques sauf indication contraire.
const [ammConfig]   = PublicKey.findProgramAddressSync(
  [Buffer.from("amm_config"), u16ToBytes(index)],
  CPMM_PROGRAM_ID,
);
const [authority]   = PublicKey.findProgramAddressSync(
  [Buffer.from("vault_and_lp_mint_auth_seed")],
  CPMM_PROGRAM_ID,
);
const [poolState]   = PublicKey.findProgramAddressSync(
  [Buffer.from("pool"), ammConfig.toBuffer(), token0Mint.toBuffer(), token1Mint.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [lpMint]      = PublicKey.findProgramAddressSync(
  [Buffer.from("pool_lp_mint"), poolState.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [vault0]      = PublicKey.findProgramAddressSync(
  [Buffer.from("pool_vault"), poolState.toBuffer(), token0Mint.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [vault1]      = PublicKey.findProgramAddressSync(
  [Buffer.from("pool_vault"), poolState.toBuffer(), token1Mint.toBuffer()],
  CPMM_PROGRAM_ID,
);
const [observation] = PublicKey.findProgramAddressSync(
  [Buffer.from("observation"), poolState.toBuffer()],
  CPMM_PROGRAM_ID,
);
```

`token0Mint` / `token1Mint` sont **triés par ordre d'octets de clé publique** (token0 < token1) avant le hachage. Faire cela mal produit un PDA valide pour un pool inexistant.

Les graines CLMM équivalentes suivent le même style ; voir [`products/clmm/accounts`](/fr/products/clmm/accounts).

## Comment vérifier une adresse on-chain

1. **Solana Explorer.** Collez l'adresse dans [explorer.solana.com](https://explorer.solana.com) et confirmez qu'elle est marquée `Program` avec une autorité de mise à niveau actuelle. Mainnet-beta devrait afficher les déploiements signés par l'autorité de mise à niveau de Raydium.
2. **CLI.** Utilisez `solana program show <PROGRAM_ID> -u mainnet-beta` pour inspecter l'emplacement de déploiement, le chargeur BPF, l'autorité de mise à niveau et la longueur des données. Enregistrez-les dans votre runbook.
3. **Attachement IDL.** `anchor idl fetch <PROGRAM_ID> --provider.cluster mainnet` fonctionne pour **CLMM, LaunchLab et Lock**, qui conservent toujours un compte `anchor:idl` hérité détenu par le programme lui-même. Cela **ne fonctionne pas** pour CPMM : l'IDL on-chain de CPMM a été déplacé vers le programme Program Metadata (`ProgM6JCCvbYkfKqJYHePx4xxSUSqJp7rh8Lyv7nk7S`) dans la mise à niveau de 2026-09, donc récupérez-le de là à la place. AMM v4, Stable AMM et Farm n'ont pas d'IDL on-chain. Les IDLs sont mirrorés sur [github.com/raydium-io/raydium-idl](https://github.com/raydium-io/raydium-idl) — comparez l'IDL on-chain par rapport au dépôt avant de lui faire confiance.
4. **Autorités de configuration/administrateur.** Pour les comptes de configuration CPMM/CLMM, lisez le champ `owner`/`protocol_owner` et confirmez qu'il correspond au multisig Raydium actuel publié dans [`security/admin-and-multisig`](/fr/security/admin-and-multisig).

Si l'une des quatre vérifications ci-dessus est en désaccord avec cette page, traitez cette page comme incorrecte et ouvrez un problème avant d'écrire un nouveau code par rapport aux adresses.

## Mise à jour de cette page

- Les modifications des IDs de programme sont critiques pour la sécurité. Ne **pas** expédier une modification d'ID de programme sans (a) créer un lien vers l'annonce Raydium, (b) ajouter une entrée dans [`reference/changelog`](/fr/reference/changelog) et (c) exécuter une vérification de lien sur la documentation pour confirmer qu'aucune page ne référence toujours l'ancienne valeur.
- Les dépréciations restent dans le tableau avec une note de statut plutôt que d'être supprimées — les pools existants se résolvent toujours via l'ancien programme.
