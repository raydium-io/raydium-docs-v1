## `Withdraw`

销毁 LP，接收两种代币。

**参数**

```
amount: u64    // 要销毁的 LP
```

**账户** — 类似 `Deposit`，方向相反；`lp_mint` 对销毁可写，用户 ATA 是接收方。账户布局不变（市场账户仍按位置传递，被忽略）。不再有从 OpenBook 结算的步骤——按比例分配的数学直接使用金库余额。

## `SwapBaseIn`

精确输入交换。始终是**AMM 路径**交换（不通过 OpenBook 匹配路由）。

<Note>
  **为新代码使用 V2 变体。** 由于 AMM v4 的 OpenBook 依赖已被移除，V1 入口点（`SwapBaseIn`、`SwapBaseOut`）仍然期望完整的 17 账户列表（或 18 个带可选 target-orders 账户），但 OpenBook/市场账户现在**按位置被接受并被忽略**——它们不被验证，不发起 CPI。传递错误的账户*数量*仍会以 `WrongAccountsNumber` 回滚，但市场账户*内容*不再被检查。新的集成应使用 [`SwapBaseInV2` / `SwapBaseOutV2`](#swapbaseinv2--swapbaseoutv2)，它们采用更小的账户列表，代表当今的规范执行路径。V1 形式在此记录以供完整性和阅读现有链上交易。
</Note>

**参数**

```
amount_in:            u64
minimum_amount_out:   u64
```

**账户**（简化）

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `token_program` |   |   |
| 2 | `amm` | W |   |
| 3 | `amm_authority` |   |   |
| 4 | `amm_open_orders` | W |   |
| 5 | `amm_target_orders` | W |   |
| 6 | `pool_coin_token_account` | W |   |
| 7 | `pool_pc_token_account` | W |   |
| 8 | `market_program` |   |   |
| 9 | `market` | W |   |
| 10 | `market_bids` | W |   |
| 11 | `market_asks` | W |   |
| 12 | `market_event_queue` | W |   |
| 13 | `market_coin_vault` | W |   |
| 14 | `market_pc_vault` | W |   |
| 15 | `market_vault_signer` |   |   |
| 16 | `user_source_token_account` | W |   |
| 17 | `user_dest_token_account` | W |   |
| 18 | `user_owner` |   | S |

**数学** — 见 [`products/amm-v4/math`](/zh/products/amm-v4/math)。

**前置条件**

- `amm.status` 允许交换（状态位掩码的第 0 位未设置）。
- `amm.state_data.pool_open_time <= now`。
- `amount_in > 0`。
- `user_source_token_account` 至少持有 `amount_in`。

**后置条件**

- 用户失去 `amount_in` 的源代币，获得 `amount_out ≥ minimum_amount_out` 的目标代币。
- `need_take_pnl_*` 按协议费份额递增。
- 注意：`state_data.swap_*_in_amount` / `swap_*_out_amount` 分析计数器**不再更新**——其值被冻结。使用交易日志进行交易量分析。

**常见错误** — `ExceededSlippage`、`InvalidInput`、`InvalidStatus`、`NotAllowed`（coin/pc mint 相同）。

## `SwapBaseInV2` / `SwapBaseOutV2`

变体交换入口点（标签 **16** / **17**），**完全跳过 OpenBook 账户**。数学与 V1 路径相同，但账户列表缩小到仅 AMM 端和用户——**8 个账户，`amm_open_orders` 不被传递**：

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `token_program` |   |   |
| 2 | `amm` | W |   |
| 3 | `amm_authority` |   |   |
| 4 | `pool_coin_token_account` | W |   |
| 5 | `pool_pc_token_account` | W |   |
| 6 | `user_source_token_account` | W |   |
| 7 | `user_dest_token_account` | W |   |
| 8 | `user_owner` |   | S |

池储备现在是金库余额（减去待处理 PnL），所以报价数学直接且与 v1 路径相同。使用 V2 来节省计算并避免传递（现在被忽略的）市场账户。Raydium 路由器在通过 AMM v4 路由时始终使用 V2 形式。

参数与 V1 形式相同（`SwapBaseInV2` 的 `amount_in / minimum_amount_out`；`SwapBaseOutV2` 的 `max_amount_in / amount_out`）。

## `MonitorStep` 和其他已移除的指令

<Warning>
  **已移除——不再可调用。** 自 2026-07 升级以来，`MonitorStep`（标签 2）已从程序中移除，如果被调用现在会**回滚**（`unimplemented!`）。其客户端构建器也被删除了。同样适用于 `MigrateToOpenBook`（5）、`WithdrawSrm`（8）、`SimulateInfo`（12）、`AdminCancelOrders`（13）以及旧版 `Initialize`（0）/ `PreInitialize`（10）池创建入口点——改用 `Initialize2`。
</Warning>

历史上，`MonitorStep` 驱动池的 OpenBook 交互：它结算已成交的订单（通过 OpenBook CPI 将收益从市场金库移到池金库），取消陈旧订单，并发布新订单以缩小 `target_orders` 和 `amm_open_orders` 之间的差距。随着 OpenBook 依赖的移除，没有什么可驱动的，指令已消失。任何仍调用它的 keeper 或集成必须移除该调用。

## `WithdrawPnl` / `TakePnl`

管理员清扫累积的协议费。

**参数**

- `WithdrawPnl` 不接受参数；它读取 `need_take_pnl_*` 并移动这些确切的数量。

<Warning>
  **破坏性更改（仅限管理员）。** 账户列表从 17（+1 可选）下降到 **10**——`amm_open_orders` 和所有六个市场账户被移除——**没有兼容性解析**。旧布局错位（旧 #5 是 `amm_open_orders`，现在是 `pool_coin_token_account`）并以 `InvalidCoinVault` 等错误失败。管理员工具必须更新。
</Warning>

**账户**（新 10 账户布局）

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `token_program` |   |   |
| 2 | `amm` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `amm_authority` |   |   |
| 5 | `pool_coin_token_account` | W |   |
| 6 | `pool_pc_token_account` | W |   |
| 7 | `pnl_coin_token_account` | W |   | 接收方。 |
| 8 | `pnl_pc_token_account` | W |   |
| 9 | `pnl_owner` |   | S | 管理员多签。 |
| 10 | `amm_target_orders` | W |   |

**效果**

- 从 `pool_coin_token_account` 转移 `need_take_pnl_coin` 到 `pnl_coin_token_account`。
- pc 相同。
- 将 `need_take_pnl_coin` 和 `need_take_pnl_pc` 置零。
- **逻辑更改**：如果金库余额不足以覆盖累积的 PnL，指令直接返回 `TakePnlError`（它不再操纵订单簿状态）。

由于累积的 PnL 已从不变量中排除，储备没有变化。

## `SetParams`

管理员参数更改，由 Raydium 多签调用。参数是 `param: u8` 标签 + 有效负载。

<Warning>
  **破坏性更改（仅限管理员）。** 账户列表被减少到仅 `[amm (W), admin (S)]`（权限、open-orders、target-orders、金库和所有市场账户被移除）。`param` 枚举被**重新编号和修剪**：`Status` = 0、`State` = 1、`Fees` = **2**（曾是 9）、`SetOpenTime` = **3**（曾是 11）。所有订单簿网格参数和 `AmmOwner`、`LastOrderDistance`、`UpdateOpenOrder` 被移除，`SetParamsInstruction` 结构体删除了 `new_pubkey` 和 `last_order_distance`。管理员工具必须更新。
</Warning>

## `CreateConfigAccount` / `UpdateConfigAccount`

程序级 `AmmConfig` PDA（seed `["amm_config_account_seed"]`）的管理员管理，它持有 PnL 所有者、创建池费用和池创建标志。

<Note>
  **在 2026-09 中更改，向后兼容。** `CreateConfigAccount` 不再读取 rent sysvar。其账户列表现在是 **4 个账户**，从 5 个下降：

  | # | 名称 | W | S |
  |---|------|---|---|
  | 1 | `admin` | W | S |
  | 2 | `amm_config` | W |   |
  | 3 | `pnl_owner` |   |   |
  | 4 | `system_program` |   |   |

  程序从 `Rent::get()` 读取 rent 参数，而不是反序列化传入的 sysvar 账户——这是 Solana 3.0 依赖升级使其自然的做法。

  被移除的账户是列表中的**最后一个**，处理程序通过 `next_account_info` 按位置读取其账户，没有长度检查。因此，仍传递旧 5 账户列表的现有管理员工具继续工作：尾部 rent 账户根本不被读取。在方便时更新它，不是紧急的。`UpdateConfigAccount` 不变。
</Note>

`Initialize2` 在位置 3 保留 rent sysvar，并仍然**使用**它：程序停止在其上调用 `Rent::from_account_info`，但它仍被转发到创建池金库和 LP mint 的 `spl_token::initialize_account` 和 `initialize_mint` CPI 中。不要从账户列表中删除它。

## `WithdrawExcessLamports`

管理员清扫坐在程序控制的账户上 rent-exempt 最小值之上的 lamport。在 2026-09 升级中添加，以恢复 [SIMD-0437 rent 减少](/zh/solana-fundamentals/rent-and-reclaimable-rent) 在每个步骤之前创建的账户上留下的过度资金。

它仅移动超额部分。代币余额、账户数据、所有者和池状态保持不变，指令在已处于最小值的账户上是无操作的——所以重复触发和在每次推出步骤后再次触发是安全的。

**参数** — 无。有效负载是单个标签字节 `18`。

**账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `collect_lamports` | W | S | 每个清扫 lamport 的目标。必须等于集群的 collect-lamports 钱包——见 [`reference/program-addresses`](/zh/reference/program-addresses#excess-lamports-collection-wallets)。任何其他签名者以 `InvalidSignAccount` 失败。 |
| 2 | `amm_authority` |   |   | 单个 AMM v4 权限 PDA，由程序从 `["amm authority"]` 重新派生，固定 nonce 为 `254`。它签署 token-program CPI。 |
| 3 | `token_program` |   |   | **SPL Token。** 根据 `spl_token::id()` 检查；错误的值以 `InvalidSplTokenProgram` 失败。 |
| 4.. | 源账户 | W |   | `M` 个要清扫的账户，任意数量，任意顺序。 |

**每个源账户的处理方式**

程序根据源账户的 `owner` 分派：

| 源账户所有者 | 处理 |
|---|---|
| SPL Token，`data_len == 165`（token 账户），非原生 | CPI `WithdrawExcessLamports`（token-program 判别式 `38`），由 `amm_authority` 签署。 |
| SPL Token，`data_len == 165`，原生（wSOL） | `WithdrawExcessLamports` 不能用于原生账户。程序 CPI `SyncNative`，测量包装的 `amount` 增长了多少，`UnwrapLamports`（判别式 `45`）恰好那个增量，然后断言包装的余额回到其预同步值——否则 `LamportsCalculateError`。池的 SOL 端流动性因此永远不被触及。 |
| SPL Token，任何其他大小（LP mint） | CPI `WithdrawExcessLamports`，由 `amm_authority` 签署。 |
| AMM v4 程序本身（`AmmInfo`、`TargetOrders`、`AmmConfig`、withdraw 队列） | 程序直接将账户扣除到 `rent.minimum_balance(data_len)`。 |
| 其他任何东西 | **静默跳过。** 无错误，无 lamport 移动。 |

**常见错误** — `InvalidSignAccount`（错误的签名者）、`InvalidSplTokenProgram`（槽 3 中的错误程序）、`InvalidProgramAddress`（错误的 `amm_authority`）、`LamportsCalculateError`（自定义代码 `60`；wSOL 往返没有净为零）和来自程序所有路径的 `InsufficientFunds`，当账户持有少于其自身 rent 最小值时。

**无 SDK 构建器。** `@raydium-io/raydium-sdk-v2` 不为此指令提供构建器，`raydium-sdk-V2-demo` 仓库也不提供——这是管理员路径。手动编码，就像 [`solana-fundamentals/rent-and-reclaimable-rent`](/zh/solana-fundamentals/rent-and-reclaimable-rent#building-the-instruction) 中的钱包端清扫对 token-program 指令所做的那样。
