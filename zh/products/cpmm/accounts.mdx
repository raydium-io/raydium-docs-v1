## CPMM 池的六个账户

每个 CPMM 池由 CPMM 程序下的六个程序派生地址（PDA）完全描述，加上它引用的一个共享 `AmmConfig` 账户。一旦你有了两个 mint，你可以确定性地推导出所有内容，无需接触网络。

| 账户 | 种子 | 所有者 | 用途 |
|---------|---------|-------|---------|
| `authority` | `"vault_and_lp_mint_auth_seed"` | CPMM | 每次金库移动和每次 LP mint/burn 的签名者。在**所有** CPMM 池中共享。 |
| `poolState` | `"pool"`、`ammConfig`、`token0Mint`、`token1Mint` **或**任何签名者提供的随机密钥对 | CPMM | 池的状态结构——mint 对、金库余额、LP 供应、费用累积、观察指针。CPMM `Initialize` 指令接受从四个种子派生的规范 PDA **或**由创建者签名的任意密钥对。随机密钥对路径存在是为了防止前置运行攻击，其中对手监视内存池并竞速占据规范 PDA，抢在合法创建者之前。 |
| `lpMint` | `"pool_lp_mint"`、`poolState` | SPL Token | 池的 LP 代币。供应量 = 总 LP 未偿还。Mint 权限 = CPMM authority PDA。 |
| `vault0` | `"pool_vault"`、`poolState`、`token0Mint` | SPL Token / Token-2022 | 持有池的 token0 余额。由 authority PDA 拥有。 |
| `vault1` | `"pool_vault"`、`poolState`、`token1Mint` | SPL Token / Token-2022 | 持有池的 token1 余额。由 authority PDA 拥有。 |
| `observation` | `"observation"`、`poolState` | CPMM | 用于 TWAP 的价格样本环形缓冲区。在每次交换时写入。 |

以及共享配置：

| 账户 | 种子 | 所有者 | 用途 |
|---------|---------|-------|---------|
| `ammConfig` | `"amm_config"`、`index: u16` | CPMM | 持有交易/协议/基金/创建者费率、默认创建者费用分享率和管理员密钥。每个"费用等级"一个。PoolState 在创建时绑定到一个，之后无法更改。 |

以及每个创建者的可选账户：

| 账户 | 种子 | 所有者 | 用途 |
|---------|---------|-------|---------|
| `creatorFeeShare` | `"creator_fee_share"`、`creator`、`ammConfig` | CPMM | 为一个费用等级上的一个池创建者覆盖 `AmmConfig.creator_fee_share_rate`。可选——当不存在时，配置默认值适用。由 2026-09-13 创建者费用分享升级添加。 |

## 仅从两个 mint 推导池

```ts
import { PublicKey } from "@solana/web3.js";
import BN from "bn.js";

const CPMM_PROGRAM_ID = new PublicKey(
  "CPMMoo8L3F4NbTegBCKVNunggL7H1ZpdTHKxQB5qKP1C"
); // mainnet — see reference/program-addresses

function u16ToBytes(n: number): Buffer {
  const b = Buffer.alloc(2);
  b.writeUInt16BE(n);
  return b;
}

// token0 < token1 by byte order. Getting this wrong yields a valid PDA
// that points at a nonexistent pool.
function sortMints(a: PublicKey, b: PublicKey): [PublicKey, PublicKey] {
  return Buffer.compare(a.toBuffer(), b.toBuffer()) < 0 ? [a, b] : [b, a];
}

export function deriveCpmmAccounts(
  mintA: PublicKey,
  mintB: PublicKey,
  ammConfigIndex = 0,
) {
  const [token0Mint, token1Mint] = sortMints(mintA, mintB);

  const [ammConfig] = PublicKey.findProgramAddressSync(
    [Buffer.from("amm_config"), u16ToBytes(ammConfigIndex)],
    CPMM_PROGRAM_ID,
  );
  const [authority] = PublicKey.findProgramAddressSync(
    [Buffer.from("vault_and_lp_mint_auth_seed")],
    CPMM_PROGRAM_ID,
  );
  const [poolState] = PublicKey.findProgramAddressSync(
    [
      Buffer.from("pool"),
      ammConfig.toBuffer(),
      token0Mint.toBuffer(),
      token1Mint.toBuffer(),
    ],
    CPMM_PROGRAM_ID,
  );
  const [lpMint] = PublicKey.findProgramAddressSync(
    [Buffer.from("pool_lp_mint"), poolState.toBuffer()],
    CPMM_PROGRAM_ID,
  );
  const [vault0] = PublicKey.findProgramAddressSync(
    [Buffer.from("pool_vault"), poolState.toBuffer(), token0Mint.toBuffer()],
    CPMM_PROGRAM_ID,
  );
  const [vault1] = PublicKey.findProgramAddressSync(
    [Buffer.from("pool_vault"), poolState.toBuffer(), token1Mint.toBuffer()],
    CPMM_PROGRAM_ID,
  );
  const [observation] = PublicKey.findProgramAddressSync(
    [Buffer.from("observation"), poolState.toBuffer()],
    CPMM_PROGRAM_ID,
  );

  return {
    ammConfig,
    authority,
    poolState,
    lpMint,
    token0Mint,
    token1Mint,
    vault0,
    vault1,
    observation,
  };
}
```

<Tip>
  **推导池 PDA 前始终对 mint 进行排序。** 种子按字节顺序对两个 mint 进行哈希，而不是按用户顺序。具有 `(A, B)` 和 `(B, A)` 的两个池会在链上发生碰撞——排序是程序使映射规范化的方式。
</Tip>

<Note>
  **池 ID 并不总是规范 PDA。** `Initialize` 除了上面的 PDA 外，还接受任意签名者密钥对作为 `pool_state`。如果传递的账户与规范 PDA 不匹配，程序要求它是签名者——即创建者传递一个他们用其签名的新密钥对。这是前置运行防御：任何竞速抢占规范 PDA 的第三方都可以被合法创建者使用随机密钥对绕过。下游 PDA（`lpMint`、`vault0`、`vault1`、`observation`）仍然从 `poolState.key()` 派生，因此它们对使用的任何地址保持唯一。索引池时，始终从链上状态发现池 ID（例如，CPMM 程序下的 `PoolState` 账户），而不是通过推导规范 PDA——后者会遗漏随机密钥对池。
</Note>

## 账户布局

完整的 Rust 定义位于 [`raydium-cp-swap`](https://github.com/raydium-io/raydium-cp-swap) 源代码中。下面的字段是你在集成中会读取的字段。

### `PoolState`

```rust
// programs/cp-swap/src/states/pool.rs
pub struct PoolState {
    pub amm_config: Pubkey,               // binds this pool to an AmmConfig
    pub pool_creator: Pubkey,             // who ran initialize
    pub token_0_vault: Pubkey,            // == vault0 PDA
    pub token_1_vault: Pubkey,            // == vault1 PDA

    pub lp_mint: Pubkey,
    pub token_0_mint: Pubkey,
    pub token_1_mint: Pubkey,

    pub token_0_program: Pubkey,          // SPL Token or Token-2022 program
    pub token_1_program: Pubkey,

    pub observation_key: Pubkey,          // == observation PDA
    pub auth_bump: u8,
    pub status: u8,                       // bitmask: deposit | withdraw | swap
    pub lp_mint_decimals: u8,
    pub mint_0_decimals: u8,
    pub mint_1_decimals: u8,

    pub lp_supply: u64,                   // mirrors lp_mint supply
    pub protocol_fees_token_0: u64,
    pub protocol_fees_token_1: u64,
    pub fund_fees_token_0: u64,
    pub fund_fees_token_1: u64,

    pub open_time: u64,                   // unix; swaps rejected before this
    pub recent_epoch: u64,

    // Creator-fee state (added after the original layout):
    pub creator_fee_on: u8,               // 0=BothToken, 1=OnlyToken0, 2=OnlyToken1
    pub enable_creator_fee: bool,
    pub padding1: [u8; 6],
    pub creator_fees_token_0: u64,
    pub creator_fees_token_1: u64,

    pub padding: [u64; 28],
}
```

实际要读取的内容：

- **`lp_supply`** ——池的内部 LP 总数。它**不**等于 LP mint 的供应量：它恰好比供应量高 100 个基础单位，因为 100 个锁定单位在这里计数但从不铸造。所有 LP 份额数学（存款、提款）都除以 `lp_supply`，所以使用此字段，不要替换 mint 的链上供应量。
- **`protocol_fees_token{0,1}`**、**`fund_fees_token{0,1}`** ——*累积的*费用尚未扫除。这些不影响交换定价；它们位于金库中，直到调用 `CollectProtocolFee` / `CollectFundFee`。`protocol_fees_token{0,1}` 在收集创建者费用时也接收协议对创建者费用的份额，所以它在交换外增长——见 [`products/cpmm/fees`](/zh/products/cpmm/fees#protocol-share-of-the-creator-fee)。
- **`status`** ——一个位掩码，控制是否允许 `Swap`、`Deposit`、`Withdraw`。由管理员通过 `UpdatePoolStatus` 更新。SDK 在构建交易前检查此项；如果你直接 CPI，自己检查。
- **`token0_program` / `token1_program`** ——为每个金库 CPI 的代币程序。一个可以是经典 SPL Token，另一个是 Token-2022；它们是独立的。
- **`open_time`** ——Unix 时间戳。此时间之前的交换失败。`open_time` 之前允许存款，以便可以对池进行种子填充。
- **`creator_fee_on` / `enable_creator_fee`** ——共同控制此池的可选创建者费用是否活跃以及从交换的哪一侧收集。`enable_creator_fee == false` 完全清零创建者费用路径。启用时，`creator_fee_on` 选择：`0` = 从交换输入的任何代币收取费用（`BothToken`）；`1` = 仅从 `token_0` 收取费用（跳过 `token_1 → token_0` 交换）；`2` = 仅从 `token_1` 收取费用。在池创建时通过 `InitializeWithPermission` 设置；之后无法更改。
- **`creator_fees_token_{0,1}`** ——累积的创建者费用，由 `CollectCreatorFee` 或 `CollectCreatorFeePermissionless` 扫除。两条路径都清零完整计数器，但自 2026-09-13 创建者费用分享升级以来，只有部分余额离开池：协议的份额**添加到 `protocol_fees_token_{0,1}`**，其余部分转移给创建者。无权限路径将收件人固定为 `pool_creator` 的规范 ATA。`PoolState` 本身没有更改——没有共享金额的单独计数器。

### `AmmConfig`

```rust
pub struct AmmConfig {
    pub bump: u8,
    pub disable_create_pool: bool,
    pub index: u16,                       // matches the seed
    pub trade_fee_rate: u64,              // e.g., 2500 = 0.25%
    pub protocol_fee_rate: u64,           // fraction of trade fee to protocol
    pub fund_fee_rate: u64,               // fraction of trade fee to fund
    pub create_pool_fee: u64,             // paid once at init (in SOL or token)
    pub protocol_owner: Pubkey,           // can call CollectProtocolFee
    pub fund_owner: Pubkey,               // can call CollectFundFee
    pub creator_fee_rate: u64,            // optional pool-creator fee rate (1/1_000_000 of volume)
    pub creator_fee_share_rate: u64,      // protocol's default share OF the creator fee
    pub padding: [u64; 14],
}
// AmmConfig::LEN == 236 bytes — unchanged.
```

需要注意三件事：

1. **`trade_fee_rate` 和 `creator_fee_rate` 是交易量的分数**，两者都以 `1/1_000_000` 单位表示。`2500` 表示交易量的 0.25%。**`protocol_fee_rate` 和 `fund_fee_rate` 是*交易费用*的分数**（不是交易量），使用相同的 `1/1_000_000` 分母。创建者费用**不是**交易费用的分数——它是自己独立的费率。完整算术在 [`products/cpmm/fees`](/zh/products/cpmm/fees)。
2. **`index` 是 `u16`**，所以种子哈希使用 2 字节大端序。字节顺序偏差一是常见的集成错误。
3. **`AmmConfig` 在池级别是不可变的。** 池在创建时指向一个 `AmmConfig`，之后永不切换。费用更改会传播，因为池在每次交换时读取配置——但池无法在费用等级之间移动。

关于创建者费用的说明：**费率本身**（`creator_fee_rate`）位于 `AmmConfig` 上，在费用等级中共享。特定池是否实际收取它（`enable_creator_fee`）以及它在交换的哪一侧（`creator_fee_on`）位于 `PoolState` 上。创建者费用**独立于**交易费用——它是自己的费率，累积到自己的计数器（`creator_fees_token_{0,1}`），永不减少交易费用的 LP / 协议 / 基金份额。扫除通过 `CollectCreatorFee` 或目标受限的 `CollectCreatorFeePermissionless` 进行，两条路径都在输出时将累积余额的份额交给协议——以 `creator_fee_share_rate`，或当该 `(creator, amm_config)` 对存在 [`CreatorFeeShare`](#creatorfeeshare) PDA 时以该费率。见 [`products/cpmm/fees`](/zh/products/cpmm/fees#protocol-share-of-the-creator-fee) 了解完整机制。

### `Permission`

由 `InitializeWithPermission` 使用的小型访问控制账户。CPMM 程序支持一条有权限的池创建路径，以便其他程序（例如 LaunchLab 在将代币升级到 CPMM 时）可以证明他们有权针对给定的 `AmmConfig` 创建池。

```rust
pub struct Permission {
    pub authority: Pubkey,    // who is allowed to call InitializeWithPermission
    pub padding: [u64; 30],
}
// Permission::LEN == 8 + 32 + 8 * 30 == 280 bytes
```

Permission PDA 由 CPMM 管理员或专用权限 PDA 创建者权限通过 `CreatePermissionPda` 创建。自 2026-09 升级以来，`ClosePermissionPda` 接受相同的两个签名者；之前仅限管理员。最终用户不直接与此账户交互——它是跨程序流的管道。见 [`security/admin-and-multisig`](/zh/security/admin-and-multisig) 了解角色边界，见 [`reference/program-addresses`](/zh/reference/program-addresses) 了解规范地址。

### `CreatorFeeShare`

一个可选账户，为一个 `(池创建者, AmmConfig)` 对覆盖协议对创建者费用的份额。由 2026-09-13 创建者费用分享升级添加。

```rust
// programs/cp-swap/src/states/creator_fee_share.rs
pub const CREATOR_FEE_SHARE_SEED: &str = "creator_fee_share";

pub struct CreatorFeeShare {
    pub bump: u8,
    pub creator: Pubkey,       // the pool creator this rate applies to
    pub amm_config: Pubkey,    // the fee tier this rate applies to
    pub share_rate: u64,       // protocol's share OF the creator fee, 1/1_000_000
    pub padding: [u64; 8],
}
// CreatorFeeShare::LEN == 8 + 1 + 32 * 2 + 8 + 8 * 8 == 145 bytes
```

```ts
const [creatorFeeShare] = PublicKey.findProgramAddressSync(
  [Buffer.from("creator_fee_share"), creator.toBuffer(), ammConfig.toBuffer()],
  CPMM_PROGRAM_ID, // see reference/program-addresses
);
```

它的行为方式：

- **它是可选的，但账户在指令中永不可选。** `CollectCreatorFee` 和 `CollectCreatorFeePermissionless` 都使用上面的种子约束声明 `creator_fee_share`，并在每次调用时接受它。程序然后检查账户是否为空或外部拥有；如果是，它回退到 `AmmConfig.creator_fee_share_rate`。所以客户端必须始终推导并传递地址，无论账户是否存在。
- **`share_rate` 在创建时上限为 `FEE_RATE_DENOMINATOR_VALUE`（`1_000_000`）**，在分割运行时再次上限。`1_000_000` 将整个创建者费用路由到协议；`0` 不路由任何费用。
- **由管理员或专用权限通过 `CreateCreatorFeeShare` / `CloseCreatorFeeShare` 创建和关闭**。关闭它会将租金返还给签名者，并将对回退到配置默认值；池创建者不是任何路径上的签名者。
- **它由创建者而不是池键入。** 一个账户管理该创建者在该 `AmmConfig` 上拥有的每个池。在两个费用等级上拥有池的创建者需要两个账户才能在两者上覆盖。

它驱动的分割算术在 [`products/cpmm/fees`](/zh/products/cpmm/fees#protocol-share-of-the-creator-fee)。

### 金库和 Token-2022

`vault0` 和 `vault1` 由 CPMM authority PDA 拥有，它们的代币程序所有者（`token_program`）是 SPL Token 或 Token-2022，由池创建时 mint 的程序确定。池透明地处理两种情况——你在 `Swap` / `Deposit` / `Withdraw` 指令账户中为每一侧传递正确的代币程序 ID。

CPMM 在池创建时强制执行严格的**扩展允许列表**（`utils/token.rs` 中的 `is_supported_mint`）。Token-2022 mint 只有在它携带的**每个**扩展都在此列表中时才能在 CPMM 池中使用：

- **`TransferFeeConfig`。** 由 mint 在每次转账时应用。对于 `SwapBaseInput` 存款，池在接收端；对于提款，在发送端。程序计算登陆金库的**净**金额并相应设置曲线。见 [`algorithms/token-2022-transfer-fees`](/zh/algorithms/token-2022-transfer-fees)。
- **`MetadataPointer`** 和 **`TokenMetadata`。** 标准链上 mint 元数据。对交换数学无影响。
- **`InterestBearingConfig`。** Mint 的 UI 金额累积利息。金库存储原始金额；曲线仅对原始金额操作。显示 APR 的 UI 应调用 Token-2022 助手来呈现 UI 金额。
- **`ScaledUiAmount`。** UI 显示缩放扩展。与 `InterestBearingConfig` 相同的处理——曲线使用原始金额。

任何其他扩展——`PermanentDelegate`、`TransferHook`、`DefaultAccountState`、`NonTransferable`、`ConfidentialTransfer`、`Group`/`GroupMember`、`MintCloseAuthority` 等——导致 `Initialize` 以 `NotSupportMint` 拒绝。一个例外是**每个 mint 注册表**：如果在种子 `[b"support_mint", mint]` 处存在 `SupportMintAssociated` PDA，无论其扩展集如何，mint 都被接纳。该 PDA 由管理员（或专用支持 mint 权限）通过 `CreateSupportMintAssociated` / `CloseSupportMintAssociated` 创建和移除，所以载入特定 mint 不再需要程序升级。

<Note>
  **2026-09 中更改。** CPMM 之前还携带硬编码的四地址 `MINT_WHITELIST`，它短路了扩展检查。该数组**已移除**；注册表 PDA 现在是唯一的绕过。任何依赖硬编码列表的 mint 在创建新池之前需要 `SupportMintAssociated` PDA——现有池不受影响，因为检查仅在池创建时运行。
</Note>

经过审查的扩展列表位于 CP-Swap 源代码中的 `programs/cp-swap/src/utils/token.rs`，可能随未来程序升级而更改。见 [`reference/token-2022-support`](/zh/reference/token-2022-support) 了解跨程序矩阵。

### 观察

观察账户是 `ObservationState` 条目的环形缓冲区，每个条目存储一个 `block_timestamp` 和一个**累积价格**。在每次交换时，如果自上次以来经过了足够的时间，程序会追加一个新观察。TWAP 通过读取两个观察并除以 `Δcumulative / Δtime` 来计算。

```rust
// OBSERVATION_NUM is hardcoded in the program to 100.
pub const OBSERVATION_NUM: usize = 100;

pub struct Observation {
    pub block_timestamp:              u64,
    pub cumulative_token_0_price_x32: u128,   // Q32.32, top 64 bits left for overflow
    pub cumulative_token_1_price_x32: u128,
}

pub struct ObservationState {
    pub initialized:           bool,
    pub observation_index:     u16,                            // circular index
    pub pool_id:               Pubkey,
    pub observations:          [Observation; OBSERVATION_NUM], // 100 entries
    pub last_update_timestamp: u64,                            // timestamp of the most recent append
    pub padding:               [u64; 3],
}
```

环形缓冲区的大小为**100 个观察**。每个观察是 40 字节（`8 + 16 + 16`），所以数组本身是 4,000 字节；`ObservationState::LEN` 恰好是**4,075 字节**（`8 + 1 + 2 + 32 + 4,000 + 8 × 4`）。

两个消费者规则：

- **不要将单个观察用作价格。** 它是*累积*，不是现货价格。使用其中两个来计算 TWAP。
- **选择至少相隔一个区块的观察。** 同一区块内的交换可能不会产生新观察；连续读取可能返回相同记录。

更多数学在 [`products/clmm/accounts`](/zh/products/clmm/accounts)。

## 账户生命周期

| 事件 | 创建的账户 | 销毁的账户 |
|-------|------------------|---------------------|
| `Initialize` | `poolState`、`lpMint`、`vault0`、`vault1`、`observation` | — |
| `Deposit` | —（可能创建用户 LP ATA） | — |
| `Withdraw` | — | — |
