大多数仅限管理员的指令（`CreateAmmConfig`、`UpdateAmmConfig`、`UpdatePoolStatus`、`CreateSupportMintAssociated`、`CreateOperationAccount`、`UpdateOperationAccount`、`CloseProtocolPosition`）由程序的硬编码 `admin` 公钥门控。`CreatePermissionPda` / `ClosePermissionPda` 接受 `admin` 公钥**或**专用的 `permission_pda_admin` 密钥。奖励流管理员指令（`TransferRewardOwner`、`CollectRemainingRewards`）由奖励资金提供者而非程序管理员门控。

V2 后缀表示"支持保管库/NFT 上的 Token-2022，需要位图扩展槽"。SDK 默认为新池选择 V2。

## `CreatePool`

**参数**

```
sqrt_price_x64: u128           // 初始价格
open_time:      u64            // 此时间之前拒绝交换
```

**账户（简化）**

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | 选定的费用等级。 |
| 3 | `pool_state` | W |   | 在此处 `init`。 |
| 4 | `token_mint_0` |   |   | 已排序。 |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | 在此处 `init`，由池权限 PDA 拥有。 |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | 在此处 `init`。 |
| 9 | `tick_array_bitmap_extension` | W |   | 在此处 `init`（V2）。 |
| 10 | `token_program` |   |   | |
| 11 | `token_program_2022` |   |   | |
| 12 | `system_program`、`rent` |   |   | |

**前置条件**

- `token_mint_0 < token_mint_1`（按字节顺序）。
- `amm_config.disable_create_pool == false`。
- 铸币未被 Token-2022 扩展允许列表拒绝。

**后置条件**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`，`tick_current = floor(log_{1.0001}(price))`。
- `pool_state.liquidity = 0`（尚无头寸）。
- `pool_state.fee_on = FromInput`（旧版默认）。
- `pool_state.dynamic_fee_info` 被清零（动态费用禁用）。

## `CreateCustomizablePool`

推荐用于新池。与 `CreatePool` 效果相同，加上每池费用收集模式和可选的动态费用选择加入。

**参数**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**账户（简化）** — 与 `CreatePool` 相同，加上当 `enable_dynamic_fee = true` 时：

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| N | `dynamic_fee_config` |   |   | 要快照的共享配置。必须已存在。 |

**前置条件** — 与 `CreatePool` 相同。如果 `enable_dynamic_fee = false`，`dynamic_fee_config` 被忽略。

**后置条件**

- `pool_state.fee_on` 设置为选定的 `CollectFeeOn` 变体。
- 如果启用了动态费用：`pool_state.dynamic_fee_info` 从提供的 `DynamicFeeConfig` 初始化（复制五个校准参数；状态字段清零）。
- 否则：`pool_state.dynamic_fee_info` 被清零（= 此池永远不会激活动态费用）。

`fee_on` 和动态费用启用位**仅**在池创建时设置。没有原地升级 — 通过旧版 `CreatePool` 创建的池无法追溯获得动态费用或单边费用。新部署应默认使用此指令。

## `CreatePermissionedPool`

`CreatePool` 和 `CreateCustomizablePool` 都从 `["pool", amm_config, token_mint_0, token_mint_1]` 派生池 PDA，因此每个 `(config, mint0, mint1)` 三元组恰好有**一个**规范池地址 — 在相同种子处的第二个 `init` 失败。`CreatePermissionedPool` 通过将客户端提供的 `seed_index: u16` 折叠到池 PDA 种子中来解除此限制，允许**同一交易对和费用等级的多个池** — 每个在其自己的地址处。因为任意池地址是特权能力，支付者必须持有授权它的 `Permission` PDA。

关于池的其他一切与 `CreateCustomizablePool` 相同：它采用相同的 `CreateCustomizableParams` 并支持单边费用和动态费用选择加入。

**参数**

```rust
customizable_params: CreateCustomizableParams   // 与 CreateCustomizablePool 相同的结构
seed_index:          u16                          // 必须非零；折叠到池 PDA 种子中
```

**账户（简化）** — 与 `CreateCustomizablePool` 相同，加上前面的：

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `payer` | W | S | 支付租金。必须是下面 `permission` PDA 的权限。 |
| 2 | `pool_creator` |   |   | 记录为 `pool_state.owner`。可能与 `payer` 不同。 |
| 3 | `permission` |   |   | PDA `["permission", payer]`。如果不存在/不由程序拥有，Anchor 拒绝调用。 |
| … | （`amm_config`、`pool_state`、铸币、保管库、`observation_state`、`tick_array_bitmap`、代币/系统程序） | | | 如 `CreateCustomizablePool` 中所示。 |

`pool_state` PDA 从 `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]` 派生。

**前置条件**

- `seed_index != 0`。`seed_index` 为 `0` 保留给旧版池并在此处被拒绝；`[0, 0]` 种子分量是使旧版池地址折叠到经典四种子形式的原因。
- `payer` 的 `permission` PDA 存在（由管理员通过 `CreatePermissionPda` 创建）。
- 与 `CreatePool` 相同的铸币/允许列表规则。

**后置条件**

- 新的 `pool_state` 存在于 `seed_index` 派生的地址处，`pool_state.seed_index = seed_index`。
- 所有其他后置状态与 `CreateCustomizablePool` 匹配（费用模式、可选动态费用）。

<Note>
  此指令**不**扩大一般池创建访问权限 — 无权限创建继续通过 `CreatePool` / `CreateCustomizablePool` 进行，这些仍然是每对一个池。`CreatePermissionedPool` 存在于白名单操作者需要同一交易对的多个池（例如不同的初始价格或启动队列）并持有由管理员授予的 `Permission` PDA 的特定情况。
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

在现有池内创建新头寸。

**参数**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // 期望的 L（或 0 以使用下面的金额）
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // 写入 NFT 元数据（Metaplex）
base_flag: Option<bool>       // true = 适配 amount0；false = 适配 amount1
```

**账户（简化）**

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `payer` | W | S |
| 2 | `position_nft_owner` |   |   |
| 3 | `position_nft_mint` | W | S（密钥对） |
| 4 | `position_nft_account` | W |   | 所有者的 NFT ATA。 |
| 5 | `metadata_account` | W |   | Metaplex（可选，如果 `with_metadata`）。 |
| 6 | `pool_state` | W |   |
| 7 | `protocol_position` |   |   |   |
| 8 | `tick_array_lower` | W |   | 如果未初始化则创建。 |
| 9 | `tick_array_upper` | W |   | 相同。 |
| 10 | `personal_position` | W |   | 在此处创建。 |
| 11 | `token_account_0`、`token_account_1` | W |   | 用户源 ATA。 |
| 12 | `token_vault_0`、`token_vault_1` | W |   | |
| 13 | `rent`、`system_program`、`token_program` |   |   | |
| 14 | `associated_token_program` |   |   | |
| 15 | `metadata_program` |   |   | 可选。 |
| 16 | `token_program_2022` |   |   | V2。 |
| 17 | `vault_0_mint`、`vault_1_mint` |   |   | V2。 |
| 18 | `tick_array_bitmap_extension` | W |   | V2（如果接触）。 |

**数学** — 见 [`products/clmm/math`](/zh/products/clmm/math)。给定 `base_flag`，程序将 `liquidity` 或 `(amount_0_max, amount_1_max)` 解析为实际的 `L` 和消耗的实际代币金额。

**前置条件**

- `tick_lower < tick_upper`，两者都是 `pool.tick_spacing` 的倍数，在 `[MIN_TICK, MAX_TICK]` 范围内。
- 所需的价位数组已通过并初始化（或通过交易中的 `InitTickArray` CPI 在此处创建）。
- 用户在源 ATA 中至少有 `amount_0_max` 和 `amount_1_max`。

**后置条件**

- `personal_position` 存在，`liquidity` 已设置，`fee_growth_inside_last` 已快照。
- 在 `tick_lower` 和 `tick_upper` 处的价位数组条目已更新（`liquidity_gross += L`，`liquidity_net ± L`，费用增长快照已维护）。
- 如果头寸在范围内（`tick_lower ≤ tick_current < tick_upper`），`pool_state.liquidity += L`。

**常见错误** — `InvalidTickIndex`、`NotApproved`、`ZeroAmountSpecified`、`TransactionTooLarge`（如果价位数组过多）。

## `IncreaseLiquidityV2`

向已开放的头寸添加流动性。

**参数**

```
liquidity: u128
amount_0_max: u64
amount_1_max: u64
base_flag: Option<bool>
```

**账户** — 如 `OpenPosition` 减去 NFT 铸币（头寸已存在；NFT 作为所有者的 ATA 持有 1 个代币传递）。

**效果**

- 从用户转移 `amount_0_actual` / `amount_1_actual` → 保管库。
- 增加 `personal_position.liquidity` 和 `pool_state.liquidity`（如果在范围内），以及端点价位的 `liquidity_gross` / `liquidity_net` 相应地。
- **收集自上次接触以来应付的费用和奖励**并将其记入 `tokens_fees_owed_{0,1}` / `reward_amount_owed`。这些仅在 `DecreaseLiquidity` 或 `CollectReward` 时支付，而不是在增加时。

## `DecreaseLiquidityV2`

从头寸移除流动性。

**参数**

```
liquidity: u128
amount_0_min: u64
amount_1_min: u64
```

**账户** — 与 `IncreaseLiquidity` 相同的形状。

**效果**

- 给定当前 `sqrt_price_x64`，计算移除的 `L` 的 `(amount_0, amount_1)`。
- 结算自上次接触以来累积的费用/奖励，与 `IncreaseLiquidity` 相同。
- 从保管库转移 `amount_0 + fees_owed_0` 和 `amount_1 + fees_owed_1` 到用户。
- 递减流动性计数器；如果新的 `personal_position.liquidity == 0`，头寸符合 `ClosePosition` 的条件。

**滑点** — `amount_0_min` 和 `amount_1_min` 是用户在输出端 Token-2022 转账费用净额后接受的最小值。

## `ClosePosition`

销毁头寸 NFT 并关闭 `PersonalPositionState`。

**前置条件**

- `personal_position.liquidity == 0`。
- `tokens_fees_owed_{0,1} == 0`。
- 所有奖励计数器 `reward_amount_owed == 0`。

（即，先收集所有内容并减少到零。）

**效果**

- 销毁 NFT。
- 关闭 NFT 铸币账户和 `personal_position` 账户，将租金退款给 `payer`。

## `SwapV2`

沿流动性曲线行走；精确输入*或*精确输出取决于 `is_base_input`。

**参数**

```
amount: u64                  // 如果 is_base_input=true 则为输入，否则为输出
other_amount_threshold: u64  // 最小输出或最大输入
sqrt_price_limit_x64: u128   // 硬限制；0 ⇒ 无限制
is_base_input: bool
```

**账户（简化）**

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2。 |
| 11 | `memo_program` |   |   | V2（某些 Token-2022 路径需要）。 |
| 12 | `input_vault_mint`、`output_vault_mint` |   |   | V2。 |
| 13 | `tick_array_bitmap_extension`（可选） | W |   | 如果交换进入扩展。 |
| 14+ | `tick_array`（剩余） | W |   | 足够的数组以跨越行走的预期范围。 |

调用者传递覆盖预期交换行走的排序价位数组列表；程序使用所需的数量。SDK 通过 `PoolUtils.computeAmountOutFormat` 或 API 的报价端点计算此列表。

**前置条件**

- `pool_state.status` 允许交换。
- `now >= open_time`。
- `sqrt_price_limit_x64` 在 `sqrt_price_x64` 的正确一侧用于该方向。

**常见错误** — `ExceededSlippage`、`SqrtPriceLimitOverflow`、`TickArrayNotFound`、`LiquidityInsufficient`。

**`SwapV2` 在内部执行的调用者应该知道的内容**（2025 年后发布）：

1. **动态费用附加费** — 如果 `pool.dynamic_fee_info` 非零，程序使用自上次交换以来遍历的价位距离更新波动率累加器（使用 [`products/clmm/fees`](/zh/products/clmm/fees) 中的过滤/衰减规则），并在 `AmmConfig.trade_fee_rate` 之上添加 `dynamic_fee_component`。总费用上限为 10%（`MAX_FEE_RATE_NUMERATOR / 1_000_000`）。
2. **限价单匹配** — 当价格行走穿过持有未平仓限价单的价位时，程序首先填充该价位处可用的限价单流动性（按 `order_phase` 的 FIFO），然后沿 LP 流动性曲线继续。已成交金额更新 `tick.unfilled_ratio_x64` 和 `tick.part_filled_orders_remaining` 以供后续结算；订单本身保持未花费状态，直到其所有者调用 `SettleLimitOrder`。
3. **单边费用路由** — 当 `pool.fee_on = Token0Only` 或 `Token1Only` 时，交换步骤仍计算相同的输入-输出交易；费用随后被路由到配置的一侧。对于配置的费用侧是输出的方向，费用从交换输出中扣除（用户收到 `out − fee`）；对于配置的费用侧是输入的方向，行为与 `FromInput` 匹配。见 `pool_state` 上的 `is_fee_on_input(zero_for_one)` 和 `is_fee_on_token0(zero_for_one)`。

`Swap`（V1）实现与 `SwapV2` 相同的动态费用、单边费用路由和限价单匹配；它缺少的唯一功能是 Token-2022 支持 — 两个保管库都必须是经典 SPL Token。任何 Token-2022 铸币的池必须通过 `SwapV2` 交换。聚合器和 SDK 已经为每个 CLMM 腿优先选择 V2，所以调用者不必根据铸币类型进行分支。

## `OpenLimitOrder`

在特定价位下单。订单坐在每价位 FIFO 队列中，并在价格穿过时填充。

**参数**

```
nonce_index:    u8       // 用户选择的 nonce 账户索引（每个钱包 0..255）
zero_for_one:   bool     // true：出售 token0 换 token1；false：出售 token1 换 token0
tick_index:     i32      // 必须是 pool.tick_spacing 的倍数
amount:         u64      // 输入代币金额
```

**账户（简化）**

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `payer` | W | S | 订单所有者；支付租金。 |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | 包含 `tick_index` 的价位数组。 |
| 4 | `limit_order_nonce` | W |   | PDA。`init_if_needed` — 在用户在此 `nonce_index` 下的第一个订单时创建。 |
| 5 | `limit_order` | W |   | PDA。在此处 `init`。 |
| 6 | `input_token_account` | W |   | 用户的输入 ATA。检查 `frozen`。 |
| 7 | `output_token_account` | W |   | 用户的**输出** ATA。在开放时不扣除 — 仅需要以便程序可以确认它不是 `frozen`（即填充可以稍后交付）。 |
| 8 | `input_vault` | W |   | 池输入保管库。 |
| 9 | `output_vault` | W |   | 池输出保管库。标识输出铸币以进行 `output_token_account` / `output_vault_mint` 检查。 |
| 10 | `input_vault_mint` |   |   | Token-2022 费用处理。 |
| 11 | `output_vault_mint` |   |   | 输出侧的铸币（冻结检查配对）。 |
| 12 | `input_token_program` |   |   | SPL 或 Token-2022。 |
| 13 | `system_program`、`rent` |   |   | |

<Note>
  **账户列表变化（2026-07 发布）。** `OpenLimitOrder` 现在也采用**输出侧**账户 — `output_token_account`、`output_vault` 和 `output_vault_mint` — 除了输入侧。它们仅用于验证：如果所有者的输入**或**输出代币账户被冻结，程序拒绝订单。这保证了填充实际上可以结算到所有者的输出 ATA，这对于允许列表/默认冻结 Token-2022 铸币（例如许可代币）很重要，其中账户可能尚未解冻。针对较旧单边账户列表构建的客户端必须添加三个输出账户。
</Note>

**前置条件**

- `input_token_account` 和 `output_token_account` 都未冻结（否则 `NotApproved`）。
- `pool_state.status` 允许交换（位 4）和限价单（位 5）操作（否则 `NotApproved`）。
- `tick_index % pool.tick_spacing == 0` 且在 `[MIN_TICK, MAX_TICK]` 范围内。
- `tick_index` 在所选方向的 **`pool.tick_current` 的正确一侧**（出售 token0 → 价位必须在当前之上，反之亦然）。在已穿过的价位处出售会立即匹配并被拒绝。

**后置条件**

- `limit_order` 存在，快照开放时的 `tick.order_phase` 和 `tick.unfilled_ratio_x64`。
- `tick.orders_amount += amount`（在当前队列中）。
- `limit_order_nonce.order_nonce += 1`。
- 发出 `OpenLimitOrderEvent`。

**常见错误** — `NotApproved`（输入或输出代币账户冻结，或池禁用了交换/限价单）、`InvalidLimitOrderAmount`（零或低于池的最小值）、`InvalidTickIndex`（超出 `[MIN_TICK, MAX_TICK]`，或在所选方向的 `tick_current` 的错误一侧）、`TickAndSpacingNotMatch`（`tick_index % pool.tick_spacing != 0`）、`OrderPhaseSaturated`。

## `IncreaseLimitOrder`

添加到现有的未平仓订单。仅可由订单的 `owner` 调用。

**参数**

```
amount: u64    // 额外的输入代币金额
```

**账户** — 如 `OpenLimitOrder` 减去 nonce 账户；`limit_order` PDA 直接传递。

**前置条件**

- `limit_order.owner == signer`。
- 订单仍在同一队列中（`tick.order_phase == limit_order.order_phase`）。如果队列已开始填充，订单已部分结算 — 调用者应首先调用 `DecreaseLimitOrder` 或 `SettleLimitOrder` 以向前推进。

**效果**

- 从所有者 ATA 转移 `amount` 到 `input_vault`。
- `limit_order.total_amount += amount`；`tick.orders_amount += amount`。

## `DecreaseLimitOrder`

减少或完全取消未平仓订单。将未成交的剩余部分支付回所有者，加上过去部分成交已结算的任何输出。

**参数**

```
amount:     u64    // 要提取的输入代币金额（最大 = 未成交剩余）
amount_min: u64    // 输入侧提取的滑点下限
```

**账户** — 输入和输出代币两侧：

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_vault_mint`、`output_vault_mint` |   |   |
| 10 | `token_program`、`token_program_2022` |   |   |

**效果**

- 从开放以来的队列 `unfilled_ratio_x64` 重新计算订单的已成交金额。
- 将已成交输出发送到 `output_token_account`。
- 将 `amount` 的未成交输入发送回 `input_token_account`。
- 相应地更新 `limit_order`。如果新的未成交剩余为零，程序关闭账户并将租金退款给 `owner`。

## `SettleLimitOrder`

将已成交的输出代币推送给所有者，而不改变订单的未成交剩余。当 `auto_withdraw` 保管人想要逐步支付长期运行的部分成交时很有用。

**调用者** — 订单的 `owner`，或程序的 `limit_order_admin`（运行自动保管人循环的离线操作热钱包）。保管人没有其他权限 — 它不能将用户资金移出已成交输出推送给订单的 `owner` ATA 之外。

**账户**

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `signer` |   | S | 所有者*或* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | 所有者的输出 ATA。 |
| 6 | `output_vault` | W |   | 池输出保管库。 |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**效果**

- 使用 `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)` 计算累积应付输出。
- 将增量转移到 `output_token_account`。
- 更新 `limit_order.settled_output`。
- **不**关闭订单；它仍对任何剩余输入开放。

## `CloseLimitOrder`

关闭完全消耗的订单账户。租金始终返回给 `limit_order.owner`，无论谁签署。

**调用者** — `owner` 或 `limit_order_admin`。

**前置条件**

- 订单有零未成交剩余（要么 `amount == total_amount` 已成交并结算，要么所有者之前将订单减少到零并忘记关闭）。

**效果**

- 关闭 `limit_order`；租金发送给 `limit_order.owner`。

## `CreateDynamicFeeConfig`（管理员）

在 u16 索引下创建可重用的参数集。

**参数**

```
index:                       u16
filter_period:               u16   // 秒；例如 30
decay_period:                u16   // 秒；例如 600。必须 > filter_period
reduction_factor:            u16   // 1..10_000；例如 5_000 = 每个衰减窗口 50% 保留
dynamic_fee_control:         u32   // 1..100_000；波动率到费用曲线的增益
max_volatility_accumulator:  u32   // 上限
```

**账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `owner` | W | S | 硬编码管理员公钥。 |
| 2 | `dynamic_fee_config` | W |   | PDA，在此处 `init`。 |
| 3 | `system_program` |   |   | |

**常见错误** — 如果 `decay_period <= filter_period` 或任何 0 值字段超出范围，则 `InvalidDynamicFeeConfigParams`。

## `UpdateDynamicFeeConfig`（管理员）

修改现有的 `DynamicFeeConfig`。已在创建时快照配置的池**不**被追溯更新；仅引用此配置的新创建池将获取新值。

**参数** — 与 `CreateDynamicFeeConfig` 相同的五个校准字段（`filter_period`、`decay_period`、`reduction_factor`、`dynamic_fee_control`、`max_volatility_accumulator`）；`index` 在创建时固定，此处不重新传递。

## `CollectProtocolFee` / `CollectFundFee`

与 CPMM 的 `CollectProtocolFee` / `CollectFundFee` 形状相同。签署者必须与 `AmmConfig.owner` / `AmmConfig.fund_owner` 匹配。从池的保管库清理累积的协议/基金费用到收件人，将相应的 `PoolState.protocol_fees_*` / `fund_fees_*` 字段清零。

## `InitializeReward`

向池添加新的奖励流。最多 3 个流可同时活跃。

**参数**

```
open_time:     u64
end_time:      u64
emissions_per_second_x64: u128   // Q64.64
```

**账户**

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `reward_funder` | W | S |
| 2 | `funder_token_account` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `operation_state` |   |   | CLMM 操作状态 PDA 门控奖励创建。 |
| 6 | `reward_token_mint` |   |   |
| 7 | `reward_token_vault` | W |   | 在此处 `init`。 |
| 8 | `reward_token_program` |   |   |
| 9 | `system_program`、`rent` |   |   |

**前置条件**

- 池上当前活跃的流少于 3 个。
- 资金提供者存入 `total_emission = emissions_per_second × (end_time − open_time)` 价值的奖励代币到保管库作为此指令的一部分。
- 按 `operation_state` 白名单的奖励铸币。

## `SetRewardParams`

扩展、充值或更改现有奖励流的发放速率。通常由池创建者或 Raydium 多签调用。约束在链上：你通常可以扩展 `end_time` 或增加发放，而不是追溯缩小它们。检查 `operation_state` 的所有者列表。

## `UpdateRewardInfos`

纯粹的簿记 — 通过将 `emissions_per_second × Δt / liquidity` 相乘将 `reward_growth_global_x64` 结算到当前时间。由每个接触流动性的指令在内部调用。作为独立指令公开，因为外部参与者（UI、cranks）有时想触发它。

## `CollectReward`

头寸所有者声称应付的奖励代币。

**账户**

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `nft_owner` |   | S |
| 2 | `nft_account` |   |   | 所有者的 ATA 持有头寸 NFT。 |
| 3 | `personal_position` | W |   |
| 4 | `pool_state` | W |   |
| 5 | `protocol_position` |   |   |   |
| 6 | `reward_token_vault` | W |   |
| 7 | `recipient_token_account` | W |   |
| 8 | `token_program` |   |   |
| 9 | `token_program_2022` |   |   |

**效果**

- 结算奖励增长（与费用相同的模式）。
- 将应付金额转移到收件人 ATA，将 `reward_amount_owed[i]` 清零。
