| 头寸 | `DecreaseLiquidity` / `DecreaseLiquidityV2` | 移除流动性；收取应付费用。 |
| 头寸 | `ClosePosition` | 销毁 NFT 并关闭 `PersonalPositionState`。如果 NFT 账户被冻结，首先使用作为剩余账户提供的池 PDA 解冻。 |
| 头寸 | `CloseProtocolPosition` | 管理员专用的旧版 `ProtocolPositionState` PDA 清理。当前程序不再创建或读取 `ProtocolPositionState` — 此指令仅用于回收由较旧程序版本创建的账户的租金。 |

| 费用 | `CollectFundFee` | 管理员基金费用清理。 |

| 奖励 | `TransferRewardOwner` | 转移可以设置或充值奖励流的权限。 |
| 奖励 | `CollectRemainingRewards` | 在奖励流的 `end_time` 之后，将任何未分配的代币清理回资金提供者。 |

| 管理员 | `CollectExcessLamports` | 从一个池的 `PoolState` 和保管库中清理超过租金豁免最低限额的 lamports，加上任何作为剩余账户传入的 CLMM 拥有的 PDA。`admin` 或专用的清理 lamports 钱包。2026-09 添加。 |

<Note>
  **没有初始化 tick 数组指令，也不需要。** Tick 数组在 `OpenPosition*` / `IncreaseLiquidity*` 内部由 `TickArrayState::get_or_create_tick_array` 创建，由 `payer` 支付。将（可能仍未初始化的、系统拥有的）tick 数组 PDA 作为 `tick_array_lower` / `tick_array_upper` 传入，程序在缺失时分配它。`OpenLimitOrder` 对其单个 `tick_array` 执行相同操作。
</Note>

大多数管理员专用指令（`CreateAmmConfig`、`UpdateAmmConfig`、`UpdatePoolStatus`、`CreateOperationAccount`、`UpdateOperationAccount`、`CloseProtocolPosition`）由程序的硬编码 `admin` 公钥门控。`CreateSupportMintAssociated` / `CloseSupportMintAssociated` 接受 `admin` 公钥**或**专用的支持铸币所有者密钥；`CollectExcessLamports` 接受 `admin` 公钥**或**专用的清理 lamports 钱包。奖励流管理员指令（`TransferRewardOwner`、`CollectRemainingRewards`）由奖励资金提供者门控，而非程序管理员。

V2 后缀表示"在保管库/NFT 上支持 Token-2022，需要位图扩展槽"。SDK 默认为新池选择 V2。

## `CreatePool`

**参数**

```
sqrt_price_x64: u128           // 初始价格
open_time:      u64            // 此时间前拒绝交换
```

**账户（简化）**

| # | 名称 | W | S | 说明 |
|---|------|---|---|------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | 选定的费用等级。 |
| 3 | `pool_state` | W |   | 在此处 `init`。 |
| 4 | `token_mint_0` |   |   | 已排序。 |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | 在此处 `init`，由池权限 PDA 拥有。 |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | 在此处 `init`。 |
| 9 | `tick_array_bitmap` | W |   | `TickArrayBitmapExtension` PDA；在此处 `init`。 |
| 10 | `token_program_0` |   |   | 拥有 `token_mint_0` 的程序 — SPL Token **或** Token-2022。 |
| 11 | `token_program_1` |   |   | 拥有 `token_mint_1` 的程序。 |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  槽 10 和 11 是**按铸币**的，不是"SPL Token 然后 Token-2022"。每个都受匹配铸币上的 `mint::token_program` 约束，因此对于 `token_mint_0` 是 Token-2022 且 `token_mint_1` 是经典 SPL 的池，你必须在槽 10 中传入 Token-2022，在槽 11 中传入 SPL Token。`CreateCustomizablePool` 和 `CreateCustomizablePoolV2` 使用相同的两个槽。
</Warning>

**前置条件**

- `token_mint_0 < token_mint_1`（按字节顺序）。
- `amm_config.disable_create_pool == false`。
- 铸币不被 Token-2022 扩展允许列表拒绝。

**后置条件**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`，`tick_current = floor(log_{1.0001}(price))`。
- `pool_state.liquidity = 0`（尚无头寸）。
- `pool_state.fee_on = FromInput`（旧版默认）。
- `pool_state.dynamic_fee_info` 被清零（动态费用禁用）。

## `CreateCustomizablePool`

推荐用于新池。与 `CreatePool` 效果相同，加上按池费用收集模式和可选的动态费用选择加入。

**参数**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**账户** — 恰好是 `CreatePool` 的 13 个声明账户。`dynamic_fee_config` **不是**声明账户。

<Warning>
  当 `enable_dynamic_fee = true` 时，要快照的 `DynamicFeeConfig` 必须作为**最后一个** `remaining_account` 提供 — 处理程序读取 `ctx.remaining_accounts.last()`。任何 `SupportMintAssociated` 绕过 PDA 必须因此在其**之前**，否则程序快照错误的账户并在反序列化时失败。在设置标志的同时省略它会导致 `AccountLack` 失败。
</Warning>

**前置条件** — 与 `CreatePool` 相同。如果 `enable_dynamic_fee = false`，不需要 `remaining_account`，任何传入的都仅被扫描以查找支持铸币记录。

**后置条件**

- `pool_state.fee_on` 设置为选定的 `CollectFeeOn` 变体。
- 如果启用了动态费用：`pool_state.dynamic_fee_info` 从提供的 `DynamicFeeConfig` 初始化（复制五个校准参数；状态字段清零）。
- 否则：`pool_state.dynamic_fee_info` 被清零（= 此池永远不活跃动态费用）。

`fee_on` 和动态费用启用位**仅**在池创建时设置。没有原地升级 — 通过旧版 `CreatePool` 创建的池无法追溯获得动态费用或单边费用。新部署应默认使用此指令。

## `CreateCustomizablePoolV2`

`CreatePool` 和 `CreateCustomizablePool` 都从 `["pool", amm_config, token_mint_0, token_mint_1]` 派生池 PDA，因此每个 `(config, mint0, mint1)` 三元组恰好对应**一个**规范池地址——在相同种子处的第二次 `init` 会失败。`CreateCustomizablePoolV2` 通过将客户端提供的 `seed_index: u16` 折叠到池 PDA 种子中来解除这一限制，允许**同一交易对和费率层级下存在多个池**——每个池都有自己的地址。任何人都可以调用它。

池的其他所有方面都与 `CreateCustomizablePool` 相同：它采用相同的 `CreateCustomizableParams` 并支持单边费用和动态费用选择加入。

<Note>
  在 [2026-10-22 升级](/zh/reference/changelog/2026-10-22-clmm-customizable-pool-v2) 之前，该指令被称为 `CreatePermissionedPool`，需要支付者持有管理员颁发的 `Permission` PDA。升级后重命名了该指令，移除了 `permission` 账户并删除了权限机制。由于名称改变，判别器也随之改变，针对 `CreatePermissionedPool` 构建的客户端必须重新构建。
</Note>

**参数**

```rust
customizable_params: CreateCustomizableParams   // 与 CreateCustomizablePool 相同的结构体
seed_index:          u16                          // 必须非零；折叠到池 PDA 种子中
```

**账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | 为每个新账户支付租金。任何钱包。 |
| 2 | `pool_creator` |   |   | 记录为 `pool_state.owner`。可能与 `payer` 不同。不是签名者且不被检查。 |
| 3 | `amm_config` |   |   | 池绑定的费率层级。 |
| 4 | `pool_state` | W |   | 在 `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]` 处 `init`。 |
| 5 | `token_mint_0` |   |   | 必须排序在 `token_mint_1` 之前。 |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`。 |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`。 |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`。 |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`。 |
| 11 | `token_program_0` |   |   | 拥有 `token_mint_0` 的程序。 |
| 12 | `token_program_1` |   |   | 拥有 `token_mint_1` 的程序。 |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts`：当 Token-2022 mint 需要时的支持 mint 注册表 PDA，以及当 `enable_dynamic_fee = true` 时**最后**的 `DynamicFeeConfig`——与 `CreateCustomizablePool` 相同。

**前置条件**

- `seed_index != 0`。`seed_index` 为 `0` 保留给旧版池，此处会被拒绝；`[0, 0]` 种子分量是使旧版池地址折叠为经典四种子形式的原因。
- 派生地址处不存在池。
- 与 `CreatePool` 相同的 mint/允许列表规则。

**后置条件**

- 新的 `pool_state` 存在于 `seed_index` 派生的地址处，其中 `pool_state.seed_index = seed_index`。
- 所有其他后状态与 `CreateCustomizablePool` 匹配（费用模式、可选动态费用）。

<Warning>
  由于 `pool_creator` 未被检查，任何支付者都可以将任何地址写入 `pool_state.owner`。该地址可以在池上调用 `InitializeReward`，但这不能证明谁创建了池。集成商不应根据 V2 池的 `owner` 标记或排名。
</Warning>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

在现有池内创建新头寸。

**参数**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // 期望的 L（或 0 以使用下面的金额）
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // 写入 NFT 元数据（Metaplex）
base_flag: Option<bool>       // true = 适配 amount0；false = 适配 amount1
```

**账户**——两个变体有**不同的**账户列表。`OpenPositionV2` 声明 22 个；`OpenPositionWithToken22Nft` 声明 20 个。

`OpenPositionV2`，按顺序：

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | |
| 2 | `position_nft_owner` |   |   | |
| 3 | `position_nft_mint` | W | S | 新密钥对。 |
| 4 | `position_nft_account` | W |   | 所有者的 NFT ATA。 |
| 5 | `metadata_account` | W |   | Metaplex 元数据 PDA。**无条件**声明，即使 `with_metadata = false`。 |
| 6 | `pool_state` | W |   | |
| 7 | `protocol_position` |   |   | 遗留的；只读 `UncheckedAccount`。 |
| 8 | `tick_array_lower` | W |   | 如果未初始化则在此创建。 |
| 9 | `tick_array_upper` | W |   | 相同。 |
| 10 | `personal_position` | W |   | 在此创建。 |
| 11 | `token_account_0` | W |   | 用户源 ATA。 |
| 12 | `token_account_1` | W |   | |
| 13 | `token_vault_0` | W |   | |
| 14 | `token_vault_1` | W |   | |
| 15 | `rent` |   |   | |
| 16 | `system_program` |   |   | |
| 17 | `token_program` |   |   | |
| 18 | `associated_token_program` |   |   | |
| 19 | `metadata_program` |   |   | Metaplex Token Metadata。 |
| 20 | `token_program_2022` |   |   | |
| 21 | `vault_0_mint` |   |   | |
| 22 | `vault_1_mint` |   |   | |

`OpenPositionWithToken22Nft` 是相同的列表，但**移除了** `metadata_account`（5）和 `metadata_program`（19）——它通过 NFT mint 上的 Token-2022 元数据扩展来写入头寸的元数据——共 20 个账户。其 `position_nft_mint` 是裸 `Signer`，`position_nft_account` 是 `UncheckedAccount`。

<Warning>
  **`tick_array_bitmap_extension` 不是任一变体上的声明账户。** 当头寸的范围超出池的内联 `tick_array_bitmap`（±512 tick 数组）时，在 `remaining_accounts[0]` 处追加种子为 `["pool_tick_array_bitmap_extension", pool_state]` 的 `TickArrayBitmapExtension` PDA。
</Warning>

**数学**——见 [`products/clmm/math`](/zh/products/clmm/math)。给定 `base_flag`，程序将 `liquidity` 或 `(amount_0_max, amount_1_max)` 解析为实际的 `L` 和消耗的实际代币金额。

**前置条件**

- `tick_lower < tick_upper`，都是 `pool.tick_spacing` 的倍数，在 `[MIN_TICK, MAX_TICK]` 范围内。
- 传递两个 tick 数组 PDA。它们**不需要**已存在——`get_or_create_tick_array` 在此指令内以 `payer` 的费用分配缺失的。没有单独的初始化 tick 数组指令。
- 用户在源 ATA 中至少有 `amount_0_max` 和 `amount_1_max`。

**后置条件**

- `personal_position` 存在，`liquidity` 已设置，`fee_growth_inside_last` 已快照。
- `tick_lower` 和 `tick_upper` 处的 tick 数组条目已更新（`liquidity_gross += L`，`liquidity_net ± L`，费用增长快照已维护）。
- 如果头寸在范围内（`tick_lower ≤ tick_current < tick_upper`），则 `pool_state.liquidity += L`。
- 头寸 NFT mint 记录 `pool_state` 作为冻结权限。在单个 NFT 被铸造后，mint 权限被移除。记录冻结权限不会改变 NFT 代币账户的状态。
- NFT 代币账户保持未冻结，除非指令是 `OpenPositionV2` 或 `OpenPositionWithToken22Nft` **且**任一保管库 mint 的冻结权限与 CLMM 的受限发行者列表匹配。只有匹配的 V2 路径冻结账户。`OpenPosition` V1 不冻结。

**常见错误**——`TickInvalidOrder`（`tick_lower >= tick_upper`）、`TickAndSpacingNotMatch`（端点不是 `tick_spacing` 的倍数）、`InvalidTickIndex`（超出 `[MIN_TICK, MAX_TICK]`）、`MissingTickArrayBitmapExtensionAccount`（范围超出内联位图且未追加扩展）、`NotApproved`（`pool_state.status` 阻止打开）、`ZeroAmountSpecified`。

<Note>
  头寸冻结不添加声明的指令账户或参数。客户端可以使用现有的 V2 布局打开这些头寸。行为在链上从 `vault_0_mint` 和 `vault_1_mint` 选择。
</Note>

## `IncreaseLiquidityV2`

向已打开的头寸添加流动性。

**参数**

```
liquidity: u128
amount_0_max: u64
amount_1_max: u64
base_flag: Option<bool>
```

**账户**——15 个，**不**可从 `OpenPosition` 派生：没有 `rent`、没有 `system_program`、没有 `associated_token_program` 和没有元数据账户。

| # | 名称 | W | S |
|---|------|---|---|
| 1 | `nft_owner` |   | S |
| 2 | `nft_account` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `protocol_position` |   |   |
| 5 | `personal_position` | W |   |
| 6 | `tick_array_lower` | W |   |
| 7 | `tick_array_upper` | W |   |
| 8 | `token_account_0` | W |   |
| 9 | `token_account_1` | W |   |
| 10 | `token_vault_0` | W |   |
| 11 | `token_vault_1` | W |   |
| 12 | `token_program` |   |   |
| 13 | `token_program_2022` |   |   |
| 14 | `vault_0_mint` |   |   |
| 15 | `vault_1_mint` |   |   |

当头寸的范围超出内联位图时，在 `remaining_accounts[0]` 处前置 `TickArrayBitmapExtension` PDA。

**效果**

- 从用户转账 `amount_0_actual` / `amount_1_actual` 到保管库。
- 增加 `personal_position.liquidity` 和 `pool_state.liquidity`（如果在范围内），并相应地增加端点 tick 的 `liquidity_gross` / `liquidity_net`。
- **收集自上次触及以来应得的费用和奖励**，并将其记入 `token_fees_owed_{0,1}` / `reward_amount_owed`。这些仅在 `DecreaseLiquidity` / `DecreaseLiquidityV2` 时支付，不在增加时支付——没有独立的收集指令。

## `ClosePosition`

销毁头寸 NFT 并关闭 `PersonalPositionState`。

**声明的账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `nft_owner` | W | S | 必须拥有持有数量为 `1` 的 NFT 代币账户。 |
| 2 | `position_nft_mint` | W |   | 必须匹配 `personal_position.nft_mint`。 |
| 3 | `position_nft_account` | W |   | NFT 所有者的账户；可以是经典 SPL Token 或 Token-2022。 |
| 4 | `personal_position` | W |   | 关闭至 `nft_owner`。 |
| 5 | `system_program` |   |   | 关闭头寸状态。 |
| 6 | `token_program` |   |   | 必须拥有 NFT 铸币和代币账户。 |

**剩余账户**

- 未冻结 NFT：无需任何账户；额外的池账户无害，因为处理程序不会读取它。
- 冻结 NFT：将 `personal_position.pool_id` 作为第一个剩余账户追加。程序将其加载为 `PoolState` 并使用其 PDA 种子来签署解冻。

**前置条件**

- `personal_position.liquidity == 0`。
- `tokens_fees_owed_{0,1} == 0`。
- 所有奖励计数器 `reward_amount_owed == 0`。

（即，先收集所有内容并减少到零。）

**效果**

- 如果 NFT 代币账户被冻结，验证第一个剩余账户等于 `personal_position.pool_id`，然后使用池 PDA 解冻它。
- 销毁 NFT。
- 关闭 NFT 代币账户和 `personal_position`，将租金退款给 `nft_owner`。如果头寸 NFT 使用 Token-2022，它也会关闭 NFT 铸币；经典 SPL Token 铸币无法关闭，供应量保持为零。

**条件客户端兼容性** — 声明的 IDL 布局未改变，因此旧版客户端继续关闭现有的和未冻结的头寸。省略池剩余账户的旧版构建器在关闭冻结头寸时会因 `AccountLack` 失败。为每次关闭都传递池是最简单的兼容策略。

**账户（简化版）**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2。 |
| 11 | `memo_program` |   |   | V2（某些 Token-2022 路径需要）。 |
| 12 | `input_vault_mint`、`output_vault_mint` |   |   | V2。 |
| 13 | `tick_array_bitmap_extension`（可选） | W |   | 如果交换进入扩展。 |
| 14+ | `tick_array`（剩余） | W |   | 足够的数组来跨越行走的预期范围。 |

调用者传递覆盖预期交换行走的排序 tick 数组列表；程序根据需要使用尽可能多的数组。SDK 通过 `PoolUtils.computeAmountOutFormat` 或 API 的报价端点计算此列表。

**前置条件**

- `pool_state.status` 允许交换。
- `now >= open_time`。
- `sqrt_price_limit_x64` 在 `sqrt_price_x64` 的正确一侧用于该方向。

**常见错误** — `TooLittleOutputReceived`（精确输入滑点）、`TooMuchInputPaid`（精确输出滑点）、`SqrtPriceLimitOverflow`、`NotEnoughTickArrayAccount`、`InvalidFirstTickArrayAccount`、`MissingTickArrayBitmapExtensionAccount`、`LiquidityInsufficient`、`NotApproved`（在 `pool_state.status` 上设置了交换位）。CLMM 没有 `ExceededSlippage` 变体 — 那是 CPMM 的 — 也没有 `TickArrayNotFound`。

**`SwapV2` 内部执行的操作，调用者应该了解**（2025 年后发布）：

1. **动态费用附加费** — 如果 `pool.dynamic_fee_info` 非零，程序使用自上次交换以来遍历的 tick 距离更新波动率累加器（使用来自 [`products/clmm/fees`](/zh/products/clmm/fees) 的过滤/衰减规则），并在 `AmmConfig.trade_fee_rate` 之上添加 `dynamic_fee_component`。总费用上限为 10%（`MAX_FEE_RATE_NUMERATOR / 1_000_000`）。
2. **限价单匹配** — 当价格行走穿过持有开放限价单的 tick 时，程序首先在该 tick 处填充可用的限价单流动性（按 `order_phase` 的 FIFO），然后沿 LP 流动性曲线继续。填充的数量更新 `tick.unfilled_ratio_x64` 和 `tick.part_filled_orders_remaining` 以供后续结算；订单本身保持未花费状态，直到其所有者调用 `SettleLimitOrder`。
3. **单边费用路由** — 当 `pool.fee_on = Token0Only` 或 `Token1Only` 时，交换步骤仍然计算相同的输入-输出交易；费用随后被路由到配置的一侧。对于配置费用侧是输出的方向，费用从交换输出中扣除（用户收到 `out − fee`）；对于配置费用侧是输入的方向，行为与 `FromInput` 匹配。参见 `PoolState` 上的 `is_fee_on_input(zero_for_one)` 和 `is_fee_on_token0(zero_for_one)`。

`Swap`（V1）实现与 `SwapV2` 相同的动态费用、单边费用路由和限价单匹配；它缺少的唯一功能是 Token-2022 支持 — 两个金库都必须是经典 SPL Token。任何具有 Token-2022 铸币的池必须通过 `SwapV2` 进行交换。聚合器和 SDK 已经为每个 CLMM 腿优先选择 V2，因此调用者不必根据铸币类型进行分支。

## `OpenLimitOrder`

在特定 tick 处下达卖单。订单位于每个 tick 的 FIFO 队列中，并在价格经过时填充。

**参数**

```
nonce_index:    u8       // 用户选择的 nonce 账户索引（每个钱包 0..255）
zero_for_one:   bool     // true：用 token0 换 token1；false：用 token1 换 token0
tick_index:     i32      // 必须是 pool.tick_spacing 的倍数
amount:         u64      // 输入代币数量
```

**账户（简化版）**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | 订单所有者；支付租金。 |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | 包含 `tick_index` 的 tick 数组。 |
| 4 | `limit_order_nonce` | W |   | PDA。`init_if_needed` — 在用户在此 `nonce_index` 下的第一个订单时创建。 |
| 5 | `limit_order` | W |   | PDA。在此处 `init`。 |
| 6 | `input_token_account` | W |   | 用户的输入 ATA。检查是否 `frozen`。 |
| 7 | `output_token_account` | W |   | 用户的**输出** ATA。打开时不扣款 — 仅需要以便程序可以确认它不是 `frozen`（即填充稍后可以交付）。 |
| 8 | `input_vault` | W |   | 池输入金库。 |
| 9 | `output_vault` | W |   | 池输出金库。标识输出铸币以进行 `output_token_account` / `output_vault_mint` 检查。 |
| 10 | `input_vault_mint` |   |   | Token-2022 费用处理。 |
| 11 | `output_vault_mint` |   |   | 输出侧的铸币（冻结检查配对）。 |
| 12 | `input_token_program` |   |   | SPL 或 Token-2022。 |
| 13 | `system_program` |   |   | 为 `limit_order`、`limit_order_nonce` 和（如需要）`tick_array` 分配提供资金。 |

**剩余账户** — `[0]` `tick_array_bitmap_extension`，仅当初始化起始索引落在池内联位图之外的 tick 数组时需要。否则不传递任何内容。

<Warning>
  **没有 `rent` 账户**：结构体在 `system_program` 处结束，13 个声明的账户。位置 14 处的杂散 `rent` 恰好落在可选位图扩展被读取的位置，因此订单看起来可以工作，直到第一次必须创建内联位图之外的 tick 数组 — 然后失败。
</Warning>

<Note>
  **账户列表变更（2026-07 发布）。** `OpenLimitOrder` 现在还接受**输出侧**账户 — `output_token_account`、`output_vault` 和 `output_vault_mint` — 除了输入侧。它们仅用于验证：如果所有者的输入**或**输出代币账户被冻结，程序会拒绝订单。这保证了填充实际上可以结算到所有者的输出 ATA，这对于允许列表/默认冻结 Token-2022 铸币（例如许可代币）很重要，其中账户可能尚未解冻。针对旧版单侧账户列表构建的客户端必须添加三个输出账户。
</Note>

**前置条件**

- `input_token_account` 和 `output_token_account` 都未被冻结（否则 `NotApproved`）。
- `pool_state.status` 允许交换（位 4）和限价单（位 5）操作（否则 `NotApproved`）。
- `tick_index % pool.tick_spacing == 0` 且在 `[MIN_TICK, MAX_TICK]` 范围内。
- `tick_index` 在所选方向的 **`pool.tick_current` 的右侧**（卖出 token0 → tick 必须在当前之上，反之亦然）。在已经穿过的 tick 处卖出会立即匹配并被拒绝。

**后置条件**

- `limit_order` 存在，在打开时快照 `tick.order_phase` 和 `tick.unfilled_ratio_x64`。
- `tick.orders_amount += amount`（在当前队列中）。
- `limit_order_nonce.order_nonce += 1`。
- 发出 `OpenLimitOrderEvent`。

**常见错误** — `NotApproved`（输入或输出代币账户冻结，或池禁用了交换/限价单）、`ZeroAmountSpecified`（输入侧转账费用后 `amount == 0`）、`InvalidLimitOrderAmount`（数量会在该 tick 处产生低于 1 个基本单位的输出，或溢出 `u64`）、`InvalidTickIndex`（超出 `[MIN_TICK, MAX_TICK]`，或在所选方向的 `tick_current` 错误一侧）、`TickAndSpacingNotMatch`（`tick_index % pool.tick_spacing != 0`）、`OrderPhaseSaturated`。

将已填充的输出代币推送给订单所有者，不改变订单的未填充部分。当 `auto_withdraw` 守护进程想要分批支付长期运行的部分填充时很有用。

**账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `signer` |   | S | owner *或* `limit_order_admin` |

| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | 所有者的输出 ATA。 |
| 6 | `output_vault` | W |   | 池的输出金库。 |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**效果**

- 更新 `limit_order.settled_output`。
- **不**关闭订单；它对任何剩余输入仍然开放。

## `CloseLimitOrder`

关闭已完全消耗的订单账户。无论谁签名，租金始终返回给 `limit_order.owner`。

**调用者** — `owner` 或 `limit_order_admin`。

**前置条件**

- 订单的未填充余额为零（要么 `amount == total_amount` 已填充并结算，要么所有者之前将订单减少到零并忘记关闭）。

**效果**

- 关闭 `limit_order`；租金发送给 `limit_order.owner`。

| 11 | `token_program_2022` |   |   | |

<Note>
  **2026-09 中的变更：新配置不再从签名者获取其费用所有者。** `create_amm_config` 现在将程序的硬编码 `protocol_fee_owner::ID` 写入 `owner`，将 `fund_fee_owner::ID` 写入 `fund_owner`。之前，它将管理员签名者的密钥复制到两者中。在主网上，这些已经是存储在所有 21 个现有配置上的相同密钥。地址在 [`reference/program-addresses`](/zh/reference/program-addresses#clmm-fee-owner-wallets) 中。

  上面接受的签名者保持不变。管理员仍然可以从任何配置中收集，**现有的 `AmmConfig` 账户不会被重写**。从账户中读取 `owner` / `fund_owner` 而不是假设任一值。`UpdateAmmConfig` 参数 `3` 和 `4` 仍然可以轮换它们。
</Note>

## `CollectExcessLamports`

管理员扫除 CLMM 控制的账户上超过租金豁免最低值的 lamport。它在 2026-09 升级中添加，以回收 [SIMD-0437 租金减少](/zh/solana-fundamentals/rent-and-reclaimable-rent) 在每个步骤之前创建的账户上留下的过度资金。

只有超额部分移动。代币余额、账户数据、所有者、池状态和价格曲线保持不变。已经处于最低值的账户保持原样，因此在每次推出步骤后可以安全地重新运行该指令。

**参数**：无。

**账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | 接收每个扫除的 lamport。必须是 CLMM 程序管理员或专用收集 lamport 钱包（见 [`reference/program-addresses`](/zh/reference/program-addresses#excess-lamports-collection-wallets)）。任何其他签名者失败并显示 `NotApproved`。 |
| 2 | `pool_state` | W |   | 被扫除的池。其 PDA 种子签署代币程序 CPI，账户本身始终被扫除。 |
| 3 | `token_program` |   |   | SPL Token。 |
| 4 | `token_program_2022` |   |   | Token-2022。两个程序都是必需的；指令为每个源账户选择一个。 |
| 5.. | `remaining_accounts` | W |   | `M` 个源账户，任意数量，任意顺序。 |

**范围：每次调用一个池。** CLMM 没有程序范围的金库权限。每个池的金库由其自己的 `PoolState` 拥有。因此，每个代币程序源必须在第 2 个槽位中有 `pool_state` 作为其权限：`token_vault_0`、`token_vault_1` 或该池的奖励金库之一。如果你传递另一个池的金库或用户的代币账户，代币程序的所有者检查失败，整个指令恢复。它不会被跳过。位置 NFT 铸币不能被扫除，因为当位置打开时其铸币权限被撤销。

**每个源账户的处理方式**

程序对 `remaining_accounts` 进行两次遍历：首先是每个代币程序 CPI，然后是直接借记。交错两者会导致运行时的 `UnbalancedInstruction` 错误，因此顺序在程序中是固定的，你不必自己排序列表。

| 遍历 | 源账户所有者 | 处理 |
|---|---|---|
| 1 | SPL Token 或 Token-2022，非原生代币账户 | CPI `WithdrawExcessLamports`（代币程序判别式 `38`），由 `pool_state` 签署。 |
| 1 | SPL Token 或 Token-2022，**原生**（wSOL）代币账户 | `WithdrawExcessLamports` 拒绝原生账户。程序 CPI `SyncNative`，测量包装的 `amount` 增长了多少，并为该增量调用 `UnwrapLamports`（判别式 `45`）。然后它要求包装的余额等于其同步前值，否则失败并显示 `LamportsCalculateError`（`6052`）。SOL 端池金库保持其完整流动性。 |
| 2 | `pool_state`（第 2 个槽位） | 直接借记至 `rent.minimum_balance(data_len)`。 |
| 2 | CLMM 程序：`AmmConfig`、`ObservationState`、`TickArrayBitmapExtension`、`TickArrayState`、`PersonalPositionState`、`LimitOrderState` 等 | 直接借记至 `rent.minimum_balance(data_len)`。账户**不**必属于第 2 个槽位中的池。 |
| — | 其他任何内容 | **静默跳过。** 无错误，无 lamport 移动。 |

<Warning>
  **第 2 遍涵盖用户支付租金的账户。** 此处传递的 `PersonalPositionState` 或 `LimitOrderState` 像任何其他 CLMM 拥有的账户一样放弃其超额。它保持租金豁免并保留其数据。当它稍后关闭时，所有者获得账户此时持有的任何内容，在扫除后是当前租金最低值。
</Warning>

交易大小是一次调用中有多少源的真正限制。这与 [`solana-fundamentals/rent-and-reclaimable-rent`](/zh/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction) 中描述的钱包端扫除的约束相同。

**常见错误**：
- `NotApproved`（`6000`）：错误的签名者。
- `LamportsCalculateError`（`6052`）：wSOL 往返没有净为零。
- 代币程序所有者不匹配错误：代币源不由 `pool_state` 拥有。
- `InsufficientFunds`：程序拥有的账户持有少于其自己的租金最低值。

**无 SDK 构建器。** `@raydium-io/raydium-sdk-v2` 不为此管理员路径提供构建器。从 IDL 手动编码。

## `InitializeReward`

向池添加新的奖励流。最多 3 个流可以同时活跃。

**参数** — 单个结构体，`param: InitializeRewardParam`：

```rust
pub struct InitializeRewardParam {
    pub open_time:                u64,
    pub end_time:                 u64,
    pub emissions_per_second_x64: u128,   // Q64.64
}
```

线路编码是三个字段背靠背，所以手工构建的指令不受影响 — 但 IDL 驱动的客户端必须传递一个 `param` 对象而不是三个位置参数。

**账户**

| # | 名称 | W | S | 说明 |
|---|------|---|---|-------|
| 1 | `reward_funder` | W | S | |
| 2 | `funder_token_account` | W |   | |
| 3 | `amm_config` |   |   | |
| 4 | `pool_state` | W |   | |
| 5 | `operation_state` |   |   | CLMM 操作状态 PDA 门控奖励创建。 |
| 6 | `reward_token_mint` |   |   | |
| 7 | `reward_token_vault` | W |   | 在此处 `init`。 |
| 8 | `reward_token_program` |   |   | |
| 9 | `system_program`、`rent` |   |   | |

**前置条件**

- 池上当前活跃的流少于 3 个。
- 资金提供者将 `total_emission = emissions_per_second × (end_time − open_time)` 价值的奖励代币作为此指令的一部分存入金库。
- 按 `operation_state` 白名单的奖励铸币。

## `SetRewardParams`

扩展、充值或更改现有奖励流的发放速率。通常由池创建者或 Raydium 多签调用。约束在链上：你通常可以扩展 `end_time` 或增加发放，而不是追溯性地缩小它们。检查 `operation_state` 的所有者列表。

## `UpdateRewardInfos`

纯粹的簿记 — 通过将 `emissions_per_second × Δt / liquidity` 相乘，将 `reward_growth_global_x64` 结算到当前时间。由每个涉及流动性的指令内部调用。作为独立指令公开，因为外部参与者（UI、cranks）有时想要触发它。

## 收集奖励

<Warning>
  **没有独立的收集奖励指令。** 程序不公开 `CollectReward` 入口点，已发布的 IDL 中也没有。
</Warning>

欠位置的奖励由 `DecreaseLiquidity` / `DecreaseLiquidityV2` 支付。要在不改变位置的情况下收集，使用 `liquidity = 0`、`amount_0_min = 0`、`amount_1_min = 0` 调用它。奖励金库和收款人账户在 `remaining_accounts` 中按每个活跃奖励的三个一组，顺序为 `reward_token_vault(W)`、`recipient_token_account(W)`、`reward_vault_mint`。

`CollectRemainingRewards` 是另一回事：它让奖励*资金提供者*在流的 `end_time` 之后扫除从未分配给任何位置的代币。
