## 交易解析

Solana 交易有三个核心组件：

- **消息（Message）**：有序的指令列表、这些指令引用的账户，以及最近的区块哈希。
- **签名（Signatures）**：每个签名者一个，证明交易已被授权。
- **最近的区块哈希（Recent blockhash）**：证明交易是最近的；具有陈旧区块哈希（超过 150 个槽）的交易会被拒绝。

### 指令

一个指令指定：

- `program_id` — 要调用的程序。
- `accounts` — 程序可能接触的账户（及其可写/签名者标志）。
- `data` — 程序解释的不透明字节。

单个交易可以包含多个指令。它们按顺序执行；如果任何一个失败，所有之前的指令都会回滚（原子性）。

典型的 Raydium 交换交易包括：

1. `ComputeBudget::SetComputeUnitLimit` — 提高默认 CU 限制。
2. `ComputeBudget::SetComputeUnitPrice` — 设置优先费用。
3. 可选的 `CreateAssociatedTokenAccount` — 如果用户没有输出 ATA，则创建一个。
4. `Raydium::SwapBaseInput` — 执行交换。
5. 可选的 `CloseAccount` — 关闭包装的 SOL ATA。

SDK 会自动打包这些指令——通过池类型自己的构建器（`raydium.cpmm.swap`、`raydium.clmm.swap`、`raydium.liquidity.swap`），或通过 `raydium.tradeV2.swap` 进行多跳路由。

## 交易中的账户

交易中任何指令接触的每个账户都必须列在交易的账户密钥中。每个账户都被标记为：

- **签名者/非签名者**：账户的所有者是否必须签署交易？
- **可写/只读**：交易是否可以修改账户？

运行时强制执行这些标志：尝试写入不可写账户的程序会失败，运行时会拒绝缺少必需签名者的交易。

对于 CPMM 交换，账户列表有约 13 个条目（参见 [`solana-fundamentals/account-model`](/zh/solana-fundamentals/account-model)）。具有多个 tick 数组交叉的 CLMM 交换可能有 20 个以上。

## 交易大小限制

Solana 将交易限制在 **1232 字节**，包括签名、消息和头部。这是复杂交易最常见的障碍——Raydium 的 CLMM 与多跳路由经常接近这个限制。

典型的约 1000 字节 Raydium 交换的分解：

| 组件 | 大小 |
|-----------|------|
| 签名 | 64 B |
| 签名计数 | 1 B |
| 消息头 | 3 B |
| 区块哈希 | 32 B |
| 账户密钥（13 × 32 B） | 416 B |
| 指令（4 × ~100-150 B） | 400–600 B |
| **总计** | ~900–1100 B |

### 地址查找表（ALTs）

ALTs 让交易通过 1 字节索引引用已发布表中的账户，而不是完整的 32 字节公钥。这大幅压缩了交易：

- 直接引用 20 个账户的交易：~640 B 的公钥。
- 使用 ALTs 的相同交易：~20 B 的索引 + ALT 引用。

Raydium 在主网上为 CPMM/CLMM 交换路径维护 ALTs。SDK 会自动使用它们。构建多跳路由的聚合器大量依赖它们。

```ts
import { VersionedTransaction } from "@solana/web3.js";

// SDK 构建带有 ALT 引用的 v0（版本化）交易
const { transaction } = await raydium.cpmm.swap({ /* ..., txVersion: TxVersion.V0 */ });
// transaction 是 VersionedTransaction，不是旧版 Transaction。
// （对于多跳路由，使用 raydium.tradeV2.swap，它返回 `transactions`
//  — 一个数组 — 其 execute() 需要 { sequentially: true }。）
```

## 计算预算

每个交易都有一个**计算单位（CU）预算**。超过它会终止执行并使交易失败。

- **默认值**：每个交易 200,000 CU。
- **最大值**：每个交易 1,400,000 CU（通过 `ComputeBudget::SetComputeUnitLimit` 提高）。
- **每块上限**：每块 48M CU（协议级别）。

典型的 Raydium CU 消耗（参见 [`integration-guides/priority-fee-tuning`](/zh/integration-guides/priority-fee-tuning) 获取完整表格）：

| 指令 | CU |
|-------------|-----|
| CPMM 交换 | ~140,000 |
| CLMM 交换（无 tick 交叉） | ~170,000 |
| CLMM 交换（4 个 tick 交叉） | ~320,000 |
| Farm v6 质押 | ~130,000 |
| CPMM 池创建 | ~250,000 |

始终通过 `ComputeBudget` 设置显式 CU 限制；否则你会得到 200k 默认值，这对大多数 Raydium 指令来说太低了。

```ts
import { ComputeBudgetProgram } from "@solana/web3.js";

tx.add(
  ComputeBudgetProgram.setComputeUnitLimit({ units: 300_000 }),
);
```

如果你设置的 CU 限制太低，交易在达到上限时会失败；设置太高，你可能在拥塞下被降低优先级（根据定价模型，你可能为从未使用的计算付费）。

## 优先费用

除了基础交易费用（每个签名 5000 lamports），验证者越来越多地优先考虑支付**优先费用**的交易：每 CU 的微 lamports 小费。

```
priority_fee = compute_unit_price (micro-lamports) × compute_unit_limit
```

示例：10,000 µL/CU × 300,000 CU = 3,000,000 µL = 0.003 SOL。

优先费用是本地的——它们只影响块内的排序；它们不会改善你被包含的机会。在拥塞期间设置合理的优先费用至关重要。

```ts
tx.add(
  ComputeBudgetProgram.setComputeUnitPrice({ microLamports: 10_000 }),
);
```

参见 [`integration-guides/priority-fee-tuning`](/zh/integration-guides/priority-fee-tuning) 了解如何动态调整这个值。

## 指令计数和账户计数限制

除了 1232 字节的总限制：

- **每个交易的最大账户数**：128。
- **每个指令的最大账户数（CPI）**：64。
- **每个交易的最大指令数**：无硬限制，仅受大小限制约束。
- **最大 CPI 深度**：4（一个程序可以调用另一个，后者可以调用另一个，最多 4 层深）。

跨越多个 tick 数组的 Raydium CLMM 交换可能会对账户限制施加很大压力——单个交换接触池、输入/输出保险库、输入/输出 ATAs、多个 tick 数组、可能是转账钩子程序的额外账户，加上强制的计算预算/系统/代币程序引用。通过 CPI 组合 Raydium 的设计（例如自动复合器）需要考虑这一点。

## Raydium 交换中的费用类别

用户交换交易需要支付两类费用：

### Solana 网络费用

支付给验证者的 SOL。

- **基础签名费**：每个签名 5000 lamports。几乎总是 1 个签名 = 0.000005 SOL。
- **优先费用**：CU 价格 × CU 限制（以微 lamports 计）。随拥塞情况变化；参见 [`integration-guides/priority-fee-tuning`](/zh/integration-guides/priority-fee-tuning)。

这些费用流向验证者，与 Raydium 无关，即使对于失败的交易也会收取（某些优先费用边界情况除外）。

### Raydium 协议费用

从交换金额中扣除。

- **交换费**：输入的百分比（CPMM 典型 0.25%，CLMM 0.01%–1% 每层级）。在 LPs 和协议目标地址之间分割。参见 [`ray/protocol-fees`](/zh/ray/protocol-fees)。

这些费用是 Raydium 会计内部的——用户将其视为零费用池会产生的输出金额较小。

### 示例：\$1000 USDC → SOL 通过 CPMM 0.25% 层级

| 费用类别 | 金额 | 流向 |
|--------------|--------|---------|
| 基础签名费 | 0.000005 SOL (~\$0.0007) | 验证者 |
| 优先费用（10k µL × 300k CU） | 0.003 SOL (~\$0.45) | 验证者 |
| CPMM 交换费（0.25%） | \$2.50 | LPs + 协议 |
| **用户总成本** | ~\$2.95 | |

滑点（价格影响 + 市场变动）不是费用，但会影响相同的底线。

## 版本化交易

Solana 有两种交易格式：

- **旧版**：原始格式，不支持 ALT。
- **v0（版本化）**：支持 ALTs，可扩展到未来版本。

所有现代 Solana 工具都使用 v0。Raydium SDK 默认发出 v0 交易。

```ts
// 直接构建 v0 交易
import { VersionedTransaction, TransactionMessage } from "@solana/web3.js";

const msg = new TransactionMessage({
  payerKey:        owner.publicKey,
  recentBlockhash: blockhash,
  instructions:    [ /* ... */ ],
}).compileToV0Message([lookupTableAccount]);

const tx = new VersionedTransaction(msg);
tx.sign([owner]);
```

## 区块哈希新鲜度

交易必须包含最后约 150 个槽（约 60 秒）内的区块哈希。超过该窗口，验证者会拒绝它。

对于重试循环，在每次重试时获取新的区块哈希：

```ts
async function sendWithRetry(tx, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    const { blockhash, lastValidBlockHeight } = await connection.getLatestBlockhash();
    tx.message.recentBlockhash = blockhash;
    tx.sign([owner]);
    try {
      return await connection.sendRawTransaction(tx.serialize());
    } catch (e) {
      if (i === maxRetries - 1) throw e;
    }
  }
}
```

参见 [`integration-guides/priority-fee-tuning`](/zh/integration-guides/priority-fee-tuning) 了解完整的重试并逐步提高费用的模式。

## 并行执行

Solana 在多核验证者上并行执行不冲突的交易。两个交易冲突的条件是它们都写同一个账户。

对 Raydium 的影响：

- 同一池上的两个交换无法并行执行——两者都写池状态。
- 池 A 上的交换和池 B 上的交换如果账户列表不重叠则并行执行。
- 只读交易永远不会阻止同一账户上的写入者（只读与自身并发，但不与写入并发）。

这就是为什么 Solana 能够维持高 DEX 吞吐量，尽管单池序列化。

## 交易确认级别

提交交易时，你选择一个确认级别：

| 级别 | 等待 | 最终性 |
|-------|------|----------|
| `processed` | ~400 ms | 未最终化；可能回滚 |
| `confirmed` | ~1 s | 超多数投票 |
| `finalized` | ~13 s | 超多数根植 |

对于交换 UX，`confirmed` 是标准的。对于处理大价值的操作（池创建、奖励充值），`finalized` 更安全。

```ts
await connection.sendAndConfirmTransaction(tx, [owner], {
  commitment: "confirmed",
});
```

## 模拟

Solana 支持在提交前模拟交易：

```ts
const sim = await connection.simulateTransaction(tx);
console.log(sim.value.logs);
console.log(sim.value.unitsConsumed);
```

Raydium SDK 在计算 `getBestSwapInfo` 时在内部使用模拟来验证选定的路由确实成功。模拟不是免费的——它消耗 RPC 容量——但它在支付前捕获错误。
