## 版本发布

<Update label="2026-08-31" description="LaunchLab：平台曲线规则替代曲线参数白名单">
  启动参数限制从 `PlatformConfig` 移至按配置的 `PlatformCurveRule` 账户。一条规则最多包含 10 个检查组，每个检查组最多 25 个 `(field, op, value)` 约束，覆盖 19 个启动参数，支持 `Eq` / `Gte` / `Lte` / `Neq` 操作——这样平台终于可以表达值范围、替代层级、毕业估值上限、迁移下限、代币类型门控或按日期切换的组，而仅支持相等性的白名单无法做到这些。`PlatformConfig` 保持其 944 字节大小：`restrict_curve_param`、`curve_rule_manager` 和移除的向量长度前缀都从填充中移出。解码器必须删除尾部的 `Vec<PlatformCurveParam>`，启动构建者必须在标志打开时将规则 PDA 附加到 `remaining_accounts`。移除了两条指令，添加了四条，添加了两个 `UpdatePlatformConfig` 变体，追加了 `6024`–`6030`。需要刷新 IDL。SDK 提供两个纯链下检查，这样创建者永远不必从已还原的交易中学习规则，条目记录了在主网启用标志前的开发网排练。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-31-launchlab-platform-curve-rules)
</Update>

<Update label="2026-08-27" description="LaunchLab：平台在铸币创建时持有提取代扣权限">
  `InitializeWithToken2022` 现在将 `PlatformConfig.transfer_fee_extension_auth` 写入新基础铸币的 `withdraw_withheld_authority`，而不是启动 `authority` PDA，这样平台可以在结合曲线阶段扫除代扣的转账费用，而不必等待毕业——程序本身没有提取代扣指令。`MigrateToCpswap` 仅在 PDA 仍持有该权限时才重新分配该权限，这保持了两代铸币的毕业工作。`transfer_fee_config_authority` 仍仅在毕业时移动，所以在启动中途轮换 `transfer_fee_extension_auth` 会无声地将两个权限留在不同的密钥上。没有账户布局、指令、参数或错误代码改变。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-27-launchlab-token2022-withheld-authority)
</Update>

<Update label="2026-08-26" description="LaunchLab：平台费率上限提高至 500 bps">
  平台 `fee_rate` 上限在验证它的两条路径上都移至 `50000`（500 bps）。`CreatePlatformConfig` 自程序首次发布以来一直被限制在 `10000`（100 bps）；`UpdatePlatformConfig` 自 2026-01-27 以来被限制在 `25000`（250 bps）。现在两个检查一致，所以以任何允许的费率创建的平台也可以以该费率更新——包括通过 `AllInfo` 批量变体，它在重写每个其他字段时重新验证 `fee_rate`。两条路径仍然引发不同的错误（创建时为 `InvalidInput`，更新时为 `InvalidPlatformInfo`）。没有账户布局、指令或错误代码改变，现有平台或启动都不会重新定价。`GlobalConfig.max_share_fee_rate` 保持在 100 bps，仅限制每笔交易的推荐 `share_fee_rate`。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-26-launchlab-platform-fee-rate-cap)
</Update>

<Update label="2026-08-24" description="LaunchLab：Token-2022 报价铸币">
  启动现在可以用 Token-2022 铸币报价。`CreateConfig`、`InitializeV2`、`InitializeWithToken2022`、四条交换指令和每个费用声明都在其报价程序槽中接受任一代币程序；已弃用的 `Initialize` 保持仅限旧版。交换滑点界限现在与支付者实际支付或接收的内容进行比较，扣除报价铸币的转账费用。`PoolState.token_program_flag` bit1 变得有意义，所以针对整个字节测试 `0` 的解码器会误读旧版基础铸币为 Token-2022。`MigrateToCpswap` 将其两个代币程序账户重命名为 `token_program` / `token_program_2022`，`6023` 被重用于 `CalculateOverflow`。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-24-launchlab-token2022-quote-mint)
</Update>

<Update label="2026-08-17" description="LaunchLab：仅 CPMM 启动和平台配置控制">
  新启动初始化现在需要 CPMM，而旧版 AMM v4 绑定状态保持可迁移。在此版本之前，`creator_scale` 生成创建者拥有的费用密钥；升级后执行的 CPMM 迁移改为将 `platform_scale + creator_scale` 合并为一个平台拥有的费用密钥份额。平台也可以用自己的 `PlatformAllowConfig` PDA 限制启动，迁移构建者必须附加两个 CPMM 支持铸币 PDA。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-17-launchlab-cpmm-only-platform-config)
</Update>

<Update label="2026-08-17" description="CLMM：受限发行人头寸 NFT 冻结">
  新 CLMM 头寸 NFT 铸币使用其池作为冻结权限，但其代币账户默认保持未冻结。冻结仅在 `OpenPositionV2` 或 `OpenPositionWithToken22Nft` 时发生，当任一底层保管库铸币的冻结权限与受限发行人列表匹配时。匹配的头寸无法转移或更改所有者，但仍可管理流动性。其 `ClosePosition` 调用必须附加池，以便 CLMM 可以原子地解冻、销毁和关闭。现有头寸保持不变。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-17-clmm-restricted-position-nft-freeze)
</Update>

<Update label="2026-08-17" description="CPMM：无权限创建者费用收集">
  一条附加的 `CollectCreatorFeePermissionless` 指令让任何支付者扫除所有累积的创建者费用，同时将受益人和两个代币目的地限制为 `PoolState.pool_creator` 和创建者的规范 ATA。原始创建者签名路径保持不变。`CreatePermissionPda` 也接受专用授予权限，而 `ClosePermissionPda` 保持仅限管理员。

  [阅读完整条目 →](/zh/reference/changelog/2026-08-17-cpmm-permissionless-creator-fee-collection)
</Update>

<Update label="2026-07-30" description="CLMM：有权限多池和限价单冻结账户保护">
  两个附加的、向后兼容的 CLMM 程序更新。`CreatePermissionedPool` 将客户端提供的非零 `seed_index` 折叠到池 PDA 种子中，让白名单操作者（持有 `Permission` PDA 的操作者）为每个 `(config, mint0, mint1)` 创建多个池——所以池 ID 不再是一对的规范标识。新管理指令 `CreatePermissionPda` / `ClosePermissionPda` 管理这些授予，`PoolState` 获得 `seed_index` 字段（从填充中切割，大小不变）。另外，`OpenLimitOrder` 现在接受输出端账户并拒绝其输入或输出代币账户被冻结的订单（`NotApproved`）。

  [阅读完整条目 →](/zh/reference/changelog/2026-07-30-clmm-permissioned-pools)
</Update>

<Update label="2026-07-22" description="AMM v4：移除 OpenBook / Serum 依赖">

  [阅读完整条目 →](/zh/reference/changelog/2026-07-22-amm-v4-openbook-removal)
</Update>

## 文档约定

- **版本控制**：本文档使用基于日历的版本控制（YYYY-MM-DD）。每次更新都会在上面的时间线顶部添加一个新条目页面和新行。
