## 不変量

CPMMは2つのヴォルト上で古典的な定数積不変量を維持します：

$$
x \cdot y = k
$$

ここで`x`はvault0の残高で、受け取り時のToken-2022転送手数料を差し引いた**後**の値です。`y`も同様です。すべてのスワップは、LPに付与される取引手数料を考慮した後、`k' ≥ k`を満たす必要があります（プロトコル、ファンド、クリエイターバケットは`k`にカウント**されません**。ヴォルトに存在しますが、曲線ビューから除外されます。下記の[曲線上の手数料](#曲線上の手数料)を参照）。したがって`k`はLPが手数料を蓄積するにつれて時間とともに単調に増加します。

LPシェアは`k`ではなくプールの準備金によって価格設定されます：

$$
\text{token0でのLP価格} = \frac{x}{\text{lpSupply}}, \qquad \text{token1でのLP価格} = \frac{y}{\text{lpSupply}}
$$

`ΔLP`個のLPトークンをバーンすると、正確に`ΔLP × x / lpSupply`のtoken0と`ΔLP × y / lpSupply`のtoken1が返されます。曲線も`k`も預金や引き出しで動きません。スワップだけが価格を変更します。

## スワップパス上の手数料モデル

CPMMはすべてのスワップに**2つの独立した手数料**を適用します：

- **取引手数料**は入力側で取られ、`AmmConfig.trade_fee_rate`で課金されます。その後、LP、プロトコル、ファンドシェアに分割されます（LPシェアはヴォルトに留まり`k`を増加させます。プロトコルとファンドシェアはヴォルト会計から抽出されます）。
- **クリエイター手数料**（`enable_creator_fee == true`の場合のみアクティブ）は`AmmConfig.creator_fee_rate`で課金されます。`PoolState.creator_fee_on`とスワップ方向に応じて、**入力**側または**出力**側で取られます（[`products/cpmm/fees`](/ja/products/cpmm/fees#which-side-of-the-trade-the-fees-are-taken-from)を参照）。独立したバケットです。取引手数料のスライスではありません。

<Note>
  **クリエイター手数料のプロトコルシェアはこのページのどこにも表示されず、それは意図的です。** これは`CollectCreatorFee`が曲線がすでに除外している2つのカウンター間で蓄積された手数料を移動するときに適用されます。スワップ数学、見積もり、`k`はそれがあってもなくても同じです。[`products/cpmm/fees`](/ja/products/cpmm/fees#protocol-share-of-the-creator-fee)を参照してください。
</Note>

定義：

- `FEE_RATE_DENOMINATOR = 1_000_000`
- `trade_fee_rate` — `AmmConfig`から、例：`2500` = 関連するボリュームサイドの0.25%
- `creator_fee_rate` — `AmmConfig`から、例：`1000` = 関連するボリュームサイドの0.10%
- `protocol_fee_rate`、`fund_fee_rate` — ボリュームではなく、取引手数料の`1/FEE_RATE_DENOMINATOR`単位で表示

クリエイター手数料が入力側にある場合：

```
total_input_fee = ceil(amount_in * (trade_fee_rate + creator_fee_rate) / FEE_RATE_DENOMINATOR)
creator_fee     = floor(total_input_fee * creator_fee_rate / (trade_fee_rate + creator_fee_rate))
trade_fee       = total_input_fee - creator_fee
amount_in_after_fees = amount_in - total_input_fee
```

クリエイター手数料が出力側にある場合：

```
trade_fee            = ceil(amount_in * trade_fee_rate / FEE_RATE_DENOMINATOR)
amount_in_after_fees = amount_in - trade_fee
amount_out_curve     = curve_output(amount_in_after_fees, ...)
creator_fee          = ceil(amount_out_curve * creator_fee_rate / FEE_RATE_DENOMINATOR)
amount_out           = amount_out_curve - creator_fee
```

どちらの場合も取引手数料は同じ方法で分割されます：

```
protocol_fee   = floor(trade_fee * protocol_fee_rate / FEE_RATE_DENOMINATOR)
fund_fee       = floor(trade_fee * fund_fee_rate     / FEE_RATE_DENOMINATOR)
lp_fee         = trade_fee - protocol_fee - fund_fee     // creator_feeはここで差し引かれません
```

`protocol_fee + fund_fee + creator_fee`の金額はヴォルトに保持されていますが、プール状態で別途追跡されます（`protocol_fees_token*`、`fund_fees_token*`、`creator_fees_token*`）。定数積不変量が`k' ≥ k`をチェックするとき、ヴォルト残高**から**3つすべての蓄積されたが未処理の手数料を差し引いた値を使用します。したがってLPは`lp_fee`のみをキャプチャします。

[`products/cpmm/fees`](/ja/products/cpmm/fees)で収集命令と計算例を参照してください。

## SwapBaseInput（入力確定）

「ユーザーは入力ミントの正確に`amount_in`を提供し、出力ミントの少なくとも`minimum_amount_out`を受け取ります。」

Token-2022を一時的に無視すると：

```
amount_in_after_trade_fee = amount_in - trade_fee
amount_out                = y − (x * y) / (x + amount_in_after_trade_fee)
```

代数的に：

$$
\text{amount\_out} = \frac{y \cdot \Delta x_{\text{net}}}{x + \Delta x_{\text{net}}}
$$

ここで`Δx_net = amount_in_after_trade_fee`です。

プログラムはその後、ヴォルト会計を更新して、プロトコル/ファンド/クリエイターに属する`trade_fee`の部分が「蓄積」バケットに座り（次のスワップの曲線`x`に含まれない）、LPシェアが次のスワップのために`x`に参加するようにします。

### 入力側のToken-2022

入力ミントに転送手数料拡張がある場合、**ミント**はユーザー→ヴォルトの転送時に手数料を差し引きます。したがってヴォルトは実際に`amount_in − transfer_fee_in(amount_in)`を受け取ります。CPMMプログラムは以下を計算します：

```
amount_actually_received = amount_in − transfer_fee_in(amount_in)
trade_fee                = ceil(amount_actually_received * trade_fee_rate / FEE_RATE_DENOMINATOR)
amount_in_after_trade_fee = amount_actually_received − trade_fee
```

そして`amount_in_after_trade_fee`に対して曲線を実行します。これが重要な理由は、**曲線価格はユーザーの見出し金額ではなく、ヴォルトに実際に到着した正味金額から計算される**からです。

### 出力側のToken-2022

出力ミントに転送手数料がある場合、プールはそのヴォルトから`amount_out`をユーザーに送信します。**ミント**は出力時に手数料をスキミングするため、ユーザーは`amount_out − transfer_fee_out(amount_out)`を受け取ります。プログラムは通常通り曲線から`amount_out`を計算しますが、見積もりを表示するときにプールの「ヴォルト送信」数をユーザーの「受け取り」数に変換するのはインテグレーターの責任です。

### スリッページチェック

`amount_out`を計算した後：

```
require(amount_out >= minimum_amount_out, "AmountSpecifiedLessThanMinimum")
```

出力ミントが転送手数料を課金する場合、SDKはスリッページ定数がヴォルトが送信する金額ではなくユーザーが実際に受け取る金額で表示されるように、転送手数料を`minimum_amount_out`を設定する前に適用します。

## SwapBaseOutput（出力確定）

「ユーザーは出力ミントの正確に`amount_out`を受け取り、入力ミントの最大`maximum_amount_in`を支払う意思があります。」

`Δx_net`の曲線を反転：

$$
\Delta x_{\text{net}} = \left\lceil \frac{x \cdot \text{amount\_out}}{y - \text{amount\_out}} \right\rceil
$$

シーリングは重要です。整数切り捨て後に`k' ≥ k`を保証します。その後：

```
// ネット入力から総入力に逆算します。
// 手数料は総額に適用されるため：
//   net = gross − ceil(gross * rate / D)
//       ≈ gross * (D − rate) / D
// 適切な場所でシーリングを使用して反転：
gross_needed = ceil(Δx_net * D / (D − trade_fee_rate))
```

Token-2022入力では、以下でラップします：

```
gross_needed_before_mint_fee
  = inflate_for_transfer_fee(gross_needed, input_mint)
```

ユーザーがミントの転送手数料控除後もプールが`gross_needed`を受け取るのに十分な金額を支払うようにします。

### スリッページチェック

```
require(gross_needed_before_mint_fee <= maximum_amount_in, "AmountSpecifiedExceedsMaximum")
```

## 計算例

プール状態、Token-2022を無視：

- `x = 1_000_000_000_000`（token0の1,000,000.000000、6デシマル）
- `y = 2_000_000_000_000`（token1の2,000,000.000000、6デシマル）
- `AmmConfig`：`trade_fee_rate = 2500`、`protocol_fee_rate = 120_000`、`fund_fee_rate = 40_000`、`creator_fee_rate = 0`

ユーザー：`amount_in = 1_000_000_000`（token0の1,000.000000）で`SwapBaseInput`を実行。クリエイター手数料は無効（`enable_creator_fee = false`）。

```
trade_fee                = ceil(1_000_000_000 * 2500 / 1_000_000)       = 2_500_000
  protocol_fee           = floor(2_500_000 * 120_000 / 1_000_000)       = 300_000
  fund_fee               = floor(2_500_000 *  40_000 / 1_000_000)       = 100_000
  lp_fee                 = 2_500_000 − 300_000 − 100_000                 = 2_100_000
creator_fee              = 0                                              // 無効

amount_in_after_trade_fee = 1_000_000_000 − 2_500_000                    = 997_500_000

amount_out = y − (x * y) / (x + Δx_net)
           = 2_000_000_000_000
             − (1_000_000_000_000 * 2_000_000_000_000)
               / (1_000_000_000_000 + 997_500_000)
           = 1_993_011_971

new_vault0_raw   = x + amount_in                                        = 1_001_000_000_000
new_vault1       = y − amount_out                                       = 1_998_006_988_029

// vault0で受け取った1_000_000_000のうち、400_000は「蓄積手数料」
// （プロトコル+ファンド）で曲線が除外すべき：
curve_x          = new_vault0_raw − (protocol_fees_token0 + fund_fees_token0)
                 = 1_001_000_000_000 − 400_000
                 = 1_000_999_600_000

k' = curve_x * new_vault1 ≈ 2.000_004_196_E24  ≥  k = 2.0E24   ✓
```

同じプールが`enable_creator_fee = true`で`creator_fee_rate = 1000`（0.10%）を入力側に設定していた場合、プログラムは`total_input_fee = ceil(1_000_000_000 * 3500 / 1_000_000) = 3_500_000`を課金し、`creator_fee = 1_000_000`と`trade_fee = 2_500_000`に分割します。`trade_fee`のプロトコル/ファンド/LP計算は上記の例から変わりません。クリエイター手数料は独立したバケットで、`creator_fees_token0`に蓄積され、プロトコルとファンドバケットとともに`curve_x`から除外されます。

入力ミントが1%のToken-2022転送手数料を持つ場合、ヴォルトは`1_000_000_000`トークンの代わりに`990_000_000`トークンを受け取り、その後のすべての計算がその正味金額を使用します。

## オブザベーション更新ルール

すべてのスワップで、プログラムはリングバッファに新しいオブザベーションをプッシュするかどうかを評価します：

```
let since_last = now − observations[head].block_timestamp;
if since_last >= MIN_OBSERVATION_INTERVAL {
    let price0 = (vault1 << 32) / vault0;            // Q32.32-ish
    let price1 = (vault0 << 32) / vault1;
    let head' = (head + 1) % OBSERVATION_NUM;
    observations[head'] = Observation {
        block_timestamp: now,
        cumulative_token0_price_x32:
            observations[head].cumulative_token0_price_x32 + price0 * since_last,
        cumulative_token1_price_x32:
            observations[head].cumulative_token1_price_x32 + price1 * since_last,
    };
    head = head';
}
```

2つの特性：

- **スポット価格ではなく累積価格。** 単一のオブザベーションは価格ではありません。時刻`t0`から`t1`までのTWAPを取得するには、各端に最も近いオブザベーションを読み取り、`(cumulative(t1) − cumulative(t0)) / (t1 − t0)`を計算します。
- **サンプルはレート制限されています。** 同じスロット内の連続したスワップは1つのオブザベーションを共有する場合があります。スワップの直後にオブザベーションを読み取ると、1スロット古く見える場合があります。これは正常です。

詳細は[`products/clmm/accounts`](/ja/products/clmm/accounts)を参照してください。

## 曲線上の手数料

これは微妙な部分であり、呼び出す価値があります。曲線計算は**正味**ヴォルト残高に対して機能します。つまり、生のSPL残高から蓄積されたプロトコル、ファンド、クリエイター手数料を差し引いた値です（3つすべてが独立したバケットです。[`products/cpmm/fees`](/ja/products/cpmm/fees)を参照）。具体的な図：

```
raw_vault_balance   = RPC getTokenAccountBalanceが返すもの
accrued_fees        = protocol_fees_token{0,1} + fund_fees_token{0,1} + creator_fees_token{0,1}
curve_balance       = raw_vault_balance − accrued_fees
invariant           = curve_balance0 * curve_balance1
```

インテグレーターへの影響：

- **生の残高から見積もらないでください。** 最初に蓄積手数料フィールドを差し引くか、`SwapBaseInput`をシミュレーションとして呼び出して戻り値を取得してください。
- **`CollectProtocolFee`はトークンをヴォルトから移動させます。** 収集後、`raw_vault_balance`は低下しますが、`curve_balance`は変わりません。プールの価格は動きません。これは意図的です。

## 精度とオーバーフロー

- すべての曲線計算は`x * y`のオーバーフローを防ぐために`u128`中間値を使用します。
- 除算はゼロに向かって丸められます。ただし、`SwapBaseOutput`の`Δx_net`は切り上げられ、手数料計算では`trade_fee`で切り上げられ、サブスプリットで切り下げられます。これらの丸め方向は、不変量が整数切り捨てのために減少しないように選択されています。
- 極端なヴォルト比率（数十億：1）を持つプールは小さなトレードで精度フロアに達する場合があります。プログラムはその場合`ZeroTradingTokens`を返します。[`reference/error-codes`](/ja/reference/error-codes)を参照してください。
