## `CreateCustomizablePool`

新しいプールに推奨されます。`CreatePool` と同じ効果に加えて、プールごとの手数料回収モードとオプションの動的手数料オプトイン。

**引数**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**アカウント** — `CreatePool` の正確に 13 個の宣言されたアカウント。`dynamic_fee_config` は宣言されたアカウント**ではありません**。

<Warning>
  `enable_dynamic_fee = true` の場合、スナップショットする `DynamicFeeConfig` は**最後の** `remaining_account` として提供される必要があります。ハンドラーは `ctx.remaining_accounts.last()` を読み取ります。したがって、`SupportMintAssociated` バイパス PDA はその前に来る必要があります。そうしないと、プログラムは間違ったアカウントをスナップショットし、逆シリアル化に失敗します。フラグが設定されている間にそれを省略すると、`AccountLack` で失敗します。
</Warning>

**前提条件** — `CreatePool` と同じ。`enable_dynamic_fee = false` の場合、`remaining_account` は不要で、渡されたものはサポート ミント レコードのみスキャンされます。

**事後条件**

- `pool_state.fee_on` は選択された `CollectFeeOn` バリアントに設定されます。
- 動的手数料が有効な場合：`pool_state.dynamic_fee_info` は提供された `DynamicFeeConfig` から初期化されます（5 つのキャリブレーション パラメータがコピーされ、状態フィールドはゼロ化されます）。
- それ以外の場合：`pool_state.dynamic_fee_info` はゼロ化されます（= このプールでは動的手数料は永遠に非アクティブ）。

`fee_on` と動的手数料有効化ビットはプール作成時**のみ**設定されます。インプレース アップグレードはありません。レガシー `CreatePool` で作成されたプールは、動的手数料または片側手数料を遡及的に取得することはできません。新しいデプロイメントはこのインストラクションをデフォルトにする必要があります。

## `CreateCustomizablePoolV2`

`CreatePool` と `CreateCustomizablePool` はどちらも `["pool", amm_config, token_mint_0, token_mint_1]` からプール PDA を導出するため、`(config, mint0, mint1)` の組み合わせごとに正確に **1 つ** の正規プールアドレスが存在します。同じシードで 2 回目の `init` を実行するとエラーになります。`CreateCustomizablePoolV2` はクライアント提供の `seed_index: u16` をプール PDA シードに組み込むことでこの制限を解除し、**同じペアと手数料階層に対して複数のプールを作成** できるようにします。各プールは独自のアドレスを持ちます。誰でも呼び出せます。

プールのその他すべての側面は `CreateCustomizablePool` と同じです。同じ `CreateCustomizableParams` を受け取り、片側手数料と動的手数料オプトインをサポートします。

<Note>
  [2026-10-22 アップグレード](/ja/reference/changelog/2026-10-22-clmm-customizable-pool-v2)までは、このインストラクションは `CreatePermissionedPool` と呼ばれており、支払者がアドミン発行の `Permission` PDA を保有する必要がありました。アップグレードにより名前が変更され、`permission` アカウントが削除され、権限メカニズムが廃止されました。ディスクリミネータは名前とともに変更されたため、`CreatePermissionedPool` に対して構築されたクライアントは再構築する必要があります。
</Note>

**引数**

```rust
customizable_params: CreateCustomizableParams   // CreateCustomizablePool と同じ構造体
seed_index:          u16                          // ゼロ以外である必要があります。プール PDA シードに組み込まれます
```

**アカウント**

| # | 名前 | W | S | 注記 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | すべての新規アカウントのレント支払い。任意のウォレット。 |
| 2 | `pool_creator` |   |   | `pool_state.owner` として記録されます。`payer` と異なる場合があります。署名者ではなく、チェックされません。 |
| 3 | `amm_config` |   |   | プールがバインドされる手数料階層。 |
| 4 | `pool_state` | W |   | `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]` で `init`。 |
| 5 | `token_mint_0` |   |   | `token_mint_1` より前にソートされている必要があります。 |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`。 |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`。 |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`。 |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`。 |
| 11 | `token_program_0` |   |   | `token_mint_0` を所有するプログラム。 |
| 12 | `token_program_1` |   |   | `token_mint_1` を所有するプログラム。 |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts`: Token-2022 ミントが必要とするサポートミント レジストリ PDA、および `enable_dynamic_fee = true` の場合は `DynamicFeeConfig` **最後に** — `CreateCustomizablePool` と同じです。

**前提条件**

- `seed_index != 0`。`seed_index` が `0` の場合はレガシープール用に予約されており、ここで拒否されます。`[0, 0]` シード コンポーネントがレガシープールアドレスを古典的な 4 シード形式に折りたたみます。
- 導出されたアドレスにプールが既に存在しません。
- `CreatePool` と同じミント / 許可リストルール。

**事後条件**

- 新しい `pool_state` が `seed_index` 導出アドレスに存在し、`pool_state.seed_index = seed_index` です。
- その他すべての事後状態は `CreateCustomizablePool` と一致します（手数料モード、オプションの動的手数料）。

<Warning>
  `pool_creator` はチェックされないため、任意の支払者が任意のアドレスを `pool_state.owner` に書き込むことができます。そのアドレスはプールで `InitializeReward` を呼び出すことができますが、プールを作成した人の証明ではありません。インテグレータは V2 プールを `owner` でラベル付けまたはランク付けしないでください。
</Warning>

**前提条件**

- `tick_lower < tick_upper`、両方とも `pool.tick_spacing` の倍数、`[MIN_TICK, MAX_TICK]` 内。
- 2 つのティック配列 PDA が渡されます。それらは既に存在する必要は **ありません** — `get_or_create_tick_array` はこのインストラクション内で `payer` の費用で不足しているものを割り当てます。個別のティック配列初期化インストラクションはありません。
- ユーザーはソース ATA に少なくとも `amount_0_max` と `amount_1_max` を持っています。

**事後条件**

- `personal_position` が存在し、`liquidity` が設定され、`fee_growth_inside_last` がスナップショットされます。
- `tick_lower` と `tick_upper` のティック配列エントリが更新されます（`liquidity_gross += L`、`liquidity_net ± L`、手数料成長スナップショットが保持されます）。
- ポジションが範囲内の場合（`tick_lower ≤ tick_current < tick_upper`）、`pool_state.liquidity += L`。
- ポジション NFT ミントは `pool_state` をフリーズ権限として記録します。ミント権限は単一の NFT がミントされた後に削除されます。フリーズ権限を記録しても、NFT トークンアカウントの状態は変わりません。
- NFT トークンアカウントは、インストラクションが `OpenPositionV2` または `OpenPositionWithToken22Nft` **かつ** いずれかのボルトミントのフリーズ権限が CLMM の制限発行者リストと一致する場合を除き、フリーズされたままです。その一致する V2 パスのみがアカウントをフリーズします。`OpenPosition` V1 はフリーズしません。

**一般的なエラー** — `TickInvalidOrder`（`tick_lower >= tick_upper`）、`TickAndSpacingNotMatch`（エンドポイントが `tick_spacing` の倍数ではない）、`InvalidTickIndex`（`[MIN_TICK, MAX_TICK]` の外）、`MissingTickArrayBitmapExtensionAccount`（範囲がインラインビットマップの外で拡張が追加されていない）、`NotApproved`（`pool_state.status` がオープンをブロック）、`ZeroAmountSpecified`。

<Note>
  ポジションのフリーズは宣言されたインストラクションアカウントまたは引数を追加しません。クライアントは既存の V2 レイアウトでこれらのポジションを開くことができます。動作はオンチェーンで `vault_0_mint` と `vault_1_mint` から選択されます。
</Note>

- `tokens_fees_owed_{0,1} == 0`。
- すべてのリワードカウンター `reward_amount_owed == 0`。

**前提条件**

- `pool_state.status` はスワップを許可します。
- `now >= open_time`。
- `sqrt_price_limit_x64` は方向に対して `sqrt_price_x64` の正しい側にあります。

**一般的なエラー** — `TooLittleOutputReceived`（正確入力スリッページ）、`TooMuchInputPaid`（正確出力スリッページ）、`SqrtPriceLimitOverflow`、`NotEnoughTickArrayAccount`、`InvalidFirstTickArrayAccount`、`MissingTickArrayBitmapExtensionAccount`、`LiquidityInsufficient`、`NotApproved`（`pool_state.status` でスワップビットが設定）。CLMM には `ExceededSlippage` バリアントがありません — その名前は CPMM のものです — また `TickArrayNotFound` もありません。

**呼び出し元が知っておくべき `SwapV2` が内部で行うこと**（2025年リリース後）：

1. **動的フィー追加料金** — `pool.dynamic_fee_info` がゼロ以外の場合、プログラムは最後のスワップ以降に走査されたティック距離を使用してボラティリティアキュムレータを更新し（[`products/clmm/fees`](/ja/products/clmm/fees) のフィルター/減衰ルール付き）、`AmmConfig.trade_fee_rate` の上に `dynamic_fee_component` を追加します。総フィーは 10%（`MAX_FEE_RATE_NUMERATOR / 1_000_000`）でキャップされます。
2. **リミットオーダーマッチング** — 価格ウォークがオープンなリミットオーダーを保持するティックを横切るとき、プログラムはまずそのティックで利用可能なリミットオーダーリクイディティを埋めます（`order_phase` による FIFO）、その後 LP リクイディティ曲線に沿って進みます。埋められた金額は `tick.unfilled_ratio_x64` と `tick.part_filled_orders_remaining` を後の決済用に更新します。オーダー自体は所有者が `SettleLimitOrder` を呼び出すまで未使用のままです。
3. **片側フィールーティング** — `pool.fee_on = Token0Only` または `Token1Only` の場合、スワップステップは同じ入出力トレードを計算します。その後、フィーは設定された側にルーティングされます。設定されたフィー側が出力である方向では、フィーはスワップ出力から差し引かれます（ユーザーは `out − fee` を受け取ります）。設定されたフィー側が入力である方向では、動作は `FromInput` と一致します。`PoolState` の `is_fee_on_input(zero_for_one)` と `is_fee_on_token0(zero_for_one)` を参照してください。

`Swap`（V1）は `SwapV2` と同じ動的フィー、片側フィールーティング、リミットオーダーマッチングを実装します。唯一欠けている機能は Token-2022 サポートです — 両方のボルトはクラシック SPL Token である必要があります。Token-2022 ミントを持つプールは `SwapV2` 経由でスワップする必要があります。アグリゲータと SDK はすでにすべての CLMM レッグで V2 を優先するため、呼び出し元はミントタイプで分岐する必要がありません。

  **`rent` アカウントはありません**：構造体は `system_program` で終わり、13 個の宣言されたアカウントです。位置 14 に迷った `rent` は、オプションのビットマップ拡張機能が読み込まれる場所に正確に着地するため、インラインビットマップの外にあるティックアレイを最初に作成する必要があるまで、オーダーは機能しているように見えます — その後失敗します。
</Warning>

<Note>
  **アカウントリスト変更（2026-07 リリース）。** `OpenLimitOrder` は入力側に加えて**出力側**アカウント — `output_token_account`、`output_vault`、`output_vault_mint` — も取得するようになりました。これらは検証にのみ使用されます。プログラムは所有者の入力**または**出力トークンアカウントがフリーズされている場合、オーダーを拒否します。これにより、フィルが実際に所有者の出力 ATA に決済できることが保証されます。これは許可リスト/デフォルトフリーズ Token-2022 ミント（例：許可トークン）の場合に重要です。ここでアカウントはまだシャされていない可能性があります。古い片側アカウントリストに対して構築されたクライアントは、3 つの出力アカウントを追加する必要があります。
</Note>

**前提条件**

- `input_token_account` も `output_token_account` もフリーズされていません（そうでない場合は `NotApproved`）。
- `pool_state.status` はスワップ（ビット 4）とリミットオーダー（ビット 5）操作の両方を許可します（そうでない場合は `NotApproved`）。
- `tick_index % pool.tick_spacing == 0` で `[MIN_TICK, MAX_TICK]` 内。
- `tick_index` は選択された方向に対して **`pool.tick_current` の右側**にあります（token0 を売却 → ティックは現在より上である必要があり、その逆も同様）。既に横切られたティックで売却することはすぐにマッチングされ、拒否されます。

**事後条件**

- `limit_order` が存在し、オープン時に `tick.order_phase` と `tick.unfilled_ratio_x64` をスナップショットします。
- `tick.orders_amount += amount`（現在のコホート内）。
- `limit_order_nonce.order_nonce += 1`。
- `OpenLimitOrderEvent` が発行されます。

**一般的なエラー** — `NotApproved`（入力または出力トークンアカウントがフリーズ、またはプールがスワップ/リミットオーダーを無効化）、`ZeroAmountSpecified`（入力側転送フィー後 `amount == 0`）、`InvalidLimitOrderAmount`（金額がそのティックで 1 ベースユニット未満の出力を生成するか、`u64` をオーバーフロー）、`InvalidTickIndex`（`[MIN_TICK, MAX_TICK]` の外、または選択された方向に対して `tick_current` の間違った側）、`TickAndSpacingNotMatch`（`tick_index % pool.tick_spacing != 0`）、`OrderPhaseSaturated`。

- オープン以降のコホートの `unfilled_ratio_x64` からオーダーの埋められた金額を再計算します。
- 埋められた出力を `output_token_account` に送信します。
- 未埋め入力の `amount` を `input_token_account` に送り返します。
- `limit_order` をそれに応じて更新します。新しい未埋め残高がゼロの場合、プログラムはアカウントをクローズし、レント を `owner` に払い戻します。

## `SettleLimitOrder`

満たされた出力トークンをオーダーの未決済残高を変更せずにオーナーにプッシュします。`auto_withdraw` キーパーが長時間実行される部分的な約定をドリップペイしたい場合に便利です。

**呼び出し元** — オーダーの `owner`、またはプログラムの `limit_order_admin`（自動キーパーループを実行するオフチェーン運用ホットウォレット）。キーパーは他の権限を持たず、満たされた出力をオーダーの `owner` ATA にプッシュする以外にユーザーファンドを移動することはできません。

**アカウント**

| # | 名前 | W | S | 注記 |
|---|------|---|---|-------|
| 1 | `signer` |   | S | owner *または* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | オーナーの出力 ATA。 |
| 6 | `output_vault` | W |   | プール出力ボルト。 |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**効果**

- `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)` を使用して累積出力を計算します。
- デルタを `output_token_account` に転送します。
- `limit_order.settled_output` を更新します。
- オーダーを閉じ**ません**。残りの入力に対してまだ開いています。

## `CloseLimitOrder`

完全に消費されたオーダーアカウントを閉じます。誰が署名するかに関わらず、レントは常に `limit_order.owner` に返されます。

**呼び出し元** — `owner` または `limit_order_admin`。

**前提条件**

- オーダーの未決済残高がゼロです（`amount == total_amount` が満たされて決済されたか、オーナーが以前オーダーをゼロに減らして閉じるのを忘れました）。

**効果**

- `limit_order` を閉じます。レントは `limit_order.owner` に送信されます。

## `CreateDynamicFeeConfig`（管理者）

u16 インデックスの下に再利用可能なパラメータセットを作成します。

**引数**


**アカウント**

| # | 名前 | W | S | 注記 |
|---|------|---|---|-------|
| 1 | `owner` | W | S | ハードコードされた管理者公開鍵。 |
| 2 | `dynamic_fee_config` | W |   | PDA、ここで `init`。 |

**一般的なエラー** — `InvalidDynamicFeeConfigParams`（`decay_period <= filter_period` の場合、または 0 値フィールドが範囲外の場合）。

## `UpdateDynamicFeeConfig`（管理者）

既存の `DynamicFeeConfig` を変更します。作成時にすでにコンフィグをスナップショットしたプールは**遡及的に更新されません**。このコンフィグを参照する新しく作成されたプールのみが新しい値を取得します。

**引数** — `CreateDynamicFeeConfig` と同じ 5 つのキャリブレーションフィールド（`filter_period`、`decay_period`、`reduction_factor`、`dynamic_fee_control`、`max_volatility_accumulator`）。`index` は作成時に固定され、ここでは再度渡されません。

| 2 | `pool_state` | W |   | |
| 3 | `amm_config` |   |   | `address = pool_state.amm_config`。 |

| 5 | `token_vault_1` | W |   | |
| 6 | `vault_0_mint` |   |   | |
| 7 | `vault_1_mint` |   |   | |

| 9 | `recipient_token_account_1` | W |   | |

<Note>
  **2026-09 で変更：新しいコンフィグはもはや署名者からフィー所有者を取得しません。** `create_amm_config` はプログラムのハードコードされた `protocol_fee_owner::ID` を `owner` に、`fund_fee_owner::ID` を `fund_owner` に書き込むようになりました。以前は、管理者署名者のキーを両方にコピーしていました。メインネットでは、これらはすでに既存の 21 個のコンフィグすべてに保存されている同じキーです。アドレスは [`reference/program-addresses`](/ja/reference/program-addresses#clmm-fee-owner-wallets) にあります。

</Note>

## `CollectExcessLamports`

CLMM が制御するアカウント上のレント免除最小値を超えるラムポートの管理者スイープ。[SIMD-0437 レント削減](/ja/solana-fundamentals/rent-and-reclaimable-rent)が各ステップの前に作成されたアカウントに残す過剰資金を回収するために 2026-09 アップグレードで追加されました。

過剰分のみが移動します。トークン残高、アカウントデータ、オーナー、プール状態、価格曲線は変わりません。アカウントがすでに最小値にある場合は、そのままにされるため、各ロールアウトステップ後に命令を安全に再実行できます。

**引数**：なし。

**アカウント**

| # | 名前 | W | S | 注記 |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | スイープされたすべてのラムポートを受け取ります。CLMM プログラム管理者または専用ラムポート収集ウォレット（[`reference/program-addresses`](/ja/reference/program-addresses#excess-lamports-collection-wallets) を参照）である必要があります。他の署名者は `NotApproved` で失敗します。 |
| 2 | `pool_state` | W |   | スイープされるプール。その PDA シードはトークンプログラム CPI に署名し、アカウント自体は常にスイープされます。 |
| 3 | `token_program` |   |   | SPL Token。 |
| 4 | `token_program_2022` |   |   | Token-2022。両方のプログラムが必要です。命令はソースアカウントごとに 1 つを選択します。 |
| 5.. | `remaining_accounts` | W |   | `M` ソースアカウント、任意の数、任意の順序。 |

**スコープ：呼び出しごとに 1 つのプール。** CLMM にはプログラム全体のボルト権限がありません。各プールのボルトは独自の `PoolState` によって所有されます。したがって、すべてのトークンプログラムソースは、スロット 2 の `pool_state` をその権限として持つ必要があります：`token_vault_0`、`token_vault_1`、またはそのプールの報酬ボルトの 1 つ。別のプールのボルトまたはユーザーのトークンアカウントを渡すと、トークンプログラムのオーナーチェックが失敗し、命令全体が戻ります。スキップされません。ポジション NFT ミントはスイープできません。ポジションが開かれるとミント権限が取り消されるためです。

**各ソースアカウントの処理方法**

プログラムは `remaining_accounts` に対して 2 つのパスを実行します：最初にすべてのトークンプログラム CPI、次に直接デビット。2 つをインターリーブするとランタイムの `UnbalancedInstruction` エラーで中止されるため、順序はプログラムで固定され、リストを自分でソートする必要はありません。

| パス | ソースアカウント所有者 | 処理 |
|---|---|---|
| 1 | SPL Token または Token-2022、非ネイティブトークンアカウント | CPI `WithdrawExcessLamports`（トークンプログラム判別式 `38`）、`pool_state` で署名。 |
| 1 | SPL Token または Token-2022、**ネイティブ**（wSOL）トークンアカウント | `WithdrawExcessLamports` はネイティブアカウントを拒否します。プログラムは `SyncNative` を CPI し、ラップされた `amount` がどれだけ増加したかを測定し、`UnwrapLamports`（判別式 `45`）をそのデルタに対して正確に呼び出します。その後、ラップされた残高が同期前の値と等しいことを要求するか、`LamportsCalculateError`（`6052`）で失敗します。SOL 側プールボルトは完全な流動性を保持します。 |
| 2 | `pool_state`（スロット 2） | `rent.minimum_balance(data_len)` まで直接デビット。 |
| 2 | CLMM プログラム：`AmmConfig`、`ObservationState`、`TickArrayBitmapExtension`、`TickArrayState`、`PersonalPositionState`、`LimitOrderState` など | `rent.minimum_balance(data_len)` まで直接デビット。アカウントはスロット 2 のプールに属する**必要はありません**。 |
| — | その他 | **サイレントにスキップされます。** エラーなし、ラムポート移動なし。 |

<Warning>
  **パス 2 はユーザーがレントを支払ったアカウントをカバーします。** ここに渡された `PersonalPositionState` または `LimitOrderState` は、他の CLMM 所有アカウントと同様に過剰分を放棄します。レント免除のままで、データを保持します。後で閉じられるとき、オーナーはアカウントがその時点で保持しているものを取得します。スイープ後は現在のレント最小値です。
</Warning>

トランザクションサイズは、1 回の呼び出しに収まるソースの数に対する実際の制限です。これは [`solana-fundamentals/rent-and-reclaimable-rent`](/ja/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction) で説明されているウォレット側スイープと同じ制約です。

**一般的なエラー**：
- `NotApproved`（`6000`）：間違った署名者。
- `LamportsCalculateError`（`6052`）：wSOL ラウンドトリップがゼロに正味化されませんでした。
- トークンプログラムオーナー不一致エラー：トークンソースが `pool_state` によって所有されていません。
- `InsufficientFunds`：プログラム所有アカウントが独自のレント最小値より少ないです。

**SDK ビルダーなし。** `@raydium-io/raydium-sdk-v2` はこの管理者パスのビルダーを提供しません。IDL から手動でエンコードしてください。

## `InitializeReward`

プールに新しい報酬ストリームを追加します。最大 3 つのストリームが同時にアクティブになる可能性があります。

**引数** — 単一の構造体、`param: InitializeRewardParam`：

```rust
pub struct InitializeRewardParam {
    pub open_time:                u64,
    pub end_time:                 u64,
    pub emissions_per_second_x64: u128,   // Q64.64
}
```

ワイヤエンコーディングは 3 つのフィールドが背中合わせなので、手動で構築された命令は影響を受けません — ただし、IDL 駆動クライアントは 3 つの位置引数ではなく 1 つの `param` オブジェクトを渡す必要があります。

**アカウント**

| # | 名前 | W | S | 注記 |
|---|------|---|---|-------|
| 1 | `reward_funder` | W | S | |
| 2 | `funder_token_account` | W |   | |
| 3 | `amm_config` |   |   | |
| 4 | `pool_state` | W |   | |
| 5 | `operation_state` |   |   | 報酬作成をゲートする CLMM 操作状態 PDA。 |
| 6 | `reward_token_mint` |   |   | |
| 7 | `reward_token_vault` | W |   | ここで `init`。 |
| 8 | `reward_token_program` |   |   | |
| 9 | `system_program`、`rent` |   |   | |

**前提条件**

- プール上で現在 3 未満のストリームがアクティブです。
- ファンダーは `total_emission = emissions_per_second × (end_time − open_time)` 相当の報酬トークンをこの命令の一部としてボルトに預けます。
- `operation_state` ごとにホワイトリストされた報酬ミント。

## `SetRewardParams`

既存の報酬ストリームを拡張、トップアップ、または排出率を変更します。通常、プール作成者または Raydium マルチシグによって呼び出されます。制約はオンチェーンに存在します：通常、`end_time` を拡張したり排出を増やしたりできますが、遡及的に縮小することはできません。`operation_state` のオーナーリストを確認してください。

## `UpdateRewardInfos`

純粋な簿記 — `reward_growth_global_x64` を `emissions_per_second × Δt / liquidity` を乗算することで現在の時刻に決済します。流動性に触れるすべての命令によって内部的に呼び出されます。外部アクター（UI、クランク）がそれをトリガーしたい場合があるため、スタンドアロン命令として公開されます。

## 報酬の収集

<Warning>
  **スタンドアロンの報酬収集命令はありません。** プログラムは `CollectReward` エントリポイントを公開せず、公開された IDL にもありません。
</Warning>

ポジションに対する報酬は `DecreaseLiquidity` / `DecreaseLiquidityV2` によって支払われます。ポジションを変更せずに収集するには、`liquidity = 0`、`amount_0_min = 0`、`amount_1_min = 0` で呼び出してください。報酬ボルトと受取人アカウントは `remaining_accounts` に、アクティブな報酬ごとに 3 つのグループで、`reward_token_vault(W)`、`recipient_token_account(W)`、`reward_vault_mint` の順序で入ります。

`CollectRemainingRewards` は別のもので、報酬*ファンダー*がストリームの `end_time` 後に、ポジションに割り当てられなかったトークンをスイープできます。
