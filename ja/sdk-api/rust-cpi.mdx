<Info>

| LaunchLab | はい | 確認されたクレート名なし；プログラム ソースはクローズドですが、オンチェーン IDL の内部メタデータ識別子は `raydium_launchpad` です。これはプロダクト名ではなく技術名です（[パターンの適用：LaunchLab](#applying-the-pattern-launchlab) の注意事項を参照） | [パターンの適用：LaunchLab](#applying-the-pattern-launchlab) |

## Cargo 依存関係

```toml icon="file-code"
# 両方のパブリック Raydium CPI クレートは `master` で Anchor =1.0.2 をピンしているため、
# 1 つのプログラムは両方に依存できます — 下の表を参照してください。
[dependencies]
anchor-lang     = "=1.0.2"
anchor-spl      = "=1.0.2"
raydium-cp-swap = { git = "https://github.com/raydium-io/raydium-cp-swap", branch = "master", features = ["cpi"] }
raydium-clmm    = { git = "https://github.com/raydium-io/raydium-clmm",    branch = "master", features = ["cpi"] }
# 注：Anchor 1.0 アップグレード前の古い `rev` をピンする場合（CPMM 2026-09-09、
# CLMM 2026-09-30）、その rev は anchor-lang 0.32.1 をピンします；=0.32.1 と 0.3x
# CpiContext API を使用してください — そして一度に 2 つのクレートのうち 1 つだけです。
# LaunchLab：プログラム ソースは公開されていません（reference/program-addresses を参照）。
# ポイントする git 依存関係はありません。代わりに公開されている IDL から CPI バインディングを生成してください。
# 下の「パターンの適用：LaunchLab」を参照してください。
# AMM v4 には公開されている Anchor CPI クレートがありません；その専用セクションを参照してください。
```

<Warning>
  **依存関係キーは、ターゲット リポジトリの `[package] name` と完全に一致する必要があります。ハイフンを含めて。** Cargo は、*git* 依存関係を解決する際に `raydium_cp_swap` を `raydium-cp-swap` と同等に扱いません。
</Warning>

`branch = "master"` は最新の公開ソースを追跡します；再現可能なビルドが必要な場合は、特定の `rev = "<commit>"` にピンしてください。プロトタイピングを終えたら推奨されます。`master` 上のアップストリーム アカウント レイアウト変更により、警告なしにビルドが破損する可能性があるためです。

`cpi` フィーチャー フラグにより、クレートはフル プログラムではなく CPI サーフェス（アカウント構造体 + インボーカー）のみにコンパイルされるため、バイナリが小さく保たれます。

**`anchor-lang` / `anchor-spl` はターゲット クレートがピンしているものと一致する必要があります**：

| クレート | `anchor-lang` / `anchor-spl` をピン |
|---|---|
| `raydium-cp-swap` (`master`) | `=1.0.2`、[2026-09-09 アップグレード](/ja/reference/changelog/2026-09-09-cpmm-anchor-1-and-excess-lamports)から |
| `raydium-clmm` (`master`) | `=1.0.2`、[2026-09-30 アップグレード](/ja/reference/changelog/2026-09-30-clmm-anchor-1-and-excess-lamports)から |
| アップグレード前の `rev` の各クレート | `0.32.1` |

<Warning>
  **両方のクレートを同じ Anchor ラインから取得してください。** 両方の `master` ブランチは `=1.0.2` をピンしているため、1 つのプログラムから CPMM と CLMM に CPI できます。ラインを混ぜるとビルドが破損します。例えば、`master` の `raydium-cp-swap` と Anchor 1.0 アップグレード前の `rev` にピンされた `raydium-clmm`。Cargo は 1 つのバイナリに 2 つの互換性のない Anchor トレイトのコピーをリンクする必要があります。混合ペアに固執している場合は、プログラムを 2 つに分割するか、一方の型付き CPI クレートをドロップして、その命令を手動でエンコードしてください（[AMM v4](#amm-v4-manual-instruction-construction) に示されているパターンはすべてのプログラムで機能します）。
</Warning>

<Warning>
  **Anchor 1.0 は、すべての CPI 呼び出しサイトが触れる 2 つのことを変更しました。** `0.3x` から動作する統合を移動する場合：

  - **`CpiContext::new` は `AccountInfo` ではなく `Pubkey` を取ります。** `CpiContext::new(ctx.accounts.cpmm_program.to_account_info(), accts)` は `CpiContext::new(*ctx.accounts.cpmm_program.key, accts)` になります。`new_with_signer` も同じです。構造体フィールドは `program_id: Pubkey` になりました。
  - **`Context` は 1 つのライフタイムを持ちます。4 つではなく。** `Context<'_, '_, 'info, 'info, MyProxySwap<'info>>` は `Context<'info, MyProxySwap<'info>>` になります。

  クライアント側では、`anchor-client` の `RequestBuilder::instructions()` は `Result<Vec<Instruction>>` ではなく `Vec<Instruction>` を返すようになりました（`?` をドロップしてください）。`CommitmentConfig` は `solana-sdk` から移動しました — `anchor_client` から取得してください。`spl-associated-token-account` 8.0 は新しい `spl-associated-token-account-interface` クレートからヘルパーを再エクスポートします。`get_associated_token_address` と `ID` は依然としてクレート ルート（`spl_associated_token_account::{get_associated_token_address, ID}`）で到達可能ですが、アドレス ヘルパーはそこで非推奨です — `spl-associated-token-account-interface` に直接依存し、`spl_associated_token_account_interface::address::get_associated_token_address` と `spl_associated_token_account_interface::program::ID` をインポートすることをお勧めします。`::address` と `::program` は*インターフェース* クレートのモジュールです；`spl_associated_token_account::address::…` は解決されません。
</Warning>

アカウント構造体をエンドツーエンドで配線する実行可能な CPI 例については、[`raydium-io/raydium-cpi-example`](https://github.com/raydium-io/raydium-cpi-example)（AMM v4、CPMM、CLMM をカバー）を参照してください。最新のブランチは [`anchor-0.31.0`](https://github.com/raydium-io/raydium-cpi-example/tree/anchor-0.31.0) です — Anchor 1.x ブランチはまだないため、そのリポジトリを**アカウント構造体配線**のリファレンスとして扱ってください。このページが要求するバージョン ピンではなく。

## 一般的な Anchor CPI パターン

このセクションでは、**CPMM** を実装例として、`Accounts` 構造体、`CpiContext`、`cpi::<ix>()` を順を追って説明します。CLMM も同じ形式に従いますが、アカウント リストが異なり、残りのアカウント（remaining accounts）が必要です。LaunchLab も同じメカニズムを使いますが、アカウント リストに CPMM/CLMM にはない複数のアカウント（`global_config`、`platform_config`、`event_authority`、`program`）が含まれるため、同じ*パターン*として扱いますが、同じ*形式*ではありません。このチュートリアルのアカウント リストが直接転用できると仮定せず、各プログラムのセクションを参照してください。

### アカウント リストの構築

すべての Raydium CPI には、呼び出し元プログラムに `Accounts` 構造体が必要です。そのフィールドは、*あなたの*命令が必要とするアカウントであり、フィールドレベルのバリデータを持ちます。フィールドの宣言順序は Raydium の命令アカウント順序と一致する必要はありません。あなた自身の IDL 生成クライアントが位置ではなく名前でアドレス指定するためです：

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};

#[derive(Accounts)]
pub struct MyProxySwap<'info> {
    #[account(mut)]
    pub user: Signer<'info>,

    /// CHECK: validated by CPMM
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    /// CHECK: ditto
    pub amm_config: UncheckedAccount<'info>,

    /// CHECK: ditto
    pub pool_authority: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    pub input_mint: Account<'info, Mint>,
    pub output_mint: Account<'info, Mint>,

    #[account(mut)]
    pub user_input_ata:  Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_output_ata: Account<'info, TokenAccount>,

    /// Typed as `Program<RaydiumCpSwap>` rather than `UncheckedAccount`: this account
    /// is the program being invoked, not Raydium-owned data, so Anchor's `Program<T>`
    /// wrapper checks its address automatically instead of leaving that check to the
    /// callee.
    pub cpmm_program: Program<'info, raydium_cp_swap::program::RaydiumCpSwap>,
    pub token_program: Program<'info, Token>,
    /// CHECK: observation PDA
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,
}
```

Raydium 側のアカウントのほとんどは `UncheckedAccount` です。呼び出し先（Raydium）がバリデーションを所有しているためです。呼び出し元プログラムは、ユーザー ATA やあなた自身の PDA など、*あなたが*所有するアカウントのみを厳密にバリデーションします。`/// CHECK:` ドキュメント コメントは、チェックが欠落していることについての Anchor の警告を抑制します。Raydium 側の唯一の例外は `cpmm_program` 自体です。これは Raydium が内部的にバリデーションするデータ アカウントではなく、呼び出されるプログラムであるため、`Program<T>` として型付けされ、手動の `/// CHECK:` ではなく Anchor の自動アドレス チェックを受けます。このほぼ `UncheckedAccount` の形式（Raydium が独自のアカウントをバリデーションする）は、CLMM と LaunchLab でも同じです。この例では両方のミントが従来の SPL Token であると仮定しています。どちらかが Token-2022 ミントである可能性がある場合は、`token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>` フィールドを追加し、以下の CPI 呼び出しでそちら側の `input_token_program`/`output_token_program` として `token_program` の代わりに渡してください。

### CPI 呼び出しの構築

Anchor は命令ごとに 1 つのヘルパーを生成します。これは CPI アカウント構造体（`cpi::accounts::Swap`、以下では `CpmmSwap` としてエイリアス化）と共に生成されます。上記の独自の `MyProxySwap` 構造体とは異なり、このフィールド名と順序は `raydium-cp-swap` の IDL によって固定され、正確に一致する必要があります：

```rust icon="rust"
use raydium_cp_swap::cpi::{self, accounts::Swap as CpmmSwap};

pub fn my_proxy_swap(
    ctx: Context<MyProxySwap>,
    amount_in: u64,
    minimum_amount_out: u64,
) -> Result<()> {
    let cpi_accounts = CpmmSwap {
        // `payer` is YOUR signer — it must own `input_token_account`.
        payer:                ctx.accounts.user.to_account_info(),
        // `authority` is CPMM's OWN vault PDA at seeds [b"vault_and_lp_mint_auth_seed"],
        // which CPMM signs with itself. Passing your signer here fails the
        // seeds constraint (`ConstraintSeeds`) before any transfer runs.
        authority:            ctx.accounts.pool_authority.to_account_info(),
        amm_config:           ctx.accounts.amm_config.to_account_info(),
        pool_state:           ctx.accounts.pool_state.to_account_info(),
        input_token_account:  ctx.accounts.user_input_ata.to_account_info(),
        output_token_account: ctx.accounts.user_output_ata.to_account_info(),
        input_vault:          ctx.accounts.input_vault.to_account_info(),
        output_vault:         ctx.accounts.output_vault.to_account_info(),
        input_token_program:  ctx.accounts.token_program.to_account_info(),
        output_token_program: ctx.accounts.token_program.to_account_info(),
        input_token_mint:     ctx.accounts.input_mint.to_account_info(),
        output_token_mint:    ctx.accounts.output_mint.to_account_info(),
        observation_state:    ctx.accounts.observation_state.to_account_info(),
    };
    // Anchor 1.0: the first argument is the program's Pubkey, not its AccountInfo.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.cpmm_program.key,
        cpi_accounts,
    );

    cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
    Ok(())
}
```

`cpi::swap_base_input` は IDL から生成されます。その引数リストは Anchor 命令の引数リストを反映しています。確認済みのすべての Anchor ベースの Raydium プログラム（CPMM、CLMM、LaunchLab）は、同じ方法で `cpi::<ix>()` ヘルパーを生成し、関数名は命令名をスネーク ケースで表したものと一致します。これが Farm v6 に拡張されるかどうかは未確認です。そのセクションを参照してください。

### 署名者シード（PDA 署名 CPI）

プログラムが PDA に代わって CPI に署名する場合（ボルト、エスクロー等で一般的）、`CpiContext::new_with_signer` を使用します：

```rust icon="rust"
let bump         = ctx.accounts.my_authority_bump;
let signer_seeds: &[&[&[u8]]] = &[&[b"my_authority", &[bump]]];

let cpi_ctx = CpiContext::new_with_signer(
    *ctx.accounts.cpmm_program.key,
    cpi_accounts,
    signer_seeds,
);

cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
```

署名者シードは PDA の導出と一致する必要があります。`authority`（または同様の署名者ロール）として渡されるアカウントについて、Solana ランタイムは PDA がこれらのシードを通じて署名することを確認します。

### 残りのアカウント

一部の Raydium 命令は**残りのアカウント**（remaining accounts）を取ります。これは固定アカウントの後に追加される可変長リストです。Anchor の CPI ヘルパーは残りのアカウントを型チェックしません。`.with_remaining_accounts(...)` を通じて渡してください：

```rust icon="rust"
let cpi_ctx = CpiContext::new(program_id, accounts)
    .with_remaining_accounts(ctx.remaining_accounts.to_vec());
```

受信側プログラムが渡した順序で残りのアカウントを反復処理するため、順序は常に重要です。確認済みの 2 つの順序：

- **CLMM `SwapV2`**: [ティック配列](#applying-the-pattern-clmm)、方向順。
- **Farm v6**: `(reward_vault, user_reward_ata)` ペア。ただし、2 番目のリワード ストリーム以降のみ。実際のトランザクションをデコードすると何が表示されるかについては、[Farm v6](#farm-v6) を参照してください。

## パターンの適用：CLMM

`SwapV2` は[一般的なパターン](#the-general-anchor-cpi-pattern)に従いますが、異なるアカウント リストとティック配列の残りのアカウント要件があります。クレートの `#[program]` モジュールは `raydium_clmm` という名前で、これは Rust の `use` パスでもあります。

<Warning>
  **CPI アカウント構造体は `SwapV2` ではなく `SwapSingleV2` という名前です。** `SwapV2` はオンチェーン*命令*名です。
</Warning>

```rust icon="rust"
use raydium_clmm::cpi::{self, accounts::SwapSingleV2 as ClmmSwap};

#[derive(Accounts)]
pub struct MyProxyClmmSwap<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: validated by CLMM
    pub amm_config: UncheckedAccount<'info>,
    /// CHECK: ditto
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    /// CHECK: observation PDA
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,

    pub token_program: Program<'info, Token>,
    pub token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>,
    /// CHECK: SPL memo program, required for some Token-2022 paths
    pub memo_program: UncheckedAccount<'info>,

    pub input_vault_mint: Account<'info, Mint>,
    pub output_vault_mint: Account<'info, Mint>,

    /// Typed as `Program<T>` rather than `UncheckedAccount`, same reason as CPMM's
    /// `cpmm_program` in the general pattern above: it's the invoked program, and
    /// `Program<T>` checks its address automatically.
    pub clmm_program: Program<'info, raydium_clmm::program::RaydiumClmm>,
    // remaining_accounts: tick_array_bitmap_extension (if the walk needs it), then
    // as many tick_array accounts as the swap's expected price range spans.
}
```

ティック配列リストは、固定数を推測するのではなく、SDK と同じ方法で現在のプール状態に対するクォートを通じて計算してください。渡した配列を超えるスワップは `TickArrayNotFound` で戻ります（完全なアカウント テーブルとエラー リストについては [`/ja/products/clmm/instructions`](/ja/products/clmm/instructions) を参照）。価格ウォークの方向で渡してください。スワップ方向の最初の配列を最初に渡します。

## パターンの適用：LaunchLab

LaunchLabはAnchorベースで、IDLが公開されています：公開リポジトリ `raydium-idl` の [`raydium_launchpad/raydium_launchpad.json`](https://github.com/raydium-io/raydium-idl/blob/master/raydium_launchpad/raydium_launchpad.json)。このIDLの内部メタデータ識別子は `raydium_launchpad` で、これは製品の別名ではなく、基盤となるプログラムの技術名です。ただし、CPMMやCLMMとは異なり、**プログラムのソースコード自体は公開されていません**（[`reference/program-addresses`](/ja/reference/program-addresses) を参照）。Cargoが指すような `git = "..."` 依存関係もなく、実際のクレートのRust `use` パスが何であるかを確認するソースもありません。

公開されているIDLからAnchorの `declare_program!` マクロを使用してバインディングを生成します。IDL JSONをクレート内の `idls/raydium_launchpad.json` に保存し（Cargoは `CARGO_MANIFEST_DIR` に相対的な `idls/` ディレクトリを探します）、`declare_program!(raydium_launchpad);` を実行すると、プログラムソースなしで、IDLから直接 `raydium_launchpad::cpi::accounts::<Ix>` 構造体と `cpi::<ix>()` 関数が生成されます。生成されるアカウント構造体の名前は常に命令名をPascalCaseにしたもの（`buy_exact_in` → `BuyExactIn`）で、フィールド名はIDLのアカウント名と完全に一致します。これは下記の `MyProxyBuy` で既に使用されているアカウントリストと同じです。

CPI形状は[一般的なパターン](#the-general-anchor-cpi-pattern)に従います。以下のアカウントリストと引数は、`products/launchlab/instructions.mdx` ではなく、オンチェーンIDLの `buy_exact_in` 命令から取得されます：

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};
use raydium_launchpad::cpi::{self, accounts::BuyExactIn};

#[derive(Accounts)]
pub struct MyProxyBuy<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: PDA, seeds = [b"vault_auth_seed"], validated by the program
    pub authority: UncheckedAccount<'info>,

    /// CHECK: validated by the program
    pub global_config: UncheckedAccount<'info>,
    /// CHECK: validated by the program
    pub platform_config: UncheckedAccount<'info>,

    /// CHECK: validated by the program
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub user_base_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_quote_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub base_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub quote_vault: Account<'info, TokenAccount>,

    pub base_token_mint: Account<'info, Mint>,
    pub quote_token_mint: Account<'info, Mint>,

    /// CHECK: base mint's token program (SPL Token or Token-2022, depending on the mint)
    pub base_token_program: UncheckedAccount<'info>,
    /// Typed as `Program<Token>` rather than `UncheckedAccount`: the IDL fixes this to
    /// classic SPL Token specifically (unlike base_token_program above), so Anchor's
    /// built-in address check on `Program<Token>` is sufficient on its own.
    pub quote_token_program: Program<'info, Token>,

    /// CHECK: PDA, seeds = [b"__event_authority"], required by the program's emit_cpi! pattern
    pub event_authority: UncheckedAccount<'info>,
    /// CHECK: the program's own account, required alongside event_authority
    pub program: UncheckedAccount<'info>,
}

pub fn my_proxy_buy(
    ctx: Context<MyProxyBuy>,
    amount_in: u64,
    minimum_amount_out: u64,
    share_fee_rate: u64,
) -> Result<()> {
    let cpi_accounts = BuyExactIn {
        payer:               ctx.accounts.payer.to_account_info(),
        authority:           ctx.accounts.authority.to_account_info(),
        global_config:       ctx.accounts.global_config.to_account_info(),
        platform_config:     ctx.accounts.platform_config.to_account_info(),
        pool_state:          ctx.accounts.pool_state.to_account_info(),
        user_base_token:     ctx.accounts.user_base_token.to_account_info(),
        user_quote_token:    ctx.accounts.user_quote_token.to_account_info(),
        base_vault:          ctx.accounts.base_vault.to_account_info(),
        quote_vault:         ctx.accounts.quote_vault.to_account_info(),
        base_token_mint:     ctx.accounts.base_token_mint.to_account_info(),
        quote_token_mint:    ctx.accounts.quote_token_mint.to_account_info(),
        base_token_program:  ctx.accounts.base_token_program.to_account_info(),
        quote_token_program: ctx.accounts.quote_token_program.to_account_info(),
        event_authority:     ctx.accounts.event_authority.to_account_info(),
        program:             ctx.accounts.program.to_account_info(),
    };
    // `program` doubles as the CPI target here: LaunchLab's own account is both one of
    // its instruction's required accounts (for its emit_cpi! pattern) and the program
    // CpiContext::new invokes.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.program.key,
        cpi_accounts,
    );

    cpi::buy_exact_in(cpi_ctx, amount_in, minimum_amount_out, share_fee_rate)?;
    Ok(())
}
```

卒業後、ターゲットプログラムは `pool_state.migrate_type` に応じてCPMMまたはAMM v4になります。`products/launchlab/accounts.mdx` によると、これは `Initialize` 時に設定されます。CPIアカウントリストは両方に対応するか、最初に `PoolState` から `migrate_type` を読み取って分岐する必要があります。

## エラー伝播

各AnchorベースのRaydiumプログラムは独自のエラー列挙型を返します。Anchorがそれをラップするため、呼び出し元プログラムは `Err(ProgramError::Custom(code))` として表示されます。特定のエラーを処理するには：

```rust icon="rust"
use raydium_cp_swap::error::ErrorCode as CpmmErr;

match cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out) {
    Ok(_) => Ok(()),
    Err(e) => {
        msg!("CPMM swap failed: {:?}", e);
        // Re-raise, or convert to your own error type.
        Err(e)
    }
}
```

呼び出しているプログラムに応じて関連するエラー型に置き換えます（CLMMの場合は `raydium_clmm::error::ErrorCode` など）。エラーコード番号はIDLポリシーに従って安定しています（[`sdk-api/anchor-idl`](/ja/sdk-api/anchor-idl#idl-change-policy)）。数値と比較することで特定のコードをテストできます。完全なエラーテーブル：[CPMM](/ja/reference/error-codes#cpmm-standard-amm-errors)、[CLMM](/ja/reference/error-codes#clmm-errors)、[AMM v4、Farm v6、LaunchLab](/ja/reference/error-codes#amm-v4-farm-v3-/-v5-/-v6-launchlab-errors)。

## 合成CPIのコンピュート予算

各CPIフレームにはオーバーヘッドがあり、呼び出し先独自のCU消費がそれに積み重なるため、プログラム内からRaydiumを呼び出すトランザクションには、200k CUのデフォルトに依存するのではなく、明示的なコンピュート予算が必要です。

<Note>
  **推定ではなく測定値です。** メインネット上のCPMM `swap_base_input` は、CPMMプログラム自体で **約23,000 CU** を消費します。2026年9月9日に高ボリュームプール上の8つのライブスワップでサンプリング（22,721～23,052）、`Program CPMMoo8… consumed N of M compute units` ログ行から読み取られました。比較：AMM v4スワップ約26,000、CLMM `swap` 約41,000、CLMM `swap_v2` 約48,000（43,838～52,887）、各ティッククロッシングで増加します。

  このページの以前のリビジョンでは、プロキシスワップCPIについて約47,700 CUを報告していました。その数値は*トランザクション全体*（`computeUnitsConsumed`）で、呼び出し元プログラム、CPIフレーム、およびATA設定を含みます。呼び出し先のコストではありません。どちらも有用ですが、同じ数値ではないため、同じ基準で比較してください。ドキュメントからコピーした数値ではなく、独自の測定から予算を立ててください。
</Note>

CLMMおよびLaunchLab CPIはより多くのコストがかかります（CLMMは特に `remaining_accounts` を介して追加のティック配列を走査し、配列ごとにCUを追加します）。ただし、上記のCPMM数値のみが測定値です。常に独自の測定から計算した明示的な `ComputeBudgetProgram::set_compute_unit_limit(...)` 命令を設定してください。ドキュメントからコピーした数値ではなく、デフォルトの200k CU制限は静かに枯渇し、プログラムがアップグレードされるにつれて命令ごとのコストが変わるためです。

## AMM v4：手動による命令構築

AMM v4はAnchorより前の時代のもので、CPIクレートがないため、このドキュメント内で上記の一般的なパターンに従わない唯一のプログラムです。`Instruction` を手動で構築します：

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_lang::solana_program::program::invoke_signed;
use anchor_lang::solana_program::instruction::{Instruction, AccountMeta};

const AMM_V4_PROGRAM_ID: Pubkey = pubkey!("675kPX9MHTjS2zt1qfr1NYHuzeLXfQM9H24wFSUt1Mp8");

// SwapBaseIn discriminator is 9.
let mut data = vec![9u8];
data.extend_from_slice(&amount_in.to_le_bytes());
data.extend_from_slice(&minimum_amount_out.to_le_bytes());

let ix = Instruction {
    program_id: AMM_V4_PROGRAM_ID,
    accounts: vec![
        AccountMeta::new_readonly(token_program_id, false),
        AccountMeta::new(amm_id, false),
        AccountMeta::new_readonly(amm_authority, false),
        // ... remaining accounts per products/amm-v4/instructions ...
    ],
    data,
};
invoke_signed(&ix, &account_infos, signer_seeds)?;
```

完全なアカウントリストについては、[`products/amm-v4/code-demos`](/ja/products/amm-v4/code-demos) を参照してください。

## Farm v6

**統合にそれが選択肢であれば、TS SDKを使用してください。** `raydium.farm.deposit(...)` （[`products/farm-staking/code-demos`](/ja/products/farm-staking/code-demos) を参照）は実際のデモで実行され、このプログラムに対するRust Anchorクレートが存在するかどうかに依存しません。

<Warning>
  **Farm v6はAnchor CPIパスを提供していません。** crates.ioに `raydium_farm_v6` クレートはなく、公開ソースリポジトリもなく、オンチェーンIDLもありません。プログラムはレガシー `anchor:idl` アカウントも、Program Metadataプログラムのエントリも持っていません（[`sdk-api/anchor-idl`](/ja/sdk-api/anchor-idl) を参照）。これを非Anchorプログラムとして扱い、以下のように手動で命令を構築してください。
</Warning>

**それでもRust CPIが必要な場合**、例えば別のオンチェーンプログラムから合成する場合は、[AMM v4](#amm-v4-manual-instruction-construction) と同じ方法で `Instruction` を手動で構築します。実際のアカウントリストと命令ディスクリミネータを独立して導出します。例えば、SDK TypeScriptレイアウト（`raydium-sdk-V2` のfarmモジュール）をデコードする、実際のトランザクションを直接デコードする（以下を参照）、またはデプロイされたプログラムをダンプして逆アセンブルします。

ハーベストまたはクレーム呼び出しと一致するゼロ引数命令形状の場合、実際のアカウント順序は固定プレフィックス（`token_program`、ファームの状態アカウント、ボルト権限PDA、そのPDAの最初のリワードボルト、2番目のPDA、呼び出し元、その最初のリワードミント用の呼び出し元のATA）の後に、最初の後のすべてのリワードストリームについて `remaining_accounts` の `(reward_vault_i, user_reward_ata_i)` ペアが続きます。ペアリング規則は実際のものですが、2番目のリワードストリームからのみ開始されます。最初のストリームのボルトとATAは固定アカウントで、互いに隣接していなく、`remaining_accounts` の一部ではありません。

## CPI フローのテスト

ローカル開発では、Raydium プログラムをテスト バリデーターで利用可能にする必要があります。3 つのオプションがあります：

1. **プログラム クローンを使用した `anchor test`。** メインネットにデプロイされたバイトコードをローカル バリデーターにプルします。以下の「[ローカル バリデーターへのプログラムのクローン](#ローカル-バリデーターへのプログラムのクローン)」で `Anchor.toml` の設定と、プール作成テストで特に注意が必要な 2 つの点を参照してください。
2. **Devnet。** Raydium はほとんどのプログラムを devnet にデプロイしていますが、すべてのプログラムで **mainnet とは異なるプログラム ID** を使用しています（CPMM、CLMM、AMM v4、Stable AMM、LaunchLab はそれぞれ異なる devnet アドレスを持っています。[`reference/program-addresses`](/ja/reference/program-addresses) の Devnet テーブルを参照してください）。Farm v3/v5/v6 は devnet に確実に公開されていません。ライブ API（`https://api-v3-devnet.raydium.io/main/info`）に現在の情報があります。`raydium_clmm` にバンドルされている `DEVNET_PROGRAM_ID` 定数（または他のクレートの同等物）を使用する場合、mainnet ID が devnet でも機能すると仮定しないでください。正しいアドレスを取得したら、`anchor test --provider.cluster devnet` を実行してライブ コードをテストしてください。
3. **ローカル デプロイ。** Raydium リポジトリ（CPMM、CLMM。LaunchLab のソースはこのオプションでは利用できません）をクローンし、ローカル バリデーターに `anchor deploy` します。テスト サイクルのオーバーヘッドが増えますが、デバッグのために呼び出し先を変更できます。

`anchor test` で実行するか、プログラムを変更しない場合は最初に `anchor build` を実行してから `anchor test --skip-build` を実行してください。

### ローカル バリデーターへのプログラムのクローン

```toml icon="file-code"
[test]
# Default (5s) isn't enough once you're cloning several accounts, since each is
# a sequential mainnet RPC round trip during validator startup.
startup_wait = 60000

[test.validator]
url = "https://api.mainnet-beta.solana.com"

[[test.validator.clone]]
address = "CAMMCzo5YL8w4VFF8KVHrK22GGUsp5VTaW7grrKgrWqK"  # CLMM

[[test.validator.clone]]
address = "CPMMoo8L3F4NbTegBCKVNunggL7H1ZpdTHKxQB5qKP1C"  # CPMM

[[test.validator.clone]]
address = "LanMV9sAd7wArD4vJFi2qDdfnVhFxYSUg6eADduJ3uj"   # LaunchLab

[[test.validator.clone]]
address = "FarmqiPv5eAj3j1GMdMCMUGXqPUvmquZtMy86QH6rzhG"  # Farm v6
```

これはプログラムのソースが公開されているかどうかに関わらず、プログラム ID で機能するため、LaunchLab は CPMM や CLMM と同じ方法でクローンされます。ただし、そのソースは利用できません。`reference/program-addresses` はここのすべてのアドレスの信頼できる情報源です。

<Warning>
  **プログラムをクローンするだけでは、テストが（既存のプールに対してスワップするのではなく）プールを*作成*する場合は不十分です。** CPMM の `initialize` 命令は、その `amm_config` および `create_pool_fee` アカウントをオンチェーン データに対して検証するため、それらもクローンする必要があります。そうしないと、`initialize` は完全に失敗します。CPMM の場合：必要なフィー ティアの `AmmConfig` をクローンします（`GET https://api-v3.raydium.io/main/cpmm-config` からそのアドレスを取得します。インデックス 0 は 0.25% ティアです）。また、[フィー受取人トークン アカウント](/ja/reference/program-addresses#shared-config-/-pda-conventions)は、その場で作成されるのではなく、正確なアドレスで検証されるため、既に存在する必要があります。
</Warning>

<Warning>
  **テストが作成したばかりのプールは、同じ瞬間にはスワップできません。** CPMM の `initialize` は、厳密に将来ではない要求された `open_time` をサイレントにオーバーライドします（`if open_time <= block_timestamp { open_time = block_timestamp + 1 }`）。したがって、`startTime: 0`（SDK に従って「すぐに開く」）でも、プールがスワップを受け入れるまでに実際には 1 秒以上のギャップが生じます。プールを作成してから遅延なくスワップするテストは、[`NotApproved`](/ja/reference/error-codes#cpmm-standard-amm-errors) に当たります。プール作成と最初のスワップの間に短い `await`（1～2 秒）があれば十分です。これはテスト固有です。人間が 2 つの別々のマニュアル コマンドを実行する場合、通常は気付きません。入力とプロセス起動で既に 1 秒以上かかるためです。
</Warning>
