## `Initialize2`

啟動綁定到現有 OpenBook 市場的新 AMM v4 池。

**參數**

```
open_time:    u64

init_coin_amount: u64
```

**帳戶**（可寫 `W`、簽署者 `S`）

| # | 名稱 | W | S | 備註 |
|---|------|---|---|-------|

| 2 | `associated_token_program` |   |   | 用於建立建立者的 LP ATA。 |
| 3 | `system_program` |   |   | |
| 4 | `rent` |   |   | 仍會轉發到 `initialize_account` / `initialize_mint` CPI 中 — 不要省略它。 |
| 5 | `amm` | W |   | `AmmInfo` PDA `[programId, market, "amm_associated_seed"]`；在此建立。 |

| 16 | `user_wallet` | W | S | 建立者。支付租金、建池費用和初始存款。 |
| 17 | `user_token_coin` | W |   | |
| 18 | `user_token_pc` | W |   | |
| 19 | `user_token_lp` | W |   | 建立者的 LP ATA；由程式建立。 |

<Note>
  **兩種可接受的佈局。** 上面的 19 個帳戶列表是建議的一種。為了向後相容，程式也會讀取
  一個 21 個帳戶的舊版佈局，它在位置 7 插入一個被忽略的 `amm_open_orders`，在位置 16 插入
  一個被忽略的 `market_program` — 這正是倉庫內 `initialize2` 指令建構器目前仍發出的內容。
  任何其他長度都會按舊版佈局的位置解析並失敗。
</Note>

**後置條件**

- 鑄給建立者的 LP = `sqrt(init_coin_amount × init_pc_amount) − 10^coin_mint.decimals`。LP 的小數位等於 `coin_mint.decimals`，因此被減去的數量剛好是一整個 LP 代幣；它從未被鑄造，永久退出流通。如果 `sqrt(...)` 低於該值，指令會以 `InitLpAmountTooLess` 還原。
- `AmmInfo.lp_amount` 儲存完整的 `sqrt(...)`，**而不是**已鑄造的數量 — 因此 `lp_mint.supply` 永久比 `amm.lp_amount` 少一整個 LP 代幣。所有按比例的數學都使用 `amm.lp_amount`。
- 未發佈 OpenBook 訂單（訂單簿網格已移除）。`AmmInfo.market` 記錄在插槽 15 傳入的帳戶，但 `AmmInfo.open_orders` 和 `AmmInfo.market_program` 都被寫為 `Pubkey::default()`，而 `coin_lot_size` / `pc_lot_size` / `min_size` 初始化為 `0`。在舊版的 21 個帳戶佈局上，額外的 `amm_open_orders` 和 `market_program` 帳戶會被讀取並丟棄。

**常見錯誤** — `InvalidCoinMint`（coin 和 pc 鑄幣相同）、`InvalidConfigAccount`（錯誤的 `amm_config` PDA）、`InvalidFee`（錯誤的建池費用目標）、`InvalidProgramAddress`（錯誤的 `amm_authority` 或錯誤的 `nonce`）、`RepeatCreateAmm`（此市場已存在流動性池）、`InitLpAmountTooLess`、`InvalidSupply`（任一初始數量為 `0`，或 LP 鑄幣已有供應量）、`AlreadyInUse`。

## `SwapBaseIn`

精確輸入交換。始終是**AMM 路徑**交換（不通過 OpenBook 配對路由）。

<Note>
  **新程式碼請使用 V2 變體。** 由於 AMM v4 的 OpenBook 依賴已被移除，V1 進入點（`SwapBaseIn`、`SwapBaseOut`）仍期望完整的 17 帳戶列表（或 18 個含可選的 target-orders 帳戶），但 OpenBook/市場帳戶現在**按位置被接受並忽略** — 它們不被驗證且不發出 CPI。傳遞錯誤的帳戶*數量*仍會以 `WrongAccountsNumber` 回復，但市場帳戶*內容*不再被檢查。新的整合應使用 [`SwapBaseInV2` / `SwapBaseOutV2`](#swapbaseinv2-swapbaseoutv2)，其採用更小的帳戶列表，代表當今的規範執行路徑。V1 形式在此記錄以供完整性和讀取現有鏈上交易。
</Note>

**參數**

```
amount_in:            u64
minimum_amount_out:   u64
```

**帳戶**（簡化）

| # | 名稱 | W | S |
|---|------|---|---|
| 1 | `token_program` |   |   |
| 2 | `amm` | W |   |
| 3 | `amm_authority` |   |   |
| 4 | `amm_open_orders` | W |   |
| 5 | `amm_target_orders` | W |   |
| 6 | `pool_coin_token_account` | W |   |
| 7 | `pool_pc_token_account` | W |   |
| 8 | `market_program` |   |   |
| 9 | `market` | W |   |
| 10 | `market_bids` | W |   |
| 11 | `market_asks` | W |   |
| 12 | `market_event_queue` | W |   |
| 13 | `market_coin_vault` | W |   |
| 14 | `market_pc_vault` | W |   |
| 15 | `market_vault_signer` |   |   |
| 16 | `user_source_token_account` | W |   |
| 17 | `user_dest_token_account` | W |   |
| 18 | `user_owner` |   | S |

**數學** — 見 [`products/amm-v4/math`](/zh-Hant/products/amm-v4/math)。

**前置條件**

- `AmmStatus::from_u64(amm.status).swap_permission()` 為真 — 也就是說，`status` 是 `1`（`Initialized`）、`6`（`SwapOnly`）或 `7`（`WaitingTrade`）。`status` 是列舉值，不是位元遮罩；見 [`products/amm-v4/accounts`](/zh-Hant/products/amm-v4/accounts#status)。
- `amm.state_data.pool_open_time <= now`。
- `amount_in > 0`。
- `user_source_token_account` 持有至少 `amount_in`。

**後置條件**

- 使用者失去 `amount_in` 的源代幣，獲得 `amount_out ≥ minimum_amount_out` 的目標代幣。
- 交換費用留在金庫中，提高不變式 `k`。交換**不會**觸及 `need_take_pnl_*` 計數器 — 協議 PnL 會在下一次 `Deposit`、`Withdraw` 或 `WithdrawPnl` 時根據 `k` 的差值重新計算（`Processor::calc_take_pnl`）。
- 注意：`state_data.swap_*_in_amount` / `swap_*_out_amount` 分析計數器**不再更新** — 其值已凍結。使用交易日誌進行交易量分析。

**常見錯誤** — `ExceededSlippage`、`InvalidInput`、`InvalidStatus`、`NotAllowed`（coin/pc mint 相同）。

## `MonitorStep` 和其他已移除的指令

<Warning>
  **已移除 — 不再可呼叫。** 自 2026-07 升級起，`MonitorStep`（標籤 2）已從程式移除，若被呼叫現在會**回復**（`unimplemented!`）。其用戶端建構器也已刪除。同樣適用於 `MigrateToOpenBook`（5）、`WithdrawSrm`（8）、`SimulateInfo`（12）、`AdminCancelOrders`（13）以及舊版 `Initialize`（0）/ `PreInitialize`（10）池建立進入點 — 改用 `Initialize2`。
</Warning>

歷史上，`MonitorStep` 會啟動池的 OpenBook 互動：它結算已填充的訂單（通過 OpenBook CPI 將收益從市場金庫移至池金庫）、取消陳舊訂單，並發佈新訂單以縮小 `target_orders` 和 `amm_open_orders` 之間的差距。隨著 OpenBook 依賴的移除，沒有任何東西需要啟動，該指令已消失。任何仍呼叫它的守護程式或整合必須移除該呼叫。

## `SetParams`

管理員參數變更，由 Raydium 多簽呼叫。參數是 `param: u8` 標籤 + 負載。

<Warning>
  **破壞性變更（僅限管理員）。** 帳戶列表被減少到僅 `[amm (W), admin (S)]`（權限、open-orders、target-orders、金庫和所有市場帳戶被移除）。`param` 列舉被**重新編號和修剪**：`Status` = 0、`State` = 1、`Fees` = **2**（曾為 9）、`SetOpenTime` = **3**（曾為 11）。所有訂單簿網格參數和 `AmmOwner`、`LastOrderDistance`、`UpdateOpenOrder` 被移除，`SetParamsInstruction` 結構體刪除了 `new_pubkey` 和 `last_order_distance`。管理員工具必須更新。

## `CreateConfigAccount` / `UpdateConfigAccount`

程式級 `AmmConfig` PDA（種子 `["amm_config_account_seed"]`）的管理員管理。該帳戶恰好持有三個有意義的欄位 — `pnl_owner`、`cancel_owner` 和 `create_pool_fee` — 加上兩個保留的填充區域；沒有池建立標誌。`UpdateConfigAccount` 以 `param = 0` 設定 `pnl_owner`，以 `param = 1` 設定 `cancel_owner`，以 `param = 2` 設定 `create_pool_fee`。

<Note>
  **在 2026-09 中變更，向後相容。** `CreateConfigAccount` 不再讀取租金系統變數。其帳戶列表現在是 **4 個帳戶**，從 5 個下降：

  | # | 名稱 | W | S |
  |---|------|---|---|
  | 1 | `admin` | W | S |
  | 2 | `amm_config` | W |   |
  | 3 | `pnl_owner` |   |   |
  | 4 | `system_program` |   |   |

  程式從 `Rent::get()` 讀取租金參數，而不是反序列化傳入的系統變數帳戶 — 這是 Solana 3.0 依賴升級使其自然的做法。

  被移除的帳戶是列表中的**最後一個**，處理器通過 `next_account_info` 按位置讀取其帳戶，無長度檢查。因此，仍傳遞舊 5 帳戶列表的現有管理員工具保持工作：尾部租金帳戶根本不被讀取。在方便時更新它，不是緊急的。`UpdateConfigAccount` 不變。
</Note>

`Initialize2` 在位置 3 保持租金系統變數，並仍**使用**它：程式停止在其上呼叫 `Rent::from_account_info`，但它仍被轉發到建立池金庫和 LP mint 的 `spl_token::initialize_account` 和 `initialize_mint` CPI。不要從帳戶列表中刪除它。

## `WithdrawExcessLamports`

從程式控制的帳戶清掃坐在租金豁免最低額上方的 lamport。在 2026-09 升級中新增，以恢復 [SIMD-0437 租金減少](/zh-Hant/solana-fundamentals/rent-and-reclaimable-rent)在每個步驟之前建立的帳戶上留下的過度資金。

它僅移動超額。代幣餘額、帳戶資料、所有者和池狀態保持不變，指令在已在最低額的帳戶上是無操作 — 所以重複發火和在每個推出步驟後再次發火是安全的。

**參數** — 無。負載是單個標籤位元組 `18`。

**帳戶**

| # | 名稱 | W | S | 備註 |
|---|------|---|---|------|
| 1 | `collect_lamports` | W | S | 每個清掃 lamport 的目標。必須等於叢集的 collect-lamports 錢包 — 見 [`reference/program-addresses`](/zh-Hant/reference/program-addresses#excess-lamports-collection-wallets)。任何其他簽署者以 `InvalidSignAccount` 失敗。 |
| 2 | `amm_authority` |   |   | 單一 AMM v4 權限 PDA，由程式從 `["amm authority"]` 以固定 nonce 254 重新衍生。它簽署代幣程式 CPI。 |
| 3 | `token_program` |   |   | **SPL Token。** 根據 `spl_token::id()` 檢查；錯誤值以 `InvalidSplTokenProgram` 失敗。 |
| 4.. | 源帳戶 | W |   | `M` 個要清掃的帳戶，任何數量，任何順序。 |

**每個源帳戶的處理方式**

程式根據源帳戶的 `owner` 分派：

| 源帳戶所有者 | 處理 |
|---|---|
| SPL Token，`data_len == 165`（代幣帳戶），非原生 | CPI `WithdrawExcessLamports`（代幣程式判別式 `38`），由 `amm_authority` 簽署。 |
| SPL Token，`data_len == 165`，原生（wSOL） | `WithdrawExcessLamports` 不能用於原生帳戶。程式 CPI `SyncNative`，測量包裝 `amount` 增長多少，`UnwrapLamports`（判別式 `45`）恰好那個差值，然後斷言包裝餘額回到其同步前值 — 否則 `LamportsCalculateError`。池的 SOL 邊流動性因此永遠不被觸及。 |
| SPL Token，任何其他大小（LP mint） | CPI `WithdrawExcessLamports`，由 `amm_authority` 簽署。 |
| AMM v4 程式本身（`AmmInfo`、`TargetOrders`、`AmmConfig`） | 程式直接將帳戶扣除到 `rent.minimum_balance(data_len)`。 |
| 任何其他 | **靜默跳過。** 無錯誤，無 lamport 移動。 |

**常見錯誤** — `InvalidSignAccount`（錯誤簽署者）、`InvalidSplTokenProgram`（槽 3 中的錯誤程式）、`InvalidProgramAddress`（錯誤 `amm_authority`）、`LamportsCalculateError`（自訂程式碼 `60`；wSOL 往返未淨為零）和來自程式擁有路徑的 `InsufficientFunds`，當帳戶持有少於其自身租金最低額時。

**無 SDK 建構器。** `@raydium-io/raydium-sdk-v2` 不提供此指令的建構器，`raydium-sdk-V2-demo` 儲存庫也不提供 — 這是管理員路徑。手動編碼，就像 [`solana-fundamentals/rent-and-reclaimable-rent`](/zh-Hant/solana-fundamentals/rent-and-reclaimable-rent#building-the-instruction) 中的錢包邊清掃對代幣程式指令所做的那樣。
