CPMM 的創作者費用一直完全流向資金池創作者。此版本讓協議保留其中一部分 — 可按費用等級或按費用等級的創作者協商 — 而不改變費用的收費方式。

保持影響範圍小的設計選擇：**分割發生在收取時，而非交換時。** 交換仍然收取 `creator_fee_rate` 並將整個金額累積到 `creator_fees_token_{0,1}`。當 `CollectCreatorFee` 或 `CollectCreatorFeePermissionless` 運行時，累積的餘額被分割，協議的部分在同一資金池上被重新標記為協議費用，只有創作者的部分離開金庫。報價、曲線、`k` 和每個 LP 面向的路徑都不受影響。

## 分割如何工作

解析，按優先順序：

1. **`CreatorFeeShare` PDA** 在 `["creator_fee_share", creator, amm_config]` — 當帳戶存在且由 CPMM 擁有時，其 `share_rate` 獲勝。
2. **`AmmConfig.creator_fee_share_rate`** — 費用等級的預設值，否則使用。

兩者都是 `u64` 超過 `FEE_RATE_DENOMINATOR_VALUE = 1_000_000`，兩者都根據該上限進行檢查。然後，按每個代幣側：

```rust
// states/creator_fee_share.rs
shared_amount  = floor(creator_fee * share_rate / 1_000_000);
creator_amount = creator_fee - shared_amount;
```

```rust
// states/pool.rs — PoolState::settle_creator_fee
self.protocol_fees_token_i = self.protocol_fees_token_i.checked_add(shared_amount_i)?;
self.creator_fees_token_i  = 0;
// creator_amount_i is returned and transferred out to the creator
```

程式測試確定的三個屬性：

- **四捨五入有利於創作者。** 份額向下取整，所以塵埃留給創作者 — 與 `Fees::protocol_fee` 和 `Fees::fund_fee` 相同方向，它們也從已累積的費用中分割份額。1 單位費用的 20% 是 0，不是 1。
- **價值守恆。** 對於每個費率和每個費用直到 `u64::MAX`，`creator_amount + shared_amount == creator_fee`。
- **`share_rate = 0` 完全是舊行為。** 預設配置值和缺失的 PDA 都給創作者整個費用，所以在管理員設置費率之前，任何現有資金池都不會改變。

因為 `protocol_fees_token*` 和 `creator_fees_token*` 都已在 `vault_amount_without_fee` 中扣除，在它們之間移動價值不會改變曲線對金庫的看法。沒有 LP 會在創作者費用收取中看到價格變化，`k` 檢查未改動。

<Note>
  **費率在收取時讀取，而非在累積時。** 在費率為 `0` 時累積的費用在最終有人調用 `Collect*` 時以任何有效的費率結算。沒有按時期或按交換的快照。
</Note>

## `CreateCreatorFeeShare` 和 `CloseCreatorFeeShare`

```rust
pub struct CreatorFeeShare {
    pub bump: u8,
    pub creator: Pubkey,
    pub amm_config: Pubkey,
    pub share_rate: u64,
    pub padding: [u64; 8],
}
// CreatorFeeShare::LEN == 145
```

`CreateCreatorFeeShare(share_rate: u64)` 初始化 PDA；`CloseCreatorFeeShare` 關閉它並將租金返還給簽署者。兩者都接受共享程式管理員**或**專用創作者費用分享所有者 — 一個新的硬編碼密鑰對，遵循與程式其他委派權限相同的 devnet/mainnet `cfg` 模式。地址在 [`reference/program-addresses`](/zh-Hant/reference/program-addresses#cpmm-creator-fee-share-authority)。

值得注意的要點：

- **資金池創作者不是任何指令的一方**，也不簽署。`creator` 帳戶未檢查 — PDA 可以為尚未擁有資金池的密鑰創建。
- **一個帳戶涵蓋一個 `(creator, amm_config)` 對**，所以它管理該創作者在該費用等級上擁有的每個資金池。在兩個等級上擁有資金池的創作者需要兩個帳戶才能在兩者上被覆蓋。
- **沒有更新路徑。** 對同一對的第二次創建失敗；要改變費率，關閉並重新創建。

## `UpdateAmmConfig` 參數 8

```rust
Some(8) => update_creator_fee_share_rate(amm_config, value),   // asserts value <= 1_000_000
```

設置費用等級的預設份額。它與 `protocol_fee_rate`（參數 `1`）無關，後者分割**交易**費用 — 在管理工具中值得小心的一點，因為兩者看起來相似，都落入 `protocol_fees_token*`。

## 搭便車

**`CollectExcessLamports` 排序修復。** 指令現在對 `remaining_accounts` 進行兩次傳遞 — 每個代幣程式 CPI 首先，然後是 CPMM 擁有的 PDA 的直接扣款 — 而不是按調用者順序分派。當 PDA 在 CPI 之前被扣款時，交錯會因執行時的 `UnbalancedInstruction`（「指令前後帳戶餘額之和不匹配」）而中止，因為調用者的待處理 lamport 變更只在 CPI 實際執行的帳戶中刷新。指令的介面未改變；調用者仍以任何順序傳遞來源，現在這確實是安全的。

**可驗證構建元資料。** 工作區 `Cargo.toml` 聲明 `[workspace.metadata.cli] solana = "3.1.10"`，所以可驗證構建解析程式構建時使用的相同 Solana CLI。沒有鏈上影響。
