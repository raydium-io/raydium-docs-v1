## AMM v4 — 狀態與發展方向

AMM v4 是原始的 Raydium 池設計：恆定乘積定價（`x · y = k`）。它最初以混合 AMM 的形式推出，整合了 OpenBook（前身為 Serum）訂單簿，將曲線的部分內容鏡像為綁定市場上的限價單。**OpenBook 整合已被停用** — 池不再與 OpenBook 共享流動性，所有交換純粹透過 V2 交換端點針對曲線執行。如今 AMM v4 實際上是一個純恆定乘積 AMM，OpenBook 帳戶保留為非活躍狀態。

### 已凍結的內容

- **不再新增費用層級。** AMM v4 的費用結構是按池設定的，在部署時確定。新池接受相同的硬編碼 ~0.25% 交易費，~12% 流向協議。
- **無新功能開發。** 自 CPMM 成為新預設選項以來，團隊未曾向 AMM v4 添加新指令。該程式處於維護模式 — 僅修復錯誤，無範圍擴展。
- **不支援 Token-2022。** AMM v4 在 Token-2022 出現之前編寫，整合從未進行改造。Token-2022 鑄幣必須使用 CPMM（或適當情況下使用 CLMM）。
- **OpenBook 整合已停用。** 每個 AMM v4 池仍在鏈上綁定到相應的 OpenBook 市場帳戶，但池不再在該市場上發佈或維護訂單。OpenBook 中斷不再影響 AMM v4 交換。

### 仍在運作的內容

- **現有池正常交易。** 未強制進行狀態遷移；2021 年創建的 v4 池在 2026 年仍是許多高交易量交易對的活躍場所。
- **流動性提供者可以照常存入、提取和收穫農場獎勵。** 遷移至 CPMM 是可選的。
- **聚合器仍透過它路由。** Jupiter 和 Raydium Trade API 都將 v4 池索引為一級場所。

### 何時仍應使用 AMM v4

老實說：很少。v4 是更好選擇的情況很少見：

- 該交易對已有深度良好、交易活躍的 v4 池，你想向現有深度添加流動性，而不是分割市場。

（OpenBook 整合路由不再是選擇 AMM v4 的理由 — 該整合已關閉。）

在所有其他情況下，**在 CPMM 上啟動新池。** 請參閱 [`user-flows/choosing-a-pool-type`](/zh-Hant/user-flows/choosing-a-pool-type) 以了解完整的決策樹。

## CPMM — 採用曲線與 v4 → CPMM 遷移

CPMM（恆定乘積做市商，內部名稱 `raydium-cp-swap`）於 2024 年部署，是一個乾淨的重寫，旨在成為新的預設恆定乘積池。它在結構上是 Raydium 程式中最簡單的：純 `x · y = k`、無訂單簿、原生 Token-2022 支援、更小的交易足跡。

### CPMM 相比 AMM v4 的優勢

- **預設流動性提供者經濟學更優。** CPMM 的預設 AmmConfig 將 100% 的交易費路由給流動性提供者（協議費可按層級切換）。AMM v4 硬編碼 ~12% 流向協議。
- **更低的池創建成本。** 無需 OpenBook 市場。創建是一筆交易，~0.15 SOL 租金 vs v4 的 ~0.6 SOL。
- **Token-2022。** 轉帳費鑄幣、轉帳掛鉤鑄幣（有注意事項）、機密轉帳 — 所有這些都在 CPMM 上支援，v4 上都不支援。
- **更清晰的整合者介面。** CPMM 有一個 Anchor-CPI 友好的已發佈 crate（`raydium-cp-swap`）、更簡單的帳戶列表和穩定的 IDL。AMM v4 附帶 IDL 但從未有維護的 Rust CPI crate。
- **每次交換的帳戶列表更小。** ~10 個帳戶 vs v4 的 ~17 個（即使不使用 OpenBook 市場帳戶也會攜帶）。

### 何時值得遷移

對於交易活躍的池，流動性提供者費用提升本身通常在幾個月內就能證明遷移的合理性。算術如下：一個每日交易量為 \$X 的池在 v4 上賺取 0.25% × \$X，其中 0.03% 流向協議（缺少的 12%）。在 CPMM 上，這部分返回給流動性提供者。一年內，這會產生有意義的複利。

對於低交易量的池，遷移更多是關於面向未來 — 更好的預設、如果需要可使用 Token-2022 支援、更容易的整合。

### 遷移如何運作

沒有原地升級。遷移是一個*創建新池、排空舊池、填充新池*的序列。完整的逐步說明在 [`user-flows/migrate-amm-v4-to-cpmm`](/zh-Hant/user-flows/migrate-amm-v4-to-cpmm)；高層次的形狀：

1. 為相同的交易對創建新的 CPMM 池，使用你想保留的相同費用層級。
2. 協調流動性提供者：宣佈一個時間窗口，在此期間舊池被排空，新池被填充。
3. 每個流動性提供者從 v4 池提取並存入新的 CPMM 池。
4. （可選）設置 CPMM 端農場以吸引激勵流動性提供者進入新池。
5. 觀察交易量遷移，因為聚合器重新加權以偏向更深的池。

鏈本身不強制執行任何這些 — Raydium 的 API 和前端只是偏向更深的池，聚合器路由通過對用戶最便宜的池。

## CLMM — 單一程式，版本間穩定

CLMM 處於其第一個程式版本。沒有 v2 — 改進已作為對同一程式 ID 的原地升級發佈（在 24 小時時間鎖定多簽後面），而不是作為新代。

這意味著**沒有 CLMM 遷移故事**：現有頭寸保留在原地，當升級發佈時程式的行為可能會略微改變，但帳戶佈局和 PDA 是穩定的。

CLMM 升級中已改變的內容：

- **`SwapV2` 指令**已添加以正確支援 Token-2022 轉帳費數學。舊的 `Swap` 仍可調用；新整合應針對 `SwapV2`。
- **獎勵流擴展** — `RewardInfo` 槽位計數已提升（原始 3 → 目前仍為 3，但預留模式已收緊）。無需數據遷移。
- **Tick 陣列壓縮** — 內部優化以減少交換跨越許多 tick 時的 CU。外部不可見。
- **Anchor 1.0 重建（2026-09-30）**：從 Anchor `0.32.1` 移至 `1.0.2` 並添加管理員 `CollectExcessLamports`。無用戶面向指令或帳戶佈局改變。請參閱 [changelog 條目](/zh-Hant/reference/changelog/2026-09-30-clmm-anchor-1-and-excess-lamports)。

IDL 位於專用的 [`raydium-idl`](https://github.com/raydium-io/raydium-idl/blob/master/raydium_clmm/raydium_clmm.json) 儲存庫（請參閱 [`sdk-api/anchor-idl`](/zh-Hant/sdk-api/anchor-idl)）。如果你針對當前程式運行較舊的 SDK，最壞的情況是缺少新指令。

## Farm v3 → v5 → v6

在所有 Raydium 程式中，Farm 有最明確的版本歷史和唯一的強制遷移路徑。三代是具有單獨程式 ID 和單獨狀態佈局的單獨程式。

### 代

| 版本 | 發佈時間 | 狀態 | 主要功能 |
|---------|----------|--------|---------------|
| **v3** | 2021 | **逐步淘汰。** 現有農場運行；不接受新農場。 | 單一獎勵流。基於槽位的發放。 |
| **v5** | 2022 年 10 月 | **逐步淘汰。** 現有農場運行；不接受新農場。 | 最多 2 個獎勵流。基於槽位的發放。整數 `per_second`。 |
| **v6** | 2024 | **目前版本。** 所有新農場。 | 最多 5 個獎勵流。牆鐘發放。Q64.64 定點 `per_second`。Token-2022 質押 + 獎勵支援。 |

### 為什麼存在三代

- **v3 → v5**：需要多個並發獎勵流（例如，雙激勵農場）。v3 的單流設計無法在不重新設計的情況下支援它。
- **v5 → v6**：v5 的 `u64` 整數發放率將最小可表達率上限設為「每秒 1 個代幣單位」。對於 9 位小數的鑄幣，這是 1 lamport/秒 — 對於低發放程式來說太粗糙了。v6 的 Q64.64 分數率修復了這個問題。v6 還將基於槽位的更新提升為牆鐘，並添加了 Token-2022 支援。

### 各代間保持不變的內容

- 「存入 LP、累積每股計數器、在提取時領取」的會計模式在 v3/v5/v6 中是相同的。數學不變；只有費率計數器的精度和支援的流數量改變。
- `UserStake`（v3/v5）和 `UserLedger`（v6）在概念上是相同的記錄，佈局不同。SDK 規範化兩者。

### 遷移路徑

農場版本間沒有原地遷移。要從 v3/v5 移至 v6：

1. 等待現有農場的發放結束（或運行完成）。
2. 質押者在舊農場上提取並領取待領獎勵。
3. 農場運營者針對相同的質押鑄幣創建新的 v6 農場。
4. 質押者重新質押進入新農場。

鏈上的現實是兩個不相關的農場帳戶。在兩個農場中都有質押的用戶有兩個 `UserLedger`（v6）/ `UserStake`（v5）記錄。

### v3 和 v5 的「逐步淘汰」意味著什麼

- v3 和 v5 程式仍已部署且可調用。現有農場仍可分配待領獎勵並接受提取。
- Raydium UI 仍會顯示具有活躍獎勵的 v3 和 v5 農場；一旦 v3/v5 農場的 `end_time` 通過，UI 會將其從「活躍」中隱藏，但保持可領取。
- 團隊不會創建新的 v3/v5 農場。「創建農場」的 SDK 幫助程式僅路由至 v6。
- v3 和 v5 *接收安全升級但不進行功能工作*。如果發現關鍵錯誤，會進行修復；如果功能可能有用，會改為添加到 v6。

每個版本的完整詳細信息在 [`products/farm-staking/accounts`](/zh-Hant/products/farm-staking/accounts) 和 [`products/farm-staking/instructions`](/zh-Hant/products/farm-staking/instructions)。

## LaunchLab — 單一程式，不斷演進的配置

LaunchLab 處於其第一個程式版本。與 CLMM 一樣，改進作為 24 小時時間鎖定後面的原地升級發佈 — 而不是作為新代。

通過升級已演進的內容：

- **創建者費用槽位。** 已添加以便啟動可將啟動後 CPMM 交易費的一部分路由給原始創建者。請參閱 [`products/launchlab/creator-fees`](/zh-Hant/products/launchlab/creator-fees)。
- **曲線公式可配置性。** 原本硬編碼為二次；現在 `LaunchConfig` 從一小組曲線形狀中選擇。

現有的 LaunchLab 啟動不受升級影響 — 一旦啟動被初始化，其參數在畢業前被凍結。

## 跨程式版本相容性

整合者經常遇到的幾個跨產品相容性注意事項：

- **CLMM `SwapV2` 與 `Swap` 指令不同。** 如果你的客戶端僅支援 `Swap`，它會無聲地誤處理 Token-2022 轉帳費 — 數學會因費用金額而出錯。更新至 `SwapV2`。
- **Farm v6 質押與 CLMM 頭寸**不像 LP 代幣質押那樣受支援。CLMM 頭寸是 NFT，不是可互換的 LP 代幣。CLMM 改為有自己的原生獎勵機制 — 請參閱 [`products/clmm/fees`](/zh-Hant/products/clmm/fees)。
- **由 Token-2022 鑄幣支援的 CPMM 池僅在 Farm v6 上的農場中工作。** v3 和 v5 拒絕 Token-2022 質押鑄幣。
- **AMM v4 池從不有 Token-2022 LP 鑄幣。** 如果你看到一個，它是假的 — AMM v4 不支援該組合。
