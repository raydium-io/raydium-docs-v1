CPI ("cross-program invocation") é o mecanismo pelo qual um programa Solana chama outro. A maioria dos programas Raydium fornece crates wrapper CPI Anchor que fazem o local da chamada parecer uma chamada de função tipada, com structs de conta que têm nomes de campo validados e helpers `cpi::<ix>()`. Esta página documenta o padrão geral uma vez, depois as diferenças por programa. Para exemplos TypeScript executáveis, veja a página `code-demos` de cada capítulo de produto.

## Qual padrão se aplica a qual programa

| Programa | Baseado em Anchor | Crate | Onde |
|---|---|---|---|
| CPMM | Sim | `raydium-cp-swap` (repo público; caminho Rust `use` é `raydium_cp_swap`) | [O padrão geral](#o-padrão-geral-de-cpi-anchor), o exemplo trabalhado |
| CLMM | Sim | `raydium-clmm` (repo público; caminho Rust `use` é `raydium_clmm`) | [Aplicando o padrão: CLMM](#aplicando-o-padrão-clmm) |
| LaunchLab | Sim | nome de crate não confirmado; fonte do programa é fechada, mas o identificador de metadados interno do IDL on-chain é `raydium_launchpad`, um nome técnico em vez do nome do produto (veja a ressalva em [Aplicando o padrão: LaunchLab](#aplicando-o-padrão-launchlab)) | [Aplicando o padrão: LaunchLab](#aplicando-o-padrão-launchlab) |
| Farm v6 | Não confirmado; nenhum IDL público ou fonte encontrada (veja o aviso em [Farm v6](#farm-v6)) | n/a | [Farm v6](#farm-v6) |
| AMM v4 | **Não**, anterior ao Anchor sem crate CPI | nenhum | [AMM v4](#amm-v4-construção-manual-de-instrução) |

Se você está integrando CPMM, CLMM ou LaunchLab, leia [o padrão geral](#o-padrão-geral-de-cpi-anchor) primeiro, depois pule para a seção do seu programa para a lista de contas e quaisquer diferenças. Farm v6 e AMM v4 são diferentes o suficiente para justificar ler suas seções de forma independente.

## Dependências Cargo

```toml icon="file-code"
# Escolha UM dos dois crates CPI Raydium por programa — veja o aviso abaixo.
[dependencies]
anchor-lang     = "=1.0.2"   # =0.32.1 se você está direcionando raydium-clmm em vez disso
anchor-spl      = "=1.0.2"   # =0.32.1 igualmente
raydium-cp-swap = { git = "https://github.com/raydium-io/raydium-cp-swap", branch = "master", features = ["cpi"] }
# raydium-clmm  = { git = "https://github.com/raydium-io/raydium-clmm",    branch = "master", features = ["cpi"] }
# LaunchLab: fonte do programa não está disponível publicamente (veja reference/program-addresses).
# Não há dependência git para apontar. Gere bindings CPI do IDL publicado
# em vez disso. Veja "Aplicando o padrão: LaunchLab" abaixo.
# AMM v4 não tem crate CPI Anchor publicado; veja sua própria seção.
```

<Warning>
  **A chave de dependência deve corresponder exatamente ao `[package] name` do repo de destino, hífens inclusos.** Cargo não trata `raydium_cp_swap` como equivalente a `raydium-cp-swap` ao resolver uma dependência *git*.
</Warning>

`branch = "master"` rastreia a fonte publicada mais recente; fixe em um `rev = "<commit>"` específico se você precisar de uma compilação reproduzível. Isso é recomendado uma vez que você passou do prototipagem, já que uma mudança de layout de conta upstream em `master` quebrará sua compilação sem aviso.

O sinalizador de feature `cpi` faz os crates compilarem apenas para a superfície CPI (structs de conta + invocadores) em vez do programa completo, então seu binário fica pequeno.

**`anchor-lang` / `anchor-spl` devem corresponder ao que o crate de destino fixa**, e a partir de 2026-09 os dois crates públicos Raydium **não concordam**:

| Crate | Fixa `anchor-lang` / `anchor-spl` |
|---|---|
| `raydium-cp-swap` | `=1.0.2` (era `0.32.1` antes da [atualização de 2026-09-09](/pt/reference/changelog/2026-09-09-cpmm-anchor-1-and-excess-lamports)) |
| `raydium-clmm` | `=0.32.1` |

<Warning>
  **Você não pode depender de ambos os crates de um programa agora.** Cada um fixa Anchor com `=`, então Cargo teria que vincular duas cópias incompatíveis dos traits Anchor em um binário, e a compilação falha. Se seu programa faz CPI em CPMM e CLMM, você tem que dividir em dois programas, ou descartar o crate CPI tipado para um deles e codificar manualmente essa instrução (o padrão mostrado para [AMM v4](#amm-v4-construção-manual-de-instrução) funciona para qualquer programa). Verifique novamente ambos os arquivos `Cargo.toml` antes de começar — espera-se que isso seja resolvido quando CLMM se mover para Anchor 1.x.
</Warning>

<Warning>
  **Anchor 1.0 mudou duas coisas que cada local de chamada CPI toca.** Se você está movendo uma integração funcional de `0.3x`:

  - **`CpiContext::new` recebe um `Pubkey`, não um `AccountInfo`.** `CpiContext::new(ctx.accounts.cpmm_program.to_account_info(), accts)` se torna `CpiContext::new(*ctx.accounts.cpmm_program.key, accts)`. O mesmo para `new_with_signer`. O campo struct agora é `program_id: Pubkey`.
  - **`Context` tem uma lifetime, não quatro.** `Context<'_, '_, 'info, 'info, MyProxySwap<'info>>` se torna `Context<'info, MyProxySwap<'info>>`.

  No lado do cliente, `anchor-client`'s `RequestBuilder::instructions()` agora retorna `Vec<Instruction>` em vez de `Result<Vec<Instruction>>` (remova o `?`), e `CommitmentConfig` saiu de `solana-sdk` — pegue de `anchor_client` em vez disso. `spl-associated-token-account` 8.0 também moveu seus helpers: `get_associated_token_address` agora está sob `::address`, e o ID do programa é `::program::ID`.
</Warning>

Para exemplos CPI funcionais que conectam os structs de conta de ponta a ponta, veja [`raydium-io/raydium-cpi-example`](https://github.com/raydium-io/raydium-cpi-example) (cobre AMM v4, CPMM e CLMM).

## O padrão geral de CPI Anchor

Esta seção percorre **CPMM** de ponta a ponta como o exemplo trabalhado: struct `Accounts`, `CpiContext`, `cpi::<ix>()`. CLMM segue a forma idêntica, com uma lista de contas diferente e um requisito de contas restantes. LaunchLab segue a mesma mecânica, mas sua lista de contas carrega várias contas sem equivalente CPMM/CLMM (`global_config`, `platform_config`, `event_authority`, `program`), então trate como o mesmo *padrão*, não a mesma *forma*. Veja a seção própria de cada programa em vez de assumir que a lista de contas deste passo a passo se transfere diretamente.

### Construção de lista de contas

Todo CPI Raydium requer um struct `Accounts` no programa chamador. Seus campos são quaisquer contas que *sua* instrução precisa, com validadores no nível do campo; sua ordem de declaração não precisa corresponder à ordem de contas da instrução própria do Raydium, já que seu próprio cliente gerado por IDL as endereça por nome, não por posição:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};

#[derive(Accounts)]
pub struct MyProxySwap<'info> {
    #[account(mut)]
    pub user: Signer<'info>,

    /// CHECK: validado por CPMM
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    /// CHECK: idem
    pub amm_config: UncheckedAccount<'info>,

    /// CHECK: idem
    pub pool_authority: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    pub input_mint: Account<'info, Mint>,
    pub output_mint: Account<'info, Mint>,

    #[account(mut)]
    pub user_input_ata:  Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_output_ata: Account<'info, TokenAccount>,

    /// Tipado como `Program<RaydiumCpSwap>` em vez de `UncheckedAccount`: esta conta
    /// é o programa sendo invocado, não dados de propriedade Raydium, então o wrapper
    /// `Program<T>` do Anchor verifica seu endereço automaticamente em vez de deixar
    /// essa verificação para o chamado.
    pub cpmm_program: Program<'info, raydium_cp_swap::program::RaydiumCpSwap>,
    pub token_program: Program<'info, Token>,
    /// CHECK: PDA de observação
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,
}
```

A maioria das contas do lado Raydium são `UncheckedAccount` porque o chamado (Raydium) possui a validação. Seu programa chamador apenas valida estritamente contas que *você* possui, como ATAs de usuário e seus próprios PDAs. O comentário de doc `/// CHECK:` suprime o aviso do Anchor sobre verificações ausentes. A exceção do lado Raydium é o próprio `cpmm_program`: é o programa sendo invocado em vez de uma conta de dados que Raydium valida internamente, então é tipado `Program<T>` e recebe a verificação de endereço automática do Anchor em vez de um `/// CHECK:` manual. Esta forma principalmente `UncheckedAccount`, onde Raydium valida suas próprias contas, é a mesma para CLMM e LaunchLab. Este exemplo assume que ambos os mints são Token SPL clássico; se qualquer um dos lados puder ser um mint Token-2022, adicione um campo `token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>` e passe-o como `input_token_program`/`output_token_program` desse lado na chamada CPI abaixo em vez de `token_program`.

### Construindo a chamada CPI

Anchor gera um helper por instrução, junto com um struct de contas CPI (`cpi::accounts::Swap`, aliasado `CpmmSwap` abaixo). Diferentemente do seu próprio struct `MyProxySwap` acima, os nomes e ordem dos campos deste são fixos pelo IDL próprio de `raydium-cp-swap` e têm que corresponder exatamente:

```rust icon="rust"
use raydium_cp_swap::cpi::{self, accounts::Swap as CpmmSwap};

pub fn my_proxy_swap(
    ctx: Context<MyProxySwap>,
    amount_in: u64,
    minimum_amount_out: u64,
) -> Result<()> {
    let cpi_accounts = CpmmSwap {
        payer:                ctx.accounts.user.to_account_info(),
        authority:            ctx.accounts.user.to_account_info(),
        amm_config:           ctx.accounts.amm_config.to_account_info(),
        pool_state:           ctx.accounts.pool_state.to_account_info(),
        input_token_account:  ctx.accounts.user_input_ata.to_account_info(),
        output_token_account: ctx.accounts.user_output_ata.to_account_info(),
        input_vault:          ctx.accounts.input_vault.to_account_info(),
        output_vault:         ctx.accounts.output_vault.to_account_info(),
        input_token_program:  ctx.accounts.token_program.to_account_info(),
        output_token_program: ctx.accounts.token_program.to_account_info(),
        input_token_mint:     ctx.accounts.input_mint.to_account_info(),
        output_token_mint:    ctx.accounts.output_mint.to_account_info(),
        observation_state:    ctx.accounts.observation_state.to_account_info(),
    };
    // Anchor 1.0: o primeiro argumento é a Pubkey do programa, não seu AccountInfo.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.cpmm_program.key,
        cpi_accounts,
    );

    cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
    Ok(())
}
```

`cpi::swap_base_input` é gerado do IDL; sua lista de argumentos espelha a lista de argumentos da instrução Anchor. Todo programa Raydium baseado em Anchor confirmado (CPMM, CLMM, LaunchLab) gera seus helpers `cpi::<ix>()` da mesma forma, com o nome da função correspondendo ao nome da instrução em snake_case. Se isso se estende a Farm v6 é não confirmado; veja sua seção.

### Sementes de assinante (CPI assinado por PDA)

Quando seu programa assina o CPI em nome de um PDA (comum para vaults, escrows, etc.), use `CpiContext::new_with_signer`:

```rust icon="rust"
let bump         = ctx.accounts.my_authority_bump;
let signer_seeds: &[&[&[u8]]] = &[&[b"my_authority", &[bump]]];

let cpi_ctx = CpiContext::new_with_signer(
    *ctx.accounts.cpmm_program.key,
    cpi_accounts,
    signer_seeds,
);

cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
```

As sementes de assinante devem corresponder à derivação do PDA. Para qualquer conta passada como `authority` (ou papel de assinante similar), o runtime Solana verifica que o PDA assina via essas sementes.

### Contas restantes

Algumas instruções Raydium recebem **contas restantes**, uma lista de comprimento variável anexada após as contas fixas. Os helpers CPI do Anchor não verificam de tipo contas restantes; passe-as via `.with_remaining_accounts(...)`:

```rust icon="rust"
let cpi_ctx = CpiContext::new(program_id, accounts)
    .with_remaining_accounts(ctx.remaining_accounts.to_vec());
```

A ordem sempre importa, já que o programa receptor itera contas restantes na ordem que você as passa. Duas ordenações confirmadas:

- **CLMM `SwapV2`**: [arrays de tick](#aplicando-o-padrão-clmm), ordenados direcionalmente.
- **Farm v6**: pares `(reward_vault, user_reward_ata)`, mas apenas do segundo fluxo de recompensa em diante; veja [Farm v6](#farm-v6) para o que a decodificação de uma transação real mostra.

## Aplicando o padrão: CLMM

`SwapV2` segue [o padrão geral](#o-padrão-geral-de-cpi-anchor) acima com uma lista de contas diferente e um requisito de contas restantes para arrays de tick. O módulo `#[program]` do crate é nomeado `raydium_clmm`, que também é seu caminho Rust `use`.

<Warning>
  **O struct de contas CPI é nomeado `SwapSingleV2`, não `SwapV2`.** `SwapV2` é o nome da *instrução* on-chain.
</Warning>

```rust icon="rust"
use raydium_clmm::cpi::{self, accounts::SwapSingleV2 as ClmmSwap};

#[derive(Accounts)]
pub struct MyProxyClmmSwap<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: validado por CLMM
    pub amm_config: UncheckedAccount<'info>,
    /// CHECK: idem
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    /// CHECK: PDA de observação
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,

    pub token_program: Program<'info, Token>,
    pub token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>,
    /// CHECK: programa SPL memo, necessário para alguns caminhos Token-2022
    pub memo_program: UncheckedAccount<'info>,

    pub input_vault_mint: Account<'info, Mint>,
    pub output_vault_mint: Account<'info, Mint>,

    /// Tipado como `Program<T>` em vez de `UncheckedAccount`, mesma razão que o
    /// `cpmm_program` do CPMM no padrão geral acima: é o programa invocado, e
    /// `Program<T>` verifica seu endereço automaticamente.
    pub clmm_program: Program<'info, raydium_clmm::program::RaydiumClmm>,
    // remaining_accounts: tick_array_bitmap_extension (se o percurso precisar), depois
    // quantas contas tick_array o intervalo de preço esperado do swap abrange.
}
```

Calcule a lista de arrays de tick da mesma forma que o SDK faz, via uma cotação contra o estado atual do pool, em vez de adivinhar uma contagem fixa; um swap que ultrapassa os arrays que você passou reverte com `TickArrayNotFound` (veja [`products/clmm/instructions`](/pt/products/clmm/instructions) para a tabela de contas completa e lista de erros). Passe-os na direção do percurso de preço: primeiro array na direção do swap primeiro.

## Aplicando o padrão: LaunchLab

LaunchLab é baseado em Anchor e IDL-publicado: [`raydium_launchpad/raydium_launchpad.json`](https://github.com/raydium-io/raydium-idl/blob/master/raydium_launchpad/raydium_launchpad.json) no repo público `raydium-idl`. O identificador de metadados interno desse IDL é `raydium_launchpad`, um nome técnico para o programa subjacente, não um nome alternativo para o produto. Diferentemente de CPMM e CLMM, porém, **a própria fonte do programa não está disponível publicamente** (veja [`reference/program-addresses`](/pt/reference/program-addresses)). Não há dependência `git = "..."` para apontar Cargo, e nenhuma fonte para confirmar qual seria o caminho Rust `use` de um crate real.

Gere bindings do IDL publicado usando a macro `declare_program!` do Anchor. Salve o JSON do IDL como `idls/raydium_launchpad.json` em seu crate (Cargo procura um diretório `idls/` relativo a `CARGO_MANIFEST_DIR`), depois `declare_program!(raydium_launchpad);` gera structs `raydium_launchpad::cpi::accounts::<Ix>` e funções `cpi::<ix>()` direto do IDL, nenhuma fonte de programa necessária. O nome do struct de contas gerado é sempre o nome da instrução em PascalCase (`buy_exact_in` → `BuyExactIn`), e os nomes dos campos correspondem aos nomes de contas do IDL exatamente, a mesma lista de contas já usada em `MyProxyBuy` abaixo.

A forma CPI segue [o padrão geral](#o-padrão-geral-de-cpi-anchor). A lista de contas e argumentos abaixo vêm da instrução `buy_exact_in` do IDL on-chain, não de `products/launchlab/instructions.mdx`:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};
use raydium_launchpad::cpi::{self, accounts::BuyExactIn};

#[derive(Accounts)]
pub struct MyProxyBuy<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: PDA, seeds = [b"vault_auth_seed"], validado pelo programa
    pub authority: UncheckedAccount<'info>,

    /// CHECK: validado pelo programa
    pub global_config: UncheckedAccount<'info>,
    /// CHECK: validado pelo programa
    pub platform_config: UncheckedAccount<'info>,

    /// CHECK: validado pelo programa
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub user_base_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_quote_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub base_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub quote_vault: Account<'info, TokenAccount>,

    pub base_token_mint: Account<'info, Mint>,
    pub quote_token_mint: Account<'info, Mint>,

    /// CHECK: programa de token do mint base (SPL Token ou Token-2022, dependendo do mint)
    pub base_token_program: UncheckedAccount<'info>,
    /// Tipado como `Program<Token>` em vez de `UncheckedAccount`: o IDL fixa isso para
    /// Token SPL clássico especificamente (diferentemente de base_token_program acima), então
    /// a verificação de endereço integrada do Anchor em `Program<Token>` é suficiente por si só.
    pub quote_token_program: Program<'info, Token>,

    /// CHECK: PDA, seeds = [b"__event_authority"], necessário pelo padrão emit_cpi! do programa
    pub event_authority: UncheckedAccount<'info>,
    /// CHECK: a própria conta do programa, necessária junto com event_authority
    pub program: UncheckedAccount<'info>,
}

pub fn my_proxy_buy(
    ctx: Context<MyProxyBuy>,
    amount_in: u64,
    minimum_amount_out: u64,
    share_fee_rate: u64,
) -> Result<()> {
    let cpi_accounts = BuyExactIn {
        payer:               ctx.accounts.payer.to_account_info(),
        authority:           ctx.accounts.authority.to_account_info(),
        global_config:       ctx.accounts.global_config.to_account_info(),
        platform_config:     ctx.accounts.platform_config.to_account_info(),
        pool_state:          ctx.accounts.pool_state.to_account_info(),
        user_base_token:     ctx.accounts.user_base_token.to_account_info(),
        user_quote_token:    ctx.accounts.user_quote_token.to_account_info(),
        base_vault:          ctx.accounts.base_vault.to_account_info(),
        quote_vault:         ctx.accounts.quote_vault.to_account_info(),
        base_token_mint:     ctx.accounts.base_token_mint.to_account_info(),
        quote_token_mint:    ctx.accounts.quote_token_mint.to_account_info(),
        base_token_program:  ctx.accounts.base_token_program.to_account_info(),
        quote_token_program: ctx.accounts.quote_token_program.to_account_info(),
        event_authority:     ctx.accounts.event_authority.to_account_info(),
        program:             ctx.accounts.program.to_account_info(),
    };
    // `program` funciona duplo como o alvo CPI aqui: a própria conta do LaunchLab é tanto uma das
    // contas necessárias de sua instrução (para seu padrão emit_cpi!) quanto o programa
    // que CpiContext::new invoca.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.program.key,
        cpi_accounts,
    );

    cpi::buy_exact_in(cpi_ctx, amount_in, minimum_amount_out, share_fee_rate)?;
    Ok(())
}
```

Pós-graduação, o programa de destino é CPMM ou AMM v4 dependendo de `pool_state.migrate_type`, que `products/launchlab/accounts.mdx` diz ser definido no tempo de `Initialize`. Sua lista de contas CPI tem que estar preparada para qualquer um, ou você precisa ler `migrate_type` de `PoolState` primeiro e ramificar.

## Propagação de erros

Cada programa Raydium baseado em Anchor retorna seu próprio enum de erro; Anchor os envolve, então seu programa chamador os vê como `Err(ProgramError::Custom(code))`. Para lidar com erros específicos:

```rust icon="rust"
use raydium_cp_swap::error::ErrorCode as CpmmErr;

match cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out) {
    Ok(_) => Ok(()),
    Err(e) => {
        msg!("CPMM swap falhou: {:?}", e);
        // Re-lance, ou converta para seu próprio tipo de erro.
        Err(e)
    }
}
```

Troque o tipo de erro relevante para o programa que você está chamando (`raydium_clmm::error::ErrorCode` para CLMM, e assim por diante). Os números de código de erro são estáveis por política de IDL ([`sdk-api/anchor-idl`](/pt/sdk-api/anchor-idl#idl-change-policy)), então você pode testar contra códigos específicos comparando contra o valor numérico. Tabelas de erro completas: [CPMM](/pt/reference/error-codes#cpmm-standard-amm-errors), [CLMM](/pt/reference/error-codes#clmm-errors), [AMM v4, Farm v6 e LaunchLab](/pt/reference/error-codes#amm-v4-farm-v3-/-v5-/-v6-launchlab-errors).

## Orçamento de computação em CPIs compostos

Cada frame CPI tem overhead, e o próprio consumo de CU do chamado se acumula no topo do seu, então uma transação que chama Raydium de dentro do seu programa precisa de um orçamento de computação explícito em vez de confiar no padrão de 200k CU.

<Note>
  **Um único ponto de dados medido, não um benchmark.** Uma estimativa comum de regra de ouro para um CPI de swap CPMM (aproximadamente 1.500 CU de overhead CPI + 150.000 CU para o swap em si + 10.000 CU para a atualização de observação, ~161.500 CU total) superestima o uso real por uma margem ampla. Um CPI de swap real (`my_proxy_swap` chamando `swap_base_input`, mints de token SPL, um pool de dois tokens recém-criado) consumiu **~47.700 CU total**, lido de `connection.getTransaction(...).meta.computeUnitsConsumed`, aproximadamente um terço dessa estimativa. Trate isso como um ponto de dados de uma forma de pool e uma configuração de mint, não uma especificação. Meça sua própria transação em vez de orçamentar fora de qualquer número.
</Note>

CPIs de CLMM e LaunchLab custam mais (CLMM em particular percorre arrays de tick adicionais via `remaining_accounts`, adicionando CU por array), mas apenas o número CPMM acima é um valor medido. Sempre defina um limite explícito `ComputeBudgetProgram::set_compute_unit_limit(...)` dimensionado a partir de sua própria medição, não um número copiado da documentação, já que o limite padrão de 200k CU se esgotará silenciosamente e os custos por instrução mudam conforme os programas são atualizados.

## AMM v4: construção manual de instrução

AMM v4 é anterior ao Anchor e não tem crate CPI, tornando-o o único programa neste documento que não segue o padrão geral acima. Construa a `Instruction` manualmente:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_lang::solana_program::program::invoke_signed;
use anchor_lang::solana_program::instruction::{Instruction, AccountMeta};

const AMM_V4_PROGRAM_ID: Pubkey = pubkey!("675kPX9MHTjS2zt1qfr1NYHuzeLXfQM9H24wFSUt1Mp8");

// O discriminador SwapBaseIn é 9.
let mut data = vec![9u8];
data.extend_from_slice(&amount_in.to_le_bytes());
data.extend_from_slice(&minimum_amount_out.to_le_bytes());

let ix = Instruction {
    program_id: AMM_V4_PROGRAM_ID,
    accounts: vec![
        AccountMeta::new_readonly(token_program_id, false),
        AccountMeta::new(amm_id, false),
        AccountMeta::new_readonly(amm_authority, false),
        // ... contas restantes por products/amm-v4/instructions ...
    ],
    data,
};
invoke_signed(&ix, &account_infos, signer_seeds)?;
```

Veja [`products/amm-v4/code-demos`](/pt/products/amm-v4/code-demos) para a lista de contas completa.

## Farm v6

**Use o SDK TS se essa for uma opção para sua integração.** `raydium.farm.deposit(...)` (veja [`products/farm-staking/code-demos`](/pt/products/farm-staking/code-demos)) é exercido por demos reais e não depende de se um crate Anchor CPI existe para este programa.

<Warning>
  **O status de CPI Anchor do Farm v6 é não confirmado, e as evidências disponíveis o contradizem.** Nenhum IDL público ou fonte existe para Farm v6, contradizendo a afirmação de `products/farm-staking/code-demos.mdx` de um crate CPI Anchor (`raydium_farm_v6`) com um struct de contas `Deposit`.
</Warning>

**Se você precisar de Rust CPI de qualquer forma**, por exemplo compondo de outro programa on-chain, construa a `Instruction` manualmente, da mesma forma que [AMM v4](#amm-v4-construção-manual-de-instrução): derive a lista de contas real e discriminadores de instrução independentemente, por exemplo decodificando os layouts TypeScript do SDK (`raydium-sdk-V2`'s farm module), decodificando transações reais diretamente (veja abaixo), ou despejando e desassemblando o programa implantado.

Para a forma de instrução de argumento zero consistente com uma chamada de harvest ou claim, a ordem de contas real é um prefixo fixo (`token_program`, a conta de estado do farm, um PDA de autoridade de vault, o primeiro vault de recompensa desse PDA, um segundo PDA, o chamador, e o ATA do chamador para esse primeiro mint de recompensa), seguido por pares `(reward_vault_i, user_reward_ata_i)` em `remaining_accounts` para cada fluxo de recompensa após o primeiro. A convenção de emparelhamento é real, mas só começa no segundo fluxo de recompensa: o vault e ATA do primeiro fluxo são contas fixas, não adjacentes um ao outro, e não fazem parte de `remaining_accounts` em tudo.

## Testando um fluxo CPI

Dev local requer que os programas Raydium estejam disponíveis em seu validador de teste. Três opções:

1. **`anchor test` com clonagem de programa.** Puxa bytecode implantado em mainnet para seu validador local; veja [Clonando programas em um validador local](#clonando-programas-em-um-validador-local) abaixo para a configuração `Anchor.toml` e duas coisas que tropeçam em testes de criação de pool especificamente.
2. **Devnet.** Raydium implanta a maioria dos programas em devnet, mas em **IDs de programa diferentes de mainnet** para cada programa (CPMM, CLMM, AMM v4, Stable AMM e LaunchLab cada um têm um endereço devnet distinto; veja a tabela Devnet em [`reference/program-addresses`](/pt/reference/program-addresses)). Farm v3/v5/v6 não são confiávelmente publicados em devnet; a API ao vivo (`https://api-v3-devnet.raydium.io/main/info`) tem o quadro atual. Se você usar constantes `DEVNET_PROGRAM_ID` agrupadas de `raydium_clmm` (ou o equivalente para outros crates), não assuma que um ID de mainnet também funciona em devnet. Execute `anchor test --provider.cluster devnet` para atingir código ao vivo uma vez que você tenha os endereços corretos.
3. **Deploy local.** Clone os repos Raydium (CPMM, CLMM; a fonte do LaunchLab não está disponível para esta opção) e `anchor deploy` para um validador local. Adiciona overhead de ciclo de teste, mas permite que você modifique o chamado para depuração.

Execute com `anchor test`, ou `anchor build` primeiro e `anchor test --skip-build` depois se você estiver iterando no arquivo de teste sem alterar o programa.

### Clonando programas em um validador local

```toml icon="file-code"
[test]
# O padrão (5s) não é suficiente uma vez que você está clonando várias contas, já que cada uma é
# uma rodada RPC de mainnet sequencial durante a inicialização do validador.
startup_wait = 60000

[test.validator]
url = "https://api.mainnet-beta.solana.com"

[[test.validator.clone]]
address = "CAMMCzo5YL8w4VFF8KVHrK22GGUsp5VTaW7grrKgrWqK"  # CLMM

[[test.validator.clone]]
address = "CPMMoo8L3F4NbTegBCKVNunggL7H1ZpdTHKxQB5qKP1C"  # CPMM

[[test.validator.clone]]
address = "LanMV9sAd7wArD4vJFi2qDdfnVhFxYSUg6eADduJ3uj"   # LaunchLab

[[test.validator.clone]]
address = "FarmqiPv5eAj3j1GMdMCMUGXqPUvmquZtMy86QH6rzhG"  # Farm v6
```

Isso funciona por ID de programa independentemente de se a fonte do programa é pública, então LaunchLab clona da mesma forma que CPMM e CLMM fazem mesmo que sua fonte não esteja disponível. `reference/program-addresses` é a fonte de verdade para cada endereço aqui.

<Warning>
  **Clonar o programa não é suficiente se seu teste também *cria* um pool** (em vez de fazer swap contra um que já existe). A instrução `initialize` do CPMM valida suas contas `amm_config` e `create_pool_fee` contra dados on-chain reais, então você precisa clonar aquelas também, ou `initialize` falha completamente. Para CPMM especificamente: clone o `AmmConfig` de nível de taxa que você quer (busque seu endereço de `GET https://api-v3.raydium.io/main/cpmm-config`, índice 0 é o nível de 0,25%) e a [conta de token receptor de taxa](/pt/reference/program-addresses#shared-config-/-pda-conventions), validada por endereço exato, não criada na hora, então tem que já existir.
</Warning>

<Warning>
  **Um pool que seu teste acabou de criar não é permutável no mesmo instante.** O `initialize` do CPMM silenciosamente sobrescreve um `open_time` solicitado que não é estritamente no futuro (`if open_time <= block_timestamp { open_time = block_timestamp + 1 }`), então mesmo `startTime: 0` ("abrir imediatamente," por o SDK) deixa uma lacuna real ≥1 segundo antes do pool aceitar swaps. Um teste que cria um pool e faz swap contra ele com zero atraso vai atingir [`NotApproved`](/pt/reference/error-codes#cpmm-standard-amm-errors). Um breve `await` (1–2s) entre criação de pool e o primeiro swap é suficiente. Isso é específico para testes; um humano executando dois comandos manuais separados normalmente não notaria, já que digitar e inicialização de processo já comem mais de um segundo.
</Warning>
