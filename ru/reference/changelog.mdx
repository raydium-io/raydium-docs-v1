## Релизы

<Update label="2026-08-24" description="LaunchLab: котировки в Token-2022 минтах">
  Запуск теперь может быть котирован в Token-2022 минте. `CreateConfig`, `InitializeV2`, `InitializeWithToken2022`, четыре инструкции swap и каждый claim комиссии принимают любую программу токенов в слоте quote-program; устаревший `Initialize` остаётся только для наследия. Границы slippage при свопе теперь сравниваются с тем, что плательщик фактически платит или получает, за вычетом комиссии передачи quote минта. Бит1 `PoolState.token_program_flag` становится значимым, поэтому декодеры, проверяющие весь байт против `0`, неправильно читают наследуемый базовый минт как Token-2022. `MigrateToCpswap` переименовывает два аккаунта token-program в `token_program` / `token_program_2022`, и `6023` переиспользуется для `CalculateOverflow`.

  [Читать полную запись →](/ru/reference/changelog/2026-08-24-launchlab-token2022-quote-mint)
</Update>

<Update label="2026-08-17" description="LaunchLab: запуски только CPMM и управление конфигурацией платформы">
  Новая инициализация запуска теперь требует CPMM, в то время как наследуемое состояние, привязанное к AMM v4, остаётся мигрируемым. До этого релиза `creator_scale` создавал Fee Key, принадлежащий создателю; миграции CPMM, выполненные после обновления, вместо этого объединяют `platform_scale + creator_scale` в одну долю Fee Key, принадлежащую платформе. Платформы также могут ограничивать запуски своими собственными PDA `PlatformAllowConfig`, и построители миграций должны добавить оба PDA поддержки минтов CPMM.

  [Читать полную запись →](/ru/reference/changelog/2026-08-17-launchlab-cpmm-only-platform-config)
</Update>

<Update label="2026-08-17" description="CLMM: замораживание позиционных NFT с ограниченным издателем">
  Новые минты позиционных NFT CLMM используют свой пул в качестве органа замораживания, но их аккаунты токенов остаются незамороженными по умолчанию. Замораживание происходит только при `OpenPositionV2` или `OpenPositionWithToken22Nft`, когда орган замораживания любого из базовых минтов хранилища совпадает со списком ограниченных издателей. Соответствующая позиция не может передаваться или менять владельца, но может управлять ликвидностью. Её вызов `ClosePosition` должен добавить пул, чтобы CLMM мог разморозить, сжечь и закрыть атомарно. Существующие позиции остаются без изменений.

  [Читать полную запись →](/ru/reference/changelog/2026-08-17-clmm-restricted-position-nft-freeze)
</Update>

<Update label="2026-08-17" description="CPMM: сбор комиссии создателя без разрешения">
  Дополнительная инструкция `CollectCreatorFeePermissionless` позволяет любому плательщику собрать все накопленные комиссии создателя, ограничивая бенефициара и оба назначения токенов на `PoolState.pool_creator` и канонические ATA создателя. Исходный путь с подписью создателя остаётся без изменений. `CreatePermissionPda` также принимает выделенный орган выдачи прав, в то время как `ClosePermissionPda` остаётся только для администратора.

  [Читать полную запись →](/ru/reference/changelog/2026-08-17-cpmm-permissionless-creator-fee-collection)
</Update>

<Update label="2026-07-30" description="CLMM: пулы с разрешением и защита замороженного аккаунта для лимитных ордеров">
  Два дополнительных, обратно совместимых обновления программы CLMM. `CreatePermissionedPool` встраивает предоставленный клиентом ненулевой `seed_index` в семена PDA пула, позволяя внесённому в белый список оператору (держателю PDA `Permission`) создавать несколько пулов на `(config, mint0, mint1)` — таким образом, ID пула больше не является каноническим для пары. Новые инструкции администратора `CreatePermissionPda` / `ClosePermissionPda` управляют этими правами, и `PoolState` получает поле `seed_index` (вырезанное из отступа, без изменения размера). Отдельно, `OpenLimitOrder` теперь принимает аккаунты выходной стороны и отклоняет ордера, чьи входные или выходные аккаунты токенов заморожены (`NotApproved`).

  [Читать полную запись →](/ru/reference/changelog/2026-07-30-clmm-permissioned-pools)
</Update>

<Update label="2026-07-22" description="AMM v4: удаление зависимости OpenBook / Serum">
  AMM v4 удаляет свою давно неиспользуемую зависимость OpenBook/Serum, все CPI книги заказов и мёртвые инструкции создания рынка. `SwapBaseIn` / `SwapBaseOut`, `Deposit` и `Withdraw` сохраняют свои макеты (удалённые аккаунты рынка теперь игнорируются, не проверяются); **критически нарушающий** `WithdrawPnl` (17 → 10, без совместимости) и `SetParams` (сокращённые аккаунты + переномерованный `param`); и `Initialize`, `PreInitialize`, `MonitorStep`, `MigrateToOpenBook`, `WithdrawSrm`, `SimulateInfo`, `AdminCancelOrders` больше не вызываются. Макеты аккаунтов в цепи и коды ошибок остаются стабильными; перенесите свопы на точки входа V2.

  [Читать полную запись →](/ru/reference/changelog/2026-07-22-amm-v4-openbook-removal)
</Update>

<Update label="2026-06-22" description="Stable AMM: удаление мёртвого кода OpenBook (рынка)">
  Stable AMM удаляет свои давно неиспользуемые аккаунты и код создания рынка OpenBook. Меньшие макеты `SwapBaseIn` / `SwapBaseOut` (18 → 9), `Deposit` (14 → 12) и `Withdraw` (21/22 → 12) (старые макеты остаются совместимыми); **критически нарушающее** изменение `WithdrawPnl` (16 → 10, без совместимости); снятие комиссии реферала; и упрощённая формула активов пула только для хранилища. Большинство других инструкций Stable больше не вызываются.

  [Читать полную запись →](/ru/reference/changelog/2026-06-22-stable-amm-openbook-cleanup)
</Update>

<Update label="2026-05-18" description="CLMM: лимитные ордера, односторонняя комиссия, динамическая комиссия">
  Три дополнительные, обратно совместимые возможности CLMM: лимитные ордера первого класса (с хранителем расчётов `limit_order_admin`), сбор односторонней комиссии (`CollectFeeOn`) и отслеживание волатильности динамической комиссии. Добавляет `CreateCustomizablePool`, переформатирование `PoolState` (**критическое изменение для индексаторов**), новые поля `TickState`, одиннадцать новых кодов ошибок (с числовым сдвигом) и соответствующие добавления SDK / API.

  [Читать полную запись →](/ru/reference/changelog/2026-05-18-clmm-limit-orders)
</Update>

## Соглашения документации

- **Версионирование**: эта документация использует календарное версионирование (YYYY-MM-DD). Каждое обновление добавляет новую страницу записи и новую строку в начало хронологии выше.
- **Одна страница на релиз**: каждое резюме релиза находится на отдельной странице в `reference/changelog/`, поэтому этот индекс остаётся кратким и каждая запись независимо ссылаема.
- **Дата проверки**: каждая запись фиксирует, когда содержимое было последний раз перепроверено по состоянию в цепи / API и исходному коду программы. Если не указано, предполагайте основную дату записи.
- **Критические изменения**: выделены в прямоугольном предупреждении на затронутых страницах и отмечены в записи.
- **Охват**: этот журнал изменений охватывает сам набор документации. Собственная историческая хронология протокола находится в [`introduction/history-and-milestones`](/ru/introduction/history-and-milestones) и является источником истины для «когда произошло X на Raydium».
