## Релизы

<Update label="2026-08-31" description="LaunchLab: правила кривой платформы заменяют список параметров кривой">
  Ограничения параметров запуска переходят с `PlatformConfig` в отдельные учётные записи `PlatformCurveRule` для каждой конфигурации. Правило содержит до 10 групп проверок с до 25 ограничениями `(field, op, value)` над 19 параметрами запуска с операторами `Eq` / `Gte` / `Lte` / `Neq` — так платформа может наконец выразить диапазон значений, альтернативные уровни, потолок оценки выпуска, нижний предел миграции, ограничение по типу токена или группу, переключающуюся по дате, чего не могла сделать список с проверкой только на равенство. `PlatformConfig` сохраняет размер 944 байта: `restrict_curve_param`, `curve_rule_manager` и префикс длины удалённого вектора выходят из заполнения. Декодеры должны удалить завершающий `Vec<PlatformCurveParam>`, а создатели запусков должны добавить PDA правила в `remaining_accounts` при включённом флаге. Удалены две инструкции, добавлены четыре, добавлены два варианта `UpdatePlatformConfig`, добавлены `6024`–`6030`. Требуется обновление IDL. SDK поставляется с двумя чистыми внецепевыми проверками, чтобы создатель никогда не узнавал правило из отменённой транзакции, а запись документирует репетицию devnet перед включением флага на mainnet.

  [Читать полную запись →](/ru/reference/changelog/2026-08-31-launchlab-platform-curve-rules)
</Update>

<Update label="2026-08-27" description="LaunchLab: платформа держит полномочие вывода удержанных средств с момента создания монеты">
  `InitializeWithToken2022` теперь записывает `PlatformConfig.transfer_fee_extension_auth` в `withdraw_withheld_authority` новой базовой монеты вместо PDA запуска `authority`, так что платформа может собирать удержанные комиссии за передачу во время фазы кривой связи, а не ждать выпуска — сама программа не имеет инструкции вывода удержанных средств. `MigrateToCpswap` переназначает это полномочие только когда PDA всё ещё его держит, что сохраняет работу выпуска для монет обоих поколений. `transfer_fee_config_authority` по-прежнему переходит только при выпуске, поэтому ротация `transfer_fee_extension_auth` во время запуска молча оставляет два полномочия на разных ключах. Ни макет учётной записи, ни инструкция, ни аргумент, ни код ошибки не изменились.

  [Читать полную запись →](/ru/reference/changelog/2026-08-27-launchlab-token2022-withheld-authority)
</Update>

<Update label="2026-08-26" description="LaunchLab: потолок комиссии платформы повышен до 500 bps">
  Потолок `fee_rate` платформы переходит на `50000` (500 bps) на обоих путях, которые его проверяют. `CreatePlatformConfig` был ограничен `10000` (100 bps) с первого релиза программы; `UpdatePlatformConfig` был ограничен `25000` (250 bps) с 2026-01-27. Две проверки теперь согласованы, так что платформа, созданная с любой разрешённой ставкой, может быть обновлена с ней же — включая через вариант `AllInfo` массовой операции, который переподтверждает `fee_rate` при переписывании каждого другого поля. Два пути по-прежнему вызывают разные ошибки (`InvalidInput` при создании, `InvalidPlatformInfo` при обновлении). Ни макет учётной записи, ни инструкция, ни код ошибки не изменились, и ни одна существующая платформа или запуск не переоценены. `GlobalConfig.max_share_fee_rate` остаётся на 100 bps и ограничивает только `share_fee_rate` реферала за транзакцию.

  [Читать полную запись →](/ru/reference/changelog/2026-08-26-launchlab-platform-fee-rate-cap)
</Update>

<Update label="2026-08-24" description="LaunchLab: котировочные монеты Token-2022">
  Запуск теперь может быть котирован в монете Token-2022. `CreateConfig`, `InitializeV2`, `InitializeWithToken2022`, четыре инструкции swap и каждый сбор комиссии принимают любую программу токена в своём слоте программы котировки; устаревший `Initialize` остаётся только для наследия. Границы проскальзывания swap теперь сравниваются с тем, что плательщик фактически платит или получает, за вычетом комиссии за передачу котировочной монеты. Бит1 `PoolState.token_program_flag` становится значимым, поэтому декодеры, которые тестируют весь байт против `0`, неправильно читают устаревшую базовую монету как Token-2022. `MigrateToCpswap` переименовывает свои два учётных записи программы токена в `token_program` / `token_program_2022`, и `6023` переиспользуется для `CalculateOverflow`.

  [Читать полную запись →](/ru/reference/changelog/2026-08-24-launchlab-token2022-quote-mint)
</Update>

<Update label="2026-08-17" description="LaunchLab: запуски только CPMM и элементы управления конфигурацией платформы">
  Новая инициализация запуска теперь требует CPMM, в то время как устаревшее состояние, привязанное к AMM v4, остаётся мигрируемым. До этого релиза `creator_scale` создавал принадлежащий создателю Fee Key; миграции CPMM, выполненные после обновления, вместо этого консолидируют `platform_scale + creator_scale` в один принадлежащий платформе Fee Key. Платформы также могут ограничивать запуски своими собственными PDA `PlatformAllowConfig`, и создатели миграций должны добавить оба PDA поддержки CPMM.

  [Читать полную запись →](/ru/reference/changelog/2026-08-17-launchlab-cpmm-only-platform-config)
</Update>

<Update label="2026-08-17" description="CLMM: замораживание NFT позиции с ограниченным издателем">
  Новые монеты NFT позиции CLMM используют свой пул в качестве полномочия замораживания, но их учётные записи токена остаются незамороженными по умолчанию. Замораживание происходит только на `OpenPositionV2` или `OpenPositionWithToken22Nft`, когда полномочие замораживания любой из базовых монет хранилища совпадает со списком ограниченных издателей. Совпадающая позиция не может передаваться или менять владельца, но может по-прежнему управлять ликвидностью. Её вызов `ClosePosition` должен добавить пул, чтобы CLMM мог разморозить, сжечь и закрыть атомарно. Существующие позиции остаются без изменений.

  [Читать полную запись →](/ru/reference/changelog/2026-08-17-clmm-restricted-position-nft-freeze)
</Update>

<Update label="2026-08-17" description="CPMM: сбор комиссии создателя без разрешения">
  Дополнительная инструкция `CollectCreatorFeePermissionless` позволяет любому плательщику собрать все накопленные комиссии создателя, ограничивая получателя и оба назначения токена на `PoolState.pool_creator` и канонические ATA создателя. Исходный путь, подписанный создателем, остаётся без изменений. `CreatePermissionPda` также принимает выделенный орган выдачи разрешений, в то время как `ClosePermissionPda` остаётся только для администратора.

  [Читать полную запись →](/ru/reference/changelog/2026-08-17-cpmm-permissionless-creator-fee-collection)
</Update>

<Update label="2026-07-30" description="CLMM: пулы с разрешением и защита замороженного учёта для лимитных ордеров">
  Два дополнительных, обратно совместимых обновления программы CLMM. `CreatePermissionedPool` включает предоставленный клиентом ненулевой `seed_index` в семена PDA пула, позволяя внесённому в белый список оператору (держателю PDA `Permission`) создавать несколько пулов на `(config, mint0, mint1)` — так что ID пула больше не является каноническим для пары. Новые инструкции администратора `CreatePermissionPda` / `ClosePermissionPda` управляют этими разрешениями, и `PoolState` получает поле `seed_index` (вырезанное из заполнения, без изменения размера). Отдельно, `OpenLimitOrder` теперь принимает учётные записи стороны вывода и отклоняет ордера, чьи входные или выходные учётные записи токена заморожены (`NotApproved`).

  [Читать полную запись →](/ru/reference/changelog/2026-07-30-clmm-permissioned-pools)
</Update>

<Update label="2026-07-22" description="AMM v4: удаление зависимости OpenBook / Serum">
  AMM v4 удаляет свою давно неиспользуемую зависимость OpenBook/Serum, все CPI книги заказов и мёртвые инструкции создания рынка. `SwapBaseIn` / `SwapBaseOut`, `Deposit` и `Withdraw` сохраняют свои макеты (удалённые учётные записи рынка теперь игнорируются, не проверяются); **критически нарушающий** `WithdrawPnl` (17 → 10, без совместимости) и `SetParams` (сокращённые учётные записи + переномерованный `param`); и `Initialize`, `PreInitialize`, `MonitorStep`, `MigrateToOpenBook`, `WithdrawSrm`, `SimulateInfo`, `AdminCancelOrders` больше не вызываются. Макеты учётных записей в цепи и коды ошибок остаются стабильными; перенесите свопы на точки входа V2.

  [Читать полную запись →](/ru/reference/changelog/2026-07-22-amm-v4-openbook-removal)
</Update>

<Update label="2026-06-22" description="Stable AMM: удаление мёртвого кода OpenBook (рынка)">
  Stable AMM удаляет свои давно неиспользуемые учётные записи и код создания рынка OpenBook. Меньшие макеты `SwapBaseIn` / `SwapBaseOut` (18 → 9), `Deposit` (14 → 12) и `Withdraw` (21/22 → 12) (старые макеты по-прежнему совместимы); **критически нарушающее** изменение `WithdrawPnl` (16 → 10, без совместимости); снятие комиссии реферала; и упрощённая формула активов пула только для хранилища. Большинство других инструкций Stable больше не вызываются.

  [Читать полную запись →](/ru/reference/changelog/2026-06-22-stable-amm-openbook-cleanup)
</Update>

<Update label="2026-05-18" description="CLMM: лимитные ордера, односторонняя комиссия, динамическая комиссия">
  Три дополнительные, обратно совместимые возможности CLMM: лимитные ордера первого класса (с хранителем `limit_order_admin`), сбор односторонней комиссии (`CollectFeeOn`) и отслеживающая волатильность динамическая комиссия. Добавляет `CreateCustomizablePool`, переформатирование `PoolState` (**критическое изменение для индексаторов**), новые поля `TickState`, одиннадцать новых кодов ошибок (с числовым сдвигом) и соответствующие добавления SDK / API.

  [Читать полную запись →](/ru/reference/changelog/2026-05-18-clmm-limit-orders)
</Update>

## Соглашения документации

- **Версионирование**: эта документация использует календарное версионирование (YYYY-MM-DD). Каждое обновление добавляет новую страницу записи и новую строку в начало хронологии выше.
- **Одна страница на релиз**: каждое резюме релиза находится на отдельной странице в `reference/changelog/`, так что этот индекс остаётся коротким и каждая запись независимо ссылаема.
- **Дата проверки**: каждая запись фиксирует, когда содержание было последний раз перепроверено на соответствие состоянию в цепи / API и исходному коду программы. Если не указано, предположите основную дату записи.
- **Критические изменения**: выделены в боксе предупреждения на затронутых страницах и помечены в записи.
- **Охват**: этот журнал изменений охватывает сам набор документации. Собственная историческая хронология протокола находится в [`introduction/history-and-milestones`](/ru/introduction/history-and-milestones) и является источником истины для «когда X произошло на Raydium».
