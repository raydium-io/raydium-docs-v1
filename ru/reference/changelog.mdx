## Релизы

<Update label="2026-08-14" description="LaunchLab: запуски только CPMM и элементы управления конфигурацией платформы">
  Новая инициализация запуска теперь требует CPMM, в то время как унаследованное состояние, привязанное к AMM v4, остаётся миграбельным. До этого релиза `creator_scale` создавал Fee Key, принадлежащий создателю; миграции CPMM, выполненные после обновления, вместо этого объединяют `platform_scale + creator_scale` в один Fee Key, принадлежащий платформе. Платформы также могут ограничивать запуски собственными PDA `PlatformAllowConfig`, и разработчики миграций должны добавить оба PDA поддержки mint CPMM.

  [Читать полную запись →](/ru/reference/changelog/2026-08-14-launchlab-cpmm-only-platform-config)
</Update>

<Update label="2026-08-14" description="CLMM: замораживание NFT позиций с ограниченным издателем">
  Новые mint NFT позиций CLMM используют свой пул в качестве органа замораживания, но их учётные записи токенов остаются незамороженными по умолчанию. Замораживание происходит только при `OpenPositionV2` или `OpenPositionWithToken22Nft`, когда орган замораживания mint базового хранилища совпадает со списком ограниченных издателей. Соответствующая позиция не может передаваться или менять владельца, но может по-прежнему управлять ликвидностью. Её вызов `ClosePosition` должен добавить пул, чтобы CLMM мог разморозить, сжечь и закрыть атомарно. Существующие позиции остаются без изменений.

  [Читать полную запись →](/ru/reference/changelog/2026-08-14-clmm-restricted-position-nft-freeze)
</Update>

<Update label="2026-08-14" description="CPMM: сбор комиссий создателя без разрешения">
  Дополнительная инструкция `CollectCreatorFeePermissionless` позволяет любому плательщику собрать все накопленные комиссии создателя, ограничивая получателя и оба назначения токенов на `PoolState.pool_creator` и канонические ATA создателя. Исходный путь, подписанный создателем, остаётся без изменений. `CreatePermissionPda` также принимает выделенный орган выдачи разрешений, в то время как `ClosePermissionPda` остаётся только для администратора.

  [Читать полную запись →](/ru/reference/changelog/2026-08-14-cpmm-permissionless-creator-fee-collection)
</Update>

<Update label="2026-07-30" description="CLMM: пулы с разрешениями и защита от замороженных счётов для лимитных ордеров">
  Два дополнительных, обратно совместимых обновления программы CLMM. `CreatePermissionedPool` включает предоставленный клиентом ненулевой `seed_index` в семена PDA пула, позволяя внесённому в белый список оператору (тому, кто держит PDA `Permission`) создавать несколько пулов на `(config, mint0, mint1)` — таким образом, ID пула больше не является каноническим для пары. Новые инструкции администратора `CreatePermissionPda` / `ClosePermissionPda` управляют этими разрешениями, и `PoolState` получает поле `seed_index` (вырезанное из отступа, без изменения размера). Отдельно, `OpenLimitOrder` теперь принимает учётные записи выходной стороны и отклоняет ордера, чьи входные или выходные учётные записи токенов заморожены (`NotApproved`).

  [Читать полную запись →](/ru/reference/changelog/2026-07-30-clmm-permissioned-pools)
</Update>

<Update label="2026-07-22" description="AMM v4: удаление зависимости OpenBook / Serum">
  AMM v4 удаляет свою давно неиспользуемую зависимость OpenBook/Serum, все CPI книги заказов и мёртвые инструкции создания рынка. `SwapBaseIn` / `SwapBaseOut`, `Deposit` и `Withdraw` сохраняют свои макеты (удалённые учётные записи рынка теперь игнорируются, не проверяются); **критически нарушающее** изменение `WithdrawPnl` (17 → 10, без совместимости) и `SetParams` (сокращённые учётные записи + перенумерованный `param`); и `Initialize`, `PreInitialize`, `MonitorStep`, `MigrateToOpenBook`, `WithdrawSrm`, `SimulateInfo`, `AdminCancelOrders` больше не вызываются. Макеты учётных записей в цепи и коды ошибок остаются стабильными; перенесите свопы на точки входа V2.

  [Читать полную запись →](/ru/reference/changelog/2026-07-22-amm-v4-openbook-removal)
</Update>

<Update label="2026-06-22" description="Stable AMM: удаление мёртвого кода OpenBook (рынок)">
  Stable AMM удаляет свои давно неиспользуемые учётные записи и код создания рынка OpenBook. Меньшие макеты `SwapBaseIn` / `SwapBaseOut` (18 → 9), `Deposit` (14 → 12) и `Withdraw` (21/22 → 12) (старые макеты по-прежнему совместимы); **критически нарушающее** изменение `WithdrawPnl` (16 → 10, без совместимости); снятие комиссии реферала; и упрощённая формула активов пула только для хранилища. Большинство других инструкций Stable больше не вызываются.

  [Читать полную запись →](/ru/reference/changelog/2026-06-22-stable-amm-openbook-cleanup)
</Update>

<Update label="2026-05-18" description="CLMM: лимитные ордера, односторонняя комиссия, динамическая комиссия">
  Три дополнительные, обратно совместимые возможности CLMM: лимитные ордера первого класса (с хранителем расчётов `limit_order_admin`), сбор односторонней комиссии (`CollectFeeOn`) и отслеживание волатильности динамической комиссии. Добавляет `CreateCustomizablePool`, переформатирование `PoolState` (**критическое изменение для индексатора**), новые поля `TickState`, одиннадцать новых кодов ошибок (с числовым сдвигом) и соответствующие добавления SDK / API.

  [Читать полную запись →](/ru/reference/changelog/2026-05-18-clmm-limit-orders)
</Update>

## Соглашения документации

- **Версионирование**: эта документация использует календарное версионирование (YYYY-MM-DD). Каждое обновление добавляет новую страницу записи и новую строку в начало хронологии выше.
- **Одна страница на релиз**: каждое резюме релиза находится на собственной странице в `reference/changelog/`, поэтому этот индекс остаётся кратким и каждая запись независимо ссылаема.
- **Дата проверки**: каждая запись фиксирует, когда содержание было последний раз перепроверено на соответствие состоянию в цепи / API и исходному коду программы. Если не указано, предположите основную дату записи.
- **Критические изменения**: выделены в прямоугольном предупреждении на затронутых страницах и помечены в записи.
- **Охват**: этот журнал изменений охватывает сам набор документации. Собственная историческая хронология протокола находится в [`introduction/history-and-milestones`](/ru/introduction/history-and-milestones) и является источником истины для «когда произошло X на Raydium».
