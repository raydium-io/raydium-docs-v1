## Краткое резюме

AMM v4 — это программа, с которой Raydium начинал. Она поддерживает инвариант constant-product (`x · y = k`). Изначально она была разработана как **гибридный AMM**: каждый пул находился поверх маркета лимитных ордеров OpenBook (ранее Serum) и отражал части своей кривой как лимитные ордера на этой книге, чтобы пользователи и агрегаторы могли своп-ить напрямую против пула (путь AMM) или против лимитных ордеров, которыми владел пул на OpenBook (путь CLOB). **Зависимость от OpenBook была удалена из программы** — пулы больше не размещают и не поддерживают ордера на OpenBook, и весь текущий трафик своп-операций проходит через точки входа AMM-only V2 swap. Token-2022 не поддерживается. AMM v4 **по-прежнему полностью функционален как constant-product AMM** — каждый пул продолжает торговать, комиссии по-прежнему начисляются, LP по-прежнему зарабатывают — но UI и SDK по умолчанию создают новые пулы в [CPMM](/ru/products/cpmm), потому что CPMM дешевле и поддерживает больше типов монет.

## История гибридного дизайна (контекст)

При запуске создание пула рядом с книгой ордеров Serum рисковало фрагментировать ликвидность. Гибридный дизайн опубликовал кривую AMM на книге как лимитные ордера, чтобы маршрутизаторы книги ордеров видели глубину пула бесплатно. После того как OpenBook отделился от Serum в конце 2022 года, программа продолжала работать с OpenBook с минимальными изменениями. По мере развития CPMM и on-chain агрегаторов преимущество со стороны книги ордеров исчезло, и интеграция AMM v4 с OpenBook в конце концов была отключена — кривая теперь является единственной поверхностью исполнения пула.

## Что даёт вам AMM v4 (чего нет в CPMM)

- **Глубокая ликвидность для устаревших пар.** Основные пары (SOL-USDC, mSOL-USDC и т. д.) с большим TVL в AMM v4 остаются самым глубоким местом для этих торговель.

(Исторически AMM v4 также предлагал видимость со стороны книги ордеров через гибридный механизм OpenBook, но этот путь больше не активен. Любой интегратор, который ранее маршрутизировал через ордера OpenBook AMM, должен теперь маршрутизировать напрямую через точки входа своп-операций AMM.)

## Чего AMM v4 не даёт вам

- **Token-2022.** Не поддерживается. AMM v4 был написан до появления Token-2022; его макеты аккаунтов предполагают классический SPL Token.
- **Низкое количество аккаунтов в своп-операциях v1.** Макеты `SwapBaseIn` / `SwapBaseOut` по-прежнему содержат аккаунты маркета OpenBook как позиционные заполнители (они принимаются, но больше не валидируются и не используются). Используйте `SwapBaseInV2` / `SwapBaseOutV2`, чтобы удалить их и сократить транзакцию.
- **Низкое использование вычислений.** Даже своп V2 стоит больше, чем своп CPMM.
- **Поток создания новых пулов по умолчанию.** Новые пулы создаются с `Initialize2` (устаревшие точки входа `Initialize` / `PreInitialize` были удалены и теперь возвращают ошибку). UI Raydium, SDK и `api-v3.raydium.io` больше не показывают кнопку "создать пул AMM v4" — путь по умолчанию для новых пулов — это CPMM.

## Как AMM v4 отличается от CPMM

| Аспект | AMM v4 | CPMM |
|--------|--------|------|
| Кривая | Constant product | Constant product |
| Зависимость от OpenBook | Удалена (изначально была; теперь удалена из программы) | Нет |
| Token-2022 | Нет | Да |
| Количество аккаунтов на своп V2 | ~9 | ~11 |
| Единицы вычислений на своп | ~80k–120k (путь V2) | ~60k–100k |
| Комиссия LP | 0,22% от объёма | Варьируется по `AmmConfig` |
| Комиссия протокола | 0,03% от объёма (фиксированная) | Варьируется по `AmmConfig` |
| Комиссия фонда | Нет | Да |
| Оракул TWAP | Нет встроенного аккаунта наблюдений | Кольцевой буфер `observation` |
| По умолчанию для новых пулов | Нет (по-прежнему принимается) | Да |

## Концептуальная модель

Пул AMM v4 сегодня — это constant-product `x · y = k` AMM. Оба хранилища полностью доступны для кривой — никакая часть не зарезервирована для ордеров OpenBook, потому что интеграция с OpenBook была удалена. Операции — это **своп** (пользователь ↔ пул, через `SwapBaseInV2` / `SwapBaseOutV2`) и **депозит** / **вывод** (операции LP). Старый **кран** (`MonitorStep`) был удалён и теперь возвращает ошибку при вызове.

*Историческая концептуальная модель (до деактивации):* часть каждого хранилища была зарезервирована как открытые ордера на книге; расчёт заполненных ордеров происходил во время своп-операций и операций LP; маршрутизированные своп-операции могли заполняться против собственных ордеров OpenBook пула. Ничего из этого не работает сегодня.

## Почему CPMM — рекомендуемый вариант по умолчанию

CPMM избавляется от зависимости OpenBook. Компромиссы:

- Транзакции CPMM на 2×–3× дешевле в вычислениях.
- CPMM поддерживает монеты Token-2022.
- Агрегаторы теперь интегрируют CPMM напрямую через Raydium SDK, поэтому преимущество видимости книги ордеров в значительной степени устарело.
- Операционный риск: исторически сбои или паузы OpenBook могли ухудшить пулы AMM v4 (устаревшие ордера). Теперь, когда зависимость от OpenBook удалена из программы, эта связь исчезла — но CPMM остаётся рекомендуемым, менее затратным вариантом по умолчанию.

См. [`protocol-overview/versions-and-migration`](/ru/protocol-overview/versions-and-migration) для руководства по миграции.

## Когда AMM v4 — правильный выбор

- Вы маршрутизируете своп-операцию, и один из кандидатов пулов — это пул AMM v4 с лучшей ценой.
- Вы предоставляете или управляете ликвидностью в существующем пуле AMM v4 — миграция — это выбор, а не требование; пул продолжает функционировать как чистый AMM.
- Вы поддерживаете интеграцию, построенную на AMM v4, и у вас нет причин для миграции.

(Видимость книги ордеров на OpenBook больше не является причиной выбирать AMM v4 — эта интеграция отключена.)

Для нового пула constant-product [CPMM](/ru/products/cpmm) — это более простой вариант по умолчанию.
