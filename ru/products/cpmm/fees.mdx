## Две независимые комиссии, четыре направления

CPMM взимает **две отдельно установленные комиссии** на каждый своп:

1. **Торговая комиссия** — взимается по ставке `AmmConfig.trade_fee_rate` и распределяется между тремя направлениями:
   - **Доля LP** — остаётся в хранилище и увеличивает `k`. Получается неявно при сжигании токенов LP.
   - **Доля протокола** — накапливается в `PoolState.protocol_fees_token*`; собирается `protocol_owner` через `CollectProtocolFee`.
   - **Доля фонда** — накапливается в `PoolState.fund_fees_token*`; собирается `fund_owner` через `CollectFundFee`.
2. **Комиссия создателя** (опциональная, для каждого пула) — взимается по ставке `AmmConfig.creator_fee_rate` **независимо** от торговой комиссии и накапливается в `PoolState.creator_fees_token*`. Создатель может собрать её через `CollectCreatorFee`, или любой плательщик может запустить путь `CollectCreatorFeePermissionless` с фиксированными направлениями. Активна только если пул был создан с `enable_creator_fee = true`.

Комиссия создателя **не является** частью торговой комиссии. Две ставки складываются при взимании комиссии на входе своп, но каждая остаётся в своём бакете — доли протокола и фонда всегда берутся только из `trade_fee`, никогда из `creator_fee`. Пул с `creator_fee_rate = 1000` (0,10%) и `trade_fee_rate = 2500` (0,25%) взимает в сумме 0,35% входа при своп с комиссией создателя на входе, из которых создатель получает 0,10%, а торговый бакет получает 0,25%.

Ставки торговой комиссии (`trade_fee_rate`, `protocol_fee_rate`, `fund_fee_rate`) и `creator_fee_rate` находятся на `AmmConfig`. Флаг `enable_creator_fee` для каждого пула и режим `creator_fee_on` (с какой стороны своп берётся комиссия создателя) находятся на `PoolState`. См. [`products/cpmm/accounts`](/ru/products/cpmm/accounts).

## Ставки и единицы

Все ставки — это `u64`, выраженные в единицах `1 / FEE_RATE_DENOMINATOR`, где `FEE_RATE_DENOMINATOR = 1_000_000`.

- **`trade_fee_rate`** — доля **объёма своп**. `2500` ⇒ 0,25% соответствующей стороны (входа или выхода, в зависимости от `creator_fee_on` — см. раздел "С какой стороны своп берутся комиссии" ниже).
- **`creator_fee_rate`** — доля **объёма своп**, взимается **отдельно** от торговой комиссии. `1000` ⇒ 0,10% соответствующей стороны.
- **`protocol_fee_rate`** и **`fund_fee_rate`** — доли **торговой комиссии**, а не объёма. `120_000` ⇒ 12% торговой комиссии.

Параметры по умолчанию для `AmmConfig[index=0]` (пул "стандартный" 0,25%) на mainnet для справки:

| Поле | Значение | Эффективный процент |
|-------|----------|-------------------|
| `trade_fee_rate` | `2500` | 0,25% объёма (торговый бакет) |
| `protocol_fee_rate` | `120000` | 12% торговой комиссии ≈ **0,030% объёма** |
| `fund_fee_rate` | `40000` | 4% торговой комиссии ≈ **0,010% объёма** |
| `creator_fee_rate` | `0` (по умолчанию) | 0% (отдельный бакет) |
| → Эффективная доля LP | | **0,210% объёма** |

Таким образом, при своп на \$1000 против `AmmConfig[0]` с `enable_creator_fee = false`: \$2,50 общей торговой комиссии, из которых \$2,10 остаётся LP, \$0,30 идёт протоколу, \$0,10 фонду. Бакет создателя равен 0, потому что комиссия создателя отключена.

Если бы тот же пул имел `enable_creator_fee = true` и `creator_fee_rate = 1000` (0,10%), пользователь платит дополнительно \$1,00 в бакет создателя — взимается с той же стороны своп, настроенной `creator_fee_on` — всего \$3,50 комиссий. Торговый бакет и его распределение между протоколом/фондом остаются неизменными.

Проверьте текущие значения mainnet в `GET https://api-v3.raydium.io/main/cpmm-config` — ставки изменяются администратором и должны читаться свежими, а не жёстко кодироваться.

## Распределение в коде

```rust
// Переформулировано из raydium-cp-swap/programs/cp-swap/src/curve/{calculator,fees}.rs.
// Фактический код ветвится по `is_creator_fee_on_input`; обе ветви сохраняют
// инвариант, что creator_fee — это собственная ставка, никогда не часть trade_fee.

const FEE_RATE_DENOMINATOR_VALUE: u64 = 1_000_000;

pub struct FeeBreakdown {
    pub amount_in_after_fees: u64,    // вход минус все комиссии, взятые со стороны входа
    pub amount_out_after_fees: u64,   // выход минус любая комиссия создателя, взятая со стороны выхода
    pub trade_fee:    u64,            // → распределяется на LP / протокол / фонд ниже
    pub protocol_fee: u64,            // доля trade_fee
    pub fund_fee:     u64,            // доля trade_fee
    pub creator_fee:  u64,            // независимый бакет (сторона входа или выхода)
}

fn take_fees_on_input(
    amount_in: u64,
    trade_rate: u64,
    creator_rate: u64,
    protocol_rate: u64,
    fund_rate: u64,
) -> (u64 /* trade_fee */, u64 /* creator_fee */, u64 /* amount_in_after_fees */) {
    // Две ставки складываются, чтобы мы округлили один раз на объединённой комиссии,
    // затем распределили пропорционально — это чисто трюк округления/эффективности.
    // Распределение соблюдает ставки точно: creator_fee/trade_fee == creator_rate/trade_rate.
    let total_fee = ((amount_in as u128) * ((trade_rate + creator_rate) as u128))
        .div_ceil(FEE_RATE_DENOMINATOR_VALUE as u128) as u64;

    let creator_fee = ((total_fee as u128) * (creator_rate as u128)
                       / ((trade_rate + creator_rate) as u128)) as u64;
    let trade_fee   = total_fee - creator_fee;

    (trade_fee, creator_fee, amount_in - total_fee)
}

fn take_creator_fee_on_output(amount_out_swapped: u64, creator_rate: u64) -> (u64, u64) {
    // Когда creator_fee_on направляет комиссию создателя на сторону выхода,
    // trade_fee берётся на входе как одна ставка, и creator_fee
    // вычисляется против выхода кривой.
    let creator_fee = ((amount_out_swapped as u128) * (creator_rate as u128))
        .div_ceil(FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    (amount_out_swapped - creator_fee, creator_fee)
}

fn split_trade_fee(
    trade_fee: u64,
    protocol_rate: u64,
    fund_rate: u64,
) -> (u64 /* protocol_fee */, u64 /* fund_fee */) {
    let protocol_fee = (trade_fee as u128 * protocol_rate as u128
                        / FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    let fund_fee     = (trade_fee as u128 * fund_rate as u128
                        / FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    (protocol_fee, fund_fee)
}
```

Примечания:

- Общая комиссия на входе округляется **вверх**, чтобы пул никогда не недозарядил.
- Подраспределения `trade_fee` (протокол, фонд) округляются **вниз**, чтобы их сумма никогда не превышала `trade_fee`; остаток — доля LP.
- `lp_share = trade_fee − protocol_fee − fund_fee` (creator_fee **не** вычитается здесь, потому что это собственный бакет).
- Комиссия создателя берётся со входа или выхода в зависимости от `PoolState.creator_fee_on` (см. следующий раздел). Ставка остаётся неизменной в любом случае.

## С какой стороны своп берутся комиссии

CPMM имеет настройку `creator_fee_on` для каждого пула (`BothToken` / `OnlyToken0` / `OnlyToken1`), которая определяет, берётся ли комиссия создателя со **входа** или **выхода** данного своп. Вспомогательная функция `is_creator_fee_on_input(direction)` сворачивает это в булево значение для каждого своп:

| `creator_fee_on` | Своп `0 → 1` | Своп `1 → 0` |
|------------------|---------------|---------------|
| `BothToken` (`0`) | сторона входа | сторона входа |
| `OnlyToken0` (`1`) | сторона входа | сторона выхода |
| `OnlyToken1` (`2`) | сторона выхода | сторона входа |

Когда комиссия создателя находится на **стороне входа**, как торговая комиссия, так и комиссия создателя вычитаются из `amount_in` перед запуском кривой. Математика котировки: возьмите объединённую `trade_rate + creator_rate` со входа.

Когда комиссия создателя находится на **стороне выхода**, только торговая комиссия вычитается из `amount_in`; кривая производит выход без комиссии, затем комиссия создателя вычитается из этого выхода. Математика котировки: возьмите `trade_rate` со входа; возьмите `creator_rate` с выхода.

Сама торговая комиссия всегда берётся со стороны входа (стандартный паттерн Uniswap-V2). Только комиссия создателя может быть на выходе.

## Как "накопленные" комиссии взаимодействуют с кривой

Важный нюанс: **комиссии протокола, фонда и создателя физически остаются в хранилище** до вызова соответствующей инструкции `Collect*`. Но они исключаются из представления кривой о балансе хранилища.

Конкретная картина после одного своп:

```
raw_vault_0_balance = getTokenAccountBalance(vault_0).amount
                    = lp_entitled + protocol_fees_token0
                      + fund_fees_token0 + creator_fees_token0

curve_x = raw_vault_0_balance − (protocol_fees_token0
                                  + fund_fees_token0
                                  + creator_fees_token0)
```

Программа использует `curve_x` (и аналогичный `curve_y`) при проверке `k' ≥ k`. Это то, как комиссии, не относящиеся к LP, достигают своих направлений **без** увеличения доли LP в пуле.

Последствия, которые вы должны учитывать при проектировании:

- **Котировка по сырым балансам неправильна.** Если вы построите котировщик на основе `getTokenAccountBalance`, вы будете постоянно переоценивать цену, которую пул будет соблюдать. Всегда вычитайте накопленные комиссии или симулируйте через `SwapBaseInput` / API.
- **`CollectProtocolFee` не движет цену.** Он перемещает токены из хранилища *и* обнуляет счётчики `protocol_fees_token*`, поэтому `curve_x` и `curve_y` остаются неизменными.
- **Комиссии LP не накапливаются в счётчик.** Они неявны в балансе хранилища. Право LP на накопленные комиссии LP осуществляется путём сжигания токенов LP (т.е. через `Withdraw`) — нет `CollectLpFee`.

## Взаимодействие с комиссиями передачи Token-2022

Комиссии передачи Token-2022 применяются **монетой**, а не CPMM. Они действуют на каждую передачу токенов — своп, депозит, вывод и сборки `Collect*`. Математика торговой комиссии CPMM вычисляется против суммы, которая **фактически попала в хранилище**, т.е. за вычетом комиссии передачи входной монеты (если есть).

Таким образом, в худшем случае пользователь платит три отдельных налога на своп с точным входом:

1. Комиссия передачи входной монеты на `amount_in` (органу сбора комиссий монеты).
2. Комиссия `trade_fee` пула на остаток (распределяется как выше).
3. Комиссия передачи выходной монеты на `amount_out` (органу сбора комиссий монеты).

Котировщик SDK учитывает все три, поэтому `minimum_amount_out` выражается в том, что пользователь фактически получает. Если вы пишете свой собственный котировщик, отразите это поведение, иначе ваши проверки проскальзывания будут систематически слишком щедрыми.

См. [`algorithms/token-2022-transfer-fees`](/ru/algorithms/token-2022-transfer-fees) для подробного вывода.

## Комиссия создателя

Комиссия создателя опциональна и для каждого пула. **Ставка** находится на `AmmConfig.creator_fee_rate`; **флаг включения** и **сторона** (`creator_fee_on`) находятся на `PoolState`:

- **Включена при создании пула.** `Initialize` устанавливает `enable_creator_fee = false` по умолчанию; пулы, созданные через `InitializeWithPermission` (используется для выпусков LaunchLab и других контролируемых путей), могут передать `enable_creator_fee = true` и выбрать `creator_fee_on`.
- **Ставка общая с уровнем комиссии.** Сама ставка — это `AmmConfig.creator_fee_rate`, одно и то же значение для каждого пула, привязанного к этой конфигурации. Каждый пул затем решает, взимать ли её (`enable_creator_fee`) и с какой стороны своп взимать (`creator_fee_on`). Когда `enable_creator_fee = false`, эффективная ставка комиссии создателя пула равна нулю независимо от значения конфигурации (см. `PoolState::adjust_creator_fee_rate` в исходном коде).
- **Независима от торговой комиссии.** Комиссия создателя никогда не уменьшает доли LP / протокола / фонда — это собственная ставка, применяемая отдельно, накапливаемая в собственных счётчиках.
- **Собирается через `CollectCreatorFee` или `CollectCreatorFeePermissionless`.** Исходный путь требует подписи `PoolState.pool_creator`. Путь без разрешения позволяет любому плательщику запустить сборку, но фиксирует оба направления на канонические ATA создателя.
- **Не может быть повторно включена или переведена после создания.** Пул, инициализированный с `enable_creator_fee = false`, никогда не будет взимать комиссию создателя; один, инициализированный с определённым `creator_fee_on`, не может переключать стороны.

Комиссии создателя — это механизм, стоящий за паттерном Raydium "Burn & Earn": токены LP заблокированы в программе [LP Lock](/ru/reference/program-addresses), поэтому создатель не может вывести ликвидность, но накопленные комиссии создателя всё ещё могут собираться бесконечно.

## Операционный поток сборки

| Подписант | Инструкция | Обнуляемые счётчики | Типичный интервал |
|--------|-------------|------------------------|-----------------|
| `amm_config.protocol_owner` | `CollectProtocolFee` | `protocol_fees_token{0,1}` | Еженедельно или программно |
| `amm_config.fund_owner` | `CollectFundFee` | `fund_fees_token{0,1}` | Еженедельно или программно |
| `pool_state.pool_creator` | `CollectCreatorFee` | `creator_fees_token{0,1}` | Когда угодно |
| Любой плательщик; создатель не подписывает | `CollectCreatorFeePermissionless` | `creator_fees_token{0,1}` | Когда угодно; ATA создателя — фиксированные направления |

Владельцы протокола и фонда — это мультиподпись Raydium на mainnet; см. [`security/admin-and-multisig`](/ru/security/admin-and-multisig). На исходном пути только для создателя подписант создателя — это учётная запись, записанная в `PoolState`. На пути без разрешения вызывающий платит за создание отсутствующего ATA создателя. Программа ограничивает `creator` до `pool_state.pool_creator` и выводит каждое направление из этого создателя плюс соответствующая монета хранилища и программа токенов, поэтому вызывающий не может перенаправить средства.

## Изменение уровня комиссии

Ставки комиссии могут быть изменены администратором через `UpdateAmmConfig` (см. [`products/cpmm/instructions`](/ru/products/cpmm/instructions)). Изменения вступают в силу при **следующем своп** для каждого пула, привязанного к этому `AmmConfig` — нет миграции, потому что пулы загружают конфигурацию при каждом своп.

Что администратор не может сделать:

- Переместить пул из одного `AmmConfig` в другой.
- Переоценить уже накопленные комиссии задним числом.
- Собрать комиссии без подписи `protocol_owner` / `fund_owner`.

## Чтение комиссий из работающего пула

```ts
// Off-chain: текущие накопленные комиссии в каждом бакете
const pool = await connection.getAccountInfo(poolStatePda);
const decoded = PoolState.decode(pool.data);
console.log(
  "Protocol accrued:",
  decoded.protocolFeesToken0.toString(),
  decoded.protocolFeesToken1.toString(),
);
console.log(
  "Fund accrued:",
  decoded.fundFeesToken0.toString(),
  decoded.fundFeesToken1.toString(),
);
console.log(
  "Creator accrued:",
  decoded.creatorFeesToken0.toString(),
  decoded.creatorFeesToken1.toString(),
);

// Off-chain: эффективные ставки сегодня.
// trade_fee_rate, creator_fee_rate — доли объёма (знаменатель 1e6).
// protocol_fee_rate, fund_fee_rate — доли *торговой комиссии* (тот же знаменатель).
const config = await fetch("https://api-v3.raydium.io/main/cpmm-config")
  .then((r) => r.json());
const tier = config.data.find((t) => t.index === decoded.ammConfigIndex);

const tradeFeeOfVolume   = tier.tradeFeeRate / 1_000_000;
const protocolOfTradeFee = tier.protocolFeeRate / 1_000_000;
const fundOfTradeFee     = tier.fundFeeRate / 1_000_000;
const lpOfTradeFee       = 1 - protocolOfTradeFee - fundOfTradeFee;

console.log("LP fee effective:",       (tradeFeeOfVolume * lpOfTradeFee * 100).toFixed(4), "%");
console.log("Protocol fee effective:", (tradeFeeOfVolume * protocolOfTradeFee * 100).toFixed(4), "%");
console.log("Fund fee effective:",     (tradeFeeOfVolume * fundOfTradeFee * 100).toFixed(4), "%");
console.log(
  "Creator fee effective:",
  decoded.enableCreatorFee
    ? ((tier.creatorFeeRate / 1_000_000) * 100).toFixed(4) + " %"
    : "0 % (disabled on this pool)",
);
```

## Сравнение с CLMM и AMM v4

См. [`reference/fee-comparison`](/ru/reference/fee-comparison) для матрицы рядом. Краткое резюме:

- **AMM v4** использует фиксированную торговую комиссию 0,25% с другим распределением LP/протокола и без комиссии фонда.
- **CLMM** комиссии — это уровни по интервалам тиков, накапливаются по позициям (не по пулам) и собираются через `DecreaseLiquidity` или `CollectFees`.
