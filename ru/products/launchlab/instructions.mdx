## Инвентарь инструкций

| Группа | Инструкция | Может вызвать |
|-------|-------------|-------------|
| Глобальная конфигурация | `CreateConfig` / `UpdateConfig` | Администратор программы; делегированный орган создания конфигурации также может вызвать `CreateConfig` |
| Жизненный цикл запуска | `Initialize` | **Никто — она всегда падает с `NotApproved`.** Сохранена только для того, чтобы дискриминатор оставался занятым и IDL оставался стабильным. Используйте `InitializeV2`. |
| Жизненный цикл запуска | `InitializeV2` | Любой (создатель) — базовый минт SPL Token; записывает `amm_creator_fee_on` для будущего выпуска CPMM и принимает минт котировки Token-2022. |
| Жизненный цикл запуска | `InitializeWithToken2022` | Любой (создатель) — базовый минт Token-2022, опциональный `TransferFeeConfig`; принимает любую программу токена котировки |
| Торговля | `BuyExactIn` / `BuyExactOut` | Любой — точный вход / точный выход покупки на кривой связи |
| Торговля | `SellExactIn` / `SellExactOut` | Любой — точный вход / точный выход продажи на кривой связи |
| Выпуск | `MigrateToAmm` | Кошелек миграции — устаревший выпуск AMM v4 для пулов, инициализированных до того, как было принято создание только CPMM. С 2026-09 не принимает аргументы и аккаунты OpenBook. |
| Выпуск | `MigrateToCpswap` | Кошелек миграции — выпуск в CPMM. Все вновь инициализированные запуски используют этот путь. Оборачивает `InitializeWithPermission` на CPMM. |
| Комиссии | `CollectFee` | Администратор — сбор комиссий протокола из запуска |
| Комиссии | `CollectMigrateFee` | Администратор — сбор накопленных комиссий миграции |
| Комиссии | `ClaimCreatorFee` | Создатель — получение накопленных комиссий создателя во время фазы кривой |
| Вестинг | `CreateVestingAccount` | Создатель — выделение заблокированных токенов бенефициару, разблокированных после выпуска |
| Вестинг | `CreatePlatformVestingAccount` | Администратор платформы — выделение заблокированных токенов бенефициарам на стороне платформы |
| Вестинг | `ClaimVestedToken` | Бенефициар — получение разблокированных токенов после cliff |
| Конфигурация платформы | `CreatePlatformConfig` / `UpdatePlatformConfig` | Администратор платформы |
| Конфигурация платформы | `CreatePlatformCurveRule` / `UpdatePlatformCurveRule` / `RemovePlatformCurveRule` / `ClosePlatformCurveRule` | `PlatformConfig.curve_rule_manager` или администратор платформы — управление правилом параметров запуска одного `GlobalConfig` |
| Комиссии платформы | `ClaimPlatformFee` / `ClaimPlatformFeeFromVault` | Администратор платформы |
| Доступ платформы | `CreatePlatformAllowConfig` / `ClosePlatformAllowConfig` | Администратор платформы — управление списком разрешений `GlobalConfig`, используемым при включении ограничения платформой |
| Рента | `CollectExcessLamports` | Администратор программы или выделенный кошелек сбора lamports — сбор lamports выше минимума, освобожденного от аренды, из хранилищ и PDA, контролируемых LaunchLab. Добавлено в 2026-09. |

Разделение "ExactIn/ExactOut" отражает `SwapBaseInput` / `SwapBaseOutput` CPMM — на цепи это отдельные дискриминаторы инструкций с немного другим округлением.

**Выбор пути выпуска.** Каждый новый вызов `InitializeV2` и `InitializeWithToken2022` должен установить `migrate_type = 1` (`CPSWAP`). Любая попытка инициализировать новый пул, привязанный к AMM v4, возвращает `MigrateTypeNotMatch`. `amm_creator_fee_on` только выбирает, применяется ли результирующая комиссия создателя CPMM к токену котировки или обоим токенам; он не выбирает целевую программу. Устаревший `Initialize` вообще не может создать запуск (см. ниже).

`MigrateToAmm` остается вызываемым для существующего `PoolState`, который был инициализирован с `migrate_type = 0` до этого ограничения. Выпуск не переписывает существующее состояние пула и не удаляет устаревшую инструкцию.

**Программа токена на стороне котировки.** Минт котировки может принадлежать либо программе SPL Token, либо Token-2022. Каждая инструкция, которая его касается — `CreateConfig`, `InitializeV2`, `InitializeWithToken2022`, все четыре инструкции торговли, `CollectFee`, `CollectMigrateFee`, `ClaimCreatorFee`, `ClaimPlatformFee` и `ClaimPlatformFeeFromVault` — принимает владеющую программу в слот своего аккаунта quote-program. Позиции аккаунтов не изменились; изменилось только принимаемое значение. Передайте программу, которая фактически владеет `GlobalConfig.quote_mint`, которую вы можете прочитать из бита1 `PoolState.token_program_flag` для существующего запуска (см. [`accounts`](/ru/products/launchlab/accounts#poolstate)) или из владельца аккаунта минта в противном случае.

Устаревший `Initialize` здесь неуместен: его аккаунт quote-program по-прежнему типизирован как SPL Token, и с обновлением 2026-09 инструкция падает перед чтением любого аккаунта. Запустите через `InitializeV2` или `InitializeWithToken2022`.

`MigrateToCpswap` — другое исключение, в противоположном направлении — он принимает **обе** программы безусловно, а не одну на минт. См. [аккаунты миграции ниже](#cpmm-migration-token-programs).

## `Initialize`

<Warning>
  **Удалено фактически с обновлением 2026-09 — эта инструкция всегда падает.** Обработчик `initialize` теперь представляет собой просто логирование `Not supported. Please use initialize_v2 instruction` и `NotApproved` (`6000`). Она сохранена исключительно для того, чтобы ее дискриминатор оставался занятым и IDL сохранял стабильную форму. (Структура `Accounts` не изменилась, поэтому сгенерированная Anchor валидация все еще выполняется первой; транзакция откатывается в любом случае.)

  Ранее она была заблокирована на часах: она работала до трех дней после переключения `get_upgrade_timestamp` и падала после. Этот помощник временных меток исчез, поэтому отказ теперь безусловный. Существующие запуски, созданные через нее, не затронуты — они торгуют и выпускаются нормально через `MigrateToAmm` или `MigrateToCpswap` в зависимости от их сохраненного `migrate_type`.

  Аргументы и список аккаунтов ниже сохранены для декодирования исторических транзакций. Используйте `InitializeV2` для всего нового — она принимает ту же форму плюс `amm_creator_fee_on` и отдельный аккаунт quote-token-program.
</Warning>

Создайте новый запуск. `InitializeV2` имеет ту же форму ниже и добавляет `amm_creator_fee_on` плюс отдельный аккаунт quote-token-program.

**Аргументы**

```
launch_params: {
    curve_type:                 u8,
    base_supply_max:            u64,
    base_supply_graduation:     u64,
    k:                          u128,              // или initial_virtual_quote_reserve для curve_type=1
    open_time:                  u64,
    quote_mint:                 Pubkey,
    base_token_metadata: {                         // встроенные name/symbol/uri; программа CPI в Metaplex
        name:   String,
        symbol: String,
        uri:    String,
    },
    fees: {
        buy_numerator:   u64,
        buy_denominator: u64,
        sell_numerator:  u64,
        sell_denominator: u64,
        lp_share:        u64,
        creator_share:   u64,
        protocol_share:  u64,
        total_share:     u64,
    },
    post_graduation_lp_policy:  u8,                // 0 = Burn, 1 = Lock, 2 = ToCreator
}
```

**Аккаунты** (сокращенно)

| # | Имя | W | S | Примечания |
|---|------|---|---|-------|
| 1 | `creator` | W | S | Платит за ренту + создание базового минта. |
| 2 | `launch_config` |   |   | Привязка конфигурации протокола. |
| 3 | `launch_state` | W |   | Новый аккаунт. |
| 4 | `launch_authority` |   |   | PDA. |
| 5 | `base_mint` | W | S | Свежая Keypair (или PDA) — эта инструкция инициализирует ее. |
| 6 | `base_vault` | W |   | ATA `launch_authority` на `base_mint`. |
| 7 | `quote_mint` |   |   | |
| 8 | `quote_vault` | W |   | ATA `launch_authority` на `quote_mint`. |
| 9 | `metadata` | W |   | Metaplex metadata PDA. |
| 10 | `metaplex_program` |   |   | |
| 11 | `token_program` |   |   | SPL Token для базового минта. `InitializeV2` и `InitializeWithToken2022` принимают отдельный аккаунт quote-program, который может быть любой программой. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

**Предусловия**

- `quote_mint ∈ launch_config.allowed_quote_mints`.
- `base_supply_graduation ≤ base_supply_max`.
- Параметры комиссии проходят проверки `launch_config.max_*_fee_rate`.
- `open_time ≥ now − slop` (SDK требует `≥ now`; программа допускает небольшое обратное датирование).
- `curve_type` распознан.

**Постусловия**

- `base_mint` имеет `supply = base_supply_max`, все в `base_vault`.
- `base_mint.mint_authority = launch_authority`, `freeze_authority = None`.
- `LaunchState` инициализирован с `status = Active`, `base_sold = 0`, `quote_reserve_real = 0`.
- `quote_reserve_target` вычислен из параметров кривой + `base_supply_graduation` + `buy_numerator` (приблизительно).
- Для `InitializeWithToken2022` с прикрепленным `TransferFeeConfig`: `transfer_fee_config_authority = launch_authority`, и `withdraw_withheld_authority = PlatformConfig.transfer_fee_extension_auth` когда это поле установлено, иначе `launch_authority`. Сторона вывода записывается при создании минта именно для того, чтобы платформа могла собрать удержанные комиссии перед выпуском. См. [`platform-config`](/ru/products/launchlab/platform-config#token-2022-transfer-fee-authorities).

**Распространенные ошибки** — `InvalidQuoteMint`, `FeeRateTooHigh`, `InvalidCurveParams`, `MathOverflow`.

## `Buy` (канонический вариант: `BuyExactIn`)

Пользователь предоставляет фиксированный `quote_in`; кривая вычисляет `base_out`.

**Аргументы**

```
quote_in:          u64
minimum_base_out:  u64
```

**Аккаунты**

| # | Имя | W | S |
|---|------|---|---|
| 1 | `user` | W | S |
| 2 | `launch_state` | W |   |
| 3 | `launch_authority` |   |   |
| 4 | `base_vault` | W |   |
| 5 | `quote_vault` | W |   |
| 6 | `user_base_ata` | W |   |
| 7 | `user_quote_ata` | W |   |
| 8 | `base_mint` |   |   |
| 9 | `quote_mint` |   |   |
| 10 | `token_program` |   |   |
| 11 | `associated_token_program` |   |   |
| 12 | `system_program` |   |   |

**Предусловия**

- `launch_state.status == Active`.
- `now ≥ open_time`.
- `user_quote_ata.balance ≥ quote_in`.
- `quote_in > 0`.

**Эффект**

1. Разделите `quote_in` на `quote_in_after_fee` и части комиссии.
2. Newton-решите кривую для `base_out` с учетом post-fee котировки.
3. `require(base_out ≥ minimum_base_out)` иначе откатите `ExceededSlippage`.
4. Переместите `quote_in` пользователь → хранилище. Переместите `base_out` хранилище → пользователь.
5. Обновите `base_sold += base_out`, `quote_reserve_real += quote_in_after_fee × (lp_share / total_share)`.
6. Обновите счетчики комиссий (`protocol_fees_quote`, `creator_fees_quote`).
7. `state_data.num_buys += 1`.
8. Если `quote_reserve_real ≥ quote_reserve_target` после обновления, SDK обычно цепляет инструкцию `Graduate` в той же транзакции. Программа не автоматически выпускает внутри `Buy` — требуется последующий `Graduate`.

## `BuyExactOut`

Пользователь указывает точный `base_out`; программа вычисляет `quote_in`.

**Аргументы**

```
base_out:      u64
maximum_quote_in: u64
```

Те же аккаунты, что и `BuyExactIn`. Использует замкнутую форму квадратичного интеграла (или обратный CPMM для curve_type 1) вместо итерации Newton.

## `Sell` / `SellExactIn` / `SellExactOut`

Зеркало `Buy`. Пользователь возвращает `base_in` кривой и получает `quote_out`. Комиссия вычитается из `quote_out`, поэтому пользователь получает меньше, чем сырые интегрированные доходы.

**Предусловия** —

- `user_base_ata.balance ≥ base_in`.
- Продажа не может опустить `base_sold` ниже 0 (избыточно с вышеизложенным при условии, что учет согласован).
- Запуск `Active`.

**Эффект** — симметричен `Buy`. `base_sold` уменьшается, `quote_reserve_real` уменьшается. Комиссии по-прежнему начисляются.

### Комиссии за передачу на стороне котировки

Когда минт котировки несет `TransferFeeConfig`, сумма, которую перемещает хранилище, и сумма, которая дебетуется или кредитуется плательщику, отличаются, и граница проскальзывания проверяется против стороны плательщика. На минте котировки без расширения каждый случай ниже идентичен простому устаревшему минту.

| Инструкция | Аргумент | Проверено против |
|---|---|---|
| `BuyExactIn` | `amount_in` | Кривая оценивается на `amount_in − transfer_fee(amount_in)` — что достигает хранилища. Полное заполнение дебетует ровно `amount_in`; частичное заполнение дебетует потребленную сумму хранилища плюс его обратную комиссию. |
| `BuyExactOut` | `maximum_amount_in` | Сумма хранилища **плюс** обратная комиссия за передачу — реальный дебет. |
| `SellExactIn` | `minimum_amount_out` | Что продавец сохраняет после удержания монетой, не валовая сумма, покидающая хранилище. |
| `SellExactOut` | `amount_out` | Доставлено ровно. Кривая нацелена на `amount_out` плюс обратная комиссия за передачу. |

Два следствия для котирования:

- Граница, вычисленная так, как если бы минт был без комиссии, отклоняется. Передача свободной от комиссии стоимости как `maximum_amount_in` или свободных от комиссии доходов как `minimum_amount_out` откатывает с `ExceededSlippage`.
- `real_quote` продвигается только на то, что достигло хранилища. `BuyExactIn` из `amount_in` на 5% минте котировки перемещает `real_quote` на `amount_in × 0.95`.

Минт котировки со 100% комиссией (`10000` базовых пунктов) не может быть инвертирован и откатывает с `CalculateOverflow` на путях exact-out.

Оба минта на стороне торговли также ограничены программой, переданной в их соответствующий слот, поэтому несоответствие `base_token_program` теперь падает вместо игнорирования. См. [`algorithms/token-2022-transfer-fees`](/ru/algorithms/token-2022-transfer-fees) для базовой математики комиссий.

### Оставшиеся аккаунты торговли

Все четыре инструкции торговли принимают свою сантехнику комиссий через `remaining_accounts` в этом порядке:

| Индекс | Аккаунт | Когда |
|---|---|---|
| 0 | `share_fee_receiver` | Только когда `share_fee_rate > 0`. Сдвигает каждый индекс ниже на один при наличии. |
| next | `system_program` | Всегда. Финансирует создание хранилища комиссий. |
| next | `platform_fee_vault` | Всегда. PDA с семенами `[platform_config, quote_token_mint]`, создана при первом использовании. |
| next | `creator_fee_vault` | Всегда. PDA с семенами `[creator, quote_token_mint]`, создана при первом использовании. |

<Note>
  **Изменено в 2026-09: последние три теперь безусловны, и `system_program` проверяется.** До этого выпуска программа читала их только когда `unix_timestamp >= get_upgrade_timestamp()` и полностью пропускала разделение комиссий платформы/создателя до этого момента. Временная метка давно прошла, поэтому поведение на mainnet практически не изменилось — но ветвь удалена из кода, и построитель, который все еще опускает три аккаунта, теперь всегда падает с `NotEnoughRemainingAccounts` (`6018`) вместо только после переключения. Слот `system_program` дополнительно проверяется против `System::id()` и возвращает `InvalidInput` (`6002`) если он содержит что-то еще, где ранее любой аккаунт был принят в этой позиции.
</Note>

## `MigrateToAmm` / `MigrateToCpswap`

Выпустите запуск в торгуемый пул после того, как кривая достигла `total_quote_fund_raising`. Новые запуски только CPMM. `MigrateToAmm` сохранен для существующих пулов, чей сохраненный `migrate_type` равен `0`.

**Кто подписывает**

- `MigrateToAmm` — `migrate_to_amm_wallet`, записанный на привязке `GlobalConfig`.
- `MigrateToCpswap` — `migrate_to_cpswap_wallet`, записанный на привязке `GlobalConfig`.

Эти кошельки обычно удерживаются операционным кранком выпуска Raydium; на практике выпуск происходит секунды после пересечения порога, независимо от того, кто запустил финальную покупку.

**Аргументы**

Ни один не принимает никаких.

<Warning>
  **Критическое изменение (только кошелек миграции, 2026-09).** `MigrateToAmm` отбросил все три аргумента — `base_lot_size`, `quote_lot_size`, `market_vault_signer_nonce` — **и девять аккаунтов**. Его данные инструкции теперь просто дискриминатор, поэтому старый построитель отправляет 17 неожиданных байтов аргумента и предоставляет список аккаунтов, который больше не совпадает.

  Это следует за собственным [удалением OpenBook](/ru/reference/changelog/2026-07-22-amm-v4-openbook-removal) AMM v4: `Initialize2` AMM v4 больше не принимает `market_program` или `amm_open_orders`, поэтому LaunchLab не имел ничего для пересылки. Программа также перестала CPI-ить `initialize_openbook_market`, что конфигурировали три аргумента.

  Удаленные аккаунты: `openbook_program`, `request_queue`, `event_queue`, `bids`, `asks`, `market_vault_signer`, `market_base_vault`, `market_quote_vault` и `amm_open_orders`. Аккаунт `market` **остается** в своей позиции — AMM v4 по-прежнему записывает его как поле ссылки — но теперь он объявлен как простой `#[account(mut)]`: без ограничений владельца, адреса или семян. Он полностью не проверяется, он пересылается прямо в CPI AMM v4 `Initialize2`, и программа больше его не инициализирует. Вызывающий, который хочет, чтобы аккаунт market был реально инициализированным рынком, должен создать его сам заранее.

  Оставшийся список из 23 аккаунтов в порядке: `payer`, `base_mint`, `quote_mint`, `market`, `amm_program`, `amm_pool`, `amm_authority`, `amm_lp_mint`, `amm_base_vault`, `amm_quote_vault`, `amm_target_orders`, `amm_config`, `amm_create_fee_destination`, `authority`, `pool_state`, `global_config`, `base_vault`, `quote_vault`, `pool_lp_token`, `spl_token_program`, `associated_token_program`, `system_program`, `rent_program`.

  `MigrateToCpswap` не затронут — он никогда не имел аргументов.
</Warning>

**Эффект (общий для обоих)**

1. Проверьте `pool_state.status == Migrate` (т.е. `quote_reserve_target` был достигнут). Иначе откатите с `PoolMigrated` (статус уже был `Migrated`) или `PoolFunding` (все еще в финансировании).
2. Проверьте `pool_state.migrate_type` соответствует инструкции (`0` для AMM, `1` для CPMM). Иначе откатите с `MigrateTypeNotMatch`.
3. Вычислите резервы после выпуска:
   - `base_amount_out = base_vault.amount − vesting_schedule.total_locked_amount`
   - `quote_amount_out = quote_vault.amount − quote_protocol_fee − migrate_fee − platform_fee`
4. CPI в целевую программу (`AMM v4 Initialize2` или `CPMM InitializeWithPermission`) с этими резервами для создания пула после выпуска.
5. Для миграций CPMM, выполненных после обновления 2026-08-17, объедините `platform_scale + creator_scale` в одну заблокированную долю LP, принадлежащую платформе, и отчеканьте максимум один Fee Key NFT в `platform_nft_wallet`. Сожгите остаток `burn_scale`. До обновления `creator_scale` был заблокирован отдельно и его Fee Key перешел создателю токена. Завершенные исторические миграции не изменяются. Для устаревшего выпуска AMM v4 расположение LP следует существующему потоку этой инструкции.
6. (Нет шага mint-authority. `base_mint.mint_authority` уже был установлен на `None` при создании запуска — см. примечание ниже.)
7. Переверните `pool_state.status = Migrated`, установите `vesting_schedule.start_time = block_time + cliff_period`.

**Передача прав расширения Token-2022** — когда базовый минт является минтом Token-2022, несущим `TransferFeeConfig` **и** `PlatformConfig.transfer_fee_extension_auth` не по умолчанию, миграция также переназначает права этого расширения ключу платформы:

- `transfer_fee_config_authority` всегда переназначается. PDA запуска `authority` держит его на всю фазу до выпуска, поэтому всегда есть что переместить.
- `WithheldWithdraw` переназначается **только когда PDA `authority` все еще его держит**. Запуски, созданные с 2026-08-27 и позже, уже несут `transfer_fee_extension_auth` на этом органе от создания минта, поэтому шаг пропускается. Охрана — это то, что предотвращает откат миграции на этих минтах — PDA не может отказаться от права, которое оно больше не держит.

Если `transfer_fee_extension_auth` равен `Pubkey::default()` во время миграции, ни один орган не движется и оба остаются с PDA `authority` навсегда. См. [`platform-config`](/ru/products/launchlab/platform-config#token-2022-transfer-fee-authorities).

<Note>
  **Предложение базового минта фиксируется с момента создания, а не с момента выпуска.** `InitializeV2` и `InitializeWithToken2022` чеканят всю предложение в базовое хранилище и затем немедленно отзывают `MintTokens` в той же инструкции, поэтому `base_mint.mint_authority` равен `None` на всю жизнь запуска. Миграция его не касается. (Более ранние версии этой страницы размещали отзыв при выпуске; это было неправильно.) Единственные права, которые миграция может переместить, — это описанные ниже права Token-2022 transfer-fee.
</Note>

**Постусловия** — `BuyExactIn`, `BuyExactOut`, `SellExactIn`, `SellExactOut` будут отклонять с этого момента с `PoolMigrated`. Результирующий пул AMM канонический и торгует как любой другой пул AMM v4 / CPMM.

**Распространенные ошибки** — `PoolFunding`, `PoolMigrated`, `MigrateTypeNotMatch`, `InvalidCpSwapConfig`, `MathOverflow`.

### Оставшиеся аккаунты миграции CPMM

Клиенты, строящие `MigrateToCpswap`, должны использовать эти фиксированные индексы `remaining_accounts`:

| Индекс | Аккаунт |
|---|---|
| 0–4 | Владелец Fee Key платформы, минт, аккаунт токена, PDA заблокированной ликвидности и аккаунт метаданных |
| 5 | Оригинальный создатель запуска; используется когда `platform_cp_creator` не установлен |
| 6 | PDA разрешения CPMM, полученный из `[b"permission", launch_authority]` |
| 7 | Сконфигурированный `platform_cp_creator`; используется когда поле не по умолчанию |
| 8 | PDA поддержки-минта CPMM для отсортированного `mint0`, полученный из `[b"support_mint", mint0]` |
| 9 | PDA поддержки-минта CPMM для отсортированного `mint1`, полученный из `[b"support_mint", mint1]` |

Инструкция требует минимум десять оставшихся аккаунтов. Аккаунты поддержки-минта — это входы CPI только для чтения. Получите оба адреса даже когда минт не имеет инициализированной записи поддержки. Старые построители, которые все еще добавляют аккаунты блокировки создателя или опускают индексы 8–9, должны быть обновлены.

<Note>
  **Изменено в 2026-09.** Две очистки, ни одна из которых не изменяет правильного построителя:

  - **Путь разрешенного CPMM теперь единственный путь.** `MigrateToCpswap` раньше выбирал между `InitializeCpSwap` и `InitializeCpSwapWithPermission` на основе `unix_timestamp >= get_upgrade_timestamp()`. Помощник временных меток и устаревший CPI оба исчезли, поэтому путь разрешения — и, следовательно, минимум десять аккаунтов — применяется безусловно.
  - **Три ограничения адреса переместились из структуры аккаунта в тело инструкции.** `platform_config`, `base_vault` и `quote_vault` по-прежнему требуются для соответствия значениям, сохраненным на `PoolState`, но несоответствие теперь поднимается `require_keys_eq!` вместо ограничения Anchor `address =`. Проверка эквивалентна; только поверхность ошибок отличается — вы получаете общий `RequireKeysEqViolated` (`2502`) Anchor вместо `ConstraintAddress` (`2012`), и он сообщается без имени аккаунта. Обновите любую обработку ошибок, которая совпадала с `2012` для этих трех аккаунтов.
</Note>

### Программы токенов миграции CPMM

`MigrateToCpswap` принимает обе программы токенов безусловно и сам определяет, какая программа владеет каждым минтом. Его два аккаунта программы токенов были переименованы соответственно:

| Позиция | Аккаунт | Значение |
|---|---|---|
| первый | `token_program` | Всегда программа SPL Token |
| второй | `token_program_2022` | Всегда программа Token-2022 |

Они заменяют бывший `base_token_program` (какая бы программа ни владела базовым минтом) и `quote_token_program` (всегда устаревший). Позиции не изменились, поэтому это изменение значения, а не изменение макета — но два значения близки к инвертированным, и построитель, который продолжает передавать свою старую пару, будет поставлять Token-2022 где требуется программа устаревшего, как только любой минт будет минтом Token-2022.

Программа устаревшего требуется даже когда ни один минт ее не использует, потому что минт LP CPMM и заблокированный Fee Key NFT ликвидности всегда живут на нем.

## Список разрешений `GlobalConfig` платформы

`PlatformConfig.restrict_global_config` контролирует проверку:

- `0`: платформа принимает любой иначе действительный `GlobalConfig`; аккаунт разрешения не требуется.
- `1`: `Initialize`, `InitializeV2` и `InitializeWithToken2022` должны включать соответствующий `PlatformAllowConfig` где-нибудь в `remaining_accounts`.

Администратор платформы создает или закрывает PDA с `CreatePlatformAllowConfig` и `ClosePlatformAllowConfig`. Его семена — `[b"platform_allow_config", platform_config, global_config]`. Бывшие управляемые администратором инструкции `PlatformGlobalAccess` и PDA вышли на пенсию.

## Правила параметров запуска платформы

Четыре инструкции управляют одним аккаунтом `PlatformCurveRule`. Все четыре подписаны `PlatformConfig.curve_rule_manager` или администратором платформы — программа принимает администратора путем повторного получения PDA `PlatformConfig` от подписывающего, поэтому отдельный аккаунт это не доказывает. Подписывающий, который ни то ни другое, возвращает `InvalidCurveRuleAuthority`.

| Инструкция | Аккаунты | Аргументы |
|---|---|---|
| `CreatePlatformCurveRule` | `curve_rule_authority` (подписывающий, mut), `platform_config`, `global_config`, `platform_curve_rule` (mut), `system_program` | нет |
| `UpdatePlatformCurveRule` | те же пять | `group_id: u16`, `constraints: Vec<ParamConstraint>` |
| `RemovePlatformCurveRule` | те же пять | `group_id: u16` |
| `ClosePlatformCurveRule` | первые четыре | нет |

`platform_curve_rule` — это PDA в `[b"platform_curve_rule", platform_config, global_config]`.

- **`Create`** выделяет аккаунт, не содержащий группу. Это состояние ничего не ограничивает.
- **`Update`** вставляет группу с этим `group_id`, полностью заменяя ее, если она существует. Он изменяет размер аккаунта, чтобы он подходил, поэтому подписывающий пополняет ренту, которую он растет, и получает обратно ренту, которую он сжимает. Новая группа сверх десятой возвращает `CurveRuleGroupsExceeded`; более 25 ограничений, неизвестное поле или оператор, или одна и та же пара `(field, op)` дважды в одной группе возвращает `InvalidCurveRuleConstraint`; четыре поля, полученные из `TotalSellA`, на конфигурации без постоянного произведения возвращают `CurveRuleFieldNotSupportedByCurve`.
- **`Remove`** удаляет одну группу по id, сжимая аккаунт и возвращая разницу. Неизвестный id возвращает `CurveRuleGroupNotExist`.
- **`Close`** возвращает всю ренту подписывающему. Конфигурация затем снова не ограничена, даже если `restrict_curve_param` остается `1`.

Ни один из четырех не изменяет, применяются ли правила. Это `UpdatePlatformConfig::RestrictCurveParam(0 | 1)`, который может вызвать только администратор платформы.

**На пути запуска.** Пока `restrict_curve_param` равен `1`, `InitializeV2` и `InitializeWithToken2022` требуют PDA правила в `remaining_accounts` — включая когда он не существует, чтобы его опущение не могло пропустить проверку. Отсутствующий аккаунт — это `NotEnoughRemainingAccounts`; запуск, который не удовлетворяет никакой группе, — это `CurveParamNotMatchPlatformRule`. Проверка выполняется перед собственными ограничениями `GlobalConfig` и может только их сузить. Модель и сборники: [`products/launchlab/curve-rules`](/ru/products/launchlab/curve-rules). Обе ошибки избежны на стороне клиента — SDK отражает эту проверку как чистую функцию, см. [Проверьте перед отправкой](/ru/products/launchlab/curve-rules#check-before-you-send).

## `CollectExcessLamports`

Сбор администратором lamports, сидящих выше минимума, освобожденного от аренды, на аккаунтах, которые контролирует LaunchLab. Добавлено в обновлении 2026-09, чтобы протокол мог вернуть избыточное финансирование, которое [SIMD-0437 снижение аренды](/ru/solana-fundamentals/rent-and-reclaimable-rent) оставляет на аккаунтах, созданных до каждого шага.

Движется только избыток. Балансы токенов, данные аккаунта, владельцы, состояние кривой и вестинг не затронуты, и инструкция — это no-op для аккаунта, уже находящегося на минимуме — поэтому безопасно переустанавливать после каждого шага развертывания.

**Аргументы** — нет.

**Аккаунты**

| # | Имя | W | S | Примечания |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Пункт назначения для каждого собранного lamport. Должен быть либо администратором программы LaunchLab, либо выделенным кошельком сбора lamports — см. [`reference/program-addresses`](/ru/reference/program-addresses#excess-lamports-collection-wallets). Любой другой подписывающий падает с `InvalidOwner` (`6001`). |
| 2 | `authority` |   |   | **Один** из трех PDA органов хранилища LaunchLab (см. ниже). Подписывает CPI программы токенов для каждого аккаунта токена в этом вызове. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Оба требуются безусловно; программа выбирает по исходному аккаунту. |
| 5.. | `remaining_accounts` | W |   | `M` исходных аккаунтов для сбора, любое количество, любой порядок. |

**Выбор `authority`**

Аккаунт передается непроверенным и разрешается программой, которая повторно получает все три PDA органов LaunchLab и совпадает:

| Семя | Владеет |
|---|---|
| `[b"vault_auth_seed"]` | Каждое хранилище базового и котировочного пула запуска |
| `[b"platform_fee_vault_auth_seed"]` | Каждое хранилище комиссий платформы |
| `[b"creator_fee_vault_auth_seed"]` | Каждое хранилище комиссий создателя |

Ключ, не совпадающий ни с одним из трех, падает всю инструкцию с `InvalidOwner` (`6001`).

<Warning>
  **Группируйте исходные аккаунты по органу.** Один вызов несет один `authority`, и программа токенов требует подписания фактического владельца аккаунта. Аккаунт токена, принадлежащий другому из трех PDA, чем переданный `authority`, делает CPI неудачным и берет всю транзакцию с собой. Собирайте хранилища пулов, хранилища комиссий платформы и хранилища комиссий создателя в отдельных транзакциях.

  Принадлежащие программе PDA — исключение — они дебетуются напрямую, поэтому они могут ехать с любым органом.
</Warning>

**Как обрабатывается каждый исходный аккаунт**

| Владелец исходного аккаунта | Обработка |
|---|---|
| SPL Token или Token-2022, аккаунт токена, не являющийся нативным | CPI `WithdrawExcessLamports` (дискриминант программы токенов `38`), подписано `authority`. |
| SPL Token или Token-2022, **нативный** (wSOL) аккаунт токена | `WithdrawExcessLamports` отклоняет нативные аккаунты. Программа CPI `SyncNative`, измеряет, насколько выросла обернутая `amount`, `UnwrapLamports` (дискриминант `45`) ровно на эту дельту, затем требует, чтобы обернутый баланс равнялся его значению перед синхронизацией — иначе `LamportsCalculateError` (`6031`). Запуск, котируемый в SOL, поэтому сохраняет свой полный резерв котировки. |
| Сама программа LaunchLab — `PoolState`, `GlobalConfig`, `PlatformConfig`, `VestingRecord`, `PlatformCurveRule`, `PlatformAllowConfig` | Программа дебетует аккаунт напрямую вниз до `rent.minimum_balance(data_len)`. |
| Что-либо еще | **Пропущено молча.** Нет ошибки, нет перемещенных lamports. |

**Базовые минты не могут быть собраны.** `InitializeV2` и `InitializeWithToken2022` отзывают `MintTokens` на базовом минте в той же инструкции, которая чеканит предложение, поэтому никакой ключ не может подписать `WithdrawExcessLamports` для него — рента минта остается там навсегда.

**Распространенные ошибки** — `InvalidOwner` (`6001`, неправильный подписывающий или `authority`, который не является ни одним из трех PDA), `LamportsCalculateError` (`6031`, круговой путь wSOL не привел к нулю) и `InsufficientFunds` из пути, принадлежащего программе, когда аккаунт содержит меньше, чем его собственный минимум аренды.

**Нет построителя SDK.** `@raydium-io/raydium-sdk-v2` не поставляет построитель для этой инструкции, и ни репо `raydium-sdk-V2-demo` — это путь администратора. Кодируйте вручную, как это делает сбор на стороне кошелька в [`solana-fundamentals/rent-and-reclaimable-rent`](/ru/solana-fundamentals/rent-and-reclaimable-rent#building-the-instruction) для инструкции программы токенов.
