| المبادلة | `SwapRouterBaseIn` | متعدد القفزات، يستخدمه الموجه. |

| أمر الحد | `DecreaseLimitOrder` | تقليل أو إلغاء أمر مفتوح؛ يدفع الباقي غير المملوء بالإضافة إلى أي مخرجات تم تسويتها بالفعل. |
| أمر الحد | `SettleLimitOrder` | دفع رموز الإخراج المملوءة إلى مالك الأمر. قابل للاستدعاء من قبل المالك أو حارس التشغيل. |
| أمر الحد | `CloseLimitOrder` | إغلاق حساب أمر مستهلك بالكامل. الإيجار يعود دائمًا إلى `owner` الأمر. قابل للاستدعاء من قبل المالك أو الحارس. |
| الرسوم | `CollectProtocolFee` | كنس إداري لرسوم البروتوكول. |
| الرسوم | `CollectFundFee` | كنس إداري لرسوم الصندوق. |
| المكافآت | `InitializeReward` | إرفاق تدفق مكافآت جديد بمجمع. |
| المكافآت | `SetRewardParams` | تغيير معدل الانبعاث/النهاية للمكافأة الموجودة. |
| المكافآت | `UpdateRewardInfos` | تسوية نمو المكافآت إلى الآن (يُستدعى بواسطة أي مبادلة / تغيير موضع). |
| المكافآت | `TransferRewardOwner` | نقل السلطة التي يمكنها تعيين أو تعبئة تدفق مكافآت. |
| المكافآت | `CollectRemainingRewards` | بعد `end_time` لتدفق المكافآت، كنس أي رموز غير مخصصة مرة أخرى إلى الممول. |
| المسؤول | `CloseSupportMintAssociated` | إزالة تسجيل `SupportMintAssociated` للـ mint واسترجاع إيجاره. |
| المسؤول | `CollectExcessLamports` | كنس lamports فوق الحد الأدنى المعفي من الإيجار من `PoolState` وخزانات مجمع واحد، بالإضافة إلى أي PDAs مملوكة لـ CLMM تم تمريرها. `admin` أو محفظة كنس lamports المخصصة. تمت الإضافة 2026-09. |

<Note>
  **لا توجد تعليمة init-tick-array، ولا حاجة لها.** يتم إنشاء مصفوفة علامة *داخل*
  `OpenPosition*` / `IncreaseLiquidity*` بواسطة `TickArrayState::get_or_create_tick_array`، مدفوعة من قبل
  `payer`. مرر PDA مصفوفة العلامة (ربما لا تزال غير مهيأة، مملوكة للنظام) كـ
  `tick_array_lower` / `tick_array_upper` والبرنامج يخصصها إذا كانت مفقودة.
  `OpenLimitOrder` يفعل الشيء نفسه لـ `tick_array` الواحد الخاص به.
</Note>

معظم التعليمات الإدارية فقط (`CreateAmmConfig`، `UpdateAmmConfig`، `UpdatePoolStatus`، `CreateOperationAccount`، `UpdateOperationAccount`، `CloseProtocolPosition`) محمية بمفتاح `admin` المشفر في البرنامج. `CreateSupportMintAssociated` / `CloseSupportMintAssociated` تقبل إما مفتاح `admin` **أو** مفتاح مالك دعم mint مخصص؛ `CollectExcessLamports` تقبل إما مفتاح `admin` **أو** محفظة كنس lamports مخصصة. تعليمات إدارة تدفق المكافآت (`TransferRewardOwner`، `CollectRemainingRewards`) محمية بممول المكافآت، وليس مسؤول البرنامج.

لاحقة V2 تعني "يدعم Token-2022 على الخزانات / NFT، يتطلب فتحة امتداد bitmap". يختار SDK V2 بشكل افتراضي للمجمعات الجديدة.

## `CreatePool`

**المعاملات**

```
sqrt_price_x64: u128           // السعر الأولي
open_time:      u64            // رفض المبادلات قبل هذا الوقت
```

**الحسابات (مختصرة)**

| # | الاسم | W | S | ملاحظات |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | فئة الرسوم المختارة. |
| 3 | `pool_state` | W |   | `init` هنا. |
| 4 | `token_mint_0` |   |   | مرتبة. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` هنا، مملوكة بواسطة PDA سلطة المجمع. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` هنا. |
| 9 | `tick_array_bitmap` | W |   | PDA `TickArrayBitmapExtension`؛ `init` هنا. |
| 10 | `token_program_0` |   |   | البرنامج الذي يمتلك `token_mint_0` — SPL Token **أو** Token-2022. |
| 11 | `token_program_1` |   |   | البرنامج الذي يمتلك `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  الفتحات 10 و 11 هي **لكل mint**، وليس "SPL Token ثم Token-2022". كل واحدة مقيدة بـ
  `mint::token_program` على mint المطابق، لذا بالنسبة لمجمع `token_mint_0` هو Token-2022 و
  `token_mint_1` هو SPL كلاسيكي يجب عليك تمرير Token-2022 في الفتحة 10 و SPL Token في الفتحة 11.
  `CreateCustomizablePool` و `CreateCustomizablePoolV2` تستخدم نفس الفتحتين.
</Warning>

**الشروط المسبقة**

- `token_mint_0 < token_mint_1` حسب ترتيب البايت.
- `amm_config.disable_create_pool == false`.
- لم يتم رفض Mints بواسطة قائمة السماح بامتداد Token-2022.

**الشروط اللاحقة**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`، `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (لا توجد مراكز حتى الآن).
- `pool_state.fee_on = FromInput` (الافتراضي القديم).
- `pool_state.dynamic_fee_info` مصفر (الرسوم الديناميكية معطلة).

## `CreateCustomizablePool`

موصى به للمجمعات الجديدة. نفس التأثير مثل `CreatePool` بالإضافة إلى وضع جمع الرسوم لكل مجمع واختيار رسوم ديناميكية اختياري.

**المعاملات**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**الحسابات** — بالضبط الـ 13 حساب المعلن عنها لـ `CreatePool`. `dynamic_fee_config` **ليس** حساب معلن عنه.

<Warning>
  عندما `enable_dynamic_fee = true`، يجب توفير `DynamicFeeConfig` للالتقاط كـ
  **آخر** `remaining_account` — يقرأ المعالج `ctx.remaining_accounts.last()`. أي
  PDAs تجاوز `SupportMintAssociated` يجب أن تأتي *قبله*، وإلا يلتقط البرنامج
  الحساب الخاطئ ويفشل في فك التسلسل. حذفه بينما العلم مضبوط يفشل مع
  `AccountLack`.
</Warning>

**الشروط المسبقة** — نفس `CreatePool`. إذا كان `enable_dynamic_fee = false`، لا يلزم `remaining_account` وأي يتم تمريره يتم فحصه فقط لسجلات دعم mint.

**الشروط اللاحقة**

- `pool_state.fee_on` مضبوط على متغير `CollectFeeOn` المختار.
- إذا تم تفعيل الرسوم الديناميكية: يتم تهيئة `pool_state.dynamic_fee_info` من `DynamicFeeConfig` المزود (خمسة معاملات معايرة مسخوخة؛ حقول الحالة مصفرة).
- وإلا: `pool_state.dynamic_fee_info` مصفر (= الرسوم الديناميكية غير نشطة إلى الأبد لهذا المجمع).

يتم تعيين `fee_on` وبت تفعيل الرسوم الديناميكية **فقط** عند إنشاء المجمع. لا يوجد ترقية في المكان — المجمعات التي تم إنشاؤها عبر `CreatePool` القديم لا يمكنها الحصول بأثر رجعي على رسوم ديناميكية أو رسوم أحادية الجانب. يجب أن تستخدم النشرات الجديدة هذه التعليمة بشكل افتراضي.

## `CreateCustomizablePoolV2`

يشتق كل من `CreatePool` و `CreateCustomizablePool` عنوان PDA للمجموعة من `["pool", amm_config, token_mint_0, token_mint_1]`، لذا يوجد عنوان مجموعة قانوني واحد بالضبط لكل ثلاثية `(config, mint0, mint1)` — محاولة `init` ثانية بنفس البذور تفشل. يرفع `CreateCustomizablePoolV2` هذا القيد بدمج `seed_index: u16` يوفره العميل في بذور PDA للمجموعة، مما يسمح بـ **مجموعات متعددة لنفس الزوج ومستوى الرسوم** — كل واحدة بعنوانها الخاص. يمكن لأي شخص استدعاؤها.

كل شيء آخر عن المجموعة متطابق مع `CreateCustomizablePool`: تأخذ نفس `CreateCustomizableParams` وتدعم الرسوم أحادية الجانب والاختيار الديناميكي للرسوم.

<Note>
  حتى ترقية [2026-10-22](/ar/reference/changelog/2026-10-22-clmm-customizable-pool-v2)، كانت هذه التعليمة تُسمى `CreatePermissionedPool` وتتطلب من الدافع الاحتفاظ بـ PDA `Permission` صادرة من المسؤول. أعادت الترقية تسميتها وأزالت حساب `permission` وحذفت آلية الأذونات. تغيّر المميز مع الاسم، لذا يجب إعادة بناء العملاء المبنيين مقابل `CreatePermissionedPool`.
</Note>

**الحجج**

```rust
customizable_params: CreateCustomizableParams   // same struct as CreateCustomizablePool
seed_index:          u16                          // must be non-zero; folded into the pool PDA seeds
```

**الحسابات**

| # | الاسم | W | S | ملاحظات |
|---|------|---|---|-------|
| 1 | `payer` | W | S | يدفع الإيجار لكل حساب جديد. أي محفظة. |
| 2 | `pool_creator` |   |   | مسجل كـ `pool_state.owner`. قد يختلف عن `payer`. ليس موقّعاً ولا يتم التحقق منه. |
| 3 | `amm_config` |   |   | مستوى الرسوم الذي تربط به المجموعة. |
| 4 | `pool_state` | W |   | `init` في `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`. |
| 5 | `token_mint_0` |   |   | يجب أن يأتي قبل `token_mint_1`. |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`. |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`. |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`. |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`. |
| 11 | `token_program_0` |   |   | البرنامج الذي يمتلك `token_mint_0`. |
| 12 | `token_program_1` |   |   | البرنامج الذي يمتلك `token_mint_1`. |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts`: PDAs سجل العملات المساعدة عندما تحتاج عملة Token-2022 إليها، و `DynamicFeeConfig` **أخيراً** عندما `enable_dynamic_fee = true` — كما في `CreateCustomizablePool`.

**الشروط المسبقة**

- `seed_index != 0`. يتم رفض `seed_index` بقيمة `0` لأنها محجوزة للمجموعات القديمة؛ مكون البذرة `[0, 0]` هو ما يجعل عنوان المجموعة القديمة ينهار إلى الشكل الكلاسيكي ذي البذور الأربع.
- لا توجد مجموعة بالفعل في العنوان المشتق.
- نفس قواعد العملات / قائمة السماح مثل `CreatePool`.

**الشروط اللاحقة**

- يوجد `pool_state` جديد في العنوان المشتق من `seed_index`، مع `pool_state.seed_index = seed_index`.
- جميع حالات ما بعد الأخرى تطابق `CreateCustomizablePool` (وضع الرسوم، الرسوم الديناميكية الاختيارية).

<Warning>
  لأن `pool_creator` غير مفحوص، يمكن لأي دافع كتابة أي عنوان في `pool_state.owner`. يمكن لهذا العنوان استدعاء `InitializeReward` على المجموعة، لكن هذا ليس إثباتاً لمن أنشأ المجموعة. يجب على المدمجين عدم تصنيف أو ترتيب مجموعات V2 حسب `owner`.
</Warning>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

إنشاء موضع جديد داخل مجموعة موجودة.

**الحجج**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // desired L (or 0 to use amounts below)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // write NFT metadata (Metaplex)
base_flag: Option<bool>       // true = fit to amount0; false = fit to amount1

**الحسابات** — للمتغيرين قوائم حسابات *مختلفة*. يعلن `OpenPositionV2` عن 22؛ `OpenPositionWithToken22Nft` يعلن عن 20.

`OpenPositionWithToken22Nft` هي نفس القائمة مع `metadata_account` (5) و `metadata_program` (19) **محذوفة** — تكتب بيانات الموضع من خلال امتداد البيانات الوصفية Token-2022 على عملة NFT بدلاً من ذلك — مما يعطي 20 حساباً. `position_nft_mint` الخاص به هو `Signer` عادي و `position_nft_account` هو `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` ليس حساباً معلناً على أي من المتغيرين.** عندما يقع نطاق الموضع خارج `tick_array_bitmap` المضمن للمجموعة (±512 مصفوفة tick)، أضف PDA `TickArrayBitmapExtension` في البذور `["pool_tick_array_bitmap_extension", pool_state]` كـ `remaining_accounts[0]`.
</Warning>

**الرياضيات** — انظر [`products/clmm/math`](/ar/products/clmm/math). بناءً على `base_flag`، يحل البرنامج إما `liquidity` أو `(amount_0_max, amount_1_max)` إلى `L` الفعلي ومبالغ الرموز الفعلية المستهلكة.

**الشروط المسبقة**

- `tick_lower < tick_upper`، كلاهما مضاعفات `pool.tick_spacing`، ضمن `[MIN_TICK, MAX_TICK]`.
- يتم تمرير PDA مصفوفتي tick. لا تحتاج إلى أن تكون موجودة بالفعل — `get_or_create_tick_array` تخصص واحدة مفقودة على حساب `payer` داخل هذه التعليمة. لا توجد تعليمة init-tick-array منفصلة.
- المستخدم لديه على الأقل `amount_0_max` و `amount_1_max` في ATAs المصدر.

**الشروط اللاحقة**

- يوجد `personal_position`، مع تعيين `liquidity`، و `fee_growth_inside_last` مأخوذة لحظة.
- تم تحديث إدخالات مصفوفة tick في `tick_lower` و `tick_upper` (`liquidity_gross += L`، `liquidity_net ± L`، لقطات نمو الرسوم المحفوظة).
- `pool_state.liquidity += L` إذا كان الموضع ضمن النطاق (`tick_lower ≤ tick_current < tick_upper`).
- تسجل عملة NFT `pool_state` كسلطة تجميد. تتم إزالة سلطة الإصدار بعد صك NFT الواحد. لا يغير تسجيل سلطة التجميد حالة حساب رمز NFT.
- يبقى حساب رمز NFT غير مجمد ما لم تكن التعليمة `OpenPositionV2` أو `OpenPositionWithToken22Nft` **و** تطابق سلطة تجميد أي من عملات الخزان قائمة المُصدرين المقيدين بـ CLMM. فقط هذا المسار V2 المطابق يجمد الحساب. لا يجمد `OpenPosition` V1.

**الأخطاء الشائعة** — `TickInvalidOrder` (`tick_lower >= tick_upper`)، `TickAndSpacingNotMatch` (نقطة نهاية ليست مضاعفة `tick_spacing`)، `InvalidTickIndex` (خارج `[MIN_TICK, MAX_TICK]`)، `MissingTickArrayBitmapExtensionAccount` (النطاق خارج الخريطة النقطية المضمنة ولم يتم إلحاق الامتداد)، `NotApproved` (`pool_state.status` يمنع الفتح)، `ZeroAmountSpecified`.

<Note>
  تجميد الموضع لا يضيف حسابات تعليمات معلنة أو حجج. يمكن للعملاء فتح هذه المواضع باستخدام تخطيطات V2 الموجودة. يتم اختيار السلوك على السلسلة من `vault_0_mint` و `vault_1_mint`.
</Note>

يمرر المستدعون قائمة مرتبة من مصفوفات التكات التي تغطي سير المبادلة المتوقع؛ يستخدم البرنامج ما يحتاجه. يحسب SDK هذه القائمة عبر `PoolUtils.computeAmountOutFormat` أو نقطة نهاية الاقتباس في API.

**الشروط المسبقة**

- `pool_state.status` يسمح بالمبادلة.
- `now >= open_time`.
- `sqrt_price_limit_x64` على الجانب الصحيح من `sqrt_price_x64` للاتجاه.

**الأخطاء الشائعة** — `TooLittleOutputReceived` (انزلاق الإدخال الدقيق)، `TooMuchInputPaid` (انزلاق الإخراج الدقيق)، `SqrtPriceLimitOverflow`، `NotEnoughTickArrayAccount`، `InvalidFirstTickArrayAccount`، `MissingTickArrayBitmapExtensionAccount`، `LiquidityInsufficient`، `NotApproved` (بت المبادلة مضبوط على `pool_state.status`). لا يحتوي CLMM على متغير `ExceededSlippage` — هذا الاسم خاص بـ CPMM — ولا على `TickArrayNotFound`.

**ما يفعله `SwapV2` داخلياً مما يجب أن يعرفه المستدعون** (بعد إصدار 2025):

1. **رسم ديناميكي إضافي** — إذا كان `pool.dynamic_fee_info` غير صفري، يحدّث البرنامج مراكم التقلب باستخدام مسافة التكات المقطوعة منذ آخر مبادلة (مع قواعد التصفية/الاضمحلال من [`products/ar/clmm/fees`](/ar/products/clmm/fees)) ويضيف `dynamic_fee_component` فوق `AmmConfig.trade_fee_rate`. الرسم الإجمالي مقيد بـ 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **مطابقة أوامر الحد** — عندما يعبر سير السعر تكة تحتوي على أوامر حد مفتوحة، يملأ البرنامج أولاً سيولة أوامر الحد المتاحة في تلك التكة (FIFO حسب `order_phase`)، ثم يمضي على طول منحنى سيولة LP. تحدّث المبالغ المملوءة `tick.unfilled_ratio_x64` و`tick.part_filled_orders_remaining` للتسوية لاحقاً؛ تبقى الأوامر نفسها غير منفقة حتى يستدعي مالكها `SettleLimitOrder`.
3. **توجيه رسم أحادي الجانب** — عندما يكون `pool.fee_on = Token0Only` أو `Token1Only`، تحسب خطوة المبادلة نفس الإدخال-الإخراج؛ يُوجَّه الرسم بعد ذلك إلى الجانب المُعيَّن. للاتجاهات حيث الجانب المُعيَّن للرسم هو الإخراج، يُخصم الرسم من إخراج المبادلة (يتلقى المستخدم `out − fee`)؛ للاتجاهات حيث يكون الإدخال، السلوك يطابق `FromInput`. انظر `is_fee_on_input(zero_for_one)` و`is_fee_on_token0(zero_for_one)` على `PoolState`.

`Swap` (V1) ينفذ نفس الرسم الديناميكي وتوجيه الرسم أحادي الجانب ومطابقة أوامر الحد مثل `SwapV2`؛ الميزة الوحيدة التي ينقصها هي دعم Token-2022 — يجب أن تكون كلا الخزائن رمز SPL كلاسيكي. يجب مبادلة المجموعات التي تحتوي على أي نعت Token-2022 عبر `SwapV2`. يفضل المجمّع و SDK بالفعل V2 لكل ساق CLMM حتى لا يضطر المستدعون إلى التفرع حسب نوع النعت.

<Note>
  **تغيير قائمة الحسابات (إصدار 2026-07).** يأخذ `OpenLimitOrder` الآن أيضاً حسابات جانب **الإخراج** — `output_token_account` و`output_vault` و`output_vault_mint` — بالإضافة إلى جانب الإدخال. تُستخدم فقط للتحقق: يرفض البرنامج الأمر إذا كان حساب رمز الإدخال **أو** الإخراج للمالك مجمداً. هذا يضمن أن الملء يمكن فعلاً تسويته إلى ATA الإخراج للمالك، وهذا مهم لنعوت Token-2022 المجمدة افتراضياً / قائمة السماح (مثل الرموز المرخصة) حيث قد لا يكون الحساب مذاباً بعد. يجب على العملاء المبنيين مقابل قائمة الحسابات أحادية الجانب الأقدم إضافة الحسابات الثلاثة للإخراج.
</Note>

**الشروط المسبقة**

- لا `input_token_account` ولا `output_token_account` مجمد (وإلا `NotApproved`).
- `pool_state.status` يسمح بعمليات المبادلة (بت 4) وأوامر الحد (بت 5) (وإلا `NotApproved`).
- `tick_index % pool.tick_spacing == 0` وضمن `[MIN_TICK, MAX_TICK]`.
- `tick_index` على **الجانب الأيمن من `pool.tick_current`** للاتجاه المختار (بيع token0 → يجب أن تكون التكة فوق الحالية، والعكس صحيح). البيع في تكة تم عبورها بالفعل سيُطابق فوراً ويُرفض.

**الشروط اللاحقة**

- `limit_order` موجود، يلتقط `tick.order_phase` و`tick.unfilled_ratio_x64` عند وقت الفتح.
- `tick.orders_amount += amount` (في المجموعة الحالية).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` مُطلق.

**الأخطاء الشائعة** — `NotApproved` (حساب رمز الإدخال أو الإخراج مجمد، أو المجموعة لديها مبادلة / أوامر حد معطلة)، `ZeroAmountSpecified` (`amount == 0` بعد رسم التحويل من جانب الإدخال)، `InvalidLimitOrderAmount` (المبلغ سينتج إخراج أقل من 1 وحدة أساسية في تلك التكة، أو تجاوز `u64`)، `InvalidTickIndex` (خارج `[MIN_TICK, MAX_TICK]`، أو على الجانب الخاطئ من `tick_current` للاتجاه المختار)، `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`)، `OrderPhaseSaturated`.

```

**الحسابات** — جانبا رمز الإدخال والإخراج:

| # | الاسم | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |

| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |

## `SettleLimitOrder`

**المُستدعي** — إما مالك الأمر `owner`، أو `limit_order_admin` للبرنامج (محفظة تشغيلية ساخنة خارج السلسلة تشغّل حلقة keeper آلية). لا توجد سلطة أخرى للـ keeper — لا يمكنه نقل أموال المستخدم خارج دفع المخرجات المملوءة إلى ATA مالك الأمر.

**الحسابات**

| # | الاسم | W | S | ملاحظات |
|---|------|---|---|-------|
| 1 | `signer` |   | S | المالك *أو* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | ATA المخرجات للمالك. |
| 6 | `output_vault` | W |   | خزينة مخرجات المجموعة. |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**التأثير**

- يحسب المخرجات المتراكمة المستحقة باستخدام `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)`.
- ينقل الفرق إلى `output_token_account`.
- يحدّث `limit_order.settled_output`.
- **لا** يغلق الأمر؛ يبقى مفتوحاً ضد أي مدخلات متبقية.

## `CloseLimitOrder`

أغلق حساب أمر مستهلك بالكامل. يتم دائماً إرجاع الإيجار إلى `limit_order.owner` بغض النظر عمن يوقّع.

**المُستدعي** — إما `owner` أو `limit_order_admin`.

**الشروط المسبقة**

- الأمر لديه صفر بقايا غير مملوءة (إما تم ملء `amount == total_amount` وتسويته، أو قلّل المالك الأمر إلى صفر سابقاً ونسي الإغلاق).

**التأثير**

- يغلق `limit_order`؛ يتم إرسال الإيجار إلى `limit_order.owner`.

## `CollectExcessLamports`

مسح المسؤول للـ lamports فوق الحد الأدنى المعفي من الإيجار على الحسابات التي يتحكم بها CLMM. تمت إضافته في ترقية 2026-09 لاسترجاع الإفراط في التمويل الذي يتركه [SIMD-0437 rent reduction](/ar/solana-fundamentals/rent-and-reclaimable-rent) على الحسابات المُنشأة قبل كل خطوة.

فقط الفائض ينتقل. أرصدة الرموز، بيانات الحساب، المالكون، حالة المجموعة ومنحنى السعر لم تتغير. الحساب الذي يكون بالفعل عند حده الأدنى يُترك كما هو، لذا يمكن إعادة تشغيل التعليمات بأمان بعد كل خطوة نشر.

**الحجج**: لا توجد.

**الحسابات**

| # | الاسم | W | S | ملاحظات |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | يستقبل كل lamport مُمسوح. يجب أن يكون مسؤول برنامج CLMM أو محفظة جمع lamports المخصصة (انظر [`reference/program-addresses`](/ar/reference/program-addresses#excess-lamports-collection-wallets)). أي موقّع آخر يفشل مع `NotApproved`. |
| 2 | `pool_state` | W |   | المجموعة التي يتم مسحها. بذور PDA الخاصة بها توقّع CPIs برنامج الرموز، والحساب يتم مسحه دائماً بنفسه. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. كلا البرنامجين مطلوبان؛ تختار التعليمات واحداً لكل حساب مصدر. |
| 5.. | `remaining_accounts` | W |   | `M` حساب مصدر، أي عدد، أي ترتيب. |

**النطاق: مجموعة واحدة لكل استدعاء.** CLMM لا يحتوي على سلطة خزينة على مستوى البرنامج. خزائن كل مجموعة مملوكة من قبل `PoolState` الخاص بها. لذلك يجب أن يكون لكل مصدر برنامج رموز `pool_state` في الفتحة 2 كسلطة له: `token_vault_0`، `token_vault_1`، أو أحد خزائن المكافآت لتلك المجموعة. إذا مررت خزينة مجموعة أخرى أو حساب رموز المستخدم، فإن فحص مالك برنامج الرموز يفشل والتعليمة بأكملها تنعكس. لا يتم تخطيها. لا يمكن مسح نقوش NFT للمواضع، لأن سلطة الضرب الخاصة بهم تم إلغاؤها عند فتح الموضع.

**كيفية التعامل مع كل حساب مصدر**

يقوم البرنامج بمسح واحد على `remaining_accounts`: كل CPIs برنامج الرموز أولاً، ثم الخصومات المباشرة. يؤدي التشابك بين الاثنين إلى الإجهاض مع خطأ `UnbalancedInstruction` في وقت التشغيل، لذا يتم إصلاح الترتيب في البرنامج ولا تضطر إلى فرز القائمة بنفسك.

| المسح | مالك حساب المصدر | المعالجة |
|---|---|---|
| 1 | SPL Token أو Token-2022، حساب رموز غير أصلي | CPI `WithdrawExcessLamports` (مميز برنامج الرموز `38`)، موقّع من قبل `pool_state`. |
| 1 | SPL Token أو Token-2022، **أصلي** (wSOL) حساب رموز | `WithdrawExcessLamports` يرفض الحسابات الأصلية. يقوم البرنامج بـ CPI `SyncNative`، يقيس كم نما `amount` المُغلّف، ويستدعي `UnwrapLamports` (مميز `45`) لهذا الفرق بالضبط. ثم يتطلب أن يساوي الرصيد المُغلّف قيمته قبل المزامنة، أو يفشل مع `LamportsCalculateError` (`6052`). خزينة مجموعة جانب SOL تحتفظ بسيولتها الكاملة. |
| 2 | `pool_state` (الفتحة 2) | مخصوم مباشرة إلى `rent.minimum_balance(data_len)`. |
| 2 | برنامج CLMM: `AmmConfig`، `ObservationState`، `TickArrayBitmapExtension`، `TickArrayState`، `PersonalPositionState`، `LimitOrderState`، وما إلى ذلك | مخصوم مباشرة إلى `rent.minimum_balance(data_len)`. الحساب **لا** يجب أن ينتمي إلى المجموعة في الفتحة 2. |
| — | أي شيء آخر | **تم تخطيه بصمت.** لا خطأ، لا lamports مُنقولة. |

<Warning>
  **المسح 2 يغطي الحسابات التي دفع المستخدم إيجارها.** `PersonalPositionState` أو `LimitOrderState` مُمرر هنا يتخلى عن فائضه مثل أي حساب مملوك من قبل CLMM آخر. يبقى معفياً من الإيجار ويحتفظ ببيانات الحساب. عند إغلاقه لاحقاً، يحصل المالك على ما يحتفظ به الحساب في تلك النقطة، وهو بعد المسح الحد الأدنى الحالي للإيجار.
</Warning>

حجم المعاملة هو الحد الحقيقي على عدد المصادر التي تناسب استدعاء واحد. إنه نفس القيد الموجود في المسح من جانب المحفظة الموصوف في [`solana-fundamentals/rent-and-reclaimable-rent`](/ar/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**الأخطاء الشائعة**:
- `NotApproved` (`6000`): موقّع خاطئ.
- `LamportsCalculateError` (`6052`): رحلة wSOL ذهاباً وإياباً لم تصل إلى صفر.
- خطأ عدم تطابق مالك برنامج الرموز: مصدر رموز لا يملكه `pool_state`.
- `InsufficientFunds`: حساب مملوك من قبل البرنامج يحتفظ بأقل من حده الأدنى للإيجار.

**لا يوجد منشئ SDK.** `@raydium-io/raydium-sdk-v2` لا يشحن منشئاً لهذا المسار الإداري. قم بترميزه يدوياً من IDL.

## `InitializeReward`

أضف تدفق مكافآت جديد إلى مجموعة. قد يكون هناك ما يصل إلى 3 تدفقات نشطة في نفس الوقت.

ترميز السلك هو الحقول الثلاثة متتالية، لذا فإن التعليمة المبنية يدوياً لا تتأثر — لكن عميل يعتمد على IDL يجب أن يمرر كائن `param` واحد بدلاً من ثلاث حجج موضعية.

**الحسابات**

| # | الاسم | W | S | ملاحظات |
|---|------|---|---|-------|
| 1 | `reward_funder` | W | S | |

| 4 | `pool_state` | W |   | |
| 5 | `operation_state` |   |   | PDA حالة عملية CLMM يحد من إنشاء المكافآت. |

## `SetRewardParams`

مدّد أو أضف إلى أو غيّر معدل الانبعاث على تدفق مكافآت موجود. عادة ما يتم استدعاؤها من قبل منشئ مجموعة أو multisig Raydium. القيود تعيش على السلسلة: يمكنك عادة تمديد `end_time` أو زيادة الانبعاثات، وليس تقليلها بأثر رجعي. تحقق من قائمة المالكين في `operation_state`.

## `UpdateRewardInfos`

محاسبة بحتة — تسوي `reward_growth_global_x64` للوقت الحالي بضرب `emissions_per_second × Δt / liquidity`. يتم استدعاؤها داخلياً من قبل كل تعليمة تلمس السيولة. تُعرّض كتعليمة مستقلة لأن الجهات الفاعلة الخارجية (واجهات المستخدم، الـ cranks) تريد أحياناً تشغيلها.

## جمع المكافآت

<Warning>
  **لا توجد تعليمة جمع مكافآت مستقلة.** البرنامج لا يعرّض نقطة دخول `CollectReward`، و IDL المنشور لا يحتوي على واحدة أيضاً.

`CollectRemainingRewards` شيء مختلف: يسمح لـ *ممول* المكافآت، بعد `end_time` للتدفق، بمسح الرموز التي لم يتم تخصيصها أبداً لأي موضع.
