| Admin | `UpdateAmmConfig` | Thay đổi tỷ lệ trên một tầng hiện có. |
| Admin | `UpdatePoolStatus` | Tạm dừng/tiếp tục hoạt động trên một pool. |
| Admin | `CreateSupportMintAssociated` | Cho phép danh sách một cấu hình phần mở rộng mint Token-2022 để sử dụng trong các pool CLMM. |
| Admin | `CreateOperationAccount` | Khởi tạo tài khoản hoạt động ở cấp chương trình (một lần). |
| Admin | `UpdateOperationAccount` | Sửa đổi danh sách trắng tài khoản hoạt động. |
| Admin | `CreateDynamicFeeConfig` | Tạo một bộ tham số phí động có thể tái sử dụng dưới một chỉ mục u16. |
| Admin | `UpdateDynamicFeeConfig` | Sửa đổi một `DynamicFeeConfig` hiện có. Các pool đã chụp nó không bị ảnh hưởng. |

| Admin | `ClosePermissionPda` | Thu hồi quyền được cấp trước đó bằng cách đóng PDA `Permission` của nó; tiền thuê nhà hoàn lại cho người gọi. |
| Pool | `CreatePool` | Khởi tạo một pool CLMM được ràng buộc với một `AmmConfig`. Đường dẫn phí tiêu chuẩn, FromInput. Tồn tại cùng với `CreateCustomizablePool`. |
| Pool | `CreateCustomizablePool` | Được khuyến nghị cho các pool mới. Cùng hình dạng với `CreatePool` cộng với `collect_fee_on` và cờ `enable_dynamic_fee` tùy chọn. |

| Vị trí | `ClosePosition` | Đốt NFT và đóng `PersonalPositionState`. Nếu tài khoản NFT bị đóng băng, trước tiên hãy rã đông nó với pool PDA được cung cấp làm tài khoản còn lại. |
| Vị trí | `CloseProtocolPosition` | Quét chỉ dành cho admin cho các PDA `ProtocolPositionState` kế thừa. Chương trình hiện tại không còn tạo hoặc đọc `ProtocolPositionState` — lệnh này chỉ tồn tại để thu hồi tiền thuê nhà trên các tài khoản được tạo bởi các phiên bản chương trình cũ hơn. |
| Swap | `Swap` / `SwapV2` | Swap thanh khoản không đổi. Cả hai biến thể áp dụng phí động, định tuyến phí một chiều và khớp lệnh giới hạn; sự khác biệt duy nhất là `SwapV2` chấp nhận mint Token-2022 (biến thể V1 yêu cầu cả hai vault là SPL Token cổ điển). |
| Swap | `SwapRouterBaseIn` | Nhiều bước nhảy, được sử dụng bởi bộ định tuyến. |
| Lệnh giới hạn | `OpenLimitOrder` | Đặt một lệnh bán ở một tick. Các token chưa điền nằm trên tick; công cụ khớp điền chúng khi giá vượt qua. |
| Lệnh giới hạn | `IncreaseLimitOrder` | Thêm vào một lệnh mở hiện có. |
| Lệnh giới hạn | `DecreaseLimitOrder` | Giảm hoặc hủy một lệnh mở; trả lại phần còn lại chưa điền cộng với bất kỳ đầu ra nào đã được giải quyết. |
| Lệnh giới hạn | `SettleLimitOrder` | Đẩy các token đầu ra đã điền cho chủ sở hữu lệnh. Có thể gọi bởi chủ sở hữu hoặc người giữ hoạt động. |
| Lệnh giới hạn | `CloseLimitOrder` | Đóng một tài khoản lệnh đã tiêu thụ hoàn toàn. Tiền thuê nhà luôn quay lại `owner` của lệnh. Có thể gọi bởi chủ sở hữu hoặc người giữ. |
| Phí | `CollectProtocolFee` | Quét admin của phí giao thức. |
| Phí | `CollectFundFee` | Quét admin của phí quỹ. |
| Phần thưởng | `InitializeReward` | Gắn một luồng phần thưởng mới vào một pool. |
| Phần thưởng | `SetRewardParams` | Thay đổi tỷ lệ phát hành/kết thúc của phần thưởng hiện có. |
| Phần thưởng | `UpdateRewardInfos` | Giải quyết tăng trưởng phần thưởng cho đến bây giờ (được gọi bởi bất kỳ swap / thay đổi vị trí nào). |
| Phần thưởng | `TransferRewardOwner` | Chuyển cơ quan có thể đặt hoặc bổ sung một luồng phần thưởng. |
| Phần thưởng | `CollectRemainingRewards` | Sau `end_time` của luồng phần thưởng, quét bất kỳ token chưa được phân bổ nào quay lại cho người tài trợ. |
| Admin | `CloseSupportMintAssociated` | Loại bỏ đăng ký `SupportMintAssociated` của một mint và hoàn lại tiền thuê nhà của nó. |
| Admin | `CollectExcessLamports` | Quét lamport vượt quá mức tối thiểu miễn phí thuê nhà từ `PoolState` của một pool và các vault của nó, cộng với bất kỳ PDA nào do CLMM sở hữu được truyền vào. `admin` hoặc ví thu thập lamport chuyên dụng. Được thêm vào 2026-09. |

<Note>
  **Không có lệnh init-tick-array, và không cần thiết.** Một tick array được tạo *bên trong*
  `OpenPosition*` / `IncreaseLiquidity*` bởi `TickArrayState::get_or_create_tick_array`, được trả tiền bởi
  `payer`. Truyền PDA tick-array (có thể vẫn chưa được khởi tạo, do hệ thống sở hữu) làm
  `tick_array_lower` / `tick_array_upper` và chương trình phân bổ nó nếu nó bị thiếu.
  `OpenLimitOrder` làm tương tự cho `tick_array` duy nhất của nó.
</Note>

Hầu hết các lệnh chỉ dành cho admin (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) được kiểm soát bởi khóa `admin` được mã hóa cứng của chương trình. `CreatePermissionPda` / `ClosePermissionPda` chấp nhận khóa `admin` **hoặc** khóa `permission_pda_admin` chuyên dụng; `CreateSupportMintAssociated` / `CloseSupportMintAssociated` chấp nhận khóa `admin` **hoặc** khóa chủ sở hữu mint hỗ trợ chuyên dụng; `CollectExcessLamports` chấp nhận khóa `admin` **hoặc** ví thu thập lamport chuyên dụng. Các lệnh admin luồng phần thưởng (`TransferRewardOwner`, `CollectRemainingRewards`) được kiểm soát bởi người tài trợ phần thưởng, không phải admin chương trình.

Hậu tố V2 có nghĩa là "hỗ trợ Token-2022 trên vault / NFT, yêu cầu khe bitmap-extension". SDK chọn V2 theo mặc định cho các pool mới.

## `CreatePool`

**Đối số**

```
sqrt_price_x64: u128           // giá ban đầu
open_time:      u64            // swap bị từ chối trước thời gian này
```

**Tài khoản (tóm tắt)**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Tầng phí được chọn. |
| 3 | `pool_state` | W |   | `init` ở đây. |
| 4 | `token_mint_0` |   |   | Được sắp xếp. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` ở đây, được sở hữu bởi pool authority PDA. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` ở đây. |
| 9 | `tick_array_bitmap` | W |   | PDA `TickArrayBitmapExtension`; `init` ở đây. |
| 10 | `token_program_0` |   |   | Chương trình sở hữu `token_mint_0` — SPL Token **hoặc** Token-2022. |
| 11 | `token_program_1` |   |   | Chương trình sở hữu `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Khe 10 và 11 là **theo mint**, không phải "SPL Token rồi Token-2022". Mỗi cái bị ràng buộc bởi
  `mint::token_program` trên mint phù hợp, vì vậy đối với một pool có `token_mint_0` là Token-2022 và
  `token_mint_1` là SPL cổ điển, bạn phải truyền Token-2022 vào khe 10 và SPL Token vào khe 11.
  `CreateCustomizablePool` và `CreatePermissionedPool` sử dụng cùng hai khe.
</Warning>

**Điều kiện tiên quyết**

- `token_mint_0 < token_mint_1` theo thứ tự byte.
- `amm_config.disable_create_pool == false`.
- Các mint không bị từ chối bởi danh sách cho phép phần mở rộng Token-2022.

**Điều kiện sau**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (chưa có vị trí).
- `pool_state.fee_on = FromInput` (mặc định kế thừa).
- `pool_state.dynamic_fee_info` được đặt thành 0 (phí động bị vô hiệu hóa).

## `CreateCustomizablePool`

Được khuyến nghị cho các pool mới. Cùng hiệu ứng với `CreatePool` cộng với chế độ thu thập phí trên mỗi pool và tùy chọn phí động tùy chọn.

**Đối số**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Tài khoản** — chính xác 13 tài khoản được khai báo của `CreatePool`. `dynamic_fee_config` **không** phải là một tài khoản được khai báo.

<Warning>
  Khi `enable_dynamic_fee = true`, `DynamicFeeConfig` để chụp phải được cung cấp làm
  **tài khoản cuối cùng** `remaining_account` — trình xử lý đọc `ctx.remaining_accounts.last()`. Bất kỳ
  PDA `SupportMintAssociated` bypass nào phải do đó đi *trước* nó, hoặc chương trình chụp
  tài khoản sai và không thành công deserialization. Bỏ qua nó trong khi cờ được đặt thất bại với
  `AccountLack`.
</Warning>

**Điều kiện tiên quyết** — giống như `CreatePool`. Nếu `enable_dynamic_fee = false`, không cần `remaining_account` và bất kỳ cái nào được truyền chỉ được quét để tìm các bản ghi mint hỗ trợ.

**Điều kiện sau**

- `pool_state.fee_on` được đặt thành biến thể `CollectFeeOn` được chọn.
- Nếu phí động được bật: `pool_state.dynamic_fee_info` được khởi tạo từ `DynamicFeeConfig` được cung cấp (năm tham số hiệu chỉnh được sao chép; các trường trạng thái được đặt thành 0).
- Nếu không: `pool_state.dynamic_fee_info` được đặt thành 0 (= phí động không hoạt động mãi mãi cho pool này).

`fee_on` và bit bật phí động được đặt **chỉ** khi tạo pool. Không có nâng cấp tại chỗ — các pool được tạo qua `CreatePool` kế thừa không thể có được phí động hoặc phí một chiều một cách hồi tưởng. Các triển khai mới nên mặc định cho lệnh này.

## `CreatePermissionedPool`

Cả `CreatePool` và `CreateCustomizablePool` đều lấy PDA pool từ `["pool", amm_config, token_mint_0, token_mint_1]`, vì vậy có chính xác **một** địa chỉ pool chính tắc cho mỗi bộ ba `(config, mint0, mint1)` — một `init` thứ hai ở cùng seed sẽ thất bại. `CreatePermissionedPool` nâng cao hạn chế đó bằng cách gấp `seed_index: u16` do khách hàng cung cấp vào seed PDA pool, cho phép **nhiều pool cho cùng một cặp và tầng phí** — mỗi cái ở địa chỉ riêng của nó. Vì một địa chỉ pool tùy ý là một khả năng có đặc quyền, người trả phí phải giữ một PDA `Permission` cho phép nó.

Mọi thứ khác về pool là giống hệt với `CreateCustomizablePool`: nó lấy cùng `CreateCustomizableParams` và hỗ trợ phí một chiều và tùy chọn phí động.

**Đối số**

```rust
customizable_params: CreateCustomizableParams   // cùng struct như CreateCustomizablePool
seed_index:          u16                          // phải khác 0; được gấp vào seed PDA pool
```

**Tài khoản (tóm tắt)** — giống như `CreateCustomizablePool` cộng với, ở phía trước:

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Trả tiền thuê nhà. Phải là cơ quan của PDA `permission` dưới đây. |
| 2 | `pool_creator` |   |   | Được ghi lại là `pool_state.owner`. Có thể khác với `payer`. |
| 3 | `permission` |   |   | PDA `["permission", payer]`. Anchor từ chối cuộc gọi nếu nó không tồn tại / không được sở hữu bởi chương trình. |
| … | (`amm_config`, `pool_state`, mint, vault, `observation_state`, `tick_array_bitmap`, token/system program) | | | Như trong `CreateCustomizablePool`. |

PDA `pool_state` được lấy từ `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`.

**Điều kiện tiên quyết**

- `seed_index != 0`. Một `seed_index` của `0` được dành riêng cho các pool kế thừa và bị từ chối ở đây; thành phần seed `[0, 0]` là những gì làm cho địa chỉ pool kế thừa sụp đổ thành dạng bốn seed cổ điển.
- PDA `permission` cho `payer` tồn tại (được tạo bởi admin qua `CreatePermissionPda`).
- Các quy tắc mint / danh sách cho phép giống như `CreatePool`.

**Điều kiện sau**

- Một `pool_state` mới tồn tại ở địa chỉ được lấy từ `seed_index`, với `pool_state.seed_index = seed_index`.
- Tất cả các trạng thái sau khác khớp với `CreateCustomizablePool` (chế độ phí, phí động tùy chọn).

<Note>
  Lệnh này **không** mở rộng quyền truy cập tạo pool chung — tạo không cần phép tiếp tục thông qua `CreatePool` / `CreateCustomizablePool`, vẫn là một pool trên mỗi cặp. `CreatePermissionedPool` tồn tại cho trường hợp cụ thể khi một nhà khai thác được liệt kê trắng danh cần nhiều pool cho cùng một cặp (ví dụ: giá ban đầu khác nhau hoặc nhóm khởi chạy) và giữ một PDA `Permission` được cấp bởi admin.
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Tạo một vị trí mới bên trong một pool hiện có.

**Đối số**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // L mong muốn (hoặc 0 để sử dụng số tiền dưới đây)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // ghi siêu dữ liệu NFT (Metaplex)
base_flag: Option<bool>       // true = vừa với amount0; false = vừa với amount1
```

**Tài khoản** — hai biến thể có *danh sách tài khoản khác nhau*. `OpenPositionV2` khai báo 22; `OpenPositionWithToken22Nft` khai báo 20.

`OpenPositionV2`, theo thứ tự:

| 10 | `personal_position` | W |   | Được tạo ở đây. |

| 21 | `vault_0_mint` |   |   | |
| 22 | `vault_1_mint` |   |   | |

`OpenPositionWithToken22Nft` là cùng danh sách với `metadata_account` (5) và `metadata_program` (19) **bị loại bỏ** — nó ghi siêu dữ liệu vị trí của nó thông qua phần mở rộng siêu dữ liệu Token-2022 trên mint NFT thay thế — cho 20 tài khoản. `position_nft_mint` của nó là một `Signer` trần và `position_nft_account` là một `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` không phải là một tài khoản được khai báo trên cả hai biến thể.** Khi phạm vi vị trí nằm ngoài `tick_array_bitmap` nội tuyến của pool (±512 tick array), hãy nối PDA `TickArrayBitmapExtension` ở seed `["pool_tick_array_bitmap_extension", pool_state]` làm
  `remaining_accounts[0]`.
</Warning>

**Toán học** — xem [`products/clmm/math`](/vi/products/clmm/math). Cho `base_flag`, chương trình giải quyết `liquidity` hoặc `(amount_0_max, amount_1_max)` thành `L` thực tế và số tiền token thực tế được tiêu thụ.

**Điều kiện tiên quyết**

- `tick_lower < tick_upper`, cả hai bội số của `pool.tick_spacing`, trong `[MIN_TICK, MAX_TICK]`.
- Hai PDA tick-array được truyền. Chúng **không** cần phải tồn tại — `get_or_create_tick_array` phân bổ một cái bị thiếu ở chi phí của `payer` bên trong lệnh này. Không có lệnh init-tick-array riêng biệt.
- Người dùng có ít nhất `amount_0_max` và `amount_1_max` trong các ATA nguồn.

**Điều kiện sau**

- `personal_position` tồn tại, `liquidity` được đặt, `fee_growth_inside_last` được chụp.
- Các mục tick-array ở `tick_lower` và `tick_upper` được cập nhật (`liquidity_gross += L`, `liquidity_net ± L`, ảnh chụp tăng trưởng phí được duy trì).
- `pool_state.liquidity += L` nếu vị trí nằm trong phạm vi (`tick_lower ≤ tick_current < tick_upper`).
- Mint NFT vị trí ghi lại `pool_state` làm cơ quan đóng băng. Cơ quan mint được loại bỏ sau khi NFT duy nhất được mint. Ghi lại cơ quan đóng băng không thay đổi trạng thái của tài khoản token NFT.
- Tài khoản token NFT vẫn không bị đóng băng trừ khi lệnh là `OpenPositionV2` hoặc `OpenPositionWithToken22Nft` **và** cơ quan phát hành hạn chế của mint vault bất kỳ khớp với danh sách. Chỉ đường dẫn V2 khớp đó mới đóng băng tài khoản. `OpenPosition` V1 không đóng băng.

**Lỗi phổ biến** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (một điểm cuối không phải là bội số của `tick_spacing`), `InvalidTickIndex` (ngoài `[MIN_TICK, MAX_TICK]`), `MissingTickArrayBitmapExtensionAccount` (phạm vi ngoài bitmap nội tuyến và phần mở rộng không được nối), `NotApproved` (`pool_state.status` chặn mở), `ZeroAmountSpecified`.

<Note>
  Đóng băng vị trí không thêm tài khoản lệnh được khai báo hoặc đối số. Khách hàng có thể mở các vị trí này với bố cục V2 hiện có. Hành vi được chọn trên chuỗi từ `vault_0_mint` và `vault_1_mint`.
</Note>

## `ClosePosition`

Đốt NFT vị trí và đóng `PersonalPositionState`.

**Tài khoản được khai báo**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `nft_owner` | W | S | Phải sở hữu tài khoản token NFT giữ số tiền `1`. |
| 2 | `position_nft_mint` | W |   | Phải khớp với `personal_position.nft_mint`. |
| 3 | `position_nft_account` | W |   | Tài khoản của chủ sở hữu NFT; có thể là SPL Token cổ điển hoặc Token-2022. |
| 4 | `personal_position` | W |   | Đóng cho `nft_owner`. |
| 5 | `system_program` |   |   | Đóng trạng thái vị trí. |
| 6 | `token_program` |   |   | Phải sở hữu mint NFT và tài khoản token. |

**Tài khoản còn lại**

- NFT không bị đóng băng: không cần; một tài khoản pool bổ sung là vô hại vì trình xử lý không đọc nó.
- NFT bị đóng băng: nối `personal_position.pool_id` làm tài khoản còn lại đầu tiên. Chương trình tải nó làm `PoolState` và sử dụng seed PDA của nó để ký rã đông.

**Điều kiện tiên quyết**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Tất cả bộ đếm phần thưởng `reward_amount_owed == 0`.

(Tức là, thu thập mọi thứ và giảm xuống 0 trước.)

**Hiệu ứng**

- Nếu tài khoản token NFT bị đóng băng, xác minh tài khoản còn lại đầu tiên bằng `personal_position.pool_id`, sau đó rã đông nó với pool PDA.
- Đốt NFT.
- Đóng tài khoản token NFT và `personal_position`, hoàn lại tiền thuê nhà cho `nft_owner`. Nếu NFT vị trí sử dụng Token-2022, nó cũng đóng mint NFT; mint SPL Token cổ điển không thể đóng và vẫn có cung cấp 0.

Rã đông, đốt và đóng là nguyên tử. NFT không thể trở nên có thể chuyển được giữa các bước đó.

**Ngắt khách hàng có điều kiện** — bố cục IDL được khai báo không thay đổi, vì vậy khách hàng kế thừa tiếp tục đóng các vị trí hiện có và không bị đóng băng. Một trình xây dựng kế thừa bỏ qua tài khoản pool còn lại sẽ thất bại với `AccountLack` khi đóng một vị trí bị đóng băng. Truyền pool cho mỗi lần đóng là chiến lược tương thích đơn giản nhất.

## `SwapV2`

**Tài khoản (tóm tắt)**

|---|------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2. |
| 11 | `memo_program` |   |   | V2 (bắt buộc cho một số đường dẫn Token-2022). |
| 12 | `input_vault_mint`, `output_vault_mint` |   |   | V2. |
| 13 | `tick_array_bitmap_extension` (tùy chọn) | W |   | Nếu swap đi vào phần mở rộng. |
| 14+ | `tick_array` (còn lại) | W |   | Đủ array để bao trùm phạm vi dự kiến của bước đi. |

Người gọi truyền một danh sách tick array được xếp hạng bao trùm bước đi swap dự kiến; chương trình sử dụng bao nhiêu nó cần. SDK tính toán danh sách này qua `PoolUtils.computeAmountOutFormat` hoặc điểm cuối trích dẫn của API.

**Điều kiện tiên quyết**

- `pool_state.status` cho phép swap.
- `now >= open_time`.
- `sqrt_price_limit_x64` nằm ở phía chính xác của `sqrt_price_x64` cho hướng.

**Lỗi phổ biến** — `TooLittleOutputReceived` (trượt giá chính xác-in), `TooMuchInputPaid` (trượt giá chính xác-out), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (bit swap được đặt trên `pool_state.status`). CLMM không có biến thể `ExceededSlippage` — tên đó là của CPMM — và không có `TickArrayNotFound`.

**Những gì `SwapV2` làm bên trong mà người gọi nên biết** (phát hành sau 2025):

1. **Phụ phí phí động** — nếu `pool.dynamic_fee_info` khác 0, chương trình cập nhật bộ tích lũy biến động bằng cách sử dụng khoảng cách tick được duyệt kể từ swap cuối cùng (với các quy tắc bộ lọc/phân rã từ [`products/clmm/fees`](/vi/products/clmm/fees)) và thêm `dynamic_fee_component` trên `AmmConfig.trade_fee_rate`. Tổng phí được giới hạn ở 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Khớp lệnh giới hạn** — khi bước đi giá vượt qua một tick giữ các lệnh giới hạn mở, chương trình trước tiên điền thanh khoản lệnh giới hạn có sẵn ở tick đó (FIFO theo `order_phase`), sau đó tiếp tục dọc theo đường cong thanh khoản LP. Các số tiền đã điền cập nhật `tick.unfilled_ratio_x64` và `tick.part_filled_orders_remaining` để giải quyết sau; các lệnh chính nó vẫn chưa được chi tiêu cho đến khi chủ sở hữu của chúng gọi `SettleLimitOrder`.
3. **Định tuyến phí một chiều** — khi `pool.fee_on = Token0Only` hoặc `Token1Only`, bước swap vẫn tính toán cùng một giao dịch đầu vào-đầu ra; phí sau đó được định tuyến đến phía được cấu hình. Đối với các hướng mà phía phí được cấu hình là đầu ra, phí được khấu trừ từ đầu ra swap (người dùng nhận `out − fee`); đối với các hướng mà nó là đầu vào, hành vi khớp với `FromInput`. Xem `is_fee_on_input(zero_for_one)` và `is_fee_on_token0(zero_for_one)` trên `PoolState`.

`Swap` (V1) thực hiện cùng phí động, định tuyến phí một chiều và khớp lệnh giới hạn như `SwapV2`; tính năng duy nhất nó thiếu là hỗ trợ Token-2022 — cả hai vault phải là SPL Token cổ điển. Các pool có bất kỳ mint Token-2022 nào phải được swap qua `SwapV2`. Bộ tập hợp và SDK đã ưu tiên V2 cho mỗi chân CLMM vì vậy người gọi không phải phân nhánh trên loại mint.

## `OpenLimitOrder`

Một `rent` lạc ở vị trí 14 hạ cánh chính xác nơi phần mở rộng bitmap tùy chọn được đọc, vì vậy lệnh dường như hoạt động cho đến lần đầu tiên một tick array ngoài bitmap nội tuyến phải được tạo — và sau đó thất bại.
</Warning>

<Note>
  **Thay đổi danh sách tài khoản (phát hành 2026-07).** `OpenLimitOrder` hiện cũng lấy các tài khoản **phía đầu ra** — `output_token_account`, `output_vault` và `output_vault_mint` — ngoài phía đầu vào. Chúng chỉ được sử dụng để xác thực: chương trình từ chối lệnh nếu tài khoản token đầu vào **hoặc** đầu ra của chủ sở hữu bị đóng băng. Điều này đảm bảo rằng một điền có thể thực sự được giải quyết cho ATA đầu ra của chủ sở hữu, điều này quan trọng đối với các mint Token-2022 được cho phép / đóng băng mặc định (ví dụ: token được phép) nơi một tài khoản có thể chưa được rã đông. Khách hàng được xây dựng dựa trên danh sách tài khoản một chiều cũ phải thêm ba tài khoản đầu ra.
</Note>

**Điều kiện tiên quyết**

- Cả `input_token_account` và `output_token_account` đều không bị đóng băng (nếu không `NotApproved`).
- `pool_state.status` cho phép cả hoạt động swap (bit 4) và lệnh giới hạn (bit 5) (nếu không `NotApproved`).
- `tick_index % pool.tick_spacing == 0` và trong `[MIN_TICK, MAX_TICK]`.
- `tick_index` nằm ở **phía bên phải của `pool.tick_current`** cho hướng được chọn (bán token0 → tick phải ở trên hiện tại, và ngược lại). Bán ở một tick đã vượt qua sẽ được khớp ngay lập tức và bị từ chối.

**Điều kiện sau**

- `limit_order` tồn tại, chụp `tick.order_phase` và `tick.unfilled_ratio_x64` tại thời gian mở.
- `tick.orders_amount += amount` (trong nhóm hiện tại).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` được phát hành.

**Lỗi phổ biến** — `NotApproved` (tài khoản token đầu vào hoặc đầu ra bị đóng băng, hoặc pool có swap / lệnh giới hạn bị vô hiệu hóa), `ZeroAmountSpecified` (`amount == 0` sau phí chuyển phía đầu vào), `InvalidLimitOrderAmount` (số tiền sẽ tạo ra đầu ra dưới 1 đơn vị cơ sở ở tick đó, hoặc tràn `u64`), `InvalidTickIndex` (ngoài `[MIN_TICK, MAX_TICK]`, hoặc ở phía sai của `tick_current` cho hướng được chọn), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `IncreaseLimitOrder`

Thêm vào một lệnh mở hiện có. Chỉ có thể gọi bởi `owner` của lệnh.

**Đối số**

```
amount: u64    // số tiền token đầu vào bổ sung
```

**Tài khoản** — 8, chỉ phía đầu vào. Nó bỏ tài khoản nonce, cả ba tài khoản phía đầu ra **và** `system_program`.

| # | Tên | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `input_vault` | W |   |
| 7 | `input_vault_mint` |   |   |
| 8 | `input_token_program` |   |   |

**Điều kiện tiên quyết**

- `limit_order.owner == signer`.
- Lệnh vẫn nằm trong cùng một nhóm (`tick.order_phase == limit_order.order_phase`). Nếu nhóm đã bắt đầu điền, lệnh được giải quyết một phần — người gọi nên gọi `DecreaseLimitOrder` hoặc `SettleLimitOrder` trước để cuộn về phía trước.

**Hiệu ứng**

- Chuyển `amount` từ ATA chủ sở hữu đến `input_vault`.
- `limit_order.total_amount += amount`; `tick.orders_amount += amount`.

## `DecreaseLimitOrder`

Giảm hoặc hủy hoàn toàn một lệnh mở. Trả lại phần còn lại chưa điền cho chủ sở hữu, cộng với bất kỳ đầu ra nào đã được giải quyết bởi các điền một phần trong quá khứ.

**Đối số**

```
amount:     u64    // số tiền token đầu vào để rút (tối đa = phần còn lại chưa điền)
amount_min: u64    // sàn trượt giá trên rút phía đầu vào
```

**Tài khoản** — cả phía token đầu vào và đầu ra:

| # | Tên | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_vault_mint`, `output_vault_mint` |   |   |
| 10 | `token_program`, `token_program_2022` |   |   |

**Hiệu ứng**

- Tính toán lại số tiền đã điền của lệnh từ `unfilled_ratio_x64` của nhóm kể từ khi mở.
- Gửi đầu ra đã điền đến `output_token_account`.
- Gửi `amount` của đầu vào chưa điền quay lại `input_token_account`.
- Cập nhật `limit_order` tương ứng. Nếu phần còn lại chưa điền mới bằng 0, chương trình đóng tài khoản và hoàn lại tiền thuê nhà cho `owner`.

## `SettleLimitOrder`

Đẩy các token đầu ra đã điền cho chủ sở hữu mà không thay đổi phần còn lại chưa điền của lệnh. Hữu ích khi các người giữ `auto_withdraw` muốn drip-pay các điền một phần chạy dài.

**Người gọi** — hoặc `owner` của lệnh, hoặc `limit_order_admin` của chương trình (một ví nóng hoạt động ngoài chuỗi chạy một vòng lặp người giữ tự động). Người giữ không có cơ quan khác — nó không thể di chuyển quỹ của người dùng ngoài việc đẩy đầu ra đã điền đến ATA `owner`.

**Tài khoản**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `signer` |   | S | chủ sở hữu *hoặc* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | ATA đầu ra của chủ sở hữu. |
| 6 | `output_vault` | W |   | Vault đầu ra của pool. |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**Hiệu ứng**

- Tính toán đầu ra tích lũy nợ bằng cách sử dụng `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)`.
- Chuyển delta
