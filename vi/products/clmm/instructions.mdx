## Danh sách hướng dẫn

| Nhóm | Hướng dẫn | Ghi chú |
|-------|-------------|-------|
| Admin | `CreateAmmConfig` | Xác định một mức phí mới. |
| Admin | `UpdateAmmConfig` | Thay đổi tỷ lệ trên một mức hiện có. |
| Admin | `UpdatePoolStatus` | Tạm dừng/tiếp tục hoạt động trên một pool. |
| Admin | `CreateSupportMintAssociated` | Cho phép danh sách cấu hình phần mở rộng mint Token-2022 để sử dụng trong các pool CLMM. |
| Admin | `CreateOperationAccount` | Khởi tạo tài khoản hoạt động cấp chương trình (một lần). |
| Admin | `UpdateOperationAccount` | Sửa đổi danh sách trắng tài khoản hoạt động. |
| Admin | `CreateDynamicFeeConfig` | Tạo một bộ tham số phí động có thể tái sử dụng dưới một chỉ mục u16. |
| Admin | `UpdateDynamicFeeConfig` | Sửa đổi một `DynamicFeeConfig` hiện có. Các pool đã chụp nó không bị ảnh hưởng. |
| Admin | `CreatePermissionPda` | Cấp cho một cơ quan quyền gọi `CreatePermissionedPool` bằng cách khởi tạo PDA `Permission` của nó. |
| Admin | `ClosePermissionPda` | Thu hồi quyền được cấp trước đó bằng cách đóng PDA `Permission` của nó; tiền thuê trả lại cho người gọi. |
| Pool | `CreatePool` | Khởi tạo một pool CLMM được liên kết với một `AmmConfig`. Đường dẫn phí tiêu chuẩn, FromInput. Tồn tại cùng với `CreateCustomizablePool`. |
| Pool | `CreateCustomizablePool` | Được khuyến nghị cho các pool mới. Cùng hình dạng với `CreatePool` cộng với `collect_fee_on` và cờ `enable_dynamic_fee` tùy chọn. |
| Pool | `CreatePermissionedPool` | Tạo một pool **bổ sung** cho một cặp đã có một, sử dụng `seed_index` do khách hàng cung cấp được gấp vào PDA pool. Người trả phí phải giữ một PDA `Permission`. |
| Position | `OpenPosition` / `OpenPositionV2` / `OpenPositionWithToken22Nft` | Mint một NFT vị trí. `OpenPositionV2` thay thế V1 (bố cục tài khoản mới hơn với khe bitmap-extension); `OpenPositionWithToken22Nft` phát hành NFT vị trí dưới dạng Token-2022 thay vì SPL Token. Mã mới nên sử dụng V2 hoặc biến thể Token-2022. |
| Position | `IncreaseLiquidity` / `IncreaseLiquidityV2` | Thêm thanh khoản vào một vị trí hiện có. |
| Position | `DecreaseLiquidity` / `DecreaseLiquidityV2` | Loại bỏ thanh khoản; thu thập phí nợ. |
| Position | `ClosePosition` | Đốt NFT và đóng `PersonalPositionState`. |
| Position | `CloseProtocolPosition` | Quét chỉ dành cho admin cho các PDA `ProtocolPositionState` cũ. Chương trình hiện tại không còn tạo hoặc đọc `ProtocolPositionState` — hướng dẫn này chỉ tồn tại để thu hồi tiền thuê trên các tài khoản được tạo bởi các phiên bản chương trình cũ hơn. |
| Swap | `Swap` / `SwapV2` | Swap thanh khoản không đổi. Cả hai biến thể đều áp dụng phí động, định tuyến phí một chiều và khớp lệnh giới hạn; sự khác biệt duy nhất là `SwapV2` chấp nhận mint Token-2022 (biến thể V1 yêu cầu cả hai vault phải là SPL Token cổ điển). |
| Swap | `SwapRouterBaseIn` | Nhiều bước, được sử dụng bởi bộ định tuyến. |
| Limit order | `OpenLimitOrder` | Đặt lệnh bán ở một tick. Các token chưa điền nằm trên tick; công cụ khớp điền chúng khi giá vượt qua. |
| Limit order | `IncreaseLimitOrder` | Thêm vào một lệnh mở hiện có. |
| Limit order | `DecreaseLimitOrder` | Giảm hoặc hủy một lệnh mở; trả lại phần còn lại chưa điền cộng với bất kỳ đầu ra nào đã được giải quyết. |
| Limit order | `SettleLimitOrder` | Đẩy các token đầu ra đã điền cho chủ sở hữu lệnh. Có thể gọi bởi chủ sở hữu hoặc bởi người giữ hoạt động. |
| Limit order | `CloseLimitOrder` | Đóng một tài khoản lệnh đã được tiêu thụ hoàn toàn. Tiền thuê luôn trả lại cho `owner` của lệnh. Có thể gọi bởi chủ sở hữu hoặc người giữ. |
| Fees | `CollectProtocolFee` | Quét admin của phí giao thức. |
| Fees | `CollectFundFee` | Quét admin của phí quỹ. |
| Rewards | `InitializeReward` | Gắn một luồng phần thưởng mới vào một pool. |
| Rewards | `SetRewardParams` | Thay đổi tỷ lệ phát hành/kết thúc của một phần thưởng hiện có. |
| Rewards | `UpdateRewardInfos` | Giải quyết tăng trưởng phần thưởng đến bây giờ (được gọi bởi bất kỳ swap / thay đổi vị trí nào). |
| Rewards | `TransferRewardOwner` | Chuyển cơ quan có thể đặt hoặc bổ sung một luồng phần thưởng. |
| Rewards | `CollectRemainingRewards` | Sau `end_time` của luồng phần thưởng, quét bất kỳ token chưa được phân bổ nào trở lại cho người tài trợ. |
| Utility | `InitTickArray` | Khởi tạo một tài khoản tick-array (thường được gói với `OpenPosition`). |

Hầu hết các hướng dẫn chỉ dành cho admin (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateSupportMintAssociated`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) được kiểm soát bởi khóa `admin` được mã hóa cứng của chương trình. `CreatePermissionPda` / `ClosePermissionPda` chấp nhận khóa `admin` **hoặc** khóa `permission_pda_admin` chuyên dụng. Các hướng dẫn admin luồng phần thưởng (`TransferRewardOwner`, `CollectRemainingRewards`) được kiểm soát bởi người tài trợ phần thưởng, không phải admin chương trình.

Hậu tố V2 có nghĩa là "hỗ trợ Token-2022 trên vault / NFT, yêu cầu khe bitmap-extension". SDK chọn V2 theo mặc định cho các pool mới.

## `CreatePool`

**Đối số**

```
sqrt_price_x64: u128           // giá ban đầu
open_time:      u64            // swap bị từ chối trước thời gian này
```

**Tài khoản (tóm tắt)**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Mức phí được chọn. |
| 3 | `pool_state` | W |   | `init` ở đây. |
| 4 | `token_mint_0` |   |   | Được sắp xếp. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` ở đây, được sở hữu bởi PDA cơ quan pool. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` ở đây. |
| 9 | `tick_array_bitmap_extension` | W |   | `init` ở đây (V2). |
| 10 | `token_program` |   |   | |
| 11 | `token_program_2022` |   |   | |
| 12 | `system_program`, `rent` |   |   | |

**Điều kiện tiên quyết**

- `token_mint_0 < token_mint_1` theo thứ tự byte.
- `amm_config.disable_create_pool == false`.
- Các mint không bị từ chối bởi danh sách cho phép phần mở rộng Token-2022.

**Điều kiện sau**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (chưa có vị trí).
- `pool_state.fee_on = FromInput` (mặc định cũ).
- `pool_state.dynamic_fee_info` được đặt thành 0 (phí động bị vô hiệu hóa).

## `CreateCustomizablePool`

Được khuyến nghị cho các pool mới. Cùng hiệu ứng với `CreatePool` cộng với chế độ thu thập phí trên mỗi pool và tùy chọn phí động tùy chọn.

**Đối số**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Tài khoản (tóm tắt)** — giống như `CreatePool` cộng với, khi `enable_dynamic_fee = true`:

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| N | `dynamic_fee_config` |   |   | Cấu hình được chia sẻ để chụp từ. Phải đã tồn tại. |

**Điều kiện tiên quyết** — giống như `CreatePool`. Nếu `enable_dynamic_fee = false`, `dynamic_fee_config` bị bỏ qua.

**Điều kiện sau**

- `pool_state.fee_on` được đặt thành biến thể `CollectFeeOn` được chọn.
- Nếu phí động được bật: `pool_state.dynamic_fee_info` được khởi tạo từ `DynamicFeeConfig` được cung cấp (năm tham số hiệu chỉnh được sao chép; các trường trạng thái được đặt thành 0).
- Nếu không: `pool_state.dynamic_fee_info` được đặt thành 0 (= phí động không hoạt động mãi mãi cho pool này).

`fee_on` và bit bật phí động được đặt **chỉ** khi tạo pool. Không có nâng cấp tại chỗ — các pool được tạo qua `CreatePool` cũ không thể có phí động hoặc phí một chiều một cách hồi tưởng. Các triển khai mới nên mặc định sử dụng hướng dẫn này.

## `CreatePermissionedPool`

Cả `CreatePool` và `CreateCustomizablePool` đều lấy PDA pool từ `["pool", amm_config, token_mint_0, token_mint_1]`, vì vậy có chính xác **một** địa chỉ pool chính tắc cho mỗi bộ ba `(config, mint0, mint1)` — một `init` thứ hai ở cùng các seed sẽ thất bại. `CreatePermissionedPool` nâng cao hạn chế đó bằng cách gấp `seed_index: u16` do khách hàng cung cấp vào các seed PDA pool, cho phép **nhiều pool cho cùng một cặp và mức phí** — mỗi cái ở địa chỉ riêng của nó. Vì một địa chỉ pool tùy ý là một khả năng có đặc quyền, người trả phí phải giữ một PDA `Permission` ủy quyền cho nó.

Mọi thứ khác về pool đều giống với `CreateCustomizablePool`: nó lấy cùng `CreateCustomizableParams` và hỗ trợ phí một chiều và tùy chọn phí động.

**Đối số**

```rust
customizable_params: CreateCustomizableParams   // cùng struct như CreateCustomizablePool
seed_index:          u16                          // phải khác 0; được gấp vào các seed PDA pool
```

**Tài khoản (tóm tắt)** — giống như `CreateCustomizablePool` cộng với, ở phía trước:

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Trả tiền thuê. Phải là cơ quan của PDA `permission` dưới đây. |
| 2 | `pool_creator` |   |   | Được ghi lại là `pool_state.owner`. Có thể khác với `payer`. |
| 3 | `permission` |   |   | PDA `["permission", payer]`. Anchor từ chối cuộc gọi nếu nó không tồn tại / không được sở hữu bởi chương trình. |
| … | (`amm_config`, `pool_state`, mint, vault, `observation_state`, `tick_array_bitmap`, token/system program) | | | Như trong `CreateCustomizablePool`. |

PDA `pool_state` được lấy từ `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`.

**Điều kiện tiên quyết**

- `seed_index != 0`. Một `seed_index` của `0` được dành riêng cho các pool cũ và bị từ chối ở đây; thành phần seed `[0, 0]` là những gì làm cho địa chỉ pool cũ sụp đổ thành dạng bốn seed cổ điển.
- PDA `permission` cho `payer` tồn tại (được tạo bởi admin qua `CreatePermissionPda`).
- Các quy tắc mint / danh sách cho phép giống như `CreatePool`.

**Điều kiện sau**

- Một `pool_state` mới tồn tại ở địa chỉ được lấy từ `seed_index`, với `pool_state.seed_index = seed_index`.
- Tất cả các trạng thái sau khác phù hợp với `CreateCustomizablePool` (chế độ phí, phí động tùy chọn).

<Note>
  Hướng dẫn này **không** mở rộng quyền truy cập tạo pool chung — tạo không cần phép tiếp tục thông qua `CreatePool` / `CreateCustomizablePool`, vẫn là một pool trên mỗi cặp. `CreatePermissionedPool` tồn tại cho trường hợp cụ thể khi một nhà khai thác được liệt kê trắng cần nhiều pool cho cùng một cặp (ví dụ: giá ban đầu khác nhau hoặc nhóm khởi chạy) và giữ một PDA `Permission` được cấp bởi admin.
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Tạo một vị trí mới bên trong một pool hiện có.

**Đối số**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // L mong muốn (hoặc 0 để sử dụng số tiền dưới đây)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // viết siêu dữ liệu NFT (Metaplex)
base_flag: Option<bool>       // true = vừa với amount0; false = vừa với amount1
```

**Tài khoản (tóm tắt)**

| # | Tên | W | S |
|---|------|---|---|
| 1 | `payer` | W | S |
| 2 | `position_nft_owner` |   |   |
| 3 | `position_nft_mint` | W | S (keypair) |
| 4 | `position_nft_account` | W |   | ATA của chủ sở hữu cho NFT. |
| 5 | `metadata_account` | W |   | Metaplex (tùy chọn, nếu `with_metadata`). |
| 6 | `pool_state` | W |   |
| 7 | `protocol_position` |   |   |   |
| 8 | `tick_array_lower` | W |   | Được tạo nếu chưa được khởi tạo. |
| 9 | `tick_array_upper` | W |   | Tương tự. |
| 10 | `personal_position` | W |   | Được tạo ở đây. |
| 11 | `token_account_0`, `token_account_1` | W |   | ATA nguồn của người dùng. |
| 12 | `token_vault_0`, `token_vault_1` | W |   | |
| 13 | `rent`, `system_program`, `token_program` |   |   | |
| 14 | `associated_token_program` |   |   | |
| 15 | `metadata_program` |   |   | Tùy chọn. |
| 16 | `token_program_2022` |   |   | V2. |
| 17 | `vault_0_mint`, `vault_1_mint` |   |   | V2. |
| 18 | `tick_array_bitmap_extension` | W |   | V2 (nếu được chạm). |

**Toán học** — xem [`products/clmm/math`](/vi/products/clmm/math). Cho `base_flag`, chương trình giải quyết `liquidity` hoặc `(amount_0_max, amount_1_max)` thành `L` thực tế và số tiền token thực tế được tiêu thụ.

**Điều kiện tiên quyết**

- `tick_lower < tick_upper`, cả hai là bội số của `pool.tick_spacing`, trong `[MIN_TICK, MAX_TICK]`.
- Các tick array bắt buộc được chuyển và khởi tạo (hoặc được tạo ở đây qua `InitTickArray` CPI trong giao dịch).
- Người dùng có ít nhất `amount_0_max` và `amount_1_max` trong các ATA nguồn.

**Điều kiện sau**

- `personal_position` tồn tại, `liquidity` được đặt, `fee_growth_inside_last` được chụp.
- Các mục tick-array tại `tick_lower` và `tick_upper` được cập nhật (`liquidity_gross += L`, `liquidity_net ± L`, ảnh chụp tăng trưởng phí được duy trì).
- `pool_state.liquidity += L` nếu vị trí nằm trong phạm vi (`tick_lower ≤ tick_current < tick_upper`).

**Lỗi phổ biến** — `InvalidTickIndex`, `NotApproved`, `ZeroAmountSpecified`, `TransactionTooLarge` (nếu quá nhiều tick array).

## `IncreaseLiquidityV2`

Thêm thanh khoản vào một vị trí đã mở.

**Đối số**

```
liquidity: u128
amount_0_max: u64
amount_1_max: u64
base_flag: Option<bool>
```

**Tài khoản** — giống như `OpenPosition` trừ mint NFT (vị trí đã tồn tại; NFT được chuyển dưới dạng ATA của chủ sở hữu giữ 1 token).

**Hiệu ứng**

- Chuyển `amount_0_actual` / `amount_1_actual` từ người dùng → vault.
- Tăng `personal_position.liquidity` và `pool_state.liquidity` (nếu nằm trong phạm vi), và `liquidity_gross` / `liquidity_net` của tick điểm cuối tương ứng.
- **Thu thập phí và phần thưởng nợ kể từ lần chạm cuối cùng** và ghi có chúng vào `tokens_fees_owed_{0,1}` / `reward_amount_owed`. Những khoản này chỉ được trả khi `DecreaseLiquidity` hoặc `CollectReward`, không phải khi tăng.

## `DecreaseLiquidityV2`

Loại bỏ thanh khoản từ một vị trí.

**Đối số**

```
liquidity: u128
amount_0_min: u64
amount_1_min: u64
```

**Tài khoản** — cùng hình dạng với `IncreaseLiquidity`.

**Hiệu ứng**

- Tính toán `(amount_0, amount_1)` cho `L` được loại bỏ cho `sqrt_price_x64` hiện tại.
- Giải quyết phí/phần thưởng tích lũy kể từ lần chạm cuối cùng, giống như `IncreaseLiquidity`.
- Chuyển `amount_0 + fees_owed_0` và `amount_1 + fees_owed_1` từ vault đến người dùng.
- Giảm bộ đếm thanh khoản; nếu `personal_position.liquidity` mới `== 0`, vị trí đủ điều kiện cho `ClosePosition`.

**Slippage** — `amount_0_min` và `amount_1_min` là mức tối thiểu mà người dùng chấp nhận sau khi trừ phí chuyển Token-2022 ở phía đầu ra.

## `ClosePosition`

Đốt NFT vị trí và đóng `PersonalPositionState`.

**Điều kiện tiên quyết**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Tất cả bộ đếm phần thưởng `reward_amount_owed == 0`.

(Tức là, thu thập mọi thứ và giảm xuống 0 trước.)

**Hiệu ứng**

- Đốt NFT.
- Đóng tài khoản mint NFT và tài khoản `personal_position`, hoàn lại tiền thuê cho `payer`.

## `SwapV2`

Đi bộ dọc theo đường cong thanh khoản; đầu vào chính xác *hoặc* đầu ra chính xác tùy thuộc vào `is_base_input`.

**Đối số**

```
amount: u64                  // đầu vào nếu is_base_input=true, đầu ra nếu không
other_amount_threshold: u64  // tối thiểu ra hoặc tối đa vào
sqrt_price_limit_x64: u128   // giới hạn cứng; 0 ⇒ không giới hạn
is_base_input: bool
```

**Tài khoản (tóm tắt)**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2. |
| 11 | `memo_program` |   |   | V2 (bắt buộc cho một số đường dẫn Token-2022). |
| 12 | `input_vault_mint`, `output_vault_mint` |   |   | V2. |
| 13 | `tick_array_bitmap_extension` (tùy chọn) | W |   | Nếu swap đi vào phần mở rộng. |
| 14+ | `tick_array` (còn lại) | W |   | Đủ array để bao quanh phạm vi dự kiến của bước đi. |

Người gọi chuyển một danh sách tick array được xếp hạng bao quanh bước đi swap dự kiến; chương trình sử dụng bao nhiêu nó cần. SDK tính toán danh sách này qua `PoolUtils.computeAmountOutFormat` hoặc điểm cuối báo giá của API.

**Điều kiện tiên quyết**

- `pool_state.status` cho phép swap.
- `now >= open_time`.
- `sqrt_price_limit_x64` nằm ở phía chính xác của `sqrt_price_x64` cho hướng.

**Lỗi phổ biến** — `ExceededSlippage`, `SqrtPriceLimitOverflow`, `TickArrayNotFound`, `LiquidityInsufficient`.

**Những gì `SwapV2` làm nội bộ mà người gọi nên biết** (phát hành sau 2025):

1. **Phí bổ sung động** — nếu `pool.dynamic_fee_info` khác 0, chương trình cập nhật bộ tích lũy biến động bằng cách sử dụng khoảng cách tick được duyệt kể từ swap cuối cùng (với các quy tắc bộ lọc/phân rã từ [`products/clmm/fees`](/vi/products/clmm/fees)) và thêm `dynamic_fee_component` trên `AmmConfig.trade_fee_rate`. Tổng phí được giới hạn ở 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Khớp lệnh giới hạn** — khi bước đi giá vượt qua một tick giữ các lệnh giới hạn mở, chương trình trước tiên điền thanh khoản lệnh giới hạn có sẵn ở tick đó (FIFO theo `order_phase`), sau đó tiếp tục dọc theo đường cong thanh khoản LP. Các số tiền đã điền cập nhật `tick.unfilled_ratio_x64` và `tick.part_filled_orders_remaining` để giải quyết sau; các lệnh tự nó vẫn chưa được chi tiêu cho đến khi chủ sở hữu của nó gọi `SettleLimitOrder`.
3. **Định tuyến phí một chiều** — khi `pool.fee_on = Token0Only` hoặc `Token1Only`, bước swap vẫn tính toán cùng một giao dịch đầu vào-đầu ra; phí sau đó được định tuyến đến phía được cấu hình. Đối với các hướng mà phía phí được cấu hình là đầu ra, phí được khấu trừ từ đầu ra swap (người dùng nhận `out − fee`); đối với các hướng mà nó là đầu vào, hành vi phù hợp với `FromInput`. Xem `is_fee_on_input(zero_for_one)` và `is_fee_on_token0(zero_for_one)` trên `PoolState`.

`Swap` (V1) thực hiện cùng phí động, định tuyến phí một chiều và khớp lệnh giới hạn như `SwapV2`; tính năng duy nhất nó thiếu là hỗ trợ Token-2022 — cả hai vault phải là SPL Token cổ điển. Các pool có bất kỳ mint Token-2022 nào phải được swap qua `SwapV2`. Bộ tổng hợp và SDK đã ưu tiên V2 cho mọi chân CLMM vì vậy người gọi không phải phân nhánh theo loại mint.

## `OpenLimitOrder`

Đặt lệnh bán ở một tick cụ thể. Lệnh nằm trong một nhóm FIFO trên mỗi tick và điền khi giá vượt qua.

**Đối số**

```
nonce_index:    u8       // chỉ mục tài khoản nonce được chọn của người dùng (0..255 trên mỗi ví)
zero_for_one:   bool     // true: bán token0 lấy token1; false: bán token1 lấy token0
tick_index:     i32      // phải là bội số của pool.tick_spacing
amount:         u64      // số tiền token đầu vào
```

**Tài khoản (tóm tắt)**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Chủ sở hữu lệnh; trả tiền thuê. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | Tick array chứa `tick_index`. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — được tạo khi lệnh đầu tiên của người dùng dưới `nonce_index` này. |
| 5 | `limit_order` | W |   | PDA. `init` ở đây. |
| 6 | `input_token_account` | W |   | ATA đầu vào của người dùng. Được kiểm tra xem có `frozen`. |
| 7 | `output_token_account` | W |   | ATA **đầu ra** của người dùng. Không bị khấu trừ khi mở — chỉ bắt buộc để chương trình có thể xác nhận nó không `frozen` (tức là điền có thể được giao sau). |
| 8 | `input_vault` | W |   | Vault đầu vào của pool. |
| 9 | `output_vault` | W |   | Vault đầu ra của pool. Xác định mint đầu ra cho các kiểm tra `output_token_account` / `output_vault_mint`. |
| 10 | `input_vault_mint` |   |   | Xử lý phí Token-2022. |
| 11 | `output_vault_mint` |   |   | Mint của phía đầu ra (ghép nối kiểm tra frozen). |
| 12 | `input_token_program` |   |   | SPL hoặc Token-2022. |
| 13 | `system_program`, `rent` |   |   | |

<Note>
  **Thay đổi danh sách tài khoản (phát hành 2026-07).** `OpenLimitOrder` hiện cũng lấy các tài khoản **phía đầu ra** — `output_token_account`, `output_vault` và `output_vault_mint` — ngoài phía đầu vào. Chúng chỉ được sử dụng để xác thực: chương trình từ chối lệnh nếu tài khoản token đầu vào **hoặc** đầu ra của chủ sở hữu bị frozen. Điều này đảm bảo rằng một điền thực sự có thể được giải quyết cho ATA đầu ra của chủ sở hữu, điều này quan trọng đối với các mint Token-2022 danh sách cho phép / frozen mặc định (ví dụ: token được phép) nơi một tài khoản có thể chưa được thaw. Các khách hàng được xây dựng dựa trên danh sách tài khoản một chiều cũ phải thêm ba tài khoản đầu ra.
</Note>

**Điều kiện tiên quyết**

- Cả `input_token_account` và `output_token_account` đều không bị frozen (nếu không `NotApproved`).
- `pool_state.status` cho phép cả hoạt động swap (bit 4) và giới hạn-lệnh (bit 5) (nếu không `NotApproved`).
- `tick_index % pool.tick_spacing == 0` và trong `[MIN_TICK, MAX_TICK]`.
- `tick_index` nằm ở **phía bên phải của `pool.tick_current`** cho hướng được chọn (bán token0 → tick phải ở trên hiện tại, và ngược lại). Bán ở một tick đã vượt qua sẽ được khớp ngay lập tức và bị từ chối.

**Điều kiện sau**

- `limit_order` tồn tại, chụp `tick.order_phase` và `tick.unfilled_ratio_x64` khi mở.
- `tick.orders_amount += amount` (trong nhóm hiện tại).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` được phát hành.

**Lỗi phổ biến** — `NotApproved` (tài khoản token đầu vào hoặc đầu ra bị frozen, hoặc pool đã vô hiệu hóa swap / giới hạn-lệnh), `InvalidLimitOrderAmount` (0 hoặc dưới mức tối thiểu của pool), `InvalidTickIndex` (ngoài `[MIN_TICK, MAX_TICK]`, hoặc ở phía sai của `tick_current` cho hướng được chọn), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `IncreaseLimitOrder`

Thêm vào một lệnh mở hiện có. Chỉ có thể gọi bởi `owner` của lệnh.

**Đối số**

```
amount: u64    // số tiền token đầu vào bổ sung
```

**Tài khoản** — giống như `OpenLimitOrder` trừ tài khoản nonce; PDA `limit_order` được chuyển trực tiếp.

**Điều kiện tiên quyết**

- `limit_order.owner == signer`.
- Lệnh vẫn nằm trong cùng một nhóm (`tick.order_phase == limit_order.order_phase`). Nếu nhóm đã bắt đầu điền, lệnh được giải quyết một phần — người gọi nên gọi `DecreaseLimitOrder` hoặc `SettleLimitOrder` trước để cuộn tiến.

**Hiệu ứng**

- Chuyển `amount` từ ATA chủ sở hữu đến `input_vault`.
- `limit_order.total_amount += amount`; `tick.orders_amount += amount`.

## `DecreaseLimitOrder`

Giảm hoặc hủy hoàn toàn một lệnh mở. Trả phần còn lại chưa điền cho chủ sở hữu, cộng với bất kỳ đầu ra nào đã được giải quyết bởi các điền một phần trong quá khứ.

**Đối số**

```
amount:     u64    // số tiền token đầu vào để rút (tối đa = phần còn lại chưa điền)
amount_min: u64    // sàn slippage trên rút phía đầu vào
```

**Tài khoản** — cả phía token đầu vào và đầu ra:

| # | Tên | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_vault_mint`, `output_vault_mint` |   |   |
| 10 | `token_program`, `token_program_2022` |   |   |

**Hiệu ứng**

- Tính toán lại số tiền đã điền của lệnh từ `unfilled_ratio_x64` của nhóm kể từ khi mở.
- Gửi đầu ra đã điền đến `output_token_account`.
- Gửi `amount` của đầu vào chưa điền trở lại `input_token_account`.
- Cập nhật `limit_order` tương ứng. Nếu phần còn lại chưa điền mới là 0, chương trình đóng tài khoản và hoàn lại tiền thuê cho `owner`.

## `SettleLimitOrder`

Đẩy các token đầu ra đã điền cho chủ sở hữu mà không thay đổi phần còn lại chưa điền của lệnh. Hữu ích khi các keeper `auto_withdraw` muốn drip-pay các điền một phần chạy dài.

**Người gọi** — hoặc `owner` của lệnh, hoặc `limit_order_admin` của chương trình (một ví nóng hoạt động ngoài chuỗi chạy một vòng lặp keeper tự động). Keeper không có cơ quan khác — nó không thể di chuyển quỹ người dùng ngoài việc đẩy đầu ra đã điền đến ATA `owner` của lệnh.

**Tài khoản**

| # | Tên | W | S |
|---|------|---|---|
| 1 | `signer` |   | S | owner *hoặc* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | ATA đầu ra của chủ sở hữu. |
| 6 | `output_vault` | W |   | Vault đầu ra của pool. |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**Hiệu ứng**

- Tính toán đầu ra tích lũy nợ bằng cách sử dụng `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)`.
- Chuyển delta đến `output_token_account`.
- Cập nhật `limit_order.settled_output`.
- **Không** đóng lệnh; nó vẫn mở đối với bất kỳ đầu vào còn lại nào.

## `CloseLimitOrder`

Đóng một tài khoản lệnh đã được tiêu thụ hoàn toàn. Tiền thuê luôn được trả lại cho `limit_order.owner` bất kể ai ký.

**Người gọi** — hoặc `owner` hoặc `limit_order_admin`.

**Điều kiện tiên quyết**

- Lệnh có phần còn lại chưa điền bằng 0 (hoặc `amount == total_amount` đã được điền và giải quyết, hoặc chủ sở hữu trước đó đã giảm lệnh xuống 0 và quên đóng).

**Hiệu ứng**

- Đóng `limit_order`; tiền thuê được gửi đến `limit_order.owner`.

## `CreateDynamicFeeConfig` (admin)

Tạo một bộ tham số có thể tái sử dụng dưới một chỉ mục u16.

**Đối số**

```
index:                       u16
filter_period:               u16   // giây; ví dụ: 30
decay_period:                u16   // giây; ví dụ: 600. Phải > filter_period
reduction_factor:            u16   // 1..10_000; ví dụ: 5_000 = 50% giữ lại trên mỗi cửa sổ phân rã
dynamic_fee_control:         u32   // 1..100_000; lợi ích trên đường cong biến động-đến-phí
max_volatility_accumulator:  u32   // trần
```

**Tài khoản**

| # | Tên | W | S | Ghi chú |
|---|------|---|---|-------|
| 1 | `owner` | W | S | Khóa admin được mã hóa cứng. |
| 2 | `dynamic_fee_config` | W |   | PDA, `init` ở đây. |
| 3 | `system_program` |   |   | |

**Lỗi phổ biến** — `InvalidDynamicFeeConfigParams` nếu `decay_period <= filter_period` hoặc bất kỳ trường giá trị 0 nào nằm ngoài giới hạn.

## `UpdateDynamicFeeConfig` (admin)

Sửa đổi một `DynamicFeeConfig` hiện có. Các pool đã chụp cấu hình khi tạo **không** được cập nhật hồi tưởng; chỉ các pool mới được tạo tham chiếu cấu hình này sẽ nhận các giá trị mới.

**Đối số** — cùng năm trường hiệu chỉnh như `CreateDynamicFeeConfig` (`filter_period`, `decay_period`, `reduction_factor`, `dynamic_fee_control`, `max_volatility_accumulator`); `index` được cố định khi tạo và không được chuyển lại ở đây.

## `CollectProtocolFee` / `CollectFundFee`

## `SetRewardParams`

Mở rộng, bổ sung hoặc thay đổi tỷ lệ phát hành trên một luồng phần thưởng hiện có. Thường được gọi bởi người tạo pool hoặc multisig Raydium. ## `UpdateRewardInfos`
