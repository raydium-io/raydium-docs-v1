## 두 가지 독립적인 수수료, 네 가지 목적지

CPMM은 모든 스왑에 **두 가지 별도 요율의 수수료**를 부과합니다:

1. **거래 수수료** — `AmmConfig.trade_fee_rate`에서 부과되며 세 가지 목적지로 분배됩니다:
   - **LP 몫** — 볼트에 남아 `k`를 증가시킵니다. LP 토큰을 소각하여 암묵적으로 청구됩니다.
   - **프로토콜 몫** — `PoolState.protocol_fees_token*`에 누적되며, `protocol_owner`가 `CollectProtocolFee`를 통해 수집합니다.
   - **펀드 몫** — `PoolState.fund_fees_token*`에 누적되며, `fund_owner`가 `CollectFundFee`를 통해 수집합니다.
2. **크리에이터 수수료** (선택사항, 풀별) — `AmmConfig.creator_fee_rate`에서 거래 수수료와 **독립적으로** 부과되며 `PoolState.creator_fees_token*`에 누적됩니다. 크리에이터는 `CollectCreatorFee`를 통해 수집하거나, 누구든지 목적지 제약이 있는 `CollectCreatorFeePermissionless` 경로를 트리거할 수 있습니다. `enable_creator_fee = true`로 풀이 생성되었을 때만 활성화됩니다.

크리에이터 수수료는 거래 수수료의 일부가 **아닙니다**. 두 요율은 스왑 입력에서 수수료를 취할 때 함께 더해지지만, 각각은 자신의 버킷으로 유지됩니다 — 프로토콜과 펀드 몫은 항상 `trade_fee`에서만 파생되며, `creator_fee`에서는 절대 파생되지 않습니다. `creator_fee_rate = 1000` (0.10%)과 `trade_fee_rate = 2500` (0.25%)을 가진 풀은 크리에이터 수수료 온 입력 스왑에서 입력의 0.35%를 합쳐서 부과하며, 이 중 크리에이터가 0.10%를 유지하고 거래 수수료 버킷이 0.25%를 받습니다.

거래 수수료 요율(`trade_fee_rate`, `protocol_fee_rate`, `fund_fee_rate`)과 `creator_fee_rate`은 모두 `AmmConfig`에 있습니다. 풀별 `enable_creator_fee` 플래그와 `creator_fee_on` 모드(거래의 어느 쪽에서 크리에이터 수수료를 취할지)는 `PoolState`에 있습니다. [`/ko/products/cpmm/accounts`](/ko/products/cpmm/accounts)를 참조하세요.

## 요율과 단위

모든 요율은 `1 / FEE_RATE_DENOMINATOR` 단위로 표시되는 `u64`이며, 여기서 `FEE_RATE_DENOMINATOR = 1_000_000`입니다.

- **`trade_fee_rate`** 는 **스왑 거래량**의 분수입니다. `2500` ⇒ 관련 쪽(입력 또는 출력, `creator_fee_on`에 따라 다름 — 아래 "거래의 어느 쪽에서 수수료를 취할지" 참조)의 0.25%.
- **`creator_fee_rate`** 는 **스왑 거래량**의 분수이며, 거래 수수료와 **별도로** 취합니다. `1000` ⇒ 관련 쪽의 0.10%.
- **`protocol_fee_rate`** 와 **`fund_fee_rate`** 는 거래량이 아닌 **거래 수수료**의 분수입니다. `120_000` ⇒ 거래 수수료의 12%.

메인넷의 `AmmConfig[index=0]` (표준 0.25% 풀)에 대한 기본 매개변수 (참고용):

| 필드 | 값 | 유효 백분율 |
|-------|-------|-------------------|
| `trade_fee_rate` | `2500` | 거래량의 0.25% (거래 수수료 버킷) |
| `protocol_fee_rate` | `120000` | 거래 수수료의 12% ≈ **거래량의 0.030%** |
| `fund_fee_rate` | `40000` | 거래 수수료의 4% ≈ **거래량의 0.010%** |
| `creator_fee_rate` | `0` (기본값) | 0% (별도 버킷) |
| → LP 몫 유효 | | **거래량의 0.210%** |

따라서 `AmmConfig[0]`에 대해 `enable_creator_fee = false`인 \$1,000 스왑에서: \$2.50 총 거래 수수료, 이 중 \$2.10은 LP와 함께 유지되고, \$0.30은 프로토콜로, \$0.10은 펀드로 갑니다. 크리에이터 버킷은 크리에이터 수수료가 비활성화되어 있으므로 0입니다.

같은 풀이 `enable_creator_fee = true`이고 `creator_fee_rate = 1000` (0.10%)을 가졌다면, 사용자는 크리에이터 버킷에 추가로 \$1.00을 지불합니다 — `creator_fee_on`으로 구성된 거래의 같은 쪽에서 취함 — 총 \$3.50의 수수료를 위해. 거래 수수료 버킷과 그 프로토콜/펀드 분배는 변경되지 않습니다.

현재 메인넷 값을 `GET https://api-v3.raydium.io/main/cpmm-config`에 대해 확인하세요 — 요율은 관리자가 변경 가능하며 하드코딩하기보다는 새로 읽어야 합니다.

## 코드의 분배

```rust
// raydium-cp-swap/programs/cp-swap/src/curve/{calculator,fees}.rs에서 의역됨.
// 실제 코드는 `is_creator_fee_on_input`에서 분기하며, 두 분기 모두
// creator_fee가 자신의 요율이며 trade_fee의 일부가 아니라는 불변성을 유지합니다.

const FEE_RATE_DENOMINATOR_VALUE: u64 = 1_000_000;

pub struct FeeBreakdown {
    pub amount_in_after_fees: u64,    // 입력에서 취한 모든 수수료를 뺀 입력
    pub amount_out_after_fees: u64,   // 출력에서 취한 크리에이터 수수료를 뺀 출력
    pub trade_fee:    u64,            // → 아래 LP / 프로토콜 / 펀드 버킷으로 분배
    pub protocol_fee: u64,            // trade_fee의 몫
    pub fund_fee:     u64,            // trade_fee의 몫
    pub creator_fee:  u64,            // 독립적인 버킷 (입력 또는 출력 쪽)
}

fn take_fees_on_input(
    amount_in: u64,
    trade_rate: u64,
    creator_rate: u64,
    protocol_rate: u64,
    fund_rate: u64,
) -> (u64 /* trade_fee */, u64 /* creator_fee */, u64 /* amount_in_after_fees */) {
    // 두 요율이 더해져서 합친 수수료에서 한 번 반올림한 후
    // 비례적으로 분배합니다 — 이는 순전히 반올림/효율성 트릭입니다. 분배는
    // 요율을 정확히 준수합니다: creator_fee/trade_fee == creator_rate/trade_rate.
    let total_fee = ((amount_in as u128) * ((trade_rate + creator_rate) as u128))
        .div_ceil(FEE_RATE_DENOMINATOR_VALUE as u128) as u64;

    let creator_fee = ((total_fee as u128) * (creator_rate as u128)
                       / ((trade_rate + creator_rate) as u128)) as u64;
    let trade_fee   = total_fee - creator_fee;

    (trade_fee, creator_fee, amount_in - total_fee)
}

fn take_creator_fee_on_output(amount_out_swapped: u64, creator_rate: u64) -> (u64, u64) {
    // creator_fee_on이 크리에이터 수수료를 출력 쪽으로 라우팅할 때,
    // trade_fee는 입력에서 단일 요율로 취해지고, creator_fee는
    // 곡선 출력에 대해 계산됩니다.
    let creator_fee = ((amount_out_swapped as u128) * (creator_rate as u128))
        .div_ceil(FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    (amount_out_swapped - creator_fee, creator_fee)
}

fn split_trade_fee(
    trade_fee: u64,
    protocol_rate: u64,
    fund_rate: u64,
) -> (u64 /* protocol_fee */, u64 /* fund_fee */) {
    let protocol_fee = (trade_fee as u128 * protocol_rate as u128
                        / FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    let fund_fee     = (trade_fee as u128 * fund_rate as u128
                        / FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    (protocol_fee, fund_fee)
}
```

참고:

- 입력의 총 수수료는 **올림**되므로 풀은 절대 과소 청구하지 않습니다.
- `trade_fee`의 부분 분배(프로토콜, 펀드)는 **내림**되므로 그 합이 `trade_fee`를 초과하지 않습니다; 나머지는 LP 몫입니다.
- `lp_share = trade_fee − protocol_fee − fund_fee` (creator_fee는 자신의 버킷이므로 여기서 **빼지 않습니다**).
- 크리에이터 수수료는 `PoolState.creator_fee_on`에 따라 입력 또는 출력에서 취합니다 (다음 섹션 참조). 요율은 어느 쪽이든 변경되지 않습니다.

## 거래의 어느 쪽에서 수수료를 취할지

CPMM은 풀별 `creator_fee_on` 설정(`BothToken` / `OnlyToken0` / `OnlyToken1`)을 가지고 있으며, 이는 크리에이터 수수료를 주어진 스왑의 **입력** 쪽에서 취할지 **출력** 쪽에서 취할지를 결정합니다. 런타임 헬퍼 `is_creator_fee_on_input(direction)`은 스왑별로 이를 부울로 축약합니다:

| `creator_fee_on` | 스왑 `0 → 1` | 스왑 `1 → 0` |
|------------------|---------------|---------------|
| `BothToken` (`0`) | 입력 쪽 | 입력 쪽 |
| `OnlyToken0` (`1`) | 입력 쪽 | 출력 쪽 |
| `OnlyToken1` (`2`) | 출력 쪽 | 입력 쪽 |

크리에이터 수수료가 **입력** 쪽에 있을 때, 거래 수수료와 크리에이터 수수료 모두 곡선이 실행되기 전에 `amount_in`에서 공제됩니다. 견적 수학: 입력에서 합친 `trade_rate + creator_rate`를 취합니다.

크리에이터 수수료가 **출력** 쪽에 있을 때, 거래 수수료만 `amount_in`에서 공제됩니다; 곡선은 수수료 없는 출력을 생성한 후, 크리에이터 수수료가 그 출력에서 공제됩니다. 견적 수학: 입력에서 `trade_rate`를 취합니다; 출력에서 `creator_rate`를 취합니다.

거래 수수료 자체는 항상 입력 쪽에서 취합니다 (표준 Uniswap-V2 패턴). 크리에이터 수수료만 출력에 도달할 수 있습니다.

## "누적된" 수수료가 곡선과 상호작용하는 방식

중요한 미묘함: **프로토콜, 펀드, 크리에이터 수수료는 각각의 `Collect*` 명령이 호출될 때까지 물리적으로 볼트에 남아 있습니다**. 하지만 곡선의 볼트 잔액 보기에서는 제외됩니다.

한 번의 스왑 후 구체적인 그림:

```
raw_vault_0_balance = getTokenAccountBalance(vault_0).amount
                    = lp_entitled + protocol_fees_token0
                      + fund_fees_token0 + creator_fees_token0

curve_x = raw_vault_0_balance − (protocol_fees_token0
                                  + fund_fees_token0
                                  + creator_fees_token0)
```

프로그램은 `k' ≥ k`를 강제할 때 `curve_x` (및 유사한 `curve_y`)를 사용합니다. 이것이 비LP 수수료가 LP 몫을 부풀리지 않고 목적지에 도달하는 방식입니다.

설계할 때 고려해야 할 결과:

- **원본 잔액에서 견적을 작성하는 것은 잘못되었습니다.** `getTokenAccountBalance`에서 견적을 작성하면, 풀이 준수할 가격을 지속적으로 과대평가합니다. 항상 누적된 수수료를 빼거나, `SwapBaseInput` / API를 통해 시뮬레이션하세요.
- **`CollectProtocolFee`는 가격을 이동하지 않습니다.** 볼트에서 토큰을 이동하고 `protocol_fees_token*` 카운터를 0으로 설정하므로, `curve_x`와 `curve_y`는 변경되지 않습니다.
- **LP 수수료는 카운터에 누적되지 않습니다.** 이들은 볼트 잔액에 암묵적입니다. LP의 누적된 LP 수수료에 대한 권리는 LP 토큰을 소각하여 행사됩니다 (즉, `Withdraw`를 통해) — `CollectLpFee`는 없습니다.

## Token-2022 전송 수수료와의 상호작용

Token-2022 전송 수수료는 CPMM이 아닌 **민트**에 의해 적용됩니다. 이들은 모든 토큰 전송 — 스왑, 예치, 인출, `Collect*` 수집에 작용합니다. CPMM의 거래 수수료 수학은 **실제로 볼트에 도달한** 금액에 대해 계산됩니다. 즉, 입력 민트의 전송 수수료를 뺀 금액입니다 (있는 경우).

따라서 최악의 경우 사용자는 입력 정확 스왑에서 세 가지 별개의 세금을 지불합니다:

1. 입력 민트의 `amount_in`에 대한 전송 수수료 (민트의 수수료 권한에).
2. 나머지에 대한 풀의 `trade_fee` (위에 따라 분배).
3. 출력 민트의 `amount_out`에 대한 전송 수수료 (민트의 수수료 권한에).

SDK의 견적 도구는 세 가지 모두를 고려하므로 `minimum_amount_out`은 사용자가 실제로 받는 것으로 표시됩니다. 자신의 견적 도구를 작성하는 경우, 그 동작을 반영하거나 슬리피지 검사가 체계적으로 너무 관대할 것입니다.

자세한 유도는 [`/ko/algorithms/token-2022-transfer-fees`](/ko/algorithms/token-2022-transfer-fees)를 참조하세요.

## 크리에이터 수수료

크리에이터 수수료는 선택사항이며 풀별입니다. **요율**은 `AmmConfig.creator_fee_rate`에 있고; **활성화 플래그**와 **쪽**(`creator_fee_on`)은 `PoolState`에 있습니다:

- **풀 생성 시 활성화됨.** `Initialize`는 기본적으로 `enable_creator_fee = false`를 설정합니다; `InitializeWithPermission`을 통해 생성된 풀 (LaunchLab 졸업 및 기타 게이트된 경로에서 사용)은 `enable_creator_fee = true`를 전달하고 `creator_fee_on`을 선택할 수 있습니다.
- **요율은 수수료 계층과 공유됩니다.** 요율 자체는 `AmmConfig.creator_fee_rate`이며, 그 구성에 바인딩된 모든 풀에서 동일한 값입니다. 각 풀은 그 후 그것을 청구할지(`enable_creator_fee`) 결정하고 스왑의 어느 쪽에서 청구할지(`creator_fee_on`) 결정합니다. `enable_creator_fee = false`일 때, 풀의 유효 크리에이터 수수료 요율은 구성 값에 관계없이 0입니다 (소스의 `PoolState::adjust_creator_fee_rate` 참조).
- **거래 수수료와 독립적입니다.** 크리에이터 수수료는 LP / 프로토콜 / 펀드 몫을 절대 줄이지 않습니다 — 이는 자신의 요율이며, 별도로 적용되고, 자신의 카운터에 누적됩니다.
- **`CollectCreatorFee` 또는 `CollectCreatorFeePermissionless`를 통해 수집됩니다.** 원본 경로는 `PoolState.pool_creator`가 서명해야 합니다. 권한 없는 경로는 누구든지 수집을 트리거할 수 있지만 두 목적지를 크리에이터의 정규 ATA로 고정합니다.
- **생성 후 다시 활성화하거나 다시 라우팅할 수 없습니다.** `enable_creator_fee = false`로 초기화된 풀은 절대 크리에이터 수수료를 청구하지 않습니다; 특정 `creator_fee_on`으로 초기화된 풀은 쪽을 전환할 수 없습니다.

크리에이터 수수료는 Raydium의 "Burn & Earn" 패턴의 메커니즘입니다: LP 토큰은 [LP Lock](/reference/program-addresses) 프로그램 아래에 잠겨 있으므로 크리에이터는 유동성을 인출할 수 없지만, 누적된 크리에이터 수수료는 여전히 무한정 수집할 수 있습니다.

## 수집 운영 흐름

| 서명자 | 명령 | 소스 카운터 0으로 설정 | 일반적인 주기 |
|--------|-------------|------------------------|-----------------|
| `amm_config.protocol_owner` | `CollectProtocolFee` | `protocol_fees_token{0,1}` | 주간 또는 프로그래밍 방식 |
| `amm_config.fund_owner` | `CollectFundFee` | `fund_fees_token{0,1}` | 주간 또는 프로그래밍 방식 |
| `pool_state.pool_creator` | `CollectCreatorFee` | `creator_fees_token{0,1}` | 언제든지 |
| 모든 지불자; 크리에이터는 서명하지 않음 | `CollectCreatorFeePermissionless` | `creator_fees_token{0,1}` | 언제든지; 크리에이터 ATA는 고정 목적지 |

프로토콜 및 펀드 소유자는 메인넷의 Raydium 멀티시그입니다; [`/ko/security/admin-and-multisig`](/ko/security/admin-and-multisig)를 참조하세요. 원본 크리에이터 전용 경로에서, 크리에이터 서명자는 `PoolState`에 기록된 계정입니다. 권한 없는 경로에서, 호출자는 누락된 크리에이터 ATA를 생성하기 위해 비용을 지불합니다. 프로그램은 `creator`를 `pool_state.pool_creator`로 제약하고 각 목적지를 그 크리에이터와 해당 볼트 민트 및 토큰 프로그램에서 파생하므로, 호출자는 자금을 리다이렉트할 수 없습니다.

## 수수료 계층 변경

수수료 요율은 관리자가 `UpdateAmmConfig`를 통해 변경할 수 있습니다 (참조: [`/ko/products/cpmm/instructions`](/ko/products/cpmm/instructions)). 변경 사항은 그 `AmmConfig`에 바인딩된 모든 풀에 대해 **다음 스왑**에 적용됩니다 — 풀이 각 스왑에서 구성을 로드하기 때문에 마이그레이션이 없습니다.

관리자가 할 수 없는 것:

- 풀을 한 `AmmConfig`에서 다른 것으로 이동합니다.
- 이미 누적된 수수료를 소급해서 재가격합니다.
- `protocol_owner` / `fund_owner` 서명자 없이 수수료를 수집합니다.

## 실행 중인 풀에서 수수료 읽기

```ts
// 오프체인: 각 버킷의 현재 누적된 수수료
const pool = await connection.getAccountInfo(poolStatePda);
const decoded = PoolState.decode(pool.data);
console.log(
  "Protocol accrued:",
  decoded.protocolFeesToken0.toString(),
  decoded.protocolFeesToken1.toString(),
);
console.log(
  "Fund accrued:",
  decoded.fundFeesToken0.toString(),
  decoded.fundFeesToken1.toString(),
);
console.log(
  "Creator accrued:",
  decoded.creatorFeesToken0.toString(),
  decoded.creatorFeesToken1.toString(),
);

// 오프체인: 오늘의 유효 요율.
// trade_fee_rate, creator_fee_rate는 거래량의 분수입니다 (분모 1e6).
// protocol_fee_rate, fund_fee_rate는 *거래 수수료*의 분수입니다 (같은 분모).
const config = await fetch("https://api-v3.raydium.io/main/cpmm-config")
  .then((r) => r.json());
const tier = config.data.find((t) => t.index === decoded.ammConfigIndex);

const tradeFeeOfVolume   = tier.tradeFeeRate / 1_000_000;
const protocolOfTradeFee = tier.protocolFeeRate / 1_000_000;
const fundOfTradeFee     = tier.fundFeeRate / 1_000_000;
const lpOfTradeFee       = 1 - protocolOfTradeFee - fundOfTradeFee;

console.log("LP fee effective:",       (tradeFeeOfVolume * lpOfTradeFee * 100).toFixed(4), "%");
console.log("Protocol fee effective:", (tradeFeeOfVolume * protocolOfTradeFee * 100).toFixed(4), "%");
console.log("Fund fee effective:",     (tradeFeeOfVolume * fundOfTradeFee * 100).toFixed(4), "%");
console.log(
  "Creator fee effective:",
  decoded.enableCreatorFee
    ? ((tier.creatorFeeRate / 1_000_000) * 100).toFixed(4) + " %"
    : "0 % (disabled on this pool)",
);
```

## CLMM 및 AMM v4와의 비교

[`/ko/reference/fee-comparison`](/ko/reference/fee-comparison)에서 나란히 비교 표를 참조하세요. 요약:

- **AMM v4**는 고정 0.25% 거래 수수료를 사용하며 다른 LP/프로토콜 분배와 펀드 수수료가 없습니다.
- **CLMM** 수수료는 틱 간격 계층별이며, 풀별이 아닌 포지션별로 누적되며, `DecreaseLiquidity` 또는 `CollectFees`를 통해 청구됩니다.
