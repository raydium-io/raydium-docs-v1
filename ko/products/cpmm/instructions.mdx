## 명령어 요약

| 판별자 이름 | 서명자 | 수행 작업 |
|-------|-----------|--------------|
| `Initialize` | 풀 생성자 | 두 개의 민트와 `AmmConfig`에서 새로운 CPMM 풀을 생성합니다. 권한 없음; 누구나 호출할 수 있습니다. 새 풀에서 `enable_creator_fee = false`를 하드코딩합니다. `pool_state` 계정은 정규 PDA 또는 새로운 임의 키쌍일 수 있습니다 (Initialize 계정 참조). |
| `InitializeWithPermission` | 지불자 + `Permission` PDA 보유자 | `Initialize`의 권한 있는 변형입니다. 호출자(`payer`)는 자신의 공개키에서 파생된 `Permission` PDA를 소유해야 합니다. 게이트된 풀 생성이 필요한 플랫폼에서 사용됩니다 (예: LaunchLab 졸업). 호출자가 `creator_fee_on` (`BothToken` / `OnlyToken0` / `OnlyToken1`)을 고정하고 새 풀에서 `enable_creator_fee = true`를 강제합니다. `pool_state`의 `creator` 필드는 지불자가 아닌 별도로 전달된 `creator` 계정으로 설정됩니다. `Initialize`와 동일한 정규-PDA-또는-임의-키쌍 유연성이 `pool_state`에 적용됩니다. |
| `Deposit` | LP | 두 토큰 모두에 유동성을 추가하고 LP 토큰을 받습니다. |
| `Withdraw` | LP | LP 토큰을 소각하고 기본 토큰을 비례적으로 받습니다. |
| `SwapBaseInput` | 스왑 실행자 | 정확한 입력 스왑 (`amount_in` 입력, ≥ `minimum_amount_out` 출력). |
| `SwapBaseOutput` | 스왑 실행자 | 정확한 출력 스왑 (≤ `maximum_amount_in` 입력, `amount_out` 출력). |
| `CollectProtocolFee` | `protocol_owner` (`AmmConfig`에서) | 볼트에서 누적된 프로토콜 수수료를 수집합니다. |
| `CollectFundFee` | `fund_owner` (`AmmConfig`에서) | 볼트에서 누적된 펀드 수수료를 수집합니다. |
| `CollectCreatorFee` | `pool_creator` | 누적된 크리에이터 수수료를 수집합니다 (크리에이터 수수료가 활성화된 경우), 프로토콜의 몫을 제외하고, 이는 풀의 프로토콜 버킷에 기록됩니다. |
| `CollectCreatorFeePermissionless` | 모든 지불자 | 누적된 크리에이터 수수료를 `pool_creator`의 정규 토큰 계정으로 수집하고, 동일한 프로토콜 몫을 제외합니다. 지불자는 누락된 수신자 ATA를 생성할 수 있지만 전송을 리디렉션할 수 없습니다. |
| `UpdatePoolStatus` | `admin` | 비트마스크를 통해 풀의 특정 작업을 일시 중지/재개합니다. |
| `UpdateAmmConfig` | `admin` | `AmmConfig`의 수수료율 또는 프로토콜/펀드 소유자를 변경합니다. |
| `CreateAmmConfig` | `admin` | 새로운 수수료 계층 (새로운 `AmmConfig` 계정)을 생성합니다. |
| `CreatePermissionPda` | `admin` 또는 위임된 권한-PDA 생성자 | 특정 권한이 `InitializeWithPermission`을 호출할 수 있도록 하는 `Permission` PDA를 발급합니다. |
| `ClosePermissionPda` | `admin` 또는 전담 권한-PDA 생성자 | 이전에 발급된 `Permission` PDA를 취소합니다. 2026-09 업그레이드 이후 전담 생성자 권한은 발급한 권한을 닫을 수도 있습니다. 이전에는 관리자 전용이었습니다. |
| `CreateSupportMintAssociated` | `admin` 또는 전담 지원-민트 소유자 | 그렇지 않으면 확장 허용 목록에 실패할 Token-2022 민트를 등록하고, `SupportMintAssociated` PDA를 생성합니다. |
| `CloseSupportMintAssociated` | `admin` 또는 전담 지원-민트 소유자 | 민트의 등록을 제거합니다. |
| `CollectExcessLamports` | `admin` 또는 전담 수집-lamports 지갑 | CPMM 제어 볼트, LP 민트 및 PDA에서 최소 임차료 이상의 lamport를 수집합니다. 2026-09에 추가됨. |
| `CreateCreatorFeeShare` | `admin` 또는 전담 크리에이터-수수료-공유 소유자 | 하나의 `(creator, amm_config)` 쌍에 대한 크리에이터 수수료의 사용자 정의 프로토콜 몫을 설정하고, `AmmConfig.creator_fee_share_rate`를 재정의합니다. 2026-09-13에 추가됨. |
| `CloseCreatorFeeShare` | `admin` 또는 전담 크리에이터-수수료-공유 소유자 | 해당 재정의를 제거합니다. 쌍은 구성 기본값으로 돌아갑니다. 2026-09-13에 추가됨. |

상태 비트마스크: 각 풀의 `status`는 `u8`이며, 비트 0 = 입금 비활성화, 비트 1 = 출금 비활성화, 비트 2 = 스왑 비활성화 (`PoolStatusBitIndex { Deposit, Withdraw, Swap }` 프로그램에서). 명확한 비트는 작업이 허용됨을 의미하고, 설정된 비트는 일시 중지됨을 의미합니다. `UpdatePoolStatus`는 원시 `u8`을 사용하고 기존 값을 덮어씁니다.

다음 섹션에서는 각각을 자세히 설명합니다. 계정 순서는 CPMM IDL을 따릅니다. SDK와 `raydium-cp-swap/programs/cp-swap/src/instructions`의 Rust 클라이언트가 이 순서와 일치합니다.

## `Initialize`

새로운 CPMM 풀을 생성합니다.

**인자**

```
init_amount_0: u64
init_amount_1: u64
open_time:     u64   // Unix 타임스탬프; 이 시간 이전의 스왑은 거부됨
```

**계정** (W = 쓰기 가능, S = 서명자)

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `creator` | W | S | 임차료를 지불합니다. `pool_state.pool_creator`로 기록됩니다. |
| 2 | `amm_config` |   |   | 선택된 수수료 계층. |
| 3 | `authority` |   |   | CPMM 글로벌 권한 PDA. |
| 4 | `pool_state` | W | S* | 여기서 `init`됩니다. **정규 PDA `["pool", amm_config, token_0_mint, token_1_mint]` 또는** 새로운 임의 키쌍 — 정규 PDA가 아닐 때, 프로그램은 `pool_state`가 서명하도록 요구합니다 (`require_eq!(pool_account_info.is_signer, true)`). 임의 키쌍 경로는 생성자가 정규 PDA에 대한 프론트러닝 시도를 피할 수 있게 합니다. 다운스트림 PDA (`lp_mint`, `vaults`, `observation_state`)는 어느 쪽이든 `pool_state.key()`에서 파생됩니다. |
| 5 | `token_0_mint` |   |   | 정렬됨: `token_0_mint < token_1_mint`. |
| 6 | `token_1_mint` |   |   | |
| 7 | `lp_mint` | W |   | 여기서 `init`됩니다. 권한이 `authority`로 설정됩니다. |
| 8 | `creator_token_0` | W |   | `init_amount_0`의 소스 ATA. |
| 9 | `creator_token_1` | W |   | `init_amount_1`의 소스 ATA. |
| 10 | `creator_lp_token` | W |   | `lp_mint`의 생성자 ATA. `init` (not `init_if_needed`) — 이미 존재하지 않아야 하며, `lp_mint`가 이 동일한 명령어에서 생성되므로 존재할 수 없습니다. |
| 11 | `token_0_vault` | W |   | 여기서 `init`됩니다. `authority`가 소유합니다. |
| 12 | `token_1_vault` | W |   | |
| 13 | `create_pool_fee` | W |   | 생성자가 지불한 `create_pool_fee`의 대상 ATA. |
| 14 | `observation_state` | W |   | 여기서 `init`됩니다. |
| 15 | `token_program` |   |   | SPL Token (LP 민트용). |
| 16 | `token_0_program` |   |   | SPL Token 또는 Token-2022. |
| 17 | `token_1_program` |   |   | SPL Token 또는 Token-2022. |
| 18 | `associated_token_program` |   |   | |
| 19 | `system_program` |   |   | |
| 20 | `rent` |   |   | |

`*` `pool_state`는 임의 키쌍 경로에서만 서명합니다. 정규-PDA 경로는 `pool_state` 서명 없이 실행됩니다.

**사전 조건**

- 민트가 정렬되어 있습니다 (`token_0_mint < token_1_mint` 바이트 순서로).
- 어떤 민트도 CPMM 허용 목록 외의 확장을 사용하지 않습니다 (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) — [`products/cpmm/accounts`](/ko/products/cpmm/accounts#vaults-and-token-2022)를 참조하세요. `SupportMintAssociated` PDA (시드 `[b"support_mint", mint]`)가 존재하는 민트는 확장 검사를 건너뜁니다 — **하지만 해당 PDA를 `remaining_accounts`에 추가해야 합니다**. 프로그램은 전달한 계정만 스캔하고 PDA를 직접 로드하지 않으므로, 레지스트리에 의존하면서 계정을 제공하지 않으면 `NotSupportMint` (`6007`)로 실패합니다. 순서는 중요하지 않습니다 (키로 일치). 우회가 필요한 민트당 하나의 항목을 전달하세요. 해당 레지스트리는 2026-09 업그레이드가 하드코딩된 4-민트 화이트리스트를 제거한 이후 유일한 우회입니다.
- `creator`는 각 ATA에서 최소 `init_amount_0`과 `init_amount_1`을 보유합니다.
- `amm_config.disable_create_pool == false`.

**사후 조건**

- `pool_state.lp_supply = sqrt(init_amount_0 * init_amount_1)` — **전체** 제곱근. 생성자는 `lp_supply − 100`을 민팅받습니다. 100개의 잠긴 기본 단위는 `lp_supply`에 계산되지만 절대 민팅되지 않습니다.
- 따라서 `lp_mint.supply == pool_state.lp_supply − 100`은 풀의 수명 동안 유지됩니다. 모든 LP-공유 수학 (입금, 출금)은 `lp_supply`로 나누므로 해당 필드를 사용하고 민트의 온체인 공급을 대체하지 마세요. `sqrt(...) < 100`이면 `InitLpAmountTooLess`로 되돌립니다.
- `observation_state`가 초기화됩니다. `observation_index = 0`이고 `pool_id = pool_state.key()`.
- `create_pool_fee` lamport가 생성자에서 수신자로 전송되고 네이티브 SOL로 동기화됩니다 (wSOL ATA입니다).
- 풀의 상태 비트마스크는 `0`입니다 (입금 / 출금 / 스왑 모두 활성화).
- `enable_creator_fee = false`이고 `creator_fee_on = BothToken`. `Initialize`는 크리에이터 수수료 활성화를 지원하지 않습니다 — 해당 경로는 `InitializeWithPermission`입니다.
- `open_time`은 호출자가 `<= block_timestamp` 값을 전달한 경우 `block_timestamp + 1`로 범프됩니다. 스왑은 `open_time` 이전에 거부됩니다. 입금과 출금은 즉시 작동합니다.

**일반적인 오류** (전체 목록은 [`reference/error-codes`](/ko/reference/error-codes)에서)

- `InvalidInput` — 민트가 정렬되지 않았거나 동일한 민트.
- `NotSupportMint` — 차단된 Token-2022 확장.
- `ExceededSlippage` — 드물게; `init_amount_0/1`이 소수 자릿수 불일치로 인해 0 LP를 초래하는 경우.

## `Deposit`

풀에 비례하여 두 토큰 모두에 유동성을 추가합니다.

**인자**

```
lp_token_amount:   u64   // LP에 민팅할 LP 토큰 수
maximum_token_0:   u64
maximum_token_1:   u64
```

**계정**

| # | 이름 | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `owner_lp_token` | W |   |
| 5 | `token_0_account` | W |   |
| 6 | `token_1_account` | W |   |
| 7 | `token_0_vault` | W |   |
| 8 | `token_1_vault` | W |   |
| 9 | `token_program` |   |   |
| 10 | `token_program_2022` |   |   |
| 11 | `vault_0_mint` |   |   |
| 12 | `vault_1_mint` |   |   |
| 13 | `lp_mint` | W |   |

**수학**

```
total_0 = vault_0 − protocol_fees_0 − fund_fees_0 − creator_fees_0    // 측면 1도 동일

needed_token_0 = ceil(lp_token_amount * total_0 / lp_supply)
transfer_0     = needed_token_0 + inverse_transfer_fee(needed_token_0) // Token-2022
require(transfer_0 <= maximum_token_0, "ExceededSlippage")             // 측면 1도 동일
```

두 가지 세부 사항이 주목할 가치가 있습니다: 비례 기반은 **수수료 제외** 볼트 총액 (`vault_amount_without_fee`, 즉 원시 잔액에서 누적된 프로토콜, 펀드 및 크리에이터 카운터를 뺀 값)이며, 원시 볼트 잔액이 아닙니다. 그리고 슬리피지 상한은 지불자가 실제로 전송하는 것에 대해 확인되며, Token-2022 전송 수수료가 추가된 후이며, 총 볼트 이동이 아닙니다.

`k`의 비례성에 변화 없음 — 두 총액과 `lp_supply`는 동일한 계수로 확장됩니다.

**사후 조건**

- `lp_supply += lp_token_amount`.
- `vault_0 += needed_token_0` (입력의 Token-2022 전송 수수료 제외).
- `vault_1 += needed_token_1` (입력의 Token-2022 전송 수수료 제외).

**일반적인 오류** — `ExceededSlippage`, `ZeroTradingTokens`, `InvalidStatus` (입금이 일시 중지된 경우).

## `Withdraw`

LP 토큰을 소각하고 기본 토큰을 비례적으로 받습니다.

**인자**

```
lp_token_amount:   u64
minimum_token_0:   u64
minimum_token_1:   u64
```

**계정**

| # | 이름 | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `owner_lp_token` | W |   |
| 5 | `token_0_account` | W |   |
| 6 | `token_1_account` | W |   |
| 7 | `token_0_vault` | W |   |
| 8 | `token_1_vault` | W |   |
| 9 | `token_program` |   |   |
| 10 | `token_program_2022` |   |   |
| 11 | `vault_0_mint` |   |   |
| 12 | `vault_1_mint` |   |   |
| 13 | `lp_mint` | W |   |
| 14 | `memo_program` |   |   |

처음 13개 계정은 `Deposit`과 동일하며, `lp_mint`는 LP 토큰이 소각되므로 쓰기 가능합니다. `Withdraw`는 추가로 14번째 계정 `memo_program` (제약 `address = memo::ID`)을 사용합니다 — `Deposit`은 그렇지 않습니다. 13-계정 `Withdraw`는 Anchor 역직렬화에 실패하므로 LP는 나갈 수 없습니다.

**수학**

```
total_0 = vault_0 − protocol_fees_0 − fund_fees_0 − creator_fees_0    // 측면 1도 동일

out_token_0     = min(total_0, floor(lp_token_amount * total_0 / lp_supply))
receive_token_0 = out_token_0 − transfer_fee(out_token_0)             // Token-2022
require(receive_token_0 >= minimum_token_0, "ExceededSlippage")       // 측면 1도 동일

// Deposit과 마찬가지로: 기반은 수수료 제외 볼트 총액이고, 바닥은
// LP가 실제로 받는 것에 대해 확인되며, 전송 수수료 후입니다.
```

**사후 조건**

- `lp_supply -= lp_token_amount`.
- 볼트는 `out_token_0` / `out_token_1`을 전송합니다 (총액; 사용자는 Token-2022 전송 수수료 제외 후 받습니다).

| 10 | `creator_token_0` | W |   | 토큰 0의 크리에이터 부분의 대상. |

| 13 | `token_1_program` |   |   | SPL Token 또는 Token-2022, 토큰 1과 일치. |
| 14 | `associated_token_program` |   |   | |
| 15 | `system_program` |   |   | |

**효과**

```
share_rate = creator_fee_share.share_rate   (계정이 존재하는 경우)
           | amm_config.creator_fee_share_rate   (그렇지 않은 경우)

shared_i  = floor(creator_fees_token_i * share_rate / 1_000_000)
creator_i = creator_fees_token_i - shared_i

vault_i에서 creator_token_i로 creator_i 전송
pool_state.protocol_fees_token_i += shared_i     // 볼트에 남음
pool_state.creator_fees_token_i   = 0
pool_state.recent_epoch = current epoch
```

프로토콜의 몫은 여기서 볼트를 떠나지 않습니다 — 프로토콜 수수료로 다시 레이블이 지정되고 `CollectProtocolFee`를 기다립니다. 두 카운터 모두 이미 곡선의 볼트 보기에서 제외되므로 풀의 가격은 이동하지 않습니다. 전체 유도는 [`products/cpmm/fees`](/ko/products/cpmm/fees#protocol-share-of-the-creator-fee)를 참조하세요.

## `CollectCreatorFeePermissionless`

**인자** — 없음.

**계정**

| # | 이름 | W | S | 참고 |

| 2 | `creator` |   |   | `pool_state.pool_creator`와 같아야 합니다. 서명하지 않습니다. |
| 3 | `authority` |   |   | CPMM 글로벌 볼트 권한 PDA. |

| 11 | `creator_token_0` | W |   | `vault_0_mint`에 대한 크리에이터의 정규 ATA. 누락되면 생성됩니다. |

## `CreateAmmConfig`

새로운 수수료 계층을 생성합니다.

**인자**

```
index:             u16
trade_fee_rate:    u64
protocol_fee_rate: u64
fund_fee_rate:     u64
create_pool_fee:   u64
creator_fee_rate:  u64
```

**계정**

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `owner` | W | S | 관리자. |
| 2 | `amm_config` | W |   | 여기서 `init`됩니다. |
| 3 | `system_program` |   |   |

**사전 조건**

- 동일한 `index`를 가진 기존 `AmmConfig`가 없습니다.
- `protocol_fee_rate + fund_fee_rate <= FEE_RATE_DENOMINATOR_VALUE`.

<Note>
  **2026-09에서 변경됨: 새 구성의 수수료 소유자는 더 이상 서명자에서 오지 않습니다.** `create_amm_config`는 이제 프로그램의 하드코딩된 `protocol_fee_owner::ID`를 `protocol_owner`에 쓰고 `fund_fee_owner::ID`를 `fund_owner`에 쓰며, 관리자 서명자의 키를 둘 다에 복사하는 대신입니다. 주소는 [`reference/program-addresses`](/ko/reference/program-addresses#cpmm-fee-owner-wallets)에 있습니다.

  결과: 새로 생성된 `AmmConfig`의 수수료는 전담 수수료 지갑에 도착하며, 관리자는 수집을 위한 수락된 *서명자*로 남아 있습니다 — `CollectProtocolFee` / `CollectFundFee`는 `amm_config.protocol_owner` / `fund_owner` **또는** `crate::admin::ID`를 수락합니다 — 따라서 수집을 위해 아무것도 회전할 필요가 없습니다. 변경된 것은 기본적으로 수익이 가는 위치뿐입니다. **기존 `AmmConfig` 계정은 다시 쓰이지 않습니다** — 저장된 것이 무엇이든 여전히 지배하므로 항상 계정에서 `protocol_owner` / `fund_owner`를 읽으십시오. `UpdateAmmConfig` 매개변수 `3`과 `4`는 여전히 회전합니다.
</Note>

## `UpdateAmmConfig`

기존 `AmmConfig`의 수수료율 또는 소유권을 변경합니다. `param: u8` (업데이트할 필드)과 `value: u64`를 사용합니다. 전체 디스패치 테이블:

- `param = 0` → `trade_fee_rate` (어설션 `trade_fee_rate + creator_fee_rate < 1_000_000`)
- `param = 1` → `protocol_fee_rate` (어설션 `≤ 1_000_000` 및 `+ fund_fee_rate ≤ 1_000_000`)
- `param = 2` → `fund_fee_rate` (어설션 `≤ 1_000_000` 및 `+ protocol_fee_rate ≤ 1_000_000`)
- `param = 3` → `protocol_owner`. 새 키는 `value`에 **없습니다**: `remaining_accounts[0]`으로 추가합니다 (읽기 전용 괜찮음). 기본 공개키가 아니어야 하며, 계정을 생략하면 `unwrap()`에서 패닉합니다.
- `param = 4` → `fund_owner`. `3`과 동일한 메커니즘.
- `param = 5` → `create_pool_fee`
- `param = 6` → `disable_create_pool` (0이 아닌 `value`는 비활성화)
- `param = 7` → `creator_fee_rate` (어설션 `creator_fee_rate + trade_fee_rate < 1_000_000`)
- `param = 8` → `creator_fee_share_rate` (어설션 `≤ 1_000_000`). 2026-09-13에 추가됨. 이 계층에서 크리에이터 수수료의 프로토콜 기본 몫; [`products/cpmm/fees`](/ko/products/cpmm/fees#protocol-share-of-the-creator-fee)를 참조하세요. 거래 수수료를 분할하는 `protocol_fee_rate`와 관련이 없습니다.

다른 `param`은 `InvalidInput`을 반환합니다.

변경 사항은 관리자에 의해 서명되고 다음 스왑에서 이 `AmmConfig`에 바인딩된 **모든 풀**에 영향을 미칩니다. 마이그레이션 없음; 풀은 단순히 새 값을 읽습니다.

## `CreateCreatorFeeShare`

하나의 `(creator, amm_config)` 쌍에 대한 크리에이터 수수료의 사용자 정의 프로토콜 몫을 설정하고, 해당 수수료 계층에서 해당 크리에이터가 소유한 모든 풀에 대해 `AmmConfig.creator_fee_share_rate`를 재정의합니다. 2026-09-13 크리에이터-수수료-공유 업그레이드에서 추가됨.

**인자**

```
share_rate: u64   // 크리에이터 수수료의 프로토콜 몫, FEE_RATE_DENOMINATOR = 1_000_000 이상
```

**계정**

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `owner` | W | S | CPMM 프로그램 관리자 **또는** 전담 크리에이터-수수료-공유 소유자여야 합니다 — [`reference/program-addresses`](/ko/reference/program-addresses#cpmm-creator-fee-share-authority)를 참조하세요. 다른 서명자는 `InvalidOwner` (`6001`)로 실패합니다. 임차료를 지불합니다. |
| 2 | `creator` |   |   | 비율이 적용되는 풀 생성자. 확인되지 않음 — 기존 풀 생성자일 필요가 없으며 서명하지 않습니다. |
| 3 | `amm_config` |   |   | 비율이 적용되는 수수료 계층. |
| 4 | `creator_fee_share` | W |   | `["creator_fee_share", creator, amm_config]`에서 여기서 `init`됩니다, `space = 145`. |
| 5 | `system_program` |   |   | |

**사전 조건**

- `share_rate <= 1_000_000`, 그렇지 않으면 `InvalidInput` (`6003`).
- PDA는 아직 존재하지 않아야 합니다 — Anchor의 `init`은 동일한 쌍에 대한 두 번째 호출에서 실패합니다. 비율을 변경하려면 계정을 닫고 다시 생성하세요.

**사후 조건**

- `creator_fee_share`는 `bump`, `creator`, `amm_config` 및 `share_rate`를 저장합니다.
- `amm_config` 아래 `creator`에 의해 생성된 풀에서 이후의 모든 `CollectCreatorFee` / `CollectCreatorFeePermissionless`는 구성 대신 이 계정에서 몫을 해결합니다.

<Note>
  풀 생성자는 이 명령어의 당사자가 아니며 서명하지 않습니다. 비율은 수집 시간에 읽혀지므로 수수료가 이미 누적된 후에 생성된 재정의는 해당 누적 잔액에도 적용됩니다.
</Note>

## `CollectExcessLamports`

CPMM이 제어하는 계정에서 최소 임차료 이상의 lamport의 관리자 수집. 2026-09 업그레이드에서 추가되어 프로토콜이 [SIMD-0437 임차료 감소](/ko/solana-fundamentals/rent-and-reclaimable-rent)가 각 단계 전에 생성된 계정에 남기는 과잉 자금을 회수할 수 있습니다.

초과분만 이동합니다. 토큰 잔액, 계정 데이터, 소유자, 풀 상태 및 곡선은 변경되지 않으며, 명령어는 이미 최소값에 있는 계정에 대해 작동하지 않습니다 — 따라서 각 롤아웃 단계 후에 다시 실행하는 것이 안전합니다.

**인자** — 없음.

**계정**

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | 모든 수집된 lamport의 대상. CPMM 프로그램 관리자 또는 전담 수집-lamport 지갑이어야 합니다 — [`reference/program-addresses`](/ko/reference/program-addresses#excess-lamports-collection-wallets)를 참조하세요. 다른 서명자는 `InvalidOwner`로 실패합니다. |
| 2 | `authority` |   |   | 시드 `[b"vault_and_lp_mint_auth_seed"]`의 CPMM 볼트-및-LP-민트 권한 PDA. 토큰-프로그램 CPI에 서명합니다. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. 둘 다 무조건 필요합니다. 프로그램은 소스 계정당 선택합니다. |
| 5.. | `remaining_accounts` | W |   | 수집할 `M`개의 소스 계정, 임의의 수, 임의의 순서. |

<Note>
  **순서 수정, 2026-09-13.** 프로그램은 이제 `remaining_accounts`에 대해 두 번의 패스를 만듭니다 — 모든 토큰-프로그램 CPI 먼저, 그 다음 CPMM 소유 PDA의 직접 차변. PDA가 CPI 앞에 차변되면 런타임의 `UnbalancedInstruction` ("명령어 전후의 계정 잔액 합이 일치하지 않음")으로 중단되었습니다. 호출자가 실제로 수행하는 CPI만 보류 중인 lamport 변경 사항을 계정으로 플러시하기 때문입니다. 호출자는 목록을 직접 그룹화하거나 정렬할 필요가 없습니다.
</Note>

**각 소스 계정이 처리되는 방식**

프로그램은 소스 계정의 `owner`에 따라 디스패치합니다:

| 소스 계정 소유자 | 처리 |
|---|---|
| SPL Token 또는 Token-2022, 비-네이티브 토큰 계정 또는 민트 — 풀 볼트 및 LP 민트 | CPI `WithdrawExcessLamports` (토큰-프로그램 판별자 `38`), `authority`에 의해 서명됨. |
| SPL Token 또는 Token-2022, **네이티브** (wSOL) 토큰 계정 | `WithdrawExcessLamports`는 네이티브 계정을 거부합니다. 프로그램은 `SyncNative`를 CPI하고, 래핑된 `amount`가 얼마나 증가했는지 측정하고, `UnwrapLamports` (판별자 `45`)를 정확히 그 델타에 대해 CPI한 다음, 래핑된 잔액이 사전 동기화 값과 같아야 합니다 — 그렇지 않으면 `LamportsCalculateError` (`6015`). SOL 측 풀 볼트는 따라서 전체 유동성을 유지합니다. |
| CPMM 프로그램 자체 — `PoolState`, `AmmConfig`, `ObservationState`, `Permission`, `SupportMintAssociated` | 프로그램은 계정을 `rent.minimum_balance(data_len)`까지 직접 차변합니다. |
| 다른 것 | **조용히 건너뜁니다.** 오류 없음, lamport 이동 없음. |

무제한 `remaining_accounts` 목록을 사용하므로 거래 크기가 실제 제한입니다 — [`solana-fundamentals/rent-and-reclaimable-rent`](/ko/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction)에 설명된 지갑 측 수집과 동일한 제약입니다.

**일반적인 오류** — `InvalidOwner` (`6001`, 잘못된 서명자), `LamportsCalculateError` (`6015`, wSOL 왕복이 0으로 정산되지 않음), 그리고 계정이
