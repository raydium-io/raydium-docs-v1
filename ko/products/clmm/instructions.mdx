## 명령어 목록

| 그룹 | 명령어 | 설명 |
|-------|-------------|-------|
| 관리자 | `CreateAmmConfig` | 새로운 수수료 계층을 정의합니다. |
| 관리자 | `UpdateAmmConfig` | 기존 계층의 요금을 변경합니다. |
| 관리자 | `UpdatePoolStatus` | 풀의 작업을 일시 중지/재개합니다. |
| 관리자 | `CreateSupportMintAssociated` | CLMM 풀에서 사용할 Token-2022 민트 확장 구성을 허용 목록에 추가합니다. |
| 관리자 | `CreateOperationAccount` | 프로그램 수준의 작업 계정을 초기화합니다 (일회성). |
| 관리자 | `UpdateOperationAccount` | 작업 계정 허용 목록을 수정합니다. |
| 관리자 | `CreateDynamicFeeConfig` | u16 인덱스 아래에서 재사용 가능한 동적 수수료 매개변수 집합을 만듭니다. |
| 관리자 | `UpdateDynamicFeeConfig` | 기존 `DynamicFeeConfig`를 수정합니다. 이미 스냅샷한 풀은 영향을 받지 않습니다. |
| 관리자 | `CreatePermissionPda` | `CreatePermissionedPool`을 호출할 권리를 권한에 부여하여 `Permission` PDA를 초기화합니다. |
| 관리자 | `ClosePermissionPda` | `Permission` PDA를 닫아 이전에 부여된 권한을 취소합니다. 임차료는 호출자에게 환불됩니다. |
| 풀 | `CreatePool` | `AmmConfig`에 바인딩된 CLMM 풀을 초기화합니다. 표준, FromInput 수수료 경로. `CreateCustomizablePool`과 공존합니다. |
| 풀 | `CreateCustomizablePool` | 새 풀에 권장됩니다. `CreatePool`과 동일한 형태에 `collect_fee_on`과 선택적 `enable_dynamic_fee` 플래그가 추가됩니다. |
| 풀 | `CreatePermissionedPool` | 이미 풀이 있는 쌍에 대해 **추가** 풀을 만들고, 클라이언트가 제공한 `seed_index`를 풀 PDA에 포함합니다. 지불자는 `Permission` PDA를 보유해야 합니다. |
| 포지션 | `OpenPosition` / `OpenPositionV2` / `OpenPositionWithToken22Nft` | 포지션 NFT를 발행합니다. `OpenPositionV2`는 V1을 대체합니다. `OpenPositionWithToken22Nft`는 NFT를 Token-2022로 발행합니다. V2 경로는 기본 볼트 민트의 동결 권한이 제한된 발급자 목록과 일치할 때만 NFT 계정을 동결합니다. 그렇지 않으면 계정은 동결되지 않은 상태로 유지됩니다. |
| 포지션 | `IncreaseLiquidity` / `IncreaseLiquidityV2` | 기존 포지션에 유동성을 추가합니다. |
| 포지션 | `DecreaseLiquidity` / `DecreaseLiquidityV2` | 유동성을 제거하고 지불해야 할 수수료를 수집합니다. |
| 포지션 | `ClosePosition` | NFT를 소각하고 `PersonalPositionState`를 닫습니다. NFT 계정이 동결되어 있으면 먼저 남은 계정으로 제공된 풀 PDA로 해제합니다. |
| 포지션 | `CloseProtocolPosition` | 레거시 `ProtocolPositionState` PDA에 대한 관리자 전용 정리입니다. 현재 프로그램은 더 이상 `ProtocolPositionState`를 생성하거나 읽지 않습니다. 이 명령어는 이전 프로그램 버전에서 생성한 계정의 임차료를 회수하기 위해서만 존재합니다. |
| 스왑 | `Swap` / `SwapV2` | 상수 유동성 스왑입니다. 두 변형 모두 동적 수수료, 단측 수수료 라우팅, 지정가 주문 매칭을 적용합니다. 유일한 차이점은 `SwapV2`가 Token-2022 민트를 허용한다는 것입니다 (V1 변형은 두 볼트 모두 클래식 SPL 토큰이어야 함). |
| 스왑 | `SwapRouterBaseIn` | 라우터에서 사용하는 다중 홉입니다. |
| 지정가 주문 | `OpenLimitOrder` | 틱에서 판매 주문을 배치합니다. 미체결 토큰은 틱에 앉아 있고, 가격이 지나갈 때 매칭 엔진이 채웁니다. |
| 지정가 주문 | `IncreaseLimitOrder` | 기존 공개 주문에 추가합니다. |
| 지정가 주문 | `DecreaseLimitOrder` | 공개 주문을 줄이거나 취소합니다. 미체결 나머지와 이미 정산된 출력을 지불합니다. |
| 지정가 주문 | `SettleLimitOrder` | 채워진 출력 토큰을 주문 소유자에게 푸시합니다. 주문 소유자 또는 운영 담당자가 호출할 수 있습니다. |
| 지정가 주문 | `CloseLimitOrder` | 완전히 소비된 주문 계정을 닫습니다. 임차료는 항상 주문의 `owner`에게 반환됩니다. 소유자 또는 담당자가 호출할 수 있습니다. |
| 수수료 | `CollectProtocolFee` | 프로토콜 수수료의 관리자 정리입니다. |
| 수수료 | `CollectFundFee` | 펀드 수수료의 관리자 정리입니다. |
| 보상 | `InitializeReward` | 풀에 새로운 보상 스트림을 연결합니다. |
| 보상 | `SetRewardParams` | 기존 보상의 배출 속도/종료를 변경합니다. |
| 보상 | `UpdateRewardInfos` | 보상 성장을 현재로 정산합니다 (모든 스왑/포지션 변경으로 호출됨). |
| 보상 | `TransferRewardOwner` | 보상 스트림을 설정하거나 충전할 수 있는 권한을 이전합니다. |
| 보상 | `CollectRemainingRewards` | 보상 스트림의 `end_time` 이후, 할당되지 않은 토큰을 펀더에게 다시 정리합니다. |
| 관리자 | `CloseSupportMintAssociated` | 민트의 `SupportMintAssociated` 등록을 제거하고 그 임차료를 환불합니다. |

<Note>
  **init-tick-array 명령어는 없으며, 필요하지도 않습니다.** 틱 배열은 `OpenPosition*` /
  `IncreaseLiquidity*` *내부에서* `TickArrayState::get_or_create_tick_array`에 의해 생성되며
  비용은 `payer`가 부담합니다. (아직 초기화되지 않아 시스템이 소유한 상태일 수도 있는) 틱 배열
  PDA를 `tick_array_lower` / `tick_array_upper`로 전달하면 프로그램이 누락된 경우 할당합니다.
  `OpenLimitOrder`도 자신의 단일 `tick_array`에 대해 동일하게 동작합니다.
</Note>

대부분의 관리자 전용 명령어 (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`)는 프로그램의 하드코딩된 `admin` 공개 키로 제어됩니다. `CreatePermissionPda` / `ClosePermissionPda`는 `admin` 공개 키 **또는** 전용 `permission_pda_admin` 키를 허용합니다. `CreateSupportMintAssociated` / `CloseSupportMintAssociated`는 `admin` 공개 키 **또는** 전용 support-mint 소유자 키를 허용합니다. 보상 스트림 관리자 명령어 (`TransferRewardOwner`, `CollectRemainingRewards`)는 프로그램 관리자가 아닌 보상 펀더로 제어됩니다.

V2 접미사는 "볼트/NFT에서 Token-2022를 지원하며, 비트맵 확장 슬롯이 필요함"을 의미합니다. SDK는 새 풀에 대해 기본적으로 V2를 선택합니다.

## `CreatePool`

**인자**

```
sqrt_price_x64: u128           // 초기 가격
open_time:      u64            // 이 시간 이전의 스왑은 거부됨
```

**계정 (축약)**

| # | 이름 | W | S | 설명 |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | 선택한 수수료 계층. |
| 3 | `pool_state` | W |   | 여기서 `init`. |
| 4 | `token_mint_0` |   |   | 정렬됨. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | 여기서 `init`, 풀 권한 PDA가 소유. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | 여기서 `init`. |
| 9 | `tick_array_bitmap` | W |   | `TickArrayBitmapExtension` PDA; 여기서 `init`. |
| 10 | `token_program_0` |   |   | `token_mint_0`을 소유한 프로그램 — SPL Token **또는** Token-2022. |
| 11 | `token_program_1` |   |   | `token_mint_1`을 소유한 프로그램. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  슬롯 10과 11은 "SPL Token 다음 Token-2022"가 아니라 **민트별**입니다. 각 슬롯은 해당 민트의
  `mint::token_program`으로 제약되므로, `token_mint_0`이 Token-2022이고 `token_mint_1`이
  클래식 SPL인 풀에서는 슬롯 10에 Token-2022, 슬롯 11에 SPL Token을 전달해야 합니다.
  `CreateCustomizablePool`과 `CreatePermissionedPool`도 동일한 두 슬롯을 사용합니다.
</Warning>

**전제 조건**

- `token_mint_0 < token_mint_1` (바이트 순서).
- `amm_config.disable_create_pool == false`.
- 민트는 Token-2022 확장 허용 목록에 의해 거부되지 않습니다.

**사후 조건**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (아직 포지션 없음).
- `pool_state.fee_on = FromInput` (레거시 기본값).
- `pool_state.dynamic_fee_info`는 0으로 설정됨 (동적 수수료 비활성화).

## `CreateCustomizablePool`

새 풀에 권장됩니다. `CreatePool`과 동일한 효과에 풀별 수수료 수집 모드와 선택적 동적 수수료 옵트인을 추가합니다.

**인자**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**계정** — `CreatePool`의 선언된 13개 계정과 정확히 동일합니다. `dynamic_fee_config`는 선언된 계정이 **아닙니다**.

<Warning>
  `enable_dynamic_fee = true`일 때 스냅샷할 `DynamicFeeConfig`는 **마지막** `remaining_account`로
  제공해야 합니다 — 핸들러가 `ctx.remaining_accounts.last()`를 읽습니다. 따라서
  `SupportMintAssociated` 우회 PDA는 그보다 *앞에* 와야 하며, 그렇지 않으면 프로그램이 잘못된
  계정을 스냅샷하여 역직렬화에 실패합니다. 플래그가 설정된 상태에서 이를 생략하면
  `AccountLack`으로 실패합니다.
</Warning>

**전제 조건** — `CreatePool`과 동일합니다. `enable_dynamic_fee = false`이면 `remaining_account`가 필요하지 않으며, 전달된 것이 있어도 support-mint 레코드만 검사합니다.

**사후 조건**

- `pool_state.fee_on`이 선택한 `CollectFeeOn` 변형으로 설정됨.
- 동적 수수료가 활성화된 경우: `pool_state.dynamic_fee_info`는 제공된 `DynamicFeeConfig`에서 초기화됨 (5개의 보정 매개변수 복사됨, 상태 필드는 0으로 설정됨).
- 그렇지 않으면: `pool_state.dynamic_fee_info`는 0으로 설정됨 (= 이 풀에 대해 동적 수수료는 영구적으로 비활성화).

`fee_on`과 동적 수수료 활성화 비트는 **풀 생성 시에만** 설정됩니다. 제자리 업그레이드는 없습니다. 레거시 `CreatePool`을 통해 생성된 풀은 동적 수수료나 단측 수수료를 소급하여 얻을 수 없습니다. 새 배포는 이 명령어를 기본값으로 사용해야 합니다.

## `CreatePermissionedPool`

`CreatePool`과 `CreateCustomizablePool` 모두 `["pool", amm_config, token_mint_0, token_mint_1]`에서 풀 PDA를 파생하므로, `(config, mint0, mint1)` 트리플당 정확히 **하나의** 정규 풀 주소가 있습니다. 같은 시드에서 두 번째 `init`은 실패합니다. `CreatePermissionedPool`은 클라이언트가 제공한 `seed_index: u16`을 풀 PDA 시드에 포함하여 이 제한을 해제하므로, **같은 쌍과 수수료 계층에 대해 여러 풀**을 만들 수 있습니다. 각각 자신의 주소에서. 임의의 풀 주소는 특권 기능이므로, 지불자는 이를 승인하는 `Permission` PDA를 보유해야 합니다.

풀에 대한 다른 모든 것은 `CreateCustomizablePool`과 동일합니다. 동일한 `CreateCustomizableParams`를 사용하고 단측 수수료와 동적 수수료 옵트인을 지원합니다.

**인자**

```rust
customizable_params: CreateCustomizableParams   // CreateCustomizablePool과 동일한 구조체
seed_index:          u16                          // 0이 아니어야 함. 풀 PDA 시드에 포함됨
```

**계정 (축약)** — `CreateCustomizablePool`과 동일하며, 앞에:

| # | 이름 | W | S | 설명 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | 임차료를 지불합니다. 아래 `permission` PDA의 권한이어야 합니다. |
| 2 | `pool_creator` |   |   | `pool_state.owner`로 기록됩니다. `payer`와 다를 수 있습니다. |
| 3 | `permission` |   |   | PDA `["permission", payer]`. Anchor는 존재하지 않거나 프로그램이 소유하지 않으면 호출을 거부합니다. |
| … | (`amm_config`, `pool_state`, 민트, 볼트, `observation_state`, `tick_array_bitmap`, 토큰/시스템 프로그램) | | | `CreateCustomizablePool`과 같음. |

`pool_state` PDA는 `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`에서 파생됩니다.

**전제 조건**

- `seed_index != 0`. `seed_index` 0은 레거시 풀을 위해 예약되어 있으며 여기서 거부됩니다. `[0, 0]` 시드 구성 요소는 레거시 풀 주소를 클래식 4시드 형식으로 축소하는 것입니다.
- `payer`에 대한 `permission` PDA가 존재합니다 (관리자가 `CreatePermissionPda`를 통해 생성).
- `CreatePool`과 동일한 민트/허용 목록 규칙.

**사후 조건**

- 새로운 `pool_state`가 `seed_index` 파생 주소에 존재하며, `pool_state.seed_index = seed_index`.
- 다른 모든 사후 상태는 `CreateCustomizablePool`과 일치합니다 (수수료 모드, 선택적 동적 수수료).

<Note>
  이 명령어는 일반 풀 생성 접근을 확대하지 **않습니다**. 무허가 생성은 `CreatePool` / `CreateCustomizablePool`을 통해 계속되며, 이는 쌍당 하나의 풀로 유지됩니다. `CreatePermissionedPool`은 화이트리스트된 운영자가 같은 쌍에 대해 여러 풀이 필요한 경우 (예: 다른 초기 가격 또는 출시 코호트)이고 관리자가 부여한 `Permission` PDA를 보유하는 특정 경우에 존재합니다.
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

기존 풀 내에 새로운 포지션을 만듭니다.

**인자**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // 원하는 L (또는 아래 금액을 사용하려면 0)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // NFT 메타데이터 작성 (Metaplex)
base_flag: Option<bool>       // true = amount0에 맞춤; false = amount1에 맞춤
```

**계정 (축약)**

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | |
| 2 | `position_nft_owner` |   |   | |
| 3 | `position_nft_mint` | W | S | 새 키페어. |
| 4 | `position_nft_account` | W |   | 소유자의 NFT용 ATA. |
| 5 | `metadata_account` | W |   | Metaplex 메타데이터 PDA. `with_metadata = false`인 경우에도 **무조건** 선언됩니다. |
| 6 | `pool_state` | W |   | |

  **`tick_array_bitmap_extension`은 두 변형 모두에서 선언된 계정이 아닙니다.** 포지션의 범위가
  풀의 인라인 `tick_array_bitmap`(±512 틱 배열)을 벗어나는 경우, 시드
  `["pool_tick_array_bitmap_extension", pool_state]`의 `TickArrayBitmapExtension` PDA를
  `remaining_accounts[0]`으로 추가하세요.
</Warning>

**수학** — [`products/clmm/math`](/ko/products/clmm/math) 참조. `base_flag`가 주어지면, 프로그램은 `liquidity` 또는 `(amount_0_max, amount_1_max)` 중 하나를 실제 `L`과 소비된 실제 토큰 금액으로 해석합니다.

**전제 조건**

- `tick_lower < tick_upper`, 둘 다 `pool.tick_spacing`의 배수, `[MIN_TICK, MAX_TICK]` 범위 내.
- 두 개의 틱 배열 PDA가 전달됩니다. 이미 존재할 필요는 **없습니다** — 이 명령어 내부에서 `get_or_create_tick_array`가 `payer`의 비용으로 누락된 것을 할당합니다. 별도의 init-tick-array 명령어는 없습니다.
- 사용자는 소스 ATA에 최소 `amount_0_max`와 `amount_1_max`를 보유합니다.

**사후 조건**

- `personal_position`이 존재하고, `liquidity`가 설정되고, `fee_growth_inside_last`가 스냅샷됨.
- `tick_lower`와 `tick_upper`의 틱 배열 항목이 업데이트됨 (`liquidity_gross += L`, `liquidity_net ± L`, 수수료 성장 스냅샷 유지).
- 포지션이 범위 내인 경우 `pool_state.liquidity += L` (`tick_lower ≤ tick_current < tick_upper`).
- 포지션 NFT 민트는 `pool_state`를 동결 권한으로 기록합니다. 민트 권한은 단일 NFT가 발행된 후 제거됩니다. 동결 권한을 기록해도 NFT 토큰 계정의 상태는 변경되지 않습니다.
- NFT 토큰 계정은 명령어가 `OpenPositionV2` 또는 `OpenPositionWithToken22Nft` **이고** 볼트 민트의 동결 권한이 CLMM의 제한된 발급자 목록과 일치하는 경우를 제외하고는 동결되지 않은 상태로 유지됩니다. 일치하는 V2 경로만 계정을 동결합니다. `OpenPosition` V1은 동결하지 않습니다.

**일반적인 오류** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (끝점이 `tick_spacing`의 배수가 아님), `InvalidTickIndex` (`[MIN_TICK, MAX_TICK]` 범위 밖), `MissingTickArrayBitmapExtensionAccount` (범위가 인라인 비트맵을 벗어났는데 확장이 추가되지 않음), `NotApproved` (`pool_state.status`가 열기를 차단), `ZeroAmountSpecified`.

<Note>
  포지션 동결은 선언된 명령어 계정이나 인자를 추가하지 않습니다. 클라이언트는 기존 V2 레이아웃으로 이러한 포지션을 열 수 있습니다. 동작은 `vault_0_mint`와 `vault_1_mint`에서 온체인으로 선택됩니다.
</Note>

포지션 NFT를 소각하고 `PersonalPositionState`를 닫습니다.

| 2 | `position_nft_mint` | W |   | `personal_position.nft_mint`와 일치해야 합니다. |

| 4 | `personal_position` | W |   | `nft_owner`로 닫힙니다. |
| 5 | `system_program` |   |   | 포지션 상태를 닫습니다. |
| 6 | `token_program` |   |   | NFT 민트와 토큰 계정을 소유해야 합니다. |

**남은 계정**

- 동결되지 않은 NFT: 필요 없음. 추가 풀 계정은 핸들러가 읽지 않으므로 무해합니다.
- 동결된 NFT: `personal_position.pool_id`를 첫 번째 남은 계정으로 추가합니다. 프로그램은 이를 `PoolState`로 로드하고 해제에 서명하기 위해 PDA 시드를 사용합니다.

**전제 조건**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- 모든 보상 카운터 `reward_amount_owed == 0`.

(즉, 먼저 모든 것을 수집하고 0으로 감소시킵니다.)

**효과**

- NFT 토큰 계정이 동결되어 있으면, 첫 번째 남은 계정이 `personal_position.pool_id`와 같은지 확인한 후 풀 PDA로 해제합니다.
- NFT를 소각합니다.
- NFT 토큰 계정과 `personal_position`을 닫고, 임차료를 `nft_owner`에게 환불합니다. 포지션 NFT가 Token-2022를 사용하면 NFT 민트도 닫습니다. 클래식 SPL 토큰 민트는 닫을 수 없으며 공급량 0으로 유지됩니다.

해제, 소각, 닫기는 원자적입니다. NFT는 이 단계 사이에 양도 가능해질 수 없습니다.

**조건부 클라이언트 중단** — 선언된 IDL 레이아웃은 변경되지 않으므로 레거시 클라이언트는 기존 및 동결되지 않은 포지션을 계속 닫습니다. 풀 남은 계정을 생략하는 레거시 빌더는 동결된 포지션을 닫을 때 `AccountLack`으로 실패합니다. 모든 닫기에 대해 풀을 전달하는 것이 가장 간단한 호환 전략입니다.

## `SwapV2`

유동성 곡선을 따라갑니다. `is_base_input`에 따라 정확한 입력 **또는** 정확한 출력.


**계정 (축약)**

| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |

| 14+ | `tick_array` (남은 것) | W |   | 스왑 워크의 예상 범위를 포함할 충분한 배열. |

호출자는 예상 스왑 워크를 포함하는 순위가 지정된 틱 배열 목록을 전달합니다. 프로그램은 필요한 만큼 사용합니다. SDK는 `PoolUtils.computeAmountOutFormat` 또는 API의 견적 끝점을 통해 이 목록을 계산합니다.

**전제 조건**

- `pool_state.status`가 스왑을 허용합니다.
- `now >= open_time`.
- `sqrt_price_limit_x64`는 방향에 대해 `sqrt_price_x64`의 올바른 쪽에 있습니다.

**일반적인 오류** — `TooLittleOutputReceived` (exact-in 슬리피지), `TooMuchInputPaid` (exact-out 슬리피지), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (`pool_state.status`에 스왑 비트가 설정됨). CLMM에는 `ExceededSlippage` 변형이 없습니다 — 그 이름은 CPMM의 것입니다 — 그리고 `TickArrayNotFound`도 없습니다.

**`SwapV2`가 내부적으로 수행하는 작업 (호출자가 알아야 할 사항)** (2025년 이후 릴리스):

1. **동적 수수료 할증** — `pool.dynamic_fee_info`가 0이 아니면, 프로그램은 마지막 스왑 이후 순회한 틱 거리를 사용하여 변동성 누적기를 업데이트하고 (필터/감소 규칙 포함 [`products/clmm/fees`](/ko/products/clmm/fees)) `AmmConfig.trade_fee_rate` 위에 `dynamic_fee_component`를 추가합니다. 총 수수료는 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`)로 제한됩니다.
2. **지정가 주문 매칭** — 가격 워크가 공개 지정가 주문을 보유한 틱을 지날 때, 프로그램은 먼저 해당 틱에서 사용 가능한 지정가 주문 유동성을 채우고 (FIFO by `order_phase`), 그 다음 LP 유동성 곡선을 따라갑니다. 채워진 금액은 나중의 정산을 위해 `tick.unfilled_ratio_x64`와 `tick.part_filled_orders_remaining`을 업데이트합니다. 주문 자체는 소유자가 `SettleLimitOrder`를 호출할 때까지 미지출 상태로 유지됩니다.
3. **단측 수수료 라우팅** — `pool.fee_on = Token0Only` 또는 `Token1Only`일 때, 스왑 단계는 여전히 동일한 입력-출력 거래를 계산합니다. 그 다음 수수료는 구성된 쪽으로 라우팅됩니다. 구성된 수수료 쪽이 출력인 방향의 경우, 수수료는 스왑 출력에서 차감됩니다 (사용자는 `out − fee`를 받음). 구성된 쪽이 입력인 방향의 경우, 동작은 `FromInput`과 일치합니다. `PoolState`의 `is_fee_on_input(zero_for_one)`과 `is_fee_on_token0(zero_for_one)`을 참조하세요.

`Swap` (V1)은 `SwapV2`와 동일한 동적 수수료, 단측 수수료 라우팅, 지정가 주문 매칭을 구현합니다. 유일하게 부족한 기능은 Token-2022 지원입니다. 두 볼트 모두 클래식 SPL 토큰이어야 합니다. Token-2022 민트가 있는 풀은 `SwapV2`를 통해 스왑해야 합니다. 애그리게이터와 SDK는 이미 모든 CLMM 레그에 대해 V2를 선호하므로 호출자는 민트 유형에 따라 분기할 필요가 없습니다.

## `OpenLimitOrder`

특정 틱에서 판매 주문을 배치합니다. 주문은 틱별 FIFO 코호트에 앉아 있고 가격이 지나갈 때 채워집니다.

**인자**

```
nonce_index:    u8       // 사용자가 선택한 논스 계정 인덱스 (지갑당 0..255)
zero_for_one:   bool     // true: 토큰0을 토큰1로 판매; false: 토큰1을 토큰0으로 판매
tick_index:     i32      // pool.tick_spacing의 배수여야 함
amount:         u64      // 입력 토큰 금액
```

**계정 (축약)**

| # | 이름 | W | S | 설명 |
|---|------|---|---|-------|
| 1 | `payer` | W | S | 주문 소유자. 임차료를 지불합니다. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | `tick_index`를 포함하는 틱 배열. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — 사용자의 이 `nonce_index` 아래 첫 주문에서 생성됨. |
| 5 | `limit_order` | W |   | PDA. 여기서 `init`. |
| 6 | `input_token_account` | W |   | 사용자의 입력 ATA. `frozen` 확인됨. |
| 7 | `output_token_account` | W |   | 사용자의 **출력** ATA. 열기 시 차감되지 않음. 프로그램이 `frozen`이 아님을 확인할 수 있도록 필요함 (즉, 채우기는 나중에 전달될 수 있음). |
| 8 | `input_vault` | W |   | 풀 입력 볼트. |
| 9 | `output_vault` | W |   | 풀 출력 볼트. 출력 쪽의 민트를 식별합니다 (`output_token_account` / `output_vault_mint` 확인 쌍). |
| 10 | `input_vault_mint` |   |   | Token-2022 수수료 처리. |
| 11 | `output_vault_mint` |   |   | 출력 쪽의 민트 (동결 확인 쌍). |
| 12 | `input_token_program` |   |   | SPL 또는 Token-2022. |
| 13 | `system_program` |   |   | `limit_order`, `limit_order_nonce`, 그리고 필요한 경우 `tick_array` 할당의 자금을 댑니다. |

**남은 계정** — `[0]` `tick_array_bitmap_extension`으로, 시작 인덱스가 풀의 인라인 비트맵을 벗어나는 틱 배열을 초기화할 때만 필요합니다. 그 외에는 아무것도 전달하지 마세요.

<Warning>
  **`rent` 계정은 없습니다**: 구조체는 `system_program`에서 끝나며 선언된 계정은 13개입니다.
  위치 14에 엉뚱하게 들어간 `rent`는 선택적 비트맵 확장이 읽히는 바로 그 자리에 놓이므로,
  인라인 비트맵 밖의 틱 배열을 처음으로 생성해야 하는 순간까지는 순서가 잘 작동하는 것처럼
  보이다가 그 시점에 실패합니다.
</Warning>

<Note>
  **계정 목록 변경 (2026-07 릴리스).** `OpenLimitOrder`는 이제 입력 쪽 외에도 **출력 쪽** 계정 — `output_token_account`, `output_vault`, `output_vault_mint` — 도 사용합니다. 이들은 검증에만 사용됩니다. 프로그램은 소유자의 입력 **또는** 출력 토큰 계정이 동결되어 있으면 주문을 거부합니다. 이는 채우기가 실제로 소유자의 출력 ATA로 정산될 수 있음을 보장합니다. 이는 허용 목록/기본 동결 Token-2022 민트 (예: 허가된 토큰)에 중요합니다. 여기서 계정이 아직 해제되지 않았을 수 있습니다. 이전 단측 계정 목록에 대해 빌드된 클라이언트는 3개의 출력 계정을 추가해야 합니다.
</Note>

**전제 조건**

- `input_token_account`와 `output_token_account` 모두 동결되지 않음 (그렇지 않으면 `NotApproved`).
- `pool_state.status`가 스왑 (비트 4)과 지정가 주문 (비트 5) 작업을 모두 허용함 (그렇지 않으면 `NotApproved`).
- `tick_index % pool.tick_spacing == 0`이고 `[MIN_TICK, MAX_TICK]` 범위 내.
- `tick_index`는 선택한 방향에 대해 **`pool.tick_current`의 올바른 쪽**에 있음 (토큰0 판매 → 틱은 현재 위에 있어야 함, 그 반대도 마찬가지). 이미 지나간 틱에서 판매하면 즉시 매칭되고 거부됩니다.

**사후 조건**

- `limit_order`가 존재하고, 열기 시간에 `tick.order_phase`와 `tick.unfilled_ratio_x64`를 스냅샷함.
- `tick.orders_amount += amount` (현재 코호트에서).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` 발행됨.

**일반적인 오류** — `NotApproved` (입력 또는 출력 토큰 계정 동결, 또는 풀이 스왑/지정가 주문 비활성화), `ZeroAmountSpecified` (입력 측 전송 수수료 차감 후 `amount == 0`), `InvalidLimitOrderAmount` (해당 틱에서 출력이 1 기본 단위 미만이 되거나 `u64`를 오버플로우하는 금액), `InvalidTickIndex` (`[MIN_TICK, MAX_TICK]` 범위 밖, 또는 선택한 방향에 대해 `tick_current`의 잘못된 쪽), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `IncreaseLimitOrder`

기존 공개 주문에 추가합니다. 주문의 `owner`만 호출할 수 있습니다.

**인자**

```
amount: u64    // 추가 입력 토큰 금액
```

**계정** — 8개, 입력 측만. 논스 계정, 출력 측 계정 3개 전부, **그리고** `system_program`이 빠집니다.

| # | 이름 | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `input_vault` | W |   |
| 7 | `input_vault_mint` |   |   |
| 8 | `input_token_program` |   |   |

**전제 조건**

- `limit_order.owner == signer`.
- 주문이 여전히 동일한 코호트에 있음 (`tick.order_phase == limit_order.order_phase`). 코호트가 이미 채우기를 시작했으면, 주문은 부분적으로 정산됨. 호출자는 먼저 `DecreaseLimitOrder` 또는 `SettleLimitOrder`를 호출하여 앞으로 이동해야 합니다.

**효과**

- 소유자 ATA에서 `input_vault`로 `amount`를 전송합니다.
- `limit_order.total_amount += amount`. `tick.orders_amount += amount`.

## `DecreaseLimitOrder`

공개 주문을 줄이거나 완전히 취소합니다. 미체결 나머지를 소유자에게 지불하고, 과거 부분 채우기로 이미 정산된 출력도 지불합니다.

**인자**

```
amount:     u64    // 인출할 입력 토큰 금액 (최대 = 미체결 나머지)
amount_min: u64    // 입력 쪽 인출에 대한 슬리피지 하한
```

**계정** — 입력 및 출력 토큰 쪽:

| # | 이름 | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_vault_mint`, `output_vault_mint` |   |   |
| 10 | `token_program`, `token_program_2022` |   |   |

**효과**

- 열기 이후 코호트의 `unfilled_ratio_x64`에서 주문의 채워진 금액을 재계산합니다.
- 채워진 출력을 `output_token_account`로 보냅니다.
- 미체결 입력의 `amount`를 `input_token_account`로 다시 보냅니다.
- `limit_order`를 그에 따라 업데이트합니다. 새로운 미체결 나머지가 0이면, 프로그램은 계정을 닫고 임차료를 `owner`에게 환불합니다.

## `SettleLimitOrder`

주문의 미체결 나머지를 변경하지 않고 채워진 출력 토큰을 소유자에게 푸시합니다. `auto_withdraw` 담당자가 장기 실행 부분 채우기를 점진적으로 지불하려고 할 때 유용합니다.

**호출자** — 주문의 `owner` 또는 프로그램의 `limit_order_admin` (자동화된 담당자 루프를 실행하는 오프체인 운영 핫 지갑). 담당자는 다른 권한이 없습니다. 채워진 출력을 주문의 `owner` ATA로 푸시하는 것 외에는 사용자 자금을 이동할 수 없습니다.

**계정**

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `signer` |   | S | 소유자 *또는* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | 소유자의 출력 ATA. |
| 6 | `output_vault` | W |   | 풀 출력 볼트. |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**효과**

- `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)`를 사용하여 누적 출력 지불액을 계산합니다.
- 델타를 `output_token_account`로 전송합니다.
- `limit_order.settled_output`을 업데이트합니다.
- 주문을 닫지 **않습니다**. 남은 입력에 대해 여전히 열려 있습니다.

## `CloseLimitOrder`

완전히 소비된 주문 계정을 닫습니다. 임차료는 누가 서명하든 항상 `limit_order.owner`에게 반환됩니다.

**호출자** — `owner` 또는 `limit_order_admin`.

**전제 조건**

- 주문의 미체결 나머지가 0임 (`amount == total_amount`가 채워지고 정산되었거나, 소유자가 이전에 주문을 0으로 감소시키고 닫기를 잊음).

**효과**

- `limit_order`를 닫습니다. 임차료는 `limit_order.owner`로 전송됩니다.

## `InitializeReward`

풀에 새로운 보상 스트림을 추가합니다. 최대 3개의 스트림이 한 번에 활성화될 수 있습니다.

**계정**

| # | 이름 | W | S | 참고 |
|---|------|---|---|-------|
| 1 | `reward_funder` | W | S |
| 2 | `funder_token_account` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |

| 6 | `reward_token_mint` |   |   |

- `operation_state`당 화이트리스트된 보상 민트.

## `SetRewardParams`

기존 보상 스트림을 연장, 충전 또는 배출 속도를 변경합니다. 일반적으로 풀 생성자 또는 Raydium 멀티시그에서 호출합니다. 제약은 온체인에 있습니다. 일반적으로 `end_time`을 연장하거나 배출을 증가시킬 수 있지만, 소급하여 축소할 수는 없습니다. `operation_state`의 소유자 목록을 확인하세요.

## `UpdateRewardInfos`

순수 부기 — `reward_growth_global_x64`를 현재 시간으로 정산합니다. `emissions_per_second × Δt / liquidity`를 곱합니다. 모든 유동성 터치 명령어에 의해 내부적으로 호출됩니다. 외부 행위자 (UI, 크랭크)가 때때로 이를 트리거하려고 하므로 독립 실행형 명령어로 노출됩니다.

## Collecting rewards

<Warning>
  **독립적인 보상 수집 명령어는 없습니다.** 프로그램은 `CollectReward` 진입점을 노출하지 않으며,
  공개된 IDL에도 없습니다.
</Warning>

포지션에 지불해야 할 보상은 `DecreaseLiquidity` / `DecreaseLiquidityV2`가 지급합니다. 포지션을
변경하지 않고 수집하려면 `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`으로 호출하세요.
보상 볼트와 수신자 계정은 활성 보상마다 3개씩 묶여 `remaining_accounts`에 들어가며, 순서는
`reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`입니다.

`CollectRemainingRewards`는 다른 것입니다: 스트림의 `end_time` 이후에 보상 *펀더*가 어떤
포지션에도 할당되지 않은 토큰을 정리할 수 있게 해줍니다.
