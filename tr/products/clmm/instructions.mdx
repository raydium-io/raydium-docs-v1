Ödül akışı admin talimatları (`TransferRewardOwner`, `CollectRemainingRewards`) program admin'i değil, ödül fon sağlayıcısı tarafından kapılanır.

V2 soneki "Token-2022'yi kasa/NFT'de destekler, bitmap-uzantı yuvası gerektirir" anlamına gelir. SDK yeni havuzlar için varsayılan olarak V2'yi seçer.

## `CreatePool`

**Argümanlar**

```
sqrt_price_x64: u128           // başlangıç fiyatı
open_time:      u64            // bu saatten önce swap'lar reddedilir
```

**Hesaplar (kısaltılmış)**

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Seçilen ücret seviyesi. |
| 3 | `pool_state` | W |   | Burada `init`. |
| 4 | `token_mint_0` |   |   | Sıralanmış. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | Burada `init`, havuz yetkilisi PDA'sı tarafından sahip olunan. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | Burada `init`. |
| 9 | `tick_array_bitmap_extension` | W |   | Burada `init` (V2). |
| 10 | `token_program` |   |   | |
| 11 | `token_program_2022` |   |   | |
| 12 | `system_program`, `rent` |   |   | |

**Ön koşullar**

- `token_mint_0 < token_mint_1` bayt sırasına göre.
- `amm_config.disable_create_pool == false`.
- Mint'ler Token-2022 uzantı izin listesi tarafından reddedilmez.

**Son koşullar**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (henüz pozisyon yok).
- `pool_state.fee_on = FromInput` (eski varsayılan).
- `pool_state.dynamic_fee_info` sıfırlanır (dinamik ücret devre dışı).

## `CreateCustomizablePool`

Yeni havuzlar için önerilir. `CreatePool` ile aynı etki artı havuz başına ücret toplama modu ve isteğe bağlı dinamik ücret katılımı.

**Argümanlar**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Hesaplar (kısaltılmış)** — `CreatePool` ile aynı artı, `enable_dynamic_fee = true` olduğunda:

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| N | `dynamic_fee_config` |   |   | Anlık görüntü almak için paylaşılan yapılandırma. Zaten var olmalıdır. |

**Ön koşullar** — `CreatePool` ile aynı. `enable_dynamic_fee = false` ise, `dynamic_fee_config` yoksayılır.

**Son koşullar**

- `pool_state.fee_on` seçilen `CollectFeeOn` varyantına ayarlanır.
- Dinamik ücret etkinleştirilirse: `pool_state.dynamic_fee_info` sağlanan `DynamicFeeConfig`'den başlatılır (beş kalibrasyon parametresi kopyalanır; durum alanları sıfırlanır).
- Aksi takdirde: `pool_state.dynamic_fee_info` sıfırlanır (= bu havuz için dinamik ücret sonsuza kadar etkin değil).

`fee_on` ve dinamik ücret etkinleştirme biti **yalnızca** havuz oluşturma sırasında ayarlanır. Yerinde yükseltme yoktur — eski `CreatePool` aracılığıyla oluşturulan havuzlar dinamik ücret veya tek taraflı ücret kazanamaz. Yeni dağıtımlar varsayılan olarak bu talimata geçmelidir.

## `CreatePermissionedPool`

Hem `CreatePool` hem de `CreateCustomizablePool` havuz PDA'sını `["pool", amm_config, token_mint_0, token_mint_1]`'den türetir, bu nedenle `(config, mint0, mint1)` üçlüsü başına tam olarak **bir** kanonik havuz adresi vardır — aynı seed'lerde ikinci `init` başarısız olur. `CreatePermissionedPool` istemci tarafından sağlanan `seed_index: u16`'yı havuz PDA seed'lerine katarak bu kısıtlamayı kaldırır, **aynı çift ve ücret seviyesi için birden fazla havuza** izin verir — her biri kendi adresinde. Keyfi bir havuz adresi ayrıcalıklı bir yetenek olduğundan, ödeyici bunu yetkilendiren bir `Permission` PDA'sı tutmalıdır.

Havuz hakkında diğer her şey `CreateCustomizablePool` ile aynıdır: aynı `CreateCustomizableParams`'ı alır ve tek taraflı ücret ve dinamik ücret katılımını destekler.

**Argümanlar**

```rust
customizable_params: CreateCustomizableParams   // CreateCustomizablePool ile aynı yapı
seed_index:          u16                          // sıfır olmayan olmalıdır; havuz PDA seed'lerine katlanır
```

**Hesaplar (kısaltılmış)** — `CreateCustomizablePool` ile aynı artı, başında:

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Kirayı öder. Aşağıdaki `permission` PDA'sının yetkilisi olmalıdır. |
| 2 | `pool_creator` |   |   | `pool_state.owner` olarak kaydedilir. `payer`'dan farklı olabilir. |
| 3 | `permission` |   |   | PDA `["permission", payer]`. Anchor, var olmadığı veya program tarafından sahip olunan olmadığı takdirde çağrıyı reddeder. |
| … | (`amm_config`, `pool_state`, mint'ler, kasalar, `observation_state`, `tick_array_bitmap`, token/sistem programları) | | | `CreateCustomizablePool`'da olduğu gibi. |

`pool_state` PDA'sı `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`'den türetilir.

**Ön koşullar**

- `seed_index != 0`. `0` olan `seed_index` eski havuzlar için ayrılmıştır ve burada reddedilir; `[0, 0]` seed bileşeni, eski havuz adresinin klasik dört seed formuna çökmesini sağlayan şeydir.
- `payer` için `permission` PDA'sı var olur (admin tarafından `CreatePermissionPda` aracılığıyla oluşturulur).
- `CreatePool` ile aynı mint / izin listesi kuralları.

**Son koşullar**

- Yeni `pool_state` `seed_index`-türetilmiş adresinde var olur, `pool_state.seed_index = seed_index` ile.
- Diğer tüm son durum `CreateCustomizablePool` ile eşleşir (ücret modu, isteğe bağlı dinamik ücret).

<Note>
  Bu talimat genel havuz oluşturma erişimini **genişletmez** — izinsiz oluşturma `CreatePool` / `CreateCustomizablePool` aracılığıyla devam eder, bunlar çift başına bir havuz kalır. `CreatePermissionedPool` beyaz listeye alınmış bir operatörün aynı çift için birden fazla havuza ihtiyaç duyduğu (örn. farklı başlangıç fiyatları veya başlatma kohortları) ve admin tarafından verilen `Permission` PDA'sı tuttuğu belirli durum için vardır.
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Mevcut bir havuz içinde yeni bir pozisyon oluşturun.

**Argümanlar**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // istenen L (veya aşağıdaki tutarları kullanmak için 0)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // NFT meta verilerini yaz (Metaplex)
base_flag: Option<bool>       // true = amount0'a sığdır; false = amount1'e sığdır
```

**Hesaplar (kısaltılmış)**

| # | Ad | W | S |
|---|------|---|---|
| 1 | `payer` | W | S |
| 2 | `position_nft_owner` |   |   |
| 3 | `position_nft_mint` | W | S (keypair) |
| 4 | `position_nft_account` | W |   | NFT için sahibinin ATA'sı. |
| 5 | `metadata_account` | W |   | Metaplex (isteğe bağlı, `with_metadata` ise). |
| 6 | `pool_state` | W |   |
| 7 | `protocol_position` |   |   |   |
| 8 | `tick_array_lower` | W |   | Başlatılmamışsa oluşturulur. |
| 9 | `tick_array_upper` | W |   | Aynı. |
| 10 | `personal_position` | W |   | Burada oluşturulur. |
| 11 | `token_account_0`, `token_account_1` | W |   | Kullanıcı kaynak ATA'ları. |
| 12 | `token_vault_0`, `token_vault_1` | W |   | |
| 13 | `rent`, `system_program`, `token_program` |   |   | |
| 14 | `associated_token_program` |   |   | |
| 15 | `metadata_program` |   |   | İsteğe bağlı. |
| 16 | `token_program_2022` |   |   | V2. |
| 17 | `vault_0_mint`, `vault_1_mint` |   |   | V2. |
| 18 | `tick_array_bitmap_extension` | W |   | V2 (dokunulursa). |

**Matematik** — [`products/clmm/math`](/tr/products/clmm/math) bölümüne bakın. `base_flag` verildiğinde, program gerçek `L` ve tüketilen gerçek token tutarlarına `liquidity` veya `(amount_0_max, amount_1_max)`'ı çözer.

**Ön koşullar**

- `tick_lower < tick_upper`, her ikisi de `pool.tick_spacing`'in katları, `[MIN_TICK, MAX_TICK]` içinde.
- Gerekli tick dizileri geçilir ve başlatılır (veya işlemde `InitTickArray` CPI aracılığıyla burada oluşturulur).
- Kullanıcı kaynak ATA'larında en az `amount_0_max` ve `amount_1_max` vardır.

**Son koşullar**

- `personal_position` var olur, `liquidity` ayarlanır, `fee_growth_inside_last` anlık görüntüsü alınır.
- Tick-array girdileri `tick_lower` ve `tick_upper`'da güncellenir (`liquidity_gross += L`, `liquidity_net ± L`, ücret büyümesi anlık görüntüleri korunur).
- `pool_state.liquidity += L` pozisyon aralıkta ise (`tick_lower ≤ tick_current < tick_upper`).

**Yaygın hatalar** — `InvalidTickIndex`, `NotApproved`, `ZeroAmountSpecified`, `TransactionTooLarge` (çok fazla tick dizisi ise).

## `IncreaseLiquidityV2`

Zaten açık olan bir pozisyona likidite ekleyin.

**Argümanlar**

```
liquidity: u128
amount_0_max: u64
amount_1_max: u64
base_flag: Option<bool>
```

**Hesaplar** — `OpenPosition` gibi NFT mint'i hariç (pozisyon zaten var olur; NFT, 1 token tutan sahibinin ATA'sı olarak geçilir).

**Etki**

- `amount_0_actual` / `amount_1_actual`'ı kullanıcıdan → kasalara aktarır.
- `personal_position.liquidity` ve `pool_state.liquidity`'yi (aralıkta ise) ve uç tick `liquidity_gross` / `liquidity_net`'i buna göre artırır.
- **Son dokunuştan bu yana ödenen ücretleri ve ödülleri toplar** ve bunları `tokens_fees_owed_{0,1}` / `reward_amount_owed`'a kredi olarak verir. Bunlar yalnızca `DecreaseLiquidity` veya `CollectReward`'da ödenir, artışta değil.

## `DecreaseLiquidityV2`

Bir pozisyondan likiditeyi kaldırın.

**Argümanlar**

```
liquidity: u128
amount_0_min: u64
amount_1_min: u64
```

**Hesaplar** — `IncreaseLiquidity` ile aynı şekil.

**Etki**

- Kaldırılan `L` için geçerli `sqrt_price_x64` verildiğinde `(amount_0, amount_1)`'i hesaplar.
- Son dokunuştan bu yana tahakkuk eden ücretleri/ödülleri kapatır, `IncreaseLiquidity` ile aynı.
- `amount_0 + fees_owed_0` ve `amount_1 + fees_owed_1`'i kasalardan kullanıcıya aktarır.
- Likidite sayaçlarını azaltır; yeni `personal_position.liquidity == 0` ise, pozisyon `ClosePosition` için uygun hale gelir.

**Kayma** — `amount_0_min` ve `amount_1_min` kullanıcının çıktı tarafında Token-2022 transfer ücretleri net olarak kabul ettiği minimumlar.

## `ClosePosition`

Pozisyon NFT'sini yakın ve `PersonalPositionState`'i kapatın.

**Ön koşullar**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Tüm ödül sayaçları `reward_amount_owed == 0`.

(Yani, her şeyi toplayın ve önce sıfıra azaltın.)

**Etki**

- NFT'yi yakar.
- NFT mint hesabını ve `personal_position` hesabını kapatır, kirayı `payer`'a geri verir.

**Hesaplar (kısaltılmış)**

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2. |
| 11 | `memo_program` |   |   | V2 (bazı Token-2022 yolları için gerekli). |
| 12 | `input_vault_mint`, `output_vault_mint` |   |   | V2. |
| 13 | `tick_array_bitmap_extension` (isteğe bağlı) | W |   | Swap uzantıya girerse. |
| 14+ | `tick_array` (kalan) | W |   | Yürüyüşün beklenen aralığını kapsayacak kadar dizi. |

Arayanlar beklenen swap yürüyüşünü kapsayan sıralanmış tick dizileri listesini geçer; program ihtiyaç duyduğu kadarını kullanır. SDK bu listeyi `PoolUtils.computeAmountOutFormat` veya API'nin quote uç noktası aracılığıyla hesaplar.

**Ön koşullar**

- `pool_state.status` swap'a izin verir.
- `now >= open_time`.
- `sqrt_price_limit_x64` yön için `sqrt_price_x64`'ün doğru tarafında.

**Yaygın hatalar** — `ExceededSlippage`, `SqrtPriceLimitOverflow`, `TickArrayNotFound`, `LiquidityInsufficient`.

**`SwapV2`'nin arayanların bilmesi gereken dahili olarak yaptığı şey** (2025 sonrası sürüm):

1. **Dinamik ücret ek ücreti** — `pool.dynamic_fee_info` sıfır değilse, program son swap'tan bu yana geçilen tick mesafesini kullanarak volatilite biriktiricisini günceller (filtre/bozunma kuralları [`products/clmm/fees`](/tr/products/clmm/fees)'den) ve `AmmConfig.trade_fee_rate`'nin üzerine `dynamic_fee_component` ekler. Toplam ücret %10 ile sınırlandırılır (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Limit-order eşleştirmesi** — fiyat yürüyüşü açık limit emirleri tutan bir tick'i geçtiğinde, program önce o tick'te mevcut limit-order likiditeyi doldurur (FIFO `order_phase` ile), ardından LP likidite eğrisi boyunca ilerler. Doldurulmuş tutarlar `tick.unfilled_ratio_x64` ve `tick.part_filled_orders_remaining`'i daha sonraki kapatma için günceller; emirler kendileri sahibi `SettleLimitOrder` çağırana kadar harcı olmaz.
3. **Tek taraflı ücret yönlendirmesi** — `pool.fee_on = Token0Only` veya `Token1Only` olduğunda, swap adımı yine de aynı giriş-çıkış ticaretini hesaplar; ücret daha sonra yapılandırılan tarafa yönlendirilir. Yapılandırılan ücret tarafının çıkış olduğu yönler için, ücret swap çıkışından düşülür (kullanıcı `out − fee` alır); yapılandırılan tarafın giriş olduğu yönler için, davranış `FromInput` ile eşleşir. `PoolState`'de `is_fee_on_input(zero_for_one)` ve `is_fee_on_token0(zero_for_one)` bölümüne bakın.

`Swap` (V1) `SwapV2` ile aynı dinamik ücret, tek taraflı ücret yönlendirmesi ve limit-order eşleştirmesini uygular; eksik olduğu tek özellik Token-2022 desteğidir — her iki kasa da klasik SPL Token olmalıdır. Token-2022 mint'i olan havuzlar `SwapV2` aracılığıyla swap'lanmalıdır. Toplayıcı ve SDK zaten her CLMM bacağı için V2'yi tercih eder, bu nedenle arayanlar mint türüne göre dallanmak zorunda değildir.

## `OpenLimitOrder`

Belirli bir tick'te satış emri verin. Emir, tick başına FIFO kohortunda oturur ve fiyat geçtikçe doldurulur.

**Argümanlar**

```
nonce_index:    u8       // kullanıcının seçtiği nonce-hesap dizini (cüzdan başına 0..255)
zero_for_one:   bool     // true: token0'ı token1 için sat; false: token1'i token0 için sat
tick_index:     i32      // pool.tick_spacing'in katı olmalıdır
amount:         u64      // giriş-token tutarı
```

**Hesaplar (kısaltılmış)**

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Emir sahibi; kirayı öder. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | `tick_index`'i içeren tick dizisi. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — kullanıcının bu `nonce_index` altında ilk emrinde oluşturulur. |
| 5 | `limit_order` | W |   | PDA. Burada `init`. |
| 6 | `input_token_account` | W |   | Kullanıcının giriş ATA'sı. `frozen` için kontrol edilir. |
| 7 | `output_token_account` | W |   | Kullanıcının **çıkış** ATA'sı. Açılışta borçlandırılmaz — program daha sonra doldurulabilir olduğunu doğrulayabilmesi için gerekli. |
| 8 | `input_vault` | W |   | Havuz giriş kasası. |
| 9 | `output_vault` | W |   | Havuz çıkış kasası. `output_token_account` / `output_vault_mint` kontrolleri için çıkış mint'ini tanımlar. |
| 10 | `input_vault_mint` |   |   | Token-2022 ücret işleme. |
| 11 | `output_vault_mint` |   |   | Çıkış tarafının mint'i (frozen-check eşleştirmesi). |
| 12 | `input_token_program` |   |   | SPL veya Token-2022. |
| 13 | `system_program`, `rent` |   |   | |

<Note>
  **Hesap listesi değişikliği (2026-07 sürümü).** `OpenLimitOrder` artık giriş tarafına ek olarak **çıkış tarafı** hesaplarını da alır — `output_token_account`, `output_vault` ve `output_vault_mint`. Bunlar yalnızca doğrulama için kullanılır: program, sahibinin giriş **veya** çıkış token hesabı dondurulmuşsa emri reddeder. Bu, doldurulmuş çıktının sahibinin çıkış ATA'sına gerçekten kapatılabilmesini garanti eder; bu, izin listesi / varsayılan dondurulmuş Token-2022 mint'leri (örn. izinli tokenler) için önemlidir; burada bir hesap henüz çözülmemiş olabilir. Eski tek taraflı hesap listesine karşı oluşturulan istemciler üç çıkış hesabı eklemelidir.
</Note>

**Ön koşullar**

- Ne `input_token_account` ne de `output_token_account` dondurulmuş değildir (aksi takdirde `NotApproved`).
- `pool_state.status` hem swap (bit 4) hem de limit-order (bit 5) işlemlerine izin verir (aksi takdirde `NotApproved`).
- `tick_index % pool.tick_spacing == 0` ve `[MIN_TICK, MAX_TICK]` içinde.
- `tick_index` seçilen yön için **`pool.tick_current`'ın doğru tarafında** (token0 satmak → tick mevcut üzerinde olmalıdır, ve tersi). Zaten geçilmiş bir tick'te satmak hemen eşleştirilir ve reddedilir.

**Son koşullar**

- `limit_order` var olur, açılış zamanında `tick.order_phase` ve `tick.unfilled_ratio_x64`'ü anlık görüntüsü alır.
- `tick.orders_amount += amount` (mevcut kohortda).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` yayınlanır.

**Yaygın hatalar** — `NotApproved` (giriş veya çıkış token hesabı dondurulmuş, veya havuzun swap / limit-order devre dışı), `InvalidLimitOrderAmount` (sıfır veya havuzun minimumunun altında), `InvalidTickIndex` (`[MIN_TICK, MAX_TICK]` dışında, veya seçilen yön için `tick_current`'ın yanlış tarafında), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `IncreaseLimitOrder`

Mevcut açık emre ekleyin. Yalnızca emrin `owner`'ı tarafından çağrılabilir.

**Argümanlar**

```
amount: u64    // ek giriş-token tutarı
```

**Hesaplar** — `OpenLimitOrder` gibi nonce hesabı hariç; `limit_order` PDA'sı doğrudan geçilir.

**Ön koşullar**

- `limit_order.owner == signer`.
- Emir hala aynı kohortda (`tick.order_phase == limit_order.order_phase`). Kohort zaten doldurulmaya başlamışsa, emir kısmen kapatılmıştır — çağıran önce `DecreaseLimitOrder` veya `SettleLimitOrder` çağırmalıdır.

**Etki**

- `amount`'ı sahibi ATA'sından `input_vault`'a aktarır.
- `limit_order.total_amount += amount`; `tick.orders_amount += amount`.

## `DecreaseLimitOrder`

Açık emri azaltın veya tamamen iptal edin. Doldurulmayan kalanı sahibine geri ödeyin, artı geçmiş kısmi doldurmalar tarafından zaten kapatılan çıktı.

**Argümanlar**

```
amount:     u64    // çekilecek giriş-token tutarı (max = doldurulmayan kalan)
amount_min: u64    // giriş tarafı çekimi üzerinde kayma tabanı
```

**Hesaplar** — hem giriş hem de çıkış token tarafları:

| # | Ad | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `pool_state` | W |   |
| 3 | `tick_array` | W |   |
| 4 | `limit_order` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_vault_mint`, `output_vault_mint` |   |   |
| 10 | `token_program`, `token_program_2022` |   |   |

**Etki**

- Emrin doldurulmuş tutarını açılıştan bu yana kohortun `unfilled_ratio_x64`'ünden yeniden hesaplar.
- Doldurulmuş çıktıyı `output_token_account`'a gönderir.
- `amount` doldurulmayan girişi `input_token_account`'a geri gönderir.
- `limit_order`'ı buna göre günceller. Yeni doldurulmayan kalan sıfırsa, program hesabı kapatır ve kirayı `owner`'a geri verir.

## `SettleLimitOrder`

Doldurulmuş çıktı tokenlerini sahibine gönderin; emrin doldurulmayan kalanını değiştirmeden. Uzun süreli kısmi doldurmalar için `auto_withdraw` tutucuları damla ödeme yapmak istediğinde kullanışlı.

**Çağıran** — emrin `owner`'ı veya program'ın `limit_order_admin`'i (otomatik tutucu döngüsü çalıştıran çevrimdışı operasyonel sıcak cüzdan). Tutucu başka yetkilendirmeye sahip değildir — doldurulmuş çıktıyı emrin `owner` ATA'sına göndermek dışında kullanıcı fonlarını hareket ettiremez.

**Hesaplar**

| # | Ad | W | S |
|---|------|---|---|
| 1 | `signer` |   | S | sahibi *veya* `limit_order_admin` |
| 2 | `pool_state` |   |   | |
| 3 | `tick_array` |   |   | |
| 4 | `limit_order` | W |   | |
| 5 | `output_token_account` | W |   | Sahibinin çıkış ATA'sı. |
| 6 | `output_vault` | W |   | Havuz çıkış kasası. |
| 7 | `output_vault_mint` |   |   | |
| 8 | `output_token_program` |   |   | |

**Etki**

- `(limit_order.unfilled_ratio_x64, tick.unfilled_ratio_x64)` kullanarak kümülatif çıktı borçlandırılan tutarı hesaplar.
- Deltayı `output_token_account`'a aktarır.
- `limit_order.settled_output`'u günceller.
- Emri kapatmaz; kalan giriş karşısında hala açıktır.

## `CloseLimitOrder`

Tamamen tüketilmiş emir hesabını kapatın. Kira kim imzalarsa imzasın her zaman `limit_order.owner`'a döner.

**Çağıran** — `owner` veya `limit_order_admin`.

**Ön koşullar**

- Emrin sıfır doldurulmayan kalanı vardır (ya `amount == total_amount` doldurulmuş ve kapatılmış, ya da sahibi daha önce emri sıfıra azalttı ve kapatmayı unuttu).

**Etki**

- `limit_order`'ı kapatır; kira `limit_order.owner`'a gönderilir.

## `UpdateDynamicFeeConfig` (admin)

Mevcut `DynamicFeeConfig`'i değiştirin. Oluşturma zamanında yapılandırmayı zaten anlık görüntüsü alan havuzlar **retroaktif olarak güncellenmez**; yalnızca bu yapılandırmaya başvuran yeni oluşturulan havuzlar yeni değerleri alacaktır.

**Argümanlar** — `CreateDynamicFeeConfig` ile aynı beş kalibrasyon alanı (`filter_period`, `decay_period`, `reduction_factor`, `dynamic_fee_control`, `max_volatility_accumulator`); `index` oluşturma zamanında sabitlenir ve burada yeniden geçilmez.
