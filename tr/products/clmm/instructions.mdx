| Limit emri | `CloseLimitOrder` | Tamamen tüketilmiş emir hesabını kapatın. Kira her zaman emrin `owner`'ına döner. Sahibi veya bekçi tarafından çağrılabilir. |
| Ücretler | `CollectProtocolFee` | Protokol ücretlerinin admin tarafından yapılan taraması. |
| Ücretler | `CollectFundFee` | Fon ücretlerinin admin tarafından yapılan taraması. |

| Admin | `CollectExcessLamports` | Bir havuzun `PoolState` ve kasalarından kira muafiyeti minimumunun üzerindeki lamportları, artı geçirilen CLMM'ye ait herhangi bir PDA'yı tarayın. `admin` veya özel lamport toplama cüzdanı. 2026-09'da eklendi. |

<Note>
  **Tick dizisi başlatma talimatı yoktur ve buna gerek yoktur.** Tick dizisi *içinde* oluşturulur
  `OpenPosition*` / `IncreaseLiquidity*` tarafından `TickArrayState::get_or_create_tick_array` aracılığıyla, `payer` tarafından ödenir. (Muhtemelen hala başlatılmamış, sistem tarafından sahip olunan) tick dizisi PDA'sını
  `tick_array_lower` / `tick_array_upper` olarak geçirin ve program eksikse onu tahsis eder.
  `OpenLimitOrder` tek `tick_array`'i için aynı şeyi yapar.
</Note>

Çoğu admin tarafından yapılan talimat (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) program'ın sabit kodlanmış `admin` genel anahtarı tarafından kapılanır. `CreateSupportMintAssociated` / `CloseSupportMintAssociated` `admin` genel anahtarını **veya** özel bir destek-mint sahibi anahtarını kabul eder; `CollectExcessLamports` `admin` genel anahtarını **veya** özel bir lamport toplama cüzdanını kabul eder. Ödül akışı admin talimatları (`TransferRewardOwner`, `CollectRemainingRewards`) program admini tarafından değil, ödül fon sağlayıcısı tarafından kapılanır.

V2 soneki "Token-2022'yi kasalar / NFT'de destekler, bitmap-uzantı slotu gerektirir" anlamına gelir. SDK yeni havuzlar için varsayılan olarak V2'yi seçer.

## `CreatePool`

**Argümanlar**

```
sqrt_price_x64: u128           // başlangıç fiyatı
open_time:      u64            // bu saatten önce swaplar reddedilir
```

**Hesaplar (kısaltılmış)**

| # | Ad | W | S | Notlar |
|---|-----|---|---|--------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Seçilen ücret katmanı. |
| 3 | `pool_state` | W |   | Burada `init`. |
| 4 | `token_mint_0` |   |   | Sıralanmış. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | Burada `init`, havuz yetkisi PDA'sı tarafından sahip olunan. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | Burada `init`. |
| 9 | `tick_array_bitmap` | W |   | `TickArrayBitmapExtension` PDA'sı; burada `init`. |
| 10 | `token_program_0` |   |   | `token_mint_0`'ı sahip olan program — SPL Token **veya** Token-2022. |
| 11 | `token_program_1` |   |   | `token_mint_1`'i sahip olan program. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Slotlar 10 ve 11 **mint başına**, "SPL Token sonra Token-2022" değildir. Her biri eşleşen mint'teki
  `mint::token_program` tarafından kısıtlanır, bu nedenle `token_mint_0`'ı Token-2022 ve
  `token_mint_1`'i klasik SPL olan bir havuz için slot 10'a Token-2022 ve slot 11'e SPL Token geçirmelisiniz.
  `CreateCustomizablePool` ve `CreateCustomizablePoolV2` aynı iki slotu kullanır.
</Warning>

**Ön koşullar**

- `token_mint_0 < token_mint_1` bayt sırasına göre.
- `amm_config.disable_create_pool == false`.
- Mintler Token-2022 uzantı izin listesi tarafından reddedilmez.

**Son koşullar**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (henüz pozisyon yok).
- `pool_state.fee_on = FromInput` (eski varsayılan).
- `pool_state.dynamic_fee_info` sıfırlanır (dinamik ücret devre dışı).

## `CreateCustomizablePool`

Yeni havuzlar için önerilir. `CreatePool` ile aynı etki artı havuz başına ücret toplama modu ve isteğe bağlı dinamik ücret katılımı.

**Argümanlar**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Hesaplar** — `CreatePool`'un tam olarak 13 beyan edilen hesabı. `dynamic_fee_config` beyan edilen bir hesap **değildir**.

<Warning>
  `enable_dynamic_fee = true` olduğunda, anlık görüntü alınacak `DynamicFeeConfig` **son** `remaining_account` olarak sağlanmalıdır — işleyici `ctx.remaining_accounts.last()` okur. Herhangi bir
  `SupportMintAssociated` bypass PDA'sı bu nedenle *önce* gelmelidir, aksi takdirde program yanlış hesabın anlık görüntüsünü alır ve deserialization başarısız olur. Bayrak ayarlanmışken onu atlama `AccountLack` ile başarısız olur.
</Warning>

**Ön koşullar** — `CreatePool` ile aynı. `enable_dynamic_fee = false` ise, `remaining_account` gerekli değildir ve geçirilen herhangi biri yalnızca destek-mint kayıtları için taranır.

**Son koşullar**

- `pool_state.fee_on` seçilen `CollectFeeOn` varyantına ayarlanır.
- Dinamik ücret etkinleştirilirse: `pool_state.dynamic_fee_info` sağlanan `DynamicFeeConfig`'den başlatılır (beş kalibrasyon parametresi kopyalanır; durum alanları sıfırlanır).
- Aksi takdirde: `pool_state.dynamic_fee_info` sıfırlanır (= bu havuz için dinamik ücret sonsuza kadar etkin değil).

`fee_on` ve dinamik ücret etkinleştirme biti **yalnızca** havuz oluşturma sırasında ayarlanır. Yerinde yükseltme yoktur — eski `CreatePool` aracılığıyla oluşturulan havuzlar geriye dönük olarak dinamik ücret veya tek taraflı ücret kazanamaz. Yeni dağıtımlar varsayılan olarak bu talimata geçmelidir.

## `CreateCustomizablePoolV2`

Hem `CreatePool` hem de `CreateCustomizablePool`, pool PDA'sını `["pool", amm_config, token_mint_0, token_mint_1]` adresinden türetir; bu nedenle her `(config, mint0, mint1)` üçlüsü için tam olarak **bir** kanonik pool adresi vardır — aynı seed'lerle ikinci bir `init` başarısız olur. `CreateCustomizablePoolV2` bu kısıtlamayı kaldırarak, istemci tarafından sağlanan `seed_index: u16` değerini pool PDA seed'lerine katarak **aynı çift ve ücret katmanı için birden fazla pool** oluşturmaya izin verir — her biri kendi adresinde. Herkes bunu çağırabilir.

Pool hakkındaki diğer her şey `CreateCustomizablePool` ile aynıdır: aynı `CreateCustomizableParams` parametrelerini alır ve tek taraflı ücret ile dinamik ücret seçeneğini destekler.

<Note>
  [2026-10-22 yükseltmesine](/tr/reference/changelog/2026-10-22-clmm-customizable-pool-v2) kadar bu talimat `CreatePermissionedPool` olarak adlandırılıyordu ve ödeyicinin yönetici tarafından verilen bir `Permission` PDA'sına sahip olmasını gerektiriyordu. Yükseltme adını değiştirdi, `permission` hesabını kaldırdı ve izin mekanizmasını sildi. Ayırıcı adla birlikte değişti, bu nedenle `CreatePermissionedPool` karşısında oluşturulan istemcilerin yeniden oluşturulması gerekir.
</Note>

**Argümanlar**

```rust
customizable_params: CreateCustomizableParams   // CreateCustomizablePool ile aynı struct
seed_index:          u16                          // sıfır olmayan olmalı; pool PDA seed'lerine katılır
```

**Hesaplar**

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Her yeni hesap için kirayı öder. Herhangi bir cüzdan. |
| 2 | `pool_creator` |   |   | `pool_state.owner` olarak kaydedilir. `payer` ile farklı olabilir. İmzalayan değil ve kontrol edilmez. |
| 3 | `amm_config` |   |   | Pool'un bağlandığı ücret katmanı. |
| 4 | `pool_state` | W |   | `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]` adresinde `init`. |
| 5 | `token_mint_0` |   |   | `token_mint_1` öncesinde sıralanmalı. |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`. |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`. |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`. |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`. |
| 11 | `token_program_0` |   |   | `token_mint_0`'ı sahiplenen program. |
| 12 | `token_program_1` |   |   | `token_mint_1`'i sahiplenen program. |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts`: Token-2022 mint'i gerektiğinde destek-mint kayıt defteri PDA'ları ve `enable_dynamic_fee = true` olduğunda `DynamicFeeConfig` **son** — `CreateCustomizablePool`'da olduğu gibi.

**Ön Koşullar**

- `seed_index != 0`. `seed_index` değeri `0` eski pool'lar için ayrılmıştır ve burada reddedilir; `[0, 0]` seed bileşeni, eski bir pool adresinin klasik dört seed formuna çökmesini sağlayan şeydir.
- Türetilen adresinde henüz pool yok.
- `CreatePool` ile aynı mint / izin listesi kuralları.

**Son Koşullar**

- Yeni bir `pool_state`, `seed_index`-türetilmiş adresinde `pool_state.seed_index = seed_index` ile var.
- Diğer tüm son durumlar `CreateCustomizablePool` ile eşleşir (ücret modu, isteğe bağlı dinamik ücret).

<Warning>
  `pool_creator` kontrol edilmediğinden, herhangi bir ödeyici `pool_state.owner`'a herhangi bir adres yazabilir. Bu adres pool'da `InitializeReward`'ı çağırabilir, ancak bu pool'u kimin oluşturduğunun kanıtı değildir. Entegratörler V2 pool'larını `owner` değerine göre etiketlemeli veya sıralamaktan kaçınmalıdır.
</Warning>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Mevcut bir pool içinde yeni bir pozisyon oluşturun.

**Argümanlar**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // istenen L (veya aşağıdaki tutarları kullanmak için 0)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // NFT meta verilerini yaz (Metaplex)
base_flag: Option<bool>       // true = amount0'a uydur; false = amount1'e uydur
```

**Hesaplar** — iki varyant *farklı* hesap listelerine sahiptir. `OpenPositionV2` 22 tane bildirir; `OpenPositionWithToken22Nft` 20 tane bildirir.

`OpenPositionV2`, sırasıyla:

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `payer` | W | S | |
| 2 | `position_nft_owner` |   |   | |
| 3 | `position_nft_mint` | W | S | Yeni keypair. |
| 4 | `position_nft_account` | W |   | NFT için sahibinin ATA'sı. |
| 5 | `metadata_account` | W |   | Metaplex meta veri PDA'sı. `with_metadata = false` olduğunda bile **koşulsuz olarak** bildirilir. |
| 6 | `pool_state` | W |   | |
| 7 | `protocol_position` |   |   | Kalıntı; salt okunur `UncheckedAccount`. |
| 8 | `tick_array_lower` | W |   | Başlatılmamışsa burada oluşturulur. |
| 9 | `tick_array_upper` | W |   | Aynı. |
| 10 | `personal_position` | W |   | Burada oluşturulur. |
| 11 | `token_account_0` | W |   | Kullanıcı kaynak ATA'sı. |
| 12 | `token_account_1` | W |   | |
| 13 | `token_vault_0` | W |   | |
| 14 | `token_vault_1` | W |   | |
| 15 | `rent` |   |   | |
| 16 | `system_program` |   |   | |
| 17 | `token_program` |   |   | |
| 18 | `associated_token_program` |   |   | |
| 19 | `metadata_program` |   |   | Metaplex Token Metadata. |
| 20 | `token_program_2022` |   |   | |
| 21 | `vault_0_mint` |   |   | |
| 22 | `vault_1_mint` |   |   | |

`OpenPositionWithToken22Nft`, `metadata_account` (5) ve `metadata_program` (19) **kaldırılmış** aynı listedir — bunun yerine pozisyonun meta verilerini NFT mint'indeki Token-2022 meta veri uzantısı aracılığıyla yazar — 20 hesap verir. `position_nft_mint`'i basit bir `Signer` ve `position_nft_account`'ı bir `UncheckedAccount`'tır.

<Warning>
  **`tick_array_bitmap_extension` her iki varyant üzerinde de bildirilmiş bir hesap değildir.** Pozisyonun aralığı pool'un satır içi `tick_array_bitmap` (±512 tick dizileri) dışına düştüğünde, `TickArrayBitmapExtension` PDA'sını `["pool_tick_array_bitmap_extension", pool_state]` seed'lerinde `remaining_accounts[0]` olarak ekleyin.
</Warning>

**Matematik** — bkz. [`products/clmm/math`](/tr/products/clmm/math). `base_flag` verildiğinde, program `liquidity` veya `(amount_0_max, amount_1_max)` değerlerini gerçek `L` ve tüketilen gerçek token tutarlarına çözer.

**Ön Koşullar**

- `tick_lower < tick_upper`, her ikisi de `pool.tick_spacing`'in katları, `[MIN_TICK, MAX_TICK]` içinde.
- İki tick-array PDA'sı geçirilir. Bunlar **zaten var olmak zorunda değildir** — `get_or_create_tick_array` eksik olanı bu talimat içinde `payer`'ın masrafına ayırır. Ayrı bir init-tick-array talimatı yoktur.
- Kullanıcı kaynak ATA'larında en az `amount_0_max` ve `amount_1_max` tutarına sahiptir.

**Son Koşullar**

- `personal_position` var, `liquidity` ayarlanmış, `fee_growth_inside_last` anlık görüntüsü alınmış.
- `tick_lower` ve `tick_upper` adreslerindeki tick-array girdileri güncellendi (`liquidity_gross += L`, `liquidity_net ± L`, ücret-büyüme anlık görüntüleri korunmuş).
- `pool_state.liquidity += L` eğer pozisyon aralık içindeyse (`tick_lower ≤ tick_current < tick_upper`).
- Pozisyon NFT mint'i `pool_state`'i dondurma yetkilisi olarak kaydeder. Mint yetkilisi tek NFT basıldıktan sonra kaldırılır. Dondurma yetkilisini kaydetmek NFT token hesabının durumunu değiştirmez.
- NFT token hesabı, talimat `OpenPositionV2` veya `OpenPositionWithToken22Nft` **ve** vault mint'lerinden herhangi birinin dondurma yetkilisi CLMM'nin kısıtlı-yayıncı listesiyle eşleşmediği sürece dondurulmamış kalır. Yalnızca bu eşleşen V2 yolu hesabı dondurur. `OpenPosition` V1 dondurmaz.

**Yaygın hatalar** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (bir uç nokta `tick_spacing`'in katı değil), `InvalidTickIndex` (`[MIN_TICK, MAX_TICK]` dışında), `MissingTickArrayBitmapExtensionAccount` (aralık satır içi bitmap dışında ve uzantı eklenmedi), `NotApproved` (`pool_state.status` açmayı engeller), `ZeroAmountSpecified`.

<Note>
  Pozisyon dondurma, bildirilmiş talimat hesapları veya argümanları eklemez. İstemciler bu pozisyonları mevcut V2 düzenleriyle açabilir. Davranış zincir üzerinde `vault_0_mint` ve `vault_1_mint` adresinden seçilir.
</Note>

Çağıranlar, beklenen swap yürüyüşünü kapsayan sıralanmış bir tick dizi listesi geçerler; program ihtiyaç duyduğu kadarını kullanır. SDK bu listeyi `PoolUtils.computeAmountOutFormat` veya API'nin quote uç noktası aracılığıyla hesaplar.

**Ön koşullar**

- `pool_state.status` swap'a izin verir.
- `now >= open_time`.
- `sqrt_price_limit_x64` yön için `sqrt_price_x64`'ün doğru tarafında.

**Yaygın hatalar** — `TooLittleOutputReceived` (tam giriş slippage), `TooMuchInputPaid` (tam çıkış slippage), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (swap biti `pool_state.status`'ta ayarlanmış). CLMM'nin `ExceededSlippage` varyantı yoktur — bu ad CPMM'nindir — ve `TickArrayNotFound` yoktur.

**`SwapV2`'nin çağıranların bilmesi gereken dahili işlemleri** (2025 sonrası sürüm):

1. **Dinamik ücret ek ücreti** — `pool.dynamic_fee_info` sıfır değilse, program volatilite biriktiricisini son swap'tan bu yana geçilen tick mesafesi kullanarak günceller (ücret [`products/clmm/fees`](/tr/products/clmm/fees) kurallarından filtre/bozunma ile) ve `AmmConfig.trade_fee_rate`'in üzerine bir `dynamic_fee_component` ekler. Toplam ücret %10 ile sınırlandırılır (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Limit emri eşleştirmesi** — fiyat yürüyüşü açık limit emirleri tutan bir tick'i geçtiğinde, program önce o tick'te mevcut limit emri likiditeyi doldurur (FIFO by `order_phase`), ardından LP likidite eğrisi boyunca devam eder. Doldurulmuş miktarlar `tick.unfilled_ratio_x64` ve `tick.part_filled_orders_remaining`'i sonraki kapatma için günceller; emirler kendileri sahibi `SettleLimitOrder`'ı çağırana kadar harcı olmaz.
3. **Tek taraflı ücret yönlendirmesi** — `pool.fee_on = Token0Only` veya `Token1Only` olduğunda, swap adımı yine de aynı giriş-çıkış ticaretini hesaplar; ücret daha sonra yapılandırılmış tarafa yönlendirilir. Yapılandırılmış ücret tarafının çıkış olduğu yönler için, ücret swap çıkışından düşülür (kullanıcı `out − fee` alır); giriş olduğu yönler için davranış `FromInput` ile eşleşir. `PoolState`'deki `is_fee_on_input(zero_for_one)` ve `is_fee_on_token0(zero_for_one)`'a bakın.

`Swap` (V1) `SwapV2` ile aynı dinamik ücreti, tek taraflı ücret yönlendirmesini ve limit emri eşleştirmesini uygular; eksik olduğu tek özellik Token-2022 desteğidir — her iki vault da klasik SPL Token olmalı. Herhangi bir Token-2022 mint'i olan pool'lar `SwapV2` aracılığıyla swap edilmelidir. Toplayıcı ve SDK zaten her CLMM bacağı için V2'yi tercih eder, bu nedenle çağıranların mint türüne göre dallanması gerekmez.

| 1 | `payer` | W | S | Emir sahibi; kirayı öder. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | `tick_index`'i içeren tick dizisi. |

**Kalan hesaplar** — `[0]` `tick_array_bitmap_extension`, yalnızca başlangıç indeksi pool'un satır içi bitmap'inin dışına düşen bir tick dizisini başlatırken gerekli. Aksi takdirde hiçbir şey geçmeyin.

<Warning>
  **`rent` hesabı yoktur**: yapı `system_program`'da biter, 13 bildirilen hesap. Konumda 14'te dolaşan bir `rent`, tam olarak isteğe bağlı bitmap uzantısının okunduğu yere iner, bu nedenle emir satır içi bitmap'inin dışında bir tick dizisinin ilk kez oluşturulması gerekene kadar çalışıyor gibi görünür — ve sonra başarısız olur.
</Warning>

<Note>
  **Hesap listesi değişikliği (2026-07 sürümü).** `OpenLimitOrder` artık giriş tarafına ek olarak **çıkış tarafı** hesaplarını da alır — `output_token_account`, `output_vault` ve `output_vault_mint`. Bunlar yalnızca doğrulama için kullanılır: program sahibinin giriş **veya** çıkış token hesabı donmuşsa emri reddeder. Bu, doldurmanın gerçekten sahibinin çıkış ATA'sına kapatılabileceğini garanti eder; bu, izin listesi / varsayılan donmuş Token-2022 mint'leri (örn. izinli tokenlar) için önemlidir; burada bir hesap henüz çözülmemiş olabilir. Eski tek taraflı hesap listesine karşı oluşturulan istemciler üç çıkış hesabını eklemelidir.
</Note>

**Ön koşullar**

- Ne `input_token_account` ne de `output_token_account` donmuş değil (aksi takdirde `NotApproved`).
- `pool_state.status` hem swap (bit 4) hem de limit-order (bit 5) işlemlerine izin verir (aksi takdirde `NotApproved`).
- `tick_index % pool.tick_spacing == 0` ve `[MIN_TICK, MAX_TICK]` içinde.
- `tick_index` seçilen yön için **`pool.tick_current`'ın sağ tarafında** (token0 satışı → tick mevcut üzerinde olmalı, ve tersi). Zaten geçilmiş bir tick'te satış hemen eşleştirilir ve reddedilir.

**Sonrası koşullar**

- `limit_order` var, açılış zamanında `tick.order_phase` ve `tick.unfilled_ratio_x64`'ü anlık görüntüler.
- `tick.orders_amount += amount` (mevcut kohortda).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` yayınlanır.

**Yaygın hatalar** — `NotApproved` (giriş veya çıkış token hesabı donmuş, veya pool swap / limit-order devre dışı), `ZeroAmountSpecified` (giriş tarafı transfer ücreti sonrası `amount == 0`), `InvalidLimitOrderAmount` (miktar o tick'te 1 temel birim altında çıkış üretir veya `u64` taşar), `InvalidTickIndex` (`[MIN_TICK, MAX_TICK]` dışında, veya seçilen yön için `tick_current`'ın yanlış tarafında), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

Mevcut bir `DynamicFeeConfig`'i değiştirin. Oluşturma zamanında yapılandırmayı zaten anlık görüntüsü alan havuzlar **geriye dönük olarak** güncellenmez; yalnızca bu yapılandırmaya başvuran yeni oluşturulan havuzlar yeni değerleri alacaktır.

**Argümanlar** — `CreateDynamicFeeConfig` ile aynı beş kalibrasyon alanı (`filter_period`, `decay_period`, `reduction_factor`, `dynamic_fee_control`, `max_volatility_accumulator`); `index` oluşturma sırasında sabitlenir ve burada yeniden geçirilmez.

## `CollectExcessLamports`

CLMM'nin kontrol ettiği hesaplardaki kira-muaf minimumun üzerindeki lamportların yönetici taraması. [SIMD-0437 kira azaltması](/tr/solana-fundamentals/rent-and-reclaimable-rent) her adımdan önce oluşturulan hesaplarda bıraktığı aşırı finansmanı geri almak için 2026-09 yükseltmesinde eklendi.

Yalnızca fazlalık hareket eder. Token bakiyeleri, hesap verileri, sahipleri, havuz durumu ve fiyat eğrisi dokunulmaz. Zaten minimumda olan bir hesap olduğu gibi bırakılır, bu nedenle her dağıtım adımından sonra talimat güvenle yeniden çalıştırılabilir.

**Argümanlar**: hiçbiri.

**Hesaplar**

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Her taranmış lamportı alır. CLMM program yöneticisi veya özel lamport-toplama cüzdanı olmalıdır (bkz. [`reference/program-addresses`](/tr/reference/program-addresses#excess-lamports-collection-wallets)). Başka herhangi bir imzalayan `NotApproved` ile başarısız olur. |
| 2 | `pool_state` | W |   | Taranmakta olan havuz. PDA tohumları token-program CPI'larını imzalar ve hesap her zaman kendisi taranır. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Her iki program da gereklidir; talimat kaynak hesap başına birini seçer. |
| 5.. | `remaining_accounts` | W |   | `M` kaynak hesabı, herhangi bir sayı, herhangi bir sıra. |

**Kapsam: çağrı başına bir havuz.** CLMM'nin program genelinde kasa yetkisi yoktur. Her havuzun kasaları kendi `PoolState`'i tarafından sahiplenilir. Bu nedenle her token-program kaynağının slot 2'de `pool_state`'i yetkili olarak olması gerekir: `token_vault_0`, `token_vault_1` veya o havuzun ödül kasalarından biri. Başka bir havuzun kasasını veya bir kullanıcının token hesabını geçerseniz, token programının sahip kontrolü başarısız olur ve tüm talimat geri döner. Atlanmaz. Pozisyon NFT mintleri taranmaz, çünkü mint yetkisi pozisyon açıldığında iptal edilir.

**Her kaynak hesabın nasıl işlendiği**

Program `remaining_accounts` üzerinde iki geçiş yapar: önce her token-program CPI'sı, sonra doğrudan borçlar. İkisini araya sokmak çalışma zamanının `UnbalancedInstruction` hatasıyla iptal olur, bu nedenle sıra programda sabitlenir ve listeyi kendiniz sıralamanız gerekmez.

| Geçiş | Kaynak hesap sahibi | İşleme |
|---|---|---|
| 1 | SPL Token veya Token-2022, yerel olmayan token hesabı | CPI `WithdrawExcessLamports` (token-program ayırıcı `38`), `pool_state` tarafından imzalanmış. |
| 1 | SPL Token veya Token-2022, **yerel** (wSOL) token hesabı | `WithdrawExcessLamports` yerel hesapları reddeder. Program `SyncNative`'i CPI'lar, sarılı `amount`'un ne kadar büyüdüğünü ölçer ve tam o delta için `UnwrapLamports` (ayırıcı `45`) çağırır. Daha sonra sarılı bakiyenin ön-senkronizasyon değerine eşit olmasını gerektirir, aksi takdirde `LamportsCalculateError` (`6052`) ile başarısız olur. SOL tarafı havuz kasası tam likiditeyi tutar. |
| 2 | `pool_state` (slot 2) | Doğrudan `rent.minimum_balance(data_len)` kadar borçlandırılır. |
| 2 | CLMM programı: `AmmConfig`, `ObservationState`, `TickArrayBitmapExtension`, `TickArrayState`, `PersonalPositionState`, `LimitOrderState` ve benzeri | Doğrudan `rent.minimum_balance(data_len)` kadar borçlandırılır. Hesap slot 2'deki havuza ait olmak **zorunda değildir**. |
| — | Başka herhangi bir şey | **Sessizce atlanır.** Hata yok, lamport hareket yok. |

<Warning>
  **Geçiş 2, bir kullanıcının kirasını ödediği hesapları kapsar.** Burada geçirilen bir `PersonalPositionState` veya `LimitOrderState`, diğer herhangi bir CLMM tarafından sahip olunan hesap gibi fazlalığından vazgeçer. Kira-muaf kalır ve verilerini tutar. Daha sonra kapatıldığında, sahip o noktada hesabın tuttuğu her şeyi geri alır; bu, bir tarama sonrasında geçerli kira minimumdur.
</Warning>

İşlem boyutu, bir çağrıya kaç kaynağın sığabileceğinin gerçek sınırıdır. Bu, [`solana-fundamentals/rent-and-reclaimable-rent`](/tr/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction) içinde açıklanan cüzdan tarafı tarama ile aynı kısıtlamadır.

**Yaygın hatalar**:
- `NotApproved` (`6000`): yanlış imzalayan.
- `LamportsCalculateError` (`6052`): wSOL gidiş-dönüş sıfıra net olmadı.
- Bir token-program sahip-uyuşmazlığı hatası: bir token kaynağı `pool_state` tarafından sahip değildir.
- `InsufficientFunds`: bir programa ait hesap kendi kira minimumundan daha az tutar.

**SDK oluşturucu yok.** `@raydium-io/raydium-sdk-v2` bu yönetici yolu için bir oluşturucu göndermez. IDL'den elle kodlayın.

## `InitializeReward`

Bir havuza yeni bir ödül akışı ekleyin. Aynı anda en fazla 3 akış etkin olabilir.

**Argümanlar** — tek bir yapı, `param: InitializeRewardParam`:

```rust
pub struct InitializeRewardParam {
    pub open_time:                u64,
    pub end_time:                 u64,
    pub emissions_per_second_x64: u128,   // Q64.64
}
```

Tel kodlaması üç alanın arka arkaya olmasıdır, bu nedenle elle oluşturulan bir talimat etkilenmez — ancak IDL tarafından yönlendirilen bir istemci üç konumsal argüman yerine bir `param` nesnesi geçmelidir.

**Hesaplar**

| # | Ad | W | S | Notlar |
|---|------|---|---|-------|
| 1 | `reward_funder` | W | S |
| 2 | `funder_token_account` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `operation_state` |   |   | Ödül oluşturmayı kapılayan CLMM işlem durumu PDA'sı. |
| 6 | `reward_token_mint` |   |   |
| 7 | `reward_token_vault` | W |   | Burada `init` edilir. |
| 8 | `reward_token_program` |   |   |
| 9 | `system_program`, `rent` |   |   |

**Ön koşullar**

- Havuzda 3'ten az akış şu anda etkindir.
- Funder, bu talimatın bir parçası olarak `total_emission = emissions_per_second × (end_time − open_time)` değerinde ödül tokenini kasaya yatırır.
- `operation_state` başına beyaz listeye alınmış ödül mint'i.

## `SetRewardParams`

Mevcut bir ödül akışını genişletin, doldurabilir veya emisyon oranını değiştirin. Tipik olarak havuz yaratıcısı veya Raydium multisig tarafından çağrılır. Kısıtlamalar zincir üzerinde yaşar: genellikle `end_time`'ı genişletebilir veya emisyonları artırabilir, geriye dönük olarak küçültemezsiniz. `operation_state`'in sahip listesini kontrol edin.

## `UpdateRewardInfos`

Saf muhasebe — `reward_growth_global_x64`'ü geçerli zamana `emissions_per_second × Δt / liquidity` çarparak kapatır. Likiditeye dokunan her talimat tarafından dahili olarak çağrılır. Dış aktörler (UI'lar, kranklar) bazen bunu tetiklemek istediğinden, bağımsız bir talimat olarak açığa çıkarılır.

## Ödülleri toplama

<Warning>
  **Bağımsız bir ödül toplama talimatı yoktur.** Program `CollectReward` giriş noktasını açığa çıkarmaz ve yayınlanan IDL'nin de hiçbiri yoktur.
</Warning>

Bir pozisyona borçlu olunan ödüller `DecreaseLiquidity` / `DecreaseLiquidityV2` tarafından ödenir. Pozisyonu değiştirmeden toplamak için `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0` ile çağırın. Ödül kasaları ve alıcı hesapları `remaining_accounts`'a etkin ödül başına üçlü gruplar halinde, `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint` sırasında gider.

`CollectRemainingRewards` farklı bir şeydir: ödül *funder*'ının, bir akışın `end_time`'ından sonra, herhangi bir pozisyona tahsis edilmemiş tokenları taramasına izin verir.
