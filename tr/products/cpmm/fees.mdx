## İki bağımsız ücret, dört hedef

CPMM her swap işleminde **iki ayrı oranlı ücret** alır:

1. **İşlem ücreti** — `AmmConfig.trade_fee_rate` oranında alınır ve üç hedefe bölünür:
   - **LP payı** — vault'ta kalır ve `k`'yi büyütür. LP token'larını yakarak örtülü olarak talep edilir.
   - **Protokol payı** — `PoolState.protocol_fees_token*` hesabına tahakkuk eder; `protocol_owner` tarafından `CollectProtocolFee` aracılığıyla toplanır.
   - **Fon payı** — `PoolState.fund_fees_token*` hesabına tahakkuk eder; `fund_owner` tarafından `CollectFundFee` aracılığıyla toplanır.
2. **Yaratıcı ücreti** (isteğe bağlı, havuz başına) — `AmmConfig.creator_fee_rate` oranında işlem ücretinden **bağımsız** olarak alınır ve `PoolState.creator_fees_token*` hesabına tahakkuk eder. Yaratıcı bunu `CollectCreatorFee` aracılığıyla toplayabilir veya herhangi bir ödeyici hedef kısıtlı `CollectCreatorFeePermissionless` yolunu tetikleyebilir. Yalnızca havuz `enable_creator_fee = true` ile oluşturulduğunda etkindir.

Yaratıcı ücreti işlem ücretinin bir dilimi **değildir**. İki oran swap girdisinde ücret alınırken toplanır, ancak her biri kendi hesabında kalır — protokol ve fon payları her zaman yalnızca `trade_fee`'den türetilir, asla `creator_fee`'den değil. `creator_fee_rate = 1000` (0,10%) ve `trade_fee_rate = 2500` (0,25%) olan bir havuz, yaratıcı-ücret-girdisi swap'inde girdinin birleşik %0,35'ini alır; bunun %0,10'unu yaratıcı tutar ve %0,25'i işlem-ücreti hesabına gider.

İşlem-ücreti oranları (`trade_fee_rate`, `protocol_fee_rate`, `fund_fee_rate`) ve `creator_fee_rate` hepsi `AmmConfig` üzerinde bulunur. Havuz başına `enable_creator_fee` bayrağı ve `creator_fee_on` modu (yaratıcı ücretinin hangi tarafından alındığı) `PoolState` üzerinde bulunur. Bkz. [`products/cpmm/accounts`](/tr/products/cpmm/accounts).

## Oranlar ve birimler

Tüm oranlar `u64` türündedir ve `1 / FEE_RATE_DENOMINATOR` biriminde gösterilir; burada `FEE_RATE_DENOMINATOR = 1_000_000`.

- **`trade_fee_rate`** **swap hacminin** bir kesridir. `2500` ⇒ ilgili tarafın %0,25'i (giriş veya çıkış, `creator_fee_on`'a bağlı olarak — aşağıdaki "Ücretlerin alındığı taraf" bölümüne bakın).
- **`creator_fee_rate`** **swap hacminin** bir kesridir, işlem ücretinden **ayrı** olarak alınır. `1000` ⇒ ilgili tarafın %0,10'u.
- **`protocol_fee_rate`** ve **`fund_fee_rate`** hacmin değil, **işlem ücretinin** kesirleridir. `120_000` ⇒ işlem ücretinin %12'si.

Mainnet'te `AmmConfig[index=0]` (standart %0,25 havuz) için varsayılan parametreler, referans için:

| Alan | Değer | Etkili yüzde |
|-------|-------|-------------------|
| `trade_fee_rate` | `2500` | hacmin %0,25'i (işlem-ücreti hesabı) |
| `protocol_fee_rate` | `120000` | işlem ücretinin %12 ≈ **hacmin %0,030'u** |
| `fund_fee_rate` | `40000` | işlem ücretinin %4 ≈ **hacmin %0,010'u** |
| `creator_fee_rate` | `0` (varsayılan) | %0 (ayrı hesap) |
| → LP payı etkili | | **hacmin %0,210'u** |

Yani `AmmConfig[0]` ile `enable_creator_fee = false` olan bir \$1.000 swap'inde: \$2,50 toplam işlem ücreti, bunun \$2,10'u LP'lerde kalır, \$0,30 protokole gider, \$0,10 fona gider. Yaratıcı ücreti devre dışı bırakıldığı için yaratıcı hesabı 0'dır.

Aynı havuzun `enable_creator_fee = true` ve `creator_fee_rate = 1000` (%0,10%) olması durumunda, kullanıcı yaratıcı hesabına ek \$1,00 öder — `creator_fee_on` tarafından yapılandırılan aynı taraftan alınır — toplam \$3,50 ücret için. İşlem-ücreti hesabı ve onun protokol/fon bölünüşü değişmez.

Geçerli mainnet değerlerini `GET https://api-v3.raydium.io/main/cpmm-config` ile doğrulayın — oranlar yönetici tarafından değiştirilebilir ve sabit kodlanmak yerine taze okunmalıdır.

## Bölünüş, kodda

```rust
// raydium-cp-swap/programs/cp-swap/src/curve/{calculator,fees}.rs'den parafraz.
// Gerçek kod `is_creator_fee_on_input` üzerinde dallanır; her iki dal da
// yaratıcı_ücreti'nin asla trade_fee'nin bir dilimi olmadığı değişmezini korur.

const FEE_RATE_DENOMINATOR_VALUE: u64 = 1_000_000;

pub struct FeeBreakdown {
    pub amount_in_after_fees: u64,    // girdiden tüm giriş tarafı ücretleri çıkarıldıktan sonra
    pub amount_out_after_fees: u64,   // çıkıştan alınan herhangi bir yaratıcı ücreti çıkarıldıktan sonra
    pub trade_fee:    u64,            // → aşağıda LP / protokol / fon hesaplarına bölünür
    pub protocol_fee: u64,            // trade_fee'nin payı
    pub fund_fee:     u64,            // trade_fee'nin payı
    pub creator_fee:  u64,            // bağımsız hesap (giriş veya çıkış tarafı)
}

fn take_fees_on_input(
    amount_in: u64,
    trade_rate: u64,
    creator_rate: u64,
    protocol_rate: u64,
    fund_rate: u64,
) -> (u64 /* trade_fee */, u64 /* creator_fee */, u64 /* amount_in_after_fees */) {
    // İki oran toplanır, böylece birleşik ücret üzerinde bir kez yuvarlanır, sonra
    // orantılı olarak bölünür — bu tamamen yuvarlama/verimlilik numarasıdır. Bölünüş
    // oranları tam olarak onurlandırır: creator_fee/trade_fee == creator_rate/trade_rate.
    let total_fee = ((amount_in as u128) * ((trade_rate + creator_rate) as u128))
        .div_ceil(FEE_RATE_DENOMINATOR_VALUE as u128) as u64;

    let creator_fee = ((total_fee as u128) * (creator_rate as u128)
                       / ((trade_rate + creator_rate) as u128)) as u64;
    let trade_fee   = total_fee - creator_fee;

    (trade_fee, creator_fee, amount_in - total_fee)
}

fn take_creator_fee_on_output(amount_out_swapped: u64, creator_rate: u64) -> (u64, u64) {
    // creator_fee_on yaratıcı ücreti çıkış tarafına yönlendirdiğinde,
    // trade_fee giriş tarafından tek bir oran olarak alınır ve creator_fee
    // eğri çıkışına karşı hesaplanır.
    let creator_fee = ((amount_out_swapped as u128) * (creator_rate as u128))
        .div_ceil(FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    (amount_out_swapped - creator_fee, creator_fee)
}

fn split_trade_fee(
    trade_fee: u64,
    protocol_rate: u64,
    fund_rate: u64,
) -> (u64 /* protocol_fee */, u64 /* fund_fee */) {
    let protocol_fee = (trade_fee as u128 * protocol_rate as u128
                        / FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    let fund_fee     = (trade_fee as u128 * fund_rate as u128
                        / FEE_RATE_DENOMINATOR_VALUE as u128) as u64;
    (protocol_fee, fund_fee)
}
```

Notlar:

- Giriş tarafındaki toplam ücret **yukarı** yuvarlanır, böylece havuz asla eksik ücret almaz.
- `trade_fee`'nin alt bölünüşleri (protokol, fon) **aşağı** yuvarlanır, böylece toplamları `trade_fee`'yi aşmaz; kalan LP payıdır.
- `lp_share = trade_fee − protocol_fee − fund_fee` (creator_fee kendi hesabı olduğu için **çıkarılmaz**).
- Yaratıcı ücreti `PoolState.creator_fee_on`'a bağlı olarak giriş veya çıkış tarafından alınır (sonraki bölüme bakın). Oran her iki şekilde de değişmez.

## Ücretlerin alındığı taraf

CPMM'nin havuz başına `creator_fee_on` ayarı (`BothToken` / `OnlyToken0` / `OnlyToken1`) vardır; bu, yaratıcı ücretinin belirli bir swap'in **giriş** tarafından mı yoksa **çıkış** tarafından mı alındığını belirler. Runtime yardımcısı `is_creator_fee_on_input(direction)` bunu swap başına bir boole'ye daraltır:

| `creator_fee_on` | Swap `0 → 1` | Swap `1 → 0` |
|------------------|---------------|---------------|
| `BothToken` (`0`) | giriş tarafı | giriş tarafı |
| `OnlyToken0` (`1`) | giriş tarafı | çıkış tarafı |
| `OnlyToken1` (`2`) | çıkış tarafı | giriş tarafı |

Yaratıcı ücreti **giriş** tarafında olduğunda, hem işlem ücreti hem de yaratıcı ücreti eğri çalışmadan önce `amount_in`'den düşülür. Fiyat hesaplama: girdiden birleşik `trade_rate + creator_rate`'i alın.

Yaratıcı ücreti **çıkış** tarafında olduğunda, yalnızca işlem ücreti `amount_in`'den düşülür; eğri ücretlendirilmemiş bir çıkış üretir, sonra yaratıcı ücreti bu çıkıştan düşülür. Fiyat hesaplama: girdiden `trade_rate`'i alın; çıkıştan `creator_rate`'i alın.

İşlem ücreti kendisi her zaman giriş tarafından alınır (standart Uniswap-V2 deseni). Yalnızca yaratıcı ücreti çıkışta olabilir.

## "Tahakkuk eden" ücretlerin eğri ile etkileşimi

Önemli bir incelik: **protokol, fon ve yaratıcı ücretleri vault'ta fiziksel olarak kalır** ilgili `Collect*` talimatı çağrılana kadar. Ancak eğrinin vault bakiyesi görüşünden hariç tutulurlar.

Bir swap'ten sonra somut bir resim:

```
raw_vault_0_balance = getTokenAccountBalance(vault_0).amount
                    = lp_entitled + protocol_fees_token0
                      + fund_fees_token0 + creator_fees_token0

curve_x = raw_vault_0_balance − (protocol_fees_token0
                                  + fund_fees_token0
                                  + creator_fees_token0)
```

Program `k' ≥ k` uygulanırken `curve_x` (ve benzer `curve_y`) kullanır. Bu, LP olmayan ücretlerin LP payını şişirmeden hedeflerine ulaşmasıdır.

Tasarlarken dikkate alınması gereken sonuçlar:

- **Ham bakiyelerden fiyat hesaplamak yanlıştır.** `getTokenAccountBalance` üzerinden bir fiyat hesaplayıcı oluşturursanız, havuzun onayladığı fiyatı tutarlı olarak abartacaksınız. Her zaman tahakkuk eden ücretleri çıkarın veya `SwapBaseInput` / API aracılığıyla simüle edin.
- **`CollectProtocolFee` fiyatı hareket ettirmez.** Token'ları vault'tan çıkarır *ve* `protocol_fees_token*` sayaçlarını sıfırlar, böylece `curve_x` ve `curve_y` değişmez.
- **LP ücretleri sayaca tahakkuk etmez.** Bunlar vault bakiyesinde örtülüdür. LP'nin birikmiş LP ücretlerine hakkı LP token'larını yakarak (yani `Withdraw` aracılığıyla) kullanılır — `CollectLpFee` yoktur.

## Token-2022 transfer ücretleri ile etkileşim

Token-2022 transfer ücretleri CPMM tarafından değil, **mint** tarafından uygulanır. Her token transferinde — swap, yatırma, çekme ve `Collect*` toplamaları — etki ederler. CPMM'nin işlem-ücreti hesaplaması **vault'ta gerçekten inen** miktara karşı hesaplanır, yani giriş mint'inin transfer ücretinin net'i (varsa).

Yani en kötü durumda bir kullanıcı giriş-tam swap'inde üç ayrı vergi öder:

1. Giriş mint'inin `amount_in` üzerindeki transfer ücreti (mint'in ücret yetkilisine).
2. Havuzun `trade_fee`'si kalana karşı (yukarıda bölünmüş).
3. Çıkış mint'inin `amount_out` üzerindeki transfer ücreti (mint'in ücret yetkilisine).

SDK'nın fiyat hesaplayıcısı üçünü de hesaba katarken `minimum_amount_out` kullanıcının gerçekten aldığı şeyde gösterilir. Kendi fiyat hesaplayıcınızı yazıyorsanız, bu davranışı yansıtın, aksi takdirde slippage kontrolleri sistematik olarak çok cömert olacaktır.

Ayrıntılı türetme için [`algorithms/token-2022-transfer-fees`](/tr/algorithms/token-2022-transfer-fees) bölümüne bakın.

## Yaratıcı ücreti

Yaratıcı ücreti isteğe bağlı ve havuz başına. **Oran** `AmmConfig.creator_fee_rate` üzerinde bulunur; **etkinleştirme bayrağı** ve **taraf** (`creator_fee_on`) `PoolState` üzerinde bulunur:

- **Havuz oluşturmada etkinleştirilir.** `Initialize` varsayılan olarak `enable_creator_fee = false` ayarlar; `InitializeWithPermission` aracılığıyla oluşturulan havuzlar (LaunchLab mezuniyetleri ve diğer kapılı yollar tarafından kullanılır) `enable_creator_fee = true` geçirebilir ve `creator_fee_on` seçebilir.
- **Oran ücret katmanı ile paylaşılır.** Oran kendisi `AmmConfig.creator_fee_rate`'dir, o config'e bağlı her havuz arasında aynı değer. Her havuz daha sonra bunu alıp almayacağına (`enable_creator_fee`) ve swap'in hangi tarafından alacağına (`creator_fee_on`) karar verir. `enable_creator_fee = false` olduğunda, havuzun etkili yaratıcı-ücret oranı config değerinden bağımsız olarak sıfırdır (kaynakta `PoolState::adjust_creator_fee_rate` bölümüne bakın).
- **İşlem ücretinden bağımsız.** Yaratıcı ücreti asla LP / protokol / fon paylarını azaltmaz — kendi oranıdır, ayrı olarak uygulanır, kendi sayaçlarında tahakkuk eder.
- **`CollectCreatorFee` veya `CollectCreatorFeePermissionless` aracılığıyla toplanır.** Orijinal yol `PoolState.pool_creator`'ün imzalamasını gerektirir. İzinsiz yol herhangi bir ödeyicinin koleksiyonu tetiklemesine izin verir ancak her iki hedefi de yaratıcının kanonik ATA'larına sabitler.
- **Oluşturulduktan sonra yeniden etkinleştirilemez veya yeniden yönlendirilmez.** `enable_creator_fee = false` ile başlatılan bir havuz asla yaratıcı ücreti almayacak; belirli bir `creator_fee_on` ile başlatılan bir havuz taraf değiştiremez.

Yaratıcı ücretleri Raydium'un "Burn & Earn" deseni arkasındaki mekanizmadır: LP token'ları [LP Lock](/tr/reference/program-addresses) programı altında kilitlenir, böylece yaratıcı likiditeyi çekemez, ancak tahakkuk eden yaratıcı ücretleri süresiz olarak toplanabilir.

## Koleksiyon operasyonel akışı

| İmzalayan | Talimat | Sıfırlanan kaynak sayaçları | Tipik sıklık |
|--------|-------------|------------------------|-----------------|
| `amm_config.protocol_owner` | `CollectProtocolFee` | `protocol_fees_token{0,1}` | Haftalık veya programlı |
| `amm_config.fund_owner` | `CollectFundFee` | `fund_fees_token{0,1}` | Haftalık veya programlı |
| `pool_state.pool_creator` | `CollectCreatorFee` | `creator_fees_token{0,1}` | Herhangi bir zaman |
| Herhangi bir ödeyici; yaratıcı imzalamaz | `CollectCreatorFeePermissionless` | `creator_fees_token{0,1}` | Herhangi bir zaman; yaratıcı ATA'ları sabit hedeflerdir |

Protokol ve fon sahipleri mainnet'te Raydium multisig'idir; bkz. [`security/admin-and-multisig`](/tr/security/admin-and-multisig). Orijinal yaratıcı-yalnızca yolunda, yaratıcı imzalayan `PoolState` içinde kaydedilen hesaptır. İzinsiz yolda, çağıran eksik yaratıcı ATA'sını oluşturmak için ödeme yapar. Program `creator`'ü `pool_state.pool_creator` ile kısıtlar ve her hedefi o yaratıcı artı ilgili vault mint'i ve token programından türetir, böylece çağıran fonları yeniden yönlendiremez.

## Ücret katmanını değiştirme

Ücret oranları yönetici tarafından `UpdateAmmConfig` aracılığıyla değiştirilebilir (bkz. [`products/cpmm/instructions`](/tr/products/cpmm/instructions)). Değişiklikler o `AmmConfig`'e bağlı her havuz için **sonraki swap'te** etkili olur — geçiş yoktur, çünkü havuzlar her swap'te config'i yükler.

Yöneticinin yapamadığı şeyler:

- Bir havuzu bir `AmmConfig`'den diğerine taşımak.
- Zaten tahakkuk eden ücretleri geriye dönük olarak yeniden fiyatlandırmak.
- `protocol_owner` / `fund_owner` imzalayan olmadan ücretleri toplamak.

## Çalışan bir havuzdan ücretleri okuma

```ts
// Zincir dışı: her hesapta tahakkuk eden geçerli ücretler
const pool = await connection.getAccountInfo(poolStatePda);
const decoded = PoolState.decode(pool.data);
console.log(
  "Protokol tahakkuk:",
  decoded.protocolFeesToken0.toString(),
  decoded.protocolFeesToken1.toString(),
);
console.log(
  "Fon tahakkuk:",
  decoded.fundFeesToken0.toString(),
  decoded.fundFeesToken1.toString(),
);
console.log(
  "Yaratıcı tahakkuk:",
  decoded.creatorFeesToken0.toString(),
  decoded.creatorFeesToken1.toString(),
);

// Zincir dışı: bugün etkili oranlar.
// trade_fee_rate, creator_fee_rate hacmin kesirleridir (payda 1e6).
// protocol_fee_rate, fund_fee_rate *işlem ücretinin* kesirleridir (aynı payda).
const config = await fetch("https://api-v3.raydium.io/main/cpmm-config")
  .then((r) => r.json());
const tier = config.data.find((t) => t.index === decoded.ammConfigIndex);

const tradeFeeOfVolume   = tier.tradeFeeRate / 1_000_000;
const protocolOfTradeFee = tier.protocolFeeRate / 1_000_000;
const fundOfTradeFee     = tier.fundFeeRate / 1_000_000;
const lpOfTradeFee       = 1 - protocolOfTradeFee - fundOfTradeFee;

console.log("LP ücreti etkili:",       (tradeFeeOfVolume * lpOfTradeFee * 100).toFixed(4), "%");
console.log("Protokol ücreti etkili:", (tradeFeeOfVolume * protocolOfTradeFee * 100).toFixed(4), "%");
console.log("Fon ücreti etkili:",     (tradeFeeOfVolume * fundOfTradeFee * 100).toFixed(4), "%");
console.log(
  "Yaratıcı ücreti etkili:",
  decoded.enableCreatorFee
    ? ((tier.creatorFeeRate / 1_000_000) * 100).toFixed(4) + " %"
    : "0 % (bu havuzda devre dışı)",
);
```

## CLMM ve AMM v4 ile karşılaştırma

Yan yana matris için [`reference/fee-comparison`](/tr/reference/fee-comparison) bölümüne bakın. Özet:

- **AMM v4** farklı bir LP/protokol bölünüşü ve fon ücreti olmayan sabit %0,25 işlem ücreti kullanır.
- **CLMM** ücretleri tick-aralığı katmanı başına, havuz başına değil konum başına tahakkuk eder ve `DecreaseLiquidity` veya `CollectFees` aracılığıyla talep edilir.
