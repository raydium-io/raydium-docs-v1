<Info>
  CPI ("cross-program invocation") es el mecanismo mediante el cual un programa de Solana invoca a otro. La mayoría de los programas de Raydium incluyen crates de envoltura CPI basadas en Anchor que hacen que el sitio de llamada se parezca a una llamada de función tipada, con estructuras de cuenta que tienen nombres de campo validados y ayudantes `cpi::<ix>()`. Esta página documenta el patrón general una sola vez, luego las diferencias por programa. Para TypeScript ejecutable, consulta la página `code-demos` de cada capítulo de producto.
</Info>

## Qué patrón se aplica a cada programa

| Programa | Basado en Anchor | Crate | Dónde |
|---|---|---|---|
| CPMM | Sí | `raydium-cp-swap` (repositorio público; la ruta de uso de Rust es `raydium_cp_swap`) | [El patrón general](#the-general-anchor-cpi-pattern), el ejemplo trabajado |
| CLMM | Sí | `raydium-clmm` (repositorio público; la ruta de uso de Rust es `raydium_clmm`) | [Aplicar el patrón: CLMM](#applying-the-pattern-clmm) |
| LaunchLab | Sí | sin nombre de crate confirmado; la fuente del programa es cerrada, pero el identificador de metadatos internos del IDL en cadena es `raydium_launchpad`, un nombre técnico en lugar del nombre del producto (consulta la advertencia en [Aplicar el patrón: LaunchLab](#applying-the-pattern-launchlab)) | [Aplicar el patrón: LaunchLab](#applying-the-pattern-launchlab) |
| Farm v6 | Sin confirmar; no se encontró IDL público ni fuente (consulta la advertencia en [Farm v6](#farm-v6)) | n/a | [Farm v6](#farm-v6) |
| AMM v4 | **No**, anterior a Anchor sin crate CPI | ninguno | [AMM v4](#amm-v4-manual-instruction-construction) |

Si estás integrando CPMM, CLMM o LaunchLab, lee primero [el patrón general](#the-general-anchor-cpi-pattern), luego salta a la sección de tu programa para la lista de cuentas y cualquier diferencia. Farm v6 y AMM v4 son lo suficientemente diferentes como para justificar leer sus secciones de forma independiente.

## Dependencias de Cargo

```toml icon="file-code"
# Ambos crates CPI públicos de Raydium fijan Anchor =1.0.2 en `master`,
# por lo que un programa puede depender de uno o ambos — consulta la tabla a continuación.
[dependencies]
anchor-lang     = "=1.0.2"
anchor-spl      = "=1.0.2"
raydium-cp-swap = { git = "https://github.com/raydium-io/raydium-cp-swap", branch = "master", features = ["cpi"] }
raydium-clmm    = { git = "https://github.com/raydium-io/raydium-clmm",    branch = "master", features = ["cpi"] }
# NOTA: si fijas una `rev` más antigua anterior a la actualización de Anchor 1.0 (CPMM 2026-09-09,
# CLMM 2026-09-30), esa rev fija anchor-lang 0.32.1; usa =0.32.1 y la API de CpiContext 0.3x
# — y entonces solo uno de los dos crates a la vez.
# LaunchLab: la fuente del programa no está disponible públicamente (consulta reference/program-addresses).
# No hay dependencia de git a la que apuntar. Genera enlaces CPI desde el IDL publicado
# en su lugar. Consulta "Aplicar el patrón: LaunchLab" a continuación.
# AMM v4 no tiene un crate CPI de Anchor publicado; consulta su propia sección.
```

<Warning>
  **La clave de dependencia debe coincidir exactamente con el `[package] name` del repositorio de destino, incluidos los guiones.** Cargo no trata `raydium_cp_swap` como equivalente a `raydium-cp-swap` al resolver una dependencia de *git*.
</Warning>

`branch = "master"` rastrea la fuente publicada más reciente; fija a un `rev = "<commit>"` específico si necesitas una compilación reproducible. Esto se recomienda una vez que hayas pasado la fase de prototipado, ya que un cambio de diseño de cuenta ascendente en `master` romperá tu compilación sin previo aviso.

La bandera de característica `cpi` hace que los crates se compilen solo a la superficie de CPI (estructuras de cuenta + invocadores) en lugar del programa completo, por lo que tu binario se mantiene pequeño.

**`anchor-lang` / `anchor-spl` debe coincidir con lo que fija el crate de destino**:

| Crate | Fija `anchor-lang` / `anchor-spl` |
|---|---|
| `raydium-cp-swap` (`master`) | `=1.0.2`, de la [actualización 2026-09-09](/es/reference/changelog/2026-09-09-cpmm-anchor-1-and-excess-lamports) |
| `raydium-clmm` (`master`) | `=1.0.2`, de la [actualización 2026-09-30](/es/reference/changelog/2026-09-30-clmm-anchor-1-and-excess-lamports) |
| Cualquier crate en una `rev` anterior a su actualización | `0.32.1` |

<Warning>
  **Toma ambos crates de la misma línea de Anchor.** Ambas ramas `master` fijan `=1.0.2`, por lo que un programa puede hacer CPI en CPMM y CLMM desde un solo crate. Mezclar líneas rompe la compilación: por ejemplo, `raydium-cp-swap` en `master` con `raydium-clmm` fijado a una `rev` anterior a su actualización de Anchor 1.0. Cargo tendría que vincular dos copias incompatibles de los rasgos de Anchor en un binario. Si estás atrapado en un par mixto, divide el programa en dos, o abandona el crate CPI tipado para un lado y codifica manualmente esa instrucción (el patrón mostrado para [AMM v4](#amm-v4-manual-instruction-construction) funciona para cualquier programa).
</Warning>

<Warning>
  **Anchor 1.0 cambió dos cosas que toca cada sitio de llamada CPI.** Si estás moviendo una integración funcional de `0.3x`:

  - **`CpiContext::new` toma un `Pubkey`, no un `AccountInfo`.** `CpiContext::new(ctx.accounts.cpmm_program.to_account_info(), accts)` se convierte en `CpiContext::new(*ctx.accounts.cpmm_program.key, accts)`. Lo mismo para `new_with_signer`. El campo de estructura ahora es `program_id: Pubkey`.
  - **`Context` tiene una vida útil, no cuatro.** `Context<'_, '_, 'info, 'info, MyProxySwap<'info>>` se convierte en `Context<'info, MyProxySwap<'info>>`.

  En el lado del cliente, `anchor-client`'s `RequestBuilder::instructions()` ahora devuelve `Vec<Instruction>` en lugar de `Result<Vec<Instruction>>` (suelta el `?`), y `CommitmentConfig` se movió fuera de `solana-sdk` — tómalo de `anchor_client` en su lugar. `spl-associated-token-account` 8.0 re-exporta sus ayudantes desde el nuevo crate `spl-associated-token-account-interface`. `get_associated_token_address` e `ID` aún son alcanzables en la *raíz del crate* (`spl_associated_token_account::{get_associated_token_address, ID}`), pero los ayudantes de dirección están deprecados allí — prefiere depender de `spl-associated-token-account-interface` directamente e importar `spl_associated_token_account_interface::address::get_associated_token_address` y `spl_associated_token_account_interface::program::ID`. Ten en cuenta que `::address` y `::program` son módulos del crate de *interfaz*; `spl_associated_token_account::address::…` no se resuelve.
</Warning>

Para ejemplos de CPI funcionales que cablean las estructuras de cuenta de extremo a extremo, consulta [`raydium-io/raydium-cpi-example`](https://github.com/raydium-io/raydium-cpi-example) (cubre AMM v4, CPMM y CLMM). Su rama más nueva es [`anchor-0.31.0`](https://github.com/raydium-io/raydium-cpi-example/tree/anchor-0.31.0) — aún no hay rama de Anchor 1.x, así que trata ese repositorio como la referencia para el **cableado de estructura de cuenta**, no para los pines de versión que esta página ordena.

## El patrón general de CPI en Anchor

Esta sección recorre **CPMM** de principio a fin como ejemplo práctico: struct `Accounts`, `CpiContext`, `cpi::<ix>()`. CLMM sigue la misma estructura, con una lista de cuentas diferente y un requisito de remaining-accounts. LaunchLab sigue la misma mecánica, pero su lista de cuentas incluye varias cuentas sin equivalente en CPMM/CLMM (`global_config`, `platform_config`, `event_authority`, `program`), así que trátalo como el mismo *patrón*, no la misma *forma*. Consulta la sección de cada programa en lugar de asumir que la lista de cuentas de este tutorial se transfiere directamente.

### Construcción de la lista de cuentas

Cada CPI de Raydium requiere un struct `Accounts` en el programa que realiza la llamada. Sus campos son las cuentas que *tu* instrucción necesita, con validadores a nivel de campo; el orden de su declaración no tiene que coincidir con el orden de cuentas de la instrucción de Raydium, ya que tu cliente generado por IDL las direcciona por nombre, no por posición:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};

#[derive(Accounts)]
pub struct MyProxySwap<'info> {
    #[account(mut)]
    pub user: Signer<'info>,

    /// CHECK: validated by CPMM
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    /// CHECK: ditto
    pub amm_config: UncheckedAccount<'info>,

    /// CHECK: ditto
    pub pool_authority: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    pub input_mint: Account<'info, Mint>,
    pub output_mint: Account<'info, Mint>,

    #[account(mut)]
    pub user_input_ata:  Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_output_ata: Account<'info, TokenAccount>,

    /// Typed as `Program<RaydiumCpSwap>` rather than `UncheckedAccount`: this account
    /// is the program being invoked, not Raydium-owned data, so Anchor's `Program<T>`
    /// wrapper checks its address automatically instead of leaving that check to the
    /// callee.
    pub cpmm_program: Program<'info, raydium_cp_swap::program::RaydiumCpSwap>,
    pub token_program: Program<'info, Token>,
    /// CHECK: observation PDA
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,
}
```

La mayoría de las cuentas del lado de Raydium son `UncheckedAccount` porque el programa llamado (Raydium) es responsable de la validación. Tu programa que realiza la llamada solo valida estrictamente las cuentas que *tú* posees, como las ATAs del usuario y tus propios PDAs. El comentario de documentación `/// CHECK:` suprime la advertencia de Anchor sobre validaciones faltantes. La única excepción del lado de Raydium es `cpmm_program` en sí: es el programa que se invoca en lugar de una cuenta de datos que Raydium valida internamente, así que se tipifica como `Program<T>` y obtiene la verificación automática de dirección de Anchor en lugar de un `/// CHECK:` manual. Esta forma mayormente `UncheckedAccount`, donde Raydium valida sus propias cuentas, es la misma para CLMM y LaunchLab. Este ejemplo asume que ambos mints son Token SPL clásico; si cualquiera de los lados puede ser un mint Token-2022, añade un campo `token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>` y pásalo como `input_token_program`/`output_token_program` de ese lado en la llamada CPI de abajo en lugar de `token_program`.

### Construcción de la llamada CPI

Anchor genera un helper por instrucción, junto con un struct de cuentas CPI (`cpi::accounts::Swap`, aliasado como `CpmmSwap` abajo). A diferencia de tu struct `MyProxySwap` anterior, los nombres y el orden de los campos de este están fijados por el IDL propio de `raydium-cp-swap` y tienen que coincidir exactamente:

```rust icon="rust"
use raydium_cp_swap::cpi::{self, accounts::Swap as CpmmSwap};

pub fn my_proxy_swap(
    ctx: Context<MyProxySwap>,
    amount_in: u64,
    minimum_amount_out: u64,
) -> Result<()> {
    let cpi_accounts = CpmmSwap {
        // `payer` is YOUR signer — it must own `input_token_account`.
        payer:                ctx.accounts.user.to_account_info(),
        // `authority` is CPMM's OWN vault PDA at seeds [b"vault_and_lp_mint_auth_seed"],
        // which CPMM signs with itself. Passing your signer here fails the
        // seeds constraint (`ConstraintSeeds`) before any transfer runs.
        authority:            ctx.accounts.pool_authority.to_account_info(),
        amm_config:           ctx.accounts.amm_config.to_account_info(),
        pool_state:           ctx.accounts.pool_state.to_account_info(),
        input_token_account:  ctx.accounts.user_input_ata.to_account_info(),
        output_token_account: ctx.accounts.user_output_ata.to_account_info(),
        input_vault:          ctx.accounts.input_vault.to_account_info(),
        output_vault:         ctx.accounts.output_vault.to_account_info(),
        input_token_program:  ctx.accounts.token_program.to_account_info(),
        output_token_program: ctx.accounts.token_program.to_account_info(),
        input_token_mint:     ctx.accounts.input_mint.to_account_info(),
        output_token_mint:    ctx.accounts.output_mint.to_account_info(),
        observation_state:    ctx.accounts.observation_state.to_account_info(),
    };
    // Anchor 1.0: the first argument is the program's Pubkey, not its AccountInfo.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.cpmm_program.key,
        cpi_accounts,
    );

    cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
    Ok(())
}
```

`cpi::swap_base_input` se genera a partir del IDL; su lista de argumentos refleja la lista de argumentos de la instrucción de Anchor. Cada programa de Raydium basado en Anchor confirmado (CPMM, CLMM, LaunchLab) genera sus helpers `cpi::<ix>()` de la misma manera, con el nombre de la función coincidiendo con el nombre de la instrucción en snake_case. Si esto se extiende a Farm v6 no está confirmado; consulta su sección.

### Signer seeds (CPI firmado por PDA)

Cuando tu programa firma el CPI en nombre de un PDA (común para bóvedas, depósitos en garantía, etc.), usa `CpiContext::new_with_signer`:

```rust icon="rust"
let bump         = ctx.accounts.my_authority_bump;
let signer_seeds: &[&[&[u8]]] = &[&[b"my_authority", &[bump]]];

let cpi_ctx = CpiContext::new_with_signer(
    *ctx.accounts.cpmm_program.key,
    cpi_accounts,
    signer_seeds,
);

cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
```

Los signer seeds deben coincidir con la derivación del PDA. Para cualquier cuenta pasada como `authority` (o rol de firmante similar), el runtime de Solana verifica que el PDA firme a través de estos seeds.

### Remaining accounts

Algunas instrucciones de Raydium toman **remaining accounts**, una lista de longitud variable añadida después de las cuentas fijas. Los helpers CPI de Anchor no verifican el tipo de remaining accounts; pásalos a través de `.with_remaining_accounts(...)`:

```rust icon="rust"
let cpi_ctx = CpiContext::new(program_id, accounts)
    .with_remaining_accounts(ctx.remaining_accounts.to_vec());
```

El orden siempre importa, ya que el programa receptor itera los remaining accounts en el orden que los pasas. Dos órdenes confirmados:

- **CLMM `SwapV2`**: [tick arrays](#applying-the-pattern-clmm), ordenados direccionalmente.
- **Farm v6**: pares `(reward_vault, user_reward_ata)`, pero solo a partir del segundo flujo de recompensas en adelante; consulta [Farm v6](#farm-v6) para ver qué muestra la decodificación de una transacción real.

## Aplicar el patrón: CLMM

`SwapV2` sigue [el patrón general](#the-general-anchor-cpi-pattern) anterior con una lista de cuentas diferente y un requisito de remaining-accounts para tick arrays. El módulo `#[program]` del crate se llama `raydium_clmm`, que también es su ruta de `use` en Rust.

<Warning>
  **El struct de cuentas CPI se llama `SwapSingleV2`, no `SwapV2`.** `SwapV2` es el nombre de la *instrucción* en cadena.
</Warning>

```rust icon="rust"
use raydium_clmm::cpi::{self, accounts::SwapSingleV2 as ClmmSwap};

#[derive(Accounts)]
pub struct MyProxyClmmSwap<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: validated by CLMM
    pub amm_config: UncheckedAccount<'info>,
    /// CHECK: ditto
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    /// CHECK: observation PDA
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,

    pub token_program: Program<'info, Token>,
    pub token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>,
    /// CHECK: SPL memo program, required for some Token-2022 paths
    pub memo_program: UncheckedAccount<'info>,

    pub input_vault_mint: Account<'info, Mint>,
    pub output_vault_mint: Account<'info, Mint>,

    /// Typed as `Program<T>` rather than `UncheckedAccount`, same reason as CPMM's
    /// `cpmm_program` in the general pattern above: it's the invoked program, and
    /// `Program<T>` checks its address automatically.
    pub clmm_program: Program<'info, raydium_clmm::program::RaydiumClmm>,
    // remaining_accounts: tick_array_bitmap_extension (if the walk needs it), then
    // as many tick_array accounts as the swap's expected price range spans.
}
```

Calcula la lista de tick-array de la misma manera que lo hace el SDK, a través de una cotización contra el estado actual del pool, en lugar de adivinar un número fijo; un swap que supera los arrays que pasaste revierte con `TickArrayNotFound` (consulta [`products/clmm/instructions`](/es/products/clmm/instructions) para la tabla de cuentas completa y la lista de errores). Pásalos en la dirección del recorrido de precios: primer array en dirección de swap primero.

## Aplicar el patrón: LaunchLab

LaunchLab está basado en Anchor e IDL publicado: [`raydium_launchpad/raydium_launchpad.json`](https://github.com/raydium-io/raydium-idl/blob/master/raydium_launchpad/raydium_launchpad.json) en el repositorio público `raydium-idl`. El identificador de metadatos interno de ese IDL es `raydium_launchpad`, un nombre técnico para el programa subyacente, no un nombre alternativo para el producto. A diferencia de CPMM y CLMM, sin embargo, **el código fuente del programa no está disponible públicamente** (ver [`reference/program-addresses`](/es/reference/program-addresses)). No hay una dependencia `git = "..."` a la que apuntar con Cargo, ni código fuente para confirmar cuál sería la ruta `use` real de Rust en un crate.

Genera bindings desde el IDL publicado usando la macro `declare_program!` de Anchor. Guarda el JSON del IDL como `idls/raydium_launchpad.json` en tu crate (Cargo busca un directorio `idls/` relativo a `CARGO_MANIFEST_DIR`), luego `declare_program!(raydium_launchpad);` genera structs `raydium_launchpad::cpi::accounts::<Ix>` y funciones `cpi::<ix>()` directamente desde el IDL, sin necesidad del código fuente del programa. El nombre del struct de cuentas generado siempre es el nombre de la instrucción en PascalCase (`buy_exact_in` → `BuyExactIn`), y los nombres de los campos coinciden exactamente con los nombres de las cuentas del IDL, la misma lista de cuentas ya utilizada en `MyProxyBuy` a continuación.

La forma del CPI sigue [el patrón general](#the-general-anchor-cpi-pattern). La lista de cuentas y los argumentos a continuación provienen de la instrucción `buy_exact_in` del IDL en cadena, no de `products/launchlab/instructions.mdx`:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};
use raydium_launchpad::cpi::{self, accounts::BuyExactIn};

#[derive(Accounts)]
pub struct MyProxyBuy<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: PDA, seeds = [b"vault_auth_seed"], validated by the program
    pub authority: UncheckedAccount<'info>,

    /// CHECK: validated by the program
    pub global_config: UncheckedAccount<'info>,
    /// CHECK: validated by the program
    pub platform_config: UncheckedAccount<'info>,

    /// CHECK: validated by the program
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub user_base_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_quote_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub base_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub quote_vault: Account<'info, TokenAccount>,

    pub base_token_mint: Account<'info, Mint>,
    pub quote_token_mint: Account<'info, Mint>,

    /// CHECK: base mint's token program (SPL Token or Token-2022, depending on the mint)
    pub base_token_program: UncheckedAccount<'info>,
    /// Typed as `Program<Token>` rather than `UncheckedAccount`: the IDL fixes this to
    /// classic SPL Token specifically (unlike base_token_program above), so Anchor's
    /// built-in address check on `Program<Token>` is sufficient on its own.
    pub quote_token_program: Program<'info, Token>,

    /// CHECK: PDA, seeds = [b"__event_authority"], required by the program's emit_cpi! pattern
    pub event_authority: UncheckedAccount<'info>,
    /// CHECK: the program's own account, required alongside event_authority
    pub program: UncheckedAccount<'info>,
}

pub fn my_proxy_buy(
    ctx: Context<MyProxyBuy>,
    amount_in: u64,
    minimum_amount_out: u64,
    share_fee_rate: u64,
) -> Result<()> {
    let cpi_accounts = BuyExactIn {
        payer:               ctx.accounts.payer.to_account_info(),
        authority:           ctx.accounts.authority.to_account_info(),
        global_config:       ctx.accounts.global_config.to_account_info(),
        platform_config:     ctx.accounts.platform_config.to_account_info(),
        pool_state:          ctx.accounts.pool_state.to_account_info(),
        user_base_token:     ctx.accounts.user_base_token.to_account_info(),
        user_quote_token:    ctx.accounts.user_quote_token.to_account_info(),
        base_vault:          ctx.accounts.base_vault.to_account_info(),
        quote_vault:         ctx.accounts.quote_vault.to_account_info(),
        base_token_mint:     ctx.accounts.base_token_mint.to_account_info(),
        quote_token_mint:    ctx.accounts.quote_token_mint.to_account_info(),
        base_token_program:  ctx.accounts.base_token_program.to_account_info(),
        quote_token_program: ctx.accounts.quote_token_program.to_account_info(),
        event_authority:     ctx.accounts.event_authority.to_account_info(),
        program:             ctx.accounts.program.to_account_info(),
    };
    // `program` doubles as the CPI target here: LaunchLab's own account is both one of
    // its instruction's required accounts (for its emit_cpi! pattern) and the program
    // CpiContext::new invokes.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.program.key,
        cpi_accounts,
    );

    cpi::buy_exact_in(cpi_ctx, amount_in, minimum_amount_out, share_fee_rate)?;
    Ok(())
}
```

Después de la graduación, el programa destino es CPMM o AMM v4 dependiendo de `pool_state.migrate_type`, que según `products/launchlab/accounts.mdx` se establece en el momento de `Initialize`. Tu lista de cuentas CPI tiene que estar preparada para cualquiera de los dos, o necesitas leer `migrate_type` de `PoolState` primero y ramificarte.

## Propagación de errores

Cada programa Raydium basado en Anchor devuelve su propio enum de error; Anchor los envuelve, por lo que tu programa llamador los ve como `Err(ProgramError::Custom(code))`. Para manejar errores específicos:

```rust icon="rust"
use raydium_cp_swap::error::ErrorCode as CpmmErr;

match cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out) {
    Ok(_) => Ok(()),
    Err(e) => {
        msg!("CPMM swap failed: {:?}", e);
        // Re-raise, or convert to your own error type.
        Err(e)
    }
}
```

Sustituye el tipo de error relevante para el programa que estés llamando (`raydium_clmm::error::ErrorCode` para CLMM, y así sucesivamente). Los números de código de error son estables según la política del IDL ([`sdk-api/anchor-idl`](/es/sdk-api/anchor-idl#idl-change-policy)), por lo que puedes probar contra códigos específicos comparando contra el valor numérico. Tablas de errores completas: [CPMM](/es/reference/error-codes#cpmm-standard-amm-errors), [CLMM](/es/reference/error-codes#clmm-errors), [AMM v4, Farm v6, y LaunchLab](/es/reference/error-codes#amm-v4-farm-v3-/-v5-/-v6-launchlab-errors).

## Presupuesto de cómputo en CPIs compuestos

Cada frame de CPI tiene sobrecarga, y el consumo de CU propio del programa llamado se suma al tuyo, por lo que una transacción que llama a Raydium desde dentro de tu programa necesita un presupuesto de cómputo explícito en lugar de depender del default de 200k CU.

<Note>
  **Medido, no estimado.** Un `swap_base_input` de CPMM en mainnet consume **~23,000 CU** en el programa CPMM mismo — muestreado el 2026-09-09 en ocho swaps en vivo en un pool de alto volumen (22,721–23,052), leído de la línea de log `Program CPMMoo8… consumed N of M compute units`. Para comparación: swap de AMM v4 ~26,000; `swap` de CLMM ~41,000; `swap_v2` de CLMM ~48,000 (43,838–52,887), aumentando con cada cruce de tick.

  Una revisión anterior de esta página reportaba ~47,700 CU para un CPI de proxy-swap. Esa cifra era la *transacción completa* (`computeUnitsConsumed`), que incluye tu propio programa, el frame de CPI y cualquier configuración de ATA — no el costo del programa llamado. Ambos son útiles, pero no son el mismo número, así que compara lo similar con lo similar. Mide tu propia transacción en lugar de presupuestar basándote en ninguno de los dos.
</Note>

Los CPIs de CLMM y LaunchLab cuestan más (CLMM en particular recorre arrays de tick adicionales vía `remaining_accounts`, agregando CU por array), pero solo la cifra de CPMM anterior es un valor medido. Siempre establece un límite explícito `ComputeBudgetProgram::set_compute_unit_limit(...)` dimensionado a partir de tu propia medición, no un número copiado de la documentación, ya que el límite default de 200k CU se agotará silenciosamente y los costos por instrucción cambian a medida que los programas se actualizan.

## AMM v4: construcción manual de Instruction

AMM v4 es anterior a Anchor y no tiene un crate de CPI, lo que lo convierte en el único programa en este documento que no sigue el patrón general anterior. Construye la `Instruction` manualmente:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_lang::solana_program::program::invoke_signed;
use anchor_lang::solana_program::instruction::{Instruction, AccountMeta};

const AMM_V4_PROGRAM_ID: Pubkey = pubkey!("675kPX9MHTjS2zt1qfr1NYHuzeLXfQM9H24wFSUt1Mp8");

// SwapBaseIn discriminator is 9.
let mut data = vec![9u8];
data.extend_from_slice(&amount_in.to_le_bytes());
data.extend_from_slice(&minimum_amount_out.to_le_bytes());

let ix = Instruction {
    program_id: AMM_V4_PROGRAM_ID,
    accounts: vec![
        AccountMeta::new_readonly(token_program_id, false),
        AccountMeta::new(amm_id, false),
        AccountMeta::new_readonly(amm_authority, false),
        // ... remaining accounts per products/amm-v4/instructions ...
    ],
    data,
};
invoke_signed(&ix, &account_infos, signer_seeds)?;
```

Ver [`products/amm-v4/code-demos`](/es/products/amm-v4/code-demos) para la lista completa de cuentas.

## Farm v6

**Usa el SDK de TS si esa es una opción para tu integración.** `raydium.farm.deposit(...)` (ver [`products/farm-staking/code-demos`](/es/products/farm-staking/code-demos)) está ejercitado por demos reales y no depende de si existe un crate Anchor de Rust para este programa.

<Warning>
  **Farm v6 no ofrece ruta de CPI de Anchor.** No hay un crate `raydium_farm_v6` en crates.io, no hay repositorio de código fuente público, y no hay IDL en cadena — el programa no tiene ni una cuenta `anchor:idl` heredada ni una entrada en el Program Metadata program (ver [`sdk-api/anchor-idl`](/es/sdk-api/anchor-idl)). Trátalo como un programa que no es de Anchor y construye sus instrucciones manualmente, como se muestra a continuación.
</Warning>

**Si necesitas CPI de Rust de todas formas**, por ejemplo componiendo desde otro programa en cadena, construye la `Instruction` manualmente, de la misma manera que [AMM v4](#amm-v4-manual-instruction-construction): deriva la lista de cuentas real y los discriminadores de instrucción de forma independiente, por ejemplo decodificando los layouts de TypeScript del SDK (`raydium-sdk-V2`'s farm module), decodificando transacciones reales directamente (ver a continuación), o volcando y desensambland el programa desplegado.

Para la forma de instrucción de cero argumentos consistente con una llamada de harvest o claim, el orden de cuentas real es un prefijo fijo (`token_program`, la cuenta de estado del farm, un PDA de autoridad de bóveda, la primera bóveda de recompensas de ese PDA, un segundo PDA, el llamador, y el ATA del llamador para ese primer mint de recompensa), seguido de pares `(reward_vault_i, user_reward_ata_i)` en `remaining_accounts` para cada stream de recompensa después del primero. La convención de emparejamiento es real, pero solo comienza en el segundo stream de recompensa: la bóveda y ATA del primer stream son cuentas fijas, no adyacentes entre sí, y no son parte de `remaining_accounts` en absoluto.

## Prueba de un flujo CPI

El desarrollo local requiere que los programas de Raydium estén disponibles en tu validador de prueba. Tienes tres opciones:

1. **`anchor test` con clonación de programa.** Extrae el bytecode desplegado en mainnet hacia tu validador local; consulta [Clonación de programas en un validador local](#clonación-de-programas-en-un-validador-local) más abajo para la configuración de `Anchor.toml` y dos cosas que suelen causar problemas en las pruebas de creación de pools.
2. **Devnet.** Raydium despliega la mayoría de programas en devnet, pero con **IDs de programa diferentes a los de mainnet** para cada uno (CPMM, CLMM, AMM v4, Stable AMM y LaunchLab tienen direcciones distintas en devnet; consulta la tabla de Devnet en [`reference/program-addresses`](/es/reference/program-addresses)). Farm v3/v5/v6 no se publican de forma confiable en devnet; la API en vivo (`https://api-v3-devnet.raydium.io/main/info`) tiene la información actual. Si usas las constantes `DEVNET_PROGRAM_ID` incluidas en `raydium_clmm` (o equivalentes en otros crates), no asumas que un ID de mainnet también funciona en devnet. Ejecuta `anchor test --provider.cluster devnet` para probar el código en vivo una vez que tengas las direcciones correctas.
3. **Despliegue local.** Clona los repositorios de Raydium (CPMM, CLMM; el código fuente de LaunchLab no está disponible para esta opción) y ejecuta `anchor deploy` en un validador local. Añade sobrecarga al ciclo de prueba pero te permite modificar el programa llamado para depuración.

Ejecuta con `anchor test`, o primero `anchor build` y luego `anchor test --skip-build` si estás iterando sobre el archivo de prueba sin cambiar el programa.

### Clonación de programas en un validador local

```toml icon="file-code"
[test]
# El valor por defecto (5s) no es suficiente una vez que clonas varias cuentas, ya que cada una es
# un viaje RPC secuencial a mainnet durante el inicio del validador.
startup_wait = 60000

[test.validator]
url = "https://api.mainnet-beta.solana.com"

[[test.validator.clone]]
address = "CAMMCzo5YL8w4VFF8KVHrK22GGUsp5VTaW7grrKgrWqK"  # CLMM

[[test.validator.clone]]
address = "CPMMoo8L3F4NbTegBCKVNunggL7H1ZpdTHKxQB5qKP1C"  # CPMM

[[test.validator.clone]]
address = "LanMV9sAd7wArD4vJFi2qDdfnVhFxYSUg6eADduJ3uj"   # LaunchLab

[[test.validator.clone]]
address = "FarmqiPv5eAj3j1GMdMCMUGXqPUvmquZtMy86QH6rzhG"  # Farm v6
```

Esto funciona por ID de programa independientemente de si el código fuente del programa es público, así que LaunchLab se clona de la misma manera que CPMM y CLMM aunque su código fuente no esté disponible. `reference/program-addresses` es la fuente de verdad para cada dirección aquí.

<Warning>
  **Clonar el programa no es suficiente si tu prueba también *crea* un pool** (en lugar de hacer swap contra uno que ya existe). La instrucción `initialize` de CPMM valida sus cuentas `amm_config` y `create_pool_fee` contra datos reales en cadena, así que necesitas clonarlas también, o `initialize` falla directamente. Para CPMM específicamente: clona el `AmmConfig` de nivel de comisión que desees (obtén su dirección de `GET https://api-v3.raydium.io/main/cpmm-config`, el índice 0 es el nivel del 0.25%) y la [cuenta de token receptora de comisiones](/es/reference/program-addresses#shared-config-/-pda-conventions), validada por dirección exacta, no creada sobre la marcha, así que ya debe existir.
</Warning>

<Warning>
  **Un pool que tu prueba acaba de crear no es intercambiable en el mismo instante.** La instrucción `initialize` de CPMM anula silenciosamente un `open_time` solicitado que no está estrictamente en el futuro (`if open_time <= block_timestamp { open_time = block_timestamp + 1 }`), así que incluso `startTime: 0` ("abierto inmediatamente," según el SDK) deja una brecha real de ≥1 segundo antes de que el pool acepte swaps. Una prueba que crea un pool e inmediatamente hace swap contra él sin demora golpeará [`NotApproved`](/es/reference/error-codes#cpmm-standard-amm-errors). Un breve `await` (1–2s) entre la creación del pool y el primer swap es suficiente. Esto es específico de las pruebas; un humano ejecutando dos comandos manuales separados normalmente no lo notaría, ya que escribir e iniciar procesos ya consumen más de un segundo.
</Warning>
