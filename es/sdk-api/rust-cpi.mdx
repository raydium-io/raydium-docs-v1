<Info>
  CPI («cross-program invocation», invocación entre programas) es el mecanismo mediante el cual un programa de Solana llama a otro. La mayoría de los programas de Raydium incluyen crates de envoltura CPI de Anchor que hacen que el sitio de llamada se parezca a una llamada de función tipada, con estructuras de cuentas que tienen nombres de campo validados y ayudantes `cpi::<ix>()`. Esta página documenta el patrón general una sola vez, luego las diferencias por programa. Para TypeScript ejecutable, consulta la página `code-demos` de cada capítulo de producto.
</Info>

## Qué patrón se aplica a qué programa

|---|---|---|---|
| CPMM | Sí | `raydium-cp-swap` (repositorio público; la ruta de `use` de Rust es `raydium_cp_swap`) | [El patrón general](#the-general-anchor-cpi-pattern), el ejemplo trabajado |
| CLMM | Sí | `raydium-clmm` (repositorio público; la ruta de `use` de Rust es `raydium_clmm`) | [Aplicar el patrón: CLMM](#applying-the-pattern-clmm) |
| LaunchLab | Sí | sin nombre de crate confirmado; la fuente del programa es cerrada, pero el identificador de metadatos internos del IDL en cadena es `raydium_launchpad`, un nombre técnico en lugar del nombre del producto (consulta la advertencia en [Aplicar el patrón: LaunchLab](#applying-the-pattern-launchlab)) | [Aplicar el patrón: LaunchLab](#applying-the-pattern-launchlab) |
| Farm v6 | Sin confirmar; no se encontró IDL público ni fuente (consulta la advertencia en [Farm v6](#farm-v6)) | n/a | [Farm v6](#farm-v6) |

Farm v6 y AMM v4 son lo suficientemente diferentes como para justificar leer sus secciones de forma independiente.

## Dependencias de Cargo

```toml icon="file-code"
# Elige UNA de las dos crates CPI de Raydium por programa — consulta la advertencia a continuación.
[dependencies]
anchor-lang     = "=1.0.2"   # =0.32.1 si estás apuntando a raydium-clmm en su lugar
anchor-spl      = "=1.0.2"   # =0.32.1 igualmente
raydium-cp-swap = { git = "https://github.com/raydium-io/raydium-cp-swap", branch = "chore/upgrade-anchor", features = ["cpi"] }
# NOTA: el `master` de raydium-cp-swap aún fija anchor-lang 0.32.1. Los pines `=1.0.2`
# anteriores solo se resuelven contra la rama de actualización; si apuntas a `master`, usa =0.32.1
# y la API CpiContext 0.3x.
# raydium-clmm  = { git = "https://github.com/raydium-io/raydium-clmm",    branch = "master", features = ["cpi"] }
# LaunchLab: la fuente del programa no está disponible públicamente (consulta reference/program-addresses).
# No hay dependencia git a la que apuntar. Genera enlaces CPI desde el IDL publicado
# en su lugar. Consulta "Aplicar el patrón: LaunchLab" a continuación.
# AMM v4 no tiene una crate CPI de Anchor publicada; consulta su propia sección.
```

<Warning>
  **La clave de dependencia debe coincidir exactamente con el `[package] name` del repositorio de destino, guiones incluidos.** Cargo no trata `raydium_cp_swap` como equivalente a `raydium-cp-swap` al resolver una dependencia *git*.
</Warning>

`branch = "master"` rastrea la última fuente publicada; fija a un `rev = "<commit>"` específico si necesitas una compilación reproducible. Esto se recomienda una vez que hayas pasado la fase de prototipado, ya que un cambio de diseño de cuenta en `master` romperá tu compilación sin advertencia de otro modo.

La bandera de característica `cpi` hace que las crates se compilen solo a la superficie CPI (estructuras de cuentas + invocadores) en lugar del programa completo, por lo que tu binario se mantiene pequeño.

**`anchor-lang` / `anchor-spl` deben coincidir con lo que fija la crate de destino**, y a partir de 2026-09 las dos crates públicas de Raydium **no están de acuerdo**:

| Crate | Fija `anchor-lang` / `anchor-spl` |
|---|---|
| `raydium-cp-swap` (`chore/upgrade-anchor`) | `=1.0.2` — de la [actualización de 2026-09-09](/es/reference/changelog/2026-09-09-cpmm-anchor-1-and-excess-lamports) |
| `raydium-cp-swap` (`master`) | `0.32.1`, fijado con caret — la actualización no ha llegado a `master` |
| `raydium-clmm` (`master`) | `=0.32.1` |

<Warning>
  **No puedes depender de ambas crates desde un programa en este momento.** Cada una fija Anchor con `=`, por lo que Cargo tendría que vincular dos copias incompatibles de los rasgos de Anchor en un binario, y la compilación falla. Si tu programa hace CPI tanto a CPMM como a CLMM, tienes que dividirlo en dos programas, o dejar la crate CPI tipada para uno de ellos y codificar manualmente esa instrucción (el patrón mostrado para [AMM v4](#amm-v4-manual-instruction-construction) funciona para cualquier programa). Vuelve a verificar ambos archivos `Cargo.toml` antes de comenzar — se espera que esto se resuelva cuando CLMM se mueva a Anchor 1.x.
</Warning>

<Warning>
  **Anchor 1.0 cambió dos cosas que toca cada sitio de llamada CPI.** Si estás moviendo una integración funcional de `0.3x`:

  - **`CpiContext::new` toma un `Pubkey`, no un `AccountInfo`.** `CpiContext::new(ctx.accounts.cpmm_program.to_account_info(), accts)` se convierte en `CpiContext::new(*ctx.accounts.cpmm_program.key, accts)`. Lo mismo para `new_with_signer`. El campo de estructura ahora es `program_id: Pubkey`.
  - **`Context` tiene una vida útil, no cuatro.** `Context<'_, '_, 'info, 'info, MyProxySwap<'info>>` se convierte en `Context<'info, MyProxySwap<'info>>`.

  En el lado del cliente, `RequestBuilder::instructions()` de `anchor-client` ahora devuelve `Vec<Instruction>` en lugar de `Result<Vec<Instruction>>` (elimina el `?`), y `CommitmentConfig` se movió fuera de `solana-sdk` — tómalo de `anchor_client` en su lugar. `spl-associated-token-account` 8.0 re-exporta sus ayudantes desde la nueva crate `spl-associated-token-account-interface`. `get_associated_token_address` e `ID` aún son accesibles en la *raíz de la crate* (`spl_associated_token_account::{get_associated_token_address, ID}`), pero los ayudantes de dirección están deprecados allí — prefiere depender de `spl-associated-token-account-interface` directamente e importar `spl_associated_token_account_interface::address::get_associated_token_address` y `spl_associated_token_account_interface::program::ID`. Ten en cuenta que `::address` y `::program` son módulos de la crate *interface*; `spl_associated_token_account::address::…` no se resuelve.
</Warning>

Para ejemplos CPI funcionales que cablean las estructuras de cuentas de extremo a extremo, consulta [`raydium-io/raydium-cpi-example`](https://github.com/raydium-io/raydium-cpi-example) (cubre AMM v4, CPMM y CLMM). Su rama más nueva es [`anchor-0.31.0`](https://github.com/raydium-io/raydium-cpi-example/tree/anchor-0.31.0) — aún no hay rama de Anchor 1.x, así que trata ese repositorio como la referencia para **cableado de estructura de cuentas**, no para los pines de versión que esta página ordena.

## El patrón general de CPI de Anchor

Esta sección recorre **CPMM** de extremo a extremo como el ejemplo trabajado: estructura `Accounts`, `CpiContext`, `cpi::<ix>()`. CLMM sigue la forma idéntica, con una lista de cuentas diferente y un requisito de cuentas restantes. LaunchLab sigue la misma mecánica pero su lista de cuentas lleva varias cuentas sin equivalente en CPMM/CLMM (`global_config`, `platform_config`, `event_authority`, `program`), así que trátalo como el mismo *patrón*, no la misma *forma*. Consulta la sección propia de cada programa en lugar de asumir que la lista de cuentas de este tutorial se transfiere directamente.

### Construcción de la lista de cuentas

Cada CPI de Raydium requiere una estructura `Accounts` en el programa que llama. Sus campos son las cuentas que *tu* instrucción necesita, con validadores a nivel de campo; su orden de declaración no tiene que coincidir con el orden de cuentas de instrucción de Raydium, ya que tu propio cliente generado por IDL las direcciona por nombre, no por posición:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};

#[derive(Accounts)]
pub struct MyProxySwap<'info> {
    #[account(mut)]
    pub user: Signer<'info>,

    /// CHECK: validado por CPMM
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    /// CHECK: ídem
    pub amm_config: UncheckedAccount<'info>,

    /// CHECK: ídem
    pub pool_authority: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    pub input_mint: Account<'info, Mint>,
    pub output_mint: Account<'info, Mint>,

    #[account(mut)]
    pub user_input_ata:  Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_output_ata: Account<'info, TokenAccount>,

    /// Tipado como `Program<RaydiumCpSwap>` en lugar de `UncheckedAccount`: esta cuenta
    /// es el programa que se invoca, no datos propiedad de Raydium, por lo que el envoltorio
    /// `Program<T>` de Anchor verifica su dirección automáticamente en lugar de dejar esa
    /// verificación al llamado.
    pub cpmm_program: Program<'info, raydium_cp_swap::program::RaydiumCpSwap>,
    pub token_program: Program<'info, Token>,
    /// CHECK: PDA de observación
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,
}
```

La mayoría de las cuentas del lado de Raydium son `UncheckedAccount` porque el llamado (Raydium) posee la validación. Tu programa que llama solo valida estrictamente cuentas que *tú* posees, como ATAs de usuario y tus propios PDAs. El comentario de documentación `/// CHECK:` suprime la advertencia de Anchor sobre verificaciones faltantes. La excepción del lado de Raydium es `cpmm_program` en sí: es el programa que se invoca en lugar de una cuenta de datos que Raydium valida internamente, por lo que se tipea como `Program<T>` y obtiene la verificación de dirección automática de Anchor en lugar de un `/// CHECK:` manual. Esta forma mayormente `UncheckedAccount`, donde Raydium valida sus propias cuentas, es la misma para CLMM y LaunchLab. Este ejemplo asume que ambos mints son Token SPL clásico; si cualquiera puede ser un mint Token-2022, agrega un campo `token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>` y pásalo como `input_token_program`/`output_token_program` de ese lado en la llamada CPI a continuación en lugar de `token_program`.

### Construir la llamada CPI

Anchor genera un ayudante por instrucción, junto con una estructura de cuentas CPI (`cpi::accounts::Swap`, con alias `CpmmSwap` a continuación). A diferencia de tu propia estructura `MyProxySwap` anterior, los nombres y orden de este campo son fijos por el IDL propio de `raydium-cp-swap` y tienen que coincidir exactamente:

```rust icon="rust"
use raydium_cp_swap::cpi::{self, accounts::Swap as CpmmSwap};

pub fn my_proxy_swap(
    ctx: Context<MyProxySwap>,
    amount_in: u64,
    minimum_amount_out: u64,
) -> Result<()> {
    let cpi_accounts = CpmmSwap {
        // `payer` es TU firmante — debe poseer `input_token_account`.
        payer:                ctx.accounts.user.to_account_info(),
        // `authority` es el PDA de bóveda PROPIO de CPMM en semillas [b"vault_and_lp_mint_auth_seed"],
        // que CPMM firma consigo mismo. Pasar tu firmante aquí falla la
        // restricción de semillas (`ConstraintSeeds`) antes de que se ejecute cualquier transferencia.
        authority:            ctx.accounts.pool_authority.to_account_info(),
        amm_config:           ctx.accounts.amm_config.to_account_info(),
        pool_state:           ctx.accounts.pool_state.to_account_info(),
        input_token_account:  ctx.accounts.user_input_ata.to_account_info(),
        output_token_account: ctx.accounts.user_output_ata.to_account_info(),
        input_vault:          ctx.accounts.input_vault.to_account_info(),
        output_vault:         ctx.accounts.output_vault.to_account_info(),
        input_token_program:  ctx.accounts.token_program.to_account_info(),
        output_token_program: ctx.accounts.token_program.to_account_info(),
        input_token_mint:     ctx.accounts.input_mint.to_account_info(),
        output_token_mint:    ctx.accounts.output_mint.to_account_info(),
        observation_state:    ctx.accounts.observation_state.to_account_info(),
    };
    // Anchor 1.0: el primer argumento es el Pubkey del programa, no su AccountInfo.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.cpmm_program.key,
        cpi_accounts,
    );

    cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
    Ok(())
}
```

`cpi::swap_base_input` se genera desde el IDL; su lista de argumentos refleja la lista de argumentos de la instrucción de Anchor. Cada programa de Raydium basado en Anchor confirmado (CPMM, CLMM, LaunchLab) genera sus ayudantes `cpi::<ix>()` de la misma manera, con el nombre de función coincidiendo con el nombre de instrucción en snake_case. Si esto se extiende a Farm v6 no está confirmado; consulta su sección.

### Semillas de firmante (CPI firmado por PDA)

Cuando tu programa firma el CPI en nombre de un PDA (común para bóvedas, depósitos en garantía, etc.), usa `CpiContext::new_with_signer`:

```rust icon="rust"
let bump         = ctx.accounts.my_authority_bump;
let signer_seeds: &[&[&[u8]]] = &[&[b"my_authority", &[bump]]];

let cpi_ctx = CpiContext::new_with_signer(
    *ctx.accounts.cpmm_program.key,
    cpi_accounts,
    signer_seeds,
);

cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out)?;
```

Las semillas de firmante deben coincidir con la derivación del PDA. Para cualquier cuenta pasada como `authority` (o rol de firmante similar), el tiempo de ejecución de Solana verifica que el PDA firme a través de estas semillas.

### Cuentas restantes

Algunas instrucciones de Raydium toman **cuentas restantes**, una lista de longitud variable anexada después de las cuentas fijas. Los ayudantes CPI de Anchor no verifican de tipo las cuentas restantes; pásalas a través de `.with_remaining_accounts(...)`:

```rust icon="rust"
let cpi_ctx = CpiContext::new(program_id, accounts)
    .with_remaining_accounts(ctx.remaining_accounts.to_vec());
```

El orden siempre importa, ya que el programa receptor itera las cuentas restantes en el orden que las pasas. Dos órdenes confirmadas:

- **CLMM `SwapV2`**: [arrays de tick](#applying-the-pattern-clmm), ordenados direccionalmente.
- **Farm v6**: pares `(reward_vault, user_reward_ata)`, pero solo desde la segunda secuencia de recompensas en adelante; consulta [Farm v6](#farm-v6) para ver qué muestra la decodificación de una transacción real.

## Aplicar el patrón: CLMM

`SwapV2` sigue [el patrón general](#the-general-anchor-cpi-pattern) anterior con una lista de cuentas diferente y un requisito de cuentas restantes para arrays de tick. El módulo `#[program]` de la crate se llama `raydium_clmm`, que también es su ruta de `use` de Rust.

<Warning>
  **La estructura de cuentas CPI se llama `SwapSingleV2`, no `SwapV2`.** `SwapV2` es el nombre de *instrucción* en cadena.
</Warning>

```rust icon="rust"
use raydium_clmm::cpi::{self, accounts::SwapSingleV2 as ClmmSwap};

#[derive(Accounts)]
pub struct MyProxyClmmSwap<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: validado por CLMM
    pub amm_config: UncheckedAccount<'info>,
    /// CHECK: ídem
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub input_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_token_account: Account<'info, TokenAccount>,
    #[account(mut)]
    pub input_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub output_vault: Account<'info, TokenAccount>,

    /// CHECK: PDA de observación
    #[account(mut)]
    pub observation_state: UncheckedAccount<'info>,

    pub token_program: Program<'info, Token>,
    pub token_program_2022: Program<'info, anchor_spl::token_2022::Token2022>,
    /// CHECK: programa de memo SPL, requerido para algunas rutas de Token-2022
    pub memo_program: UncheckedAccount<'info>,

    pub input_vault_mint: Account<'info, Mint>,
    pub output_vault_mint: Account<'info, Mint>,

    /// Tipado como `Program<T>` en lugar de `UncheckedAccount`, por la misma razón que
    /// `cpmm_program` de CPMM en el patrón general anterior: es el programa invocado, y
    /// `Program<T>` verifica su dirección automáticamente.
    pub clmm_program: Program<'info, raydium_clmm::program::RaydiumClmm>,
    // remaining_accounts: tick_array_bitmap_extension (si el recorrido lo necesita), luego
    // tantas cuentas tick_array como el rango de precio esperado del swap abarque.
}
```

Calcula la lista de arrays de tick de la misma manera que lo hace el SDK, a través de una cotización contra el estado actual del pool, en lugar de adivinar un conteo fijo; un swap que supera los arrays que pasaste se revierte con `TickArrayNotFound` (consulta [`products/clmm/instructions`](/es/products/clmm/instructions) para la tabla de cuentas completa y la lista de errores). Pásalos en la dirección del recorrido de precio: primer array en dirección de swap primero.

## Aplicar el patrón: LaunchLab

LaunchLab está basado en Anchor e IDL-publicado: [`raydium_launchpad/raydium_launchpad.json`](https://github.com/raydium-io/raydium-idl/blob/master/raydium_launchpad/raydium_launchpad.json) en el repositorio público `raydium-idl`. El identificador de metadatos internos de ese IDL es `raydium_launchpad`, un nombre técnico para el programa subyacente, no un nombre alternativo para el producto. A diferencia de CPMM y CLMM, sin embargo, **la fuente del programa en sí no está disponible públicamente** (consulta [`reference/program-addresses`](/es/reference/program-addresses)). No hay dependencia `git = "..."` a la que apuntar Cargo, y no hay fuente para confirmar cuál sería la ruta de `use` de Rust de una crate real.

Genera enlaces desde el IDL publicado usando la macro `declare_program!` de Anchor. Guarda el JSON del IDL como `idls/raydium_launchpad.json` en tu crate (Cargo busca un directorio `idls/` relativo a `CARGO_MANIFEST_DIR`), luego `declare_program!(raydium_launchpad);` genera estructuras `raydium_launchpad::cpi::accounts::<Ix>` y funciones `cpi::<ix>()` directamente desde el IDL, sin fuente de programa requerida. El nombre de la estructura de cuentas generada es siempre el nombre de instrucción en PascalCase (`buy_exact_in` → `BuyExactIn`), y los nombres de campo coinciden exactamente con los nombres de cuenta del IDL, la misma lista de cuentas ya utilizada en `MyProxyBuy` a continuación.

La forma CPI sigue [el patrón general](#the-general-anchor-cpi-pattern). La lista de cuentas y argumentos a continuación provienen de la instrucción `buy_exact_in` del IDL en cadena, no de `products/launchlab/instructions.mdx`:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_spl::token::{Token, TokenAccount, Mint};
use raydium_launchpad::cpi::{self, accounts::BuyExactIn};

#[derive(Accounts)]
pub struct MyProxyBuy<'info> {
    #[account(mut)]
    pub payer: Signer<'info>,

    /// CHECK: PDA, semillas = [b"vault_auth_seed"], validado por el programa
    pub authority: UncheckedAccount<'info>,

    /// CHECK: validado por el programa
    pub global_config: UncheckedAccount<'info>,
    /// CHECK: validado por el programa
    pub platform_config: UncheckedAccount<'info>,

    /// CHECK: validado por el programa
    #[account(mut)]
    pub pool_state: UncheckedAccount<'info>,

    #[account(mut)]
    pub user_base_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub user_quote_token: Account<'info, TokenAccount>,
    #[account(mut)]
    pub base_vault: Account<'info, TokenAccount>,
    #[account(mut)]
    pub quote_vault: Account<'info, TokenAccount>,

    pub base_token_mint: Account<'info, Mint>,
    pub quote_token_mint: Account<'info, Mint>,

    /// CHECK: programa de token del mint base (Token SPL o Token-2022, dependiendo del mint)
    pub base_token_program: UncheckedAccount<'info>,
    /// Tipado como `Program<Token>` en lugar de `UncheckedAccount`: el IDL fija esto a
    /// Token SPL clásico específicamente (a diferencia de base_token_program anterior), por lo que la
    /// verificación de dirección incorporada de Anchor en `Program<Token>` es suficiente por sí sola.
    pub quote_token_program: Program<'info, Token>,

    /// CHECK: PDA, semillas = [b"__event_authority"], requerido por el patrón emit_cpi! del programa
    pub event_authority: UncheckedAccount<'info>,
    /// CHECK: la cuenta del programa en sí, requerida junto con event_authority
    pub program: UncheckedAccount<'info>,
}

pub fn my_proxy_buy(
    ctx: Context<MyProxyBuy>,
    amount_in: u64,
    minimum_amount_out: u64,
    share_fee_rate: u64,
) -> Result<()> {
    let cpi_accounts = BuyExactIn {
        payer:               ctx.accounts.payer.to_account_info(),
        authority:           ctx.accounts.authority.to_account_info(),
        global_config:       ctx.accounts.global_config.to_account_info(),
        platform_config:     ctx.accounts.platform_config.to_account_info(),
        pool_state:          ctx.accounts.pool_state.to_account_info(),
        user_base_token:     ctx.accounts.user_base_token.to_account_info(),
        user_quote_token:    ctx.accounts.user_quote_token.to_account_info(),
        base_vault:          ctx.accounts.base_vault.to_account_info(),
        quote_vault:         ctx.accounts.quote_vault.to_account_info(),
        base_token_mint:     ctx.accounts.base_token_mint.to_account_info(),
        quote_token_mint:    ctx.accounts.quote_token_mint.to_account_info(),
        base_token_program:  ctx.accounts.base_token_program.to_account_info(),
        quote_token_program: ctx.accounts.quote_token_program.to_account_info(),
        event_authority:     ctx.accounts.event_authority.to_account_info(),
        program:             ctx.accounts.program.to_account_info(),
    };
    // `program` actúa como el objetivo CPI aquí: la propia cuenta de LaunchLab es tanto una de
    // las cuentas requeridas de su instrucción (para su patrón emit_cpi!) como el programa
    // que CpiContext::new invoca.
    let cpi_ctx = CpiContext::new(
        *ctx.accounts.program.key,
        cpi_accounts,
    );

    cpi::buy_exact_in(cpi_ctx, amount_in, minimum_amount_out, share_fee_rate)?;
    Ok(())
}
```

Después de la graduación, el programa de destino es CPMM o AMM v4 dependiendo de `pool_state.migrate_type`, que `products/launchlab/accounts.mdx` dice que se establece en el momento de `Initialize`. Tu lista de cuentas CPI tiene que estar preparada para cualquiera, o necesitas leer `migrate_type` de `PoolState` primero y ramificar.

## Propagación de errores

Cada programa de Raydium basado en Anchor devuelve su propio enum de error; Anchor los envuelve, por lo que tu programa que llama los ve como `Err(ProgramError::Custom(code))`. Para manejar errores específicos:

```rust icon="rust"
use raydium_cp_swap::error::ErrorCode as CpmmErr;

match cpi::swap_base_input(cpi_ctx, amount_in, minimum_amount_out) {
    Ok(_) => Ok(()),
    Err(e) => {
        msg!("El swap de CPMM falló: {:?}", e);
        // Re-lanzar, o convertir a tu propio tipo de error.
        Err(e)
    }
}
```

Intercambia el tipo de error relevante para el programa que estás llamando (`raydium_clmm::error::ErrorCode` para CLMM, y así sucesivamente). Los números de código de error son estables según la política de IDL ([`sdk-api/anchor-idl`](/es/sdk-api/anchor-idl#idl-change-policy)), por lo que puedes probar contra códigos específicos comparando contra el valor numérico. Tablas de errores completas: [CPMM](/es/reference/error-codes#cpmm-standard-amm-errors), [CLMM](/es/reference/error-codes#clmm-errors), [AMM v4, Farm v6 y LaunchLab](/es/reference/error-codes#amm-v4-farm-v3-/-v5-/-v6-launchlab-errors).

## Presupuesto de cómputo en CPIs compuestos

Cada marco CPI tiene sobrecarga, y el consumo de CU propio del llamado se apila encima del tuyo, por lo que una transacción que llama a Raydium desde dentro de tu programa necesita un presupuesto de cómputo explícito en lugar de confiar en el límite predeterminado de 200k CU.

<Note>
  **Medido, no estimado.** Un `swap_base_input` de CPMM en mainnet consume **~23,000 CU** en el programa CPMM en sí — muestreado el 2026-09-09 en ocho swaps en vivo en un pool de alto volumen (22,721–23,052), leído de la línea de registro `Program CPMMoo8… consumed N of M compute units`. Para comparación: swap de AMM v4 ~26,000; `swap` de CLMM ~41,000; `swap_v2` de CLMM ~48,000 (43,838–52,887), aumentando con cada cruce de tick.

  Una revisión anterior de esta página reportaba ~47,700 CU para un CPI de proxy-swap. Esa cifra era la *transacción completa* (`computeUnitsConsumed`), que incluye tu propio programa, el marco CPI y cualquier configuración de ATA — no el costo del llamado. Ambos son útiles, pero no son el mismo número, así que compara como con como. Mide tu propia transacción en lugar de presupuestar de cualquiera.
</Note>

Los CPIs de CLMM y LaunchLab cuestan más (CLMM en particular recorre arrays de tick adicionales a través de `remaining_accounts`, agregando CU por array), pero solo la cifra de CPMM anterior es un valor medido. Siempre establece un límite explícito de `ComputeBudgetProgram::set_compute_unit_limit(...)` dimensionado desde tu propia medición, no un número copiado de la documentación, ya que el límite predeterminado de 200k CU se agotará silenciosamente y los costos por instrucción cambian a medida que los programas se actualizan.

## AMM v4: construcción manual de instrucciones

AMM v4 es anterior a Anchor y no tiene crate CPI, lo que lo convierte en el único programa en este documento que no sigue el patrón general anterior. Construye la `Instruction` manualmente:

```rust icon="rust"
use anchor_lang::prelude::*;
use anchor_lang::solana_program::program::invoke_signed;
use anchor_lang::solana_program::instruction::{Instruction, AccountMeta};

const AMM_V4_PROGRAM_ID: Pubkey = pubkey!("675kPX9MHTjS2zt1qfr1NYHuzeLXfQM9H24wFSUt1Mp8");

// El discriminador de SwapBaseIn es 9.
let mut data = vec![9u8];
data.extend_from_slice(&amount_in.to_le_bytes());
data.extend_from_slice(&minimum_amount_out.to_le_bytes());

let ix = Instruction {
    program_id: AMM_V4_PROGRAM_ID,
    accounts: vec![
        AccountMeta::new_readonly(token_program_id, false),
        AccountMeta::new(amm_id, false),
        AccountMeta::new_readonly(amm_authority, false),
        // ... cuentas restantes según products/amm-v4/instructions ...
    ],
    data,
};
invoke_signed(&ix, &account_infos, signer_seeds)?;
```

Consulta [`products/amm-v4/code-demos`](/es/products/amm-v4/code-demos) para la lista de cuentas completa.

## Farm v6

**Usa el SDK de TS si esa es una opción para tu integración.** `raydium.farm.deposit(...)` (consulta [`products/farm-staking/code-demos`](/es/products/farm-staking/code-demos)) es ejercitado por demostraciones reales y no depende de si existe una crate de Anchor para este programa.

<Warning>
  **Farm v6 no ofrece ruta CPI de Anchor.** No hay crate `raydium_farm_v6` en crates.io, no hay repositorio de fuente pública, y no hay IDL en cadena — el programa no tiene ni una cuenta `anchor:idl` heredada ni una entrada en el programa de Metadatos del Programa (consulta [`sdk-api/anchor-idl`](/es/sdk-api/anchor-idl)). Trátalo como un programa que no es de Anchor y construye sus instrucciones manualmente, como a continuación.
</Warning>

**Si necesitas Rust CPI de todas formas**, por ejemplo componiendo desde otro programa en cadena, construye la `Instruction` manualmente, de la misma manera que [AMM v4](#amm-v4-manual-instruction-construction): deriva la lista de cuentas real y los discriminadores de instrucción de forma independiente, por ejemplo decodificando los diseños de TypeScript del SDK (`raydium-sdk-V2`'s farm module), decodificando transacciones reales directamente (consulta a continuación), o volcando y desensambla el programa desplegado.

Para la forma de instrucción sin argumentos consistente con una llamada de cosecha o reclamación, el orden de cuenta real es un prefijo fijo (`token_program`, la cuenta de estado del farm, un PDA de autoridad de bóveda, la primera bóveda de recompensa de ese PDA, un segundo PDA, el llamador, y el ATA del llamador para ese primer mint de recompensa), seguido de pares `(reward_vault_i, user_reward_ata_i)` en `remaining_accounts` para cada secuencia de recompensa después de la primera. La convención de emparejamiento es real, pero solo comienza en la segunda secuencia de recompensa: la bóveda y ATA de la primera secuencia son cuentas fijas, no adyacentes entre sí, y no son parte de `remaining_accounts` en absoluto.

## Probar un flujo CPI

El desarrollo local requiere que los programas de Raydium estén disponibles en tu validador de prueba. Tres opciones:

1. **`anchor test` con clonación de programa.** Extrae bytecode desplegado en mainnet a tu validador local; consulta [Clonar programas en un validador local](#cloning-programs-into-a-local-validator) a continuación para la configuración de `Anchor.toml` y dos cosas que causan problemas en pruebas de creación de pool específicamente.
2. **Devnet.** Raydium despliega la mayoría de los programas a devnet, pero en **IDs de programa diferentes que mainnet** para cada programa (CPMM, CLMM, AMM v4, Stable AMM y LaunchLab cada uno tienen una dirección devnet distinta; consulta la tabla Devnet en [`reference/program-addresses`](/es/reference/program-addresses)). Farm v3/v5/v6 no se publican de manera confiable en devnet; la API en vivo (`https://api-v3-devnet.raydium.io/main/info`) tiene la imagen actual. Si usas constantes `DEVNET_PROGRAM_ID` incluidas en `raydium_clmm` (o el equivalente para otras crates), no asumas que un ID de mainnet también funciona en devnet. Ejecuta `anchor test --provider.cluster devnet` para golpear código en vivo una vez que tengas las direcciones correctas.
3. **Despliegue local.** Clona los repositorios de Raydium (CPMM, CLMM; la fuente de LaunchLab no está disponible para esta opción) y `anchor deploy` a un validador local. Agrega sobrecarga de ciclo de prueba pero te permite modificar el llamado para depuración.

Ejecuta con `anchor test`, o `anchor build` primero y `anchor test --skip-build` después si estás iterando en el archivo de prueba sin cambiar el programa.

### Clonar programas en un validador local

```toml icon="file-code"
[test]
# El predeterminado (5s) no es suficiente una vez que estés clonando varias cuentas, ya que cada una es
# un viaje RPC de mainnet secuencial durante el inicio del validador.
startup_wait = 60000

[test.validator]
url = "https://api.mainnet-beta.solana.com"

[[test.validator.clone]]
address = "CAMMCzo5YL8w4VFF8KVHrK22GGUsp5VTaW7grrKgrWqK"  # CLMM

[[test.validator.clone]]
address = "CPMMoo8L3F4NbTegBCKVNunggL7H1ZpdTHKxQB5qKP1C"  # CPMM

[[test.validator.clone]]
address = "LanMV9sAd7wArD4vJFi2qDdfnVhFxYSUg6eADduJ3uj"   # LaunchLab

[[test.validator.clone]]
address = "FarmqiPv5eAj3j1GMdMCMUGXqPUvmquZtMy86QH6rzhG"  # Farm v6
```

Esto funciona por ID de programa independientemente de si la fuente del programa es pública, por lo que LaunchLab se clona de la misma manera que CPMM y CLMM incluso aunque su fuente no esté disponible. `reference/program-addresses` es la fuente de verdad para cada dirección aquí.

<Warning>
  **Clonar el programa no es suficiente si tu prueba también *crea* un pool** (en lugar de hacer swap contra uno que ya existe). La instrucción `initialize` de CPMM valida sus cuentas `amm_config` y `create_pool_fee` contra datos reales en cadena, por lo que también necesitas clonar esas, o `initialize` falla directamente. Para CPMM específicamente: clona el `AmmConfig` de nivel de tarifa que desees (obtén su dirección de `GET https://api-v3.raydium.io/main/cpmm-config`, el índice 0 es el nivel de 0.25%) y la [cuenta de token receptora de tarifa](/es/reference/program-addresses#shared-config-/-pda-conventions), validada por dirección exacta, no creada sobre la marcha, por lo que ya debe existir.
</Warning>

<Warning>
  **Un pool que tu prueba acaba de crear no es intercambiable en el mismo instante.** La instrucción `initialize` de CPMM anula silenciosamente un `open_time` solicitado que no está estrictamente en el futuro (`if open_time <= block_timestamp { open_time = block_timestamp + 1 }`), por lo que incluso `startTime: 0` («abierto inmediatamente», según el SDK) deja una brecha real de ≥1 segundo antes de que el pool acepte swaps. Una prueba que crea un pool e inmediatamente hace swap contra él golpeará [`NotApproved`](/es/reference/error-codes#cpmm-standard-amm-errors). Una breve `await` (1–2s) entre la creación del pool y el primer swap es suficiente. Esto es específico de las pruebas; un humano ejecutando dos comandos manuales separados normalmente no lo notaría, ya que escribir e iniciar procesos ya consumen más de un segundo.
</Warning>
