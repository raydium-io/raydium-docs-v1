<Note>
  **No hay instrucción de inicialización de matriz de tick, y ninguna es necesaria.** Una matriz de tick se crea *dentro de*
  `OpenPosition*` / `IncreaseLiquidity*` por `TickArrayState::get_or_create_tick_array`, pagada por
  `payer`. Pasa el PDA de matriz de tick (posiblemente aún no inicializado, propiedad del sistema) como
  `tick_array_lower` / `tick_array_upper` y el programa lo asigna si falta.
  `OpenLimitOrder` hace lo mismo para su único `tick_array`.
</Note>

La mayoría de instrucciones solo de administrador (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) están controladas por la clave `admin` codificada del programa. `CreatePermissionPda` / `ClosePermissionPda` aceptan la clave `admin` **o** una clave `permission_pda_admin` dedicada; `CreateSupportMintAssociated` / `CloseSupportMintAssociated` aceptan la clave `admin` **o** una clave de propietario de mint de soporte dedicada; `CollectExcessLamports` acepta la clave `admin` **o** una billetera de recopilación de lamports dedicada. Las instrucciones de administrador de flujo de recompensas (`TransferRewardOwner`, `CollectRemainingRewards`) están controladas por el financiador de recompensas, no por el administrador del programa.

El sufijo V2 significa "soporta Token-2022 en bóvedas / NFT, requiere ranura de extensión de mapa de bits". El SDK elige V2 por defecto para nuevos pools.

## `CreatePool`

**Argumentos**

```
sqrt_price_x64: u128           // precio inicial
open_time:      u64            // swaps rechazados antes de este tiempo
```

**Cuentas (abreviadas)**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Nivel de comisión elegido. |
| 3 | `pool_state` | W |   | `init` aquí. |
| 4 | `token_mint_0` |   |   | Ordenado. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` aquí, propiedad del PDA de autoridad del pool. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` aquí. |
| 9 | `tick_array_bitmap` | W |   | El PDA `TickArrayBitmapExtension`; `init` aquí. |
| 10 | `token_program_0` |   |   | El programa que posee `token_mint_0` — SPL Token **o** Token-2022. |
| 11 | `token_program_1` |   |   | El programa que posee `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Las ranuras 10 y 11 son **por mint**, no "SPL Token luego Token-2022". Cada una está restringida por
  `mint::token_program` en el mint coincidente, así que para un pool cuyo `token_mint_0` es Token-2022 y
  `token_mint_1` es SPL clásico debes pasar Token-2022 en la ranura 10 y SPL Token en la ranura 11.
  `CreateCustomizablePool` y `CreatePermissionedPool` usan las mismas dos ranuras.
</Warning>

**Precondiciones**

- `token_mint_0 < token_mint_1` por orden de bytes.
- `amm_config.disable_create_pool == false`.
- Los mints no son rechazados por la lista de permisos de extensión Token-2022.

**Postcondiciones**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (sin posiciones aún).
- `pool_state.fee_on = FromInput` (predeterminado heredado).
- `pool_state.dynamic_fee_info` está en cero (comisión dinámica deshabilitada).

## `CreateCustomizablePool`

Recomendado para nuevos pools. Mismo efecto que `CreatePool` más modo de recopilación de comisiones por pool y una opción de comisión dinámica opcional.

**Argumentos**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Cuentas** — exactamente las 13 cuentas declaradas de `CreatePool`. `dynamic_fee_config` **no** es una cuenta declarada.

<Warning>
  Cuando `enable_dynamic_fee = true`, el `DynamicFeeConfig` a capturar debe suministrarse como la
  **última** `remaining_account` — el manejador lee `ctx.remaining_accounts.last()`. Cualquier
  PDA de derivación `SupportMintAssociated` debe por lo tanto venir *antes* que ella, o el programa captura
  la cuenta incorrecta y falla la deserialización. Omitirla mientras la bandera está establecida falla con
  `AccountLack`.
</Warning>

**Precondiciones** — igual que `CreatePool`. Si `enable_dynamic_fee = false`, no se requiere `remaining_account` y cualquiera que se pase solo se escanea para registros de mint de soporte.

**Postcondiciones**

- `pool_state.fee_on` establecido en la variante `CollectFeeOn` elegida.
- Si la comisión dinámica fue habilitada: `pool_state.dynamic_fee_info` se inicializa desde el `DynamicFeeConfig` suministrado (cinco parámetros de calibración copiados; campos de estado en cero).
- De lo contrario: `pool_state.dynamic_fee_info` está en cero (= comisión dinámica inactiva para siempre en este pool).

`fee_on` y la bandera de habilitación de comisión dinámica se establecen **solo** en la creación del pool. No hay actualización in situ — los pools creados a través del `CreatePool` heredado no pueden obtener retroactivamente comisión dinámica o comisión de un solo lado. Las nuevas implementaciones deben usar esta instrucción por defecto.

## `CreatePermissionedPool`

Tanto `CreatePool` como `CreateCustomizablePool` derivan el PDA del pool de `["pool", amm_config, token_mint_0, token_mint_1]`, así que hay exactamente **un** dirección de pool canónica por triple `(config, mint0, mint1)` — un segundo `init` en las mismas semillas falla. `CreatePermissionedPool` levanta esa restricción plegando un `seed_index: u16` suministrado por el cliente en las semillas del PDA del pool, permitiendo **múltiples pools para el mismo par y nivel de comisión** — cada uno en su propia dirección. Porque una dirección de pool arbitraria es una capacidad privilegiada, el pagador debe tener un PDA `Permission` que lo autorice.

Todo lo demás sobre el pool es idéntico a `CreateCustomizablePool`: toma los mismos `CreateCustomizableParams` y soporta comisión de un lado y la opción de comisión dinámica.

**Argumentos**

```rust
customizable_params: CreateCustomizableParams   // misma estructura que CreateCustomizablePool
seed_index:          u16                          // debe ser distinto de cero; plegado en las semillas del PDA del pool
```

**Cuentas (abreviadas)** — igual que `CreateCustomizablePool` más, al frente:

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` | W | S | Paga la renta. Debe ser la autoridad del PDA `permission` abajo. |
| 2 | `pool_creator` |   |   | Registrado como `pool_state.owner`. Puede diferir de `payer`. |
| 3 | `permission` |   |   | PDA `["permission", payer]`. Anchor rechaza la llamada si no existe / no es propiedad del programa. |
| … | (`amm_config`, `pool_state`, mints, bóvedas, `observation_state`, `tick_array_bitmap`, programas de token/sistema) | | | Como en `CreateCustomizablePool`. |

El PDA `pool_state` se deriva de `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`.

**Precondiciones**

- `seed_index != 0`. Un `seed_index` de `0` está reservado para pools heredados y se rechaza aquí; el componente de semilla `[0, 0]` es lo que hace que una dirección de pool heredada se colapse a la forma de cuatro semillas clásica.
- El PDA `permission` para `payer` existe (creado por un administrador a través de `CreatePermissionPda`).
- Mismas reglas de mint / lista de permisos que `CreatePool`.

**Postcondiciones**

- Un nuevo `pool_state` existe en la dirección derivada de `seed_index`, con `pool_state.seed_index = seed_index`.
- Todo otro post-estado coincide con `CreateCustomizablePool` (modo de comisión, comisión dinámica opcional).

<Note>
  Esta instrucción **no** amplía el acceso general de creación de pools — la creación sin permisos continúa a través de `CreatePool` / `CreateCustomizablePool`, que permanecen como un pool por par. `CreatePermissionedPool` existe para el caso específico donde un operador en la lista blanca necesita varios pools para el mismo par (p. ej. precios iniciales o cohortes de lanzamiento diferentes) y tiene un PDA `Permission` otorgado por el administrador.
</Note>

## `OpenPositionV2` / `OpenPositionWithToken22Nft`

Crea una nueva posición dentro de un pool existente.

**Argumentos**

```
tick_lower_index: i32
tick_upper_index: i32
tick_array_lower_start_index: i32
tick_array_upper_start_index: i32
liquidity:  u128              // L deseada (o 0 para usar montos abajo)
amount_0_max: u64
amount_1_max: u64
with_metadata: bool           // escribe metadatos NFT (Metaplex)
base_flag: Option<bool>       // true = ajusta a amount0; false = ajusta a amount1
```

**Cuentas** — las dos variantes tienen listas de cuentas *diferentes*. `OpenPositionV2` declara 22; `OpenPositionWithToken22Nft` declara 20.

`OpenPositionV2`, en orden:

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` | W | S | |
| 2 | `position_nft_owner` |   |   | |
| 3 | `position_nft_mint` | W | S | Keypair fresco. |
| 4 | `position_nft_account` | W |   | ATA del propietario para el NFT. |
| 5 | `metadata_account` | W |   | PDA de metadatos de Metaplex. Declarado **incondicionalmente**, incluso cuando `with_metadata = false`. |
| 6 | `pool_state` | W |   | |
| 7 | `protocol_position` |   |   | Vestigial; `UncheckedAccount` de solo lectura. |
| 8 | `tick_array_lower` | W |   | Creado aquí si no está inicializado. |
| 9 | `tick_array_upper` | W |   | Igual. |
| 10 | `personal_position` | W |   | Creado aquí. |
| 11 | `token_account_0` | W |   | ATA de fuente del usuario. |
| 12 | `token_account_1` | W |   | |
| 13 | `token_vault_0` | W |   | |
| 14 | `token_vault_1` | W |   | |
| 15 | `rent` |   |   | |
| 16 | `system_program` |   |   | |
| 17 | `token_program` |   |   | |
| 18 | `associated_token_program` |   |   | |
| 19 | `metadata_program` |   |   | Metaplex Token Metadata. |
| 20 | `token_program_2022` |   |   | |
| 21 | `vault_0_mint` |   |   | |
| 22 | `vault_1_mint` |   |   | |

`OpenPositionWithToken22Nft` es la misma lista con `metadata_account` (5) y `metadata_program` (19) **removidos** — escribe los metadatos de la posición a través de la extensión de metadatos Token-2022 en el mint del NFT en su lugar — dando 20 cuentas. Su `position_nft_mint` es un `Signer` desnudo y `position_nft_account` un `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` no es una cuenta declarada en ninguna variante.** Cuando el rango de la posición cae fuera del `tick_array_bitmap` en línea del pool (±512 matrices de tick), agrega el PDA `TickArrayBitmapExtension` en semillas `["pool_tick_array_bitmap_extension", pool_state]` como `remaining_accounts[0]`.
</Warning>

**Matemática** — consulta [`products/clmm/math`](/es/products/clmm/math). Dado `base_flag`, el programa resuelve `liquidity` o `(amount_0_max, amount_1_max)` en la `L` real y los montos de token reales consumidos.

**Precondiciones**

- `tick_lower < tick_upper`, ambos múltiplos de `pool.tick_spacing`, dentro de `[MIN_TICK, MAX_TICK]`.
- Los dos PDAs de matriz de tick se pasan. **No** necesitan existir ya — `get_or_create_tick_array` asigna uno faltante a expensas de `payer` dentro de esta instrucción. No hay instrucción separada de inicialización de matriz de tick.
- El usuario tiene al menos `amount_0_max` y `amount_1_max` en los ATAs de fuente.

**Postcondiciones**

- `personal_position` existe, `liquidity` establecida, `fee_growth_inside_last` capturada.
- Entradas de matriz de tick en `tick_lower` y `tick_upper` actualizadas (`liquidity_gross += L`, `liquidity_net ± L`, instantáneas de crecimiento de comisión mantenidas).
- `pool_state.liquidity += L` si la posición está en rango (`tick_lower ≤ tick_current < tick_upper`).
- El mint del NFT de la posición registra `pool_state` como autoridad de congelación. La autoridad de acuñación se elimina después de que se acuña el único NFT. Registrar la autoridad de congelación no cambia el estado de la cuenta de token del NFT.
- La cuenta de token del NFT permanece descongelada a menos que la instrucción sea `OpenPositionV2` u `OpenPositionWithToken22Nft` **y** la autoridad de congelación de cualquier mint de bóveda coincida con la lista de emisores restringidos de CLMM. Solo esa ruta V2 coincidente congela la cuenta. `OpenPosition` V1 no congela.

**Errores comunes** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (un extremo no es múltiplo de `tick_spacing`), `InvalidTickIndex` (fuera de `[MIN_TICK, MAX_TICK]`), `MissingTickArrayBitmapExtensionAccount` (rango fuera del mapa de bits en línea y la extensión no fue agregada), `NotApproved` (`pool_state.status` bloquea la apertura), `ZeroAmountSpecified`.

<Note>
  La congelación de posición no agrega cuentas de instrucción declaradas o argumentos. Los clientes pueden abrir estas posiciones con los diseños V2 existentes. El comportamiento se selecciona en cadena desde `vault_0_mint` y `vault_1_mint`.
</Note>

**Efecto**

| # | Nombre | W | S |
|---|--------|---|---|
| 1 | `nft_owner` |   | S |
| 2 | `nft_account` |   |   |
| 3 | `personal_position` | W |   |
| 4 | `pool_state` | W |   |
| 5 | `protocol_position` |   |   |
| 6 | `token_vault_0` | W |   |
| 7 | `token_vault_1` | W |   |
| 8 | `tick_array_lower` | W |   |
| 9 | `tick_array_upper` | W |   |
| 10 | `recipient_token_account_0` | W |   |
| 11 | `recipient_token_account_1` | W |   |
| 12 | `token_program` |   |   |
| 13 | `token_program_2022` |   |   |
| 14 | `memo_program` |   |   |
| 15 | `vault_0_mint` |   |   |
| 16 | `vault_1_mint` |   |   |

**Cuentas restantes** — tres por recompensa activa siendo recopilada, en el orden `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`. Antepone el PDA `TickArrayBitmapExtension` cuando el rango de la posición está fuera del mapa de bits en línea.

<Note>
  Esta es también la **única** forma de recopilar comisiones y recompensas. Para recopilar sin cambiar la
  posición, llámala con `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`.
</Note>

**Efecto**

- Calcula `(amount_0, amount_1)` para la `L` removida dado el `sqrt_price_x64` actual.
- Liquida comisiones/recompensas acumuladas desde el último toque, igual que `IncreaseLiquidity`.
- Transfiere `amount_0 + fees_owed_0` y `amount_1 + fees_owed_1` fuera de las bóvedas al usuario.
- Disminuye los contadores de liquidez; si el nuevo `personal_position.liquidity == 0`, la posición es elegible para `ClosePosition`.

**Deslizamiento** — `amount_0_min` y `amount_1_min` son los mínimos que el usuario acepta netos de comisiones de transferencia Token-2022 en el lado de salida.

## `ClosePosition`

Quema el NFT de posición y cierra `PersonalPositionState`.

**Cuentas declaradas**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `nft_owner` | W | S | Debe poseer la cuenta de token del NFT que contiene cantidad `1`. |
| 2 | `position_nft_mint` | W |   | Debe coincidir con `personal_position.nft_mint`. |
| 3 | `position_nft_account` | W |   | Cuenta del propietario del NFT; puede ser SPL Token clásico o Token-2022. |
| 4 | `personal_position` | W |   | Cerrado a `nft_owner`. |
| 5 | `system_program` |   |   | Cierra el estado de posición. |
| 6 | `token_program` |   |   | Debe poseer el mint y la cuenta de token del NFT. |

**Cuentas restantes**

- NFT descongelado: ninguno requerido; una cuenta de pool extra es inofensiva porque el manejador no la lee.
- NFT congelado: agrega `personal_position.pool_id` como la primera cuenta restante. El programa lo carga como `PoolState` y usa sus semillas de PDA para firmar el descongelamiento.

**Precondiciones**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Todos los contadores de recompensas `reward_amount_owed == 0`.

(Es decir, recopila todo y disminuye a cero primero.)

**Efecto**

- Si la cuenta de token del NFT está congelada, verifica que la primera cuenta restante sea igual a `personal_position.pool_id`, luego la descongela con el PDA del pool.
- Quema el NFT.
- Cierra la cuenta de token del NFT y `personal_position`, reembolsando renta a `nft_owner`. Si el NFT de posición usa Token-2022, también cierra el mint del NFT; los mints de SPL Token clásico no pueden cerrarse y permanecen con suministro cero.

El descongelamiento, quema y cierre son atómicos. El NFT no puede volverse transferible entre esos pasos.

**Ruptura condicional del cliente** — el diseño IDL declarado no cambia, así que los clientes heredados continúan cerrando posiciones existentes y descongeladas. Un constructor heredado que omite la cuenta de pool restante falla con `AccountLack` al cerrar una posición congelada. Pasar el pool para cada cierre es la estrategia compatible más simple.

## `SwapV2`

Camina la curva de liquidez; entrada exacta *o* salida exacta dependiendo de `is_base_input`.

**Argumentos**

```
amount: u64                  // entrada si is_base_input=true, salida de lo contrario
other_amount_threshold: u64  // mín. salida o máx. entrada
sqrt_price_limit_x64: u128   // límite duro; 0 ⇒ sin límite
is_base_input: bool
```

**Cuentas (abreviadas)**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2. |
| 11 | `memo_program` |   |   | V2 (requerido para algunas rutas Token-2022). |
| 12 | `input_vault_mint`, `output_vault_mint` |   |   | V2. |
| 13 | `tick_array_bitmap_extension` (opcional) | W |   | Si el swap camina hacia la extensión. |
| 14+ | `tick_array` (restantes) | W |   | Suficientes matrices para abarcar el rango esperado del recorrido. |

Los llamadores pasan una lista clasificada de matrices de tick que cubren el recorrido de swap esperado; el programa usa tantas como necesita. El SDK calcula esta lista a través de `PoolUtils.computeAmountOutFormat` o el punto final de cotización de la API.

**Precondiciones**

- `pool_state.status` permite swap.
- `now >= open_time`.
- `sqrt_price_limit_x64` está en el lado correcto de `sqrt_price_x64` para la dirección.

**Errores comunes** — `TooLittleOutputReceived` (deslizamiento exacto en), `TooMuchInputPaid` (deslizamiento exacto fuera), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (bit de swap establecido en `pool_state.status`). CLMM no tiene variante `ExceededSlippage` — ese nombre es de CPMM — y no tiene `TickArrayNotFound`.

**Lo que `SwapV2` hace internamente que los llamadores deben saber** (lanzamiento posterior a 2025):

1. **Recargo de comisión dinámica** — si `pool.dynamic_fee_info` es distinto de cero, el programa actualiza el acumulador de volatilidad usando la distancia de tick recorrida desde el último swap (con las reglas de filtro/decaimiento de [`products/clmm/fees`](/es/products/clmm/fees)) y agrega un `dynamic_fee_component` encima de `AmmConfig.trade_fee_rate`. La comisión total está limitada al 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Coincidencia de órdenes limitadas** — cuando el recorrido de precio cruza un tick que contiene órdenes limitadas abiertas, el programa primero completa la liquidez de orden limitada disponible en ese tick (FIFO por `order_phase`), luego procede a lo largo de la curva de liquidez de LP. Los montos completados actualizan `tick.unfilled_ratio_x64` y `tick.part_filled_orders_remaining` para liquidación posterior; las órdenes en sí permanecen no gastadas hasta que su propietario llama a `SettleLimitOrder`.
3. **Enrutamiento de comisión de un lado** — cuando `pool.fee_on = Token0Only` o `Token1Only`, el paso de swap aún calcula el mismo comercio entrada-salida; la comisión se enruta entonces al lado configurado. Para direcciones donde el lado de comisión configurado es la salida, la comisión se deduce de la salida del swap (el usuario recibe `out − fee`); para direcciones donde es la entrada, el comportamiento coincide con `FromInput`. Consulta `is_fee_on_input(zero_for_one)` e `is_fee_on_token0(zero_for_one)` en `PoolState`.

`Swap` (V1) implementa la misma comisión dinámica, enrutamiento de comisión de un lado y coincidencia de órdenes limitadas que `SwapV2`; la única característica que le falta es soporte Token-2022 — ambas bóvedas deben ser SPL Token clásico. Los pools con cualquier mint Token-2022 deben ser intercambiados a través de `SwapV2`. El agregador y SDK ya prefieren V2 para cada rama CLMM así que los llamadores no tienen que ramificarse en tipo de mint.

## `OpenLimitOrder`

Coloca una orden de venta en un tick específico. La orden se sienta en una cohorte FIFO por tick y se completa cuando el precio camina pasado.

**Argumentos**

```
nonce_index:    u8       // índice de cuenta nonce elegido por el usuario (0..255 por billetera)
zero_for_one:   bool     // true: vende token0 por token1; false: vende token1 por token0
tick_index:     i32      // debe ser múltiplo de pool.tick_spacing
amount:         u64      // monto de token de entrada
```

**Cuentas (abreviadas)**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` | W | S | Propietario de la orden; paga renta. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | La matriz de tick que contiene `tick_index`. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — creado en la primera orden del usuario bajo este `nonce_index`. |
| 5 | `limit_order` | W |   | PDA. `init` aquí. |
| 6 | `input_token_account` | W |   | ATA de entrada del usuario. Verificado para `frozen`. |
| 7 | `output_token_account` | W |   | ATA de **salida** del usuario. No debitado en apertura — requerido solo para que el programa confirme que no está `frozen` (es decir, el relleno puede entregarse después). |
| 8 | `input_vault` | W |   | Bóveda de entrada del pool. |
| 9 | `output_vault` | W |   | Bóveda de salida del pool. Identifica el mint de salida para las verificaciones `output_token_account` / `output_vault_mint`. |
| 10 | `input_vault_mint` |   |   | Manejo de comisión Token-2022. |
| 11 | `output_vault_mint` |   |   | Mint del lado de salida (emparejamiento de verificación congelada). |
| 12 | `input_token_program` |   |   | SPL o Token-2022. |
| 13 | `system_program` |   |   | Financia `limit_order`, `limit_order_nonce` y — si es necesario — la asignación de `tick_array`. |

**Cuentas restantes** — `[0]` `tick_array_bitmap_extension`, requerido solo cuando se inicializa una matriz de tick cuyo índice de inicio cae fuera del mapa de bits en línea del pool. No pases nada de lo contrario.

<Warning>
  No hay **cuenta `rent`**: la estructura termina en `system_program`, 13 cuentas declaradas. Un `rent` extraviado
  en la posición 14 cae exactamente donde se lee la extensión de mapa de bits opcional, así que la orden
  parece funcionar hasta la primera vez que una matriz de tick fuera del mapa de bits en línea tiene que ser creada —
  y luego falla.
</Warning>

<Note>
  **Cambio de lista de cuentas (lanzamiento 2026-07).** `OpenLimitOrder` ahora también toma las cuentas del **lado de salida** — `output_token_account`, `output_vault` y `output_vault_mint` — además del lado de entrada. Se usan solo para validación: el programa rechaza la orden si la cuenta de token de entrada **o** salida del propietario está congelada. Esto garantiza que un relleno pueda ser liquidado a la ATA de salida del propietario, lo que importa para mints Token-2022 de lista de permisos / congelados por defecto (p. ej. tokens permisionados) donde una cuenta puede no estar aún descongelada. Los clientes construidos contra la lista de cuentas de un solo lado anterior deben agregar las tres cuentas de salida.
</Note>

**Precondiciones**

- Ni `input_token_account` ni `output_token_account` están congelados (de lo contrario `NotApproved`).
- `pool_state.status` permite tanto swap (bit 4) como operaciones de orden limitada (bit 5) (de lo contrario `NotApproved`).
- `tick_index % pool.tick_spacing == 0` y dentro de `[MIN_TICK, MAX_TICK]`.
- `tick_index` está en el **lado correcto de `pool.tick_current`** para la dirección elegida (vender token0 → tick debe estar arriba del actual, y viceversa). Vender en un tick ya cruzado sería coincidido inmediatamente y se rechaza.

**Postcondiciones**

- `limit_order` existe, capturando `tick.order_phase` y `tick.unfilled_ratio_x64` en tiempo de apertura.
- `tick.orders_amount += amount` (en la cohorte actual).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` emitido.

**Errores comunes** — `NotApproved` (cuenta de token de entrada o salida congelada, o el pool tiene swap / orden limitada deshabilitada), `ZeroAmountSpecified` (`amount == 0` después de la comisión de transferencia del lado de entrada), `InvalidLimitOrderAmount` (el monto produciría una salida por debajo de 1 unidad base en ese tick, u overflow `u64`), `InvalidTickIndex` (fuera de `[MIN_TICK, MAX_TICK]`, o en el lado incorrecto de `tick_current` para la dirección elegida), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `CollectExcessLamports`

Barrido de administrador de lamports por encima del mínimo exento de renta en cuentas que CLMM controla. Se agregó en la actualización 2026-09 para reclamar el exceso de financiamiento que la [reducción de renta SIMD-0437](/es/solana-fundamentals/rent-and-reclaimable-rent) deja en cuentas creadas antes de cada paso.

Solo el exceso se mueve. Los saldos de token, datos de cuenta, propietarios, estado del pool y la curva de precio no se tocan. Una cuenta ya en su mínimo se deja como está, así que la instrucción puede ser re-ejecutada de forma segura después de cada paso de lanzamiento.

**Argumentos**: ninguno.

**Cuentas**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Recibe cada lamport barrido. Debe ser el administrador del programa CLMM o la billetera de recopilación de lamports dedicada (consulta [`reference/program-addresses`](/es/reference/program-addresses#excess-lamports-collection-wallets)). Cualquier otro firmante falla con `NotApproved`. |
| 2 | `pool_state` | W |   | El pool siendo barrido. Sus semillas de PDA firman los CPIs del programa de token, y la cuenta siempre se barre a sí misma. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Ambos programas son requeridos; la instrucción elige uno por cuenta de fuente. |
| 5.. | `remaining_accounts` | W |   | `M` cuentas de fuente, cualquier número, cualquier orden. |

**Alcance: un pool por llamada.** CLMM no tiene autoridad de bóveda a nivel de programa. Las bóvedas de cada pool son propiedad de su propio `PoolState`. Cada fuente del programa de token debe por lo tanto tener el `pool_state` en la ranura 2 como su autoridad: `token_vault_0`, `token_vault_1`, o una de las bóvedas de recompensas de ese pool. Si pasas la bóveda de otro pool o una cuenta de token de usuario, la verificación de propietario del programa de token falla y toda la instrucción se revierte. No se salta. Los mints de NFT de posición no pueden ser barridos, porque su autoridad de acuñación se revoca cuando se abre la posición.

**Cómo se maneja cada cuenta de fuente**

El programa hace dos pasadas sobre `remaining_accounts`: cada CPI del programa de token primero, luego los débitos directos. Intercalar los dos aborta con el error `UnbalancedInstruction` del tiempo de ejecución, así que el orden se fija en el programa y no tienes que ordenar la lista tú mismo.

| Pasada | Propietario de cuenta de fuente | Manejo |
|---|---|---|
| 1 | Cuenta de token no nativa de SPL Token o Token-2022 | CPI `WithdrawExcessLamports` (discriminante del programa de token `38`), firmado por `pool_state`. |
| 1 | Cuenta de token **nativa** (wSOL) de SPL Token o Token-2022 | `WithdrawExcessLamports` rechaza cuentas nativas. El programa CPIs `SyncNative`, mide cuánto creció el `amount` envuelto, y llama a `UnwrapLamports` (discriminante `45`) para exactamente ese delta. Luego requiere que el saldo envuelto sea igual a su valor pre-sincronización, o falla con `LamportsCalculateError` (`6052`). Una bóveda de pool del lado SOL mantiene su liquidez completa. |
| 2 | `pool_state` (ranura 2) | Debitado directamente hasta `rent.minimum_balance(data_len)`. |
| 2 | El programa CLMM: `AmmConfig`, `ObservationState`, `TickArrayBitmapExtension`, `TickArrayState`, `PersonalPositionState`, `LimitOrderState`, y así sucesivamente | Debitado directamente hasta `rent.minimum_balance(data_len)`. La cuenta **no** tiene que pertenecer al pool en la ranura 2. |
| — | Cualquier otra cosa | **Saltado silenciosamente.** Sin error, sin lamports movidos. |

<Warning>
  **La pasada 2 cubre cuentas cuya renta pagó un usuario.** Un `PersonalPositionState` o `LimitOrderState` pasado aquí renuncia a su exceso como cualquier otra cuenta propiedad de CLMM. Permanece exento de renta y mantiene sus datos. Cuando se cierra más tarde, el propietario recupera lo que la cuenta contiene en ese punto, que después de un barrido es el mínimo de renta actual.
</Warning>

El tamaño de la transacción es el límite real de cuántas fuentes caben en una llamada. Es la misma restricción que el barrido del lado de la billetera descrito en [`solana-fundamentals/rent-and-reclaimable-rent`](/es/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**Errores comunes**:
- `NotApproved` (`6000`): firmante incorrecto.
- `LamportsCalculateError` (`6052`): el viaje redondo de wSOL no neteó a cero.
- Un error de falta de coincidencia de propietario del programa de token: una fuente de token no es propiedad de `pool_state`.
