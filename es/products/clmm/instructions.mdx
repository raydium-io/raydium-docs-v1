<Note>
  **No hay instrucción de inicialización de matriz de ticks, y ninguna es necesaria.** Una matriz de ticks se crea *dentro de*
  `OpenPosition*` / `IncreaseLiquidity*` por `TickArrayState::get_or_create_tick_array`, pagada por
  `payer`. Pasa el PDA de matriz de ticks (posiblemente aún no inicializado, propiedad del sistema) como
  `tick_array_lower` / `tick_array_upper` y el programa lo asigna si falta.
  `OpenLimitOrder` hace lo mismo para su único `tick_array`.
</Note>

La mayoría de instrucciones solo de administrador (`CreateAmmConfig`, `UpdateAmmConfig`, `UpdatePoolStatus`, `CreateOperationAccount`, `UpdateOperationAccount`, `CloseProtocolPosition`) están protegidas por la clave pública `admin` codificada del programa. `CreateSupportMintAssociated` / `CloseSupportMintAssociated` aceptan la clave pública `admin` **o** una clave de propietario de mint de soporte dedicada; `CollectExcessLamports` acepta la clave pública `admin` **o** una billetera de recopilación de lamports dedicada. Las instrucciones de administrador de flujo de recompensas (`TransferRewardOwner`, `CollectRemainingRewards`) están protegidas por el financiador de recompensas, no por el administrador del programa.

El sufijo V2 significa "soporta Token-2022 en bóvedas / NFT, requiere ranura de extensión de mapa de bits". El SDK elige V2 por defecto para nuevos pools.

**Argumentos**

```
sqrt_price_x64: u128           // precio inicial

```

**Cuentas (abreviadas)**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `pool_creator` | W | S | |
| 2 | `amm_config` |   |   | Nivel de comisión elegido. |
| 3 | `pool_state` | W |   | `init` aquí. |
| 4 | `token_mint_0` |   |   | Ordenado. |
| 5 | `token_mint_1` |   |   | |
| 6 | `token_vault_0` | W |   | `init` aquí, propiedad del PDA de autoridad del pool. |
| 7 | `token_vault_1` | W |   | |
| 8 | `observation_state` | W |   | `init` aquí. |
| 9 | `tick_array_bitmap` | W |   | El PDA `TickArrayBitmapExtension`; `init` aquí. |
| 10 | `token_program_0` |   |   | El programa que posee `token_mint_0` — Token SPL **o** Token-2022. |
| 11 | `token_program_1` |   |   | El programa que posee `token_mint_1`. |
| 12 | `system_program` |   |   | |
| 13 | `rent` |   |   | |

<Warning>
  Las ranuras 10 y 11 son **por mint**, no "Token SPL luego Token-2022". Cada una está restringida por
  `mint::token_program` en el mint correspondiente, por lo que para un pool cuyo `token_mint_0` es Token-2022 y
  `token_mint_1` es SPL clásico debes pasar Token-2022 en la ranura 10 y Token SPL en la ranura 11.
  `CreateCustomizablePool` y `CreateCustomizablePoolV2` usan las mismas dos ranuras.
</Warning>

**Precondiciones**

- `token_mint_0 < token_mint_1` por orden de bytes.
- `amm_config.disable_create_pool == false`.
- Los mints no son rechazados por la lista de permisos de extensión Token-2022.

**Postcondiciones**

- `pool_state.sqrt_price_x64 = sqrt_price_x64`, `tick_current = floor(log_{1.0001}(price))`.
- `pool_state.liquidity = 0` (sin posiciones aún).
- `pool_state.fee_on = FromInput` (predeterminado heredado).
- `pool_state.dynamic_fee_info` está en cero (comisión dinámica deshabilitada).

## `CreateCustomizablePool`

Recomendado para nuevos pools. Mismo efecto que `CreatePool` más modo de recopilación de comisión por pool y una opción de comisión dinámica opcional.

**Argumentos**

```rust
pub struct CreateCustomizableParams {
    pub sqrt_price_x64:    u128,
    pub collect_fee_on:    CollectFeeOn,   // FromInput | Token0Only | Token1Only
    pub enable_dynamic_fee: bool,
}
```

**Cuentas** — exactamente las 13 cuentas declaradas de `CreatePool`. `dynamic_fee_config` **no** es una cuenta declarada.

<Warning>
  Cuando `enable_dynamic_fee = true`, el `DynamicFeeConfig` a capturar debe suministrarse como la
  **última** `remaining_account` — el manejador lee `ctx.remaining_accounts.last()`. Cualquier
  PDA de derivación `SupportMintAssociated` debe por lo tanto venir *antes* que ella, o el programa captura
  la cuenta incorrecta y falla la deserialización. Omitirla mientras la bandera está establecida falla con
  `AccountLack`.
</Warning>

**Precondiciones** — igual que `CreatePool`. Si `enable_dynamic_fee = false`, no se requiere `remaining_account` y cualquiera que se pase solo se escanea para registros de mint de soporte.

**Postcondiciones**

- `pool_state.fee_on` establecido en la variante `CollectFeeOn` elegida.
- Si la comisión dinámica fue habilitada: `pool_state.dynamic_fee_info` se inicializa desde el `DynamicFeeConfig` suministrado (cinco parámetros de calibración copiados; campos de estado en cero).
- De lo contrario: `pool_state.dynamic_fee_info` está en cero (= comisión dinámica inactiva para siempre para este pool).

`fee_on` y la bandera de habilitación de comisión dinámica se establecen **solo** en la creación del pool. No hay actualización in situ — los pools creados a través del `CreatePool` heredado no pueden obtener retroactivamente comisión dinámica o comisión de un lado. Las nuevas implementaciones deben usar esta instrucción por defecto.

## `CreateCustomizablePoolV2`

Tanto `CreatePool` como `CreateCustomizablePool` derivan el PDA del pool a partir de `["pool", amm_config, token_mint_0, token_mint_1]`, por lo que existe exactamente **una** dirección de pool canónica por cada tupla `(config, mint0, mint1)` — un segundo `init` con las mismas semillas falla. `CreateCustomizablePoolV2` elimina esa restricción al incorporar un `seed_index: u16` suministrado por el cliente en las semillas del PDA del pool, permitiendo **múltiples pools para el mismo par y nivel de comisión** — cada uno en su propia dirección. Cualquiera puede llamarlo.

Todo lo demás sobre el pool es idéntico a `CreateCustomizablePool`: toma los mismos `CreateCustomizableParams` y admite comisión de un solo lado y la opción de comisión dinámica.

<Note>
  Hasta la [actualización del 2026-10-22](/es/reference/changelog/2026-10-22-clmm-customizable-pool-v2), esta instrucción se llamaba `CreatePermissionedPool` y requería que el pagador tuviera un PDA de `Permission` emitido por un administrador. La actualización la renombró, eliminó la cuenta `permission` y borró la maquinaria de permisos. El discriminador cambió con el nombre, por lo que los clientes compilados contra `CreatePermissionedPool` deben reconstruirse.
</Note>

**Argumentos**

```rust
customizable_params: CreateCustomizableParams   // misma estructura que CreateCustomizablePool
seed_index:          u16                          // debe ser distinto de cero; se incorpora en las semillas del PDA del pool
```

**Cuentas**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` | W | S | Paga la renta de cada cuenta nueva. Cualquier billetera. |
| 2 | `pool_creator` |   |   | Se registra como `pool_state.owner`. Puede diferir de `payer`. No es un firmante y no se verifica. |
| 3 | `amm_config` |   |   | Nivel de comisión al que se vincula el pool. |
| 4 | `pool_state` | W |   | `init` en `["pool", amm_config, token_mint_0, token_mint_1, seed_index.to_le_bytes()]`. |
| 5 | `token_mint_0` |   |   | Debe ordenarse antes de `token_mint_1`. |
| 6 | `token_mint_1` |   |   | |
| 7 | `token_vault_0` | W |   | PDA `["pool_vault", pool_state, token_mint_0]`. |
| 8 | `token_vault_1` | W |   | PDA `["pool_vault", pool_state, token_mint_1]`. |
| 9 | `observation_state` | W |   | PDA `["observation", pool_state]`. |
| 10 | `tick_array_bitmap` | W |   | PDA `["pool_tick_array_bitmap_extension", pool_state]`. |
| 11 | `token_program_0` |   |   | Programa que posee `token_mint_0`. |
| 12 | `token_program_1` |   |   | Programa que posee `token_mint_1`. |
| 13 | `system_program` |   |   | |
| 14 | `rent` |   |   | |

`remaining_accounts`: los PDAs del registro de mints de soporte cuando un mint de Token-2022 los necesita, y el `DynamicFeeConfig` **al final** cuando `enable_dynamic_fee = true` — como en `CreateCustomizablePool`.

**Precondiciones**

- `seed_index != 0`. Un `seed_index` de `0` está reservado para pools heredados y se rechaza aquí; el componente de semilla `[0, 0]` es lo que hace que la dirección de un pool heredado se reduzca a la forma clásica de cuatro semillas.
- No existe ningún pool en la dirección derivada.
- Las mismas reglas de mint y lista de permitidos que `CreatePool`.

**Postcondiciones**

- Existe un nuevo `pool_state` en la dirección derivada de `seed_index`, con `pool_state.seed_index = seed_index`.
- Todo el resto del estado posterior coincide con `CreateCustomizablePool` (modo de comisión, comisión dinámica opcional).

<Warning>
  Dado que `pool_creator` no se verifica, cualquier pagador puede escribir cualquier dirección en `pool_state.owner`. Esa dirección puede llamar a `InitializeReward` en el pool, pero no es prueba de quién creó el pool. Los integradores no deben etiquetar ni clasificar pools V2 por su `owner`.
</Warning>

Crea una nueva posición dentro de un pool existente.

**Argumentos**

```

`OpenPositionWithToken22Nft` es la misma lista con `metadata_account` (5) y `metadata_program` (19) **eliminados** — escribe los metadatos de la posición a través de la extensión de metadatos de Token-2022 en el mint del NFT en su lugar — dando 20 cuentas. Su `position_nft_mint` es un `Signer` simple y `position_nft_account` es un `UncheckedAccount`.

<Warning>
  **`tick_array_bitmap_extension` no es una cuenta declarada en ninguna de las dos variantes.** Cuando el rango de la posición cae fuera del `tick_array_bitmap` en línea del pool (±512 arrays de ticks), añade el PDA `TickArrayBitmapExtension` en las semillas `["pool_tick_array_bitmap_extension", pool_state]` como `remaining_accounts[0]`.
</Warning>

**Matemáticas** — ver [`products/clmm/math`](/es/products/clmm/math). Dado `base_flag`, el programa resuelve `liquidity` o `(amount_0_max, amount_1_max)` en la `L` real y los montos de token reales consumidos.

**Precondiciones**

- `tick_lower < tick_upper`, ambos múltiplos de `pool.tick_spacing`, dentro de `[MIN_TICK, MAX_TICK]`.
- Se pasan los dos PDAs de arrays de ticks. **No** necesitan existir ya — `get_or_create_tick_array` asigna uno faltante en `payer`'s expense dentro de esta instrucción. No hay una instrucción separada de inicialización de arrays de ticks.
- El usuario tiene al menos `amount_0_max` y `amount_1_max` en los ATAs de origen.

**Postcondiciones**

- `personal_position` existe, `liquidity` establecida, `fee_growth_inside_last` capturada.
- Las entradas del array de ticks en `tick_lower` y `tick_upper` se actualizan (`liquidity_gross += L`, `liquidity_net ± L`, snapshots de crecimiento de comisión mantenidos).
- `pool_state.liquidity += L` si la posición está en rango (`tick_lower ≤ tick_current < tick_upper`).
- El mint del NFT de la posición registra `pool_state` como autoridad de congelación. La autoridad de acuñación se elimina después de que se acuña el único NFT. Registrar la autoridad de congelación no cambia el estado de la cuenta de token del NFT.
- La cuenta de token del NFT permanece descongelada a menos que la instrucción sea `OpenPositionV2` u `OpenPositionWithToken22Nft` **y** la autoridad de congelación de cualquiera de los mints de bóveda coincida con la lista de emisores restringidos de CLMM. Solo esa ruta V2 coincidente congela la cuenta. `OpenPosition` V1 no congela.

**Errores comunes** — `TickInvalidOrder` (`tick_lower >= tick_upper`), `TickAndSpacingNotMatch` (un extremo no es múltiplo de `tick_spacing`), `InvalidTickIndex` (fuera de `[MIN_TICK, MAX_TICK]`), `MissingTickArrayBitmapExtensionAccount` (rango fuera del bitmap en línea y la extensión no fue añadida), `NotApproved` (`pool_state.status` bloquea la apertura), `ZeroAmountSpecified`.

<Note>
  La congelación de posiciones no añade cuentas de instrucción declaradas ni argumentos. Los clientes pueden abrir estas posiciones con los layouts V2 existentes. El comportamiento se selecciona en cadena a partir de `vault_0_mint` y `vault_1_mint`.
</Note>

**Cuentas restantes** — tres por cada recompensa activa siendo recaudada, en el orden `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`. Antepone el PDA `TickArrayBitmapExtension` cuando el rango de la posición está fuera del bitmap en línea.

<Note>
  Esta es también la **única** forma de recaudar comisiones y recompensas. Para recaudar sin cambiar la posición, llámala con `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`.
</Note>

**Efecto**

- Calcula `(amount_0, amount_1)` para la `L` eliminada dado el `sqrt_price_x64` actual.
- Liquida comisiones/recompensas acumuladas desde el último toque, igual que `IncreaseLiquidity`.
- Transfiere `amount_0 + fees_owed_0` y `amount_1 + fees_owed_1` fuera de las bóvedas al usuario.
- Decrementa los contadores de liquidez; si el nuevo `personal_position.liquidity == 0`, la posición es elegible para `ClosePosition`.

**Slippage** — `amount_0_min` y `amount_1_min` son los mínimos que el usuario acepta netos de comisiones de transferencia de Token-2022 en el lado de salida.

## `ClosePosition`

Quema el NFT de posición y cierra `PersonalPositionState`.

**Cuentas declaradas**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `nft_owner` | W | S | Debe ser propietario de la cuenta de token NFT con cantidad `1`. |
| 2 | `position_nft_mint` | W |   | Debe coincidir con `personal_position.nft_mint`. |
| 3 | `position_nft_account` | W |   | Cuenta del propietario del NFT; puede ser Token SPL clásico o Token-2022. |
| 4 | `personal_position` | W |   | Se cierra a `nft_owner`. |
| 5 | `system_program` |   |   | Cierra el estado de la posición. |
| 6 | `token_program` |   |   | Debe ser propietario del mint del NFT y de la cuenta de token. |

**Cuentas restantes**

- NFT no congelado: ninguna requerida; una cuenta de pool adicional es inofensiva porque el manejador no la lee.
- NFT congelado: añade `personal_position.pool_id` como la primera cuenta restante. El programa la carga como `PoolState` y usa sus semillas PDA para firmar el descongelamiento.

**Precondiciones**

- `personal_position.liquidity == 0`.
- `tokens_fees_owed_{0,1} == 0`.
- Todos los contadores de recompensas `reward_amount_owed == 0`.

(Es decir, recopila todo y disminuye a cero primero.)

**Efecto**

- Si la cuenta de token del NFT está congelada, verifica que la primera cuenta restante sea igual a `personal_position.pool_id`, luego la descongela con el PDA del pool.
- Quema el NFT.
- Cierra la cuenta de token del NFT y `personal_position`, reembolsando la renta a `nft_owner`. Si el NFT de posición usa Token-2022, también cierra el mint del NFT; los mints de Token SPL clásico no pueden cerrarse y permanecen con suministro cero.

El descongelamiento, quema y cierre son atómicos. El NFT no puede volverse transferible entre esos pasos.

**Ruptura de cliente condicional** — el diseño IDL declarado no cambia, por lo que los clientes heredados continúan cerrando posiciones existentes y no congeladas. Un constructor heredado que omita la cuenta de pool restante falla con `AccountLack` al cerrar una posición congelada. Pasar el pool para cada cierre es la estrategia compatible más simple.

**Argumentos**

other_amount_threshold: u64  // mín. salida o máx. entrada
sqrt_price_limit_x64: u128   // límite duro; 0 ⇒ sin límite

```

**Cuentas (resumidas)**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` |   | S | |
| 2 | `amm_config` |   |   | |
| 3 | `pool_state` | W |   | |
| 4 | `input_token_account` | W |   | |
| 5 | `output_token_account` | W |   | |
| 6 | `input_vault` | W |   | |
| 7 | `output_vault` | W |   | |
| 8 | `observation_state` | W |   | |
| 9 | `token_program` |   |   | |
| 10 | `token_program_2022` |   |   | V2. |
| 11 | `memo_program` |   |   | V2 (requerido para algunas rutas de Token-2022). |
| 12 | `input_vault_mint`, `output_vault_mint` |   |   | V2. |
| 13 | `tick_array_bitmap_extension` (opcional) | W |   | Si el swap entra en la extensión. |
| 14+ | `tick_array` (restantes) | W |   | Suficientes arrays para abarcar el rango esperado del recorrido. |

Los llamadores pasan una lista clasificada de arrays de ticks que cubren el recorrido de swap esperado; el programa usa tantos como necesita. El SDK calcula esta lista mediante `PoolUtils.computeAmountOutFormat` o el endpoint de cotización de la API.

**Precondiciones**

- `pool_state.status` permite swap.
- `now >= open_time`.
- `sqrt_price_limit_x64` está en el lado correcto de `sqrt_price_x64` para la dirección.

**Errores comunes** — `TooLittleOutputReceived` (slippage entrada exacta), `TooMuchInputPaid` (slippage salida exacta), `SqrtPriceLimitOverflow`, `NotEnoughTickArrayAccount`, `InvalidFirstTickArrayAccount`, `MissingTickArrayBitmapExtensionAccount`, `LiquidityInsufficient`, `NotApproved` (bit de swap establecido en `pool_state.status`). CLMM no tiene variante `ExceededSlippage` — ese nombre es de CPMM — ni `TickArrayNotFound`.

**Lo que `SwapV2` hace internamente que los llamadores deben saber** (lanzamiento posterior a 2025):

1. **Recargo de tarifa dinámica** — si `pool.dynamic_fee_info` es distinto de cero, el programa actualiza el acumulador de volatilidad usando la distancia de tick recorrida desde el último swap (con las reglas de filtro/decaimiento de [`products/clmm/fees`](/es/products/clmm/fees)) y añade un `dynamic_fee_component` además de `AmmConfig.trade_fee_rate`. La tarifa total está limitada al 10% (`MAX_FEE_RATE_NUMERATOR / 1_000_000`).
2. **Coincidencia de órdenes limitadas** — cuando el recorrido de precio cruza un tick que contiene órdenes limitadas abiertas, el programa primero llena la liquidez de órdenes limitadas disponible en ese tick (FIFO por `order_phase`), luego procede a lo largo de la curva de liquidez de LP. Los montos llenados actualizan `tick.unfilled_ratio_x64` y `tick.part_filled_orders_remaining` para liquidación posterior; las órdenes en sí permanecen sin gastar hasta que su propietario llama a `SettleLimitOrder`.
3. **Enrutamiento de tarifa unilateral** — cuando `pool.fee_on = Token0Only` o `Token1Only`, el paso de swap aún calcula el mismo comercio entrada-salida; la tarifa se enruta entonces al lado configurado. Para direcciones donde el lado de tarifa configurado es la salida, la tarifa se deduce de la salida del swap (el usuario recibe `out − fee`); para direcciones donde es la entrada, el comportamiento coincide con `FromInput`. Consulta `is_fee_on_input(zero_for_one)` e `is_fee_on_token0(zero_for_one)` en `PoolState`.

`Swap` (V1) implementa la misma tarifa dinámica, enrutamiento de tarifa unilateral y coincidencia de órdenes limitadas que `SwapV2`; la única característica que le falta es soporte para Token-2022 — ambas bóvedas deben ser Token SPL clásico. Los pools con cualquier mint de Token-2022 deben intercambiarse mediante `SwapV2`. El agregador y el SDK ya prefieren V2 para cada rama CLMM, por lo que los llamadores no tienen que ramificarse según el tipo de mint.

## `OpenLimitOrder`

Coloca una orden de venta en un tick específico. La orden se sienta en una cohorte FIFO por tick y se llena cuando el precio la cruza.

**Argumentos**

```
nonce_index:    u8       // índice de cuenta nonce elegido por el usuario (0..255 por billetera)
zero_for_one:   bool     // verdadero: vender token0 por token1; falso: vender token1 por token0
tick_index:     i32      // debe ser múltiplo de pool.tick_spacing
amount:         u64      // cantidad de token de entrada
```

**Cuentas (resumidas)**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `payer` | W | S | Propietario de la orden; paga renta. |
| 2 | `pool_state` | W |   | |
| 3 | `tick_array` | W |   | El array de ticks que contiene `tick_index`. |
| 4 | `limit_order_nonce` | W |   | PDA. `init_if_needed` — creada en la primera orden del usuario bajo este `nonce_index`. |
| 5 | `limit_order` | W |   | PDA. `init` aquí. |
| 6 | `input_token_account` | W |   | ATA de entrada del usuario. Verificada por `frozen`. |
| 7 | `output_token_account` | W |   | ATA de **salida** del usuario. No se debita al abrir — requerida solo para que el programa confirme que no está `frozen` (es decir, el llenado puede entregarse después). |
| 8 | `input_vault` | W |   | Bóveda de entrada del pool. |
| 9 | `output_vault` | W |   | Bóveda de salida del pool. Identifica el mint de salida para las verificaciones `output_token_account` / `output_vault_mint`. |
| 10 | `input_vault_mint` |   |   | Manejo de tarifa Token-2022. |
| 11 | `output_vault_mint` |   |   | Mint del lado de salida (emparejamiento de verificación congelada). |
| 12 | `input_token_program` |   |   | SPL o Token-2022. |
| 13 | `system_program` |   |   | Financia `limit_order`, `limit_order_nonce` y — si es necesario — la asignación de `tick_array`. |

**Cuentas restantes** — `[0]` `tick_array_bitmap_extension`, requerida solo cuando se inicializa un array de ticks cuyo índice de inicio cae fuera del bitmap en línea del pool. No pases nada en caso contrario.

<Warning>
  No hay **cuenta `rent`**: la estructura termina en `system_program`, 13 cuentas declaradas. Un `rent` extraviado en la posición 14 cae exactamente donde se lee la extensión de bitmap opcional, por lo que la orden parece funcionar hasta la primera vez que un array de ticks fuera del bitmap en línea tiene que crearse — y luego falla.
</Warning>

<Note>
  **Cambio de lista de cuentas (lanzamiento 2026-07).** `OpenLimitOrder` ahora también toma las cuentas del **lado de salida** — `output_token_account`, `output_vault` y `output_vault_mint` — además del lado de entrada. Se usan solo para validación: el programa rechaza la orden si la cuenta de token de entrada **o** salida del propietario está congelada. Esto garantiza que un llenado pueda liquidarse realmente a la ATA de salida del propietario, lo que importa para mints de Token-2022 con lista de permitidos / congelados por defecto (por ejemplo, tokens con permisos) donde una cuenta puede no estar aún descongelada. Los clientes construidos contra la lista de cuentas unilateral más antigua deben añadir las tres cuentas de salida.
</Note>

**Precondiciones**

- Ni `input_token_account` ni `output_token_account` están congeladas (en caso contrario `NotApproved`).
- `pool_state.status` permite tanto operaciones de swap (bit 4) como de orden limitada (bit 5) (en caso contrario `NotApproved`).
- `tick_index % pool.tick_spacing == 0` y dentro de `[MIN_TICK, MAX_TICK]`.
- `tick_index` está en el **lado derecho de `pool.tick_current`** para la dirección elegida (vender token0 → tick debe estar por encima del actual, y viceversa). Vender en un tick ya cruzado sería igualado inmediatamente y se rechaza.

**Postcondiciones**

- `limit_order` existe, capturando `tick.order_phase` y `tick.unfilled_ratio_x64` en el momento de apertura.
- `tick.orders_amount += amount` (en la cohorte actual).
- `limit_order_nonce.order_nonce += 1`.
- `OpenLimitOrderEvent` emitido.

**Errores comunes** — `NotApproved` (cuenta de token de entrada o salida congelada, o el pool tiene swap / orden limitada deshabilitada), `ZeroAmountSpecified` (`amount == 0` después de la tarifa de transferencia del lado de entrada), `InvalidLimitOrderAmount` (la cantidad produciría una salida por debajo de 1 unidad base en ese tick, u overflow `u64`), `InvalidTickIndex` (fuera de `[MIN_TICK, MAX_TICK]`, o en el lado incorrecto de `tick_current` para la dirección elegida), `TickAndSpacingNotMatch` (`tick_index % pool.tick_spacing != 0`), `OrderPhaseSaturated`.

## `CollectExcessLamports`

Barrido administrativo de lamports por encima del mínimo exento de renta en cuentas que CLMM controla. Se agregó en la actualización 2026-09 para recuperar el exceso de financiamiento que la [reducción de renta SIMD-0437](/es/solana-fundamentals/rent-and-reclaimable-rent) deja en cuentas creadas antes de cada paso.

Solo se mueve el exceso. Los saldos de tokens, datos de cuenta, propietarios, estado del pool y la curva de precios no se tocan. Una cuenta ya en su mínimo se deja como está, por lo que la instrucción se puede ejecutar nuevamente de forma segura después de cada paso de implementación.

**Argumentos**: ninguno.

**Cuentas**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Recibe cada lamport barrido. Debe ser el administrador del programa CLMM o la billetera dedicada de recopilación de lamports (ver [`reference/program-addresses`](/es/reference/program-addresses#excess-lamports-collection-wallets)). Cualquier otro firmante falla con `NotApproved`. |
| 2 | `pool_state` | W |   | El pool siendo barrido. Sus semillas PDA firman los CPIs del programa de tokens, y la cuenta siempre se barre a sí misma. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Ambos programas son requeridos; la instrucción elige uno por cuenta de origen. |
| 5.. | `remaining_accounts` | W |   | `M` cuentas de origen, cualquier número, cualquier orden. |

**Alcance: un pool por llamada.** CLMM no tiene autoridad de bóveda a nivel de programa. Las bóvedas de cada pool son propiedad de su propio `PoolState`. Por lo tanto, cada fuente del programa de tokens debe tener el `pool_state` en la ranura 2 como su autoridad: `token_vault_0`, `token_vault_1`, o una de las bóvedas de recompensa de ese pool. Si pasas la bóveda de otro pool o la cuenta de token de un usuario, la verificación de propietario del programa de tokens falla y toda la instrucción se revierte. No se omite.

**Cómo se maneja cada cuenta de origen**

El programa hace dos pasadas sobre `remaining_accounts`: primero cada CPI del programa de tokens, luego los débitos directos. Intercalar los dos aborta con el error `UnbalancedInstruction` del tiempo de ejecución, por lo que el orden se fija en el programa y no tienes que ordenar la lista tú mismo.

| Pasada | Propietario de cuenta de origen | Manejo |
|---|---|---|
| 1 | Cuenta de token SPL Token o Token-2022, token no nativo | CPI `WithdrawExcessLamports` (discriminante del programa de tokens `38`), firmado por `pool_state`. |
| 1 | Cuenta de token SPL Token o Token-2022, **nativa** (wSOL) | `WithdrawExcessLamports` rechaza cuentas nativas. El programa hace CPI a `SyncNative`, mide cuánto creció el `amount` envuelto, y llama a `UnwrapLamports` (discriminante `45`) para exactamente ese delta. Luego requiere que el saldo envuelto sea igual a su valor pre-sincronización, o falla con `LamportsCalculateError` (`6052`). Una bóveda de pool del lado SOL mantiene su liquidez completa. |
| 2 | `pool_state` (ranura 2) | Debitado directamente hasta `rent.minimum_balance(data_len)`. |
| 2 | El programa CLMM: `AmmConfig`, `ObservationState`, `TickArrayBitmapExtension`, `TickArrayState`, `PersonalPositionState`, `LimitOrderState`, y así sucesivamente | Debitado directamente hasta `rent.minimum_balance(data_len)`. La cuenta **no** tiene que pertenecer al pool en la ranura 2. |
| — | Cualquier otra cosa | **Omitida silenciosamente.** Sin error, sin lamports movidos. |

<Warning>
  **La pasada 2 cubre cuentas cuya renta pagó un usuario.** Un `PersonalPositionState` o `LimitOrderState` pasado aquí cede su exceso como cualquier otra cuenta propiedad de CLMM. Permanece exento de renta y mantiene sus datos. Cuando se cierre más tarde, el propietario recupera lo que la cuenta tenga en ese momento, que después de un barrido es el mínimo de renta actual.
</Warning>

El tamaño de la transacción es el límite real de cuántas fuentes caben en una llamada. Es la misma restricción que el barrido del lado de la billetera descrito en [`solana-fundamentals/rent-and-reclaimable-rent`](/es/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**Errores comunes**:
- `NotApproved` (`6000`): firmante incorrecto.
- `LamportsCalculateError` (`6052`): el viaje de ida y vuelta de wSOL no llegó a cero.
- Un error de falta de coincidencia de propietario del programa de tokens: una fuente de token no es propiedad de `pool_state`.
- `InsufficientFunds`: una cuenta propiedad del programa tiene menos que su propio mínimo de renta.

**Sin constructor SDK.** `@raydium-io/raydium-sdk-v2` no incluye un constructor para esta ruta de administrador. Codifícalo a mano desde el IDL.

## `InitializeReward`

Agrega un nuevo flujo de recompensa a un pool. Hasta 3 flujos pueden estar activos a la vez.

**Argumentos** — una única estructura, `param: InitializeRewardParam`:

```rust
pub struct InitializeRewardParam {
    pub open_time:                u64,
    pub end_time:                 u64,
    pub emissions_per_second_x64: u128,   // Q64.64
}
```

La codificación de cable es los tres campos uno tras otro, por lo que una instrucción construida a mano no se ve afectada — pero un cliente impulsado por IDL debe pasar un objeto `param` en lugar de tres argumentos posicionales.

**Cuentas**

| # | Nombre | W | S | Notas |
|---|--------|---|---|-------|
| 1 | `reward_funder` | W | S |
| 2 | `funder_token_account` | W |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `operation_state` |   |   | PDA de estado de operación CLMM que controla la creación de recompensas. |
| 6 | `reward_token_mint` |   |   |
| 7 | `reward_token_vault` | W |   | `init` aquí. |
| 8 | `reward_token_program` |   |   |
| 9 | `system_program`, `rent` |   |   |

**Precondiciones**

- Menos de 3 flujos activos actualmente en el pool.
- El financiador deposita `total_emission = emissions_per_second × (end_time − open_time)` de token de recompensa en la bóveda como parte de esta instrucción.
- Mint de recompensa en la lista blanca por `operation_state`.

## `SetRewardParams`

Extiende, recarga o cambia la tasa de emisión en un flujo de recompensa existente. Típicamente llamado por un creador de pool o el multisig de Raydium. Las restricciones viven en cadena: generalmente puedes extender `end_time` o aumentar emisiones, no reducirlas retroactivamente. Verifica la lista de propietarios de `operation_state`.

## `UpdateRewardInfos`

Pura contabilidad — liquida `reward_growth_global_x64` al tiempo actual multiplicando `emissions_per_second × Δt / liquidity`. Llamado internamente por cada instrucción que toca liquidez. Expuesto como una instrucción independiente porque actores externos (UIs, cranks) a veces quieren activarlo.

## Recopilación de recompensas

<Warning>
  **No hay instrucción independiente de recopilación de recompensas.** El programa no expone ningún punto de entrada `CollectReward`, y el IDL publicado tampoco tiene ninguno.
</Warning>

Las recompensas adeudadas a una posición se pagan mediante `DecreaseLiquidity` / `DecreaseLiquidityV2`. Para recopilar sin cambiar la posición, llámalo con `liquidity = 0`, `amount_0_min = 0`, `amount_1_min = 0`. Las bóvedas de recompensa y las cuentas de destinatario van en `remaining_accounts` en grupos de tres por recompensa activa, en el orden `reward_token_vault(W)`, `recipient_token_account(W)`, `reward_vault_mint`.

`CollectRemainingRewards` es algo diferente: permite al financiador de recompensas, después del `end_time` de un flujo, barrer tokens que nunca se asignaron a ninguna posición.
