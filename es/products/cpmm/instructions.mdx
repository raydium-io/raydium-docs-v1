## Resumen de instrucciones

| Nombre del discriminador | Quién firma | Qué hace |
|-------|-----------|--------------|
| `Initialize` | creador del pool | Crea un nuevo pool CPMM a partir de dos mints y una `AmmConfig`. Sin permisos; cualquiera puede llamarla. Codifica `enable_creator_fee = false` en el nuevo pool. La cuenta `pool_state` puede ser la PDA canónica o un keypair aleatorio recién creado (consulta las cuentas de Initialize). |
| `InitializeWithPermission` | pagador + titular de una PDA `Permission` | Variante con permisos de `Initialize`. El llamador (`payer`) debe poseer una PDA `Permission` derivada de su propia clave pública. Utilizada por plataformas que necesitan creación de pools controlada (p. ej. graduaciones de LaunchLab). Permite al llamador fijar `creator_fee_on` (`BothToken` / `OnlyToken0` / `OnlyToken1`) y fuerza `enable_creator_fee = true` en el nuevo pool. El campo `creator` en `pool_state` se establece en una cuenta `creator` pasada por separado, no en el pagador. La misma flexibilidad de PDA-canónica-o-keypair-aleatorio para `pool_state` que en `Initialize`. |
| `Deposit` | LP | Agrega liquidez en ambos tokens; recibe tokens LP. |
| `Withdraw` | LP | Quema tokens LP; recibe ambos tokens subyacentes prorrateados. |
| `SwapBaseInput` | intercambiador | Intercambio de entrada exacta (`amount_in` dentro, ≥ `minimum_amount_out` fuera). |
| `SwapBaseOutput` | intercambiador | Intercambio de salida exacta (≤ `maximum_amount_in` dentro, `amount_out` fuera). |
| `CollectProtocolFee` | `protocol_owner` (de `AmmConfig`) | Barre las comisiones de protocolo acumuladas de los vaults. |
| `CollectFundFee` | `fund_owner` (de `AmmConfig`) | Barre las comisiones de fondo acumuladas de los vaults. |
| `CollectCreatorFee` | `pool_creator` | Barre las comisiones del creador acumuladas (si la comisión del creador estaba habilitada), neta de la parte del protocolo, que se registra en el bucket de protocolo del pool. |
| `CollectCreatorFeePermissionless` | cualquier pagador | Barre las comisiones del creador acumuladas a las cuentas de token canónicas del `pool_creator`, neta de la misma parte del protocolo. El pagador puede crear ATAs de destinatario faltantes pero no puede redirigir la transferencia. |
| `UpdatePoolStatus` | `admin` | Pausa / reanuda operaciones específicas en un pool mediante una máscara de bits. |
| `UpdateAmmConfig` | `admin` | Cambia las tasas de comisión o el propietario del protocolo/fondo en una `AmmConfig`. |
| `CreateAmmConfig` | `admin` | Crea un nuevo nivel de comisión (nueva cuenta `AmmConfig`). |
| `CreatePermissionPda` | `admin` o creador de PDA de permisos delegado | Acuña una PDA `Permission` que permite a una autoridad específica llamar a `InitializeWithPermission`. |
| `ClosePermissionPda` | `admin` o el creador dedicado de PDA de permisos | Revoca una PDA `Permission` emitida previamente. Desde la actualización 2026-09, la autoridad creadora dedicada también puede cerrar una concesión que emitió; antes era solo de administrador. |
| `CreateSupportMintAssociated` | `admin` o el propietario dedicado de mint de soporte | Registra un mint Token-2022 que de otro modo fallaría en la lista de permitidos de extensiones, creando su PDA `SupportMintAssociated`. |
| `CloseSupportMintAssociated` | `admin` o el propietario dedicado de mint de soporte | Elimina el registro de un mint. |
| `CollectExcessLamports` | `admin` o la billetera dedicada de recopilación de lamports | Barre lamports por encima del mínimo exento de renta de vaults, mints LP y PDAs controladas por CPMM. Agregada 2026-09. |
| `CreateCreatorFeeShare` | `admin` o el propietario dedicado de comisión del creador | Establece una parte de protocolo personalizada de la comisión del creador para un par `(creator, amm_config)`, anulando `AmmConfig.creator_fee_share_rate`. Agregada 2026-09-19. |
| `CloseCreatorFeeShare` | `admin` o el propietario dedicado de comisión del creador | Elimina esa anulación; el par vuelve al valor predeterminado de la configuración. Agregada 2026-09-19. |

Máscara de estado: el `status` de cada pool es un `u8` donde bit 0 = depósito deshabilitado, bit 1 = retiro deshabilitado, bit 2 = intercambio deshabilitado (`PoolStatusBitIndex { Deposit, Withdraw, Swap }` en el programa). Un bit claro significa que la operación está permitida; un bit establecido significa que está pausada. `UpdatePoolStatus` toma un `u8` sin procesar y sobrescribe el valor existente.

Las siguientes secciones detallan cada una. El orden de cuentas sigue el IDL de CPMM; el SDK y el cliente Rust en `raydium-cp-swap/programs/cp-swap/src/instructions` coinciden con este orden.

## `Initialize`

Crea un nuevo pool CPMM.

**Argumentos**

```
init_amount_0: u64
init_amount_1: u64
open_time:     u64   // Marca de tiempo Unix; intercambios rechazados antes de esto
```

**Cuentas** (W = escribible, S = firmante)

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `creator` | W | S | Paga la renta; registrada como `pool_state.pool_creator`. |
| 2 | `amm_config` |   |   | El nivel de comisión elegido. |
| 3 | `authority` |   |   | PDA de autoridad global de CPMM. |
| 4 | `pool_state` | W | S* | `init`ializada aquí. **O bien** la PDA canónica `["pool", amm_config, token_0_mint, token_1_mint]` **o** un keypair aleatorio recién creado — cuando no es la PDA canónica, el programa requiere que `pool_state` firme (`require_eq!(pool_account_info.is_signer, true)`). La ruta de keypair aleatorio permite a un creador evadir intentos de front-running en la PDA canónica. Las PDAs posteriores (`lp_mint`, `vaults`, `observation_state`) se derivan de `pool_state.key()` de cualquier forma. |
| 5 | `token_0_mint` |   |   | Ordenado: `token_0_mint < token_1_mint`. |
| 6 | `token_1_mint` |   |   | |
| 7 | `lp_mint` | W |   | `init`ializada aquí. Autoridad establecida en `authority`. |
| 8 | `creator_token_0` | W |   | ATA de origen para `init_amount_0`. |
| 9 | `creator_token_1` | W |   | ATA de origen para `init_amount_1`. |
| 10 | `creator_lp_token` | W |   | ATA del creador en `lp_mint`. `init` (no `init_if_needed`) — no debe existir ya, lo cual no puede, ya que `lp_mint` se crea en esta misma instrucción. |
| 11 | `token_0_vault` | W |   | `init`ializada aquí. Propiedad de `authority`. |
| 12 | `token_1_vault` | W |   | |
| 13 | `create_pool_fee` | W |   | ATA de destino para la `create_pool_fee` pagada por el creador. |
| 14 | `observation_state` | W |   | `init`ializada aquí. |
| 15 | `token_program` |   |   | SPL Token (para mint LP). |
| 16 | `token_0_program` |   |   | SPL Token o Token-2022. |
| 17 | `token_1_program` |   |   | SPL Token o Token-2022. |
| 18 | `associated_token_program` |   |   | |
| 19 | `system_program` |   |   | |
| 20 | `rent` |   |   | |

`*` `pool_state` firma solo en la ruta de keypair aleatorio; la ruta de PDA canónica se ejecuta sin que `pool_state` firme.

**Precondiciones**

- Los mints están ordenados (`token_0_mint < token_1_mint` por orden de bytes).
- Ningún mint utiliza una extensión fuera de la lista de permitidos de CPMM (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) — consulta [`products/cpmm/accounts`](/es/products/cpmm/accounts#vaults-and-token-2022). Un mint cuya PDA `SupportMintAssociated` (semilla `[b"support_mint", mint]`) existe omite la verificación de extensión — **pero debes agregar esa PDA a `remaining_accounts`**. El programa solo escanea las cuentas que pasas y nunca carga la PDA por sí solo, por lo que confiar en el registro sin proporcionar la cuenta aún falla con `NotSupportMint` (`6007`). El orden no importa (la coincidencia es por clave); pasa una entrada por mint que necesita el bypass. Ese registro es el único bypass desde que la actualización 2026-09 eliminó la lista blanca de cuatro mints codificada.
- `creator` tiene al menos `init_amount_0` e `init_amount_1` en las respectivas ATAs.
- `amm_config.disable_create_pool == false`.

**Postcondiciones**

- `pool_state.lp_supply = sqrt(init_amount_0 * init_amount_1)` — la raíz cuadrada **completa**. El creador recibe `lp_supply − 100`; las 100 unidades base bloqueadas se cuentan en `lp_supply` pero nunca se acuñan.
- Entonces `lp_mint.supply == pool_state.lp_supply − 100` durante la vida del pool. Toda la matemática de participación LP (depósito, retiro) divide por `lp_supply`, así que usa ese campo y no sustituyas el suministro en cadena del mint. Revierte con `InitLpAmountTooLess` si `sqrt(...) < 100`.
- `observation_state` se inicializa; `observation_index = 0` y `pool_id = pool_state.key()`.
- Los lamports de `create_pool_fee` se transfieren del creador al receptor y se sincronizan como SOL nativo (es una ATA wSOL).
- La máscara de estado del pool es `0` (depósito / retiro / intercambio todos habilitados).
- `enable_creator_fee = false` y `creator_fee_on = BothToken`. `Initialize` **no** admite habilitar la comisión del creador — esa ruta es `InitializeWithPermission`.
- `open_time` se aumenta a `block_timestamp + 1` si el llamador pasó un valor `<= block_timestamp`. Los intercambios se rechazan antes de `open_time`; los depósitos y retiros funcionan inmediatamente.

**Errores comunes** (lista completa en [`reference/error-codes`](/es/reference/error-codes))

- `InvalidInput` — mints desordenados o mints idénticos.
- `NotSupportMint` — extensión Token-2022 bloqueada.
- `ExceededSlippage` — raramente; si `init_amount_0/1` resultan en cero LP debido a desajuste de decimales.

## `Deposit`

Agrega liquidez en ambos tokens proporcional al pool.

**Argumentos**

```
lp_token_amount:   u64   // cuántos tokens LP acuñar para el LP
maximum_token_0:   u64
maximum_token_1:   u64
```

**Cuentas**

| # | Nombre | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `owner_lp_token` | W |   |
| 5 | `token_0_account` | W |   |
| 6 | `token_1_account` | W |   |
| 7 | `token_0_vault` | W |   |
| 8 | `token_1_vault` | W |   |
| 9 | `token_program` |   |   |
| 10 | `token_program_2022` |   |   |
| 11 | `vault_0_mint` |   |   |
| 12 | `vault_1_mint` |   |   |
| 13 | `lp_mint` | W |   |

**Matemáticas**

```
total_0 = vault_0 − protocol_fees_0 − fund_fees_0 − creator_fees_0    // igual para lado 1

needed_token_0 = ceil(lp_token_amount * total_0 / lp_supply)
transfer_0     = needed_token_0 + inverse_transfer_fee(needed_token_0) // Token-2022
require(transfer_0 <= maximum_token_0, "ExceededSlippage")             // igual para lado 1
```

Dos detalles que vale la pena precisar: la base prorrateada es el total del vault **excluyendo comisiones** (`vault_amount_without_fee`, es decir, el saldo sin procesar menos los contadores de comisiones acumuladas de protocolo, fondo y creador), no el saldo del vault sin procesar; y el límite de deslizamiento se verifica contra lo que el pagador realmente transfiere, *después* de que se agregue la comisión de transferencia Token-2022, no contra el movimiento bruto del vault.

Sin cambio en la proporcionalidad de `k` — ambos totales y `lp_supply` se escalan por el mismo factor.

**Postcondiciones**

- `lp_supply += lp_token_amount`.
- `vault_0 += needed_token_0` (neto de cualquier comisión de transferencia Token-2022 en la entrada).
- `vault_1 += needed_token_1` (neto de cualquier comisión de transferencia Token-2022 en la entrada).

**Errores comunes** — `ExceededSlippage`, `ZeroTradingTokens`, `InvalidStatus` si el depósito está pausado.

## `Withdraw`

Quema tokens LP y recibe ambos tokens subyacentes prorrateados.

**Argumentos**

```
lp_token_amount:   u64
minimum_token_0:   u64
minimum_token_1:   u64
```

**Cuentas**

| # | Nombre | W | S |
|---|------|---|---|
| 1 | `owner` |   | S |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `owner_lp_token` | W |   |
| 5 | `token_0_account` | W |   |
| 6 | `token_1_account` | W |   |
| 7 | `token_0_vault` | W |   |
| 8 | `token_1_vault` | W |   |
| 9 | `token_program` |   |   |
| 10 | `token_program_2022` |   |   |
| 11 | `vault_0_mint` |   |   |
| 12 | `vault_1_mint` |   |   |
| 13 | `lp_mint` | W |   |
| 14 | `memo_program` |   |   |

Las primeras 13 cuentas son idénticas a `Deposit`, y `lp_mint` es escribible porque los tokens LP se queman. `Withdraw` además toma una 14ª cuenta, `memo_program` (restringida `address = memo::ID`) — `Deposit` no. Un `Withdraw` de 13 cuentas falla la deserialización de Anchor, por lo que el LP no puede salir.

**Matemáticas**

```
total_0 = vault_0 − protocol_fees_0 − fund_fees_0 − creator_fees_0    // igual para lado 1

out_token_0     = min(total_0, floor(lp_token_amount * total_0 / lp_supply))
receive_token_0 = out_token_0 − transfer_fee(out_token_0)             // Token-2022
require(receive_token_0 >= minimum_token_0, "ExceededSlippage")       // igual para lado 1

// Como con Deposit: la base es el total del vault excluyendo comisiones, y el piso se
// verifica contra lo que el LP realmente recibe, después de la comisión de transferencia.
```

**Postcondiciones**

- `lp_supply -= lp_token_amount`.
- Los vaults envían `out_token_0` / `out_token_1` (bruto; el usuario recibe neto de cualquier comisión de transferencia Token-2022).

## `SwapBaseInput`

Intercambio de entrada exacta.

**Argumentos**

```
amount_in:            u64
minimum_amount_out:   u64
```

**Cuentas**

| # | Nombre | W | S |
|---|------|---|---|
| 1 | `payer` |   | S |
| 2 | `authority` |   |   |
| 3 | `amm_config` |   |   |
| 4 | `pool_state` | W |   |
| 5 | `input_token_account` | W |   |
| 6 | `output_token_account` | W |   |
| 7 | `input_vault` | W |   |
| 8 | `output_vault` | W |   |
| 9 | `input_token_program` |   |   |
| 10 | `output_token_program` |   |   |
| 11 | `input_token_mint` |   |   |
| 12 | `output_token_mint` |   |   |
| 13 | `observation_state` | W |   |

El orden **entrada → salida** es por la dirección del usuario, no por la `token_0 / token_1` canónica del pool. El programa determina cuál es el vault haciendo coincidir los mints.

**Matemáticas** — consulta [`products/cpmm/math`](/es/products/cpmm/math).

**Precondiciones**

- `open_time <= now`.
- `pool_status` permite intercambio.
- Ningún mint pausado o congelado para esta autoridad.
- `amount_in > 0`.

**Errores comunes**

- `ExceededSlippage` — `amount_out < minimum_amount_out`.
- `ZeroTradingTokens` — el intercambio se redondea a cero.
- `NotApproved` — el pool está pausado para intercambios mediante `UpdatePoolStatus`.
- `InvalidInput` — los mints no coinciden con ninguno de los mints del vault del pool.

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `owner` |   | S | Debe ser igual a `amm_config.protocol_owner` **o** la clave de administrador codificada del programa. |
| 2 | `authority` |   |   |
| 3 | `pool_state` | W |   |
| 4 | `amm_config` |   |   |
| 5 | `token_0_vault` | W |   |
| 6 | `token_1_vault` | W |   |
| 7 | `vault_0_mint` |   |   |
| 8 | `vault_1_mint` |   |   |
| 9 | `recipient_token_0_account` | W |   |
| 10 | `recipient_token_1_account` | W |   |
| 11 | `token_program` |   |   |
| 12 | `token_program_2022` |   |   |

**Efecto**


## `CollectFundFee`

Misma forma que `CollectProtocolFee` pero firmada por `amm_config.fund_owner` — o, nuevamente, el administrador del programa — y poniendo a cero los contadores `fund_fees_*`. Mismo `InvalidOwner` en un firmante incorrecto.

## `CollectCreatorFee`

Firmada por `pool_state.pool_creator`. Liquida la comisión del creador acumulada y transfiere la parte del creador a las cuentas de token del creador.

**Argumentos** — ninguno.

**Cuentas**

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `creator` | W | S | Restringida `address = pool_state.pool_creator`. |
| 2 | `authority` |   |   | PDA de autoridad global de vault de CPMM. |
| 3 | `pool_state` | W |   | Contiene los contadores de comisión del creador acumulados. |
| 4 | `amm_config` |   |   | Restringida `address = pool_state.amm_config`. Lleva la `creator_fee_share_rate` predeterminada. |
| 5 | `token_0_vault` | W |   | Debe coincidir con el vault de token 0 del pool. |
| 6 | `token_1_vault` | W |   | Debe coincidir con el vault de token 1 del pool. |
| 7 | `vault_0_mint` |   |   | Debe coincidir con `token_0_vault.mint`. |
| 8 | `vault_1_mint` |   |   | Debe coincidir con `token_1_vault.mint`. |
| 9 | `creator_token_0` | W |   | Destino para la parte del creador del token 0. |
| 10 | `creator_token_1` | W |   | Destino para la parte del creador del token 1. |
| 11 | `token_0_program` |   |   | SPL Token o Token-2022, coincidiendo con token 0. |
| 12 | `token_1_program` |   |   | SPL Token o Token-2022, coincidiendo con token 1. |
| 13 | `associated_token_program` |   |   | |
| 14 | `system_program` |   |   | |
| 15 | `creator_fee_share` |   |   | **Agregada 2026-09-19**, añadida después de `system_program`. PDA en `["creator_fee_share", creator, amm_config]`. Debe pasarse en cada llamada, pero **no es necesario que exista** — cuando está vacía o no es propiedad de CPMM, el programa vuelve a `amm_config.creator_fee_share_rate`. La restricción de semilla aún se aplica, por lo que la dirección debe ser la PDA canónica. |

**Efecto**

```
share_rate = creator_fee_share.share_rate   (si la cuenta existe)
           | amm_config.creator_fee_share_rate   (de otro modo)

shared_i  = floor(creator_fees_token_i * share_rate / 1_000_000)
creator_i = creator_fees_token_i - shared_i

transfer creator_i from vault_i to creator_token_i
pool_state.protocol_fees_token_i += shared_i     // permanece en el vault
pool_state.creator_fees_token_i   = 0
pool_state.recent_epoch = current epoch
```

La parte del protocolo nunca sale del vault aquí — se reetiqueta como una comisión de protocolo y espera a `CollectProtocolFee`. Ambos contadores ya están excluidos de la vista del vault de la curva, por lo que el precio del pool no se mueve. Derivación completa en [`products/cpmm/fees`](/es/products/cpmm/fees#protocol-share-of-the-creator-fee).

**Errores comunes** — `NoFeeCollect` cuando ambos contadores del creador son cero (verificado antes de la división), `InvalidInput` (`6003`) si la `share_rate` resuelta excede `1_000_000`, `MathOverflow` (`6011`) si registrar la parte causaría desbordamiento en `protocol_fees_token_*`, y error `ConstraintSeeds` de Anchor si `creator_fee_share` no es la PDA canónica.

## `CollectCreatorFeePermissionless`

Cualquiera puede activar la recopilación de comisiones del creador. La instrucción siempre envía la parte del creador a las cuentas de token asociadas canónicas propiedad de `pool_state.pool_creator`; el llamador no puede elegir otro creador o destino. Si falta alguna ATA, el pagador financia su creación.

El `CollectCreatorFee` original sigue siendo llamable, por lo que un creador que quiera firmar su propia recopilación aún puede.

**Argumentos** — ninguno.

**Cuentas**

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `payer` | W | S | Cualquier firmante; financia ATAs de creador faltantes. |
| 2 | `creator` |   |   | Debe ser igual a `pool_state.pool_creator`; no firma. |
| 3 | `authority` |   |   | PDA de autoridad global de vault de CPMM. |
| 4 | `pool_state` | W |   | Contiene los contadores de comisión del creador acumulados. |
| 5 | `token_0_vault` | W |   | Debe coincidir con el vault de token 0 del pool. |
| 6 | `token_1_vault` | W |   | Debe coincidir con el vault de token 1 del pool. |
| 7 | `vault_0_mint` |   |   | Debe coincidir con `token_0_vault.mint`. |
| 8 | `vault_1_mint` |   |   | Debe coincidir con `token_1_vault.mint`. |
| 9 | `creator_token_0` | W |   | ATA canónica del creador para `vault_0_mint`; creada si falta. |
| 10 | `creator_token_1` | W |   | ATA canónica del creador para `vault_1_mint`; creada si falta. |
| 11 | `token_0_program` |   |   | SPL Token o Token-2022, coincidiendo con token 0. |
| 12 | `token_1_program` |   |   | SPL Token o Token-2022, coincidiendo con token 1. |
| 13 | `associated_token_program` |   |   | Crea una ATA de destinatario faltante. |
| 14 | `system_program` |   |   | Financia la creación de cuentas desde `payer`. |
| 15 | `amm_config` |   |   | **Agregada 2026-09-19**, añadida después de `system_program`. Restringida `address = pool_state.amm_config`. |
| 16 | `creator_fee_share` |   |   | **Agregada 2026-09-19**, añadida al final. Misma PDA y misma regla de existencia opcional que en `CollectCreatorFee`. |

<Warning>
  Las dos nuevas cuentas se **añaden después de `system_program`**, no se insertan. Cada cuenta desde `payer` hasta `system_program` conserva la posición que tenía antes de la actualización, por lo que la ruptura es limpia: una transacción construida contra el diseño de catorce cuentas previo a la actualización no malinterpreta un vault como una cuenta de configuración — simplemente pasa muy pocas cuentas y Anchor la rechaza con `AccountNotEnoughKeys` (`3005`) antes de que se ejecute cualquier restricción. Las cuentas siguen siendo obligatorias, así que añade ambas y actualiza el IDL; no hay ruta de compatibilidad para el diseño anterior.
</Warning>

**Efecto** — idéntico a `CollectCreatorFee` arriba: la parte se resuelve desde `creator_fee_share` o `amm_config`, la parte del protocolo se registra en `protocol_fees_token_{0,1}`, la parte del creador se transfiere a las ATAs del creador, ambos contadores del creador se ponen a cero, y `recent_epoch` se actualiza. Devuelve `NoFeeCollect` cuando ambos contadores son cero.

## `UpdatePoolStatus`

Pausa o reanuda operaciones individuales en un pool. El campo `status` es una máscara de bits:

| Bit | Bandera | Efecto cuando está establecida |
|-----|------|-----------------|
| 0 | `DEPOSIT_DISABLED` | `Deposit` rechaza con `NotApproved`. |
| 1 | `WITHDRAW_DISABLED` | `Withdraw` rechaza. |
| 2 | `SWAP_DISABLED` | `SwapBaseInput` / `SwapBaseOutput` rechazan. |

**Argumentos**

```
status: u8      // nueva máscara de bits
```

**Cuentas**

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `authority` |   | S | Debe coincidir con la clave de administrador en el programa CPMM. |
| 2 | `pool_state` | W |   |

La clave de administrador es una clave pública **compilada en el programa** (`crate::admin::ID`), no la autoridad de actualización de BPF — cambiarla requiere una actualización del programa. Consulta [`reference/program-addresses`](/es/reference/program-addresses) para el valor y [`security/admin-and-multisig`](/es/security/admin-and-multisig) para quién la posee.

## `CreateAmmConfig`

Crea un nuevo nivel de comisión.

**Argumentos**

```
index:             u16
trade_fee_rate:    u64
protocol_fee_rate: u64
fund_fee_rate:     u64
create_pool_fee:   u64
creator_fee_rate:  u64
```

**Cuentas**

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `owner` | W | S | Administrador. |
| 2 | `amm_config` | W |   | `init`ializada aquí. |
| 3 | `system_program` |   |   |

**Precondiciones**

- No existe `AmmConfig` con el mismo `index`.
- `protocol_fee_rate + fund_fee_rate <= FEE_RATE_DENOMINATOR_VALUE`.

<Note>
  **Cambiado en 2026-09: los propietarios de comisiones de la nueva configuración ya no provienen del firmante.** `create_amm_config` ahora escribe el `protocol_fee_owner::ID` codificado del programa en `protocol_owner` y `fund_fee_owner::ID` en `fund_owner`, en lugar de copiar la clave del firmante administrador en ambos. Las direcciones están en [`reference/program-addresses`](/es/reference/program-addresses#cpmm-fee-owner-wallets).

  Consecuencias: las comisiones en una `AmmConfig` recién creada van a las billeteras de comisión dedicadas en lugar de la del administrador. El administrador sigue siendo un firmante aceptado *para la recopilación* — `CollectProtocolFee` / `CollectFundFee` aceptan `amm_config.protocol_owner` / `fund_owner` **o** `crate::admin::ID` — por lo que nada tiene que rotarse para barrer; lo que cambió es solo dónde van los ingresos por defecto. **Las cuentas `AmmConfig` existentes no se reescriben** — lo que se almacena en ellas aún rige, así que siempre lee `protocol_owner` / `fund_owner` de la cuenta en lugar de asumir ninguno de los valores. Los parámetros `3` y `4` de `UpdateAmmConfig` aún los rotan.
</Note>

## `UpdateAmmConfig`

Cambia las tasas de comisión o la propiedad en una `AmmConfig` existente. Toma un `param: u8` (qué campo actualizar) y un `value: u64`. La tabla de distribución completa:

- `param = 0` → `trade_fee_rate` (afirma `trade_fee_rate + creator_fee_rate < 1_000_000`)
- `param = 1` → `protocol_fee_rate` (afirma `≤ 1_000_000` y `+ fund_fee_rate ≤ 1_000_000`)
- `param = 2` → `fund_fee_rate` (afirma `≤ 1_000_000` y `+ protocol_fee_rate ≤ 1_000_000`)
- `param = 3` → `protocol_owner`. La nueva clave **no** está en `value`: apéndala como `remaining_accounts[0]` (solo lectura está bien). No debe ser la clave pública predeterminada, y omitir la cuenta entra en pánico en un `unwrap()`.
- `param = 4` → `fund_owner`. Mismo mecanismo que `3`.
- `param = 5` → `create_pool_fee`
- `param = 6` → `disable_create_pool` (cualquier `value` distinto de cero deshabilita)
- `param = 7` → `creator_fee_rate` (afirma `creator_fee_rate + trade_fee_rate < 1_000_000`)
- `param = 8` → `creator_fee_share_rate` (afirma `≤ 1_000_000`). Agregada 2026-09-19. La parte predeterminada del protocolo **de la comisión del creador** en este nivel; consulta [`products/cpmm/fees`](/es/products/cpmm/fees#protocol-share-of-the-creator-fee). No está relacionada con `protocol_fee_rate`, que divide la comisión de intercambio.

Cualquier otro `param` devuelve `InvalidInput`.

Los cambios son firmados por el administrador y afectan **cada pool vinculado a esta `AmmConfig`** en el próximo intercambio. Sin migración; los pools simplemente leen los nuevos valores.

## `CreateCreatorFeeShare`

Establece una parte de protocolo personalizada de la comisión del creador para un par `(creator, amm_config)`, anulando `AmmConfig.creator_fee_share_rate` para cada pool que ese creador posee en ese nivel de comisión. Agregada en la actualización de comisión del creador 2026-09-19.

**Argumentos**

```
share_rate: u64   // parte del protocolo DE la comisión del creador, sobre FEE_RATE_DENOMINATOR = 1_000_000
```

**Cuentas**

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `owner` | W | S | Debe ser el administrador del programa CPMM **o** el propietario dedicado de comisión del creador — consulta [`reference/program-addresses`](/es/reference/program-addresses#cpmm-creator-fee-share-authority). Cualquier otro firmante falla con `InvalidOwner` (`6001`). Paga la renta. |
| 2 | `creator` |   |   | El creador del pool al que se aplica la tasa. Sin verificar — no tiene que ser un creador de pool existente, y no firma. |
| 3 | `amm_config` |   |   | El nivel de comisión al que se aplica la tasa. |
| 4 | `creator_fee_share` | W |   | `init`ializada aquí en `["creator_fee_share", creator, amm_config]`, `space = 145`. |
| 5 | `system_program` |   |   | |

**Precondiciones**

- `share_rate <= 1_000_000`, de otro modo `InvalidInput` (`6003`).
- La PDA no debe existir ya — el `init` de Anchor falla en una segunda llamada para el mismo par. Para cambiar una tasa, cierra la cuenta y créala de nuevo.

**Postcondiciones**

- `creator_fee_share` almacena `bump`, `creator`, `amm_config` y `share_rate`.
- Cada `CollectCreatorFee` / `CollectCreatorFeePermissionless` posterior en un pool creado por `creator` bajo `amm_config` resuelve la parte desde esta cuenta en lugar de la configuración.

<Note>
  El creador del pool no es parte de esta instrucción y no la firma. La tasa se lee en el momento de la recopilación, por lo que una anulación creada después de que las comisiones ya se hayan acumulado se aplica a ese saldo acumulado también.
</Note>

**Argumentos** — ninguno.

**Cuentas**

| 1 | `owner` | W | S | Los mismos dos firmantes aceptados que `CreateCreatorFeeShare`; recibe la renta. |
| 2 | `creator` |   |   | El creador del pool al que se aplicaba la tasa. |
| 3 | `amm_config` |   |   | El nivel de comisión al que se aplicaba la tasa. |
| 4 | `creator_fee_share` | W |   | Cerrada a `owner`. Debe ser la PDA canónica para el par. |
| 5 | `system_program` |   |   | |

**Postcondiciones**

- Las recopilaciones para ese par resuelven la parte desde `amm_config.creator_fee_share_rate` nuevamente — que es `0` a menos que un administrador haya establecido el parámetro `8` de `UpdateAmmConfig`.

## `CollectExcessLamports`

Barrido de administrador de lamports que se sientan por encima del mínimo exento de renta en cuentas que CPMM controla. Agregada en la actualización 2026-09 para que el protocolo pueda reclamar el exceso de financiamiento que la [reducción de renta SIMD-0437](/es/solana-fundamentals/rent-and-reclaimable-rent) deja en cuentas creadas antes de cada paso.

Solo se mueve el exceso. Los saldos de tokens, datos de cuentas, propietarios, estado del pool y la curva no se tocan, y la instrucción es una no-op contra una cuenta ya en su mínimo — por lo que es seguro volver a ejecutar después de cada paso de implementación.

**Argumentos** — ninguno.

**Cuentas**

| # | Nombre | W | S | Notas |
|---|------|---|---|-------|
| 1 | `collect_lamports_wallet` | W | S | Destino para cada lamport barrido. Debe ser el administrador del programa CPMM o la billetera dedicada de recopilación de lamports — consulta [`reference/program-addresses`](/es/reference/program-addresses#excess-lamports-collection-wallets). Cualquier otro firmante falla con `InvalidOwner`. |
| 2 | `authority` |   |   | La PDA de autoridad de vault y mint LP de CPMM en semilla `[b"vault_and_lp_mint_auth_seed"]`. Firma los CPIs del programa de token. |
| 3 | `token_program` |   |   | SPL Token. |
| 4 | `token_program_2022` |   |   | Token-2022. Ambos son requeridos incondicionalmente; el programa elige por cuenta de origen. |
| 5.. | `remaining_accounts` | W |   | `M` cuentas de origen para barrer, cualquier número, cualquier orden. |

<Note>
  **Corrección de orden, 2026-09-19.** El programa ahora hace dos pasadas sobre `remaining_accounts` — cada CPI del programa de token primero, luego los débitos directos de PDAs propiedad de CPMM. Intercalarlos abortaba con el `UnbalancedInstruction` del tiempo de ejecución ("la suma de saldos de cuentas antes y después de la instrucción no coinciden") siempre que una PDA se debitaba antes de un CPI, porque los cambios de lamports pendientes del llamador solo se vacían en cuentas que un CPI realmente lleva. Los llamadores no tienen que agrupar u ordenar la lista ellos mismos.
</Note>

**Cómo se maneja cada cuenta de origen**

El programa distribuye en el `owner` de la cuenta de origen:

| Propietario de cuenta de origen | Manejo |
|---|---|
| SPL Token o Token-2022, cuenta de token no nativa o mint — vaults de pool y mints LP | CPI `WithdrawExcessLamports` (discriminante del programa de token `38`), firmado por `authority`. |
| SPL Token o Token-2022, **nativa** (wSOL) cuenta de token | `WithdrawExcessLamports` rechaza cuentas nativas. El programa CPIs `SyncNative`, mide cuánto creció el `amount` envuelto, `UnwrapLamports` (discriminante `45`) para exactamente ese delta, luego requiere que el saldo envuelto sea igual a su valor pre-sincronización — de otro modo `LamportsCalculateError` (`6015`). Un vault de pool del lado SOL por lo tanto mantiene su liquidez completa. |
| El programa CPMM en sí — `PoolState`, `AmmConfig`, `ObservationState`, `Permission`, `SupportMintAssociated` | El programa debita la cuenta directamente hasta `rent.minimum_balance(data_len)`. |
| Cualquier otra cosa | **Omitida silenciosamente.** Sin error, sin lamports movidos. |

Porque toma una lista `remaining_accounts` sin límites, el tamaño de la transacción es el límite real — la misma restricción que el barrido del lado de la billetera descrito en [`solana-fundamentals/rent-and-reclaimable-rent`](/es/solana-fundamentals/rent-and-reclaimable-rent#batching-how-many-fit-in-one-transaction).

**Errores comunes** — `InvalidOwner` (`6001`, firmante incorrecto), `LamportsCalculateError` (`6015`, el viaje de ida y vuelta de wSOL no neteó a cero), e `InsufficientFunds` de la ruta propiedad del programa cuando una cuenta tiene menos que su propio mínimo de renta.

**Sin constructor SDK.** `@raydium-io/raydium-sdk-v2` no envía un constructor para esta instrucción, ni tampoco el repositorio `raydium-sdk-V2-demo` — es una ruta de administrador. Codifícala a mano, de la manera que el barrido del lado de la billetera en [`solana-fundamentals/rent-and-reclaimable-rent`](/es/solana-fundamentals/rent-and-reclaimable-rent#building-the-instruction) hace para la instrucción del programa de token.
