<Info>
  Raydium's product programs are independent codebases, but they were designed against a shared set of conventions. This page is the canonical reference for those conventions. Per-product chapters describe how the conventions are *instantiated* in their accounts; this page describes the conventions themselves.
</Info>

## What "shared" means here

Three flavors of sharing run through the codebase:

- **Convention sharing.** Programs use similar PDA, fee-accounting, and observation patterns, but each implements them with its own state and seeds.
- **Account sharing.** A handful of accounts are *literally* the same record across many pools (the global authority PDA in CPMM, the AmmConfig accounts).
- **Off-chain sharing.** API v3 and the TypeScript SDK serve multiple Raydium products. The Transaction API uses a separate host for swap quotes and transaction building.

The five primitives below cover everything that crosses program boundaries.

## 1. Authority PDAs

Raydium programs use PDAs as token vault authorities. Depending on the program, an authority PDA can be shared globally or derived for each pool or farm. Users never hold vault authority directly. A program invokes the authority PDA only when a valid instruction moves funds out.

Authority derivation is program-specific; the seeds and scope differ:

| Program | Authority PDA seeds | Notes |
|---------|---------------------|-------|
| **AMM v4** | `[b"amm authority"]` | **Single PDA shared by all AMM v4 pools.** Its bump is mirrored on every `AmmInfo` as `nonce`. |
| **CPMM** | `[b"vault_and_lp_mint_auth_seed"]` | **Single PDA shared by all CPMM pools.** No pool-specific seed. |
| **CLMM** | `pool_state` PDA seeds | Per-pool. Each pool's `pool_state` PDA is the token-account authority for its vaults. The program uses that PDA's seeds to authorize transfers out. CLMM has no program-wide vault-authority PDA. |
| **Farm v3 / v5 / v6** | `[farmId]` | Per-farm. The PDA owns staking + reward vaults for that farm. |
| **LaunchLab** | `[b"vault_auth_seed"]` | **Single PDA shared by all launches.** Two further global PDAs, `[b"platform_fee_vault_auth_seed"]` and `[b"creator_fee_vault_auth_seed"]`, own the aggregated fee vaults. |

A few things follow from this:

- For AMM v4, CPMM and LaunchLab the authority PDA is **a global account** — every pool or launch of that type uses it. If you are CPI-ing into CPMM you need it once, not per pool.
- CLMM has no program-wide authority PDA. Each pool's `pool_state` PDA is the authority for its vaults, and the program uses the pool PDA's seeds to authorize transfers out.
- For per-farm authorities, you derive the PDA from the farm ID. The SDK does this in `getPoolKeys` / `getFarmKeys`; if you are integrating directly, you derive with `findProgramAddressSync`.
- **Vault ownership cannot be changed.** Once a token account is created with the authority PDA as owner, only that PDA — invoked by the program — can transfer out. There is no admin override.

For the exact seeds and ATA layouts per program, see [`products/cpmm/accounts`](/products/cpmm/accounts), [`products/clmm/accounts`](/products/clmm/accounts), [`products/amm-v4/accounts`](/products/amm-v4/accounts), [`products/farm-staking/accounts`](/products/farm-staking/accounts), [`products/launchlab/accounts`](/products/launchlab/accounts).

## 2. Admin and config accounts

CPMM and CLMM pools reference an **`AmmConfig`** for settings such as trade, protocol, and fund fee rates. The programs use different config layouts. Pools use the config they reference, so an authorized update can change settings used by existing pools.

```rust
// CPMM AmmConfig (abridged; the CLMM layout differs)
pub struct AmmConfig {
    pub bump: u8,
    pub disable_create_pool: bool,
    pub index: u16,
    pub trade_fee_rate: u64,
    pub protocol_fee_rate: u64,
    pub fund_fee_rate: u64,
    pub create_pool_fee: u64,
    pub protocol_owner: Pubkey,
    pub fund_owner: Pubkey,
    pub creator_fee_rate: u64,
    pub creator_fee_share_rate: u64,
    pub padding: [u64; 14],
}
```

**Rules of the road:**

- **Config fields differ by program.** `disable_create_pool` and the creator-fee fields shown above are CPMM fields, not shared CLMM fields.
- **Pools use their referenced config.** Changing fee settings in a config can affect existing pools that reference it.
- **In CPMM, `protocol_owner` and `fund_owner` authorize fee collection.** They are not recipient addresses. Collection instructions receive destination token accounts separately.

AMM v4 also has an `AmmConfig`, but it serves a different purpose. AMM v4 stores swap-fee parameters on each pool, and an authorized `SetParams` instruction can update them. Farm and LaunchLab have their own config accounts, covered in their respective chapters.

A complete table of who can change what is in [`security/admin-and-multisig`](/security/admin-and-multisig). Current user-facing fee splits are in [`ray/protocol-fees`](/ray/protocol-fees).

## 3. The protocol / fund / creator fee split

CPMM and CLMM account for swap fees differently:

- **CPMM.** The trade fee is split between LPs, protocol, and fund. Protocol and fund rates are fractions of the trade fee; the remaining share stays in the pool for LPs. A pool can also enable an optional creator fee, charged separately from the trade fee. At collection, a configured share of creator fees may go to the protocol.
- **CLMM.** The trade fee is split between LPs, protocol, and fund. The program tracks the LP share through fee-growth accumulators and settles it to positions. CLMM does not use CPMM's constant-product `k` accounting or its creator-fee setting.
- **Collection.** CPMM checks the authorized protocol or fund collector against its `AmmConfig`; collection instructions receive destination token accounts separately. The creator can collect creator fees, or any payer can trigger the permissionless path, which sends the creator's share to the creator's canonical token accounts.

AMM v4 tracks LP and protocol fees. Its fee parameters are stored per pool and can be changed through an authorized instruction. For per-program details, see [`products/cpmm/fees`](/products/cpmm/fees) and [`products/clmm/fees`](/products/clmm/fees).

Specific rates are in [`reference/fee-comparison`](/reference/fee-comparison) and [`ray/protocol-fees`](/ray/protocol-fees).

## 4. Observation accounts

CPMM and CLMM keep bounded observation histories for each pool, but record different values: CPMM accumulates token prices, while CLMM accumulates ticks. The programs update observation state during swaps, but only record new ring-buffer entries when their update conditions are met. The available history limits which time windows readers can use to calculate an average. These observations do not by themselves guarantee a safe oracle price.

```rust
// CPMM ObservationState (abridged)
pub struct ObservationState {
    pub initialized: bool,
    pub observation_index: u16,            // next slot to overwrite
    pub pool_id: Pubkey,
    pub observations: [Observation; OBSERVATION_NUM],
    pub padding: [u64; 4],
}

pub struct Observation {
    pub block_timestamp: u64,
    pub cumulative_token_0_price_x32: u128,  // sum of (price × dt) since init
    pub cumulative_token_1_price_x32: u128,
}
```

For CPMM, readers can difference cumulative prices between observations and divide by the elapsed time. For CLMM, readers can difference cumulative ticks, calculate an average tick, and convert it to a price. Check the observation interval and available history before using either value.

AMM v4 has no observation account. Integrators that need historical AMM v4 prices must derive them from another data source.

Layout details and indexing math are in [`products/cpmm/accounts`](/products/cpmm/accounts) and [`products/clmm/accounts`](/products/clmm/accounts).

## 5. API, SDK, and IDL

These tools have different roles:

- **API v3** — `https://api-v3.raydium.io` provides indexed pool and product data.
- **Transaction API** — `https://transaction-v1.raydium.io` is a separate host for swap quotes and transaction building.
- **TypeScript SDK** — `@raydium-io/raydium-sdk-v2` builds transactions. Its `execute()` method can sign and submit them when you provide a supported signer or wallet.
- **IDL registry** — The [`raydium-idl`](https://github.com/raydium-io/raydium-idl) repository publishes IDLs for specific programs, including CPMM, CLMM, and LaunchLab. It is not a registry of every Raydium program.

API data is an off-chain view and may lag behind chain state. Before building a transaction, fetch from Solana RPC the account state that the instruction depends on. Do not assume indexed API values are current.

The full reference is in [`sdk-api/`](/sdk-api), with the IDL surface specifically in [`sdk-api/anchor-idl`](/sdk-api/anchor-idl).

## 6. Indexers and price feeds

API responses provide an off-chain view of pools, farms, and prices. Indexed data may lag behind on-chain state, so read the relevant accounts from Solana RPC when a transaction depends on current values. Treat API prices as display or analysis data unless the endpoint documents stronger guarantees. Do not assume an observation-derived average is a safe oracle input; assess its available history and update cadence for your use case.

## What is not shared

Worth listing explicitly, because new readers often assume more sharing than exists:

- **A CPMM swap does not route through CLMM or AMM v4.** Other program flows can invoke an AMM; for example, LaunchLab's graduation path creates a CPMM pool.
- **No shared upgrade authority across programs.** Each on-chain program has its own program-upgrade key (a 3/4 multisig plus a 24h timelock). They are not linked.
- **No shared state between farms and AMMs.** A farm doesn't know which LP it stakes is from a CPMM pool, a CLMM-position-NFT-mint, or an unrelated SPL token. The farm program treats the staking mint as opaque.
- **No oracle dependency.** Pricing is on-chain reserves. There is no Pyth/Switchboard fallback; the AMM does not check an oracle before clearing.
